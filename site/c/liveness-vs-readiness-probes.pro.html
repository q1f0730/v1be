存活与就绪探针分野

Liveness vs Readiness Probes

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

存活探针（Liveness Probe）与就绪探针（Readiness Probe）是 Kubernetes 的两类健康检查。存活探针回答进程是否卡死、需要重启；就绪探针回答此刻能否接收流量、是否应在 Service 端点中。二者属编排层，配合启动探针（Startup Probe）区分启动慢与已挂掉，决定重启与摘流。

⚙️ 02 · 原理
  1. 1

    kubelet 按 periodSeconds 周期执行探针，方式可以是 HTTP GET、TCP 连接、gRPC 或 exec 命令。

  2. 2

    启动探针存在时，在其成功之前存活和就绪探针都不执行，给慢启动应用留时间。

  3. 3

    存活探针连续失败达到 failureThreshold，kubelet 杀掉并按重启策略重启容器。

  4. 4

    就绪探针失败时容器不被重启，但其 Pod 从 Service 的端点列表中移除，不再接收流量。

  5. 5

    就绪恢复后重新加入端点；滚动发布也依赖就绪状态决定推进节奏。

🔤 03 · 术语
启动探针 (Startup Probe)
启动阶段专用探针，成功前屏蔽存活与就绪探针。
端点 (EndpointSlice)
Service 后端可接流量的 Pod 地址集合。
失败阈值 (failureThreshold)
连续失败多少次判定探针失败，默认 3。
初始延迟 (initialDelaySeconds)
容器启动后多久开始首次探测。
CrashLoopBackOff
容器反复崩溃或被杀后，重启间隔递增的状态。
💻 04 · 代码
三种探针配置yaml
containers:
  - name: api
    image: example/api:1.0
    ports: [{ containerPort: 8080 }]
    startupProbe:            # 启动最多 30×10=300 秒
      httpGet: { path: /livez, port: 8080 }
      failureThreshold: 30
      periodSeconds: 10
    livenessProbe:           # 只查进程自身，失败则重启
      httpGet: { path: /livez, port: 8080 }
      periodSeconds: 10
      timeoutSeconds: 2
      failureThreshold: 3
    readinessProbe:          # 能否接流量，失败则摘流不重启
      httpGet: { path: /readyz, port: 8080 }
      periodSeconds: 5
      failureThreshold: 2

启动探针兜住慢启动，存活探针管重启，就绪探针管是否进入负载均衡。

📊 05 · 参数对比

三类探针对照

探针回答的问题失败后果
Startup启动完成了吗超过阈值后重启容器
Liveness进程卡死了吗重启容器
Readiness现在能接流量吗从 Service 端点移除，不重启
⚖️ 06 · 方案取舍

就绪探针检查关键依赖

优点依赖不可用时自动摘流

代价共享依赖故障会让所有 Pod 同时摘流

适用依赖是实例私有的，如本地缓存加载

存活探针只检查进程

优点避免依赖抖动引发重启风暴

代价无法发现依赖导致的不可用

适用几乎总是推荐

不配存活探针

优点零误杀风险

代价死锁进程不会被自动恢复

适用进程卡死后会自行退出的应用

🕳️ 07 · 常见坑

  • ✗存活探针检查数据库，数据库抖动导致全部 Pod 被重启。

    ✓存活探针只检查进程能否响应，不调用外部依赖。

  • ✗存活和就绪用同一个端点同一参数。

    ✓分开端点，存活阈值更宽松，就绪更敏感。

  • ✗慢启动应用用很大的 initialDelaySeconds 硬撑。

    ✓改用启动探针，启动完成后再启用存活探针。

  • ✗探针超时用默认 1 秒，GC 停顿时误判失败。

    ✓根据实际延迟设置 timeoutSeconds 和阈值。

☑️ 08 · 检查清单
🎤 09 · 面试追问
就绪探针应不应该检查数据库？

要看依赖是否共享。若所有 Pod 共用一个数据库，它故障时全部 Pod 都变成未就绪，Service 无后端，用户反而拿不到友好错误。通常就绪只检查实例自身准备状态，依赖故障交给熔断和降级处理。

为什么需要启动探针？

有些应用启动需要较长时间加载。只用存活探针时，要么初始延迟设很长导致真挂掉也发现得慢，要么启动中就被误杀陷入 CrashLoopBackOff。启动探针把启动期单独处理，成功后再交给存活探针。

探针失败后流量多久会停止？

大约是 periodSeconds 乘以 failureThreshold，再加上端点更新传播到 kube-proxy 或负载均衡器的时间。因此停机时应先让就绪失败或在 preStop 中等待，避免请求打到正在退出的 Pod。
