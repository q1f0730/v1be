模块化单体

Modular Monolith

🧸 回到小白版

📐 01 · 定义

模块化单体（Modular Monolith）是作为单个可部署单元运行、但内部按业务能力划分为边界清晰模块的架构。每个模块拥有自己的领域逻辑和数据，只通过显式的公开接口或进程内事件与其他模块交互，并借助工具强制依赖规则。它保留单体的部署与调试简单性，又获得微服务式的边界，是在拆分微服务前更务实的选择。

⚙️ 02 · 原理
  1. 1

    按业务能力（限界上下文）划分模块，如订单、计费、商品，而不是按技术层（controller、service）划分。

  2. 2

    每个模块定义公开 API（接口、门面或事件），内部实现对外不可见。

  3. 3

    数据归属明确：模块只访问自己的表或 schema，不跨模块直接查询或 JOIN 他人数据。

  4. 4

    通过静态检查工具（如 import-linter、Spring Modulith、ArchUnit）在 CI 中强制模块依赖规则。

  5. 5

    当某模块确有独立扩展或部署需求时，因边界已清晰，可较低成本地将其抽取为独立服务。

🔤 03 · 术语
限界上下文 (Bounded Context)
领域模型适用的边界，常作为模块划分依据。
模块公开接口 (Module API)
模块对外暴露的唯一访问入口。
架构适应度函数 (Fitness Function)
自动化检查架构约束是否被遵守的测试。
进程内事件 (In-process Event)
模块间通过事件解耦，但仍在同一进程内传递。
分布式单体 (Distributed Monolith)
拆成多个服务却仍紧密耦合，兼具两者缺点的反模式。
💻 04 · 代码
用 import-linter 强制模块边界text
# .importlinter （pip install import-linter，运行 lint-imports）
[importlinter]
root_package = shop

# 业务模块之间互不直接导入
[importlinter:contract:modules-independent]
name = Business modules are independent
type = independence
modules =
    shop.orders
    shop.billing
    shop.catalog

# 每个模块内部分层：api 可依赖 domain，反之不行
[importlinter:contract:orders-layers]
name = Orders layering
type = layers
layers =
    shop.orders.api
    shop.orders.domain
    shop.orders.infra

在 CI 中运行 lint-imports，违反模块独立性或分层规则即失败；模块间协作改走共享事件或接口包。

三种架构对比

维度传统单体模块化单体微服务

调用方式任意函数调用公开接口/进程内事件网络调用
运维复杂度低低高

⚖️ 06 · 方案取舍

模块化单体

优点部署简单、事务简单、重构成本低

代价无法按模块独立扩缩容与部署

适用中小团队、业务边界仍在演化

微服务

优点独立部署与扩展，技术栈自治

代价分布式复杂度、运维成本高

适用大团队、模块需独立扩展

传统单体

优点起步最快

代价长期易失控、难拆分

适用原型与短期项目

🕳️ 07 · 常见坑

  • ✗按技术层划分模块，业务逻辑散落各处

    ✓按业务能力划分，每个模块内部再分层

  • ✗模块间共享数据库表并相互 JOIN

    ✓每张表只归一个模块，跨模块数据经接口获取

  • ✗只靠约定维持边界，日久失效

    ✓在 CI 中用工具强制依赖规则

  • ✗为“未来可能拆分”过早引入消息中间件

    ✓先用进程内接口或事件，真正拆分时再替换实现

🎤 09 · 面试追问
模块化单体和微服务的核心区别是什么？

两者都强调按业务划分的清晰边界，区别在于部署与通信方式：模块化单体是一个进程，模块间用函数调用或进程内事件，共享一次部署和数据库实例；微服务各自部署，通过网络通信，各自拥有数据存储，获得独立扩展能力，也承担分布式系统的全部复杂度。

什么时候应该从模块化单体拆出微服务？

当某个模块有明显不同的扩缩容需求、发布节奏或可靠性要求，或团队规模增长到需要独立交付时。若边界已清晰，拆分主要是把进程内调用替换为网络调用并迁移数据，风险可控。

为什么它对 AI 辅助开发友好？

清晰的模块边界缩小了每次改动需要理解的上下文范围，Agent 可以只读取一个模块及其公开接口；CI 中的依赖检查还能自动拦截 AI 生成的越界引用，减少架构腐化。
