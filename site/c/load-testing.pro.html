📐 01 · 定义

负载测试（Load Testing）是用工具模拟大量并发用户或请求，测量系统在预期和极限负载下的吞吐、延迟、错误率与资源使用的性能测试。它属于发布前验证和容量规划环节，常细分为基准、负载、压力、尖峰、浸泡等类型，用于找出容量拐点和瓶颈，并为自动扩缩容、限流阈值和 SLO 提供依据。

⚙️ 02 · 原理
  1. 1

    明确目标：要验证的场景、预期峰值流量、延迟与错误率阈值，最好对齐 SLO。

  2. 2

    编写脚本模拟真实用户行为，包括请求比例、思考时间、登录态和参数化数据。

  3. 3

    在与生产相近的环境中按阶段加压，如逐步爬升、保持、再回落，或突然尖峰。

  4. 4

    同时采集客户端指标和服务端指标，如 CPU、内存、连接数、数据库慢查询。

  5. 5

    分析延迟开始急剧上升或错误出现的拐点，定位瓶颈，优化后回归测试。

🔤 03 · 术语
压力测试 (Stress Test)
超出预期负载直到系统失效，观察极限与失效方式。
浸泡测试 (Soak Test)
中等负载长时间运行，发现内存泄漏等渐进问题。
尖峰测试 (Spike Test)
负载瞬间暴涨，检验扩缩容与限流反应。
虚拟用户 (Virtual User, VU)
负载工具中模拟单个用户并发执行脚本的单元。
协调遗漏 (Coordinated Omission)
压测客户端因等待慢响应而少发请求，导致延迟被低估。
💻 04 · 代码
k6 分阶段负载脚本javascript
import http from "k6/http";
import { check, sleep } from "k6";

export const options = {
  stages: [
    { duration: "2m", target: 100 },  // 2 分钟爬升到 100 个虚拟用户
    { duration: "5m", target: 100 },  // 保持 5 分钟
    { duration: "1m", target: 0 },    // 回落
  ],
  thresholds: {
    http_req_duration: ["p(95)<500"], // 95% 请求低于 500ms
    http_req_failed: ["rate<0.01"],   // 错误率低于 1%
  },
};

export default function () {
  const res = http.get("https://staging.example.com/api/products");
  check(res, { "status is 200": (r) => r.status === 200 });
  sleep(1); // 模拟用户思考时间
}

用 k6 run script.js 执行；阈值不达标时命令以非零码退出，可直接接入 CI。

⚖️ 06 · 方案取舍

在预发环境压测

优点不影响用户

代价规模与数据难以完全一致

适用常规发布前验证

生产环境压测

优点结果最真实

代价有影响用户的风险，需隔离标记

适用大促前容量确认

开环到达率模型

优点能反映真实到达流量，避免协调遗漏

代价需更多压测机资源

适用测延迟与过载行为

🕳️ 07 · 常见坑

  • ✗只压单个接口，没有模拟真实的请求组合。

    ✓按线上流量比例编排多场景脚本。

  • ✗压测机自身 CPU 或带宽先打满，结果反映的是客户端瓶颈。

    ✓监控压测机资源，必要时分布式压测。

  • ✗所有虚拟用户用同一账号和参数，缓存命中率虚高。

    ✓参数化数据，覆盖缓存未命中路径。

  • ✗只看平均延迟。

    ✓关注 p95、p99 和错误率，并对齐 SLO。

🎤 09 · 面试追问
负载测试和压力测试有什么区别？

负载测试在预期负载范围内验证系统是否满足性能目标；压力测试持续加压超出预期，直到出现失败，目的是找到极限、观察失效方式是否优雅以及能否恢复。两者回答的问题不同，通常都要做。

什么是协调遗漏，如何避免？

闭环压测中，客户端要等上一个响应才发下一个请求，服务变慢时发出的请求也变少，慢的时段被少采样，延迟被低估。使用按固定到达率发请求的开环模型，或使用会做校正的工具。

如何从压测结果确定扩缩容阈值？

找出单实例在满足延迟目标时能承受的最大吞吐和对应 CPU 或并发，留出余量作为扩缩容目标值；再结合实例启动时间，确保负载上升时新实例能在饱和前就绪。
