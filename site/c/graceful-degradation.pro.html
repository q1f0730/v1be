优雅降级

Graceful Degradation

📐 01 · 定义

优雅降级（Graceful Degradation）是系统在部分组件故障或过载时，有计划地关闭或简化非核心功能，以保住核心功能可用的设计策略。它属于应用韧性层，与超时、熔断、负载卸载配合：依赖失败时返回缓存、默认值或简化结果，而不是整页报错。关键在于提前划分功能优先级并设计每种降级形态。

⚙️ 02 · 原理
  1. 1

    梳理功能，区分核心路径（登录、下单、支付）与可降级功能（推荐、评论、个性化）。

  2. 2

    为每个可降级依赖设计兜底：缓存旧数据、静态默认值、隐藏模块或简化计算。

  3. 3

    调用每个依赖时都设置超时并配熔断器，调用失败或熔断打开时自动走兜底逻辑。

  4. 4

    系统过载时通过功能开关主动关闭高成本功能，把释放出的资源留给核心路径。

  5. 5

    对降级状态打点监控并告警，依赖恢复后自动或手动退出降级，回到完整功能。

🔤 03 · 术语
兜底响应 (Fallback)
依赖失败时返回的替代结果，如缓存或默认值。
功能开关 (Feature Flag)
运行时开启或关闭功能的配置，可用于手动降级。
静态稳定 (Static Stability)
依赖失效时用既有数据继续工作，不依赖实时变更。
降级模式 (Degraded Mode)
系统以部分功能运行的状态，应对用户可见并有监控。
过时数据 (Stale Data)
超过正常新鲜度的缓存数据，降级时可接受的权衡。
💻 04 · 代码
推荐服务失败时兜底python
import logging
import requests

POPULAR_FALLBACK = ["sku-1001", "sku-1002", "sku-1003"]  # 预先算好的热门商品
log = logging.getLogger("home")

def get_recommendations(user_id: str) -> dict:
    try:
        r = requests.get(
            f"http://recommend:8080/users/{user_id}/recs",
            timeout=0.3,              # 非核心依赖：超时要短
        )
        r.raise_for_status()
        return {"items": r.json()["items"], "degraded": False}
    except requests.RequestException as e:
        log.warning("recs degraded: %s", e)  # 记录并计入降级指标
        return {"items": POPULAR_FALLBACK, "degraded": True}

# 首页照常渲染：推荐服务挂了，用户看到的是热门商品而不是 500

非核心依赖用短超时，失败时返回预计算的热门列表并标记 degraded 便于监控。

⚖️ 06 · 方案取舍

自动降级

优点响应快，无需人工

代价可能掩盖问题，需监控

适用依赖故障可明确检测

手动功能开关

优点可控，适合大范围调整

代价依赖值班反应速度

适用过载或计划内维护

返回旧数据

优点用户体验连续

代价数据可能不准确

适用对新鲜度要求不高

🕳️ 07 · 常见坑

  • ✗降级逻辑从未触发过，真出事时兜底代码本身报错。

    ✓通过故障注入或定期演练验证降级路径。

  • ✗非核心依赖超时与核心相同，拖慢整个页面。

    ✓非核心依赖设更短超时并可并行调用。

  • ✗降级后没有指标，几周都处于降级状态无人发现。

    ✓降级打点计数并告警。

  • ✗支付等核心路径也套用宽松兜底，产生错误交易。

    ✓核心写路径失败应明确报错，不伪造成功。

🎤 09 · 面试追问
降级和熔断有什么关系？

熔断决定何时停止调用故障依赖，降级决定停止调用后返回什么。熔断器打开时请求直接进入降级逻辑，返回缓存、默认值或隐藏功能，两者配合才能既保护系统又维持体验。

哪些功能不适合降级？

涉及资金、库存扣减、权限校验等需要强一致和正确性的路径。它们失败时应明确报错或排队重试，而不是返回假成功或过时结果，否则会造成资损或安全问题。

如何验证降级设计有效？

在测试或预发环境做故障注入，如让依赖超时、返回错误或断网，观察页面是否正常渲染、指标是否记录降级；生产中可在低峰期小范围演练，并检查核心 SLO 是否保持。
