死信队列 (DLQ)

Dead Letter Queues

📐 01 · 定义

死信队列（Dead Letter Queue, DLQ）是消息系统中的旁路队列，用来收纳超过最大重试次数、过期或被显式拒绝的消息。它属于消息中间件的可靠性层，目的是把失败消息从主流程隔离出来：主队列不被阻塞，失败数据也不丢失，可在排查后重放（redrive）。

⚙️ 02 · 原理
  1. 1

    消费者拉取消息并处理，失败时不确认（nack）或可见性超时到期，消息回到队列等待再次投递。

  2. 2

    中间件为每条消息累计投递次数，例如 SQS 的 ApproximateReceiveCount、RabbitMQ 的 x-delivery-count。

  3. 3

    投递次数超过 redrive 策略中的阈值（SQS 叫 maxReceiveCount）后，消息被转移到配置好的 DLQ。

  4. 4

    RabbitMQ 中消息被 reject 且 requeue=false、TTL 过期或队列超长时，会按死信交换机（DLX）规则路由。

  5. 5

    运维对 DLQ 深度设告警，排查根因、修复代码后，把消息重放回源队列或人工处理后丢弃。

🔤 03 · 术语
重驱策略 (Redrive Policy)
SQS 中把源队列与 DLQ 关联，并设定最大接收次数的配置。
死信交换机 (DLX)
RabbitMQ 中接收死信并按路由键转发到死信队列的交换机。
可见性超时 (Visibility Timeout)
消息被取走后对其他消费者隐藏的时长，超时未删除就会再次可见。
消息重放 (Redrive / Replay)
把 DLQ 中的消息移回源队列重新处理的操作。
消息保留期 (Retention Period)
消息在队列中保存的最长时间，过期即被删除，DLQ 也受其约束。
💻 04 · 代码
SQS 绑定死信队列python
import json
import boto3

sqs = boto3.client("sqs")

# 1. 创建死信队列并取得它的 ARN
dlq_url = sqs.create_queue(QueueName="orders-dlq")["QueueUrl"]
dlq_arn = sqs.get_queue_attributes(
    QueueUrl=dlq_url, AttributeNames=["QueueArn"]
)["Attributes"]["QueueArn"]

# 2. 源队列：同一条消息被接收 5 次仍未删除，就转入 DLQ
sqs.create_queue(
    QueueName="orders",
    Attributes={
        "RedrivePolicy": json.dumps({
            "deadLetterTargetArn": dlq_arn,
            "maxReceiveCount": "5",
        })
    },
)

用 boto3 为 SQS 标准队列配置 redrive 策略，超过 5 次接收即转入 DLQ。

📊 05 · 参数对比

主流中间件的死信实现

系统触发条件关键配置
Amazon SQS接收次数超过阈值RedrivePolicy.maxReceiveCount
RabbitMQreject 不重入队、TTL 过期、超长x-dead-letter-exchange
Azure Service Bus超过最大投递次数、过期等MaxDeliveryCount（默认 10）
Kafka无内置，由消费框架实现如 Kafka Connect 的 errors.deadletterqueue.topic.name
⚖️ 06 · 方案取舍

重试 N 次后进 DLQ

优点主队列不阻塞，失败可追溯

代价需要额外的告警和重放流程

适用绝大多数异步业务消息

失败直接丢弃

优点实现最简单，无积压

代价数据静默丢失，难以排查

适用可丢的遥测、心跳类消息

无限重试

优点不需要人工介入

代价坏消息会反复占用消费者

适用几乎不推荐，仅限确定会自愈的依赖

🕳️ 07 · 常见坑

  • ✗只配了 DLQ 却没有监控，几个月后才发现里面堆了上万条消息。

    ✓对 DLQ 可见消息数设告警阈值，大于 0 即通知负责人。

  • ✗DLQ 保留期和源队列一样短，排查时消息已过期删除。

    ✓DLQ 保留期设得比源队列长，SQS 最长可设 14 天。

  • ✗maxReceiveCount 设为 1，一次瞬时网络抖动就进死信。

    ✓给瞬时故障留余量，常见取 3–10 次并配合退避。

  • ✗修完 bug 一次性重放全部死信，打爆下游。

    ✓分批、限速重放，并先用少量消息验证修复。

🎤 09 · 面试追问
DLQ 和重试的关系是什么？

重试处理瞬时故障，DLQ 兜住重试也救不回来的消息。两者配合：先有限次数重试并退避，超过阈值转入 DLQ，避免坏消息无限占用消费者，同时保留数据用于排查和重放。

消息进了 DLQ 之后应该怎么处理？

先告警通知；按错误类型分组定位根因；区分代码 bug、脏数据和下游故障；修复后小批量重放验证，再限速全量重放；无法修复的记录原因后归档或丢弃。

Kafka 没有内置 DLQ，怎么实现？

在消费端捕获异常，超过重试次数后把原消息及错误信息写入单独的死信 topic，再提交位移继续消费。Kafka Connect、Spring Kafka 等框架提供了现成的死信配置。
