分布式锁

Distributed Locks

📐 01 · 定义

分布式锁是在多个进程或机器之间协调对共享资源互斥访问的机制，常基于 Redis、etcd、ZooKeeper 或数据库实现。它分为两类用途：提升效率（避免重复工作，偶尔失效可接受）和保证正确性（绝不能并发）。后者必须考虑进程停顿、时钟和网络问题，通常需要防护令牌配合。

⚙️ 02 · 原理
  1. 1

    加锁：在共享存储中原子地创建锁记录，写入唯一持有者标识并设置过期时间。

  2. 2

    持有：获得锁的客户端执行临界区操作；执行时间较长时需在过期前续期。

  3. 3

    释放：只有持有者才能删除锁，删除前需原子比对自己的标识，避免误删他人的锁。

  4. 4

    失效：持有者崩溃后锁按过期时间自动释放，其他客户端随后可以获取。

  5. 5

    防护：存储按顺序发放递增令牌，下游资源拒绝令牌更小的写入请求。

🔤 03 · 术语
互斥 (Mutual Exclusion)
同一时刻只有一个持有者能进入临界区。
锁过期 (TTL)
防止持有者崩溃导致死锁的自动释放时间。
防护令牌 (Fencing Token)
随每次加锁递增的编号，下游据此拒绝过期持有者。
Redlock
Redis 作者提出的多实例加锁算法，其安全性有争议。
看门狗续期 (Watchdog)
后台定时延长锁过期时间，避免任务未完成锁就过期。
💻 04 · 代码
Redis 单实例锁python
import uuid, redis

r = redis.Redis(host="localhost", port=6379)

# 释放脚本：值匹配才删除，比较与删除在 Redis 中原子执行
RELEASE = """
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
end
return 0
"""

def acquire(name: str, ttl_ms: int = 30000):
    token = str(uuid.uuid4())                  # 唯一持有者标识
    ok = r.set(f"lock:{name}", token, nx=True, px=ttl_ms)  # 不存在才设置，带过期
    return token if ok else None

def release(name: str, token: str) -> bool:
    return r.eval(RELEASE, 1, f"lock:{name}", token) == 1

t = acquire("daily-report")
if t:
    try:
        pass                                   # 临界区：生成日报
    finally:
        release("daily-report", t)

适合效率型场景；若需正确性保证，应配合防护令牌或改用共识存储。

实现方式对比

实现可靠性适用
Redis 单实例 SET NX PX主从切换时可能丢锁避免重复执行等效率型
etcd / ZooKeeper基于共识，较可靠正确性要求高的协调

⚖️ 06 · 方案取舍

Redis 锁

优点性能高、实现简单

代价故障转移时锁可能丢失

适用偶发重复可接受

etcd/ZK 锁

优点强一致、会话失效自动释放

代价延迟较高，需运维共识集群

适用必须严格互斥

不加锁+幂等/乐观并发

优点无锁开销，不怕持有者停顿

代价需要设计版本号或唯一键

适用可改造为条件写的场景

🕳️ 07 · 常见坑

  • ✗用 DEL 直接释放，误删已被别人重新获取的锁

    ✓释放时用脚本比对持有者标识后再删除

  • ✗SETNX 与 EXPIRE 分两步执行，中间崩溃形成永久锁

    ✓使用 SET key value NX PX ttl 一条命令原子完成

  • ✗GC 停顿超过 TTL，两个客户端同时进入临界区

    ✓下游使用防护令牌校验，或改用条件写入

  • ✗用分布式锁保护本可用数据库约束解决的问题

    ✓优先用唯一约束、乐观锁等存储自带机制

🎤 09 · 面试追问
Redis 分布式锁有哪些坑？

SETNX 与过期分开设置导致死锁；释放时不校验持有者误删；主从异步复制下主节点宕机，锁未同步到新主即丢失；客户端停顿超过 TTL 后锁被他人获取却仍在执行。前两个可修复，后两个需要防护令牌或换共识存储。

什么是防护令牌，为什么需要？

锁服务每次授予锁时返回单调递增的编号，客户端访问共享资源时附带编号，资源方记录见过的最大编号并拒绝更小的。这样即使旧持有者因停顿以为自己仍持锁，其写入也会被拒绝。

Redlock 的争议点是什么？

Kleppmann 认为它依赖时钟漂移有界、进程停顿可控等时序假设，且不提供防护令牌，用于正确性场景不安全；antirez 认为在合理假设下可用。共识是：正确性关键场景应使用共识系统加防护令牌。
