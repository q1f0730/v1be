文档切块策略 (Chunking)

Chunking Strategies

📐 01 · 定义

文档切块（Chunking）是 RAG 索引阶段把长文档拆成适合嵌入与检索的片段的过程。块的大小、边界和附带的上下文决定了检索粒度：太大会稀释语义、挤占上下文窗口，太小会割裂含义、丢失指代。常见策略包括固定长度加重叠、递归按分隔符切分、按文档结构（标题、段落、代码块）切分、语义切分，以及父子块（检索小块、返回大块）。

⚙️ 02 · 原理
  1. 1

    解析原始文档（PDF、HTML、Markdown），去除页眉页脚等噪声，尽量保留标题层级、表格与列表结构。

  2. 2

    按策略确定边界：递归切分按段落→句子→字符逐级回退，尽量让每块不超过目标长度（以 token 或字符计）。

  3. 3

    为相邻块设置重叠（如块长的 10%–20%），缓解边界处信息被截断的问题。

  4. 4

    为每块附加元数据与上下文：来源、章节标题路径、页码，或用模型生成一句块级摘要（上下文化检索）。

  5. 5

    对块计算嵌入并写入索引；检索时可返回命中块本身，或回溯其父块/相邻块以提供更完整的上下文。

🔤 03 · 术语
块大小 (Chunk Size)
每块的最大长度，常以 token 计，需小于嵌入模型输入上限。
重叠 (Chunk Overlap)
相邻块共享的内容长度，用于保留跨边界上下文。
递归字符切分 (Recursive Splitting)
按分隔符优先级逐级切分，尽量在自然边界断开。
语义切分 (Semantic Chunking)
根据相邻句子嵌入相似度的突变处切分。
父子块 (Parent-Child / Small-to-Big)
用小块检索以求精准，返回所属大块以求完整。
上下文化检索 (Contextual Retrieval)
为每块前置一段说明其在全文位置的上下文再嵌入。
💻 04 · 代码
按标题 + 递归切分 Markdownpython
from langchain_text_splitters import (
    MarkdownHeaderTextSplitter, RecursiveCharacterTextSplitter)

md = open("handbook.md", encoding="utf-8").read()

# 1. 先按标题切，标题路径进入元数据
header_splitter = MarkdownHeaderTextSplitter(
    headers_to_split_on=[("#", "h1"), ("##", "h2"), ("###", "h3")])
sections = header_splitter.split_text(md)

# 2. 过长的章节再递归切分，带重叠
splitter = RecursiveCharacterTextSplitter(
    chunk_size=800, chunk_overlap=100,          # 按字符计；可改用 token 计数
    separators=["\n\n", "\n", "。", "！", "？", " ", ""])
chunks = splitter.split_documents(sections)

# 3. 把标题路径拼到正文前，帮助嵌入理解上下文
for c in chunks:
    path = " > ".join(v for k, v in c.metadata.items() if k.startswith("h"))
    c.page_content = f"[{path}]\n{c.page_content}"
print(len(chunks), chunks[0].page_content[:120])

先按文档结构切，再按长度兜底，并把章节路径注入每块；中文分隔符需显式加入。

📊 05 · 参数对比

切块策略对比

策略优点缺点适用
固定长度 + 重叠简单、可预测常在句中断开格式杂乱的纯文本
递归分隔符切分多在自然边界断开不理解语义通用默认方案
按文档结构切分保留章节完整性章节长短不均Markdown、HTML、技术文档
语义切分话题边界更准确需额外嵌入计算，参数敏感长篇叙述、对话记录
父子块检索精准且上下文完整存储与实现更复杂问答需要完整段落时
⚖️ 06 · 方案取舍

小块（约 100–300 token）

优点检索精准，噪声少

代价易丢上下文与指代

适用事实型问答、FAQ

大块（约 800–1500 token）

优点上下文完整

代价语义稀释，占用更多上下文

适用需要理解整段论述

小块检索 + 返回父块

优点兼顾精准与完整

代价实现复杂、索引更大

适用对质量要求高的生产 RAG

🕳️ 07 · 常见坑

  • ✗所有文档统一一种块大小，从不评测

    ✓按文档类型分别设置，并用评测集比较不同参数

  • ✗PDF 表格被拆成碎片，行列关系丢失

    ✓表格单独解析为 Markdown 或整表成块

  • ✗块中缺少章节标题，“本条款”指代不明

    ✓在块前拼接标题路径或生成上下文摘要

  • ✗块长度超过嵌入模型输入上限被静默截断

    ✓按 token 计数切分，并低于模型最大输入长度

☑️ 08 · 检查清单
🎤 09 · 面试追问
块大小如何选择？

没有通用最优值。需要考虑嵌入模型的最佳输入长度、问题类型（事实型偏小块，综合型偏大块）、文档结构和上下文预算。实践中准备评测集，测试几组块大小与重叠的 Recall@K 和最终答案质量，选择最优组合。

为什么要加重叠，重叠越大越好吗？

重叠让跨边界的句子在至少一个块中完整出现，减少截断带来的信息丢失。但重叠越大，冗余越多，索引变大、检索结果更容易重复，浪费上下文。通常取块长的一小部分并通过评测确认。

上下文化检索解决了什么问题？

孤立的块常缺少主体信息，例如“该公司营收增长 3%”不知是哪家公司。为每块前置一段由模型生成的、说明其在原文中位置与主题的上下文，再做嵌入和 BM25 索引，可显著减少检索失败，代价是索引时的额外模型调用。
