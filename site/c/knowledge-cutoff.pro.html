知识截止日期

Knowledge Cutoff

📐 01 · 定义

知识截止日期（Knowledge / Training Data Cutoff）是模型训练语料所覆盖的最晚时间点。模型参数里只编码了此前的信息，对之后发布的库版本、API 变更、新闻一无所知，却可能以旧知识自信作答。它是模型能力边界的一部分，需在应用层通过检索、工具或上下文注入弥补。

⚙️ 02 · 原理
  1. 1

    厂商在某时间点冻结训练语料，此后的数据不会进入预训练；不少厂商会在模型文档中标注截止时间。

  2. 2

    截止前的最后一段时间往往数据稀疏，模型对「临近截止」的事件掌握也可能不完整。

  3. 3

    推理时模型默认把训练分布当成「现在」，遇到新版本库会输出旧 API，属于一类可预期的幻觉。

  4. 4

    应用层用 RAG、联网搜索、MCP 文档工具或把官方文档贴进上下文，为模型提供截止后的事实。

  5. 5

    编程场景里，锁文件和本地安装版本是事实来源，应让 Agent 先读版本再写代码。

🔤 03 · 术语
训练数据截止 (Training Data Cutoff)
语料覆盖的最晚日期，模型文档中常单独列出。
参数化知识 (Parametric Knowledge)
存储在权重中的知识，更新只能靠再训练或微调。
上下文知识 (In-context Knowledge)
推理时通过提示注入的信息，优先级通常高于参数化知识。
API 漂移 (API Drift)
库或服务接口随版本变化，导致模型记忆中的写法失效。
检索增强 (RAG)
先检索外部资料再生成，用于补足截止后与私有的知识。
💻 04 · 代码
以本地版本为准约束 AIbash
# 1. 查项目里实际安装的版本（以本地为准，不信模型记忆）
npm ls next                      # Node 项目
pip show pydantic | grep Version  # Python 项目

# 2. 查包注册表上的最新版本
npm view next version
pip index versions pydantic       # pip 的实验性子命令

# 3. 把版本约束写进 Agent 规则文件，每次会话自动加载
cat >> CLAUDE.md <<'EOF'
## 版本约束
- 本项目使用 pydantic v2：用 model_dump()，不要用 .dict()
- 不确定 API 时，先查阅 https://docs.pydantic.dev/latest/
EOF

把「真实版本 + 官方文档入口」放进规则文件，让 Agent 不再凭训练记忆写旧 API。

📊 05 · 参数对比

补足新知识的手段

手段时效性成本适用
上下文贴文档即时占 Token单次任务、小文档
联网搜索工具即时有调用延迟开放问题、新闻
RAG 知识库取决于更新频率需建索引私有或大量文档
微调训练时为止高风格、领域习惯
⚖️ 06 · 方案取舍

依赖模型记忆

优点零额外成本，响应最快

代价新版本 API 易出错

适用稳定多年的基础知识

每次注入官方文档

优点准确、可指定版本

代价占上下文，需维护链接

适用频繁变化的框架与 SDK

接入文档检索工具

优点按需拉取，不占常驻上下文

代价依赖工具质量与网络

适用Agent 长任务、多库项目

🕳️ 07 · 常见坑

  • ✗直接问模型「某库最新版本是多少」并采信

    ✓以 npm view / pip index 或官方发布页为准

  • ✗以为模型会主动说明自己不知道

    ✓在提示中要求其标注不确定之处并引用文档

  • ✗Agent 生成依赖文件时随手写版本号

    ✓用包管理器命令安装，由锁文件记录真实版本

🎤 09 · 面试追问
为什么模型会自信地写出已废弃的 API？

训练语料里旧写法出现频率远高于新写法，且模型不知道当前日期之后的变化；生成按概率选最常见模式，没有内在机制判断「是否过时」。缓解：注入版本信息与官方文档、提供检索工具、用测试与类型检查兜底。

RAG 和微调哪个更适合解决知识过时？

通常是 RAG：更新只需重建索引，可引用来源、成本低。微调把知识写进权重，更新慢、难溯源，更适合学习风格、格式或领域习惯，而非频繁变化的事实。

怎样让 Agent 在多依赖项目里少踩版本坑？

规则文件写清关键依赖与版本；要求先读 package.json/锁文件；提供 MCP 文档或联网工具；写完必须跑构建、类型检查和测试；把常见迁移要点（如 v1→v2 改名）列成清单。
