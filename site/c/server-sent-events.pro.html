服务端发送事件 (SSE)

Server-Sent Events

🧸 回到小白版

📐 01 · 定义

服务端发送事件（Server-Sent Events，SSE）是 HTML 标准定义的服务端到浏览器单向推送机制：客户端发起一个普通 HTTP 请求，服务端以 text/event-stream 格式持续写出事件，连接保持打开。EventSource 内置自动重连与续传，是通知流与大模型流式输出的常用传输方式。

⚙️ 02 · 原理
  1. 1

    客户端发起 GET 请求（EventSource）或用 fetch 读取流式响应体。

  2. 2

    服务端返回 Content-Type: text/event-stream，并且不结束响应。

  3. 3

    每个事件由若干行组成：data、event、id、retry 字段，以空行结束一个事件。

  4. 4

    以冒号开头的注释行会被客户端忽略，可用作心跳，防止代理因空闲断开连接。

  5. 5

    断线后 EventSource 按 retry 间隔自动重连，并通过 Last-Event-ID 头告知最后收到的 id。

🔤 03 · 术语
text/event-stream
SSE 的 MIME 类型，UTF-8 文本、按行解析。
EventSource
浏览器内置的 SSE 客户端 API，只支持 GET。
Last-Event-ID
重连时浏览器自动携带的请求头，用于续传。
retry 字段
服务端指定的重连等待毫秒数。
命名事件 (Named Event)
用 event 字段区分类型，客户端按名监听。
💻 04 · 代码
Express SSE 与断点续传javascript
app.get('/events', (req, res) => {
  res.writeHead(200, {
    'Content-Type': 'text/event-stream',
    'Cache-Control': 'no-cache',
    'X-Accel-Buffering': 'no',          // 告诉 Nginx 不要缓冲
  });
  let id = Number(req.headers['last-event-id'] ?? 0);  // 断线重连时续传
  res.write('retry: 5000\n\n');         // 建议浏览器 5 秒后重连

  const tick = setInterval(() => {
    id += 1;
    res.write(`id: ${id}\nevent: tick\ndata: ${JSON.stringify({ t: Date.now() })}\n\n`);
  }, 1000);
  const heartbeat = setInterval(() => res.write(': ping\n\n'), 15000);

  req.on('close', () => { clearInterval(tick); clearInterval(heartbeat); });
});

// 浏览器端
const es = new EventSource('/events');
es.addEventListener('tick', (e) => console.log(e.lastEventId, JSON.parse(e.data)));
es.onerror = () => console.warn('断开，浏览器会自动重连');

id 加 Last-Event-ID 实现续传；注释行心跳保活；客户端断开时清理定时器。

⚖️ 06 · 方案取舍

EventSource

优点自动重连与续传，零依赖

代价只能 GET，不能自定义请求头

适用通知、行情等订阅推送

fetch + 流式读取

优点可 POST、带 Authorization 头

代价重连与解析需自己实现

适用调用大模型流式接口

WebSocket

优点双向实时

代价协议与运维更复杂

适用客户端也要频繁上行消息

🕳️ 07 · 常见坑

  • ✗经过 Nginx/CDN 后事件被攒成一大块

    ✓关闭代理缓冲与压缩，或返回 X-Accel-Buffering: no

  • ✗HTTP/1.1 下开多个标签页，连接数耗尽

    ✓启用 HTTP/2，或多标签共享一个连接

  • ✗客户端断开后服务端仍在生成内容

    ✓监听 close 事件，中止上游生成并清理资源

  • ✗data 中直接写含换行的文本，解析错位

    ✓数据用 JSON 编码，或每行分别加 data: 前缀

🎤 09 · 面试追问
为什么大模型 API 普遍用 SSE 而不是 WebSocket？

生成过程是一次请求对应服务端单向连续输出，SSE 正好匹配：基于普通 HTTP，复用现有鉴权、网关、日志与负载均衡，实现简单。客户端通常用 fetch 读取流，以便 POST 请求体和设置鉴权头。

SSE 如何做到断线不丢消息？

服务端为每个事件分配递增 id；浏览器重连时自动带 Last-Event-ID；服务端从该 id 之后补发。需要服务端保留一段事件历史（内存环形缓冲或 Redis Stream），超出范围时让客户端全量刷新。

SSE 的连接数限制是怎么回事？

HTTP/1.1 下浏览器对同一域名的并发连接数有限（通常 6 个），每个 SSE 占用一个，多标签页时容易耗尽导致其他请求排队。HTTP/2 多路复用可解决，或用 BroadcastChannel 让多标签共享。
