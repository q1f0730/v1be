消息顺序性保证

Message Ordering

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

消息顺序性保证是消息系统按发送顺序把消息交给消费者处理的能力。分布式消息系统通常只在一个分区或一个消息组内保证顺序，不提供全局顺序，因为全局有序意味着无法并行。设计时要先确定「需要在什么范围内有序」，再用分区键、消息组和消费策略来保证。

⚙️ 02 · 原理
  1. 1

    确定有序范围：通常是同一实体（订单、账户）的消息需要有序，不同实体可并行。

  2. 2

    按键路由：用实体 ID 作为分区键或消息组 ID，让同一实体的消息进入同一有序通道。

  3. 3

    生产端保序：重试时防止乱序，如 Kafka 开启幂等生产者，SQS FIFO 用消息组。

  4. 4

    消费端保序：同一分区或消息组内串行处理，避免多线程并发消费打乱顺序。

  5. 5

    兜底：消息携带版本号或时间序号，消费者丢弃比当前状态更旧的消息。

🔤 03 · 术语
分区内有序 (Per-partition Ordering)
Kafka 只保证同一分区内消息的写入与读取顺序。
消息组 (Message Group)
SQS FIFO 中同一组内消息严格有序、逐条投递。
队头阻塞 (Head-of-line Blocking)
有序通道中一条消息处理失败会阻塞后续消息。
乱序重试
前一批发送失败重试时，后一批已成功写入导致顺序颠倒。
版本号 (Sequence Number)
随实体变更递增的序号，用于检测和丢弃过期消息。
💻 04 · 代码
SQS FIFO 按订单保序python
import json, boto3

sqs = boto3.client("sqs")
QUEUE = "https://sqs.us-east-1.amazonaws.com/123456789012/orders.fifo"

def publish(order_id: str, seq: int, event: dict):
    sqs.send_message(
        QueueUrl=QUEUE,
        MessageBody=json.dumps({**event, "seq": seq}),
        # 同一订单的事件进入同一消息组 → 组内严格有序
        MessageGroupId=order_id,
        # 去重 ID：同一 ID 在去重窗口内只会入队一次
        MessageDeduplicationId=f"{order_id}-{seq}",
    )

publish("order-1001", 1, {"type": "Created"})
publish("order-1001", 2, {"type": "Paid"})
publish("order-2002", 1, {"type": "Created"})   # 不同组可并行消费

不同订单可并行，同一订单按序；消息带 seq 便于消费者再做兜底校验。

⚖️ 06 · 方案取舍

按实体分区有序

优点兼顾顺序与并行度

代价热点实体会形成热点分区

适用大多数业务事件

全局单分区

优点严格全局顺序

代价无法水平扩展，吞吐受限

适用量很小且确需全局序

不保序+版本号

优点最大并行，系统简单

代价消费者需处理乱序与过期消息

适用只关心最终状态

🕳️ 07 · 常见坑

  • ✗同一分区内用线程池并发处理，顺序被打乱

    ✓按 key 分配到固定的工作线程，或分区内串行处理

  • ✗扩容分区数后，同一 key 映射到新分区，短期乱序

    ✓规划好初始分区数，扩容时评估顺序影响或停写切换

  • ✗处理失败的消息被丢到重试队列，后续消息先处理

    ✓有序场景中失败要阻塞重试或整组转入死信并告警

  • ✗要求全局有序，导致系统无法扩展

    ✓分析业务真正需要的有序范围，通常按实体即可

🎤 09 · 面试追问
Kafka 如何保证同一订单的消息有序？

生产时用订单 ID 作 key，使其哈希到同一分区；开启幂等生产者避免重试乱序；消费端每个分区只由组内一个消费者读取，并在分区内串行处理。注意扩容分区会改变 key 映射。

为什么不提供全局有序？

全局有序需要所有消息经过单一序列化点，只能单分区单消费者，吞吐无法扩展且有单点问题。多数业务只需同一实体内有序，按实体分区即可同时获得顺序和并行度。

有序消费中一条消息一直失败怎么办？

有序意味着后续消息必须等待，因此先有限次重试；仍失败则需决策：阻塞并告警人工介入，或把该实体后续消息一起转入死信，避免跳过它导致状态错乱。
