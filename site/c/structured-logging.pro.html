结构化日志

Structured Logging

🧸 回到小白版

📐 01 · 定义

结构化日志（Structured Logging）是把每条日志输出为带固定字段的机器可解析记录（通常是每行一个 JSON 对象），而不是自由拼接的文本。它属于可观测性层，使日志能被采集系统按字段索引、过滤、聚合，并通过 trace_id 等字段与链路追踪、指标关联。

⚙️ 02 · 原理
  1. 1

    应用使用日志库按键值对记录事件，如 event、user_id、duration_ms，而非拼接字符串。

  2. 2

    处理器链自动补充时间戳、级别、服务名、主机等公共字段，并合并请求上下文。

  3. 3

    请求进入时绑定 request_id / trace_id 到上下文，该请求内所有日志自动携带。

  4. 4

    渲染器把记录序列化为 JSON 写到 stdout，由采集代理（如 Fluent Bit、Vector）收集。

  5. 5

    后端（如 Elasticsearch、Loki、云日志服务）按字段建索引，支持查询与告警。

🔤 03 · 术语
关联 ID (Correlation ID)
贯穿一次请求的唯一 ID，用于串联多条日志。
高基数字段 (High Cardinality)
取值极多的字段，如 user_id，影响索引成本。
上下文绑定 (Context Binding)
把字段绑定到当前请求，后续日志自动带上。
OpenTelemetry Logs
OTel 定义的日志数据模型，可与 trace 关联。
脱敏 (Redaction)
在输出前删除或掩码敏感字段。
💻 04 · 代码
structlog 输出 JSON 日志python
import uuid
import structlog

structlog.configure(
    processors=[
        structlog.contextvars.merge_contextvars,      # 合并请求上下文
        structlog.processors.add_log_level,
        structlog.processors.TimeStamper(fmt="iso", utc=True),
        structlog.processors.JSONRenderer(),           # 每行一个 JSON
    ]
)
log = structlog.get_logger()

def handle_request(user_id: int):
    structlog.contextvars.clear_contextvars()
    structlog.contextvars.bind_contextvars(request_id=str(uuid.uuid4()))
    log.info("order_created", user_id=user_id, order_id=981, amount_cents=4999)
    log.warning("payment_slow", provider="stripe", duration_ms=2300)

handle_request(42)
# {"request_id": "…", "user_id": 42, "order_id": 981, "amount_cents": 4999,
#  "event": "order_created", "level": "info", "timestamp": "…Z"}

事件名固定、变量放字段；request_id 绑定一次，整条请求的日志都能串起来。

⚖️ 06 · 方案取舍

JSON 行日志

优点通用，采集与查询工具全支持

代价体积较大，人眼阅读差

适用生产环境默认

logfmt 键值格式

优点紧凑，人机都较易读

适用Go 生态、轻量场景

开发环境彩色文本

优点本地调试友好

代价不适合采集

适用本地开发，按环境切换渲染器

🕳️ 07 · 常见坑

  • ✗把变量拼进消息：f"user {id} paid {amt}"

    ✓消息保持固定事件名，变量放独立字段

  • ✗同一含义字段在各服务命名不同（uid/userId/user_id）

    ✓制定字段命名规范，或采用 OTel 语义约定

  • ✗把密码、token、完整请求体写入日志

    ✓在处理器链中统一脱敏，并建立敏感字段清单

  • ✗异常只记录 str(e)，丢失堆栈

    ✓使用日志库的异常记录方法输出结构化堆栈

🎤 09 · 面试追问
结构化日志和链路追踪如何关联？

在日志上下文中注入当前 span 的 trace_id 与 span_id（OpenTelemetry 提供日志关联能力），日志后端与追踪后端据此互相跳转：从一条错误日志直接打开对应的完整调用链。

高基数字段会带来什么问题？

在日志系统中按字段建索引时，user_id、request_id 等高基数字段会增大索引体积与成本；Loki 等以标签索引的系统尤其要避免把它们设为标签，应作为日志内容字段查询。

日志量太大怎么控制成本？

调整级别、对高频成功日志采样、聚合为指标、设置分层保留期（热数据短、冷存储长），并删除无查询价值的字段。错误与审计日志不采样。
