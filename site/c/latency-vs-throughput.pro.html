延迟与吞吐量权衡

Latency vs Throughput

📐 01 · 定义

延迟（Latency）是单个请求从发出到完成所需的时间，吞吐量（Throughput）是单位时间内系统完成的请求或数据量。两者相关但不同：批处理、排队、并发可以提高吞吐却拉长延迟。性能目标需同时说明两者，并用分位数而非平均值描述延迟。

⚙️ 02 · 原理
  1. 1

    延迟由网络往返、排队等待、处理时间、依赖调用等组成，常用 P50、P95、P99 描述。

  2. 2

    吞吐受限于最慢的瓶颈资源（CPU、IO、锁、连接池、下游配额）。

  3. 3

    Little 定律：系统内平均在途请求数 = 到达率 × 平均停留时间，把三者联系起来。

  4. 4

    资源利用率接近饱和时，排队时间急剧上升，延迟呈非线性恶化。

  5. 5

    扇出调用中，整体延迟取决于最慢的子调用，尾延迟会被放大。

🔤 03 · 术语
分位数 (Percentile)
P99 表示 99% 的请求不超过该延迟。
尾延迟 (Tail Latency)
高分位（P99、P99.9）的延迟，影响最差体验。
Little 定律 (Little's Law)
L = λW，在途数、到达率与停留时间的关系。
饱和度 (Saturation)
资源被占满、请求开始排队的程度。
TTFT
大模型首个 token 返回所需时间，属延迟指标。
批处理 (Batching)
合并多个请求一起处理，提高吞吐、增加等待。
💻 04 · 代码
压测：同时看吞吐与分位数python
# pip install httpx
import asyncio, time, statistics, httpx

URL, N, CONCURRENCY = "http://localhost:8000/health", 500, 50

async def main():
    latencies, sem = [], asyncio.Semaphore(CONCURRENCY)
    async with httpx.AsyncClient() as client:
        async def one():
            async with sem:
                t = time.perf_counter()
                await client.get(URL)
                latencies.append(time.perf_counter() - t)
        start = time.perf_counter()
        await asyncio.gather(*(one() for _ in range(N)))
        elapsed = time.perf_counter() - start

    latencies.sort()
    pct = lambda p: latencies[int(p * (len(latencies) - 1))] * 1000
    rps = N / elapsed
    print(f"吞吐 {rps:.0f} req/s | P50 {pct(.50):.1f}ms P95 {pct(.95):.1f}ms P99 {pct(.99):.1f}ms")
    # Little 定律验证：在途请求数 ≈ 吞吐 × 平均延迟，应接近设定的并发
    print(f"估算在途 {rps * statistics.mean(latencies):.1f}（设定并发 {CONCURRENCY}）")

asyncio.run(main())

改变并发数重复测量，可看到吞吐先升后平、延迟在饱和后陡增的拐点。

📊 05 · 参数对比

常见优化手段的影响

手段吞吐延迟
批处理/合并写提升单个请求变长
增加并发/实例提升（至瓶颈）未饱和时基本不变
缓存提升命中时大幅降低
对冲请求 (Hedged Request)略降（多发请求）降低尾延迟
⚖️ 06 · 方案取舍

优先低延迟

优点交互体验好

代价资源利用率低，成本高

适用在线交互、支付链路

优先高吞吐

优点单位成本低

代价单个任务等待更久

适用离线批处理、数据管道

大模型推理批处理

优点GPU 利用率与总 tokens/s 提升

代价单请求 TTFT 与速度可能下降

适用高并发推理服务

🕳️ 07 · 常见坑

  • ✗只看平均延迟

    ✓报告 P50/P95/P99，并按接口拆分

  • ✗压测只用固定并发，掩盖排队延迟

    ✓按固定到达率施压，观察延迟随负载变化

  • ✗把利用率推到 95% 以上追求成本

    ✓为突发留余量，关注饱和后的延迟拐点

  • ✗评估大模型服务只看 tokens/s

    ✓同时看 TTFT、单请求速度与并发下的分位数

🎤 09 · 面试追问
为什么不能用平均延迟衡量性能？

延迟分布通常长尾，少量极慢请求会被平均值掩盖，而用户恰恰记住慢的那几次。一个页面依赖多个请求时，遇到尾延迟的概率被放大。所以用 P95/P99 并结合分布图来定义目标。

用 Little 定律能做什么估算？

已知目标吞吐和平均延迟，可估算需要的并发度，例如 1000 req/s × 0.05 s ≈ 50 个在途请求，据此配置连接池、线程数或实例数；反过来也能根据并发上限推算最大吞吐。

如何降低扇出系统的尾延迟？

减少扇出宽度；对子调用设置超时与部分结果降级；对冲请求（超过 P95 时向另一副本补发）；隔离慢请求的资源；消除 GC 停顿等抖动来源。Dean 与 Barroso 的《The Tail at Scale》系统讨论了这些方法。
