主从复制延迟

Replication Lag

🧸 回到小白版

📐 01 · 定义

复制延迟（Replication Lag）是副本落后于主库的程度，可用时间或日志位置差衡量。异步复制下延迟始终存在，通常很小，但在写入突增、副本上的长查询、网络或资源不足时会显著放大，导致读到旧数据、故障切换丢数据等问题。

⚙️ 02 · 原理
  1. 1

    主库提交事务并生成日志；异步模式下不等待副本即返回成功。

  2. 2

    日志经网络传输到副本，副本写入本地后再按顺序重放到数据页。

  3. 3

    延迟可拆为传输、落盘、重放三段，PostgreSQL 分别报告 write/flush/replay lag。

  4. 4

    重放若较慢（单线程应用、与查询冲突、IO 不足），延迟就会持续累积。

  5. 5

    应用需监控延迟，并按业务容忍度决定读主库、等待追上或摘除副本。

🔤 03 · 术语
LSN
PostgreSQL 日志序列号，标识 WAL 中的位置。
replay_lag
主库提交到副本重放完成之间的时间。
Seconds_Behind_Source
MySQL 副本落后主库的估算秒数。
写后读一致 (Read-your-writes)
用户总能读到自己刚写入的数据。
并行复制 (Parallel Replication)
副本多线程应用日志以加快重放。
同步复制 (Synchronous Replication)
提交需等待副本确认，消除丢失但增加写延迟。
💻 04 · 代码
PostgreSQL 监测复制延迟sql
-- 在主库：查看各副本的传输、落盘、重放延迟（PostgreSQL 10+）
SELECT application_name, client_addr, state,
       write_lag, flush_lag, replay_lag,
       pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS replay_bytes_behind
FROM pg_stat_replication;

-- 在副本：距最后一次重放的事务已过去多久
-- 注意：主库空闲时该值也会增大，不一定代表真的落后
SELECT now() - pg_last_xact_replay_timestamp() AS replay_delay;

-- 写后读：写入后在主库记下位置
SELECT pg_current_wal_lsn();          -- 例如 0/3A2B1C8

-- 读之前在副本检查是否已重放到该位置
SELECT pg_last_wal_replay_lsn() >= '0/3A2B1C8'::pg_lsn AS caught_up;
-- caught_up 为 false 时，改读主库或稍后重试

-- MySQL 8.0.22+ 对应命令：SHOW REPLICA STATUS（看 Seconds_Behind_Source）

主库视角看三段延迟，副本视角看重放时间；LSN 比较实现精确的写后读。

⚖️ 06 · 方案取舍

异步复制

优点写入延迟最低

代价存在延迟，切换可能丢数据

适用多数读扩展场景

同步复制

优点已提交事务不丢

代价写延迟增加，副本故障可能阻塞写

适用金融等零丢失要求

半同步/仲裁提交

优点兼顾可靠与可用

代价配置复杂，仍有边界情况

适用多副本高可用集群

🕳️ 07 · 常见坑

  • ✗只监控平均延迟，忽略突刺

    ✓监控最大值与 P99，并按副本分别告警

  • ✗用“距上次重放时间”判断延迟，空闲时误报

    ✓结合主库 pg_stat_replication 或心跳表

  • ✗大事务一次性更新千万行

    ✓拆成小批次，控制每批行数与间隔

  • ✗延迟很大时副本仍在负载均衡池中

    ✓超过阈值自动摘除，恢复后再加入

🎤 09 · 面试追问
怎样准确测量复制延迟？

PostgreSQL 在主库查 pg_stat_replication 的 replay_lag 与 LSN 差值；也可用心跳表：主库定期写时间戳，副本读出与当前时间比较。MySQL 的 Seconds_Behind_Source 有时不准，可用 pt-heartbeat。

复制延迟对故障切换有什么影响？

异步复制下，主库宕机时未传到副本的事务会丢失，丢失量约等于当时的延迟。切换前应选择最新的副本，并评估 RPO；要求零丢失需同步复制或仲裁提交。

如何在用户层面屏蔽延迟？

写后对该用户会话读主库一段时间；使用 LSN/GTID 令牌等待副本追上；前端乐观更新界面，先展示本地结果；对延迟敏感页面直接走主库。
