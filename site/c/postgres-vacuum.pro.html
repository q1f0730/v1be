Postgres VACUUM

📐 01 · 定义

VACUUM 是 PostgreSQL 的空间回收与维护机制。由于 MVCC 下 UPDATE/DELETE 不原地修改而是留下旧版本行（死元组），VACUUM 负责标记这些空间可复用、更新可见性映射和统计信息，并冻结旧事务 ID 以防事务 ID 回卷。日常由 autovacuum 后台进程自动执行。

⚙️ 02 · 原理
  1. 1

    MVCC 写入：UPDATE 生成新行版本，旧版本在所有事务都不再需要前不能清理。

  2. 2

    判定可回收：VACUUM 检查死元组是否已对所有活跃事务不可见，可见则标记空间可复用。

  3. 3

    更新元数据：维护空闲空间映射（FSM）和可见性映射（VM），后者支撑仅索引扫描。

  4. 4

    冻结事务 ID：把足够旧的行标记为冻结，防止 32 位事务 ID 回卷导致数据可见性错误。

  5. 5

    自动触发：死元组超过阈值（默认 50 行 + 表行数 20%）时 autovacuum 自动执行。

🔤 03 · 术语
死元组 (Dead Tuple)
已被更新或删除、对所有事务都不可见的旧行版本。
表膨胀 (Bloat)
死元组和空闲空间过多导致表和索引体积远大于实际数据。
事务 ID 回卷 (XID Wraparound)
32 位事务 ID 耗尽循环，不冻结旧行会导致数据被误判不可见。
VACUUM FULL
重写整张表彻底回收空间，期间持有排他锁阻塞读写。
可见性映射 (Visibility Map)
标记哪些页全部可见，加速仅索引扫描并减少 VACUUM 工作。
💻 04 · 代码
排查与调优 VACUUMsql
-- 1) 哪些表死元组最多、上次 autovacuum 是什么时候
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC LIMIT 10;

-- 2) 是否有长事务阻止清理（xact_start 很早的会话）
SELECT pid, state, xact_start, left(query, 60)
FROM pg_stat_activity
WHERE xact_start IS NOT NULL ORDER BY xact_start LIMIT 5;

-- 3) 各数据库距离回卷还有多远（年龄越大越危险）
SELECT datname, age(datfrozenxid) FROM pg_database ORDER BY 2 DESC;

-- 4) 大表单独调低触发比例，让 autovacuum 更早更频繁运行
ALTER TABLE orders SET (autovacuum_vacuum_scale_factor = 0.02);

-- 5) 手动执行（不锁表读写），并更新统计信息
VACUUM (VERBOSE, ANALYZE) orders;

先看死元组和长事务，再针对大表调 autovacuum；普通 VACUUM 不阻塞读写。

📊 05 · 参数对比

VACUUM 变体对比

命令锁级别效果
VACUUM不阻塞读写标记空间可复用，一般不缩小文件
VACUUM ANALYZE不阻塞读写同上并更新优化器统计信息
VACUUM FULL排他锁，阻塞读写重写表，空间归还操作系统
pg_repack（扩展）仅短暂锁在线重建表与索引，消除膨胀
⚖️ 06 · 方案取舍

调优 autovacuum

优点持续自动，避免膨胀积累

代价需理解参数，过激会占 I/O

适用所有生产库的默认做法

定期手动 VACUUM

优点可安排在低峰时段

代价间隔内仍会膨胀，依赖运维

适用批量导入或大批量删除后

VACUUM FULL / pg_repack

优点彻底回收已膨胀空间

代价FULL 锁表；repack 需额外空间

适用已严重膨胀需要缩表

🕳️ 07 · 常见坑

  • ✗关闭 autovacuum 以减少 I/O 抖动

    ✓保持开启，按表调参数，必要时提高 autovacuum 的 I/O 配额

  • ✗长时间空闲在事务中的连接，导致死元组无法清理

    ✓设置 idle_in_transaction_session_timeout，并监控长事务

  • ✗生产高峰直接执行 VACUUM FULL

    ✓评估锁影响，优先用 pg_repack 在线处理

  • ✗忽视事务 ID 年龄，直到数据库进入保护性只读

    ✓监控 age(datfrozenxid)，确保冻结持续进行

☑️ 08 · 检查清单
🎤 09 · 面试追问
为什么 PostgreSQL 需要 VACUUM？

MVCC 实现中更新和删除都保留旧版本以支持并发读，旧版本不会自动消失。VACUUM 在确认没有事务需要后回收这些空间，同时更新可见性映射和冻结旧事务 ID，后者关系到数据正确性。

表一直膨胀，autovacuum 也在跑，可能是什么原因？

常见是长事务、空闲事务、滞留的复制槽或备库 hot_standby_feedback 拖住了清理边界；也可能是大表 20% 比例阈值过高、vacuum 速度受 cost limit 限制跟不上写入速度。

VACUUM 和 VACUUM FULL 怎么选？

日常用普通 VACUUM，不阻塞读写，空间留给表内复用。只有表已严重膨胀且需要把空间还给操作系统时才考虑 FULL，它会重写表并持有排他锁；生产上常用 pg_repack 替代。
