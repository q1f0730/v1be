忽略本地环境变量文件

.env in .gitignore

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

把 .env 加入 .gitignore，是让 Git 忽略本地环境变量文件、防止其中的密钥被提交并推送到远程仓库的基础做法。.gitignore 只对尚未被跟踪的文件生效；若 .env 已被提交过，必须从索引中移除，并且历史中的密钥要视为已泄露并轮换。配套做法是提交一份只含变量名的 .env.example。

⚙️ 02 · 原理
  1. 1

    匹配规则：Git 在添加文件时按 .gitignore 中的模式判断是否忽略，支持通配符与否定规则。

  2. 2

    仅对未跟踪文件生效：已被提交过的文件不受 .gitignore 影响，修改仍会被跟踪。

  3. 3

    从索引移除：git rm --cached .env 停止跟踪但保留本地文件，再提交这次删除。

  4. 4

    历史残留：之前的提交中 .env 内容依然存在，任何能访问仓库的人都可查看。

  5. 5

    补救：轮换全部泄露密钥，必要时用 git filter-repo 重写历史并强推。

🔤 03 · 术语
.gitignore
列出 Git 应忽略的文件模式的配置文件。
未跟踪文件 (Untracked)
Git 尚未纳入版本控制的文件。
git rm --cached
从暂存区和后续版本中移除文件，但保留工作区文件。
git filter-repo
官方推荐的历史重写工具，可彻底删除历史中的文件。
全局 gitignore
通过 core.excludesFile 为本机所有仓库设置的忽略规则。
💻 04 · 代码
忽略 .env 与补救bash
# 1. 写入忽略规则（同时保留示例文件）
cat >> .gitignore <<'EOF'
.env
.env.*
!.env.example
EOF

# 2. 验证是否生效：输出匹配的规则即表示已忽略
git check-ignore -v .env

# 3. 如果 .env 之前已经被提交过：停止跟踪（本地文件保留）
git rm --cached .env
git commit -m "chore: stop tracking .env"

# 4. 检查历史中是否出现过 .env
git log --all --oneline -- .env

# 5. 若曾推送：先轮换所有密钥！再按需重写历史（需安装 git-filter-repo）
# git filter-repo --path .env --invert-paths
# 之后需强推并通知协作者重新克隆

顺序很重要：先忽略并停止跟踪，发现历史泄露时第一步是轮换密钥，重写历史只是补充。

📊 05 · 参数对比

常见文件该不该提交

文件是否提交原因
.env / .env.local否包含真实密钥与个人配置
.env.example是只列变量名，供他人参考
package-lock.json 等锁文件是保证依赖可复现
node_modules / .venv否可重新安装，体积大
dist / build通常否可由源码构建生成
⚖️ 06 · 方案取舍

项目级 .gitignore

优点团队共享，规则随仓库走

代价需每个项目维护

适用所有项目都应有

全局 gitignore

优点本机所有仓库自动生效

代价不影响队友的机器

适用个人额外保险，如编辑器文件

重写 Git 历史

优点从历史中彻底移除文件

代价破坏协作者历史，fork 与缓存中仍可能残留

适用泄露后在轮换之外的补充措施

🕳️ 07 · 常见坑

  • ✗先提交了 .env 才加 .gitignore，以为就安全了

    ✓执行 git rm --cached 停止跟踪，并轮换已提交的密钥

  • ✗只删除最新版本中的 .env 文件

    ✓历史仍可见，必须轮换，必要时重写历史

  • ✗忽略规则写成 .env 但实际文件名是 .env.production

    ✓使用 .env.* 并用 git check-ignore 验证

  • ✗把 .env.example 也忽略了

    ✓加 !.env.example 否定规则，并确保其中只有占位值

🎤 09 · 面试追问
为什么加了 .gitignore，.env 还是被提交了？

.gitignore 只影响未跟踪文件。若 .env 在添加规则之前已经被 git add 或提交过，Git 会继续跟踪它。需要 git rm --cached .env 停止跟踪并提交，同时把已进入历史的密钥视为泄露进行轮换。

重写历史后就安全了吗？

不完全。在重写之前，内容可能已被克隆、fork、CI 缓存或被自动化扫描器抓取；托管平台的缓存视图也可能短期残留。所以轮换密钥是必须的第一步，重写历史只是减少后续暴露的补充措施。

如何从流程上杜绝这类问题？

项目模板自带完善的 .gitignore；提交前钩子运行密钥扫描；托管平台开启推送保护；代码评审时检查新增文件；给 AI Agent 的规则中明确禁止创建或修改真实 .env 内容并提交。
