上下文工程

Context Engineering

📐 01 · 定义

上下文工程（Context Engineering）是为大模型在每一轮推理时组织输入窗口的系统性方法，位于模型之上的应用编排层。它决定把哪些指令、历史、检索结果、工具定义与返回、记忆放进有限的上下文窗口（Context Window）及其顺序和格式，目标是用尽量少的 token 给模型恰好够用的信息。

⚙️ 02 · 原理
  1. 1

    盘点信息源：系统提示、用户输入、对话历史、检索文档、工具 schema、工具结果、长期记忆、文件内容。

  2. 2

    按任务相关性筛选与排序，常用检索、重排（rerank）或规则过滤，剔除与当前步骤无关的内容。

  3. 3

    压缩：对长历史做摘要，对工具输出截断或提取关键字段，避免低价值 token 挤占预算。

  4. 4

    组织结构：用标签或 Markdown 分区，稳定内容放前面以利用提示缓存，关键指令放显眼位置。

  5. 5

    在 Agent 循环中持续维护：每轮写入新结果、淘汰过时信息，必要时把状态外置到文件或记忆里按需读回。

🔤 03 · 术语
上下文窗口 (Context Window)
模型单次推理可接收的最大 token 数，包含输入和输出。
上下文腐化 (Context Rot)
输入越长，模型对其中信息的利用越不稳定的现象。
提示缓存 (Prompt Caching)
复用相同前缀的计算结果，降低延迟和费用，要求前缀稳定。
压缩 (Compaction)
接近窗口上限时把历史总结成摘要后继续对话。
渐进式披露 (Progressive Disclosure)
先给索引或摘要，模型需要时再通过工具读取细节。
💻 04 · 代码
按预算拼装上下文python
def build_context(task, history, docs, budget_tokens, count):
    """count(text) -> token 数，可用 tokenizer 实现"""
    parts = ["<instructions>只根据<docs>回答，不知道就说不知道。</instructions>"]
    used = count(parts[0]) + count(task)

    # 1. 检索结果按相关度降序放入，超预算即停
    for d in sorted(docs, key=lambda d: d["score"], reverse=True):
        block = f"<doc source='{d['src']}'>{d['text']}</doc>"
        if used + count(block) > budget_tokens * 0.6:
            break
        parts.append(block); used += count(block)

    # 2. 历史只保留最近几轮，其余应先做摘要
    for turn in history[-4:]:
        parts.append(f"<turn role='{turn['role']}'>{turn['text']}</turn>")

    parts.append(f"<task>{task}</task>")
    return "\n".join(parts)

演示预算分配、按相关度截断和分区标签；历史部分为简化起见未计入预算。

一次性塞入全部资料

优点实现简单，不漏信息

代价贵、慢，长上下文下准确率可能下降

🕳️ 07 · 常见坑

  • ✗窗口足够大就不做筛选

    ✓按相关性筛选和排序，窗口大小不等于有效利用能力

  • ✗每轮把时间戳等易变内容放在提示最前

    ✓易变内容放末尾，保持前缀稳定以命中提示缓存

  • ✗工具直接返回整页 HTML 或全量日志

    ✓在工具层做提取和截断，只回传任务需要的部分

  • ✗多来源资料混在一起不标出处

    ✓用标签标注来源，便于模型引用和排查答错原因

🎤 09 · 面试追问
上下文工程和提示词工程有什么区别？

提示词工程关注怎么写指令本身；上下文工程关注整个输入窗口的构成和生命周期，包括检索、记忆、工具结果、历史压缩和缓存策略。在多轮 Agent 场景中，后者往往比措辞更决定效果。

长上下文模型出现后还需要 RAG 吗？

通常仍需要。长窗口按 token 计费且延迟更高，信息越多模型越容易遗漏中间内容；知识库规模也常远超窗口。实践中是组合：检索缩小范围，长窗口容纳更完整的片段。

Agent 跑几十轮后变笨，怎么处理？

先看上下文：是否堆满了过期工具输出。办法包括清理旧工具结果、对历史做摘要压缩、把计划和进度写进外部文件按需读回、拆成子 Agent 各自持有干净上下文，并只把结论返回主 Agent。
