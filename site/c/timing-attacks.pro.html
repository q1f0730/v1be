时序侧信道攻击

Timing Attacks

📐 01 · 定义

时序侧信道攻击（Timing Attack）是一类侧信道攻击：攻击者测量系统处理不同输入所需的时间差，推断出密钥、令牌、密码或账号是否存在等秘密信息。常见根源是逐字节提前返回的比较、依赖秘密的分支与查表，防御核心是让耗时与秘密无关（常数时间）。

⚙️ 02 · 原理
  1. 1

    找到依赖秘密的操作：如逐字节比较签名，遇到首个不同字节即返回。

  2. 2

    构造输入：攻击者逐位枚举候选值，并针对每个候选值重复发送大量请求。

  3. 3

    统计测量：对响应时间取中位数等统计量，消除网络抖动，识别略慢的候选。

  4. 4

    逐步恢复：耗时更长说明匹配到更多前缀字节，据此一位一位还原秘密。

  5. 5

    防御：使用常数时间比较、统一错误路径耗时、限流，并避免依赖秘密的分支。

🔤 03 · 术语
侧信道 (Side Channel)
通过时间、功耗、缓存等实现副作用泄露信息的途径。
常数时间 (Constant-time)
执行耗时不随秘密数据取值变化的实现方式。
短路比较 (Early-exit Comparison)
发现首个不同字节就返回的比较，耗时泄露匹配长度。
用户枚举 (User Enumeration)
通过响应差异判断某账号是否存在。
缓存时序攻击 (Cache-timing)
利用 CPU 缓存命中与否的时间差推断内存访问模式。
💻 04 · 代码
常数时间比较签名python
import hmac, hashlib

SECRET = b"server-side-secret"

def sign(msg: bytes) -> str:
    return hmac.new(SECRET, msg, hashlib.sha256).hexdigest()

def verify_bad(msg: bytes, sig: str) -> bool:
    return sign(msg) == sig          # 普通比较：可能提前返回，耗时泄露前缀匹配长度

def verify_good(msg: bytes, sig: str) -> bool:
    # compare_digest 的耗时不取决于两者有多少前缀相同
    return hmac.compare_digest(sign(msg), sig)

# Node.js 等价写法：crypto.timingSafeEqual(bufA, bufB)（要求长度相同）
print(verify_good(b"order=42", sign(b"order=42")))   # True

校验 HMAC、API 令牌、重置链接 token 时应使用常数时间比较。

⚖️ 06 · 方案取舍

常数时间比较

优点从根源消除比较类时序泄露

代价需要开发者知道在哪些地方使用

适用任何秘密值比较

统一响应耗时/加随机延迟

优点可遮掩部分业务流程差异

代价随机延迟可被统计平均掉，效果有限

适用作为辅助手段

限流与锁定

优点大幅提高统计测量所需成本

代价不消除泄露本身，可能误伤用户

适用所有认证相关接口

🕳️ 07 · 常见坑

  • ✗用 == 比较 HMAC 签名或 Webhook 签名

    ✓使用语言提供的常数时间比较函数

  • ✗登录时账号不存在直接返回，存在才算密码哈希

    ✓对不存在的账号也计算一次哈希，统一错误信息

  • ✗认为网络抖动大，远程时序攻击不可行

    ✓统计大量样本可滤除抖动，仍按可被利用来防御

  • ✗自己实现加密算法或比较逻辑

    ✓使用成熟、经过审计的密码学库

🎤 09 · 面试追问
为什么 == 比较字符串会有时序问题？

多数语言的字符串比较在遇到第一个不同字符时立即返回，前缀匹配越长耗时越长。攻击者逐位尝试并统计耗时，就能一位位恢复正确签名，把指数级暴力破解降为线性。

compare_digest 是怎么做到常数时间的？

它遍历全部字节，对每对字节做异或并累积到一个结果变量，不在中途分支或返回，最后统一判断结果是否为零，因此耗时只与长度相关，与内容匹配程度无关。

AI 生成的代码在这里常见什么问题？

生成 Webhook 签名校验、API Key 鉴权时常直接用 == 或 ===；登录逻辑先查用户再验密码导致用户枚举。审查时应专门搜索秘密值比较，并要求使用常数时间函数。
