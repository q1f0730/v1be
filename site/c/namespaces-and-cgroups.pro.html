容器底层隔离 (Namespace / cgroups)

Namespaces & cgroups

🧸 回到小白版

📐 01 · 定义

Linux 命名空间（Namespaces）和控制组（cgroups）是容器的两大内核基础。命名空间隔离进程能看到的系统资源视图，如进程号、网络、挂载点、主机名和用户；cgroups 对进程组的资源用量做限制、记账与优先级控制，如 CPU、内存、IO、进程数。容器本质上是共享宿主内核、被这两者约束的普通进程。

⚙️ 02 · 原理
  1. 1

    运行时（如 runc）通过 clone 或 unshare 系统调用为容器进程创建一组新的命名空间。

  2. 2

    PID 命名空间让容器内进程从 1 开始编号；网络命名空间提供独立网卡、路由与端口；挂载命名空间配合根文件系统切换提供独立文件视图。

  3. 3

    用户命名空间可把容器内 root 映射为宿主上的非特权用户，降低逃逸后的危害。

  4. 4

    运行时在 cgroup 层级中为容器建目录，写入 memory.max、cpu.max、pids.max 等限制并把进程加入。

  5. 5

    内存超限时内核在该 cgroup 内触发 OOM 终止进程；CPU 超出配额则被节流。再配合 capabilities、seccomp 与 LSM 收紧权限。

🔤 03 · 术语
PID 命名空间
隔离进程号空间，容器内看不到宿主的其他进程。
用户命名空间 (User Namespace)
隔离 UID/GID 映射，容器内 root 可对应宿主普通用户。
cgroup v2
统一层级的新版控制组接口，目前主流发行版与 Kubernetes 推荐使用。
cpu.max
cgroup v2 CPU 配额，格式为「配额 周期」微秒，如 50000 100000 即半核。
CPU 节流 (Throttling)
进程在周期内用完配额后被暂停调度，表现为延迟升高。
Linux Capabilities
把 root 权限拆成细粒度能力，容器默认只保留一部分。
💻 04 · 代码
手动体验命名空间与 cgroupbash
# 需要 root 和 cgroup v2；仅用于学习，勿在生产机上随意操作
# 1) 新的 PID/挂载/主机名命名空间：里面 ps 只能看到自己
sudo unshare --pid --fork --mount-proc --uts bash -c 'hostname box; hostname; ps aux'

# 2) 列出当前系统中的命名空间
lsns | head

# 3) cgroup v2：创建组并限制为半核 CPU、256MB 内存、最多 64 个进程
echo "+cpu +memory +pids" | sudo tee /sys/fs/cgroup/cgroup.subtree_control
sudo mkdir -p /sys/fs/cgroup/demo
echo "50000 100000" | sudo tee /sys/fs/cgroup/demo/cpu.max
echo 256M          | sudo tee /sys/fs/cgroup/demo/memory.max
echo 64            | sudo tee /sys/fs/cgroup/demo/pids.max
echo $$            | sudo tee /sys/fs/cgroup/demo/cgroup.procs   # 当前 shell 加入
cat /sys/fs/cgroup/demo/memory.events    # oom_kill 计数

# 4) Docker 等价写法：运行时替你完成上述设置
docker run --rm --cpus=0.5 --memory=256m --pids-limit=64 alpine sh

启用控制器的那行在部分系统上可能已由 systemd 完成；实验结束后把 shell 移出并删除 demo 目录。

主要命名空间类型

命名空间隔离内容容器中的表现
PID进程号容器主进程 PID 为 1
Network网卡、路由、端口每个容器可独立监听 80 端口

⚖️ 06 · 方案取舍

普通容器（命名空间 + cgroups）

优点启动快、开销低、密度高

代价共享内核，内核漏洞可导致逃逸

适用可信或同租户工作负载

用户态内核（如 gVisor）

优点拦截系统调用，隔离更强

代价部分系统调用性能下降或不兼容

适用运行不可信代码，如 AI 代码沙箱

轻量虚拟机（如 Firecracker、Kata）

优点独立内核，接近虚拟机隔离

代价启动与资源开销高于容器

适用多租户强隔离、Serverless 平台

🕳️ 07 · 常见坑

  • ✗以为容器等于安全沙箱，直接运行不可信代码

    ✓不可信负载使用 gVisor、微虚拟机等更强隔离并禁止特权

  • ✗设置过低的 CPU limit 导致严重节流

    ✓监控节流指标，按实测设置 limit，延迟敏感服务谨慎设 CPU 上限

  • ✗容器内应用按宿主机总内存计算堆大小

    ✓使用能识别 cgroup 限制的运行时版本或显式配置堆上限

  • ✗使用 --privileged 解决权限问题

    ✓只添加必需的 capability 或挂载，保持默认 seccomp

🎤 09 · 面试追问
容器和虚拟机的隔离本质区别？

虚拟机通过虚拟化硬件运行独立的客户机内核；容器是宿主内核上的普通进程，靠命名空间改变可见视图、cgroups 限制资源、capabilities 与 seccomp 限制系统调用。容器更轻但共享内核，内核漏洞会破坏所有容器的隔离。

Kubernetes 的 requests 和 limits 落到内核是什么？

在 cgroup v2 下，CPU request 转为 cpu.weight 用于争用时按比例分配，CPU limit 转为 cpu.max 配额会导致节流；内存 limit 转为 memory.max，超限触发 cgroup 内 OOM。内存 request 主要用于调度与驱逐判断。

为什么 AI 代码执行沙箱常不只依赖 Docker？

Agent 执行的代码不可信，普通容器与宿主共享内核，一旦存在内核或运行时漏洞就可能逃逸。因此常用 gVisor 拦截系统调用，或 Firecracker 等微虚拟机提供独立内核，再叠加网络出口限制、只读文件系统和资源配额。
