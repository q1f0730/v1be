毒丸消息

Poison Messages

📐 01 · 定义

毒丸消息（Poison Message）指无论重试多少次都会处理失败、甚至让消费者崩溃的消息，常见原因是格式错误、字段缺失、版本不兼容或触发代码缺陷。它是消息消费层的典型故障源：若不识别隔离，会在队列中反复投递，阻塞有序队列并持续消耗资源。

⚙️ 02 · 原理
  1. 1

    消费者取到消息，反序列化或业务校验时抛出异常，或者直接导致进程崩溃。

  2. 2

    消息未被确认，中间件在可见性超时或连接断开后重新投递，同一条消息开始循环。

  3. 3

    在有序队列或单分区中，这条消息挡在队头，后面的正常消息全部无法前进。

  4. 4

    中间件或消费端统计投递次数，超过上限后把它转入 DLQ，或由代码直接判定为不可重试。

  5. 5

    工程师按 DLQ 中的报错分类定位，修复解析逻辑或数据后决定重放还是丢弃。

🔤 03 · 术语
队头阻塞 (Head-of-Line Blocking)
队首消息处理不了，导致其后所有消息都被卡住。
投递计数 (Delivery Count)
同一消息被投递给消费者的累计次数，是识别毒丸的主要依据。
不可重试错误 (Non-retryable Error)
重试也不会成功的错误，如反序列化失败、校验不通过。
模式演进 (Schema Evolution)
消息结构随版本变化，新旧生产者和消费者需保持兼容。
投递上限 (Delivery Limit)
RabbitMQ 仲裁队列中消息最多被投递的次数，超过即丢弃或死信。
💻 04 · 代码
区分可重试与毒丸python
import json

class RetryableError(Exception):
    """下游超时等瞬时故障，值得重试"""

def handle(raw: bytes, send_to_dlq, process):
    try:
        msg = json.loads(raw)           # 格式错误 -> 毒丸
        order_id = msg["order_id"]       # 缺字段 -> 毒丸
    except (json.JSONDecodeError, KeyError) as e:
        send_to_dlq(raw, reason=repr(e))  # 立即隔离，不浪费重试
        return "ack"                      # 确认掉，避免堵队列

    try:
        process(order_id, msg)
        return "ack"
    except RetryableError:
        return "nack"                     # 交给中间件按策略重投

把解析和校验失败直接送进 DLQ，只对瞬时故障返回 nack 走重试。

⚖️ 06 · 方案取舍

依赖中间件投递上限

优点无需改代码，配置即生效

代价毒丸仍要白白重试 N 次

适用错误类型难以在代码里区分时

代码识别后立即死信

优点不浪费重试，队列恢复快

代价需要准确划分可重试与不可重试

适用解析、校验类错误明确时

跳过并只记日志

优点最快恢复吞吐

代价数据丢失风险高，难以审计

适用仅限可丢失的低价值消息

🕳️ 07 · 常见坑

  • ✗消费者崩溃前没确认也没记录，重启后又取到同一条，进入崩溃循环。

    ✓用投递计数兜底，并在处理前记录消息 ID 便于定位。

  • ✗把所有异常都当可重试，格式错误的消息也重试 10 次。

    ✓按异常类型分类，解析和校验错误直接进 DLQ。

  • ✗生产者升级改了字段名，消费者全部报错。

    ✓先发兼容版本的消费者，再上线生产者，配合 schema 兼容检查。

🎤 09 · 面试追问
如何判断一条失败消息是不是毒丸？

看两点：错误类型和投递次数。反序列化失败、必填字段缺失、业务校验不通过属于确定性错误，重试无意义；若同一消息投递次数持续增长且每次报同样的错，也应视为毒丸，转入 DLQ。

有序队列里出现毒丸会怎样？

会造成队头阻塞：为了保证顺序，后续消息必须等它处理完，整个分区或消息组停滞。处理方式是尽快把它移出到 DLQ，并评估跳过它是否破坏业务顺序约束。

怎样从源头减少毒丸？

生产端做 schema 校验和大小限制；使用 Schema Registry 和兼容性规则管理演进；消费者容忍未知字段；上线顺序遵循先消费者后生产者；对 AI 生成的消息处理代码补齐异常分类测试。
