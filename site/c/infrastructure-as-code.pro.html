基础设施即代码 (IaC)

Infrastructure as Code

📐 01 · 定义

基础设施即代码（IaC）是用代码文件定义服务器、网络、数据库、权限等基础设施，并由工具自动创建、变更和销毁的实践。代码纳入版本控制，经评审和流水线执行，使环境可复现、变更可审计、可回滚。常见工具有 Terraform/OpenTofu、CloudFormation、Pulumi 等。

⚙️ 02 · 原理
  1. 1

    用配置语言描述期望的资源，如一个存储桶、一组安全组规则及其依赖关系。

  2. 2

    工具读取当前状态文件和云端实际资源，计算出要创建、修改或删除的差异。

  3. 3

    plan 阶段展示变更计划，供代码评审和审批，避免意外删除。

  4. 4

    apply 阶段调用云厂商 API 执行变更，并更新状态文件记录资源映射。

  5. 5

    状态文件存放在支持加锁和加密的远程后端，多人协作时避免并发修改造成冲突。

🔤 03 · 术语
状态文件 (State)
记录代码中资源与真实资源对应关系的数据，Terraform 的核心。
计划 (Plan)
执行前计算并展示即将发生的变更。
配置漂移 (Drift)
真实资源被手工修改，与代码定义不一致。
模块 (Module)
可复用的一组资源定义，带输入变量与输出。
GitOps
以 Git 仓库为唯一事实来源，由自动化把变更同步到环境。
💻 04 · 代码
Terraform 定义存储桶text
# main.tf（HCL 语法）
terraform {
  backend "s3" {                      # 远程状态，团队共享
    bucket = "acme-tf-state"
    key    = "prod/storage.tfstate"
    region = "ap-southeast-1"
  }
}

provider "aws" { region = "ap-southeast-1" }

resource "aws_s3_bucket" "logs" {
  bucket = "acme-prod-logs"
  tags   = { owner = "platform", env = "prod" }
}

resource "aws_s3_bucket_versioning" "logs" {
  bucket = aws_s3_bucket.logs.id
  versioning_configuration { status = "Enabled" }
}

# 流程：terraform init → terraform plan（评审）→ terraform apply

声明一个开启版本控制的存储桶，状态放远程后端；先 plan 评审再 apply。

⚖️ 06 · 方案取舍

声明式（Terraform 等）

优点描述终态，易于审查差异

代价复杂逻辑表达受限

适用大多数云资源管理

通用语言（Pulumi/CDK）

优点可用循环、函数和测试框架

代价代码过于灵活时难以审查

适用开发团队主导、逻辑复杂

控制台手工操作

优点上手快

代价不可复现，无审计

适用仅限实验或紧急止血后补录

🕳️ 07 · 常见坑

  • ✗状态文件存在本地或提交进 Git，泄露密钥且多人冲突。

    ✓使用带加密和锁的远程后端。

  • ✗紧急情况在控制台手改资源，之后 apply 又改回去。

    ✓事后把改动补进代码，定期检测漂移。

  • ✗没看 plan 直接 apply，误删数据库。

    ✓在 CI 中输出 plan 并评审，关键资源加防删除保护。

  • ✗让 AI 生成 IaC 后直接在生产 apply。

    ✓先在非生产环境 plan 与 apply，评审权限和网络暴露面。

🎤 09 · 面试追问
Terraform 的状态文件有什么作用？

它记录代码中每个资源与云上真实资源 ID 的映射，以及属性快照。Terraform 据此计算差异、决定创建、更新还是删除。状态可能包含敏感信息，需要远程存储、加密和加锁，避免并发修改与泄露。

什么是配置漂移，如何处理？

真实资源因手工操作或其他工具与代码定义不一致。可以定期运行 plan 检测差异；对合理的手工变更补回代码，对不合理的通过 apply 恢复；通过权限收紧减少控制台直接修改。

IaC 与 AI 编程工具结合时要注意什么？

AI 可以快速生成模块和资源定义，但可能引入过宽的权限、公开的网络规则或不存在的参数。必须用 plan 审查变更，配合策略检查工具，并先在隔离环境验证，再推向生产。
