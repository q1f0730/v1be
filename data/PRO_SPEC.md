# 专业模式内容规范（每个概念一份 JSON 对象）

读者：已经看完小白版、想真正弄懂的人——准备面试、做技术评审、要和工程师平等对话的产品/开发者。
全部简体中文；英文术语保留原文并在首次出现时用括号给中文。可以用专业词，但每段要讲清楚。
**准确第一**：不编数字、不编版本号、不编 API。数值写成常见范围并说明前提（如「通常」「默认」「截至 2026 年」）。不确定的不写。

文件：data/pro/batch_XX.json，与 data/out/batch_XX.json 一一对应、顺序一致，是一个 JSON 数组。

## 字段（全部必填，除标注可选）
{
  "slug": "与小白版一致",
  "def": "专业定义，80–160 字。说清它是什么、属于哪一层、解决什么问题。",
  "how": ["工作原理/机制，4–6 条，按发生顺序或逻辑层次，每条 30–80 字"],
  "terms": [{"t": "术语 (English)", "d": "一句话精确解释，≤ 50 字"}],   // 4–6 个，和本概念强相关、比小白版更专业
  "code": {
    "lang": "python | javascript | typescript | bash | yaml | sql | json | http | text 之一",
    "title": "示例标题 ≤ 20 字",
    "src": "真实、能看懂、尽量可运行的代码/配置/命令/请求，8–30 行，带简短注释。不要伪造不存在的库或参数。",
    "note": "这段示例在说明什么，≤ 60 字"
  },
  "table": {"title": "≤ 16 字", "head": ["3–4 列"], "rows": [["3–5 行"]]},   // 关键参数/指标/方案对比，专业版的对照表，不要重复小白版
  "tradeoffs": [{"opt": "方案或做法", "pros": "优点 ≤ 40 字", "cons": "代价 ≤ 40 字", "when": "什么时候选 ≤ 40 字"}],   // 2–4 项
  "pitfalls": [{"bad": "专业人士也会犯的错 ≤ 50 字", "fix": "正确做法 ≤ 60 字"}],   // 3–4 项
  "checklist": ["上线/评审检查项，每条 ≤ 40 字"],   // 4–6 条
  "interview": [{"q": "有深度的面试/评审追问 ≤ 40 字", "a": "要点式回答 60–140 字"}],   // 3 题
  "refs": [{"title": "资料名", "url": "https://…"}]   // 2–4 个权威来源：官方文档、RFC、论文、维基百科、MDN 等。每个 URL 必须用 curl 实测返回 200/301/302 才能保留，打不开就换或删。
}

## 风格
- 和小白版互补，不重复比喻和翻车故事。
- 段落短、信息密度高，像一本好的技术手册。
- 与「用 AI 写代码/做产品」相关的地方点出来（Claude Code、Cursor、Agent 会在哪碰到它），但不硬凑。
- 不使用 emoji 开头（专业模式视觉要克制）。
