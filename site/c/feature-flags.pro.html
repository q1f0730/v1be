📐 01 · 定义

特性开关（Feature Flags / Feature Toggles）是在运行时通过配置决定某段代码路径是否启用的技术，让「部署代码」与「发布功能」解耦。它位于应用与发布管理层，支持灰度放量、A/B 实验、按用户或租户定向、紧急关停，也是主干开发（Trunk-Based Development）的配套手段。

⚙️ 02 · 原理
  1. 1

    代码中在新功能入口处调用开关判断，传入用户 ID、地区、套餐等评估上下文。

  2. 2

    开关定义存放在配置中心或开关服务，包含默认值、定向规则与放量百分比。

  3. 3

    SDK 拉取或订阅规则并缓存在本地，判断在进程内完成，避免每次网络调用。

  4. 4

    百分比放量通过对用户 ID 哈希分桶实现，保证同一用户结果稳定。

  5. 5

    功能全量且稳定后，删除开关判断代码与配置，避免长期积累成技术债。

🔤 03 · 术语
发布开关 (Release Toggle)
短期存在，用于逐步放出未完成或新功能。
运维开关 (Ops Toggle / Kill Switch)
出现问题时快速关闭某功能或降级。
实验开关 (Experiment Toggle)
把用户分组做 A/B 测试。
定向规则 (Targeting Rule)
按属性决定哪些用户看到哪个变体。
OpenFeature
CNCF 下的厂商中立特性开关 API 标准。
💻 04 · 代码
稳定哈希的百分比放量python
import hashlib

FLAGS = {
    "new_checkout": {"enabled": True, "rollout": 20,  # 20% 用户
                     "allow": {"tenant_internal"}},   # 内部租户全开
}

def bucket(flag: str, user_id: str) -> int:
    """同一用户对同一开关总落在同一个桶（0-99）"""
    h = hashlib.sha256(f"{flag}:{user_id}".encode()).hexdigest()
    return int(h[:8], 16) % 100

def is_enabled(flag: str, user_id: str, tenant: str) -> bool:
    cfg = FLAGS.get(flag)
    if not cfg or not cfg["enabled"]:   # 总开关，也是紧急关停入口
        return False
    if tenant in cfg["allow"]:
        return True
    return bucket(flag, user_id) < cfg["rollout"]

if is_enabled("new_checkout", user_id="u_42", tenant="acme"):
    pass  # 新结账流程
else:
    pass  # 旧流程

哈希里带上开关名，不同开关的放量人群互相独立；enabled 兼作紧急关停。

🕳️ 07 · 常见坑

  • ✗开关全量后从不清理，代码里分支越来越多

    ✓为发布开关设到期时间，全量后建任务删除

  • ✗用随机数决定放量，用户每次刷新结果不同

    ✓对用户 ID 做稳定哈希分桶

  • ✗开关服务不可用时功能行为未定义

    ✓SDK 本地缓存规则，并为每个开关设定安全默认值

  • ✗开关嵌套组合太多，测试覆盖不到

    ✓限制同时存在的开关数量，关键组合写自动化测试

🎤 09 · 面试追问
特性开关如何支持主干开发？

未完成的功能也能合入主干并部署，只是开关关闭，不影响用户。这样避免长期分支带来的合并冲突，发布节奏与开发节奏解耦，同时可在生产上对内部人员先开启验证。

开关评估应该放在服务端还是客户端？

服务端评估规则不外泄、结果可信；客户端评估响应快但规则与定向属性暴露给用户。敏感或付费功能必须服务端判定，前端开关仅用于展示层。

特性开关和 A/B 实验有什么关系？

实验依赖开关做分组曝光，但还需要稳定分流、曝光埋点、指标统计与显著性分析。普通开关只决定开或关，实验关心的是不同变体对指标的因果影响。
