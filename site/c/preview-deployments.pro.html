预览部署

Preview Deployments

📐 01 · 定义

预览部署（Preview Deployment）是在每个分支或 Pull Request 上自动构建并部署一份独立环境、分配唯一 URL 的实践，常见于 Vercel、Netlify、Cloudflare Pages 等平台。它让评审者、设计和产品在合并前直接点开真实运行的版本验证改动，是持续部署（CD）与代码评审之间的桥梁，生产环境不受影响。

⚙️ 02 · 原理
  1. 1

    平台通过 Git 集成监听推送事件；PR 打开或更新时触发构建流水线。

  2. 2

    使用预览环境的环境变量完成构建，生成不可变的部署产物，分配唯一 URL（按提交或按分支）。

  3. 3

    平台把预览链接以评论或状态检查的形式回写到 PR，供评审与自动化测试使用。

  4. 4

    E2E 测试、视觉回归、Lighthouse 等检查可直接对预览 URL 运行，结果作为合并门禁。

  5. 5

    PR 合并后，主分支触发生产部署；预览部署保留或按策略过期，对应的临时资源（如分支数据库）被清理。

🔤 03 · 术语
不可变部署 (Immutable Deployment)
每次部署生成独立且不再变化的产物和地址。
分支数据库 (Database Branching)
为预览环境创建隔离的数据库副本或分支。
部署保护 (Deployment Protection)
为预览链接加登录或密码，防止外泄。
状态检查 (Status Check)
回写到 PR 的构建/测试结果，可作为合并条件。
环境作用域变量 (Scoped Env Vars)
按 production / preview / development 区分的配置。
💻 04 · 代码
CI 中用 Vercel CLI 发预览yaml
# .github/workflows/preview.yml（Vercel Git 集成可自动完成，此为 CLI 方式）
name: Preview
on: pull_request
jobs:
  deploy:
    runs-on: ubuntu-latest
    env:
      VERCEL_ORG_ID: ${{ secrets.VERCEL_ORG_ID }}
      VERCEL_PROJECT_ID: ${{ secrets.VERCEL_PROJECT_ID }}
    steps:
      - uses: actions/checkout@v4
      - run: npm i -g vercel
      # 拉取 preview 环境的配置与环境变量
      - run: vercel pull --yes --environment=preview --token=${{ secrets.VERCEL_TOKEN }}
      - run: vercel build --token=${{ secrets.VERCEL_TOKEN }}
      # 部署预构建产物，输出预览 URL
      - run: vercel deploy --prebuilt --token=${{ secrets.VERCEL_TOKEN }} > url.txt
      - run: echo "Preview: $(cat url.txt)"

在 CI 中显式构建并部署预览环境，拿到 URL 后可继续跑 E2E 测试或评论到 PR。

📊 05 · 参数对比

预览环境的数据策略

策略隔离性成本适用
共享预发布数据库低，PR 间互相干扰低只读或轻量改动
每 PR 分支数据库高中，需自动清理涉及迁移的改动
Mock / 种子数据高低前端与演示
连接生产库无—禁止
⚖️ 06 · 方案取舍

平台原生预览（Git 集成）

优点零配置，链接自动回写 PR

代价依赖平台能力

适用前端与全栈 Web 项目

CI 自建预览环境

优点可定制，支持任意后端

代价维护成本高，需清理资源

适用复杂后端、Kubernetes 项目

只用单一 staging

优点简单

代价多个 PR 互相覆盖

适用团队小、改动少

🕳️ 07 · 常见坑

  • ✗预览环境使用生产密钥和生产数据库

    ✓为 preview 作用域配置独立的密钥与数据源

  • ✗预览链接公开可访问，泄露未发布功能

    ✓开启部署保护或 SSO 访问限制

  • ✗OAuth 回调只配了生产域名，预览登录失败

    ✓为预览域名配置回调或使用平台支持的通配方案

  • ✗临时资源从不清理，费用累积

    ✓PR 关闭时自动销毁分支数据库等资源

🎤 09 · 面试追问
预览部署与 staging 环境有何区别？

staging 是长期存在的单一环境，多个改动合并后在其中验证；预览部署按 PR 生成，彼此隔离、短期存在，能在合并前单独验证每个改动。两者常并存：PR 级预览做功能验收，staging 做集成和发布前验证。

预览环境的数据库怎么处理？

前端改动可用 Mock 或共享只读数据；涉及 schema 迁移的改动最好使用分支数据库，每个 PR 获得隔离副本，迁移互不干扰。绝不连接生产库，并确保 PR 关闭时自动销毁临时数据库。

预览部署如何融入 AI 编程流程？

Agent 提交 PR 后，平台自动生成预览链接，人类评审可直接点开验收界面效果，无需本地拉代码；也可让 Agent 对预览 URL 跑 E2E 测试或截图对比，把结果作为合并前的检查项。
