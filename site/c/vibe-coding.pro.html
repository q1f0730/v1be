氛围编程 (Vibe Coding)

Vibe Coding

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

氛围编程（Vibe Coding）由 Andrej Karpathy 在 2025 年初提出，指用自然语言描述意图、让 AI 生成并修改代码，开发者主要看运行效果而不逐行审读代码的开发方式。它极大降低了原型门槛，但把代码质量、安全和可维护性风险转移到了验证环节，适合探索期而非直接用于关键生产系统。

⚙️ 02 · 原理
  1. 1

    描述意图：用自然语言说明要做什么功能、界面长什么样、给谁用、做到什么程度算完成。

  2. 2

    AI 生成：编码 Agent 创建文件、安装依赖、写出可运行版本。

  3. 3

    运行观察：开发者运行应用，以界面和行为是否符合预期作为主要判断。

  4. 4

    反馈迭代：把报错、截图或「这里不对」直接反馈给 AI 继续修改。

  5. 5

    收敛固化：效果满意后，补测试、审查关键代码、做安全检查再上线。

🔤 03 · 术语
AI 辅助编程 (AI-assisted Coding)
开发者审读并理解 AI 代码，与纯 vibe coding 相对。
规格驱动 (Spec-driven)
先写清需求文档和验收标准，再让 AI 按规格实现。
检查点 (Checkpoint)
可回滚的状态快照，如 Git 提交或工具内置的回退点。
技术债 (Technical Debt)
为求快而留下的设计与质量问题，后期要付出修复成本。
人在回路 (Human-in-the-loop)
关键步骤由人确认或审查，而非完全自动。
💻 04 · 代码
给氛围编程加安全网bash
# 每次让 AI 大改之前：开分支 + 存档，随时可回退
git switch -c feature/ai-login        # 新建分支做实验
git add -A && git commit -m "checkpoint: before AI changes"

# 让 Claude Code 以非交互模式执行一个明确任务（-p 即 print 模式）
claude -p "给登录表单加邮箱格式校验，并补充对应单元测试"

# 看清 AI 改了什么，而不是只看界面
git diff --stat
git diff

# 跑测试与类型检查，作为客观验收（按你的项目替换命令）
npm test && npx tsc --noEmit

# 不满意就整体撤销
git restore . && git clean -fd

版本控制 + 自动化测试是氛围编程从「玩具」走向「可交付」的最低配置。

📊 05 · 参数对比

氛围编程的适用边界

场景适合程度前提条件
个人原型 / Demo高能随时推倒重来
内部小工具中高数据不敏感，有备份
对外产品 MVP中上线前人工审查安全与数据处理
支付、鉴权、医疗等低必须有专业审查与完整测试
⚖️ 06 · 方案取舍

纯氛围编程

优点最快出结果，门槛最低

代价代码不可控，安全漏洞难发现

适用一次性原型、学习探索

规格 + AI 实现 + 审查

优点质量可控，可维护

代价需要写需求和读代码

适用要长期维护或对外上线

测试先行再让 AI 实现

优点有客观验收标准

代价写测试需要一定能力

适用逻辑复杂、回归风险高

🕳️ 07 · 常见坑

  • ✗不用 Git，AI 改坏后无法回到能用的版本

    ✓每次大改前提交一次，改坏直接回退

  • ✗把含密钥、无鉴权的原型直接公开上线

    ✓上线前检查密钥、鉴权、输入校验与数据库权限

  • ✗同一会话无限追加需求，代码越来越乱

    ✓阶段性重开会话，带上清晰的现状说明和下一步目标

  • ✗只看界面效果，不看依赖和权限变更

    ✓审阅 git diff，重点看新增依赖、配置和网络请求

🎤 09 · 面试追问
Vibe coding 和 AI 辅助编程的本质区别？

在于是否理解并为代码负责。Vibe coding 以运行效果为准，基本不读代码；AI 辅助编程中开发者审查、理解并能解释 AI 写的每一部分。前者适合探索，后者是生产开发的合格标准。

团队引入氛围编程，评审应关注什么？

关注不可见风险：鉴权与权限、密钥处理、输入校验、数据库访问规则、依赖来源与许可证、错误处理与日志；要求有测试覆盖关键路径，并限制原型代码直接进入主干。

如何让 AI 产出更可维护？

给出项目规范文件（如 CLAUDE.md）约定结构与风格；先让 AI 出方案再实现；小步提交、每步可验证；要求补测试；定期让 AI 重构并解释设计，避免一次生成巨型文件。
