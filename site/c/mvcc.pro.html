多版本并发控制 (MVCC)

MVCC

📐 01 · 定义

多版本并发控制（MVCC）是数据库的并发控制机制：写操作创建数据的新版本而不覆盖旧版本，每个事务基于自己的快照读取可见版本，从而读不阻塞写、写不阻塞读。PostgreSQL、MySQL InnoDB、Oracle 等主流数据库都采用 MVCC，它是实现读已提交、可重复读、快照隔离的基础。

⚙️ 02 · 原理
  1. 1

    每个版本记录创建它的事务 ID 和删除它的事务 ID（PostgreSQL 为元组的 xmin/xmax）；InnoDB 在行上保存最近修改的事务 ID 与指向 undo 日志的回滚指针。

  2. 2

    事务开始或语句开始时获取快照，记录当时哪些事务已提交、哪些仍活跃。

  3. 3

    读取时沿版本链找到对当前快照可见的版本：PostgreSQL 在堆中保留多个元组，InnoDB 通过 undo 日志重建旧版本。

  4. 4

    写写冲突仍需行锁：两个事务改同一行时后者等待，在可重复读级别下可能因更新冲突而失败重试。

  5. 5

    不再被任何快照需要的旧版本由后台清理：PostgreSQL 的 VACUUM、InnoDB 的 purge 线程。

🔤 03 · 术语
快照 (Snapshot)
某一时刻已提交事务集合的视图，决定事务能看到哪些版本。
死元组 (Dead Tuple)
PostgreSQL 中已被更新或删除、对所有事务都不可见的旧行版本。
读视图 (Read View)
InnoDB 中判断版本可见性的结构，记录活跃事务 ID 范围。
写偏斜 (Write Skew)
快照隔离下两个事务读同一数据、各改不同行，合起来违反约束的异常。
事务 ID 回卷 (XID Wraparound)
PostgreSQL 32 位事务 ID 用尽的风险，需通过 VACUUM 冻结旧元组避免。
💻 04 · 代码
观察 PostgreSQL 的版本与膨胀sql
-- 每行的系统列：xmin 为创建它的事务 ID
SELECT xmin, xmax, id, balance FROM accounts WHERE id = 1;

UPDATE accounts SET balance = balance - 10 WHERE id = 1;
-- 再查：xmin 变了，说明是新元组；旧元组成为死元组
SELECT xmin, xmax, id, balance FROM accounts WHERE id = 1;

-- 各表死元组数量与最近一次自动清理时间
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC LIMIT 5;

-- 找出长时间未结束的事务：它们会阻止旧版本被清理
SELECT pid, state, now() - xact_start AS xact_age, left(query, 60)
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start LIMIT 5;

处于 idle in transaction 的会话持有旧快照，是表膨胀的常见元凶，可配置 idle_in_transaction_session_timeout。

⚖️ 06 · 方案取舍

MVCC

优点读写互不阻塞，读多场景并发高

代价需存储旧版本并后台清理

适用绝大多数 OLTP 业务

两阶段锁 (2PL)

优点可直接实现可串行化，无旧版本存储

代价读写互相阻塞，易死锁

适用冲突极少或需严格串行化的老系统

MVCC + 可串行化快照隔离 (SSI)

优点在 MVCC 上消除写偏斜

代价可能出现序列化失败需应用重试

适用强一致业务规则且能处理重试

🕳️ 07 · 常见坑

  • ✗连接池中事务开启后长时间不提交

    ✓设置事务和空闲事务超时，监控 xact_start 最老的会话

  • ✗以为可重复读能防止所有并发异常

    ✓识别写偏斜场景，用 SELECT ... FOR UPDATE 或可串行化级别

  • ✗大批量更新全表，瞬间产生大量死元组

    ✓分批更新，并在之后观察 autovacuum 或手动 VACUUM

  • ✗关闭 autovacuum 以「提升性能」

    ✓保持开启并按表调优阈值，否则膨胀与回卷风险更大

🎤 09 · 面试追问
MVCC 下为什么读不阻塞写？

写入不覆盖旧数据而是生成新版本，读事务依据自己的快照选择可见版本，所以不需要等写事务释放锁；写事务也不必等读者结束。只有两个事务同时写同一行时才需要行锁协调。

PostgreSQL 表膨胀的根因和处理？

UPDATE/DELETE 留下死元组，若存在长事务或复制槽持有旧快照，VACUUM 无法回收，表与索引持续变大。处理：找出并结束长事务，调优 autovacuum，必要时在线重整（如 pg_repack 扩展）或 VACUUM FULL（会锁表）。

快照隔离下的写偏斜如何发生？

例如规定至少一名医生值班，两个事务都读到两人在岗，各自把不同的人改为休息并提交，结果无人值班。两者改的是不同行，没有写写冲突。解决：对相关行加锁、用约束物化冲突，或使用可串行化隔离级别。
