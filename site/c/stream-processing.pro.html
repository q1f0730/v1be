流处理 (Flink)

Stream Processing

📐 01 · 定义

流处理（Stream Processing）是对持续到达的无界事件流进行增量、低延迟计算的数据处理范式，与按批处理有界数据集相对。Apache Flink 是代表性引擎，提供事件时间语义、水位线、窗口、有状态计算和基于检查点的容错，常用于实时风控、实时指标、实时特征和 CDC 数据同步。

⚙️ 02 · 原理
  1. 1

    从 Kafka 等消息系统或 CDC 源持续读取事件，事件携带业务发生时间（事件时间）。

  2. 2

    水位线（Watermark）声明「早于某时间的事件应已到齐」，驱动窗口触发，并容忍一定程度的乱序。

  3. 3

    按键分区后在窗口内聚合：滚动、滑动、会话窗口，或无窗口的持续聚合与流式 Join。

  4. 4

    算子状态保存在状态后端（内存或 RocksDB），引擎周期性做分布式快照（检查点）记录状态与源位点。

  5. 5

    故障时从最近检查点恢复状态并回退源位点重放；配合事务性或幂等输出可达到端到端精确一次。

🔤 03 · 术语
事件时间 (Event Time)
事件在业务中实际发生的时间，相对于被处理时的处理时间。
水位线 (Watermark)
表示事件时间进度的标记，用于判断窗口何时可以输出结果。
滚动窗口 (Tumbling Window)
固定长度、不重叠的时间窗口，如每 1 分钟一个。
检查点 (Checkpoint)
Flink 对全部算子状态与源偏移做的一致性快照，用于故障恢复。
迟到数据 (Late Data)
在水位线越过其窗口后才到达的事件，需丢弃、侧输出或更新结果。
💻 04 · 代码
Flink SQL 每分钟订单统计sql
-- 从 Kafka 读取订单，声明事件时间与 5 秒乱序容忍
CREATE TABLE orders (
  order_id STRING,
  amount   DECIMAL(10, 2),
  ts       TIMESTAMP(3),
  WATERMARK FOR ts AS ts - INTERVAL '5' SECOND
) WITH (
  'connector' = 'kafka',
  'topic' = 'orders',
  'properties.bootstrap.servers' = 'kafka:9092',
  'properties.group.id' = 'order-stats',
  'scan.startup.mode' = 'latest-offset',
  'format' = 'json'
);

-- 窗口表值函数：1 分钟滚动窗口
SELECT window_start, window_end,
       COUNT(*)    AS order_cnt,
       SUM(amount) AS gmv
FROM TABLE(
  TUMBLE(TABLE orders, DESCRIPTOR(ts), INTERVAL '1' MINUTES))
GROUP BY window_start, window_end;

水位线决定窗口何时输出：延迟超过 5 秒的事件默认不再计入已关闭窗口。

📊 05 · 参数对比

流处理引擎关键语义

语义含义工程影响
至少一次故障重放可能重复计算下游需幂等或去重
精确一次（状态）引擎内部状态不重不漏依赖检查点与可重放源
端到端精确一次输出到外部系统也不重复需事务性 Sink 或幂等写
事件时间按发生时间统计需设计水位线与迟到处理
处理时间按到达时间统计实现简单，但结果不可复现
⚖️ 06 · 方案取舍

Flink 等流引擎

优点毫秒到秒级延迟，强状态与时间语义

代价运维、状态管理和调试复杂

适用风控、实时特征等强实时场景

微批（如 Spark Structured Streaming）

优点与批处理统一 API，生态成熟

代价延迟通常受批间隔限制

适用分钟级延迟可接受、团队熟悉 Spark

定时批处理

优点最简单，易重跑与核对

代价延迟为小时或天级

适用报表与离线分析

🕳️ 07 · 常见坑

  • ✗用处理时间做业务统计，重跑结果对不上

    ✓使用事件时间与水位线，保证结果可复现

  • ✗水位线设得过紧，大量迟到数据被丢弃

    ✓按实际乱序分布设定延迟，并为迟到数据配置侧输出

  • ✗无限增长的状态（如无 TTL 的去重表）

    ✓为状态设置 TTL，或用窗口限定状态范围

  • ✗以为开了检查点就端到端精确一次

    ✓确认 Sink 支持事务或幂等写，否则仍可能重复

☑️ 08 · 检查清单
🎤 09 · 面试追问
水位线解决了什么问题？代价是什么？

事件会乱序到达，引擎需要知道何时某个事件时间窗口已经完整可以输出。水位线给出事件时间进度的估计。代价是延迟与完整性的权衡：等得越久结果越完整、输出越晚；等得太短会把迟到事件排除在外。

Flink 检查点如何保证状态一致？

JobManager 周期性向源注入屏障（barrier），屏障随数据流动；算子收到所有输入的屏障后对状态做快照，基于 Chandy-Lamport 思想的异步屏障快照。恢复时所有算子回到同一检查点，源回退到对应偏移重放，状态即不重不漏。

实时特征为什么常用流处理计算？

推荐、风控模型依赖最近几分钟的行为，如过去 5 分钟点击数、短时内交易次数。批处理延迟太高；流处理以滑动窗口持续更新并写入在线特征存储，同时需保证训练和推理的特征口径一致。
