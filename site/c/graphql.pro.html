GraphQL 查询语言

GraphQL

📐 01 · 定义

GraphQL 是一种 API 查询语言及其运行时规范，由 Facebook 开发并于 2015 年开源，现由 GraphQL Foundation 维护。服务端用强类型 Schema 描述数据图，客户端在一个端点上精确声明需要的字段与关联，服务端按查询结构返回同形状的 JSON。它属于 API 设计层，解决 REST 的过度获取、获取不足与多次往返问题。

⚙️ 02 · 原理
  1. 1

    服务端用 SDL 定义 Schema：对象类型、字段、参数，以及 Query、Mutation、Subscription 入口。

  2. 2

    客户端发送查询文档（通常 POST 到单一端点），声明所需字段的嵌套结构与变量。

  3. 3

    服务端解析并依据 Schema 校验查询，可在此加入深度、复杂度等自定义校验规则。

  4. 4

    执行阶段按字段调用解析器（resolver）获取数据，子字段的解析器以父对象为输入逐层执行。

  5. 5

    结果按查询形状组装为 JSON，字段级错误放入 errors 数组，部分成功时仍返回 data。

🔤 03 · 术语
Schema / SDL
用 Schema 定义语言描述的类型系统，是前后端契约。
解析器 (Resolver)
为某个字段获取数据的函数。
内省 (Introspection)
查询 Schema 自身结构的能力，供工具生成文档与代码。
DataLoader
在一次请求内批量合并与缓存加载，缓解 N+1 查询。
持久化查询 (Persisted Queries)
客户端只发送预注册查询的标识，限制任意查询。
💻 04 · 代码
Apollo Server 加深度限制typescript
import { ApolloServer } from "@apollo/server";
import { startStandaloneServer } from "@apollo/server/standalone";
import depthLimit from "graphql-depth-limit";

const typeDefs = `#graphql
  type Order { id: ID!, amount: Float! }
  type User  { id: ID!, name: String!, orders: [Order!]! }
  type Query { user(id: ID!): User }
`;

const resolvers = {
  Query: { user: (_: unknown, { id }: { id: string }) => db.users.find(id) },
  User:  { orders: (u: { id: string }) => db.orders.byUser(u.id) }, // 生产中用 DataLoader 批量
};

const server = new ApolloServer({
  typeDefs, resolvers,
  validationRules: [depthLimit(5)],   // 拒绝嵌套超过 5 层的查询
});
const { url } = await startStandaloneServer(server, { listen: { port: 4000 } });
console.log(url);
// 客户端：query { user(id: "1") { name orders { amount } } }

客户端只拿 name 与 orders.amount；depthLimit 在校验阶段拦截恶意深层嵌套。db 为示例数据层。

REST、GraphQL、gRPC 对比

维度RESTGraphQLgRPC
端点按资源多个 URL通常单一端点按服务方法
返回形状服务端决定客户端声明Protobuf 定义

⚖️ 06 · 方案取舍

GraphQL

优点按需取数、强类型、单次请求聚合

代价缓存、限流、安全需额外设计

适用多客户端、数据关系复杂

REST

优点简单、HTTP 缓存与工具成熟

代价过度/不足获取，多次往返

适用资源型 CRUD、公开 API

BFF（为前端定制的 REST 层）

优点按页面聚合，简单可控

代价每端维护一层，重复代码

适用端少、页面固定

🕳️ 07 · 常见坑

  • ✗不限制查询深度与复杂度，遭遇 DoS

    ✓加深度/复杂度限制、超时，公开 API 用持久化查询

  • ✗每个字段解析器单独查库，产生 N+1

    ✓用 DataLoader 批量加载，或在父解析器预取

  • ✗生产环境对外开放内省，暴露完整 Schema

    ✓按需关闭公开内省，并在解析器中做字段级授权

  • ✗只在网关做鉴权，忽略字段级权限

    ✓在解析器或指令层按用户校验每个敏感字段

🎤 09 · 面试追问
GraphQL 如何解决 N+1 问题？

解析器按字段逐个执行，列表中每个元素查一次关联会产生 N+1。DataLoader 在同一事件循环 tick 内收集所有 key，合并为一次批量查询并在请求内缓存结果。

GraphQL 为什么缓存比 REST 难？

通常所有查询都 POST 到同一 URL，HTTP 层无法按 URL 缓存；响应形状因查询而异。常用客户端规范化缓存、持久化查询配合 GET 与 CDN、或服务端按字段缓存。

GraphQL 如何做版本演进？

官方倡导无版本演进：新增字段不破坏旧查询，废弃字段用 @deprecated 标注并监控使用量，确认无人使用后再删除。必要时配合 Schema 变更检查工具在 CI 中拦截破坏性改动。
