二分定位 (Bisect)

Git Bisect

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

git bisect 是 Git 内置的二分查找工具，用于在提交历史中定位首个引入问题的提交。用户标记一个已知好的提交和一个已知坏的提交，Git 每次检出中间的提交供测试，根据结果缩小一半范围，N 个提交约需 log₂N 次测试。它属于版本控制与调试层，可配合脚本 git bisect run 完全自动化。

⚙️ 02 · 原理
  1. 1

    git bisect start 开启会话，git bisect bad 标记当前（或指定）坏提交，git bisect good <rev> 标记已知好提交。

  2. 2

    Git 检出两者之间大约中点的提交，进入分离 HEAD 状态，等待判断。

  3. 3

    开发者测试后执行 good 或 bad；无法测试（如编译失败）时执行 skip。

  4. 4

    重复直到范围缩小到一个提交，Git 输出 first bad commit 及其信息。

  5. 5

    git bisect reset 结束会话并回到开始前的分支；git bisect log 可保存过程并 replay 重放。

🔤 03 · 术语
二分查找 (Binary Search)
每次排除一半候选，复杂度为对数级。
git bisect run
传入脚本自动判断：退出码 0 为好，125 为跳过，1–127 其他值为坏。
git bisect skip
跳过无法判断的提交，可能导致结果给出一个范围。
回归 (Regression)
以前正常的功能在某次变更后出错。
分离 HEAD (Detached HEAD)
HEAD 直接指向某个提交而非分支，bisect 期间处于此状态。
💻 04 · 代码
用脚本自动二分bash
# 当前版本有 Bug，v1.4.0 时是正常的
git bisect start
git bisect bad HEAD
git bisect good v1.4.0

# 写一个判断脚本：退出码 0=好，1=坏，125=无法测试跳过
cat > /tmp/check.sh <<'EOF'
#!/bin/sh
npm ci --silent || exit 125        # 依赖装不上就跳过这个提交
npx vitest run tests/login.test.ts  # 测试通过返回 0，失败返回非 0
EOF
chmod +x /tmp/check.sh

# 全自动二分，结束时打印 first bad commit
git bisect run /tmp/check.sh

# 查看过程并结束会话，回到原分支
git bisect log
git bisect reset

测试脚本放在仓库外，避免检出旧提交时脚本消失；依赖安装失败用 125 跳过。

📊 05 · 参数对比

bisect 常用命令

命令作用备注
start / reset开始 / 结束会话reset 回到原分支
good / bad标记好坏可用 old/new 自定义术语

⚖️ 06 · 方案取舍

手动 bisect

优点无需写脚本，适合 UI 类问题

代价每步需人工判断，易误标

适用难以自动化验证的 Bug

git bisect run

优点全自动、可复现

代价需要可靠的判断脚本

适用能用测试或命令复现的 Bug

阅读 git log/blame 推断

优点快，无需检出

代价多因素问题容易判断错

适用范围很小或线索明确

🕳️ 07 · 常见坑

  • ✗把测试脚本放在仓库内，检出旧提交时脚本不存在

    ✓脚本放仓库外，或在脚本里从固定路径读取测试

  • ✗构建失败的提交被标记为 bad，误导结果

    ✓用退出码 125 / git bisect skip 跳过

  • ✗测试本身不稳定（flaky），结果随机

    ✓先保证复现脚本稳定，必要时多跑几次再判断

  • ✗结束后忘记 git bisect reset，仍在分离 HEAD

    ✓完成后立即 reset，或先用 bisect log 保存记录

☑️ 08 · 检查清单
🎤 09 · 面试追问
git bisect run 如何根据退出码判断？

退出码 0 表示好；125 表示无法测试，跳过；1 到 127 之间除 125 外表示坏；大于 127 或小于 0 会中止二分。脚本应只在确实复现 Bug 时返回非 0。

为什么保持小提交有助于 bisect？

二分定位的粒度是提交；一个提交混了大量改动，定位后仍要在大 diff 里找原因。原子化、能独立构建的小提交让定位结果直接指向根因。

合并提交多的历史能用 bisect 吗？

能。Git 会在提交图上选择中点；可用 --first-parent 只沿主干的第一父提交二分，先定位到哪次合并引入问题，再进入该分支细查。
