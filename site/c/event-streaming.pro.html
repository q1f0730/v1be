事件流平台 (Kafka)

Event Streaming

📐 01 · 定义

事件流平台（Event Streaming Platform）以持久化、只追加的分布式日志存储事件流，支持多个消费者按各自进度读取和回放历史数据。Apache Kafka 是代表：事件写入主题（topic）的分区（partition），按偏移量（offset）有序存储并按保留策略保存；消费者组实现并行消费与扩展。它是实时数据管道与流处理的中枢。

⚙️ 02 · 原理
  1. 1

    生产者把事件写入主题，按消息键（key）哈希选择分区；相同键的事件进入同一分区，保证该键内的顺序。

  2. 2

    每个分区是只追加的有序日志，事件获得递增的偏移量，并复制到多个 broker 以实现容错。

  3. 3

    事件按保留策略（时间、大小，或按键压缩）保存，被消费后不会立即删除。

  4. 4

    消费者以消费者组为单位订阅，组内各消费者分配不同分区并行处理；不同组彼此独立，各自维护偏移量。

  5. 5

    消费者提交偏移量记录进度，故障恢复或需要重算时可从指定偏移量或时间点回放。

🔤 03 · 术语
主题 (Topic)
事件的逻辑分类，由一个或多个分区组成。
分区 (Partition)
有序、只追加的日志，是并行与顺序保证的基本单位。
偏移量 (Offset)
事件在分区中的位置序号，消费者用它记录进度。
消费者组 (Consumer Group)
共享订阅的一组消费者，分区在组内分配。
日志压缩 (Log Compaction)
按键只保留最新值的保留策略，用于状态快照。
副本因子 (Replication Factor)
每个分区的副本数量，决定容错能力。
💻 04 · 代码
confluent-kafka 生产与消费python
from confluent_kafka import Producer, Consumer

conf = {"bootstrap.servers": "localhost:9092"}

# 生产者：同一 order_id 作为 key，保证该订单事件有序
p = Producer(conf)
for status in ["created", "paid", "shipped"]:
    p.produce("orders", key="order-42", value=f'{{"status":"{status}"}}')
p.flush()                                   # 等待全部送达

# 消费者：组名决定独立进度；不同组可各自完整读取同一主题
c = Consumer({**conf, "group.id": "analytics",
              "auto.offset.reset": "earliest",   # 无进度时从头读（可回放）
              "enable.auto.commit": False})
c.subscribe(["orders"])
for _ in range(10):
    msg = c.poll(1.0)
    if msg is None or msg.error():
        continue
    print(msg.partition(), msg.offset(), msg.key(), msg.value())
    c.commit(message=msg)                   # 处理成功后再提交偏移量
c.close()

键决定分区与顺序，消费者组决定独立进度；处理后手动提交偏移量，实现至少一次语义。

消息队列与事件流对比

维度传统消息队列事件流平台
消费后消息通常被删除按保留策略保留
回放一般不支持可从任意偏移量回放
多消费方需额外配置交换机/广播多个消费者组各自独立读取
顺序队列级或无保证分区内有序
典型产品RabbitMQ、SQSKafka、Redpanda、Pulsar、Kinesis
⚖️ 06 · 方案取舍

自建 Kafka 集群

优点完全可控、生态丰富

代价运维复杂（容量、升级、监控）

适用有平台团队的大规模场景

托管事件流服务

优点免运维、弹性扩展

代价成本较高，存在厂商绑定

适用中小团队、云原生

轻量队列（SQS、Redis Streams）

优点简单便宜

代价回放与生态能力有限

适用吞吐不高、无需回放

🕳️ 07 · 常见坑

  • ✗业务量很小就引入 Kafka 集群

    ✓先评估队列或托管服务，确有回放与高吞吐需求再引入

  • ✗需要全局顺序却使用多个分区

    ✓顺序只在分区内保证，按业务键分区，必要时接受单分区吞吐上限

  • ✗处理前提交偏移量，崩溃导致消息丢失

    ✓处理成功后提交，并让消费者幂等

  • ✗分区数设置过少，后期扩展消费者无效

    ✓按预期峰值吞吐规划分区数，增加分区会改变键到分区的映射

🎤 09 · 面试追问
Kafka 如何保证消息顺序？

Kafka 只保证单个分区内的顺序。生产者用业务键（如订单 ID）分区，同一键的事件进入同一分区，从而保证该键的事件有序。若需要全局顺序只能用单分区，牺牲并行度；同时需注意生产者重试可能导致乱序，可开启幂等生产者。

消费者组的分区分配规则是什么？

一个分区在同一时刻只分配给组内一个消费者，一个消费者可处理多个分区。因此组内消费者数超过分区数时，多余的消费者会空闲。不同消费者组相互独立，各自完整消费同一主题。

事件流平台为什么适合做 CDC 和数据管道？

它持久保存有序事件，多个下游（搜索索引、数据仓库、缓存失效）可各自按进度消费，互不影响；新系统上线时可从头回放历史事件补齐数据；出错时也能重置偏移量重新处理。
