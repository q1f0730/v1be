📐 01 · 定义

GitHub Actions 是 GitHub 内置的 CI/CD 与自动化平台：在仓库 .github/workflows/ 下用 YAML 定义工作流，由推送、PR、定时、手动等事件触发，在 GitHub 托管或自托管的 Runner 上执行作业。它通过可复用的 Action 生态组合构建、测试、发布与部署，是开源与中小团队最常用的流水线方案。

⚙️ 02 · 原理
  1. 1

    事件（push、pull_request、schedule、workflow_dispatch 等）触发工作流文件中声明的 on 条件。

  2. 2

    工作流包含若干 job，默认并行，可用 needs 声明依赖；每个 job 在全新的 Runner 环境中运行。

  3. 3

    job 由 steps 组成：uses 调用 Action（如 actions/checkout），run 执行 shell 命令。

  4. 4

    密钥存于仓库或环境的 Secrets，通过表达式注入，并在日志中自动打码；GITHUB_TOKEN 由平台按 permissions 自动签发。

  5. 5

    matrix 并行测试多版本，缓存加速依赖安装，concurrency 取消过时运行，环境保护规则控制部署审批。

🔤 03 · 术语
Workflow / Job / Step
工作流包含作业，作业包含按顺序执行的步骤。
Runner
执行作业的机器，分 GitHub 托管与自托管。
GITHUB_TOKEN
每次运行自动生成的仓库令牌，权限由 permissions 控制。
Matrix 策略
按参数组合生成多个并行作业，如多个 Node 版本。
OIDC 联合身份
工作流用短期令牌换取云厂商临时凭证，免存长期密钥。
💻 04 · 代码
最小可用的 CI 工作流yaml
# .github/workflows/ci.yml
name: CI
on:
  push:
    branches: [main]
  pull_request:
permissions:
  contents: read            # 最小权限
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true  # 同分支新推送取消旧运行
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node: [20, 22]
    steps:
      - uses: actions/checkout@v4      # 安全要求高时固定到提交 SHA
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
          cache: npm
      - run: npm ci
      - run: npm test
        env:
          API_KEY: ${{ secrets.API_KEY }}   # 来自仓库 Secrets

显式声明 permissions，按需注入 Secrets；第三方 Action 建议固定到提交 SHA。

⚖️ 06 · 方案取舍

GitHub 托管 Runner

优点免维护、干净环境

代价私有仓库按分钟计费，硬件规格有限

适用大多数 CI 任务

自托管 Runner

优点可用内网与 GPU，成本可控

代价需维护与安全隔离，公共仓库风险高

适用特殊硬件或内网部署

OIDC 访问云

优点无长期密钥，权限可按分支限定

代价需在云侧配置信任关系

适用部署到云平台

🕳️ 07 · 常见坑

  • ✗在 run 中直接拼接 PR 标题等不可信输入导致脚本注入

    ✓先赋给环境变量再引用，不在脚本中内联 ${{ }} 不可信值

  • ✗pull_request_target 中检出并运行 PR 代码

    ✓避免该组合；需要密钥的流程与不可信代码分离

  • ✗不声明 permissions，令牌权限过大

    ✓顶层设为只读，按 job 授予必要写权限

  • ✗第三方 Action 用可变标签引用

    ✓固定到完整提交 SHA，并用依赖更新工具跟进

🎤 09 · 面试追问
pull_request 与 pull_request_target 的区别？

pull_request 在 PR 合并后的代码上下文中运行，来自 Fork 时不提供密钥、令牌只读；pull_request_target 在基础分支上下文运行，可访问密钥与写权限，用于给 PR 打标签等。若在其中检出并执行 PR 代码，等于把密钥交给不可信代码。

如何在 Actions 中安全地部署到云？

使用 OIDC：工作流向云厂商出示 GitHub 签发的身份令牌，换取短期凭证，信任策略限定仓库、分支或环境；配合环境保护规则与审批，避免在 Secrets 中保存长期访问密钥。

CI 很慢，从哪些方面优化？

缓存依赖与构建产物；按改动路径过滤触发；拆分并行 job 与测试分片；concurrency 取消过时运行；只在必要时跑端到端测试；使用更大规格 Runner 或自托管。
