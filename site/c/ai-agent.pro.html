AI 智能体 (Agent)

📐 01 · 定义

AI 智能体（AI Agent）是以大模型为决策核心、在循环中自主规划、调用工具、观察结果并调整行动直至完成目标的系统，位于模型之上的编排层。与固定流程的工作流不同，Agent 由模型动态决定下一步做什么。Claude Code、Cursor Agent 等编码 Agent 就是读代码、改文件、跑命令的典型实现。

⚙️ 02 · 原理
  1. 1

    接收目标与上下文（系统提示、规则文件、可用工具列表），模型先产出计划或直接选择第一步动作。

  2. 2

    以工具调用形式执行动作：读写文件、运行命令、搜索、调用 API，由运行时实际执行。

  3. 3

    把工具结果作为观察（Observation）回填上下文，模型据此判断进展、修正计划或处理错误。

  4. 4

    重复“思考-行动-观察”循环，直到模型认为目标完成、达到轮次/预算上限或需要人工介入。

  5. 5

    复杂系统会引入记忆、子 Agent 分工、检查点与权限控制，以支撑长任务和降低风险。

🔤 03 · 术语
ReAct
交替生成推理与行动的 Agent 范式，是多数工具型 Agent 的基础。
工作流 (Workflow)
由代码预定义步骤、模型只负责局部的编排方式，可预测性更高。
子 Agent (Subagent)
被主 Agent 派出、拥有独立上下文执行子任务的 Agent。
停止条件 (Stopping Condition)
目标完成、轮次上限、预算耗尽或需要人工确认时结束循环。
Agent 运行时 (Harness)
围绕模型的执行框架，负责工具执行、权限、上下文管理。
💻 04 · 代码
最小 Agent 循环python
def run_agent(client, model, tools, impls, goal, max_turns=10):
    """impls: {工具名: python 函数}，实际执行由这里完成"""
    msgs = [{"role": "user", "content": goal}]
    for _ in range(max_turns):                      # 轮次上限防死循环
        r = client.messages.create(model=model, max_tokens=2048,
                                   tools=tools, messages=msgs)
        msgs.append({"role": "assistant", "content": r.content})
        if r.stop_reason != "tool_use":             # 不再调用工具即完成
            return "".join(b.text for b in r.content if b.type == "text")
        results = []
        for b in r.content:
            if b.type == "tool_use":
                try:
                    out = impls[b.name](**b.input)
                except Exception as e:              # 错误回传给模型自我修正
                    out = f"error: {e}"
                results.append({"type": "tool_result",
                                "tool_use_id": b.id, "content": str(out)})
        msgs.append({"role": "user", "content": results})
    return "达到轮次上限，任务未完成"

基于 Anthropic Messages API 的思考-行动-观察循环，含轮次上限与错误回传。

📊 05 · 参数对比

工作流 vs Agent

维度工作流Agent
控制流代码预先定义模型动态决定
可预测性高，易测试低，需评测与监控
适合任务步骤固定的流程开放、步骤未知的任务
成本延迟可控轮次多，波动大
⚖️ 06 · 方案取舍

单 Agent + 丰富工具

优点上下文统一，实现简单

代价长任务上下文膨胀

适用多数编码与操作任务

多 Agent 分工

优点并行、上下文隔离

代价协调成本高，token 消耗大

适用可拆分的大规模调研类任务

固定工作流

优点稳定、便宜

代价无法应对意外情况

适用流程明确且高频

🕳️ 07 · 常见坑

  • ✗能用工作流解决的也上 Agent

    ✓先用最简单方案，确有开放性需求再引入 Agent

  • ✗没有轮次和预算上限

    ✓设置最大轮次、token 和时间预算，超限交还给人

  • ✗给 Agent 生产环境写权限且无确认

    ✓最小权限、沙箱运行，不可逆操作需人工批准

  • ✗只看最终结果不看过程轨迹

    ✓记录完整轨迹，用于评测、排错和发现危险行为

🎤 09 · 面试追问
什么情况下应该用 Agent 而不是工作流？

当任务步骤无法预先确定、需要根据中间结果动态决策，且错误可被检测和恢复时适合 Agent，例如在陌生代码库中修 bug。若步骤固定、对稳定性和成本要求高，工作流更合适。很多生产系统是工作流中嵌入局部 Agent。

Agent 长任务中最常见的失败模式？

上下文被工具输出填满后遗忘目标；陷入重复尝试同一失败操作的循环；过早宣布完成而未验证；误用工具造成副作用。对策包括上下文压缩、外部进度文件、强制验证步骤、轮次上限和检查点。

如何评估一个 Agent？

构建贴近真实的任务集和可自动判定的结果检查（如测试是否通过），统计成功率、平均轮次、token 成本和时长；同时审阅轨迹看是否有危险或低效行为。由于存在随机性，每个任务应多次运行取统计值。
