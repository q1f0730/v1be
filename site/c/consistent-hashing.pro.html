一致性哈希

Consistent Hashing

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

一致性哈希（Consistent Hashing）是一种把键映射到节点的分布方法：键和节点都映射到同一个哈希环上，键归属于顺时针方向遇到的第一个节点。增删节点时只有相邻区间的键需要迁移，约为总量的 1/N，而非普通取模哈希那样几乎全部重映射。常用于分布式缓存、存储分片和负载均衡。

⚙️ 02 · 原理
  1. 1

    建环：把哈希值空间首尾相接成环，例如 0 到 2³²−1 的整数空间。

  2. 2

    放节点：对每个节点标识做哈希，映射到环上的若干位置（虚拟节点）。

  3. 3

    定位键：对键做哈希，沿环顺时针找到第一个节点位置，即为该键的归属节点。

  4. 4

    增删节点：只影响新节点与其前驱之间的键区间，其余键保持原有归属不变。

  5. 5

    虚拟节点：每个物理节点在环上放多个点，使负载更均匀，并可按机器权重调整。

🔤 03 · 术语
哈希环 (Hash Ring)
首尾相连的哈希值空间，节点与键都映射在上面。
虚拟节点 (Virtual Node)
一个物理节点在环上的多个映射点，用于均衡负载。
取模哈希 (Modulo Hashing)
hash(key) % N，节点数变化时几乎所有键都重映射。
Rendezvous 哈希 (HRW)
为每个键选择与之组合哈希值最大的节点，无需维护环。
Jump 一致性哈希
Google 提出的无内存开销算法，适合节点编号连续的场景。
💻 04 · 代码
带虚拟节点的哈希环python
import bisect, hashlib

def h(s: str) -> int:
    return int(hashlib.md5(s.encode()).hexdigest(), 16) % (2**32)

class Ring:
    def __init__(self, nodes, vnodes=100):
        self.ring = sorted((h(f"{n}#{i}"), n) for n in nodes for i in range(vnodes))
        self.keys = [k for k, _ in self.ring]

    def get(self, key: str) -> str:
        i = bisect.bisect(self.keys, h(key)) % len(self.keys)  # 顺时针第一个
        return self.ring[i][1]

keys = [f"user:{i}" for i in range(10000)]
r3 = Ring(["A", "B", "C"])
r4 = Ring(["A", "B", "C", "D"])
moved = sum(r3.get(k) != r4.get(k) for k in keys)
print(f"新增一个节点后迁移比例: {moved / len(keys):.1%}")   # 约 25%，取模哈希约 75%

从 3 节点扩到 4 节点只迁移约 1/4 的键；虚拟节点越多分布越均匀。

📊 05 · 参数对比

键分配算法对比

算法节点变化时迁移量特点
取模哈希几乎全部最简单，不适合动态扩缩
一致性哈希环约 1/N需维护环，用虚拟节点均衡
Rendezvous 哈希约 1/N无需环，查找需遍历所有节点
Jump 哈希约 1/N无内存开销，只适合尾部增删
⚖️ 06 · 方案取舍

一致性哈希

优点扩缩容迁移少，去中心化

代价需虚拟节点才能均衡

适用缓存集群、无中心的存储

固定槽位映射

优点迁移以槽为单位，可控

代价需维护槽到节点的映射表

适用如 Redis Cluster 的 16384 槽

中心目录

优点可任意迁移单个分片

代价目录服务成为依赖

适用需要精细控制数据放置

🕳️ 07 · 常见坑

  • ✗不用虚拟节点，几个节点在环上分布不均导致负载倾斜

    ✓每个节点设置足够多的虚拟节点，并按容量设权重

  • ✗各客户端节点列表或哈希函数不一致，路由结果不同

    ✓统一哈希函数与节点配置，由配置中心下发

  • ✗以为一致性哈希能解决热点键

    ✓热点键需要副本、本地缓存或拆分，不能靠哈希分布解决

🎤 09 · 面试追问
为什么取模哈希扩容代价大？

hash(key) % N 中 N 一变，绝大多数键的余数都会改变，从 3 台扩到 4 台约有 3/4 的键换节点，对缓存意味着大面积失效、穿透到数据库。一致性哈希只迁移约 1/N。

虚拟节点解决了什么问题？

物理节点少时在环上的位置随机，各自负责的区间大小差异很大，负载不均；节点下线时其区间全部压给一个后继。虚拟节点把每台机器打散成许多小区间，负载更均匀，下线时压力分摊到多台机器。

Redis Cluster 用的是一致性哈希吗？

不是环形一致性哈希，而是固定 16384 个哈希槽，用 CRC16(key) 对 16384 取模确定槽，再由集群维护槽到节点的映射。扩缩容时迁移槽而非重算全部键，效果类似但更可控。
