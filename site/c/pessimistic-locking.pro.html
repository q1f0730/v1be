悲观并发控制

Pessimistic Locking

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

悲观锁（Pessimistic Locking）是在读取数据时就加锁，阻止其他事务并发修改，直到本事务提交或回滚才释放。数据库中通常通过 SELECT … FOR UPDATE 等加锁读实现。它用排队等待换取正确性，适合冲突频繁、必须串行处理的短事务。

⚙️ 02 · 原理
  1. 1

    事务开始后，用加锁读（如 SELECT … FOR UPDATE）锁定目标行。

  2. 2

    其他事务对这些行的加锁读或写入会阻塞，直到锁被释放；普通 MVCC 读不受影响。

  3. 3

    持锁事务基于已锁定的最新数据完成计算并写入，然后提交，锁随之释放。

  4. 4

    可用 NOWAIT 立即失败、SKIP LOCKED 跳过已锁行，或设置锁超时，避免无限等待。

  5. 5

    跨请求或跨服务的场景可用数据库咨询锁或分布式锁，但需处理持有者崩溃。

🔤 03 · 术语
FOR UPDATE
排他行锁，阻止他人修改和加锁读取这些行。
FOR SHARE
共享行锁，允许他人读但阻止修改。
NOWAIT
遇到已被锁的行立即报错，不等待。
SKIP LOCKED
跳过已被锁的行，常用于数据库任务队列。
咨询锁 (Advisory Lock)
PostgreSQL 提供的由应用定义含义的锁。
锁粒度 (Lock Granularity)
锁覆盖范围：行、页、表，粒度越粗并发越低。
💻 04 · 代码
扣库存与任务领取sql
-- 场景一：扣库存，锁住商品行后再判断
BEGIN;
SET LOCAL lock_timeout = '3s';          -- 等锁最多 3 秒（PostgreSQL）
SELECT stock FROM products WHERE id = 42 FOR UPDATE;
-- 应用判断 stock >= 1 后：
UPDATE products SET stock = stock - 1 WHERE id = 42;
INSERT INTO orders (product_id, qty) VALUES (42, 1);
COMMIT;

-- 场景二：多个 worker 并发领取任务，互不阻塞
BEGIN;
SELECT id, payload FROM jobs
WHERE status = 'pending'
ORDER BY id
LIMIT 1
FOR UPDATE SKIP LOCKED;
-- 拿到 id 后：
UPDATE jobs SET status = 'running', started_at = now() WHERE id = $1;
COMMIT;

FOR UPDATE 串行化同一行的修改；SKIP LOCKED 让多个消费者各取一行。

📊 05 · 参数对比

加锁读选项

写法遇到已锁行典型用途
FOR UPDATE等待扣库存、改余额
FOR UPDATE NOWAIT立即报错交互式操作快速失败
FOR UPDATE SKIP LOCKED跳过该行任务队列并发领取
FOR SHARE等待写锁释放校验父记录存在且不被改
⚖️ 06 · 方案取舍

行级悲观锁

优点冲突时排队，结果确定

代价持锁期间阻塞，可能死锁

适用热点行高频写入

SKIP LOCKED 队列

优点无需额外中间件即可并发消费

代价高吞吐下不如专用消息队列

适用中小规模后台任务

分布式锁（Redis 等）

优点可跨服务、跨数据库

代价需处理过期、时钟与持有者崩溃

适用无法用单库锁表达时

🕳️ 07 · 常见坑

  • ✗加锁读放在事务外（自动提交），锁立即释放

    ✓确保 FOR UPDATE 与后续写在同一事务中

  • ✗持锁期间调用支付等外部接口

    ✓外部调用移出事务，或改为状态机异步处理

  • ✗条件列无索引，锁住大量无关行

    ✓为加锁条件建索引，缩小锁范围

  • ✗多行加锁顺序不定，引发死锁

    ✓按主键排序加锁，并配置锁超时

🎤 09 · 面试追问
SKIP LOCKED 适合做消息队列吗？

适合中小规模：利用已有数据库、与业务数据同事务提交、无需新组件。局限是高吞吐下轮询与行锁开销大、缺少消息队列的路由与重投机制。PostgreSQL 9.5 和 MySQL 8.0 起支持该语法。

为什么不直接用原子 UPDATE 扣库存？

能用就优先用：UPDATE … SET stock = stock - 1 WHERE id = ? AND stock > 0，看受影响行数即可。需要先读出数据做复杂判断（多表校验、计算优惠）时，才需要 FOR UPDATE 锁住再算。

分布式锁的主要风险是什么？

持有者因 GC 停顿或网络分区超过租期，锁被他人获取，导致两方同时操作。缓解方法是使用单调递增的 fencing token，让存储端拒绝旧 token 的写入，并缩短临界区。
