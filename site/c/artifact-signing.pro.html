制品签名与溯源 (Sigstore / SLSA)

Artifact Signing

🧸 回到小白版

📐 01 · 定义

制品签名与溯源是软件供应链完整性保障：签名证明制品（如容器镜像、二进制包）由可信身份发布且未被篡改；溯源证明（Provenance）记录它由哪个源码提交、在什么构建平台、用什么流程构建。Sigstore 提供基于 OIDC 身份的免密钥签名与透明日志；SLSA 框架定义构建完整性的分级要求。

⚙️ 02 · 原理
  1. 1

    CI 构建出制品后，以内容摘要（digest）而非可变标签作为签名对象。

  2. 2

    Sigstore 免密钥模式下，Cosign 用 CI 的 OIDC 令牌向 Fulcio 申请短期证书，证书绑定工作流身份。

  3. 3

    签名与证书记录写入 Rekor 透明日志，任何人可审计，私钥用后即弃，无需长期保管。

  4. 4

    构建平台生成 in-toto 格式的 SLSA 溯源证明，包含源码仓库、提交、构建入口与参数，并同样签名附加到制品。

  5. 5

    部署前由准入控制器或流水线校验签名身份与溯源内容，不满足策略的制品拒绝运行。

🔤 03 · 术语
Cosign
Sigstore 的签名与验证工具，支持容器镜像与任意文件。
Fulcio
Sigstore 的证书颁发机构，根据 OIDC 身份签发短期签名证书。
Rekor
Sigstore 的透明日志，记录签名事件，防止事后伪造或抵赖。
SLSA
Supply-chain Levels for Software Artifacts，按级别定义构建溯源与防篡改要求。
in-toto 证明 (Attestation)
描述制品相关声明（如溯源、SBOM）的签名元数据格式。
💻 04 · 代码
GitHub Actions 签名并生成溯源yaml
# .github/workflows/release.yml 片段；Action 版本以官方文档为准
permissions:
  contents: read
  packages: write
  id-token: write          # 允许获取 OIDC 令牌，用于免密钥签名
  attestations: write
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: sigstore/cosign-installer@v3
      - id: push
        uses: docker/build-push-action@v6
        with:
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}
      - name: 用摘要签名（不要签可变标签）
        run: cosign sign --yes ghcr.io/${{ github.repository }}@${{ steps.push.outputs.digest }}
      - uses: actions/attest-build-provenance@v2
        with:
          subject-name: ghcr.io/${{ github.repository }}
          subject-digest: ${{ steps.push.outputs.digest }}
          push-to-registry: true
# 验证：cosign verify ghcr.io/org/app@sha256:... \
#   --certificate-identity-regexp '^https://github.com/org/app/' \
#   --certificate-oidc-issuer https://token.actions.githubusercontent.com

推送到 GHCR 前需先登录（docker/login-action）；验证时必须同时限定签名身份与签发者。

📊 05 · 参数对比

SLSA v1.0 构建轨道级别

级别要求概要防护效果
Build L0无要求无保证
Build L1存在溯源证明知道制品如何构建，便于排查
Build L2托管构建平台生成并签名溯源防止构建后篡改制品或溯源
Build L3构建平台加固，构建间隔离、签名密钥不可被构建访问防止构建过程中被篡改
⚖️ 06 · 方案取舍

Sigstore 免密钥签名

优点无需管理长期私钥，身份可审计

代价依赖 OIDC 与公共基础设施可用性

适用开源项目与云上 CI

KMS 托管密钥签名

优点企业可控，可离线或私有部署

代价需要密钥轮换与权限管理

适用受监管或内网隔离环境

只依赖镜像仓库权限

优点零额外工作

代价仓库凭证泄露即可推送恶意镜像

适用不推荐用于生产

🕳️ 07 · 常见坑

  • ✗对 latest 等可变标签签名或部署

    ✓以摘要签名，并在部署清单中引用摘要

  • ✗验证时只检查有签名，不检查是谁签的

    ✓限定证书身份（仓库与工作流）与 OIDC 签发者

  • ✗签名了却没有在部署侧强制验证

    ✓在集群准入（如 policy-controller、Kyverno）中强制校验

  • ✗长期私钥存放在 CI 变量中

    ✓改用免密钥签名或 KMS，限制谁能触发签名工作流

🎤 09 · 面试追问
免密钥签名如何证明是谁签的？

签名时 CI 向 Fulcio 出示 OIDC 令牌，Fulcio 签发一张几分钟有效、内含身份信息（如仓库与工作流路径）的证书；签名事件写入 Rekor 透明日志并带时间戳。验证者校验证书链、身份字段与日志记录，即可确认签名在证书有效期内由该身份产生。

签名和溯源证明分别回答什么问题？

签名回答「这个制品是否由可信身份发布且未被改动」；溯源回答「它是从哪份源码、在哪个平台、以什么步骤构建的」。只有签名时，攻击者若控制了签名身份仍可签恶意制品；溯源让验证方能进一步要求制品来自指定仓库与受保护分支。

为什么要用摘要而不是标签？

标签是可变指针，同一标签可被重新推送指向不同内容；摘要是内容的哈希，内容一变摘要就变。对摘要签名、在部署中引用摘要，才能保证验证通过的正是被运行的那份内容，避免验证后被替换。
