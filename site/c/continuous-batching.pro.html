连续批处理 (Continuous Batching)

Continuous Batching

📐 01 · 定义

连续批处理（Continuous Batching，也称迭代级调度或 in-flight batching）是 LLM 推理服务的调度方式：调度器在每一步解码迭代时重新组批，完成的请求立即移出，新请求立即加入，而不是等整批全部生成结束。该思想由 Orca（OSDI 2022）系统化提出，现已是 vLLM、SGLang、TGI、TensorRT-LLM 等引擎的标准能力。

⚙️ 02 · 原理
  1. 1

    LLM 生成分为预填充（prefill，一次处理整个提示）和解码（decode，每步生成一个 Token）两个阶段。

  2. 2

    静态批处理中，一批请求必须一起开始、一起结束，短回答完成后其位置空转，等待最长的请求。

  3. 3

    连续批处理以单次迭代为调度粒度：每步结束检查是否有请求生成了结束符或达到长度上限，立即释放其资源。

  4. 4

    空出的容量立即分配给等待队列中的新请求，受最大并发序列数和单步最大 Token 数等预算约束。

  5. 5

    分块预填充（chunked prefill）把长提示切块，与正在解码的请求混合在同一步中，减少长提示对他人延迟的冲击。

🔤 03 · 术语
迭代级调度 (Iteration-level Scheduling)
每生成一步重新决定批内成员的调度策略。
预填充/解码 (Prefill/Decode)
处理提示的计算密集阶段与逐 Token 生成的带宽密集阶段。
分块预填充 (Chunked Prefill)
把长提示拆成多块分步处理，与解码请求共批。
max-num-seqs
vLLM 中单次迭代可同时处理的最大序列数，控制并发上限。
抢占 (Preemption)
KV 缓存不足时暂停部分请求，释放显存后再重算或换回。
💻 04 · 代码
并发压测 OpenAI 兼容服务python
# pip install openai ；假设已用推理引擎在本地 8000 端口启动服务
import asyncio, time
from openai import AsyncOpenAI

client = AsyncOpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")
MODEL = "Qwen/Qwen2.5-7B-Instruct"     # 与服务端加载的模型一致

async def one(i: int) -> int:
    r = await client.chat.completions.create(
        model=MODEL,
        messages=[{"role": "user", "content": f"写一段 {50 + i % 5 * 100} 字的介绍"}],
        max_tokens=512,
    )
    return r.usage.completion_tokens

async def main(concurrency: int = 32):
    t0 = time.perf_counter()
    tokens = await asyncio.gather(*(one(i) for i in range(concurrency)))
    dt = time.perf_counter() - t0
    print(f"并发 {concurrency}: {sum(tokens) / dt:.0f} 输出 tok/s, 总耗时 {dt:.1f}s")

for c in (1, 8, 32):
    asyncio.run(main(c))

长短不一的请求混合时，连续批处理的优势最明显；同时应记录 TTFT 和 P99 延迟，不只看吞吐。

批处理策略对比

策略调度粒度GPU 利用率延迟特征
不批处理单请求很低单请求最快，排队严重
静态批处理整个请求受最长请求拖累短请求被迫等待
动态批处理等待时间窗口内凑批中增加凑批等待
连续批处理每次解码迭代高新请求可快速加入
⚖️ 06 · 方案取舍

调大最大并发序列

优点吞吐提升，GPU 更饱满

代价单请求 TPOT 变长，KV 缓存压力增大

适用离线或吞吐优先的服务

调小最大并发序列

优点单请求速度更快、更稳定

代价吞吐下降，排队增加

适用实时对话、低延迟要求

开启分块预填充

优点长提示不再造成他人延迟尖刺

代价长提示自身 TTFT 可能略增

适用提示长度差异大的混合负载

🕳️ 07 · 常见坑

  • ✗只用单个请求测速，误判服务容量

    ✓按真实并发与长度分布压测，记录吞吐、TTFT 与 P99

  • ✗max_tokens 设置过大，预留与抢占频繁

    ✓按业务需要设置合理上限，监控抢占次数

  • ✗在应用层再自行攒批，叠加额外等待

    ✓直接并发发送请求，让引擎负责调度

  • ✗忽视长提示对整体延迟的影响

    ✓开启分块预填充或对超长请求单独路由

🎤 09 · 面试追问
为什么静态批处理会浪费 GPU？

LLM 输出长度差异巨大。静态批处理中整批必须等最长的请求结束，已完成的短请求占着批位空转，新请求也无法加入，导致 GPU 大量时间在处理填充位。连续批处理在每一步都回收与补充批位，消除了这种空转。

连续批处理和 PagedAttention 是什么关系？

连续批处理决定每一步谁在批里，需要频繁加入和移出请求；PagedAttention 以小块分配 KV 缓存，减少碎片，使同样显存能容纳更多并发序列，并让请求加入与释放的内存管理代价很低。两者结合是 vLLM 高吞吐的关键。

吞吐和延迟如何权衡？

并发越高，每步要处理的序列越多，总吞吐上升，但每个请求的每 Token 耗时变长，接近算力上限后排队时间急剧增加。应先定义 TTFT 和 TPOT 的 SLO，再在满足 SLO 的前提下找出最大吞吐对应的并发设置。
