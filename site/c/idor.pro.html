不安全的直接对象引用

IDOR

📐 01 · 定义

不安全的直接对象引用（Insecure Direct Object Reference，IDOR）指用用户可控的 ID 直接访问对象、却不校验当前用户是否有权访问的漏洞。它属于失效的访问控制（Broken Access Control），该类在 OWASP Top 10 2021 中居首，API 安全中称为 BOLA。

⚙️ 02 · 原理
  1. 1

    接口通过 URL、参数或请求体接收对象标识，如 GET /api/invoices/1024。

  2. 2

    服务端完成了认证，确认请求者已登录，但直接按 ID 查询并返回对象。

  3. 3

    攻击者修改标识为他人的值，如 1025，或批量枚举，服务端照常返回。

  4. 4

    同样的缺陷可出现在读取、修改、删除以及文件下载等任何按 ID 操作的接口。

  5. 5

    修复方式是在每次访问时把对象归属或权限与当前用户比对，或在查询中加入归属条件。

🔤 03 · 术语
BOLA
对象级授权失效，OWASP API Top 10 第一项，即 API 版 IDOR。
失效的访问控制 (Broken Access Control)
用户能执行超出其权限的操作的一类漏洞。
水平越权 (Horizontal Escalation)
访问同级别其他用户的数据。
垂直越权 (Vertical Escalation)
普通用户执行管理员等更高权限操作。
行级安全 (Row-Level Security)
数据库按策略限制每个用户可见或可改的行。
💻 04 · 代码
按归属查询修复 IDORpython
from fastapi import FastAPI, Depends, HTTPException

app = FastAPI()

# 有漏洞：只按 ID 查，任何登录用户都能看任何发票
@app.get("/v1/invoices/{invoice_id}")
def get_invoice_bad(invoice_id: int, user=Depends(current_user)):
    return db.query_one("SELECT * FROM invoices WHERE id = %s", (invoice_id,))

# 修复：查询条件中带上归属，不存在与无权统一返回 404
@app.get("/v2/invoices/{invoice_id}")
def get_invoice(invoice_id: int, user=Depends(current_user)):
    row = db.query_one(
        "SELECT * FROM invoices WHERE id = %s AND owner_id = %s",
        (invoice_id, user.id),
    )
    if row is None:
        raise HTTPException(status_code=404)
    return row

current_user 与 db 为项目自有依赖；关键是授权条件在服务端查询中强制执行。

🕳️ 07 · 常见坑

  • ✗改用 UUID 就认为修复了 IDOR

    ✓UUID 可能经日志、分享链接泄露，仍需授权检查

  • ✗只检查读取接口，忽略更新和删除

    ✓所有按 ID 操作的接口都做对象级授权

  • ✗信任请求体中的 user_id 字段

    ✓当前用户身份只从服务端会话或令牌获取

  • ✗AI 生成的 CRUD 接口没有归属校验

    ✓在提示和规则文件中明确要求对象级授权并补测试

🎤 09 · 面试追问
IDOR 为什么这么常见？

认证通常由框架统一处理，开发者容易误以为“已登录就安全”；对象级授权需要每个接口结合业务数据单独判断，难以自动化，且扫描器很难发现，因为它需要理解哪些数据属于谁。AI 生成的 CRUD 代码也常遗漏这一步。

用不可猜测的 ID 能防 IDOR 吗？

只能增加攻击难度，不能防御。ID 可能通过分享链接、日志、前端响应、Referer 等途径泄露，一旦拿到就能访问。正确做法是每次访问都校验权限，不可猜测 ID 只作为纵深防御。

如何系统地测试 IDOR？

准备至少两个不同用户（及不同角色、租户）的账号，对每个携带对象 ID 的接口，用 A 的会话请求 B 的对象，覆盖读、改、删和批量接口，断言返回 403 或 404。可以把这类用例写入自动化测试，防止回归。
