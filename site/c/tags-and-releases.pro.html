标签与发行版 (Tag / Release)

Tags & Releases

🧸 回到小白版

📐 01 · 定义

Tag（标签）是 Git 中指向特定提交的命名引用，常用于标记版本号；Release（发行版）是 GitHub 等平台在标签之上提供的发布对象，附带说明、更新日志与二进制附件。二者属于版本管理与交付层，配合语义化版本，为回滚、审计和自动化发布提供稳定锚点。

⚙️ 02 · 原理
  1. 1

    轻量标签只是指向提交的引用；附注标签是独立对象，包含作者、日期、说明，并可 GPG/SSH 签名。

  2. 2

    git push 默认不推送标签，需显式推送单个标签或使用 --tags / --follow-tags。

  3. 3

    平台基于标签创建 Release，可自动生成两版之间的变更说明并上传构建产物。

  4. 4

    CI 可监听标签推送（如 tags: ['v*']）触发构建、打包、发布到包仓库或部署。

  5. 5

    回滚或排查时，可直接检出或比较两个标签，定位版本间的差异。

🔤 03 · 术语
附注标签 (Annotated Tag)
带作者、日期与说明的标签对象，发布版本推荐使用。
轻量标签 (Lightweight Tag)
仅是指向提交的名字，不含额外元数据。
签名标签 (Signed Tag)
用 GPG 或 SSH 密钥签名，可验证发布者身份。
预发布 (Pre-release)
如 v2.0.0-rc.1，SemVer 中优先级低于正式版。
变更日志 (Changelog)
按版本记录新增、修复与破坏性变更的文档。
💻 04 · 代码
打标签并发布 Releasebash
# 确认在要发布的提交上（通常是 main 最新且 CI 通过）
git switch main && git pull --ff-only

# 创建附注标签（推荐），-m 写版本说明
git tag -a v1.2.0 -m "v1.2.0: 新增导出功能"

# 标签不会随 git push 自动推送，需单独推送
git push origin v1.2.0

# 用 GitHub CLI 创建 Release，自动生成变更说明
gh release create v1.2.0 --generate-notes ./dist/app.zip

# 查看与比较
git tag --list "v1.*"
git log --oneline v1.1.0..v1.2.0

# 发布前打错了：删除本地与远程标签（已被他人使用则不要这样做）
git tag -d v1.2.0 && git push origin --delete v1.2.0

版本标签用附注标签并单独推送；已公开的标签不要移动或复用。

📊 05 · 参数对比

标签类型对比

类型元数据可验证推荐用途
轻量标签无否本地临时标记
附注标签作者、日期、说明否正式版本
签名标签附注 + 签名是开源发布、供应链要求
⚖️ 06 · 方案取舍

手动打标签发布

优点简单直观，完全可控

代价易漏步骤，说明质量不稳

适用小项目、低频发布

基于提交规范自动发布

优点版本号与日志自动生成

代价依赖提交信息纪律与工具配置

适用高频发布的库与服务

标签触发 CI 部署

优点可追溯、可重复

代价需保护标签防误触发

适用生产发布流程

🕳️ 07 · 常见坑

  • ✗以为 git push 会带上标签

    ✓显式推送标签，或配置 push.followTags=true

  • ✗修改已公开的标签指向新提交

    ✓标签不可变，出错就发布新的补丁版本号

  • ✗在未通过 CI 的提交上打发布标签

    ✓只在主干 CI 通过的提交上打标签，并开启标签保护规则

  • ✗版本号随意，破坏性变更只升补丁位

    ✓遵循语义化版本，破坏性变更升主版本

☑️ 08 · 检查清单
🎤 09 · 面试追问
附注标签和轻量标签有何区别？

轻量标签只是一个指向提交的引用；附注标签是 Git 中独立存储的对象，包含打标者、时间、说明，可签名。git describe 默认只考虑附注标签，正式发布推荐附注或签名标签。

为什么不能移动已发布的标签？

他人和缓存（包仓库、CI、依赖锁定）已记录该标签对应的提交，移动后不同人拿到的同名版本内容不同，破坏可复现与审计，甚至被用于供应链攻击。正确做法是发布新版本号。

如何用标签驱动自动化发布？

CI 监听 v* 标签推送：检出该标签、构建测试、生成产物与校验和、创建 Release 并发布到包仓库或部署。配合标签保护规则限制谁能创建，产物签名与 SBOM 增强可信度。
