📐 01 · 定义

REST（Representational State Transfer）是 Roy Fielding 在 2000 年博士论文中提出的架构风格，核心约束有无状态、可缓存、统一接口等。REST API 通常指基于 HTTP、以资源为中心、用标准方法和状态码操作资源表示的 Web 接口，是前后端与服务间通信最常见的约定。

⚙️ 02 · 原理
  1. 1

    把业务对象建模为资源，用名词 URI 标识，如 /users/42/orders。

  2. 2

    用 HTTP 方法表达操作：GET 读取、POST 创建、PUT 替换、PATCH 部分修改、DELETE 删除。

  3. 3

    请求与响应携带资源表示（多为 JSON），通过 Content-Type 与 Accept 协商格式。

  4. 4

    每个请求自带全部上下文（如 Authorization 头），服务端不保存会话状态，便于水平扩展。

  5. 5

    用状态码表达结果，用 Cache-Control、ETag 等头支持缓存与条件请求。

🔤 03 · 术语
资源 (Resource)
可被 URI 标识的业务实体或集合。
无状态 (Stateless)
服务端不依赖前序请求保存的会话上下文。
HATEOAS
响应中携带可执行操作的链接，驱动客户端状态转换。
条件请求 (Conditional Request)
用 If-None-Match / If-Match 配合 ETag 实现缓存与并发控制。
Problem Details
RFC 9457 定义的 JSON 错误响应格式。
💻 04 · 代码
资源创建与条件更新http
POST /v1/orders HTTP/1.1
Host: api.example.com
Authorization: Bearer <token>
Content-Type: application/json
Idempotency-Key: 7f3c2a10

{"sku": "A-100", "qty": 2}

HTTP/1.1 201 Created
Location: /v1/orders/981
ETag: "v1"
Content-Type: application/json

{"id": 981, "status": "pending", "qty": 2}

PATCH /v1/orders/981 HTTP/1.1
If-Match: "v1"
Content-Type: application/merge-patch+json

{"qty": 3}

HTTP/1.1 412 Precondition Failed
Content-Type: application/problem+json

{"type": "about:blank", "title": "Precondition Failed", "status": 412}

201 + Location 表示创建成功；If-Match 携带 ETag 实现乐观并发，版本不符返回 412。

📊 05 · 参数对比

常用状态码语义

状态码含义典型场景
200 / 201 / 204成功 / 已创建 / 无内容查询、创建、删除
400 / 422请求格式错 / 语义校验失败参数缺失、字段非法
401 / 403未认证 / 无权限缺 token、越权访问
404 / 409不存在 / 状态冲突资源缺失、重复创建
429 / 503限流 / 暂不可用请求过多、维护中
⚖️ 06 · 方案取舍

REST

优点通用、可缓存、工具链成熟

代价多资源聚合需多次请求

适用公开 API、CRUD 为主的业务

GraphQL

优点客户端按需取字段，一次聚合

代价缓存与限流更复杂，易出慢查询

适用多端、数据关系复杂的前端

gRPC

优点强类型、二进制、高性能流式

代价浏览器直连需代理，可读性差

适用内部微服务间调用

🕳️ 07 · 常见坑

  • ✗所有错误都返回 200，在 body 里放 code

    ✓使用正确的 HTTP 状态码，错误体采用 Problem Details 格式

  • ✗URI 里用动词，如 /getUser、/deleteOrder

    ✓URI 用名词表示资源，动作交给 HTTP 方法

  • ✗列表接口不分页，一次返回全部数据

    ✓强制分页并限制最大页大小

  • ✗混淆 401 与 403

    ✓未认证返回 401，已认证但无权限返回 403

🎤 09 · 面试追问
PUT 和 PATCH 的区别？

PUT 用完整表示替换目标资源，语义上幂等；PATCH 发送部分修改指令，是否幂等取决于补丁格式。常见补丁格式有 JSON Merge Patch（RFC 7396）和 JSON Patch（RFC 6902）。

REST 为什么强调无状态？

每个请求自包含，任意实例都能处理，便于负载均衡、水平扩展与故障转移；也让缓存和重试更简单。会话信息改由 token 携带或存在共享存储中。

多数「REST API」真的符合 REST 吗？

大多只做到资源 URI + HTTP 方法 + JSON，缺少 HATEOAS 等约束，按 Richardson 成熟度模型约在第 2 级。工程上这通常够用，关键是语义一致和文档清晰。
