K8s资源请求与硬限制

Resource Requests & Limits

📐 01 · 定义

Kubernetes 资源请求（requests）与限制（limits）是为容器声明 CPU 和内存的两个值：requests 是调度器据以选择节点并保证分配的资源量，limits 是运行时可使用的上限。超 CPU 限制被节流，超内存限制被 OOMKill。两者的组合还决定 Pod 的 QoS 等级与驱逐优先级。

⚙️ 02 · 原理
  1. 1

    调度：调度器只看 requests，把 Pod 放到剩余可分配资源足够的节点上。

  2. 2

    CPU 请求：通过 cgroup 权重在 CPU 争用时按比例分配，不争用时可以超用。

  3. 3

    CPU 限制：通过 CFS 配额限制每个周期内可用的 CPU 时间，超出即被节流等待。

  4. 4

    内存限制：容器内存超过 limit 会被内核 OOM Killer 终止，状态显示 OOMKilled。

  5. 5

    QoS 与驱逐：节点资源紧张时按 QoS 等级与超用程度驱逐，BestEffort 最先被驱逐。

🔤 03 · 术语
QoS 等级
三档服务质量等级，由 requests 与 limits 的设置方式自动判定。
CPU 节流 (Throttling)
容器用完 CFS 配额后被暂停到下一周期，表现为延迟升高。
OOMKilled
容器因超出内存限制被内核终止的状态。
超售 (Overcommit)
节点上 limits 总和大于实际资源，依赖并非所有容器同时满载。
LimitRange / ResourceQuota
命名空间级的默认值、上下限与总量配额。
💻 04 · 代码
容器资源配置yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 3
  selector: {matchLabels: {app: api}}
  template:
    metadata: {labels: {app: api}}
    spec:
      containers:
      - name: api
        image: registry.example.com/api:1.8.3
        resources:
          requests:
            cpu: "500m"        # 调度保证 0.5 核
            memory: "512Mi"
          limits:
            memory: "512Mi"    # 内存 limit = request，避免节点内存超售
            # 不设 CPU limit：避免节流，靠 requests 在争用时分配
# QoS 为 Burstable；若 CPU、内存都设 limit 且等于 request 则为 Guaranteed

常见做法：内存 limit 等于 request，CPU 只设 request；CPU limit 按场景权衡。

📊 05 · 参数对比

QoS 等级判定

等级条件驱逐顺序
Guaranteed每个容器 CPU 与内存都设置且 limit = request最后
Burstable至少一个容器设了 request 或 limit，但不满足上条居中
BestEffort所有容器都未设置 request 与 limit最先
⚖️ 06 · 方案取舍

设置 CPU limit

优点防止单个容器占满节点 CPU

代价可能频繁节流，尾延迟升高

适用多租户、需严格隔离

不设 CPU limit

优点空闲 CPU 可被利用，延迟更稳

代价依赖准确的 requests 防止争抢

适用延迟敏感、requests 设置合理

Guaranteed QoS

优点驱逐优先级最低，表现可预期

代价资源利用率较低

适用数据库等关键有状态服务

🕳️ 07 · 常见坑

  • ✗不设 requests，节点被过度调度后频繁驱逐

    ✓根据监控的实际用量设置 requests，并用 LimitRange 设默认值

  • ✗CPU limit 设得过低，CPU 使用率不高却延迟飙升

    ✓监控节流指标，调高或去掉 CPU limit

  • ✗JVM 等运行时未按容器内存限制配置堆，频繁 OOMKilled

    ✓让运行时感知容器限制，堆上限留出非堆内存余量

  • ✗requests 远大于实际用量，集群资源大量闲置

    ✓定期按 P95 用量调整，可借助 VPA 推荐值

☑️ 08 · 检查清单
🎤 09 · 面试追问
requests 和 limits 分别影响什么？

requests 影响调度和争用时的资源保证：调度器按它找节点，CPU 争用时按其比例分配。limits 影响运行时上限：CPU 超出被节流，内存超出被 OOMKill。两者共同决定 QoS 等级和节点压力下的驱逐顺序。

CPU 使用率才 40% 为何还被节流？

CFS 配额按短周期计算，监控的使用率是长时间平均值。多线程程序可能在一个周期的前一小段用完配额，随后整个周期都被暂停，平均看并不高但请求延迟明显变长。看节流指标而非平均使用率。

内存为什么通常建议 limit 等于 request？

内存是不可压缩资源，超用无法像 CPU 那样节流回收。若 limit 远高于 request，节点内存被超售，压力大时会触发驱逐或 OOM，影响其他 Pod；设为相等让调度时的预留与实际上限一致，行为更可预期。
