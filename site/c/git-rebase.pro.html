变基 (Rebase)

Git Rebase

📐 01 · 定义

Rebase（变基）是 Git 的历史改写操作：找出当前分支相对目标基点（upstream）多出的提交，把它们按顺序作为补丁重新应用到新基点之上，生成内容相同但哈希不同的新提交。它用来得到线性历史、整理提交（压缩、改信息、重排），代价是改写了已有提交的身份。

⚙️ 02 · 原理
  1. 1

    Git 计算当前分支与 upstream 的合并基（merge base），收集从合并基到 HEAD 之间、upstream 中尚不存在的提交。

  2. 2

    把 HEAD 重置到 upstream 指向的提交，然后逐个“摘取”（cherry-pick 语义）原提交，重新生成新的提交对象。

  3. 3

    任一提交应用冲突时暂停，开发者解决后 git add 并执行 git rebase --continue，或用 --abort 回到开始前状态。

  4. 4

    交互式 rebase（-i）先打开待办列表，可对每个提交选择 pick、reword、squash、fixup、drop 或调整顺序。

  5. 5

    完成后分支指针指向新提交，旧提交仍可通过 reflog 找回，直到被垃圾回收；已推送分支需强制推送才能更新远端。

🔤 03 · 术语
合并基 (Merge Base)
两个分支最近的共同祖先提交，rebase 从这里之后开始收集提交。
交互式变基 (Interactive Rebase)
git rebase -i，可压缩、改写、重排、删除提交。
--force-with-lease
强推前确认远端仍是你上次看到的状态，比 --force 安全。
reflog
本地记录 HEAD 与分支指针每次移动的日志，用于找回 rebase 前的提交。
--autosquash
配合 fixup! 前缀的提交，在交互式 rebase 时自动排到目标提交后。
rerere
reuse recorded resolution，记住冲突解决方式，下次相同冲突自动套用。
💻 04 · 代码
功能分支变基到最新 mainbash
# 1. 取回远端最新代码
git fetch origin

# 2. 把当前功能分支的提交重放到 origin/main 之上
git rebase origin/main
# 出现冲突：编辑文件后
git add <冲突文件>
git rebase --continue      # 或 git rebase --abort 放弃

# 3. 推送前整理最近 3 个提交（压缩、改信息）
git rebase -i HEAD~3

# 4. 分支已推送过，必须强推；用 lease 防止覆盖别人的提交
git push --force-with-lease

# 5. 后悔了：查看 reflog 找回旧位置
git reflog
git reset --hard HEAD@{5}   # 以 reflog 实际输出为准

展示 fetch→rebase→整理→安全强推→reflog 回滚的完整闭环。

📊 05 · 参数对比

rebase 与 merge 对比

维度git mergegit rebase
历史形态保留分叉，产生合并提交线性，无合并提交
提交哈希不变被重放的提交全部变化
冲突处理一次性解决可能逐个提交解决
对协作者影响无已共享的分支需对方重新同步
可追溯性完整保留真实时间线更易读，但丢失分支上下文
⚖️ 06 · 方案取舍

rebase 后 fast-forward 合并

优点历史线性，git log 与 bisect 更友好

代价需强推功能分支，冲突可能多次解决

适用个人短生命周期分支

普通 merge

优点不改写历史，协作零风险

代价合并提交多，历史图复杂

适用长期共享分支、发布分支

Squash merge（平台合并）

优点每个 PR 一个提交，main 很干净

代价丢失 PR 内部细粒度提交

适用PR 内提交杂乱、团队不需细节时

🕳️ 07 · 常见坑

  • ✗在多人共享的分支上 rebase 并强推

    ✓遵守黄金法则：只 rebase 未共享或仅自己使用的分支

  • ✗用 git push --force 覆盖了同事刚推的提交

    ✓改用 --force-with-lease，并开启分支保护禁止强推 main

  • ✗冲突解决一半就慌乱执行 reset，以为代码丢了

    ✓先 git rebase --abort 回到起点，或用 reflog 找回原提交

  • ✗让 AI Agent 自动 rebase 却不检查结果

    ✓要求 Agent 列出改写的提交并在完成后跑测试，再推送

🎤 09 · 面试追问
rebase 为什么会改变提交哈希？

提交哈希由内容树、父提交、作者、提交者信息和时间等计算。rebase 把提交重放到新的父提交之上，父指针变了，哈希必然变化，即使代码改动完全相同。因此 rebase 本质是创建新提交，旧提交只是不再被分支引用。

--force 和 --force-with-lease 有何区别？

--force 无条件用本地分支覆盖远端。--force-with-lease 会检查远端分支是否仍等于本地记录的远端跟踪引用，若他人在此期间推送了新提交则拒绝，避免误删别人的工作。注意先 fetch 会刷新跟踪引用，削弱保护效果。

rebase 出错如何恢复？

进行中可 git rebase --abort 回到开始前。已完成可用 git reflog 找到 rebase 前 HEAD 的位置，再 git reset --hard 到该位置；ORIG_HEAD 通常也指向操作前的提交。旧对象在被垃圾回收前一直可找回。
