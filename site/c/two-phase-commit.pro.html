两阶段提交 (2PC)

Two-Phase Commit

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

两阶段提交（Two-Phase Commit，2PC）是让多个参与者（数据库、资源管理器）对一个分布式事务达成要么全部提交、要么全部回滚的原子提交协议。由协调者先询问所有参与者能否提交（准备阶段），全部同意后再统一下达提交（提交阶段）。它保证原子性，但存在阻塞和性能问题。

⚙️ 02 · 原理
  1. 1

    准备阶段：协调者向所有参与者发送 prepare 请求，要求各自做好提交准备。

  2. 2

    参与者投票：把事务数据和准备状态持久化并保持锁，然后回复同意或拒绝。

  3. 3

    决策：全部同意则协调者记录提交决定；任一拒绝或超时则决定回滚整个事务。

  4. 4

    提交阶段：协调者把决定发给所有参与者，参与者执行提交或回滚并释放锁。

  5. 5

    阻塞问题：参与者投同意后若协调者宕机，只能持锁等待协调者恢复后的决定。

🔤 03 · 术语
协调者 (Coordinator)
驱动协议、收集投票并做出最终提交或回滚决定的角色。
参与者 (Participant)
持有部分事务数据、参与投票并执行决定的资源管理器。
不确定状态 (In-doubt)
已投同意但未收到最终决定，必须等待而不能自行决定。
XA
X/Open 定义的分布式事务接口标准，多种数据库支持。
Saga
用一系列本地事务加补偿操作替代分布式原子提交的模式。
💻 04 · 代码
PostgreSQL 的准备事务sql
-- 需先设置 max_prepared_transactions > 0（默认 0，修改需重启）
-- 参与者 1（库 A）：执行本地操作后进入准备状态
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
PREPARE TRANSACTION 'tx-20261020-001';   -- 持久化，连接断开也不丢

-- 参与者 2（库 B）
BEGIN;
UPDATE accounts SET balance = balance + 100 WHERE id = 9;
PREPARE TRANSACTION 'tx-20261020-001';

-- 协调者：两边都准备成功后，分别下达提交
COMMIT PREPARED 'tx-20261020-001';
-- 任一方失败则对已准备的一方执行：
-- ROLLBACK PREPARED 'tx-20261020-001';

-- 排查遗留的不确定事务（会一直持有锁）
SELECT gid, prepared, database FROM pg_prepared_xacts;

数据库只提供参与者能力，协调者逻辑需由事务管理器实现；遗留准备事务会阻塞清理。

📊 05 · 参数对比

分布式事务方案对比

方案一致性主要代价
2PC / XA原子提交（强）阻塞、持锁时间长、性能低
3PC减少部分阻塞假设网络有界，实践少用
Saga最终一致需设计补偿，存在中间状态
Outbox + 消息最终一致异步延迟，消费者需幂等
⚖️ 06 · 方案取舍

2PC

优点真正的原子性，编程模型简单

代价协调者故障会阻塞，吞吐受限

适用少量参与者、低频关键操作

Saga

优点无全局锁，可用性高

代价补偿逻辑复杂，中间状态可见

适用跨微服务的长业务流程

重新划分边界

优点变成单库本地事务，最简单

代价需调整服务或数据归属

适用强一致数据可归到同一服务

🕳️ 07 · 常见坑

  • ✗协调者不持久化决定，宕机恢复后不知该提交还是回滚

    ✓协调者在发出提交前把决定写入持久日志

  • ✗遗留的准备事务长期持锁，阻塞其他写入与 VACUUM

    ✓监控 pg_prepared_xacts，建立超时人工处理流程

  • ✗在高并发微服务调用链上使用 2PC，延迟和锁争用飙升

    ✓改用 Saga 或 Outbox，或把强一致数据合并到同一服务

🎤 09 · 面试追问
2PC 为什么是阻塞协议？

参与者投同意后就放弃了单方面回滚的权利，必须等待协调者决定；若协调者此时宕机，参与者不知道其他人的投票，既不能提交也不能回滚，只能持锁等待协调者恢复，期间相关数据不可用。

2PC 和 Raft 等共识算法有什么区别？

2PC 解决原子提交：所有参与者都必须同意，任一否决即回滚，不容忍参与者故障。共识解决多副本对同一值达成一致，只需多数派，能容忍少数故障。可以用共识复制协调者状态来缓解 2PC 的阻塞。

微服务里为什么很少用 2PC？

各服务通常使用不同存储，未必支持 XA；2PC 要求所有参与者同步在线并持锁，降低可用性和吞吐，服务间耦合紧。实践中多用 Saga、Outbox 实现最终一致，或调整边界避免跨服务强一致。
