代码审查

Code Review

📐 01 · 定义

代码审查（Code Review）是代码合并前由他人系统检查变更的质量门禁，通常以 Pull Request（GitHub）或 Merge Request（GitLab）形式进行。它属于协作与质量保障层，目标是发现缺陷、保证可维护性、传播知识和统一规范。在 AI 生成代码日益增多的背景下，人类审查是最终责任环节。

⚙️ 02 · 原理
  1. 1

    作者在分支上完成改动，提交 PR 并写明目的、改动范围、测试方式和风险。

  2. 2

    CI 自动运行 lint、类型检查、测试和安全扫描，机器能查的问题先由机器拦截。

  3. 3

    审查者阅读 diff 和上下文，关注正确性、设计、安全、可读性和测试是否充分。

  4. 4

    通过评论提出问题或建议，区分必须修改与可选建议，作者回应并迭代。

  5. 5

    满足审批规则（如至少一人批准、CI 通过、代码所有者认可）后合并。

🔤 03 · 术语
Pull Request (PR)
请求将分支合并到目标分支，并承载讨论与审查。
CODEOWNERS
GitHub 文件，指定路径的负责人，可设为必需审查者。
分支保护 (Branch Protection)
规定合并前必须满足的审查和检查条件。
Nit
非阻塞的小建议，如命名、格式偏好。
LGTM
Looks Good To Me，表示审查通过。
💻 04 · 代码
用 gh CLI 完成审查bash
# 作者：创建 PR 并填写说明
gh pr create --title "feat: 订单列表分页" \
  --body "目的: 解决大客户列表超时
测试: 新增 3 个单测, 本地 pnpm test 通过
风险: 接口新增可选参数, 向后兼容"

# 审查者：检出 PR 到本地运行验证
gh pr checkout 123
pnpm test

# 查看 diff 与 CI 状态
gh pr diff 123
gh pr checks 123

# 提交审查结论
gh pr review 123 --request-changes --body "分页参数缺少上限校验"
gh pr review 123 --approve --body "LGTM"

PR 描述写清目的、测试与风险；审查者本地验证后给出明确结论。

📊 05 · 参数对比

审查关注点优先级

优先级关注点示例
高正确性与安全越权、注入、数据丢失、竞态
高设计与边界职责划分、接口兼容性
中测试充分性边界与失败路径是否覆盖
低风格与命名应交给 linter 和 formatter
⚖️ 06 · 方案取舍

强制人工审查所有 PR

优点质量与知识共享好

代价等待时间长

适用团队协作、生产代码

AI 审查辅助 + 人工终审

优点快速发现常见问题

代价存在误报与漏报

适用PR 量大、AI 生成代码多

小 PR 快速合并

优点审查易、冲突少

代价需要拆分功能与特性开关

适用持续交付团队

🕳️ 07 · 常见坑

  • ✗上千行的 PR 一次提交

    ✓拆成可独立审查的小 PR，通常几百行以内

  • ✗审查时大量讨论格式问题

    ✓格式交给自动化工具，人专注逻辑与设计

  • ✗AI 生成的代码看起来规范就直接批准

    ✓同样审查逻辑、边界和安全，并要求附测试

  • ✗评论只说“这样不好”

    ✓说明原因并给出具体建议或替代方案

🎤 09 · 面试追问
代码审查最应该关注什么？

优先关注机器难以发现的问题：业务逻辑是否正确、边界和错误处理、权限与安全、并发与数据一致性、设计是否合理、是否有足够测试。格式和简单风格问题应交给 linter 和 formatter，避免浪费审查注意力。

如何审查 AI 生成的代码？

AI 代码通常表面规范但可能存在幻觉 API、遗漏边界、过度实现或与项目约定不一致。审查时要核对调用的接口是否真实存在、检查测试是否真正验证行为、关注安全敏感点，并确认改动范围没有超出需求。

为什么提倡小 PR？

审查质量随 PR 变大而迅速下降，大 PR 往往只能粗略浏览。小 PR 更容易理解、更快获得反馈、冲突更少、出问题时更易定位和回滚。可以通过分层提交、特性开关等方式把大功能拆小。
