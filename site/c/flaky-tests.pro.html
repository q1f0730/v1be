不稳定测试 (Flaky Tests)

Flaky Tests

📐 01 · 定义

不稳定测试（Flaky Test）是在代码与环境未变的情况下，多次运行结果时而通过时而失败的测试。它属于测试工程与 CI 可靠性层，根因通常是非确定性：时序与异步等待、测试间共享状态、执行顺序依赖、外部服务、时间与随机数、资源竞争。不稳定测试会侵蚀团队对 CI 的信任，导致真实失败被当作噪音忽略。

⚙️ 02 · 原理
  1. 1

    检测：同一提交多次运行结果不同；CI 中失败后重试通过的测试被标记为疑似不稳定。

  2. 2

    复现：用重复执行（如 --repeat-each）、随机顺序、并行度变化或压力负载放大问题出现概率。

  3. 3

    定位：借助失败时的日志、截图、trace 与时间线，判断属于等待、状态、顺序、外部依赖哪一类。

  4. 4

    隔离：把确认不稳定的测试移入隔离区（quarantine），不阻塞合并，但必须有负责人与修复期限。

  5. 5

    修复：用条件等待替代固定睡眠、每个测试独立数据、模拟外部依赖、固定时间与随机种子，然后恢复。

🔤 03 · 术语
非确定性 (Non-determinism)
相同输入下结果不一致的来源，如时序、随机数。
隔离区 (Quarantine)
暂时不阻塞流水线的不稳定测试集合，需跟踪修复。
自动等待 (Auto-waiting)
测试框架在操作前等待元素可交互，替代固定延时。
测试隔离 (Test Isolation)
每个测试独立的数据与状态，不受其他测试影响。
Trace
Playwright 记录的操作、网络与 DOM 快照，用于事后排查失败。
💻 04 · 代码
Playwright：去掉固定等待typescript
import { test, expect } from "@playwright/test";

test("提交订单后显示成功", async ({ page }) => {
  await page.goto("/checkout");
  await page.getByRole("button", { name: "提交订单" }).click();

  // ❌ 固定睡眠：机器慢时不够，机器快时浪费
  // await page.waitForTimeout(2000);
  // expect(await page.textContent(".toast")).toBe("下单成功");

  // ✅ Web-first 断言：自动重试直到满足或超时
  await expect(page.getByText("下单成功")).toBeVisible();
});

// playwright.config.ts 中：
//   retries: process.env.CI ? 2 : 0,      // 重试用于暴露不稳定，不是修复
//   use: { trace: "on-first-retry" },      // 首次重试时记录 trace 便于排查
// 本地复现：npx playwright test checkout.spec.ts --repeat-each=50

expect(...).toBeVisible() 会自动等待；--repeat-each 放大复现概率，trace 帮助定位原因。

📊 05 · 参数对比

不稳定原因与修复

根因典型表现修复方向
异步等待固定 sleep，偶发超时条件等待、Web-first 断言
共享状态并行时互相覆盖数据每测试独立数据/事务回滚
顺序依赖单独跑过、一起跑挂去除隐式依赖，随机顺序运行
外部依赖第三方接口偶发失败Mock/录制回放，契约测试
时间与随机跨午夜、时区、随机数据失败注入固定时钟与随机种子
⚖️ 06 · 方案取舍

自动重试

优点减少偶发失败阻塞

代价掩盖问题，可能放过真实缺陷

适用临时缓解，并配合统计上报

隔离区 + 修复期限

优点不阻塞团队又不丢失跟踪

代价隔离期间该测试保护失效

适用已确认的不稳定测试

删除测试

优点立即消除噪音

代价失去覆盖

适用测试价值低且修复成本高

🕳️ 07 · 常见坑

  • ✗失败就点重跑，从不追查

    ✓记录每次重试通过的测试并统计不稳定率，定期修复

  • ✗用更长的 sleep 解决偶发超时

    ✓等待具体条件（元素、网络响应、状态），而非时间

  • ✗测试共用同一账号与数据库记录

    ✓每个测试创建独立数据，或使用事务回滚/独立 schema

  • ✗隔离区只进不出，越积越多

    ✓隔离需有负责人与期限，超期升级处理

☑️ 08 · 检查清单
🎤 09 · 面试追问
如何系统地发现不稳定测试？

在 CI 中记录每个测试的历史结果，失败后重试通过即标记；定期对主干同一提交多次运行；使用随机顺序与不同并行度；按不稳定率排行并分配修复。

为什么说重试不是修复？

重试只降低失败被看见的概率，根因仍在，还可能让真实的偶发缺陷（如竞态 Bug）溜进生产。重试应伴随上报与追踪，用于发现而非掩盖。

AI 生成的 E2E 测试常见哪些不稳定写法？

固定 waitForTimeout、依赖 CSS 选择器与文本位置、共用测试账号、依赖真实外部接口、断言动态内容（时间、随机 ID）。评审时应重点检查并改为语义定位与条件等待。
