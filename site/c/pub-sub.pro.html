发布订阅 (Pub/Sub)

Pub/Sub

📐 01 · 定义

发布订阅（Publish/Subscribe，Pub/Sub）是一种消息模式：发布者把消息发送到主题或频道，而不指定接收者；所有订阅该主题的订阅者各自收到一份副本，实现一对多扇出与解耦。从“即发即弃”的 Redis Pub/Sub 到持久化的 Google Cloud Pub/Sub、Kafka，投递保证差异很大。

⚙️ 02 · 原理
  1. 1

    订阅者向代理声明感兴趣的主题或频道（可支持通配符模式匹配）。

  2. 2

    发布者把消息发送到某个主题，无需知道有哪些订阅者、是否在线。

  3. 3

    代理把消息复制并投递给该主题的每个订阅（扇出）；同一订阅内的多个实例可竞争消费以实现负载分担（取决于实现）。

  4. 4

    投递语义由实现决定：Redis Pub/Sub 不持久化，订阅者离线即丢失；托管 Pub/Sub 与 Kafka 会持久化并要求确认，通常为至少一次。

  5. 5

    订阅者处理消息并确认；未确认的消息会被重投，多次失败可进入死信主题。

🔤 03 · 术语
主题 / 频道 (Topic / Channel)
发布者投递消息的逻辑命名通道。
扇出 (Fan-out)
一条消息被复制给多个订阅者。
订阅 (Subscription)
某个消费方对主题的订阅关系，可有多个实例共享。
即发即弃 (Fire-and-forget)
不持久化、不确认，订阅者不在线时消息丢失。
至少一次投递 (At-least-once)
保证不丢但可能重复，消费者需要幂等。
死信主题 (Dead-letter Topic)
存放多次处理失败消息的主题。
💻 04 · 代码
Redis Pub/Sub 发布与订阅python
import json, threading, time
import redis

r = redis.Redis(decode_responses=True)

def subscriber(name: str):
    p = r.pubsub()
    p.subscribe("order.status")          # 订阅频道
    for msg in p.listen():
        if msg["type"] == "message":
            print(name, "收到", json.loads(msg["data"]))

for n in ("通知服务", "日志服务"):
    threading.Thread(target=subscriber, args=(n,), daemon=True).start()
time.sleep(0.5)                           # 等订阅建立

# 发布：返回值是当前收到消息的订阅者数量
count = r.publish("order.status", json.dumps({"order_id": 42, "status": "paid"}))
print("送达订阅者数：", count)
time.sleep(0.5)
# 注意：Redis Pub/Sub 不持久化，订阅者离线期间的消息会丢失

一条消息被两个订阅者同时收到；Redis Pub/Sub 适合实时通知，不适合必须可靠送达的业务事件。

📊 05 · 参数对比

常见实现对比

实现持久化投递保证适用
Redis Pub/Sub否至多一次，离线即丢实时通知、缓存失效广播
Redis Streams是至少一次（消费组 + ACK）轻量可靠事件
Google Cloud Pub/Sub是至少一次，可选按序、精确一次（以文档为准）云上异步解耦
Kafka是，按保留策略至少一次为主，可配置事务高吞吐事件流、回放
⚖️ 06 · 方案取舍

即发即弃 Pub/Sub

优点延迟极低，实现简单

代价消息可能丢失，无回放

适用可容忍丢失的实时广播

持久化 Pub/Sub

优点可靠投递，支持重试与死信

代价需处理重复消息，成本更高

适用订单、支付等业务事件

点对点队列

优点每条消息只被一个消费者处理

代价不能天然广播

适用任务分发、后台作业

🕳️ 07 · 常见坑

  • ✗用 Redis Pub/Sub 传递不能丢的业务事件

    ✓改用 Redis Streams、Kafka 或托管 Pub/Sub 等持久化方案

  • ✗订阅者不幂等，重投导致重复处理

    ✓以消息 ID 去重或设计幂等操作

  • ✗订阅者处理慢，消息积压无人发现

    ✓监控积压量与消费延迟，配置死信与告警

  • ✗把发布订阅当作请求/响应使用

    ✓需要结果的调用使用 API 或带回复通道的请求模式

☑️ 08 · 检查清单
🎤 09 · 面试追问
发布订阅和消息队列有什么区别？

发布订阅是一对多：每个订阅者都收到消息副本，用于广播事件；点对点队列是一对一：每条消息只被其中一个消费者处理，用于分发任务。许多系统两者兼具，例如 Kafka 中不同消费组相当于订阅，组内消费者分担分区。

Redis Pub/Sub 适合什么场景？

适合可容忍丢失的实时广播，如在线通知推送、多实例间的缓存失效通知、聊天室在线消息。它不持久化、不确认，订阅者断线期间的消息直接丢失，因此不适合订单、支付等必须可靠处理的事件。

至少一次投递下如何避免重复处理？

让消费者幂等：用消息或业务唯一 ID 记录已处理状态，处理前先检查；或让操作天然幂等（如设置状态而非累加）。也可借助数据库唯一约束，在重复写入时安全失败。
