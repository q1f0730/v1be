Cookie 与会话

Cookies & Sessions

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

Cookie 是服务器通过 Set-Cookie 响应头让浏览器保存、并在后续请求中自动携带的小段数据；会话（Session）是服务端为已认证用户维护的状态，通常以随机会话 ID 经 Cookie 关联。二者属于 Web 状态管理层，为无状态的 HTTP 提供“记住登录”的能力，安全属性决定会话劫持与 CSRF 风险。

⚙️ 02 · 原理
  1. 1

    用户登录成功后，服务端生成高熵随机会话 ID，在存储中保存其对应的用户信息和过期时间。

  2. 2

    服务端通过 Set-Cookie 下发会话 ID，并设置 HttpOnly、Secure、SameSite 等属性。

  3. 3

    浏览器按域名、路径和 SameSite 规则，在后续请求中自动附加 Cookie。

  4. 4

    服务端读取会话 ID 并查找会话，得到当前用户；会话过期或不存在则视为未登录。

  5. 5

    登出时服务端删除会话并让 Cookie 失效；登录、提权时应重新生成会话 ID。

🔤 03 · 术语
HttpOnly
禁止 JavaScript 读取 Cookie，降低 XSS 窃取会话的风险。
Secure
只在 HTTPS 连接中发送该 Cookie。
SameSite
控制跨站请求是否携带 Cookie，取值 Strict、Lax、None。
会话固定 (Session Fixation)
攻击者让受害者使用已知会话 ID，登录后劫持。
__Host- 前缀
要求 Secure、Path=/ 且不带 Domain，防止子域覆盖。
💻 04 · 代码
安全的会话 Cookiehttp
POST /login HTTP/1.1
Host: app.example.com
Content-Type: application/json

{"email": "a@example.com", "password": "..."}

HTTP/1.1 200 OK
Set-Cookie: __Host-sid=7f3a9c...e21; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=86400

# 之后浏览器自动携带
GET /api/me HTTP/1.1
Host: app.example.com
Cookie: __Host-sid=7f3a9c...e21

# 登出：服务端删除会话，并让 Cookie 立即过期
HTTP/1.1 204 No Content
Set-Cookie: __Host-sid=; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=0

会话 ID 只是随机引用；HttpOnly、Secure、SameSite 与 __Host- 前缀共同加固。

📊 05 · 参数对比

SameSite 取值

取值跨站请求是否携带适用
Strict任何跨站请求都不带银行等高敏感操作
Lax仅顶级导航的 GET 携带多数登录会话，现代浏览器常见默认
None都携带，必须同时设置 Secure第三方嵌入、跨站 SSO
⚖️ 06 · 方案取舍

服务端会话 + Cookie

优点可随时吊销，令牌内容不暴露

代价需要会话存储

适用传统 Web 应用、同域前后端

JWT 存于 Cookie

优点无状态校验，易横向扩展

代价吊销困难

适用多服务需本地校验身份

令牌存 localStorage

优点跨域调用简单

代价XSS 可直接窃取

适用一般不推荐用于敏感会话

🕳️ 07 · 常见坑

  • ✗会话 Cookie 未设置 HttpOnly

    ✓会话 Cookie 一律 HttpOnly，前端无需读取

  • ✗登录后沿用登录前的会话 ID

    ✓认证成功后重新生成会话 ID 防止会话固定

  • ✗登出只在前端删 Cookie

    ✓服务端同时销毁会话记录

  • ✗Cookie 中直接存用户 ID 或角色

    ✓只存随机会话 ID，或使用签名并校验

☑️ 08 · 检查清单
🎤 09 · 面试追问
Cookie 和 Session 的关系？

Cookie 是浏览器端的存储与自动携带机制；Session 是服务端保存的用户状态。典型做法是 Cookie 里只放一个不可猜测的会话 ID，服务端据此查找会话数据。也可以不用服务端会话，而把签名令牌放在 Cookie 中，那就是另一种设计。

SameSite=Lax 能完全防 CSRF 吗？

不能完全依赖。Lax 阻止了大多数跨站 POST 携带 Cookie，但顶级导航的 GET 仍会携带，若有用 GET 改状态的接口就会被利用；同站的子域被攻破也不受限制；旧浏览器行为不同。仍建议配合 CSRF 令牌或校验 Origin。

为什么推荐 __Host- 前缀？

浏览器只接受满足 Secure、Path=/ 且没有 Domain 属性的 __Host- Cookie，这样 Cookie 被锁定在当前主机，不能被子域或 HTTP 页面设置或覆盖，可防御通过不安全子域进行的 Cookie 注入和会话固定。
