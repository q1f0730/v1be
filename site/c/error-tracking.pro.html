应用错误追踪与聚合

Error Tracking

📐 01 · 定义

应用错误追踪（Error Tracking）是自动捕获应用运行时的异常与崩溃，附带堆栈、版本、环境、用户操作轨迹等上下文，并按相似性聚合成问题（Issue）进行分配、告警和跟踪的实践。它覆盖前端、移动端和后端，补足日志与指标难以直接呈现的错误细节，常见工具有 Sentry 等。

⚙️ 02 · 原理
  1. 1

    应用集成 SDK，SDK 挂接全局异常处理器和框架中间件，捕获未处理异常。

  2. 2

    捕获时收集堆栈、请求信息、设备与运行时、发布版本、面包屑等上下文。

  3. 3

    事件上报到服务端，按堆栈指纹聚合为一个问题，统计发生次数和影响用户数。

  4. 4

    前端与移动端需要上传 source map 或符号表，把压缩或混淆后的堆栈还原为源码位置。

  5. 5

    新问题或回归问题触发告警，分配给负责人，修复发布后标记解决并观察是否复发。

🔤 03 · 术语
指纹 (Fingerprint)
用于判断事件是否属于同一问题的特征，通常基于堆栈。
面包屑 (Breadcrumbs)
错误发生前的操作和事件轨迹，帮助还原现场。
Source Map
把压缩后的 JavaScript 位置映射回源码的文件。
回归 (Regression)
已标记解决的问题在新版本中再次出现。
发布版本 (Release)
事件关联的应用版本，用于判断哪个版本引入了问题。
💻 04 · 代码
Sentry Python SDK 接入python
import sentry_sdk

sentry_sdk.init(
    dsn="https://<key>@<org>.ingest.sentry.io/<project>",
    environment="production",
    release="shop-api@1.4.2",     # 关联版本，便于定位引入问题的发布
    traces_sample_rate=0.1,         # 性能追踪采样 10%
    send_default_pii=False,         # 默认不发送个人信息
)

def charge(order_id: str):
    sentry_sdk.set_tag("order_id", order_id)  # 附加检索维度
    try:
        risky_payment_call(order_id)
    except TimeoutError as e:
        sentry_sdk.capture_exception(e)          # 已处理的异常也可上报
        raise
# 未捕获的异常会被 SDK 自动上报

设置环境与版本，主动上报已处理异常并附标签；未处理异常 SDK 自动捕获。

🕳️ 07 · 常见坑

  • ✗前端没上传 source map，堆栈全是压缩后的单行代码。

    ✓在 CI 构建时上传 source map 并与 release 关联。

  • ✗上报中包含密码、令牌等敏感数据。

    ✓关闭默认 PII，使用 before_send 过滤敏感字段。

  • ✗所有异常一股脑上报，配额被单一噪声问题耗尽。

    ✓忽略预期异常，配置采样与速率限制。

  • ✗问题无人认领，积压成千上万条。

    ✓按代码归属自动分配，定期清理分级。

🎤 09 · 面试追问
错误追踪如何把海量错误聚合成问题？

服务端根据事件的指纹聚合，默认基于异常类型和堆栈中应用代码的帧，忽略行号偏移等噪声；也可自定义指纹规则。聚合后统计次数、影响用户数、首次和最近出现版本，便于排优先级。

为什么错误事件要关联 release？

有了版本号，就能知道问题首次出现于哪个发布，判断是否为回归，并与提交记录关联找到可疑变更；修复后也能确认新版本是否还在发生，从而决定是否回滚。

AI 编程工具与错误追踪如何配合？

可以把聚合后的堆栈、面包屑和相关代码交给 AI 助手分析可能原因并生成修复草案；但修复仍需写测试复现问题、代码评审，并在发布后观察该问题是否停止发生。
