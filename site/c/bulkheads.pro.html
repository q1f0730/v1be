舱壁隔离模式

Bulkheads

🧸 回到小白版

📐 01 · 定义

舱壁隔离（Bulkhead）是一种弹性设计模式，借鉴船体分舱：把线程池、连接池、实例或配额按依赖、租户或功能划分为互相独立的资源池，使某一部分耗尽或故障时，其他部分仍有资源可用。它作用于服务的资源管理层，目标是限制故障的爆炸半径，防止一个慢依赖拖垮整个服务。

⚙️ 02 · 原理
  1. 1

    识别共享资源：线程池、数据库连接、HTTP 客户端连接、内存、实例。

  2. 2

    按依赖或流量类型切分资源池，例如支付调用和推荐调用各用独立线程池与并发上限。

  3. 3

    某个依赖变慢时，只会占满它自己的池，新请求在该池上快速失败或排队。

  4. 4

    其他资源池的请求不受影响，核心功能继续正常服务，用户只会看到局部降级。

  5. 5

    更大粒度上，可按租户或单元（Cell）部署独立实例组，实现基础设施级隔离。

🔤 03 · 术语
爆炸半径 (Blast Radius)
一次故障能波及的用户或功能范围。
线程池隔离 (Thread Pool Isolation)
每个依赖用独立线程池执行调用，互不抢占。
信号量隔离 (Semaphore Isolation)
用计数信号量限制并发数，开销比线程池小。
单元化架构 (Cell-based Architecture)
把系统复制成多个独立单元，每个单元只服务部分用户。
噪声邻居 (Noisy Neighbor)
共享资源中某个租户占用过多，影响其他租户。
💻 04 · 代码
按依赖拆分线程池python
from concurrent.futures import ThreadPoolExecutor, TimeoutError
import requests

# 每个下游一个独立的小池子，互不抢线程
pools = {
    "payment": ThreadPoolExecutor(max_workers=20),
    "recommend": ThreadPoolExecutor(max_workers=5),
}

def call(dep: str, url: str, timeout: float = 2.0):
    fut = pools[dep].submit(requests.get, url, timeout=timeout)
    try:
        return fut.result(timeout=timeout)
    except TimeoutError:
        return None  # 只影响这个依赖，调用方可降级

# 推荐服务变慢时，最多占住 5 个线程，支付调用不受影响
resp = call("payment", "https://httpbin.org/get")
print(resp.status_code if resp else "degraded")

为支付和推荐分配独立线程池，慢依赖只会耗尽自己的池而不拖累核心调用。

📊 05 · 参数对比

隔离粒度对比

粒度实现方式隔离强度
并发数信号量弱：仍共享线程和内存
线程/连接池独立池中：资源池互不抢占
进程/容器独立部署与资源配额强：CPU 内存隔离
单元（Cell）独立实例组与数据最强：故障限在单元内
⚖️ 06 · 方案取舍

信号量隔离

优点开销小，实现简单

代价无法中断阻塞调用

适用异步或非阻塞调用

线程池隔离

优点可设超时，隔离更彻底

代价线程多、上下文切换开销

适用阻塞式同步调用

单元化部署

优点爆炸半径最小

代价成本高，路由与运维复杂

适用大规模多租户系统

🕳️ 07 · 常见坑

  • ✗所有下游共用一个 HTTP 连接池，一个慢依赖占满连接。

    ✓按下游拆分连接池并设置各自上限和超时。

  • ✗池划得过多过小，正常峰值也触发拒绝。

    ✓按各依赖的峰值并发和延迟估算池大小，压测验证。

  • ✗隔离了线程但没设超时，池内线程永久挂起。

    ✓每个调用都配超时，并与熔断器配合。

🎤 09 · 面试追问
舱壁和熔断器有什么区别？

舱壁限制资源占用范围，保证一个依赖出问题时最多耗掉自己那份资源；熔断器检测失败率，在依赖持续故障时直接短路请求。前者控制影响面，后者减少无效调用，通常组合使用。

如何确定每个舱壁的大小？

依据利特尔定律：所需并发约等于目标吞吐乘以平均延迟，再加峰值余量。结合压测和线上指标调整，关键依赖给足，非关键依赖从严，满载时触发降级而不是排队。

单元化架构解决了什么问题？

把系统复制成多个独立单元，每个单元服务一部分用户，部署、配置变更和故障都限制在单元内。它是基础设施层面的舱壁，代价是路由层复杂和资源冗余。
