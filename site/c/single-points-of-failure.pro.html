单点故障 (SPOF)

Single Points of Failure

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

单点故障（Single Point of Failure, SPOF）是系统中一旦失效就会导致整体不可用、且没有冗余替代的组件。它可能是硬件、软件进程、网络链路、第三方服务、配置系统，甚至是唯一掌握某项操作的人。识别和消除 SPOF 是可靠性设计和架构评审的基本功，手段包括冗余、隔离、降级和去除不必要的依赖。

⚙️ 02 · 原理
  1. 1

    画出请求从用户到数据的完整路径，列出途经的每个组件、外部依赖和运维流程。

  2. 2

    对每个组件问：它挂了，服务还能工作吗？没有替代的就是 SPOF。

  3. 3

    消除方式是冗余（多副本、多可用区）、自动故障转移，或让依赖变成可选的。

  4. 4

    确实无法消除的单点，通过功能降级、缓存兜底和快速恢复手册来降低故障影响。

  5. 5

    定期复查单点清单，因为新功能、新依赖和运维流程变更都可能引入新的单点。

🔤 03 · 术语
冗余 (Redundancy)
为关键组件准备多个副本，任一失效时其他可接替。
N+1 冗余
在满足负载所需的 N 个单元外再多一个备用单元。
共享命运 (Shared Fate)
看似冗余的组件依赖同一底层资源，会一起失效。
Pod 中断预算 (PodDisruptionBudget)
限制自愿中断时同时不可用的 Pod 数量。
巴士因子 (Bus Factor)
多少人离开就会让项目无法维护，人员层面的单点。
💻 04 · 代码
多副本加中断预算yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: api }
spec:
  replicas: 3                     # 不止一个副本
  selector: { matchLabels: { app: api } }
  template:
    metadata: { labels: { app: api } }
    spec:
      containers:
        - { name: api, image: example/api:1.0 }
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: api-pdb }
spec:
  minAvailable: 2                 # 节点维护时至少保留 2 个可用
  selector: { matchLabels: { app: api } }

多副本消除进程单点，PDB 防止节点维护时副本被同时驱逐。

📊 05 · 参数对比

容易被忽略的单点

类别例子消除思路
基础设施单个 NAT 网关、单个数据库主库多可用区、托管高可用
配置与密钥唯一的配置中心、过期的证书多副本、自动续期与监控
第三方唯一的支付或短信供应商降级、备用供应商
人员流程只有一人会发布或有权限文档化、交叉培训、多人授权
⚖️ 06 · 方案取舍

全面冗余

优点可用性高

代价成本与复杂度上升

适用核心路径组件

接受单点但快速恢复

优点成本低

代价故障期间不可用

适用非核心、恢复时间可接受

去掉依赖

优点从根本上消除风险

代价需要重新设计

适用依赖价值低于风险

🕳️ 07 · 常见坑

  • ✗多台数据库实例放在同一物理机或同一可用区。

    ✓检查底层共享资源，分散到不同故障域。

  • ✗DNS 只用一家服务商。

    ✓关键域名评估多 DNS 服务商或确认服务商 SLA。

  • ✗证书、域名到期没人知道，成为时间型单点。

    ✓自动续期并对到期时间设告警。

  • ✗冗余组件从未验证，备份节点其实无法工作。

    ✓定期做故障注入或切换演练。

🎤 09 · 面试追问
在架构评审中如何系统地找单点？

画出完整请求链路和依赖图，包括 DNS、证书、网关、配置中心和第三方服务，逐一做假设失效分析；再检查冗余组件是否共享底层资源；最后看人和流程，例如谁有权限、谁会操作。

多副本就一定没有单点吗？

不一定。副本可能在同一主机、可用区或依赖同一配置服务，属于共享命运；也可能使用同一份错误配置同时发布而一起崩溃。冗余需要故障独立性，并配合分批发布。

负载均衡器本身是单点吗？

自建单台负载均衡器是单点，需用主备加虚拟 IP 或多实例加 DNS；云托管负载均衡通常由厂商在多可用区内冗余实现，但仍应确认其跨可用区配置和配额限制。
