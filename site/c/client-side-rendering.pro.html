客户端渲染 (CSR)

Client-Side Rendering

🧸 回到小白版

📐 01 · 定义

客户端渲染（CSR，Client-Side Rendering）指服务器只返回近乎空的 HTML 外壳和 JavaScript 包，由浏览器下载、解析、执行 JS 并请求数据后生成页面内容。它是纯 SPA 的默认渲染方式，交互流畅、可静态托管，但首屏内容依赖 JS 执行，易出现白屏，对 SEO 与低端设备不友好。

⚙️ 02 · 原理
  1. 1

    浏览器请求页面，收到仅含根节点（如 div#root）和 script 标签的 HTML。

  2. 2

    下载并解析 JS 包；包越大、设备越弱，解析执行耗时越长。

  3. 3

    应用启动后发起 API 请求获取数据，形成「下载 JS → 执行 → 请求数据」的串行瀑布。

  4. 4

    数据返回后框架渲染组件并写入 DOM，此时用户才看到主要内容（影响 LCP）。

  5. 5

    后续导航由前端路由完成，只请求数据与按需加载的代码块，切换迅速。

🔤 03 · 术语
FCP (First Contentful Paint)
首次绘制出任何内容的时间。
LCP (Largest Contentful Paint)
视口内最大内容元素渲染完成的时间，核心网页指标之一。
请求瀑布 (Request Waterfall)
资源依次依赖加载，总耗时为各段之和。
骨架屏 (Skeleton Screen)
数据加载前显示的占位布局，改善感知速度。
预渲染 (Prerendering)
构建时为路由生成静态 HTML，缓解 CSR 首屏与 SEO 问题。
💻 04 · 代码
按路由懒加载 + 加载占位javascript
// main.jsx：CSR 入口，按路由拆分代码，避免首包过大
import { lazy, Suspense } from "react";
import { createRoot } from "react-dom/client";
import { BrowserRouter, Routes, Route } from "react-router-dom";

const Home = lazy(() => import("./pages/Home"));
const Dashboard = lazy(() => import("./pages/Dashboard")); // 访问时才下载

function Skeleton() {
  return <div className="skeleton" aria-busy="true">加载中…</div>;
}

function App() {
  return (
    <BrowserRouter>
      <Suspense fallback={<Skeleton />}>
        <Routes>
          <Route path="/" element={<Home />} />
          <Route path="/dashboard" element={<Dashboard />} />
        </Routes>
      </Suspense>
    </BrowserRouter>
  );
}

createRoot(document.getElementById("root")).render(<App />);

懒加载缩小首包；Suspense 提供占位。数据请求也应尽早并行发起，避免瀑布。

📊 05 · 参数对比

CSR 首屏优化手段

手段作用代价
代码分割减小首包体积路由切换时有额外请求
预加载关键资源提前下载 JS/数据可能浪费带宽
骨架屏改善感知速度不缩短实际耗时
构建期预渲染首屏有 HTML、利于 SEO只适合内容较静态的路由
⚖️ 06 · 方案取舍

纯 CSR

优点部署简单（静态托管）、交互流畅

代价首屏慢、SEO 弱

适用登录后应用、内部工具

CSR + 预渲染

优点保留静态托管，首屏改善

代价动态内容仍需客户端获取

适用营销页较少变化的 SPA

SSR/SSG

优点首屏与 SEO 最好

代价需服务端或构建管线

适用内容站、电商、需收录页面

🕳️ 07 · 常见坑

  • ✗所有页面打进一个巨大的 JS 包

    ✓按路由懒加载，分析包体积移除大依赖

  • ✗组件挂载后才逐层请求数据，形成多级瀑布

    ✓在路由层并行预取数据，或使用支持预取的数据库

  • ✗对需要搜索收录的页面使用纯 CSR

    ✓改用 SSR/SSG 或预渲染

  • ✗只在高端开发机上测性能

    ✓用 Lighthouse 模拟中低端设备与慢网络

🎤 09 · 面试追问
CSR 首屏慢的根本原因？

内容生成被推迟到 JS 下载、解析、执行之后，并且通常还要再等一次数据请求，形成串行链路；低端设备上 JS 执行本身就很慢。因此 CSR 的首屏时间 ≈ HTML + JS 下载 + 执行 + 数据请求 + 渲染。

什么场景下 CSR 反而是好选择？

登录后的仪表盘、编辑器、内部工具等：不需要 SEO，用户会长时间停留，后续交互频繁，首屏成本被摊薄；同时可纯静态托管、部署简单、服务器压力小。

搜索引擎能抓取 CSR 页面吗？

Google 会渲染 JavaScript，但渲染可能延后，且依赖资源可访问、无报错；其他搜索引擎和社交平台预览抓取能力不一。需要稳定收录的页面应输出服务端 HTML。
