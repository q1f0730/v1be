持久化执行 (Temporal)

Durable Execution

🧸 回到小白版

📐 01 · 定义

持久化执行（Durable Execution）是一种编程模型：开发者用普通代码编写长流程，运行时自动持久化每一步的执行进度与结果，进程崩溃、机器重启或等待数天后，都能从中断处继续，好像代码从未停过。代表实现有 Temporal（源自 Uber Cadence）、AWS Step Functions、Restate、DBOS 等，常用于订单流程、数据管道和长时间运行的 AI Agent。

⚙️ 02 · 原理
  1. 1

    工作流（Workflow）代码负责编排逻辑；有副作用的操作（调用 API、写库、调用 LLM）封装为活动（Activity）。

  2. 2

    每次活动调度、完成、计时器触发和外部信号都作为事件追加到持久化的事件历史中。

  3. 3

    Worker 崩溃后，新的 Worker 通过重放事件历史重新执行工作流代码：已完成的活动直接返回记录的结果，不会重复执行。

  4. 4

    因此工作流代码必须确定性：不能直接读系统时间、随机数或做 IO，这些都应通过 SDK 接口或活动完成。

  5. 5

    活动失败按重试策略自动重试；持久计时器可等待数天；信号和查询让外部与运行中的工作流交互，如人工审批。

🔤 03 · 术语
工作流 (Workflow)
确定性的编排代码，其执行状态由事件历史完全决定。
活动 (Activity)
执行副作用的普通函数，可独立设置超时与重试策略。
事件历史 (Event History)
工作流执行过程中所有事件的追加日志，用于重放恢复。
重放 (Replay)
按事件历史重新运行工作流代码以恢复内存状态，跳过已完成的活动。
信号 (Signal)
外部向运行中工作流发送的异步消息，如审批通过。
工作流版本化 (Versioning)
修改运行中工作流代码时保证旧执行重放仍确定的机制。
💻 04 · 代码
Temporal Python 工作流python
# pip install temporalio ；需连接 Temporal Server
import asyncio
from datetime import timedelta
from temporalio import activity, workflow
from temporalio.common import RetryPolicy

@activity.defn
async def call_llm(prompt: str) -> str:
    ...  # 真实的模型调用：有副作用，放在活动里
    return "summary"

@workflow.defn
class ResearchAgent:
    @workflow.run
    async def run(self, topic: str) -> str:
        draft = await workflow.execute_activity(
            call_llm, f"研究 {topic}",
            start_to_close_timeout=timedelta(minutes=5),
            retry_policy=RetryPolicy(maximum_attempts=5),
        )
        # 持久计时器：等待 1 天后复查，期间 Worker 可重启
        await asyncio.sleep(timedelta(days=1).total_seconds())
        return await workflow.execute_activity(
            call_llm, f"复查并更新：{draft}",
            start_to_close_timeout=timedelta(minutes=5),
        )

工作流内的 asyncio.sleep 会被 SDK 转为持久计时器；工作流代码中不要直接做网络请求或读当前时间。

📊 05 · 参数对比

长流程实现方式对比

方式崩溃恢复长时间等待开发体验
普通脚本/进程从头重跑难最简单
队列 + 状态表手写状态机恢复需定时任务轮询逻辑分散
DAG 编排（如 Airflow）按任务重跑按调度周期适合批处理管道
持久化执行（如 Temporal）重放续跑原生持久计时器用代码写流程，需遵守确定性
⚖️ 06 · 方案取舍

Temporal 等自托管/云服务

优点能力完整，多语言 SDK，可观测性强

代价需运维服务端或付费，学习确定性约束

适用核心业务流程、长时间 Agent

云厂商状态机（如 Step Functions）

优点全托管，与云服务集成好

代价用 JSON/DSL 描述流程，绑定厂商

适用流程相对固定且已深度使用该云

数据库驱动轻量方案（如 DBOS）

优点复用现有 Postgres，部署简单

代价生态与规模能力需评估

适用中小规模、希望少引入组件

🕳️ 07 · 常见坑

  • ✗在工作流代码里直接调用 API 或 datetime.now()

    ✓副作用放进活动，时间和随机数使用 SDK 提供的确定性接口

  • ✗直接修改运行中工作流的代码逻辑，重放时报不确定性错误

    ✓使用 SDK 的版本化或补丁机制，并保留旧分支直至旧执行结束

  • ✗活动不幂等，重试导致重复扣款

    ✓活动使用幂等键，外部系统按键去重

  • ✗在工作流中传递巨大的数据，事件历史膨胀

    ✓大数据放对象存储，工作流只传引用

🎤 09 · 面试追问
Temporal 如何做到崩溃后从断点继续？

服务端持久化每个工作流的事件历史。Worker 恢复时重新执行工作流代码，遇到已记录完成的活动直接返回历史中的结果，而不是再次调用，从而重建到崩溃前的状态后继续执行。这要求工作流代码对相同历史产生相同的调度决策。

为什么持久化执行适合 AI Agent？

Agent 任务可能持续数小时、调用大量昂贵的模型与工具、需要等待人工确认。持久化执行让每次模型调用成为可重试的活动，崩溃不重复计费，能持久等待人工信号，还能完整记录执行历史用于审计与调试。

工作流确定性约束具体指什么？

给定相同事件历史，工作流代码必须做出相同的命令序列。因此不能在工作流中直接读系统时间、生成随机数、访问网络或文件、依赖全局可变状态或非确定性的迭代顺序。这些都应通过 SDK 的确定性 API 或放入活动。
