单元测试

Unit Testing

📐 01 · 定义

单元测试（Unit Testing）是针对代码中最小可测单元（通常是函数、方法或类）编写的自动化测试，在隔离外部依赖的情况下验证其输入输出与行为。它位于测试金字塔底层，数量最多、运行最快，为重构提供安全网，也是 AI 编码 Agent 判断改动是否正确的主要自动反馈信号。

⚙️ 02 · 原理
  1. 1

    确定被测单元及其契约：给定输入时应返回什么、抛出什么异常、产生什么可观察的效果。

  2. 2

    按 Arrange-Act-Assert 组织：准备数据和依赖，调用被测代码，断言结果。

  3. 3

    用测试替身（mock、stub、fake）替换数据库、网络、时间等外部依赖，保证快速和确定性。

  4. 4

    测试运行器收集并执行用例，报告通过/失败与差异；可生成覆盖率报告。

  5. 5

    在本地、Git 提交钩子和 CI 流水线中自动运行，任一测试失败即阻止合并。

🔤 03 · 术语
AAA 模式
Arrange-Act-Assert，准备、执行、断言三段式结构。
测试替身 (Test Double)
替代真实依赖的对象统称，包括 mock、stub、fake、spy。
代码覆盖率 (Code Coverage)
测试执行到的代码比例，衡量“跑过”而非“测对”。
不稳定测试 (Flaky Test)
代码未变却时过时不过的测试，常因时间、并发、顺序依赖。
参数化测试 (Parameterized Test)
同一测试逻辑用多组输入输出数据运行。
💻 04 · 代码
pytest 参数化与 mockpython
# test_pricing.py  运行: pytest -q
import pytest
from unittest.mock import Mock

def final_price(price: float, coupon: str | None, rates) -> float:
    if price < 0:
        raise ValueError("price must be >= 0")
    discount = rates.get(coupon) if coupon else 0
    return round(price * (1 - discount), 2)

@pytest.mark.parametrize("price, coupon, expected", [
    (100, None, 100.0),
    (100, "VIP", 80.0),
    (0, "VIP", 0.0),          # 边界值
])
def test_final_price(price, coupon, expected):
    rates = Mock()
    rates.get.return_value = 0.2   # 替身代替真实折扣服务
    assert final_price(price, coupon, rates) == expected

def test_negative_price_raises():
    with pytest.raises(ValueError):
        final_price(-1, None, Mock())

参数化覆盖正常与边界情况，用 Mock 隔离外部折扣服务，并验证异常分支。

📊 05 · 参数对比

测试替身类型

类型行为典型用途
Stub返回预设值固定外部接口返回
Mock预设并校验调用验证是否以正确参数调用
Fake简化但可工作的实现内存数据库
Spy记录真实调用观察调用次数与参数
⚖️ 06 · 方案取舍

大量 mock 的纯单元测试

优点快、定位准

代价与实现耦合，易测不到集成问题

适用纯计算逻辑、复杂分支

少 mock、用 fake 或真实依赖

优点更接近真实行为

代价较慢，环境依赖多

适用数据访问层、关键流程

追求高覆盖率指标

优点便于度量

代价易催生无效断言

适用仅作参考，不作硬目标

🕳️ 07 · 常见坑

  • ✗测试只断言函数被调用，不检查结果

    ✓优先断言可观察的输出和状态

  • ✗测试依赖当前时间、随机数或执行顺序

    ✓注入时钟和随机种子，每个测试独立准备数据

  • ✗让 AI 改到测试通过，它改了测试本身

    ✓明确禁止修改既有测试，审查测试文件 diff

  • ✗覆盖率 100% 就认为没有 bug

    ✓覆盖率不等于断言质量，重点覆盖边界和错误路径

🎤 09 · 面试追问
什么样的单元测试是好测试？

快速、隔离、可重复、自校验、意图清晰。它测试行为而非实现细节，重构内部代码时不需要改测试；失败信息能直接定位问题；覆盖边界和错误路径。一个测试只验证一个关注点。

mock 用多了有什么问题？

测试会与实现细节紧密耦合，重构时大量测试失败但功能并没坏；mock 的行为可能与真实依赖不一致，导致测试通过而集成失败。原则是只 mock 跨越进程边界或不可控的依赖，如网络、时间、第三方服务。

在 AI 编码中单元测试起什么作用？

测试是 Agent 最直接的成功信号，让它能自己验证改动并迭代修复。但 Agent 可能为了通过测试而改测试、写过于宽松的断言或硬编码返回值。因此要让测试先于实现存在，并在审查时重点看测试文件的变化。
