契约测试 (Pact)

Contract Testing

📐 01 · 定义

契约测试（Contract Testing）验证两个服务之间的接口约定是否仍被双方遵守，属于介于单元测试与端到端测试之间的集成测试层。主流形态是消费者驱动契约（CDC）：调用方用测试生成「我需要什么」的契约文件，提供方在 CI 中回放验证。它让微服务可以独立发布，而不必每次拉起整套环境做联调。

⚙️ 02 · 原理
  1. 1

    消费者（Consumer）在单元测试中声明期望：发什么请求、需要响应里哪些字段和类型，测试对着框架提供的 Mock Server 运行。

  2. 2

    测试通过后生成契约文件（Pact 中为 JSON 格式的 pact 文件），只包含消费者真正用到的交互，而非提供方完整 API。

  3. 3

    契约发布到中心仓库（如 Pact Broker 或 PactFlow），并标记消费者版本、分支或部署环境。

  4. 4

    提供方（Provider）在自己的 CI 中拉取相关契约，用真实服务实例逐条回放请求，按 Provider State 预置数据后比对响应。

  5. 5

    验证结果回写 Broker，形成「哪个版本与哪个版本兼容」的矩阵。

  6. 6

    部署前执行 can-i-deploy 查询矩阵，只有与目标环境中已部署的对端版本均验证通过才放行。

🔤 03 · 术语
消费者驱动契约 (Consumer-Driven Contracts)
由调用方定义所需交互，提供方负责满足，避免提供方单方面破坏调用方。
提供方状态 (Provider State)
契约中命名的前置条件，如「用户 42 存在」，提供方验证前据此准备测试数据。
匹配器 (Matchers)
按类型、正则或数组结构匹配，而非精确值，降低契约对测试数据的脆弱依赖。
Pact Broker
存储契约与验证结果的服务，提供版本兼容矩阵和 Webhook 触发验证。
can-i-deploy
Pact Broker 提供的命令，查询某版本能否安全部署到指定环境。
Pending Pacts
新契约首次验证失败时不阻断提供方构建，给提供方实现时间。
💻 04 · 代码
Pact JS 消费者测试javascript
// npm i -D @pact-foundation/pact jest（Node 18+ 自带 fetch）
const path = require('path');
const { PactV3, MatchersV3 } = require('@pact-foundation/pact');
const { like, integer } = MatchersV3;

const provider = new PactV3({
  consumer: 'WebApp',
  provider: 'UserService',
  dir: path.resolve(__dirname, 'pacts'), // 生成的契约文件位置
});

test('按 ID 获取用户', () => {
  provider
    .given('user 42 exists') // Provider State
    .uponReceiving('a request for user 42')
    .withRequest({ method: 'GET', path: '/users/42' })
    .willRespondWith({
      status: 200,
      headers: { 'Content-Type': 'application/json' },
      body: like({ userId: integer(42), name: 'Ada' }), // 按类型匹配
    });

  return provider.executeTest(async (mockServer) => {
    const res = await fetch(`${mockServer.url}/users/42`);
    const user = await res.json();
    expect(user.userId).toBe(42);
  });
});

消费者对 Mock Server 测试并生成契约文件；提供方随后用真实服务回放验证。

📊 05 · 参数对比

接口兼容性保障方案

方案验证对象反馈速度主要盲区
消费者驱动契约 (Pact)调用方实际用到的交互快，单服务 CI 内只覆盖写进契约的场景
OpenAPI Schema 比对提供方声明的完整 Schema很快，静态检查不知道哪些字段真被使用
双向契约 (Bi-Directional)消费者契约对照提供方 OpenAPI快依赖 OpenAPI 与实现一致
端到端测试整条业务链路慢，需全套环境失败定位难、易不稳定
⚖️ 06 · 方案取舍

消费者驱动契约

优点精确知道谁用了什么，破坏性改动发布前暴露

代价需要 Broker 和跨团队协作流程

适用内部微服务、调用方可控且数量有限

提供方 Schema 优先

优点一份 OpenAPI 管全部，工具链成熟

代价无法感知调用方真实依赖，易过度保守

适用公开 API、调用方未知或很多

只做端到端测试

优点最接近真实用户路径

代价慢、脆弱、阻塞独立发布

适用少量关键主流程的冒烟验证

🕳️ 07 · 常见坑

  • ✗契约里写死精确值，提供方换测试数据就失败

    ✓对 ID、时间等用类型或正则匹配器，只对业务语义字段精确断言

  • ✗把提供方全部字段写进契约

    ✓只写消费者真正读取的字段，否则提供方删任何字段都被阻断

  • ✗用契约测试验证业务逻辑

    ✓契约只管请求/响应形状与语义，业务规则交给提供方自身测试

  • ✗生成了契约却不在部署前跑 can-i-deploy

    ✓把 can-i-deploy 做成发布流水线的硬门禁，并记录部署环境

☑️ 08 · 检查清单
🎤 09 · 面试追问
契约测试与集成测试、E2E 测试的边界？

契约测试只验证两服务间接口约定，每侧在自己的 CI 中独立运行，不需要同时启动双方；集成测试通常真实连接依赖；E2E 拉起完整链路验证业务流程。契约测试换来速度和独立发布，代价是不覆盖跨服务业务正确性。

提供方想删除一个字段，流程怎么走？

先在 Broker 查哪些消费者契约用到该字段；若有，与消费者协商先改代码并发布新契约；确认生产环境中所有消费者版本都不再依赖后，提供方验证通过、can-i-deploy 放行，再删除。即 expand-contract 渐进演进。

AI 生成的契约测试要重点审查什么？

一是是否只覆盖消费者真实读取的字段，而非照抄完整响应；二是匹配器使用是否得当，避免写死值；三是 Provider State 命名是否与提供方实现一致；四是 HTTP 方法、路径、状态码是否与真实调用代码一致，防止测试自洽但与生产代码脱节。
