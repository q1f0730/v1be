密钥管理服务与信封加密

KMS & Envelope Encryption

📐 01 · 定义

密钥管理服务（KMS）是在硬件安全模块（HSM）或同等保护下集中生成、存储、轮换和审计密钥的服务。信封加密（Envelope Encryption）是使用 KMS 的标准模式：用本地生成的数据密钥（DEK）加密数据，再用 KMS 中永不导出的主密钥（KEK）加密数据密钥，密文与被包裹的 DEK 一起存放。它兼顾大数据量加密性能、细粒度密钥隔离与集中权限控制。

⚙️ 02 · 原理
  1. 1

    应用调用 KMS 的生成数据密钥接口（如 AWS KMS GenerateDataKey），同时获得明文 DEK 和被主密钥加密后的 DEK。

  2. 2

    应用在本地用明文 DEK 以 AES-256-GCM 等认证加密算法加密数据，用完立即从内存丢弃明文 DEK。

  3. 3

    把被包裹的 DEK 与密文、随机数一并存储；数据库或存储被拖走时，攻击者只拿到无法解开的密钥密文。

  4. 4

    解密时把被包裹的 DEK 发给 KMS 解密，KMS 校验调用者权限与加密上下文后返回明文 DEK，再本地解密数据。

  5. 5

    主密钥轮换只影响包裹层：新数据使用新版本主密钥，旧 DEK 仍可由旧版本解开，无需重新加密全部数据。

🔤 03 · 术语
数据密钥 (DEK)
直接加密业务数据的对称密钥，通常每个对象或每批数据一个。
密钥加密密钥 (KEK)
用来加密 DEK 的主密钥，保存在 KMS/HSM 中不导出。
加密上下文 (Encryption Context)
作为附加认证数据绑定到密文的键值对，解密时必须一致，并写入审计日志。
认证加密 (AEAD)
同时提供机密性与完整性的加密模式，如 AES-GCM。
密码学擦除 (Crypto-shredding)
删除或禁用密钥使对应密文永久无法解密，用于数据删除。
💻 04 · 代码
AWS KMS 信封加密python
# pip install boto3 cryptography ；KEY_ID 为你的 KMS 主密钥 ARN 或别名
import os, boto3
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

kms = boto3.client("kms")
KEY_ID = "alias/app-data"
CTX = {"tenant": "t-42", "purpose": "invoice"}     # 加密上下文，解密时须一致

def encrypt(plaintext: bytes) -> dict:
    dk = kms.generate_data_key(KeyId=KEY_ID, KeySpec="AES_256", EncryptionContext=CTX)
    nonce = os.urandom(12)
    ct = AESGCM(dk["Plaintext"]).encrypt(nonce, plaintext, None)
    del dk["Plaintext"]                              # 尽快丢弃明文数据密钥
    return {"wrapped_key": dk["CiphertextBlob"], "nonce": nonce, "ct": ct}

def decrypt(blob: dict) -> bytes:
    key = kms.decrypt(CiphertextBlob=blob["wrapped_key"], EncryptionContext=CTX)["Plaintext"]
    return AESGCM(key).decrypt(blob["nonce"], blob["ct"], None)

record = encrypt(b"card_last4=1234; amount=99.00")
assert decrypt(record).startswith(b"card_last4")

生产中建议使用 AWS Encryption SDK 等封装库，它们处理了消息格式、密钥缓存与算法选择。

📊 05 · 参数对比

直接 KMS 加密与信封加密

维度直接调用 KMS 加密信封加密
数据大小受接口大小上限限制（AWS 为 4 KB）任意大小
性能每次加解密都走网络数据本地加解密，仅包裹层调用 KMS
主密钥暴露从不离开 KMS从不离开 KMS
密钥粒度按主密钥可做到每对象一个 DEK
适合加密小型机密，如令牌文件、数据库字段、大批量数据
⚖️ 06 · 方案取舍

云 KMS（多租户 HSM 支撑）

优点托管、可审计、与云服务集成

代价依赖云厂商与网络可用性

适用云上应用的默认选择

专用 HSM / 自带密钥

优点满足更严格的合规与密钥主权

代价成本高，运维复杂

适用金融、政务等强监管场景

应用自管密钥

优点无外部依赖

代价密钥易泄露，缺少审计与轮换

适用不推荐用于生产敏感数据

🕳️ 07 · 常见坑

  • ✗把明文 DEK 与密文一起存储

    ✓只存储被主密钥包裹后的 DEK

  • ✗AES-GCM 重复使用相同密钥与随机数

    ✓每次加密生成新随机数，或每个对象使用新 DEK

  • ✗KMS 权限过宽，所有服务都能解密

    ✓按服务与用途拆分主密钥，最小授权并启用加密上下文条件

  • ✗每次解密都调用 KMS，触发限流与高延迟

    ✓在安全边界内短期缓存 DEK，并设置使用次数与时间上限

☑️ 08 · 检查清单
🎤 09 · 面试追问
为什么不直接用 KMS 加密所有数据？

KMS 加密接口对单次数据大小有上限，且每次调用都需网络往返并受速率限制，大数据量下性能与成本不可接受。信封加密只把很小的 DEK 交给 KMS 处理，数据在本地高速加密，同时主密钥依然从不离开 KMS。

信封加密如何简化密钥轮换？

轮换主密钥时，KMS 保留旧版本用于解密，新包裹操作使用新版本。由于数据是用 DEK 加密的，不需要重新加密海量数据；若要彻底淘汰旧主密钥，只需重新包裹存量 DEK，代价远小于重加密数据本身。

多租户 SaaS 中如何利用 KMS 做隔离？

可以为每个租户使用独立主密钥或至少独立加密上下文，KMS 策略限制只有处理该租户请求的身份才能解密。租户注销时禁用或删除其主密钥即可实现密码学擦除；审计日志按租户追踪每次解密。
