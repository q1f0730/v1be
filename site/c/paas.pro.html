📐 01 · 定义

PaaS（Platform as a Service，平台即服务）是由云厂商托管运行时、构建、扩缩容、TLS 与日志的应用托管模式，开发者只提交代码或镜像。它介于 IaaS（租虚拟机）与 SaaS（直接用软件）之间。Vercel、Netlify、Railway、Render 等是 AI 编程项目最常见的上线路径。

⚙️ 02 · 原理
  1. 1

    连接 Git 仓库后，平台在每次推送时拉取代码，自动识别框架并执行构建（或使用 Dockerfile）。

  2. 2

    构建产物被部署到平台管理的运行环境：容器、无服务器函数或边缘网络，并分配域名与 TLS 证书。

  3. 3

    环境变量与密钥在平台控制台按环境（预览/生产）配置，运行时注入进程。

  4. 4

    平台按流量或配置自动扩缩容、做健康检查，并提供日志、指标与一键回滚。

  5. 5

    数据库、缓存等有状态服务通常以附加组件或外部托管服务接入，应用本身保持无状态。

🔤 03 · 术语
IaaS / PaaS / SaaS
云服务三层：租基础设施、租运行平台、直接用软件。
预览部署 (Preview Deployment)
每个分支或 PR 自动生成独立可访问的部署地址。
构建包 (Buildpack)
自动检测语言并完成依赖安装与构建的脚本集合。
无状态 (Stateless)
实例不在本地保存持久数据，可随时被替换或扩容。
平台锁定 (Vendor Lock-in)
依赖平台专有功能，迁移到别处成本高。
💻 04 · 代码
用 Vercel CLI 部署bash
# 安装并登录
npm i -g vercel
vercel login

# 在项目目录中关联到 Vercel 项目
vercel link

# 按环境添加密钥（交互式输入值，不写进代码）
vercel env add DATABASE_URL production
vercel env pull .env.local     # 拉取开发环境变量到本地

# 部署预览版本（返回一个独立 URL）
vercel

# 确认无误后发布到生产
vercel --prod

# 查看某次部署的运行日志
vercel logs <deployment-url>

也可直接连 GitHub 自动部署；CLI 适合首次配置与排错。.env.local 不要提交。

⚖️ 06 · 方案取舍

PaaS

优点上线快、免运维、自带预览与回滚

代价规模大时单价高，受平台限制

适用MVP、小团队、前端为主项目

VPS 自运维

优点成本可控、完全自由

代价安全、更新、监控都要自己做

适用长期稳定负载、需特殊软件

Kubernetes

优点可移植、可大规模编排

代价复杂度与人力成本高

适用多服务、有平台团队

🕳️ 07 · 常见坑

  • ✗未设预算与用量告警，遭刷流量后账单暴涨

    ✓开启消费上限或告警，并为公开接口加限流

  • ✗把文件写到实例本地磁盘当持久存储

    ✓使用对象存储或数据库，实例保持无状态

  • ✗预览环境连接生产数据库

    ✓为预览/开发配置独立数据库与密钥

  • ✗重度依赖平台专有 API，迁移困难

    ✓核心逻辑保持框架通用，专有能力加一层封装

🎤 09 · 面试追问
PaaS 和 Serverless 有什么区别？

边界在模糊化。传统 PaaS 以常驻进程或容器运行应用、按实例计费；Serverless 函数按请求调度、空闲可缩到零、按调用和时长计费，但有执行时长、冷启动等限制。许多平台同时提供两种形态。

什么时候应该从 PaaS 迁出？

费用随规模显著高于自建；需要平台不支持的长连接、GPU、特殊系统依赖；合规要求数据驻留或专有网络；对延迟和网络拓扑有精细要求。迁移前先量化成本与运维人力。

为什么 PaaS 要求应用无状态？

平台会随时扩缩容、替换或重启实例，本地内存与磁盘不保证保留，多实例间也不共享。会话、上传文件、任务状态需放到数据库、缓存或对象存储，才能正确水平扩展与回滚。
