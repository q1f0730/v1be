软删除 / 逻辑删除

Soft Deletes

📐 01 · 定义

软删除（Soft Delete）是用标记列（如 deleted_at 时间戳或 is_deleted 布尔）代替物理 DELETE 的数据建模模式，查询时默认过滤已删除行。它属于应用数据模型层，用于误删恢复、审计留痕和保持引用关系，但会把「过滤已删除」的责任扩散到每一条查询。

⚙️ 02 · 原理
  1. 1

    表中增加 deleted_at 列，默认 NULL 表示有效，删除操作改为 UPDATE 写入当前时间。

  2. 2

    所有读取查询追加 WHERE deleted_at IS NULL，通常由 ORM 全局作用域或视图统一处理。

  3. 3

    唯一约束与索引改为只覆盖有效行（部分索引），避免已删除数据占用唯一键。

  4. 4

    恢复操作把 deleted_at 置回 NULL；关联数据需要按业务规则同步删除或恢复。

  5. 5

    定期任务把超过保留期的软删除数据物理清理或归档，满足存储与合规要求。

🔤 03 · 术语
硬删除 (Hard Delete)
执行 DELETE 物理移除行，无法通过应用恢复。
墓碑标记 (Tombstone)
标识数据已删除但仍保留记录的标志。
全局作用域 (Global Scope)
ORM 自动给查询附加过滤条件的机制。
归档表 (Archive Table)
把删除数据移入的独立表，主表保持干净。
被遗忘权 (Right to Erasure)
GDPR 第 17 条，用户可要求删除个人数据。
💻 04 · 代码
软删除的完整配套sql
ALTER TABLE posts ADD COLUMN deleted_at timestamptz;

-- 删除 = 打标记
UPDATE posts SET deleted_at = now() WHERE id = 42;

-- 视图统一过滤，业务代码查视图而不是原表
CREATE VIEW active_posts AS
  SELECT * FROM posts WHERE deleted_at IS NULL;

-- 唯一约束只针对有效行
CREATE UNIQUE INDEX posts_slug_active_uniq
  ON posts (slug) WHERE deleted_at IS NULL;

-- 常用查询的索引也加同样条件，体积更小
CREATE INDEX posts_author_active_idx
  ON posts (author_id, created_at) WHERE deleted_at IS NULL;

-- 定期清理：保留 30 天后物理删除（分批执行）
DELETE FROM posts
WHERE id IN (SELECT id FROM posts
             WHERE deleted_at < now() - interval '30 days' LIMIT 1000);

软删除要配套视图/作用域、部分索引和定期清理，否则会慢慢污染查询与约束。

⚖️ 06 · 方案取舍

deleted_at 列

优点实现简单，可记录删除时间

代价漏写过滤即泄露已删数据

适用需快速撤销删除的业务数据

归档表

优点主表查询与约束保持简单

代价删除需跨表事务，恢复较麻烦

适用删除频繁、主表查询量大

硬删除 + 审计日志

优点数据干净，合规处理直接

代价恢复需从日志或备份重建

适用个人敏感数据、合规优先

🕳️ 07 · 常见坑

  • ✗原生 SQL、报表、JOIN 中忘记过滤已删除行

    ✓统一通过视图或 ORM 作用域访问，并在审查中检查原生 SQL

  • ✗普通唯一索引导致删除后无法复用同名

    ✓使用 WHERE deleted_at IS NULL 的部分唯一索引

  • ✗把软删除当成满足用户删除请求

    ✓个人数据按隐私法规要求做硬删除或匿名化

  • ✗父记录软删除，子记录仍在列表中显示

    ✓明确级联规则，查询时同时检查父记录状态

☑️ 08 · 检查清单
🎤 09 · 面试追问
软删除对索引和性能有什么影响？

已删除行仍占表与索引空间，过滤条件让普通索引效率下降。应把常用索引和唯一索引改为 WHERE deleted_at IS NULL 的部分索引，并定期物理清理，控制表膨胀。

软删除和 GDPR 删除权冲突吗？

可能冲突。软删除数据仍是可识别的个人数据，收到删除请求通常需要硬删除或不可逆匿名化，并覆盖备份、日志和下游副本的处理策略。

deleted_at 和 is_deleted 布尔选哪个？

deleted_at 能同时表达状态与时间，便于按保留期清理和审计，部分索引条件同样简单；布尔字段信息量少。一般推荐时间戳，必要时另加 deleted_by 记录操作人。
