📐 01 · 定义

API（应用程序编程接口）是软件组件之间约定好的交互契约：规定可以调用哪些操作、传什么参数、返回什么结果、出错如何表示。它可以是库函数接口、操作系统接口，也可以是最常见的 Web API（通过 HTTP 访问）。API 让调用方只依赖契约而不依赖内部实现，是系统解耦和平台集成的基础。

⚙️ 02 · 原理
  1. 1

    定义契约：约定端点、方法、参数、数据格式、状态码和错误结构，常用 OpenAPI 描述。

  2. 2

    认证授权：调用方携带 API Key、OAuth 令牌等凭证，服务端识别身份并检查权限。

  3. 3

    请求处理：服务端校验参数、执行业务逻辑，并对调用频率做限流。

  4. 4

    返回结果：以约定格式（多为 JSON）返回数据与状态码，错误时给出机器可读的错误码。

  5. 5

    演进管理：通过版本号、向后兼容字段和弃用通知，在不破坏现有调用方的前提下迭代。

🔤 03 · 术语
REST
以资源为中心、用 HTTP 方法表达操作的 API 设计风格。
端点 (Endpoint)
API 中一个可访问的具体地址，如 POST /v1/messages。
OpenAPI
描述 HTTP API 的标准规范，可生成文档、客户端与测试。
幂等 (Idempotent)
重复调用产生相同效果，GET、PUT、DELETE 应满足。
限流 (Rate Limiting)
限制调用频率，超限通常返回 429 Too Many Requests。
💻 04 · 代码
一次 REST 调用http
POST /v1/orders HTTP/1.1
Host: api.example.com
Authorization: Bearer <access_token>
Content-Type: application/json
Idempotency-Key: 3f1c9a2e-order-001

{"product_id": "sku_123", "quantity": 2}

---- 成功响应 ----
HTTP/1.1 201 Created
Content-Type: application/json
Location: /v1/orders/ord_789

{"id": "ord_789", "status": "pending", "quantity": 2}

---- 错误响应 ----
HTTP/1.1 422 Unprocessable Content
Content-Type: application/json

{"error": {"code": "invalid_quantity", "message": "quantity must be >= 1"}}

方法、路径、鉴权头、请求体、状态码和结构化错误，构成一个完整的 API 契约示例。

⚖️ 06 · 方案取舍

直接调用 HTTP API

优点无额外依赖，完全可控

代价需自己处理鉴权、重试、分页

适用简单调用或无官方 SDK

使用官方 SDK

优点类型提示、重试与错误封装

代价多一个依赖，版本需跟进

适用主流服务（如模型 API）

经 MCP 暴露给 Agent

优点Agent 可按需发现并调用

代价需关注权限与安全边界

适用让 AI Agent 使用内部系统

🕳️ 07 · 常见坑

  • ✗所有错误都返回 200，错误信息写在正文里

    ✓用正确状态码，并返回结构化错误码

  • ✗修改字段含义或删除字段，老客户端崩溃

    ✓只做向后兼容的增量变更，破坏性变更走新版本

  • ✗列表接口不分页，一次返回全部数据

    ✓设计分页参数和最大条数上限

  • ✗调用第三方 API 不处理 429 和超时

    ✓设置超时，遇到 429/5xx 用指数退避重试

🎤 09 · 面试追问
PUT 和 PATCH 有什么区别？

PUT 用完整表示替换目标资源，语义上幂等；PATCH 只提交部分修改，是否幂等取决于补丁格式。实践中更新少量字段用 PATCH，整体替换用 PUT，并在文档中明确未传字段的处理方式。

如何设计 API 的错误响应？

HTTP 状态码表达类别（4xx 调用方问题、5xx 服务方问题），正文提供稳定的机器可读错误码、给人看的消息、出错字段和请求 ID。可参考 RFC 9457 Problem Details 格式，避免泄露堆栈等内部信息。

Function Calling 和 API 是什么关系？

Function Calling 让模型输出「调用哪个函数、传什么参数」的结构化请求，应用再据此真正调用 API。工具定义本质就是把 API 契约（名称、描述、参数 Schema）告诉模型，所以清晰的 API 设计直接决定 Agent 用得好不好。
