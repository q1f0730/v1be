全表扫描

Full Table Scans

📐 01 · 定义

全表扫描（Full Table Scan / Seq Scan）是查询执行器的一种访问路径：按物理顺序读取表的全部数据页，逐行判断过滤条件。它属于数据库执行计划层，本身不是错误——小表或需读大部分行时反而最快；问题在于大表上只取少量行却走了它，导致 I/O 与延迟随数据量线性增长。

⚙️ 02 · 原理
  1. 1

    SQL 经解析、改写后交给优化器（Optimizer），枚举可用访问路径：顺序扫描、索引扫描、位图扫描等。

  2. 2

    优化器依据统计信息（行数、值分布、相关性）估算每条路径的代价，选代价最低者。

  3. 3

    若过滤列无可用索引、谓词无法使用索引，或预估命中行比例高，就选择顺序扫描。

  4. 4

    执行时按页读取整张表，对每行求值 WHERE 条件，不满足的行被丢弃，读取量与表大小成正比。

  5. 5

    EXPLAIN 中出现 Seq Scan（PostgreSQL）或 type=ALL（MySQL）即为全表扫描，据此判断是否优化。

🔤 03 · 术语
执行计划 (Query Plan)
优化器为一条 SQL 选定的访问路径与算子树，用 EXPLAIN 查看。
选择性 (Selectivity)
谓词命中行占总行数的比例；越低越适合走索引。
可索引谓词 (Sargable)
能直接利用索引的条件写法，如 col = ?、col > ?。
统计信息 (Statistics)
表行数、列值分布等元数据，由 ANALYZE 收集，影响代价估算。
覆盖索引 (Covering Index)
索引包含查询所需全部列，无需回表读取数据行。
💻 04 · 代码
定位并消除全表扫描sql
-- PostgreSQL：查看实际执行计划与耗时
EXPLAIN ANALYZE
SELECT id, email FROM users WHERE lower(email) = 'a@b.com';
-- 输出若含 "Seq Scan on users"，说明逐行扫描

-- 原因：普通索引建在 email 上，但条件对列套了函数
-- 方案一：建表达式索引，与查询写法保持一致
CREATE INDEX idx_users_lower_email ON users (lower(email));

-- 方案二：前缀匹配可用 B-tree（需 text_pattern_ops 或 C 排序规则）
CREATE INDEX idx_users_email_prefix ON users (email text_pattern_ops);
EXPLAIN SELECT id FROM users WHERE email LIKE 'abc%';

-- 更新统计信息，避免优化器误判
ANALYZE users;

对列套函数会让普通索引失效；建与查询一致的表达式索引后应变为 Index Scan。

📊 05 · 参数对比

常见访问路径对比

访问路径典型场景代价特征
Seq Scan / ALL小表、读取大部分行与表大小线性相关
Index Scan高选择性等值/范围随机 I/O，命中少时快
Index Only Scan覆盖索引不回表，最省 I/O
Bitmap Heap Scan中等选择性、多条件先建位图再批量读页
⚖️ 06 · 方案取舍

新增索引

优点读查询从线性降到对数级

代价写入变慢、占存储、需维护

适用高频查询且选择性高的列

改写 SQL 使谓词可索引

优点零存储成本，立竿见影

代价需改业务代码，易被后人改回

适用函数包列、隐式类型转换导致失效

接受全表扫描

优点无额外维护成本

代价数据增长后延迟线性上升

适用小表、离线报表、读大比例行

🕳️ 07 · 常见坑

  • ✗WHERE 中对索引列做函数或运算，如 DATE(created_at)=…

    ✓改为范围条件 created_at >= … AND < …，或建表达式索引

  • ✗参数类型与列类型不一致触发隐式转换

    ✓保持绑定参数类型与列定义一致，如字符串列不要传数字

  • ✗以为 LIKE '%词%' 能走普通 B-tree 索引

    ✓前导通配无法用 B-tree；改用全文索引或 pg_trgm 等专用方案

  • ✗只在开发库测执行计划，数据量与生产差几个量级

    ✓用接近生产规模的数据或在只读副本上 EXPLAIN ANALYZE

🎤 09 · 面试追问
有索引为什么优化器仍选择全表扫描？

代价估算认为更便宜：命中比例高时随机回表比顺序读贵；统计信息过期致误判；谓词不可索引（函数、隐式转换、前导通配）；复合索引列序不匹配。用 EXPLAIN ANALYZE 对比估算与实际行数定位。

如何在生产上系统地发现全表扫描？

开慢查询日志；PostgreSQL 用 pg_stat_statements 按总耗时排序，并看 pg_stat_user_tables 里 seq_scan 偏高的大表；MySQL 看 slow log。再对 Top SQL 逐条 EXPLAIN。

复合索引 (a,b) 能否支持 WHERE b=?

B-tree 复合索引遵循最左前缀，单独按 b 过滤通常无法高效使用（个别数据库有 skip scan 优化但不可依赖）。应根据查询模式调整列顺序或为 b 单独建索引。
