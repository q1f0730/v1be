ETL 与 ELT

ETL vs ELT

📐 01 · 定义

ETL（Extract-Transform-Load）与 ELT（Extract-Load-Transform）是把数据从业务系统搬运到分析系统的两种流程。ETL 在加载前于独立引擎中完成清洗转换，只写入整理好的数据；ELT 先把原始数据原样加载进云数据仓库或湖仓，再利用仓库的计算能力用 SQL 转换。云数仓普及后，ELT + dbt 成为主流。

⚙️ 02 · 原理
  1. 1

    抽取（Extract）：从业务数据库、SaaS API、日志等源系统批量或增量（如基于时间戳或 CDC）读取数据。

  2. 2

    ETL 路径：在独立引擎（如 Spark、传统 ETL 工具）中清洗、去重、关联、脱敏，再加载结构化结果。

  3. 3

    ELT 路径：用 Fivetran、Airbyte 等工具把原始数据原样加载到仓库的原始层（raw / staging）。

  4. 4

    在仓库内用 SQL 分层建模：staging 清洗字段、intermediate 关联整合、marts 产出面向业务的宽表与指标。

  5. 5

    编排工具（如 Airflow、Dagster）调度各步骤，配合数据测试、血缘和文档保证质量与可追溯。

🔤 03 · 术语
数据仓库 (Data Warehouse)
面向分析查询优化的集中式存储，如 BigQuery、Snowflake。
dbt (data build tool)
用 SQL 和模板在仓库内做转换、测试与文档的工具。
增量加载 (Incremental Load)
只同步自上次以来新增或变化的数据。
原始层 (Raw / Staging Layer)
保存原样或轻度清洗数据的层，便于重算。
数据血缘 (Data Lineage)
记录数据从源到报表经过的转换链路。
数据契约 (Data Contract)
生产方与消费方约定的数据结构与质量规则。
💻 04 · 代码
dbt 模型：在仓库内转换（ELT 中的 T）sql
-- models/marts/daily_sales.sql
-- 原始数据已由 EL 工具加载到 raw 层，stg_ 模型做了字段清洗
{{ config(materialized='incremental', unique_key='order_date') }}

select
    date(o.created_at)            as order_date,
    count(distinct o.order_id)    as orders,
    sum(p.amount)                 as revenue
from {{ ref('stg_orders') }}   as o
join {{ ref('stg_payments') }} as p
  on p.order_id = o.order_id
where p.status = 'succeeded'
{% if is_incremental() %}
  -- 增量：只重算最近 3 天，覆盖迟到数据
  and date(o.created_at) >= (select max(order_date) - interval 3 day from {{ this }})
{% endif %}
group by 1

ref() 自动建立依赖与血缘，incremental 只重算近期分区；日期函数语法因仓库而异。

ETL 与 ELT 对比

维度ETLELT
转换位置仓库外的处理引擎仓库内（SQL）
原始数据通常不保留保留在原始层，可重算
灵活性新需求需改管道改 SQL 模型即可

⚖️ 06 · 方案取舍

ETL

优点进入仓库前完成脱敏与过滤，存储更少

代价变更成本高，丢失原始数据

适用合规要求严格、仓库算力有限

ELT

优点保留原始数据，迭代快，SQL 门槛低

代价仓库计算与存储成本上升

适用云数仓、需求快速变化

流式 ETL / CDC

优点近实时

代价架构复杂，运维成本高

适用实时看板、风控

🕳️ 07 · 常见坑

  • ✗只保存加工后的结果，口径变更无法重算

    ✓原始层完整保留数据，转换可重复执行

  • ✗原始层中的个人信息对所有分析师开放

    ✓原始层严格授权，在 staging 层脱敏

  • ✗全量重跑所有模型，成本与耗时失控

    ✓对大表使用增量模型与分区

  • ✗转换没有测试，脏数据流入报表

    ✓为关键模型加唯一性、非空、关联完整性测试

🎤 09 · 面试追问
为什么 ELT 在云数仓时代成为主流？

云数仓存算分离、可弹性扩展，在仓库内用 SQL 做大规模转换变得便宜高效；保留原始数据后，口径变化只需修改模型重算。dbt 让转换代码可以版本控制、测试和复用，使数据工程实践更接近软件工程。

什么情况下仍应选择 ETL？

当法规要求敏感数据在进入分析环境前就脱敏或过滤，目标系统算力有限或按扫描计费很贵，或需要在加载前进行复杂的非 SQL 处理（如图像、半结构化解析）时，ETL 更合适。实际中两者常混合使用。

如何处理迟到数据和增量更新？

增量模型每次只处理新数据，但事件可能迟到，因此通常回溯重算最近几天的分区；配合 unique_key 做合并（merge）避免重复。源端使用更新时间戳或 CDC 捕获修改与删除，保证仓库与源系统一致。
