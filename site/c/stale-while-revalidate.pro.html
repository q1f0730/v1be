过期仍用后台刷新 (SWR)

Stale-While-Revalidate

🧸 回到小白版

📐 01 · 定义

Stale-While-Revalidate（SWR）是一种缓存策略：缓存过了新鲜期后的一段宽限时间内，先立即返回旧（stale）内容，同时在后台异步重新验证或获取新内容并更新缓存。它由 RFC 5861 定义为 HTTP Cache-Control 扩展指令，也被前端库（如 Vercel 的 SWR）广泛采用，以少量陈旧换稳定低延迟。

⚙️ 02 · 原理
  1. 1

    响应携带 Cache-Control: max-age=N, stale-while-revalidate=M，表示 N 秒内为新鲜，此后 M 秒内可用旧内容。

  2. 2

    在 max-age 规定的新鲜期内，请求直接由缓存返回内容，完全不访问源站。

  3. 3

    超过 max-age 但在宽限期内的请求，缓存立即返回旧内容，并在后台向源站发起重新验证（可带 ETag 条件请求）。

  4. 4

    后台请求成功后更新缓存，后续请求获得新内容；超过 max-age + M 后缓存不可再直接使用旧内容，必须等待源站响应。

  5. 5

    配合 stale-if-error 指令，可在源站出错时继续返回旧内容，提高可用性。

🔤 03 · 术语
新鲜期 (Freshness Lifetime)
由 max-age 或 s-maxage 定义，期间缓存可直接使用。
重新验证 (Revalidation)
向源站确认缓存是否仍有效，常用 ETag/If-None-Match。
stale-if-error
源站出错时允许在指定时间内返回过期内容。
s-maxage
只作用于共享缓存（CDN、代理）的新鲜期。
useSWR
Vercel 的 React 数据请求 Hook，按 SWR 思路先返回缓存再重新请求。
💻 04 · 代码
HTTP 响应头与前端 useSWRjavascript
// 服务端（Express）：CDN 60 秒新鲜，之后 5 分钟内可先返回旧内容并后台刷新
app.get("/api/articles", async (req, res) => {
  res.set("Cache-Control",
    "public, s-maxage=60, stale-while-revalidate=300, stale-if-error=86400");
  res.json(await listArticles());
});
// 注意：不同 CDN 对 stale-while-revalidate 的支持不同，以各自文档为准

// 前端（React）：先显示缓存数据，同时后台重新请求
import useSWR from "swr";
const fetcher = (url) => fetch(url).then((r) => r.json());

export function ArticleList() {
  const { data, error, isLoading } = useSWR("/api/articles", fetcher);
  if (error) return <p>加载失败</p>;
  if (isLoading) return <p>加载中…</p>;
  return <ul>{data.map((a) => <li key={a.id}>{a.title}</li>)}</ul>;
}

同一思想在 CDN 层（响应头）和浏览器层（useSWR）各用一次，均以短暂旧数据换即时响应。

Cache-Control 相关指令

指令作用示例

⚖️ 06 · 方案取舍

SWR

优点响应始终快，源站压力平滑

代价用户可能看到稍旧的数据

适用文章列表、商品目录、仪表盘

严格过期（max-age 后同步回源）

优点过期后数据较新

代价过期瞬间请求变慢，可能并发回源

适用数据时效性要求中等

不缓存 / no-store

优点始终最新

代价延迟与源站负载最高

适用余额、库存扣减、个人敏感数据

🕳️ 07 · 常见坑

  • ✗对个性化或敏感接口设置 public + SWR

    ✓个人数据使用 private 或 no-store，共享缓存只缓存公共内容

  • ✗宽限期设得过长，用户长时间看到过时内容

    ✓按业务可接受的陈旧度设置，并在数据变更时主动清除 CDN 缓存

  • ✗假设所有 CDN 都支持该指令

    ✓查阅所用 CDN 文档，必要时在边缘函数中实现

  • ✗前端 useSWR 未处理错误与重复请求

    ✓配置去重、错误重试与降级展示

☑️ 08 · 检查清单
🎤 09 · 面试追问
SWR 与普通 TTL 缓存有什么区别？

普通 TTL 缓存过期后，下一个请求必须同步等待回源，延迟突增且可能多个请求同时回源。SWR 在宽限期内立即返回旧内容并后台刷新，用户不感知等待，源站请求也更平滑，代价是短时间内看到旧数据。

什么数据不适合用 SWR？

对时效和正确性要求严格的数据，如账户余额、库存扣减、支付状态、权限变更；以及个性化或敏感内容（不能进入共享缓存）。这些应直接读源，或用短 TTL 加主动失效。

前端 useSWR 解决了什么问题？

它把“先显示缓存、再后台请求、获得结果后更新界面”的模式封装成 Hook，并提供请求去重、窗口聚焦时重新验证、错误重试和乐观更新等能力，减少手写加载状态和缓存管理代码。
