多租户架构

Multi-Tenancy

📐 01 · 定义

多租户（Multi-Tenancy）是让一套应用实例与基础设施同时服务多个客户（租户）的架构方式，是 SaaS 的基础。核心问题是在隔离性、成本与运维复杂度之间取舍：数据、计算、配置和故障影响面都要按租户隔离，同时尽量共享资源以降低单租户成本。

⚙️ 02 · 原理
  1. 1

    身份层在认证时确定租户上下文（如 JWT 中的 tenant_id），并在请求整个生命周期中传递。

  2. 2

    数据层选择隔离模型：共享库共享表加 tenant_id（池化）、每租户独立 schema、或每租户独立数据库（孤岛）。

  3. 3

    在共享表模式下，用数据库行级安全（RLS）或数据访问层强制附加租户过滤，避免依赖每条查询手写条件。

  4. 4

    计算与配额层按租户限流、设置资源上限，缓解吵闹邻居（Noisy Neighbor）问题。

  5. 5

    运维层支持按租户迁移、备份恢复、计量计费，并可把大客户迁到独立资源（混合模型）。

🔤 03 · 术语
租户 (Tenant)
共享系统中逻辑隔离的一个客户单位，通常是一家组织。
孤岛/池化 (Silo/Pool)
AWS SaaS 文献中的术语：资源按租户独占或在租户间共享。
行级安全 (RLS)
数据库按策略自动过滤行，PostgreSQL 通过 CREATE POLICY 实现。
吵闹邻居 (Noisy Neighbor)
某租户过量使用共享资源，拖慢同一资源上的其他租户。
租户上下文 (Tenant Context)
贯穿请求、日志、缓存键和异步任务的当前租户标识。
💻 04 · 代码
PostgreSQL RLS 租户隔离sql
CREATE TABLE invoices (
  id         bigserial PRIMARY KEY,
  tenant_id  uuid    NOT NULL,
  amount     numeric NOT NULL
);
CREATE INDEX ON invoices (tenant_id);

ALTER TABLE invoices ENABLE ROW LEVEL SECURITY;
ALTER TABLE invoices FORCE ROW LEVEL SECURITY;  -- 表属主也受约束

CREATE POLICY tenant_isolation ON invoices
  USING (tenant_id = current_setting('app.tenant_id')::uuid)
  WITH CHECK (tenant_id = current_setting('app.tenant_id')::uuid);

-- 应用每个事务开头设置租户（连接池下务必用 SET LOCAL）
BEGIN;
SET LOCAL app.tenant_id = '6f1c2a8e-0000-4000-8000-000000000001';
SELECT * FROM invoices;          -- 只返回该租户的行
COMMIT;

超级用户和带 BYPASSRLS 的角色会绕过策略，应用应使用普通角色连接。

📊 05 · 参数对比

数据隔离模型对比

模型隔离强度单租户成本运维复杂度
共享表 + tenant_id依赖应用/RLS最低低，但迁移单租户难
每租户 schema中中迁移脚本需跑 N 次
每租户数据库强高连接数与运维随租户增长
混合（大客户独立）按层级按套餐区分需要支持两种路径
⚖️ 06 · 方案取舍

池化（共享表）

优点资源利用率高，上线新租户零成本

代价一个漏洞可能跨租户泄露

适用大量中小租户的 SaaS

孤岛（独立库/集群）

优点强隔离，便于满足合规与数据驻留

代价成本高，版本与迁移管理复杂

适用大客户、强监管行业

混合分层

优点按套餐平衡成本与隔离

代价代码与运维要同时支持多模式

适用客户规模差异大的成长期产品

🕳️ 07 · 常见坑

  • ✗缓存键、对象存储路径没带租户前缀

    ✓租户 ID 进入所有缓存键、存储路径和搜索索引的命名

  • ✗后台任务和消息消费丢失租户上下文

    ✓消息体携带 tenant_id，消费者显式设置上下文后再访问数据

  • ✗连接池里用 SET 设置租户，串到下个请求

    ✓在事务内用 SET LOCAL，或每次借出连接时重置

  • ✗租户 ID 取自请求参数而非认证令牌

    ✓以服务端校验过的身份为准，忽略客户端传入的租户字段

☑️ 08 · 检查清单
🎤 09 · 面试追问
共享表模式下如何保证不跨租户泄露？

多层防御：认证令牌确定租户；数据访问层或 ORM 全局作用域自动加过滤；数据库 RLS 作为最后一道防线，并启用 FORCE 让属主也受约束；缓存与文件路径带租户前缀；再用两个租户互访的集成测试持续回归。

如何处理吵闹邻居？

先可观测：按租户统计请求量、慢查询和资源占用。再控制：按租户限流、队列分级、查询超时和配额。最后隔离：把重度租户迁到独立的数据库分片或计算池。计费模型也可引导用量。

每租户一库的模型主要痛点是什么？

数据库数量随租户线性增长，连接池、监控、备份成本上升；每次 schema 迁移要对所有库执行并处理部分失败；跨租户分析需要额外汇总管道。适合租户少而价值高的场景。
