热点分区 / 数据倾斜

Hot Partitions

🧸 回到小白版

📐 01 · 定义

热点分区（Hot Partition）指分布式存储或消息系统中，少数分区承接了不成比例的读写流量或数据量（数据倾斜），导致这些分区被限流或过载，而其他分区空闲。根源多是分区键选择不当，如低基数、单调递增或集中在少数大客户上，会让水平扩展失效。

⚙️ 02 · 原理
  1. 1

    路由：每个请求按分区键做哈希或范围映射，最终落到某个具体分区上。

  2. 2

    若键的分布不均（如某明星用户、当天日期），大量请求落到同一分区。

  3. 3

    单分区有吞吐上限（如 DynamoDB 单分区有读写容量上限），超出后被限流。

  4. 4

    表现：集群整体资源利用率并不高，但个别分区延迟飙升、错误率上升。

  5. 5

    缓解：换更分散的键、对热键加随机后缀做写分片、加缓存、拆分热点租户。

🔤 03 · 术语
数据倾斜 (Data Skew)
数据或负载在分区间分布显著不均。
热键 (Hot Key)
访问频率远高于其他键的单个键。
写分片 (Write Sharding)
为热键追加后缀，把写入分散到多个分区。
自适应容量 (Adaptive Capacity)
DynamoDB 自动给热点分区借用更多吞吐的机制。
基数 (Cardinality)
某列不同取值的数量，低基数键易导致倾斜。
💻 04 · 代码
热键写分片python
import random

N_SUFFIX = 10   # 后缀数量，按热点流量估算

def write_key(campaign_id: str) -> str:
    # 写入时随机加后缀：同一活动的数据分散到 10 个分区键
    return f"{campaign_id}#{random.randrange(N_SUFFIX)}"

def read_keys(campaign_id: str) -> list[str]:
    # 读取时需查询所有后缀再合并（读放大的代价）
    return [f"{campaign_id}#{i}" for i in range(N_SUFFIX)]

# 若需要按 ID 精确读取单条，可改用确定性后缀：
def stable_key(campaign_id: str, item_id: int) -> str:
    return f"{campaign_id}#{item_id % N_SUFFIX}"

用读放大换写入均衡；确定性后缀可在不扇出的情况下按 ID 定位。

📊 05 · 参数对比

热点成因与对策

成因例子对策
单调递增键以日期、自增 ID 做分区键哈希化或加前缀打散
超级用户/大租户头部客户占大量流量单独分片或二级拆分
突发热点秒杀商品、热门帖子缓存、写分片、请求合并
低基数键以状态、国家做分区键组合更高基数的列
⚖️ 06 · 方案取舍

随机后缀写分片

优点写入均匀分散

代价读取需扇出合并

适用写多读少的计数、日志

前置缓存

优点直接削掉热点读

代价有一致性和缓存击穿问题

适用热点以读为主

更换分区键

优点从根本上改善分布

代价需要数据迁移和代码改动

适用倾斜是结构性的

🕳️ 07 · 常见坑

  • ✗只看集群整体指标，没发现单个分区已被限流

    ✓监控按分区/按键的流量和限流次数，识别热键

  • ✗以时间戳或日期作为分区键，当前时段全部写入一处

    ✓时间放到排序键，分区键用高基数实体 ID

  • ✗Kafka 用固定或空值较多的 key，消息全进一个分区

    ✓检查 key 分布，避免大量相同或空 key 集中

🎤 09 · 面试追问
如何发现热点分区？

看按分区或按键的指标：请求数、限流次数、延迟、存储量；云数据库常提供热键诊断工具。典型信号是整体使用率不高但出现限流或个别分区延迟高。Kafka 中表现为某些分区消费滞后明显更大。

写分片后读取怎么办？

随机后缀需并行查询所有后缀再合并，读放大与后缀数成正比；若读按某 ID，可用确定性后缀直接定位。也可用异步任务把分散数据定期聚合为汇总记录供读取。

为什么扩容解决不了热点？

热点是单个键或分区的负载超过单分区上限，增加分区数并不会把同一个键拆开，热键仍落在一个分区。必须改变键的分布或在热键前加缓存、合并请求。
