端到端测试 (E2E)

End-to-End Testing

📐 01 · 定义

端到端测试（End-to-End Testing，E2E）是从真实用户视角出发，在接近生产的完整系统上自动执行用户流程（如注册、下单）的测试，覆盖前端、后端、数据库和外部集成。它位于测试金字塔顶端，信心最高但最慢、最易不稳定，通常只覆盖关键业务路径。

⚙️ 02 · 原理
  1. 1

    启动完整应用栈（前端、API、数据库，外部服务可用沙箱或模拟），准备测试数据。

  2. 2

    测试框架驱动真实浏览器（Chromium、Firefox、WebKit），按用户操作导航、点击、输入。

  3. 3

    通过可访问性角色、文本或 test-id 定位元素，框架自动等待元素可交互。

  4. 4

    断言用户可见的结果：页面内容、URL、提示信息，必要时校验数据库状态。

  5. 5

    失败时保存截图、视频和 trace 便于排查；在 CI 中并行执行并对不稳定用例重试。

🔤 03 · 术语
Playwright
微软开源的浏览器自动化与测试框架，支持多浏览器。
自动等待 (Auto-waiting)
操作前自动等待元素可见、可用，减少硬编码 sleep。
定位器 (Locator)
描述如何找到页面元素的对象，推荐按角色和文本定位。
Trace
记录测试每一步的 DOM 快照、网络和日志，用于回放排查。
测试金字塔 (Test Pyramid)
单元测试多、集成测试中、E2E 测试少的分层结构。
💻 04 · 代码
Playwright 登录流程测试typescript
// tests/login.spec.ts  运行: npx playwright test
import { test, expect } from "@playwright/test";

test("用户登录后看到控制台", async ({ page }) => {
  await page.goto("http://localhost:3000/login");

  // 按可访问性角色和标签定位，比 CSS 选择器更稳定
  await page.getByLabel("邮箱").fill("demo@example.com");
  await page.getByLabel("密码").fill("correct-password");
  await page.getByRole("button", { name: "登录" }).click();

  // expect 会自动重试直到超时，无需手写 sleep
  await expect(page).toHaveURL(/\/dashboard/);
  await expect(page.getByRole("heading", { name: "控制台" })).toBeVisible();
});

test("密码错误时提示", async ({ page }) => {
  await page.goto("http://localhost:3000/login");
  await page.getByLabel("邮箱").fill("demo@example.com");
  await page.getByLabel("密码").fill("wrong");
  await page.getByRole("button", { name: "登录" }).click();
  await expect(page.getByText("邮箱或密码错误")).toBeVisible();
});

覆盖成功与失败路径；用角色定位和 Web 优先断言避免不稳定。

⚖️ 06 · 方案取舍

少量关键路径 E2E

优点守住核心体验，维护可控

代价覆盖面有限

适用大多数产品

大量 E2E 覆盖细节

优点表面上覆盖全

代价慢、不稳定、维护重

适用通常不推荐

E2E 中模拟外部服务

优点稳定可控

代价测不到真实集成

适用支付、短信等第三方依赖

🕳️ 07 · 常见坑

  • ✗用 sleep 固定等待

    ✓依赖框架自动等待和带重试的断言

  • ✗用易变的 CSS 类名或 DOM 层级定位

    ✓按角色、标签、文本或 data-testid 定位

  • ✗测试之间共享数据，顺序一变就失败

    ✓每个测试独立创建并清理自己的数据

  • ✗不稳定用例靠无限重试掩盖

    ✓记录 flaky 率，定位根因修复

☑️ 08 · 检查清单
🎤 09 · 面试追问
为什么 E2E 测试应该少而精？

E2E 依赖完整环境，运行慢、受网络和数据影响容易不稳定，失败时需要逐层排查才能定位。大量 E2E 会拖慢反馈、增加维护成本。应把细节逻辑交给单元和集成测试，E2E 只守护最关键的用户旅程。

如何降低 E2E 测试的不稳定性？

使用框架的自动等待和重试断言而非 sleep；用稳定的语义化定位器；每个测试隔离数据；模拟不可控的第三方服务；固定视口、时区和语言；开启 trace 分析失败原因，并统计 flaky 率逐个修复。

AI Agent 如何参与 E2E 测试？

Agent 可以根据用户故事生成 Playwright 测试草稿，或借助浏览器自动化工具（如 Playwright MCP）实际操作页面验证改动。但生成的定位器和断言需要人审查，确保测的是用户可见行为，而不是迁就当前实现。
