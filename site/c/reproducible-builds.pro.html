可复现构建

📐 01 · 定义

可复现构建（Reproducible Builds）指在相同源码、相同构建环境与指令下，任何人都能独立产出逐位（bit-for-bit）相同的制品。它属于软件供应链完整性手段，用于证明二进制确实由公开源码构建、未被构建机植入后门，也让缓存和差异审计更可靠。

⚙️ 02 · 原理
  1. 1

    固定输入：锁定源码提交、依赖版本（lockfile、哈希校验）和工具链版本，避免浮动版本。

  2. 2

    消除时间戳：用 SOURCE_DATE_EPOCH 统一写入文件的时间，归档时设置固定 mtime。

  3. 3

    消除环境差异：固定文件排序、时区、语言区域（locale）、用户/组 ID、构建路径等元数据。

  4. 4

    隔离构建：在容器或 Nix/Bazel 等密封（hermetic）环境中构建，禁止构建期联网取浮动资源。

  5. 5

    独立复验：两台或多台机器分别构建，比较产物哈希；不一致时用 diffoscope 定位差异来源。

🔤 03 · 术语
SOURCE_DATE_EPOCH
约定的环境变量，给构建工具提供统一的 Unix 时间戳。
密封构建 (Hermetic Build)
构建只依赖声明过的输入，不读取宿主机或网络上的隐式状态。
diffoscope
递归比较两个制品内部差异的工具，可深入压缩包和二进制。
SLSA
供应链制品完整性框架，按级别规定构建来源与防篡改要求。
构建来源证明 (Provenance)
描述制品由谁、用什么源码和流程构建的签名元数据。
💻 04 · 代码
产出确定性 tar 包bash
# 用最后一次提交时间作为统一时间戳
export SOURCE_DATE_EPOCH=$(git log -1 --pretty=%ct)
export TZ=UTC LC_ALL=C

# 固定排序、mtime、属主，去掉不确定元数据
tar --sort=name \
    --mtime="@${SOURCE_DATE_EPOCH}" \
    --owner=0 --group=0 --numeric-owner \
    -cf dist.tar src/

# gzip -n：不写入原文件名和时间戳
gzip -n -9 -f dist.tar
sha256sum dist.tar.gz   # 在另一台机器重复，哈希应一致

打包环节最常见的不确定来源是时间、顺序和属主，逐一固定即可复现。

⚖️ 06 · 方案取舍

容器内构建+锁定依赖

优点改造成本低，多数项目可落地

代价基础镜像和系统包仍可能漂移

适用普通业务服务

Nix / Bazel 密封构建

优点输入完全声明，复现性强

代价学习曲线陡，生态迁移成本高

适用大型单仓、对供应链要求高

只做来源证明不追求逐位一致

优点实现快，满足 SLSA 部分级别

代价无法独立验证产物与源码对应

适用短期合规、先补可追溯性

🕳️ 07 · 常见坑

  • ✗Dockerfile 里 apt-get install 不锁版本，每次构建结果不同

    ✓锁定基础镜像 digest，或使用快照源固定包版本

  • ✗认为同一台机器构建两次一致就算可复现

    ✓在不同机器、不同路径和用户下构建再比对哈希

  • ✗构建脚本里写入 date 或 git describe --dirty 等易变信息

    ✓版本信息只取自提交元数据，时间统一取 SOURCE_DATE_EPOCH

🎤 09 · 面试追问
可复现构建防的是什么威胁？

主要防构建环节被篡改：构建机或 CI 被入侵后植入代码，源码审计也发现不了。多方独立构建出相同哈希，就能证明二进制与公开源码一致。它不能防源码本身或依赖源头被投毒。

Docker 镜像为什么难以逐位复现？

层的 tar 包含文件时间戳，镜像配置含创建时间，RUN 安装的系统包随软件源变化，构建工具也可能写入元数据。需要固定基础镜像、包版本，并利用 BuildKit 对 SOURCE_DATE_EPOCH 的支持。

和 SLSA 来源证明是什么关系？

来源证明是构建方签名的声明，说明产物如何生成，信任依赖构建平台；可复现构建允许第三方自行重建验证，不必信任构建方。两者互补，前者易落地，后者证明力更强。
