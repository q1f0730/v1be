旁路缓存 (Cache-Aside)

Cache-Aside

📐 01 · 定义

旁路缓存（Cache-Aside，又称 Lazy Loading）是最常用的缓存读写模式：应用读取时先查缓存，命中直接返回；未命中则查询数据库，把结果写入缓存并设置过期时间。写入时先更新数据库，再删除（而非更新）对应缓存。缓存只是数据库的可丢弃副本，由应用代码而非缓存系统负责维护一致性。

⚙️ 02 · 原理
  1. 1

    读请求先按键查询缓存（如 Redis GET），命中则直接返回，避免访问数据库。

  2. 2

    未命中时查询数据库，将结果序列化写入缓存并设置 TTL，再返回给调用方。

  3. 3

    写请求先更新数据库，成功后删除对应缓存键，使下一次读取重新加载最新数据。

  4. 4

    选择删除而非更新缓存，可避免并发写入时缓存与数据库出现不同的写入顺序。

  5. 5

    TTL 作为最终兜底：即使删除失败或出现竞态，脏数据也会在过期后被自动纠正。

🔤 03 · 术语
缓存命中 (Cache Hit)
请求的数据在缓存中存在，直接返回。
懒加载 (Lazy Loading)
只在首次被请求时才把数据加载到缓存。
缓存失效 (Invalidation)
数据变更后让旧缓存不再被使用，常用删除键。
TTL
缓存键的存活时间，到期自动删除。
延迟双删 (Delayed Double Delete)
写库前后各删一次缓存，第二次延迟执行以缓解竞态。
负缓存 (Negative Caching)
缓存“不存在”的结果，防止重复查询数据库。
💻 04 · 代码
redis-py 实现旁路缓存python
import json, random
import redis

r = redis.Redis(decode_responses=True)
TTL = 600  # 10 分钟

def get_product(pid: int, db) -> dict | None:
    key = f"product:{pid}"
    if (cached := r.get(key)) is not None:      # 1. 先查缓存
        return json.loads(cached)
    row = db.fetch_product(pid)                  # 2. 未命中查数据库
    if row is not None:
        # 3. 写回缓存；TTL 加随机抖动，避免大量键同时过期
        r.set(key, json.dumps(row), ex=TTL + random.randint(0, 60))
    return row

def update_price(pid: int, price: float, db) -> None:
    db.update_price(pid, price)                  # 1. 先更新数据库
    r.delete(f"product:{pid}")                   # 2. 再删除缓存（不是更新）

读路径懒加载并带随机 TTL，写路径先写库后删缓存；db 为示意的数据访问对象。

📊 05 · 参数对比

常见缓存模式对比

模式读路径写路径一致性特点
Cache-Aside应用查缓存，未命中查库回填写库后删缓存应用负责，最常用
Read-Through缓存层自动从库加载通常配合其他模式对应用透明
Write-Through同上同步写缓存与数据库一致性较好，写延迟高
Write-Back同上先写缓存，异步刷库写快，宕机可能丢数据
⚖️ 06 · 方案取舍

写后删除缓存

优点实现简单，避免并发更新顺序问题

代价下次读取有一次未命中

适用绝大多数读多写少场景

写后更新缓存

优点读取始终命中

代价并发写可能导致缓存与库不一致

适用计算成本高、写少且串行

订阅变更（CDC）删除缓存

优点与业务代码解耦，可靠重试

代价引入额外组件与延迟

适用多服务共享数据、高一致性要求

🕳️ 07 · 常见坑

  • ✗先删缓存再写数据库，并发读把旧值写回缓存

    ✓先写数据库再删缓存，并设置 TTL 兜底

  • ✗缓存不设 TTL，脏数据永久存在

    ✓所有缓存键设置 TTL，并加随机抖动

  • ✗热点键过期瞬间大量请求击穿数据库

    ✓对热点键加互斥锁重建或提前异步刷新

  • ✗查询不存在的数据每次都打到数据库

    ✓对空结果做短 TTL 负缓存或使用布隆过滤器

☑️ 08 · 检查清单
🎤 09 · 面试追问
为什么是先写数据库再删缓存，而不是反过来？

若先删缓存，在写库完成前有并发读请求未命中，会把旧值读出并写回缓存，导致长期脏数据。先写库再删缓存时，出现不一致需要更苛刻的时序（读在写前查库、在删除后才回填），概率低得多，且 TTL 可兜底。

为什么删除缓存而不是直接更新缓存？

两个并发写请求可能以不同顺序完成数据库更新和缓存更新，使缓存保留较旧的值。删除让下一次读取从数据库加载最新值，避免顺序问题；同时也避免为可能不会被读取的数据做无谓的序列化计算。

Cache-Aside 能保证强一致吗？

不能，它提供的是最终一致：在写库与删缓存之间、删除失败或极端竞态下，短时间内可能读到旧数据。需要强一致的场景应直接读数据库，或使用带版本号的缓存、分布式锁等更复杂方案，并权衡性能。
