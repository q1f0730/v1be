服务端授权

Server-Side Authorization

📐 01 · 定义

服务端授权（Server-Side Authorization）指所有访问控制决策都在服务器或可信后端执行，前端的隐藏按钮、路由守卫只用于体验而不作为安全边界。它基于一个事实：客户端完全由用户控制，任何请求都可以被构造、修改和重放。这是防止越权、IDOR 和权限绕过的基本原则。

⚙️ 02 · 原理
  1. 1

    前端可以根据角色显示或隐藏功能，但这只影响界面，不阻止任何请求。

  2. 2

    每个请求到达服务端后，从可信会话或经校验的令牌中提取身份，不信任请求体中的角色字段。

  3. 3

    服务端在业务处理前执行功能级授权（能否调用此接口）和对象级授权（能否操作此资源）。

  4. 4

    默认拒绝：未显式授权的操作一律禁止，新接口必须声明所需权限。

  5. 5

    使用 BaaS 时，授权落在数据库规则（如 RLS、Security Rules）上，同样由服务端强制执行。

🔤 03 · 术语
默认拒绝 (Deny by Default)
除非明确允许，否则拒绝所有访问。
功能级授权 (Function-Level)
判断用户能否调用某个接口或功能。
对象级授权 (Object-Level)
判断用户能否访问某个具体数据对象。
批量赋值 (Mass Assignment)
把请求体字段直接写入模型，可能改到 role 等敏感字段。
策略即代码 (Policy as Code)
用 OPA 等引擎以代码形式集中管理授权规则。
💻 04 · 代码
服务端集中授权与字段白名单typescript
type User = { id: string; role: "admin" | "member" };

// 集中的授权函数：每个动作的规则写在一处，便于测试
function can(user: User, action: string, post?: { authorId: string }) {
  switch (action) {
    case "post:create": return true;
    case "post:update": return user.role === "admin" || post?.authorId === user.id;
    case "user:setRole": return user.role === "admin";
    default: return false;                       // 默认拒绝
  }
}

app.patch("/posts/:id", requireLogin, async (req, res) => {
  const post = await db.post.findUnique({ where: { id: req.params.id } });
  if (!post) return res.sendStatus(404);
  if (!can(req.user, "post:update", post)) return res.sendStatus(403);

  // 字段白名单，防止批量赋值改到 authorId 等字段
  const { title, body } = req.body;
  await db.post.update({ where: { id: post.id }, data: { title, body } });
  res.sendStatus(204);
});

身份来自 requireLogin 写入的 req.user；授权规则集中且默认拒绝，更新只取白名单字段。

📊 05 · 参数对比

前端控制 vs 服务端控制

位置作用能否作为安全边界
前端隐藏按钮/路由守卫改善体验不能
API 网关认证、限流、粗粒度规则部分
服务端业务层功能级与对象级授权能
数据库 RLS/规则数据层兜底能
⚖️ 06 · 方案取舍

代码中手写授权判断

优点直观、灵活

代价分散易漏

适用小型应用

集中授权模块或策略引擎

优点一致、可审计、易测试

代价引入抽象与依赖

适用多角色、多团队系统

数据库层授权（RLS）

优点所有访问路径统一受控

代价复杂规则难表达

适用前端直连 BaaS 数据库

🕳️ 07 · 常见坑

  • ✗只在前端判断 isAdmin 后显示管理功能

    ✓管理接口在服务端校验角色

  • ✗从请求体或 JWT 未校验部分读取 role

    ✓角色来自服务端存储或经签名校验的令牌

  • ✗把整个 req.body 传给 ORM 更新

    ✓显式挑选允许修改的字段

  • ✗Supabase 表未启用 RLS 就用 anon key 访问

    ✓所有暴露的表启用 RLS 并编写策略

☑️ 08 · 检查清单
🎤 09 · 面试追问
为什么不能依赖前端做权限控制？

前端代码运行在用户设备上，用户可以修改 JavaScript、用开发者工具改变量，或绕过界面直接用 curl、Postman 调用 API。前端控制只决定看到什么，服务端才决定能做什么，所以所有授权必须在服务端执行。

什么是批量赋值漏洞？

框架把请求体字段自动映射到数据模型并保存时，攻击者可以额外提交 role、isAdmin、ownerId 等本不应由用户修改的字段，从而提权或篡改归属。防御方法是使用字段白名单或专门的输入 DTO。

前端直连 Supabase/Firebase 如何做授权？

此时没有自建后端，数据库规则就是服务端授权：Supabase 需对表启用行级安全并编写基于 auth.uid() 的策略，Firebase 需编写 Security Rules。公开的 anon/客户端密钥不是秘密，安全完全依赖这些规则。
