内容安全策略 (CSP)

Content Security Policy

🧸 回到小白版

📐 01 · 定义

内容安全策略（Content Security Policy, CSP）是服务器通过响应头告诉浏览器页面允许从哪些来源加载和执行脚本、样式、图片、连接与框架的声明式安全机制，由 W3C 规范定义。它是防御跨站脚本（XSS）与数据注入的纵深防线：即使攻击者注入了脚本，浏览器也会拒绝执行未授权的代码。

⚙️ 02 · 原理
  1. 1

    服务器下发 Content-Security-Policy 头，由若干指令组成，如 script-src、style-src、connect-src。

  2. 2

    浏览器加载每个资源或执行脚本前，按对应指令检查来源，不匹配即阻止并在控制台报错。

  3. 3

    严格 CSP 推荐用每次请求随机生成的 nonce 或脚本哈希授权内联脚本，而非域名白名单。

  4. 4

    'strict-dynamic' 允许已授权脚本动态加载的子脚本，简化第三方库的配置。

  5. 5

    先用 Content-Security-Policy-Report-Only 只报告不拦截，收集违规后再切换为强制模式。

🔤 03 · 术语
nonce
每次响应随机生成的值，只有带匹配 nonce 的脚本才能执行。
'strict-dynamic'
信任由已授权脚本加载的脚本，忽略域名白名单。
'unsafe-inline'
允许所有内联脚本，基本抵消 CSP 防 XSS 的作用。
Report-Only 模式
只上报违规不拦截，用于灰度上线。
Trusted Types
CSP 扩展，限制危险 DOM API 只接受经过处理的值。
💻 04 · 代码
Express 下发 nonce CSPjavascript
const express = require("express");
const crypto = require("crypto");
const app = express();

app.use((req, res, next) => {
  // 每个响应生成新的随机 nonce
  res.locals.nonce = crypto.randomBytes(16).toString("base64");
  res.setHeader("Content-Security-Policy", [
    `script-src 'nonce-${res.locals.nonce}' 'strict-dynamic'`,
    "object-src 'none'",
    "base-uri 'none'",
    "frame-ancestors 'none'",
  ].join("; "));
  next();
});

app.get("/", (req, res) => {
  // 只有带正确 nonce 的脚本能执行，注入的 <script> 会被拦截
  res.send(`<!doctype html>
<script nonce="${res.locals.nonce}" src="/app.js"></script>
<script nonce="${res.locals.nonce}">console.log("ok")</script>`);
});

app.listen(3000);

nonce 每次随机且不可预测；strict-dynamic 让 app.js 动态加载的脚本也能运行。

📊 05 · 参数对比

关键指令

指令控制什么建议值
script-src脚本来源与内联脚本nonce/哈希 + 'strict-dynamic'
object-src插件内容（object/embed）'none'
base-uri<base> 标签可设的地址'none' 或 'self'
connect-srcfetch/XHR/WebSocket 目标按需列出 API 域名
frame-ancestors谁可以嵌入本页'none' 或 'self'
⚖️ 06 · 方案取舍

域名白名单 CSP

优点直观，易理解

代价白名单域上的 JSONP/旧库常可绕过

适用不推荐单独使用

nonce + strict-dynamic

优点防护强，维护成本较低

代价需服务端渲染时注入 nonce

适用服务端渲染的应用

哈希 CSP

优点适合静态页面，无需服务端

代价脚本内容变更需更新哈希

适用静态站点、内联脚本固定

🕳️ 07 · 常见坑

  • ✗为了让页面正常加上 'unsafe-inline'

    ✓改用 nonce 或哈希；内联事件处理器重构为 addEventListener

  • ✗nonce 固定写死或可预测

    ✓每个响应用安全随机数生成新 nonce

  • ✗直接上线强制模式，页面大面积失效

    ✓先 Report-Only 收集违规报告，修复后再强制

  • ✗CDN 缓存了带 nonce 的 HTML

    ✓带 nonce 的页面不可被共享缓存，或改用哈希方案

🎤 09 · 面试追问
为什么域名白名单式 CSP 容易被绕过？

白名单中的大型 CDN 或第三方域常托管 JSONP 接口或旧版 AngularJS 等可被利用的脚本，攻击者借助它们执行任意代码。Google 的研究表明大量白名单策略可被绕过，因此推荐 nonce/哈希加 strict-dynamic。

有了 CSP 还需要做输出转义吗？

需要。CSP 是纵深防御，用于在 XSS 已发生时阻止执行；根本防御仍是上下文相关的输出编码、使用安全的模板与 API。CSP 配置失误或浏览器差异时，转义仍是第一道防线。

AI 生成的前端代码常与 CSP 冲突在哪？

常见是内联 onclick 处理器、内联 style、eval 或 new Function、动态插入 script。应要求生成代码使用 addEventListener、外部或带 nonce 的脚本，并在 Report-Only 模式下验证。
