📐 01 · 定义

OpenTelemetry（OTel）是 CNCF 的开源可观测性标准与工具集，定义了生成、采集和导出遥测数据（链路追踪、指标、日志）的统一 API、SDK、语义约定和 OTLP 传输协议，并提供 Collector 作为采集与处理管道。它让埋点与后端解耦，避免被单一监控厂商锁定。

⚙️ 02 · 原理
  1. 1

    埋点：通过各语言 SDK 的自动插桩或手动 API 生成 span、指标和日志记录。

  2. 2

    上下文传播：用 W3C traceparent 等请求头在服务间传递 trace ID，把调用串成链路。

  3. 3

    SDK 处理：在进程内完成采样、批量缓冲，并补充服务名等资源属性后导出。

  4. 4

    Collector：接收 OTLP 等多种格式的数据，经过滤、脱敏、批处理后转发到多个后端。

  5. 5

    后端分析：Jaeger、Prometheus 或商业平台存储并展示数据，可随时切换后端。

🔤 03 · 术语
OTLP
OpenTelemetry 的原生传输协议，支持 gRPC 与 HTTP。
Collector
独立运行的遥测管道，由接收器、处理器、导出器组成。
语义约定 (Semantic Conventions)
统一的属性命名规范，如 http.request.method。
资源 (Resource)
描述遥测来源的属性，如 service.name、部署环境。
采样 (Sampling)
只保留部分链路以控制成本，分头部采样与尾部采样。
上下文传播 (Context Propagation)
跨进程传递追踪上下文，使调用能串联成链路。
💻 04 · 代码
Collector 基础管道yaml
receivers:
  otlp:
    protocols:
      grpc: {endpoint: 0.0.0.0:4317}
      http: {endpoint: 0.0.0.0:4318}

processors:
  memory_limiter:            # 防止 Collector 自身内存溢出，放在最前面
    check_interval: 1s
    limit_mib: 1024
  batch: {}                  # 批量发送，降低导出开销

exporters:
  otlphttp:
    endpoint: https://otel-backend.example.com
  debug: {}                  # 调试时打印到 Collector 日志

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, batch]
      exporters: [otlphttp]
    metrics:
      receivers: [otlp]
      processors: [memory_limiter, batch]
      exporters: [otlphttp, debug]

应用统一发到 Collector，后端变化只需改导出器；处理器顺序会影响行为。

OTel 组件分工

组件职责运行位置
API定义埋点接口，库作者依赖它应用进程内
SDK实现采样、处理、导出应用进程内
自动插桩无需改代码为常见框架埋点应用进程内/代理

应用直连后端

优点部署简单，少一跳

适用小规模、单一后端

🕳️ 07 · 常见坑

  • ✗各服务 service.name 不规范，链路和指标无法归属

    ✓统一设置资源属性，包括服务名、版本和环境

  • ✗跨服务调用未传播上下文，链路断成多段

    ✓确保 HTTP/消息客户端插桩并传递 traceparent 头

  • ✗全量采集链路，存储成本失控

    ✓按需配置头部或尾部采样，保留错误与慢请求

  • ✗Collector 未配 memory_limiter，流量突增时 OOM

    ✓启用 memory_limiter 并为 Collector 设置资源限制

🎤 09 · 面试追问
OpenTelemetry 解决了什么问题？

过去每个监控厂商有自己的 SDK 和协议，换后端要重写埋点。OTel 统一了 API、数据模型和传输协议，埋点只做一次，可导出到任意兼容后端；同时统一三类信号的关联，如从指标跳到链路再到日志。

头部采样和尾部采样有何区别？

头部采样在链路开始时就决定是否保留，开销小但可能丢掉之后才出错的链路；尾部采样在 Collector 等待整条链路结束后再按错误、延迟等条件决定，能保留有价值的链路，但需缓存数据、资源消耗更大。

为什么推荐使用 Collector？

它把遥测处理从应用剥离：集中做批处理、重试、脱敏、采样和多后端路由；应用只需发 OTLP 到本地，换后端或调整策略不必重新发布应用；也能接收 Prometheus、Jaeger 等旧格式便于迁移。
