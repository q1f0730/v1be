技术债

Technical Debt

📐 01 · 定义

技术债（Technical Debt）由 Ward Cunningham 提出，比喻为了短期交付而采取的次优设计或实现：它像借款一样换来当下速度，但之后每次修改都要支付「利息」（额外成本），直到通过重构「还本」。它属于工程管理层概念，AI 生成代码速度快、一致性差，更容易在不知不觉中累积技术债。

⚙️ 02 · 原理
  1. 1

    产生：赶工期的捷径、缺少测试、复制粘贴、过时依赖、设计随需求漂移而不再匹配。

  2. 2

    计息：后续改动需理解和绕开这些问题，表现为开发变慢、缺陷增多、新人上手难。

  3. 3

    识别：变更频繁且复杂度高的热点文件、反复出问题的模块、静态分析告警与过期依赖。

  4. 4

    管理：把债务显式登记为待办，评估「利息」与修复成本，排入迭代持续偿还。

  5. 5

    预防：代码评审、测试、规则文件与自动化检查，减少无意识的新债。

🔤 03 · 术语
技术债象限 (Debt Quadrant)
Fowler 按鲁莽/审慎 × 有意/无意把技术债分为四类。
重构 (Refactoring)
不改变外部行为地改善代码内部结构。
代码异味 (Code Smell)
暗示深层设计问题的表面特征，如超长函数、重复代码。
热点分析 (Hotspot Analysis)
结合修改频率与复杂度定位最值得偿还的代码。
童子军规则 (Boy Scout Rule)
每次离开时让代码比来时更整洁一点。
💻 04 · 代码
定位技术债热点bash
# 1) 近半年改动最频繁的文件（改得多 = 利息高的候选）
git log --since="6 months ago" --format= --name-only \
  | grep -v '^$' | sort | uniq -c | sort -rn | head -15

# 2) 代码里自己标记的债务
grep -rnE "TODO|FIXME|HACK" src/ | wc -l

# 3) 复杂度检查（Python：ruff 的 McCabe 规则 C901）
ruff check src/ --select C901

# 4) 过期依赖
npm outdated          # Node 项目
pip list --outdated   # Python 项目

# 5) 把结果交给 Agent 做优先级排序
# claude -p "根据以上热点与告警，列出前 5 项技术债及修复方案"

高修改频率 × 高复杂度的交集，通常是投入产出比最高的偿还对象。

📊 05 · 参数对比

技术债类型与利息

类型典型表现利息体现
代码债重复代码、超长函数改一处漏一处
测试债关键路径无测试不敢改、回归靠人肉
架构债边界混乱、循环依赖小需求牵动大范围
依赖债长期不升级的库安全漏洞、升级跨度大
文档债无 README、无决策记录新人与 Agent 上手慢
⚖️ 06 · 方案取舍

有意举债快速上线

优点抢时间窗口、验证需求

代价需计划偿还，否则利息累积

适用MVP、市场窗口期（审慎有意型）

持续小步偿还

优点风险低，不打断交付

代价需团队纪律与时间预留

适用长期维护的产品

大规模重写

优点可彻底更换架构

代价风险高、周期长、易重蹈覆辙

适用原系统已无法演进

🕳️ 07 · 常见坑

  • ✗债务只存在口头，从不登记

    ✓建技术债清单，记录影响、利息与修复估算

  • ✗把所有不喜欢的代码都叫技术债

    ✓以对交付速度与缺陷的实际影响来衡量

  • ✗让 AI 生成大量代码而不评审、不补测试

    ✓要求 Agent 同步写测试，评审重复与偏离约定处

  • ✗一次性大重写替代渐进重构

    ✓采用绞杀者模式逐步替换，保持系统可用

🎤 09 · 面试追问
如何向非技术管理者解释偿还技术债的价值？

用业务指标说话：功能交付周期变长、线上缺陷与故障增多、新人上手时间延长。把具体债务与这些指标关联，给出修复成本与预期收益，以投资回报而非代码洁癖来论证。

怎样决定先还哪笔债？

看利息与成本：优先处理修改频繁、缺陷集中、阻碍近期路线图的区域；结合修改频率与复杂度的热点分析；先为其补测试，再小步重构，避免碰很少修改的稳定旧代码。

AI 编码为什么容易加速技术债？

生成速度快、评审跟不上；模型倾向复制已有模式甚至错误模式；对项目约定不熟导致风格和抽象不一致；容易加功能而少删代码。需规则文件、测试与严格评审来约束。
