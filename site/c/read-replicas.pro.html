只读副本

Read Replicas

📐 01 · 定义

只读副本（Read Replica）是从主库持续复制数据、只对外提供读查询的数据库实例。它通过把读流量分摊出去来扩展读能力，也可用于报表隔离、跨地域就近读取和故障切换候选。它不能扩展写能力，且通常为异步复制，读到的数据可能略旧。

⚙️ 02 · 原理
  1. 1

    主库把变更写入日志（PostgreSQL 的 WAL、MySQL 的 binlog），并持续发送给副本。

  2. 2

    副本接收并重放这些日志，保持与主库数据近似一致，且拒绝写入。

  3. 3

    应用或代理层按语句类型路由：写请求和强一致读走主库，其余读走副本。

  4. 4

    多个副本可放在负载均衡后，按健康状态与延迟剔除异常节点。

  5. 5

    主库故障时，可把某个副本提升（promote）为新主库，其余副本改为跟随它。

🔤 03 · 术语
流复制 (Streaming Replication)
PostgreSQL 通过网络实时传输 WAL 的复制方式。
异步复制 (Asynchronous Replication)
主库提交不等待副本确认，延迟低但可能丢数据。
读写分离 (Read/Write Splitting)
按读写类型把请求路由到不同实例。
提升 (Promote)
把副本转为可写的主库。
热备 (Hot Standby)
处于恢复状态但可接受只读查询的备库。
💻 04 · 代码
应用层读写分离python
from sqlalchemy import create_engine, text

primary = create_engine("postgresql+psycopg://app@db-primary:5432/app")
replica = create_engine("postgresql+psycopg://app@db-replica:5432/app")

def engine_for(readonly: bool, need_fresh: bool = False):
    # 写操作、以及刚写完马上要读的场景，一律走主库
    if not readonly or need_fresh:
        return primary
    return replica

# 列表页：容忍少量延迟，走副本
with engine_for(readonly=True).connect() as conn:
    posts = conn.execute(text("SELECT id, title FROM posts ORDER BY id DESC LIMIT 20")).all()

# 用户刚提交订单后查看详情：需要最新数据，走主库
with engine_for(readonly=True, need_fresh=True).connect() as conn:
    order = conn.execute(text("SELECT * FROM orders WHERE id = :id"), {"id": 1001}).one()

# 确认连接到的是副本（PostgreSQL 处于恢复模式即为副本）
with replica.connect() as conn:
    print(conn.execute(text("SELECT pg_is_in_recovery()")).scalar())  # True

按一致性需求而非仅按 SELECT 路由；刚写完就读的场景回主库。

📊 05 · 参数对比

副本的用途与注意点

用途收益注意点
分摊在线读流量提升读吞吐需处理复制延迟
报表/分析查询不影响主库长查询可能与复制冲突
跨地域就近读降低远端用户延迟跨区流量费与更大延迟
故障切换候选缩短恢复时间异步副本可能缺最新事务
⚖️ 06 · 方案取舍

应用层路由

优点可按业务语义精确控制

代价代码侵入，易漏判

适用一致性要求各异的业务

代理层路由（ProxySQL 等）

优点应用无感知

代价无法理解业务一致性需求

适用存量系统快速接入

加缓存替代副本

优点延迟更低、成本更低

代价失效逻辑复杂

适用热点读集中在少数数据

🕳️ 07 · 常见坑

  • ✗所有 SELECT 一律走副本，用户刚改的资料显示旧值

    ✓写后短时间内或关键读回主库

  • ✗副本规格比主库小，延迟持续扩大

    ✓副本规格不低于主库，监控重放速度

  • ✗把副本当备份

    ✓误删也会被复制过去，仍需独立备份与 PITR

  • ✗事务内混用主库和副本连接

    ✓一个事务内的读写使用同一连接

🎤 09 · 面试追问
只读副本能解决写入瓶颈吗？

不能。每个副本都要重放主库的全部写入，写压力并未分摊。写瓶颈需靠优化写路径、批量化、垂直扩容、分区或分片。副本只扩展读和隔离分析负载。

如何保证“写后读”一致？

常见方法：写入后一段时间内该用户的读走主库；记录写入时主库日志位置（如 LSN），读时选择已重放到该位置的副本或等待；关键页面直接读主库。按业务重要性选择。

副本上的长查询会带来什么问题？

PostgreSQL 热备上，重放需要清理的行版本可能被长查询依赖，产生冲突：要么取消查询，要么延迟重放（max_standby_streaming_delay）。开启 hot_standby_feedback 可减少取消，但会让主库膨胀。
