依赖版本锁文件

Lockfiles

📐 01 · 定义

依赖锁文件（Lockfile）记录依赖树中每个包的精确版本、来源与完整性哈希，如 package-lock.json、pnpm-lock.yaml、poetry.lock、uv.lock、Cargo.lock。它属于构建与供应链层，保证不同机器、CI 与生产安装出完全一致的依赖，是可复现构建与防篡改的基础。

⚙️ 02 · 原理
  1. 1

    清单文件（如 package.json）只写版本范围，例如 ^1.2.0，允许匹配多个版本。

  2. 2

    包管理器解析范围与传递依赖，选出一组确定版本，连同来源 URL 和哈希写入锁文件。

  3. 3

    后续安装优先按锁文件还原，不再重新解析，因此新发布的版本不会被意外引入。

  4. 4

    安装时校验下载内容的哈希（如 npm 的 integrity 字段），不匹配即报错。

  5. 5

    升级依赖时显式执行 update 命令重新解析，锁文件变化随代码一起提交与审查。

🔤 03 · 术语
语义化版本 (SemVer)
主.次.修订版本号约定，^ 与 ~ 表示允许的升级范围。
传递依赖 (Transitive Dependency)
依赖的依赖，通常占依赖树的大多数。
完整性哈希 (Integrity Hash)
包内容的摘要，用于校验未被篡改。
可复现构建 (Reproducible Build)
相同输入在任何环境产生相同产物。
冻结安装 (Frozen Install)
锁文件与清单不一致时直接失败，不改写锁文件。
💻 04 · 代码
CI 中严格按锁文件安装bash
# Node.js：npm ci 只按 package-lock.json 安装，
# 与 package.json 不一致时报错，且会先删除 node_modules
npm ci

# pnpm / Yarn（v2+）的等价写法
pnpm install --frozen-lockfile
yarn install --immutable

# Python (uv)：锁文件过期则失败
uv sync --locked

# Python (pip)：要求每个包都有哈希
pip install --require-hashes -r requirements.txt

# 本地有意升级某个依赖，再提交锁文件的 diff
npm install lodash@latest
git add package.json package-lock.json
git commit -m "chore(deps): bump lodash"

CI 与生产用冻结模式安装，锁文件只在有意升级时变化并经过审查。

⚖️ 06 · 方案取舍

提交锁文件

优点环境一致，可复现，可审计

代价锁文件冲突与 diff 较大

适用应用、服务，几乎总是

库项目不依赖锁文件发布

优点让使用方自行解析兼容版本

代价库自身 CI 结果可能不稳定

适用发布到注册表的库（锁文件仍可用于开发）

自动依赖升级 PR

优点持续获得安全修复

代价PR 噪声，需要测试兜底

适用有可靠 CI 的项目

🎤 09 · 面试追问
有了 ^ 版本范围为什么还需要锁文件？

范围允许匹配新发布的版本，不同时间安装会得到不同依赖树，传递依赖更不可控。锁文件固定解析结果，保证可复现，并让每次依赖变化都显式出现在代码审查里。

锁文件如何防范供应链攻击？

完整性哈希能发现已锁定版本被替换或下载被篡改；但若锁定的版本本身是恶意发布就无能为力。还需结合依赖审查、漏洞与恶意包扫描、延迟采用新版本和最小化依赖。

npm install 和 npm ci 的区别？

npm install 会按范围解析并可能更新锁文件；npm ci 要求锁文件存在且与 package.json 一致，删除 node_modules 后严格按锁文件安装，不写回锁文件，适合 CI 与生产构建。
