Protobuf二进制序列化

Protocol Buffers

📐 01 · 定义

Protocol Buffers（Protobuf）是 Google 开发的语言无关、平台无关的结构化数据序列化格式。开发者在 .proto 文件中定义消息结构，编译器生成各语言代码。它以字段编号而非字段名编码，体积小、解析快，并有明确的前后向兼容规则，是 gRPC 的默认载荷格式。

⚙️ 02 · 原理
  1. 1

    在 .proto 中为每个字段指定类型和唯一的字段编号。

  2. 2

    protoc 生成各语言的消息类，提供序列化与反序列化方法。

  3. 3

    编码时每个字段写为“标签 + 值”：标签由字段编号和线路类型组成，整数用变长编码。

  4. 4

    未赋值的默认值字段通常不写出；解析时遇到不认识的编号会作为未知字段保留或跳过。

  5. 5

    因为只认编号不认名字，改字段名不影响兼容，改编号或类型则会破坏兼容。

🔤 03 · 术语
字段编号 (Field Number)
字段在二进制中的唯一标识，一旦使用不可更改。
线路类型 (Wire Type)
决定如何读取值：VARINT、I64、LEN、I32 等。
Varint
变长整数编码，小数值占用更少字节。
reserved
声明已废弃的编号或名称，防止被复用。
字段存在性 (Field Presence)
能否区分“未设置”和“设为默认值”。
未知字段 (Unknown Fields)
旧代码不认识的新字段，解析时保留不报错。
💻 04 · 代码
.proto 定义与演进规则text
// user.proto
syntax = "proto3";
package demo.v1;

message User {
  int64  id    = 1;              // 1–15 号字段的标签只占 1 字节，留给高频字段
  string name  = 2;
  optional string nickname = 3;  // optional 可区分“未设置”与空字符串
  repeated string tags = 4;
  Status status = 5;
  reserved 6;                    // 已删除字段的编号，永不复用
  reserved "email";              // 也保留旧字段名
}

enum Status {
  STATUS_UNSPECIFIED = 0;        // proto3 枚举第一个值必须是 0，作为默认值
  STATUS_ACTIVE = 1;
  STATUS_BANNED = 2;
}

// 编码示例：字段 1 为 varint 150 → 字节 08 96 01
//   08 = (字段号 1 << 3) | 线路类型 0(VARINT)
// 生成代码：protoc --python_out=. user.proto

编号决定编码与兼容性；删除字段要 reserved，枚举零值作为未指定。

📊 05 · 参数对比

字段变更的兼容性

变更是否兼容说明
新增字段（新编号）兼容旧代码视为未知字段
删除字段并 reserved兼容编号不可再用
修改字段名二进制兼容JSON 映射与生成代码会变
修改编号或不兼容类型不兼容数据会被错误解析
⚖️ 06 · 方案取舍

Protobuf

优点体积小、解析快、强类型契约

代价不可读，需 schema 才能解码

适用服务间通信、大量数据传输

JSON

优点人类可读，浏览器原生

代价体积大，无强制 schema

适用公开 API、调试友好优先

Avro / Thrift

优点Avro 适合数据管道与 schema 演进

代价生态与工具链差异

适用Kafka 等大数据场景

🕳️ 07 · 常见坑

  • ✗删除字段后把编号分配给新字段

    ✓删除时 reserved 编号和名称

  • ✗把 int32 改成 string 等不兼容类型

    ✓新增字段承载新类型，逐步迁移

  • ✗proto3 无法区分“没传”与“传了 0”

    ✓需要区分时用 optional 或包装类型

  • ✗枚举零值赋予业务含义

    ✓零值固定为 UNSPECIFIED，业务值从 1 开始

🎤 09 · 面试追问
Protobuf 为什么比 JSON 小？

不传输字段名，只传一个小整数标签；整数用 varint 变长编码，小数值只占一两个字节；默认值字段通常不写出；无引号、括号等语法字符。代价是必须有 schema 才能解读。

proto3 的字段存在性问题是什么？

早期 proto3 中标量字段无存在性，0、空字符串与未设置无法区分，部分更新语义因此难以表达。现在可用 optional 关键字恢复显式存在性，或使用 google.protobuf 包装类型。

如何在团队里防止破坏性 proto 变更？

在 CI 中用 buf breaking 等工具对比新旧 schema；约定只新增字段、删除必 reserved；包名带版本，重大变更走新版本包；代码评审重点关注编号与类型改动。
