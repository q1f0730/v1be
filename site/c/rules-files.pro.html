规则文件 (AGENTS.md / CLAUDE.md)

Rules Files

📐 01 · 定义

规则文件（Rules Files）是放在仓库中、由 AI 编码工具在会话开始时自动读入的 Markdown 指令文件，如 CLAUDE.md、AGENTS.md、.cursor/rules。它属于上下文工程的“常驻上下文”层，用来固化项目约定、常用命令和禁区，避免每次对话重复交代。

⚙️ 02 · 原理
  1. 1

    工具启动时按约定路径查找规则文件，并把内容注入系统提示或首轮上下文。

  2. 2

    多层级叠加：用户级（如 ~/.claude/CLAUDE.md）、项目根目录、子目录各自生效，越靠近当前文件越具体。

  3. 3

    Claude Code 支持在 CLAUDE.md 中用 @path 导入其他文件；子目录的 CLAUDE.md 在访问该目录文件时按需加载。

  4. 4

    Cursor 的 .cursor/rules/*.mdc 通过 frontmatter 控制始终生效、按 glob 匹配生效或由模型判断引用。

  5. 5

    规则只是提示而非强制约束；需要硬保证的事项应配合 hooks、权限配置、lint 或 CI 落实。

🔤 03 · 术语
AGENTS.md
跨工具的开放约定文件名，Codex、Cursor 等多种编码 Agent 支持读取。
CLAUDE.md
Claude Code 的项目记忆文件，可用 /init 生成初稿。
Glob 作用域 (Glob Scoping)
按文件路径模式决定某条规则何时注入上下文。
Hooks
在工具调用前后执行的脚本，可强制执行规则文件只能建议的事。
常驻上下文 (Persistent Context)
每次会话都会加载的内容，每个 token 都长期占用预算。
💻 04 · 代码
一份精简的 AGENTS.mdtext
# AGENTS.md

## 项目
Next.js 14 App Router + TypeScript + Prisma(PostgreSQL)

## 常用命令
- 安装: pnpm install
- 开发: pnpm dev
- 测试: pnpm test -- --run    # 改完代码必须跑
- 类型检查: pnpm typecheck

## 约定
- 组件放 src/components，一个文件一个组件
- 数据库访问只能经过 src/lib/db.ts
- 新接口必须有 zod 入参校验

## 禁止
- 不要修改 prisma/migrations 下已有文件
- 不要提交 .env*，不要打印密钥

只写 AI 无法从代码推断、又经常出错的信息：命令、边界、禁区。版本号以项目实际为准。

⚖️ 06 · 方案取舍

单一大规则文件

优点集中好维护

代价常驻 token 多，重点被稀释

适用小项目

按目录或 glob 拆分

优点只在相关时加载

代价规则分散，需约定位置

适用Monorepo 或多技术栈

规则 + hooks/CI 强制

优点关键约束可验证

代价配置成本更高

适用安全、合规相关约束

🕳️ 07 · 常见坑

  • ✗把整份架构文档和代码风格指南都塞进去

    ✓风格交给 linter，长文档放外部用引用，规则文件保持精炼

  • ✗规则写了“不要删数据”就以为安全

    ✓关键禁令用权限设置、hooks 或沙箱实际阻止

  • ✗多个工具各维护一份，内容逐渐矛盾

    ✓以 AGENTS.md 为主，其他文件引用或软链接它

  • ✗规则文件里写了密钥或内网地址

    ✓规则文件会进仓库和模型上下文，敏感信息放环境变量

🎤 09 · 面试追问
规则文件里应该写什么、不写什么？

写模型从代码里推断不出来且常犯错的：构建测试命令、架构边界、禁区、团队特有约定。不写能被 linter/formatter 保证的风格、显而易见的通用常识、经常变化的细节和敏感信息。目标是短而高信号。

为什么规则文件不是可靠的安全控制？

它只是被注入上下文的文本，模型可能遗忘、误解，或被提示注入覆盖。安全约束需要在执行层强制：工具权限白名单、hooks 拦截危险命令、沙箱隔离、CI 检查，规则文件只负责说明意图。

Monorepo 中规则文件怎么组织？

根目录放全局约定和通用命令，各子包放自己的规则文件说明本包的技术栈和测试方式，利用工具的层级加载或 glob 作用域就近生效，避免把所有子项目细节一次性常驻在上下文中。
