CAP定理

CAP Theorem

📐 01 · 定义

CAP 定理指出：分布式数据系统在发生网络分区（P）时，无法同时保证一致性（C，此处指线性一致性）和可用性（A，每个非故障节点都要返回响应），只能二选一。它由 Brewer 提出、Gilbert 与 Lynch 于 2002 年形式化证明，是分析分布式存储取舍的基础框架。

⚙️ 02 · 原理
  1. 1

    前提：网络分区在分布式系统中不可避免，因此 P 不是可选项。

  2. 2

    冲突：分区发生时两侧节点无法通信，却可能各自继续收到读写请求。

  3. 3

    选 C（CP）：少数派一侧拒绝请求或返回错误，保证读到的总是最新值。

  4. 4

    选 A（AP）：两侧都继续服务，可能读到旧值或产生写冲突，分区恢复后再合并。

  5. 5

    无分区时可同时兼顾 C 与 A，此时取舍转为延迟与一致性之间（PACELC）。

🔤 03 · 术语
网络分区 (Network Partition)
节点间消息丢失或无限延迟，集群被分割成互不相通的部分。
线性一致性 (Linearizability)
CAP 中 C 的定义：所有操作看起来按实时顺序原子执行。
CAP 可用性
每个非故障节点收到的请求最终都必须返回非错误响应。
PACELC
分区时在 A 与 C 间选择，否则在延迟 L 与一致性 C 间选择。
多数派 (Majority Quorum)
超过半数节点，CP 系统常以此决定哪一侧继续服务。
💻 04 · 代码
MongoDB 的一致性旋钮javascript
// mongosh：同一数据库可按操作选择偏 C 还是偏 A

// 偏一致：写入需多数节点确认，读线性一致（只能读主）
db.accounts.updateOne(
  { _id: 42 }, { $inc: { balance: -100 } },
  { writeConcern: { w: "majority", wtimeout: 5000 } }
);
db.accounts.find({ _id: 42 })
  .readConcern("linearizable")
  .maxTimeMS(5000);

// 偏可用/低延迟：从最近的节点读，可能读到旧数据
db.products.find({ category: "book" })
  .readPref("nearest")
  .readConcern("local");

CAP 不是整库的标签，很多系统允许按操作在一致性与可用性之间调节。

📊 05 · 参数对比

典型系统的默认倾向

系统倾向说明
etcd / ZooKeeperCP少数派分区不可写，保证一致
Cassandra / DynamoDB（默认读）AP可调一致性级别，默认偏可用
MongoDB（多数写+多数读）偏 CP主节点在少数派时会降级
单机 PostgreSQL不适用非分布式，不涉及分区取舍
⚖️ 06 · 方案取舍

CP 设计

优点数据始终正确，推理简单

代价分区时部分请求失败

适用余额、库存、配置与锁

AP 设计

优点始终可写可读，延迟低

代价需处理旧数据和冲突合并

适用购物车、社交动态、计数

按操作可调

优点关键路径强一致，其余高可用

代价开发者需理解每个选项含义

适用业务混合多种一致性需求

🕳️ 07 · 常见坑

  • ✗把系统简单标为 CA，忽视分区必然发生

    ✓分布式系统必须设计分区行为，CA 只适用于单机

  • ✗把 CAP 的 C 与 ACID 的 C 混为一谈

    ✓CAP 的 C 指线性一致性，ACID 的 C 指满足约束

  • ✗以为选了 AP 就不会有一致性问题需要处理

    ✓为冲突设计合并策略，如版本向量、CRDT 或业务规则

🎤 09 · 面试追问
为什么说 CAP 中 P 不能放弃？

跨机器通信总可能丢包、延迟或断网，分区是会发生的事实而非可选特性。系统真正的选择只是分区发生时牺牲一致性还是可用性；声称 CA 的分布式系统，实际是在分区时未定义行为。

CAP 有哪些常被批评的局限？

定义很窄：C 仅指线性一致性，A 要求所有非故障节点响应；只讨论分区时的情况，忽略了正常运行下的延迟取舍；现实系统多是部分可用、可调一致性的光谱。PACELC 等模型对此做了补充。

设计库存系统你会选 CP 还是 AP？

扣减库存需要防超卖，核心扣减走 CP（单主或共识存储，分区时拒绝写入）；商品浏览展示的库存数可用 AP 缓存，允许短暂不准。即按操作区分，而不是整个系统一刀切。
