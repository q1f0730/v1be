数据库范式化

Normalization

📐 01 · 定义

范式化（Normalization）是关系数据库的建模方法：依据函数依赖把数据拆分到多个表，使每个事实只存储一次，以消除冗余带来的更新、插入、删除异常。常用范式依次为 1NF、2NF、3NF 和 BCNF，OLTP 系统通常以 3NF 为设计基线。

⚙️ 02 · 原理
  1. 1

    识别实体和属性，找出函数依赖：哪些属性由哪些属性唯一决定。

  2. 2

    1NF：每个字段只存原子值，不在一列里塞列表或重复列组。

  3. 3

    2NF：在 1NF 基础上，非主属性必须依赖整个复合主键，而非其中一部分。

  4. 4

    3NF：非主属性不能传递依赖于主键（如 订单→客户→客户城市），应拆到客户表。

  5. 5

    拆分后通过外键关联，查询时用 JOIN 组合，约束保证引用完整性。

🔤 03 · 术语
函数依赖 (Functional Dependency)
A 的值确定则 B 的值唯一确定，记作 A→B。
候选键 (Candidate Key)
能唯一标识一行的最小属性集合。
传递依赖 (Transitive Dependency)
A→B 且 B→C，C 间接依赖 A。
更新异常 (Update Anomaly)
同一事实存多处，只改一处导致不一致。
BCNF
每个决定因素都是候选键，比 3NF 更严格。
💻 04 · 代码
从宽表拆到 3NFsql
-- 反例：客户信息随每个订单重复存储
-- orders_flat(order_id, customer_email, customer_name, customer_city,
--             product_sku, product_name, unit_price, qty)

-- 拆分后：每个事实只存一次
CREATE TABLE customers (
  id    bigint PRIMARY KEY,
  email text UNIQUE NOT NULL,
  name  text NOT NULL,
  city  text
);
CREATE TABLE products (
  sku   text PRIMARY KEY,
  name  text NOT NULL,
  price numeric(10,2) NOT NULL          -- 当前标价
);
CREATE TABLE orders (
  id          bigint PRIMARY KEY,
  customer_id bigint NOT NULL REFERENCES customers(id),
  created_at  timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE order_items (
  order_id   bigint REFERENCES orders(id),
  sku        text REFERENCES products(sku),
  qty        int NOT NULL CHECK (qty > 0),
  unit_price numeric(10,2) NOT NULL,    -- 下单时成交价，是独立事实
  PRIMARY KEY (order_id, sku)
);

客户改城市只改一行；成交价属于订单明细的事实，保留在明细表并非冗余。

⚖️ 06 · 方案取舍

严格 3NF

优点写入一致、无更新异常

代价查询需多表 JOIN

适用OLTP 核心业务表

适度反范式

优点读路径快、查询简单

代价需同步冗余，可能不一致

适用读远多于写的热点查询

JSON 列存半结构化

优点模式灵活

代价约束弱，难做引用完整性

适用属性多变、少被关联查询

🕳️ 07 · 常见坑

  • ✗把订单成交价也规范化成引用商品当前价

    ✓区分“当前值”和“历史事实”，历史事实应快照

  • ✗逗号分隔字符串存多个标签

    ✓建关联表，支持索引与约束

  • ✗为范式而范式，拆出大量一对一小表

    ✓按访问模式与依赖关系合理合并

  • ✗拆表后外键列不建索引

    ✓为外键列建索引，保证 JOIN 与删除性能

🎤 09 · 面试追问
3NF 和 BCNF 的区别？

3NF 允许“非候选键决定主属性”的依赖存在，BCNF 不允许，要求每个非平凡函数依赖的左边都是超键。实践中多数 3NF 设计已满足 BCNF，差异只在存在多个重叠候选键时出现。

订单表里存商品名算违反范式吗？

取决于语义。如果它代表“下单时的商品名”，是订单的历史事实，商品改名不应影响旧订单，存下来是正确建模；如果只是为了少一次 JOIN 而复制当前名称，就是反范式冗余，需要同步机制。

让 AI 生成数据库表结构时要检查什么？

看是否有重复存储的属性和列表型字段；外键与唯一约束是否齐全；历史数据是否被错误引用为当前值；索引是否覆盖外键和常用查询；命名是否一致。AI 常给出能跑但冗余的宽表。
