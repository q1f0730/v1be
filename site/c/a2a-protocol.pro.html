智能体互联协议 (A2A)

Agent2Agent Protocol

📐 01 · 定义

A2A（Agent2Agent）是 Google 于 2025 年发起、后交由 Linux 基金会托管的开放协议，规定不同厂商的 Agent 如何发现能力、委派任务、交换消息与产物。它属于应用层，基于 HTTP(S) 上的 JSON-RPC 2.0，支持 SSE 流式与 Webhook 推送。MCP 连接 Agent 与工具，A2A 连接 Agent 与 Agent。

⚙️ 02 · 原理
  1. 1

    服务方发布 Agent Card（JSON），声明端点、技能、输入输出模态和认证方式，放在约定的 well-known 路径（文件名以规范版本为准）。

  2. 2

    客户端 Agent 读取 Agent Card 选择合适的远程 Agent，并按其声明的方案（如 OAuth 2.0、API Key）完成认证。

  3. 3

    客户端发送 message/send 或 message/stream 请求，消息由多个 Part 组成（文本、文件、结构化数据）。

  4. 4

    服务端创建 Task 并维护生命周期状态，如 submitted、working、input-required、completed、failed、canceled。

  5. 5

    长任务可通过 SSE 流式推送状态更新，或通过客户端注册的推送通知 Webhook 异步回调；结果以 Artifact 形式返回。

  6. 6

    远程 Agent 对客户端是不透明的：只暴露能力与结果，不暴露内部提示词、工具或记忆。

🔤 03 · 术语
Agent Card
描述 Agent 身份、端点、技能和认证要求的 JSON 文档，用于能力发现。
任务 (Task)
A2A 中有状态的工作单元，带 ID 与生命周期状态，可被查询或取消。
产物 (Artifact)
任务产出的结果，如文档、图片或结构化数据，由一个或多个 Part 组成。
Part
消息或产物中的内容片段，常见类型为文本、文件和结构化数据。
不透明执行 (Opaque Execution)
协作双方不共享内部状态与工具，只通过协议约定的消息交互。
💻 04 · 代码
A2A 发送消息请求http
POST /a2a HTTP/1.1
Host: travel-agent.example.com
Content-Type: application/json
Authorization: Bearer <token>

{
  "jsonrpc": "2.0",
  "id": "req-1",
  "method": "message/send",
  "params": {
    "message": {
      "role": "user",
      "messageId": "msg-001",
      "parts": [
        { "kind": "text", "text": "预订 11 月 5 日上海两晚酒店，预算 800 元/晚" }
      ]
    }
  }
}

JSON-RPC 2.0 调用 message/send；响应会返回 Task（含 id 与 status）或直接返回消息。字段以所用规范版本为准。

📊 05 · 参数对比

MCP 与 A2A 分工

维度MCPA2A
连接对象模型/Agent ↔ 工具与数据源Agent ↔ Agent
交互粒度单次工具调用可多轮、长时间运行的任务
状态调用基本无状态Task 有完整生命周期
对方可见性工具 schema 完全暴露远程 Agent 内部不透明
典型传输stdio 或 Streamable HTTPHTTP + JSON-RPC，SSE / Webhook
⚖️ 06 · 方案取舍

A2A 跨 Agent 委派

优点跨厂商互通，远程 Agent 可独立演进

代价多一跳网络与认证，调试链路更长

适用对方是独立团队或第三方运营的 Agent

把对方包装成 MCP 工具

优点接入简单，现有客户端直接可用

代价难表达多轮交互与长任务状态

适用对方能力是一次请求一次返回

同进程多 Agent 框架

优点延迟低、共享上下文方便

代价绑定单一框架与部署

适用所有 Agent 由同一团队维护

🕳️ 07 · 常见坑

  • ✗把远程 Agent 返回内容直接当可信指令执行

    ✓将其视为不可信输入，敏感动作需本地授权或人工确认

  • ✗Agent Card 声明了技能却不做认证与授权

    ✓按 Card 声明的方案强制认证，并在服务端按调用方做权限校验

  • ✗长任务只用同步请求，超时就丢结果

    ✓使用流式或推送通知，并支持 tasks/get 轮询恢复

  • ✗不处理 input-required 状态，任务卡死

    ✓客户端识别该状态，补充信息或转人工后继续同一 Task

☑️ 08 · 检查清单
🎤 09 · 面试追问
已经有 MCP 了，为什么还需要 A2A？

MCP 把能力建模为工具：调用方掌握全部参数，对方无自主性。A2A 把对方建模为自主 Agent：可多轮澄清、长时间运行、返回多种产物，内部实现不透明。二者常组合：Agent 内部用 MCP 调工具，Agent 之间用 A2A 协作。

A2A 如何支持耗时数小时的任务？

服务端创建有状态 Task 并立即返回 ID；客户端可通过 message/stream 的 SSE 接收增量状态，或注册推送通知 Webhook 断开连接后等回调，还可用 tasks/get 查询。需要用户补充信息时进入 input-required 状态。

跨组织 A2A 协作的主要安全风险？

一是身份与授权：需按 Card 声明的方案认证并按调用方限权；二是内容可信度：远程返回可能携带注入指令，应视为数据；三是数据外泄：委派前做最小化脱敏；四是 Webhook 伪造：校验签名或令牌。
