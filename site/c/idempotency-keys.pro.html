幂等键 (Idempotency Key)

Idempotency Keys

📐 01 · 定义

幂等键（Idempotency Key）是客户端为一次逻辑操作生成的唯一标识，随请求发送；服务端据此识别重试，保证同一操作无论请求几次只产生一次副作用。它属于 API 设计与分布式可靠性层，用于让本不幂等的 POST（支付、下单、发消息）可以安全重试，Stripe 等支付 API 以此为标准做法。

⚙️ 02 · 原理
  1. 1

    客户端在用户发起操作时生成唯一键（通常 UUID v4），首次请求与所有重试都携带同一个键。

  2. 2

    服务端收到请求，先在存储中以「键 + 调用方」原子地占位，若已存在则不再执行业务逻辑。

  3. 3

    首个请求执行业务并把响应状态码与响应体与该键一起持久化。

  4. 4

    后续同键请求：若前一次已完成，直接返回存储的结果；若仍在处理中，返回冲突或让其稍后重试。

  5. 5

    服务端校验同键请求的参数是否一致，不一致报错；键在保留期后过期清理。

🔤 03 · 术语
幂等性 (Idempotency)
同一操作执行一次和多次，对系统状态的影响相同。
Idempotency-Key 头
IETF 草案定义的 HTTP 请求头，用于携带幂等键。
请求指纹 (Request Fingerprint)
请求参数的哈希，用于检测同键不同参数的误用。
至少一次投递 (At-least-once)
消息可能重复送达的投递语义，消费端需幂等。
原子占位 (Atomic Claim)
用唯一约束或 SET NX 保证同一个键只有一个请求获得执行权。
💻 04 · 代码
Redis 实现幂等处理python
import json, redis
r = redis.Redis()

def handle_payment(key: str, payload: dict, charge):
    slot = f"idem:{key}"
    # 原子占位：只有第一个请求能写入，24 小时后过期
    if r.set(slot, json.dumps({"state": "processing"}), nx=True, ex=86400):
        result = charge(payload)  # 真正扣款，只会执行一次
        r.set(slot, json.dumps({"state": "done", "result": result}), ex=86400)
        return 201, result
    saved = json.loads(r.get(slot))
    if saved["state"] == "processing":
        return 409, {"error": "same request in progress"}
    return 200, saved["result"]  # 重复请求：返回首次结果

# 客户端：同一次点击的所有重试使用同一个 key
# headers = {"Idempotency-Key": str(uuid.uuid4())}

SET NX 保证只有一个请求获得执行权；生产中还需处理执行中崩溃与参数一致性校验。

📊 05 · 参数对比

幂等实现方式对比

方式适用场景局限
幂等键 + 结果存储支付、下单等 POST需额外存储与过期策略
业务唯一约束订单号、外部事件 ID只防重复写，不返回原响应
条件更新 / 乐观锁状态机流转、扣库存需要版本或状态字段
天然幂等方法PUT、DELETE 按资源覆盖不适用于创建类操作
⚖️ 06 · 方案取舍

Redis 存幂等记录

优点延迟低、TTL 自动清理

代价与业务数据库非同一事务

适用高并发、可接受极端情况补偿

数据库表存幂等记录

优点可与业务写入同事务，强一致

代价增加数据库写压力

适用资金类操作

只依赖下游幂等（如支付网关）

优点实现最省事

代价自身副作用（发货、通知）仍会重复

适用单一外部调用且下游支持

🕳️ 07 · 常见坑

  • ✗每次重试都生成新的幂等键

    ✓键在用户操作发起时生成并随重试复用，存在客户端状态里

  • ✗先执行业务、后检查键，存在并发窗口

    ✓先原子占位再执行，或用唯一约束保证互斥

  • ✗同键不同参数时静默返回旧结果

    ✓存参数指纹，不一致返回 422 等明确错误

  • ✗执行中进程崩溃，键永远停在 processing

    ✓为处理中状态设较短超时或可恢复机制，允许安全重试

☑️ 08 · 检查清单
🎤 09 · 面试追问
为什么 POST 需要幂等键，而 PUT 通常不需要？

PUT 语义是把资源设为指定状态，重复执行结果相同，天然幂等；POST 常用于创建或触发动作，每次执行都产生新副作用，重试会重复，所以需要显式幂等键。

两个同键请求同时到达怎么办？

必须原子占位：数据库唯一约束或 Redis SET NX。抢到的执行；另一个看到处理中状态，返回 409 或等待后读取结果。否则会出现检查后执行的竞态。

幂等键能实现 exactly-once 吗？

网络层无法保证恰好一次投递，幂等键是在至少一次投递基础上，让副作用只生效一次，即 effectively-once。前提是副作用与幂等记录的写入一致。
