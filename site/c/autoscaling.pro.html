自动弹性扩缩容

Autoscaling

📐 01 · 定义

自动扩缩容（Autoscaling）是按负载指标自动增减计算资源的机制，包括水平扩缩副本、垂直调整单实例资源和扩缩节点。它位于编排与基础设施层，在满足性能目标的同时控制成本。典型实现有 Kubernetes HPA、VPA、Cluster Autoscaler、KEDA 和云伸缩组，难点是指标选择、反应速度与防振荡。

⚙️ 02 · 原理
  1. 1

    控制器周期性采集指标，如 CPU 利用率、每秒请求数、队列长度或自定义指标。

  2. 2

    按目标值计算期望副本数，HPA 的基本公式为当前副本数乘以当前值与目标值之比，向上取整。

  3. 3

    施加最小与最大副本限制，并用稳定窗口和速率策略抑制频繁扩缩。

  4. 4

    新副本需要被调度、拉镜像、启动并通过就绪检查后才真正分担流量。

  5. 5

    节点资源不足时，集群自动扩缩器增加节点；负载下降后按策略回收。

🔤 03 · 术语
HPA (Horizontal Pod Autoscaler)
Kubernetes 中按指标自动调整副本数的控制器。
稳定窗口 (Stabilization Window)
扩缩决策参考的历史时间段，HPA 缩容默认 300 秒。
KEDA
基于事件源（如队列长度）驱动扩缩，可缩到零的 Kubernetes 组件。
集群自动扩缩器 (Cluster Autoscaler)
根据待调度 Pod 和节点利用率增减节点。
振荡 (Flapping)
扩缩容决策频繁来回切换，导致不稳定和浪费。
💻 04 · 代码
HPA autoscaling/v2yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: api }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: api }
  minReplicas: 3              # 下限：保证可用性与跨区分布
  maxReplicas: 30             # 上限：保护下游与预算
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 70 }
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300   # 观察 5 分钟再缩，防抖
      policies:
        - { type: Percent, value: 50, periodSeconds: 60 }
    scaleUp:
      policies:
        - { type: Pods, value: 4, periodSeconds: 60 }

按 CPU 70% 目标扩缩，缩容慢、扩容快；CPU 利用率需要 Pod 设置了 requests。

⚖️ 06 · 方案取舍

响应式扩缩

优点按实际负载，资源利用率高

代价有滞后，突发时来不及

适用负载平滑变化

预测/定时扩缩

优点提前准备容量

代价预测不准时浪费或不足

适用有明显周期规律

缩到零

优点空闲零成本

代价首个请求有冷启动

适用低频任务、事件驱动

🕳️ 07 · 常见坑

  • ✗Pod 未设置 CPU requests，HPA 无法计算利用率。

    ✓为容器设置合理 requests 后再启用按利用率扩缩。

  • ✗最大副本数不设或过大，扩容打爆数据库连接数。

    ✓按下游容量设置上限，配合连接池。

  • ✗应用启动慢，扩容跟不上突发流量。

    ✓优化启动时间，提高最小副本或预测扩容。

  • ✗HPA 与 VPA 同时基于 CPU 调整同一工作负载，互相干扰。

    ✓避免两者使用同一资源指标，或让 VPA 仅给建议。

🎤 09 · 面试追问
HPA 是如何计算目标副本数的？

期望副本数等于当前副本数乘以当前指标值与目标值之比，再向上取整。多个指标取最大值；比值接近 1 时在容忍度内不动作；随后应用最小最大限制和 behavior 中的稳定窗口与速率策略。

为什么扩容要快、缩容要慢？

扩容慢会导致过载和用户受损，代价大；缩容过快可能在负载回升时来不及扩回，造成振荡。因此常让扩容积极，缩容设较长稳定窗口和较小速率。

消息消费者该用什么指标扩缩？

用队列积压量或积压能被处理完的预计时间，比 CPU 更直接。可以用 KEDA 接入 SQS、Kafka 等事件源，按积压扩缩并支持缩到零；同时注意消费者数量不应超过分区数等并行上限。
