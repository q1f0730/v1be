持续集成 / 持续交付 (CI/CD)

CI/CD

📐 01 · 定义

CI/CD 指持续集成（Continuous Integration）与持续交付/持续部署（Continuous Delivery/Deployment）。CI 要求频繁合入主干，每次提交自动构建与测试；持续交付让主干随时可发布，持续部署则自动发布到生产。它是软件交付的流水线层，用自动化缩短反馈周期、降低发布风险。

⚙️ 02 · 原理
  1. 1

    开发者推送代码或发起合并请求（PR），代码托管平台的事件触发流水线运行。

  2. 2

    CI 阶段：拉取代码、安装依赖、静态检查、单元测试、构建制品如容器镜像。

  3. 3

    制品带唯一版本号推送到制品库，后续环境使用同一个制品，不重复构建。

  4. 4

    CD 阶段：部署到测试或预发环境，运行集成测试，再经审批或自动发布到生产。

  5. 5

    生产发布采用滚动、蓝绿或金丝雀策略，监控指标异常时自动或手动回滚。

🔤 03 · 术语
持续交付 (Continuous Delivery)
每次变更都可随时发布，但上线需要人工触发。
持续部署 (Continuous Deployment)
通过所有检查的变更自动发布到生产。
制品 (Artifact)
构建产出的可部署单元，如镜像、安装包。
主干开发 (Trunk-Based Development)
开发者频繁合入主干，分支生命周期很短。
DORA 指标 (DORA Metrics)
部署频率、变更前置时间、变更失败率、恢复时间等交付效能指标。
💻 04 · 代码
GitHub Actions 流水线yaml
# .github/workflows/ci.yml
name: ci
on:
  push: { branches: [main] }
  pull_request:
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci          # 按锁文件安装，结果可复现
      - run: npm run lint
      - run: npm test
  deploy:
    needs: test              # 测试通过才部署
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production  # 可在仓库设置中配置审批
    steps:
      - uses: actions/checkout@v4
      - run: ./scripts/deploy.sh

PR 上只跑检查与测试，合入 main 后才部署；environment 可挂审批与密钥。

📊 05 · 参数对比

三个概念的边界

阶段自动化范围上线方式
持续集成构建与测试不涉及部署
持续交付构建、测试、部署到预发生产需人工触发
持续部署全流程通过检查即自动上线
⚖️ 06 · 方案取舍

持续部署

优点交付最快，批次小风险低

代价需要完善测试和监控回滚

适用测试覆盖好、可快速回滚的服务

持续交付加人工审批

优点上线可控

代价审批可能成为瓶颈

适用受监管或高风险系统

定期批量发布

优点协调简单

代价变更大，出错难定位

适用移动端商店发布等受限场景

🕳️ 07 · 常见坑

  • ✗每个环境重新构建镜像，生产与测试的不是同一份制品。

    ✓构建一次，按版本号在各环境晋级。

  • ✗流水线不稳定，大家习惯重跑直到变绿。

    ✓追踪并修复不稳定测试，必要时隔离。

  • ✗密钥直接写在流水线文件里。

    ✓使用平台密钥管理或 OIDC 联合身份。

  • ✗AI 生成的代码直接合入，跳过评审与测试。

    ✓同样走评审、测试和流水线门禁。

🎤 09 · 面试追问
持续交付和持续部署的区别？

两者都保证主干随时可发布并自动部署到预发。持续交付在生产发布前保留人工决策；持续部署在所有自动检查通过后直接发布生产，没有人工步骤，因此对测试、监控和回滚要求更高。

如何衡量 CI/CD 的效果？

常用 DORA 指标：部署频率、变更前置时间、变更失败率、故障恢复时间。前两者衡量速度，后两者衡量稳定性。好的流水线应同时提升两类指标，而不是以稳定换速度。

为什么强调构建一次、多处部署？

若每个环境重新构建，依赖版本、构建参数可能不同，测试通过的不一定是上线的。用同一个带版本号的制品在环境间晋级，保证测过的就是部署的，也便于回滚到确定版本。
