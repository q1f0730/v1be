金丝雀发布 / 灰度发布

Canary Releases

📐 01 · 定义

金丝雀发布（Canary Release）是先把新版本发布给一小部分流量或用户，对比新旧版本的关键指标，确认无异常后再逐步扩大比例直至全量的渐进式发布策略。它属于发布与变更管理层，用小范围暴露降低坏版本的影响面，常与自动化指标分析配合，异常时自动中止并回滚。

⚙️ 02 · 原理
  1. 1

    部署少量新版本实例，路由层按比例、请求头或用户分组把一部分流量导向新版本。

  2. 2

    收集金丝雀与基线版本的错误率、延迟、业务指标，进行对比分析。

  3. 3

    按预设步骤逐步提高流量比例，例如 5%、25%、50%、100%，每步停留观察。

  4. 4

    任一阶段指标显著劣化，自动或手动中止发布，流量全部切回旧版本。

  5. 5

    放量到 100% 后清理旧版本，并把本次结果和指标记录下来，用于改进后续的判定阈值。

🔤 03 · 术语
基线 (Baseline)
与金丝雀同时运行的旧版本对照组，用于公平比较。
流量权重 (Traffic Weight)
分配给新版本的流量比例。
自动金丝雀分析 (Automated Canary Analysis)
按指标统计比较自动判定发布是否继续。
渐进式交付 (Progressive Delivery)
金丝雀、功能开关等逐步放量的交付方法总称。
服务网格 (Service Mesh)
如 Istio，可按比例精细拆分服务间流量。
💻 04 · 代码
Argo Rollouts 金丝雀yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata: { name: api }
spec:
  replicas: 10
  selector: { matchLabels: { app: api } }
  template:
    metadata: { labels: { app: api } }
    spec:
      containers:
        - name: api
          image: example/api:1.5.0
  strategy:
    canary:
      steps:
        - setWeight: 10            # 先放 10% 流量
        - pause: { duration: 10m } # 观察 10 分钟
        - setWeight: 50
        - pause: {}                # 无限期暂停，人工确认后继续
        - setWeight: 100

按步骤放量与暂停；可再挂 AnalysisTemplate 按指标自动中止。

📊 05 · 参数对比

流量拆分方式

方式精度适用场景
按副本比例粗，受副本数限制无网格的简单集群
网关/服务网格权重精确百分比需要精细控制
按用户或请求头定向到特定人群内部员工、测试用户先用
⚖️ 06 · 方案取舍

自动分析放量

优点快速、客观，减少人工盯盘

代价需要可靠指标与阈值

适用指标体系成熟

人工审批放量

优点可结合业务判断

代价慢，依赖值守

适用重大或首次变更

按用户分组

优点体验一致，便于排查

代价样本可能不具代表性

适用先给内部或低风险用户

🕳️ 07 · 常见坑

  • ✗金丝雀流量太小或时间太短，指标没有统计意义。

    ✓确保每步有足够请求量与观察时间。

  • ✗把金丝雀与历史数据比较，被流量周期误导。

    ✓与同时段的基线版本对比。

  • ✗同一用户请求在新旧版本间跳来跳去，体验不一致。

    ✓需要时按用户粘性路由。

  • ✗数据库迁移在金丝雀开始前就破坏了兼容性。

    ✓迁移保持向后兼容，与代码发布解耦。

🎤 09 · 面试追问
金丝雀分析应看哪些指标？

技术指标如错误率、p99 延迟、资源使用和崩溃次数；业务指标如下单转化率、支付成功率。应与同时运行的基线比较，设统计显著性和阈值，并留足样本量，避免小流量下的随机波动误判。

金丝雀和 A/B 测试有何区别？

金丝雀关注新版本是否安全稳定，目标是尽快全量或回滚；A/B 测试关注不同方案对用户行为的影响，需要长期分组和统计实验设计。两者都拆分流量，但目的和持续时间不同。

没有服务网格能做金丝雀吗？

可以。通过调整新旧版本副本数比例粗略拆分；或在 Ingress、云负载均衡上配置权重；也可在应用层用功能开关按用户启用。精度和控制能力不如网格，但足够起步。
