会话固定攻击

Session Fixation

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

会话固定（Session Fixation）是一类会话管理漏洞：攻击者先让受害者使用一个攻击者已知的会话 ID，待受害者登录后，该 ID 被提升为已认证状态，攻击者即可冒用。根因是应用在认证前后沿用同一个会话标识。

⚙️ 02 · 原理
  1. 1

    攻击者从目标站获得一个合法但未认证的会话 ID，或利用宽松策略自造一个。

  2. 2

    通过 URL 参数、子域写 Cookie、XSS 等方式把该 ID 植入受害者浏览器。

  3. 3

    受害者正常登录，服务端只在原会话上写入用户身份，没有更换会话 ID。

  4. 4

    攻击者携带同一会话 ID 访问，被服务端识别为已登录的受害者。

  5. 5

    防御核心：认证或权限变化时作废旧会话并签发新 ID，并拒绝服务端未签发过的 ID。

🔤 03 · 术语
会话标识 (Session ID)
服务端会话的随机索引，通常放在 Cookie 中。
会话再生 (Session Regeneration)
登录或提权时销毁旧会话、生成新 ID 并迁移必要数据。
严格模式 (Strict Mode)
只接受服务端自己创建的会话 ID，拒绝客户端自造 ID。
__Host- 前缀 Cookie
要求 Secure、Path=/ 且无 Domain，防止子域覆盖写入。
权限提升点 (Privilege Change)
登录、切换角色、二次验证完成等需要换会话的时刻。
💻 04 · 代码
Express 登录时再生会话javascript
// npm i express express-session
const session = require('express-session');
app.use(session({
  name: '__Host-sid',            // 防子域覆盖
  secret: process.env.SESSION_SECRET,
  resave: false,
  saveUninitialized: false,     // 未登录不发会话
  cookie: { httpOnly: true, secure: true, sameSite: 'lax', path: '/' }
}));

app.post('/login', async (req, res, next) => {
  const user = await verifyPassword(req.body.username, req.body.password);
  if (!user) return res.status(401).send('用户名或密码错误');
  // 关键：认证成功后换新的会话 ID
  req.session.regenerate((err) => {
    if (err) return next(err);
    req.session.userId = user.id;
    req.session.save((err) => (err ? next(err) : res.redirect('/')));
  });
});

regenerate 会销毁旧会话并签发新 ID；verifyPassword 为业务自定义函数。

⚖️ 06 · 方案取舍

登录时再生会话

优点直接切断攻击链，成本极低

代价需迁移购物车等匿名数据

适用所有有登录态的应用都应做

无状态 JWT 会话

优点无服务端会话可固定

代价吊销困难，需另做黑名单

适用已有成熟 token 体系的 API

绑定客户端特征（IP/UA）

优点增加冒用难度

代价移动网络 IP 常变，误伤多

适用仅作辅助风控信号

🕳️ 07 · 常见坑

  • ✗只在注册时换会话，登录、二次验证后不换

    ✓每个权限提升点都调用会话再生

  • ✗再生后旧会话未销毁仍可使用

    ✓确认存储层删除旧会话记录

  • ✗Cookie 设置 Domain=.example.com，子域可覆盖

    ✓认证 Cookie 用 __Host- 前缀且不设 Domain

  • ✗PHP 未开启 session.use_strict_mode

    ✓开启严格模式并在登录后 session_regenerate_id(true)

🎤 09 · 面试追问
会话固定和会话劫持有什么区别？

劫持是登录后窃取受害者的会话 ID（如 XSS 读 Cookie、网络嗅探）；固定是登录前把已知 ID 塞给受害者，等它被提升权限。前者靠保护 ID 不泄露，后者靠认证时更换 ID。

为什么 HttpOnly 不能完全防会话固定？

HttpOnly 阻止脚本读取 Cookie，但固定攻击不需要读取，只需写入或让服务端接受攻击者提供的 ID。子域写 Cookie、URL 传 sid 都绕得过 HttpOnly，必须靠再生会话与严格模式。

再生会话时要注意哪些数据迁移？

保留合理的匿名态数据（购物车、语言偏好），丢弃与认证相关的临时状态（CSRF token 应重新生成）。确保原子性：先建新会话再删旧会话，避免并发请求落到半迁移状态。
