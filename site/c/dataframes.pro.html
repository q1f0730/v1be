📐 01 · 定义

数据框（DataFrame）是带列名、按列存储类型化数据的二维表结构，是 pandas、Polars、R 等数据分析工具的核心抽象，支持向量化的筛选、变换、分组聚合与连接。它属于数据处理层：适合在单机内存中处理从几千到数千万行的表格数据，常作为 ETL、分析与机器学习特征工程的工作台。

⚙️ 02 · 原理
  1. 1

    每列是同一类型的数组（整数、浮点、字符串、日期等），按列存储便于向量化计算与压缩。

  2. 2

    读取 CSV、Parquet、数据库等数据源时推断或指定列类型，类型错误是后续计算出错的首要原因。

  3. 3

    运算以整列为单位执行（向量化），底层由 C/Rust 实现，远快于 Python 逐行循环。

  4. 4

    groupby/group_by 按键分组后聚合，merge/join 按键连接多表，语义与 SQL 对应。

  5. 5

    Polars 提供惰性 API：先构建查询计划，collect 时统一优化（谓词下推、投影裁剪）再执行。

🔤 03 · 术语
向量化 (Vectorization)
对整列一次性运算，避免 Python 层逐行循环。
dtype
列的数据类型，决定可用运算与内存占用。
惰性求值 (Lazy Evaluation)
延迟执行，先优化整个查询计划再计算。
Apache Arrow
跨语言的列式内存格式，Polars 基于它，pandas 也可选用。
Parquet
列式存储文件格式，带类型与压缩，比 CSV 更适合分析。
💻 04 · 代码
清洗与聚合：pandas 与 Polarspython
# pip install pandas polars
import pandas as pd

df = pd.read_csv("sales.csv", parse_dates=["date"])
df.info()                                   # 先看每列类型与空值

# 金额列混有「元」和千分位逗号：清洗后转数值，无法转换的置为 NaN
df["amount"] = pd.to_numeric(
    df["amount"].astype(str).str.replace("元", "").str.replace(",", ""),
    errors="coerce",
)
print("无法解析的金额:", df["amount"].isna().sum())

monthly = df.groupby(df["date"].dt.to_period("M"))["amount"].sum()
print(monthly)

# Polars 惰性查询：只读取需要的列，过滤下推到扫描阶段
import polars as pl
out = (
    pl.scan_csv("clean_sales.csv")
      .filter(pl.col("amount") > 0)
      .group_by("region")
      .agg(pl.col("amount").sum().alias("total"))
      .sort("total", descending=True)
      .collect()
)
print(out)

先检查类型与空值再计算；大文件用 Polars 惰性 API 或 Parquet 格式。

⚖️ 06 · 方案取舍

pandas

优点生态最全、资料多、AI 生成代码最熟练

代价大数据量时内存与速度受限

适用中小数据、需兼容现有库

Polars

优点多线程、惰性优化、内存效率高

代价API 与 pandas 不同，部分库需转换

适用大文件、性能敏感管道

SQL/数据仓库

优点数据量无单机上限、可共享

代价需基础设施，交互探索稍慢

适用超出单机内存或团队共享

🕳️ 07 · 常见坑

  • ✗用 for 循环或 apply 逐行处理大表

    ✓改用向量化表达式或内置方法

  • ✗不检查 dtype，数字列被读成字符串

    ✓读取后先 info/schema，必要时显式指定类型

  • ✗对筛选结果切片赋值引发链式赋值问题

    ✓使用 .loc 一次完成筛选与赋值，或显式 .copy()

  • ✗CSV 反复读写丢失类型且很慢

    ✓中间结果存 Parquet

🎤 09 · 面试追问
为什么向量化比 Python 循环快？

循环中每次迭代都有解释器开销与对象装箱；向量化把整列交给 C/Rust 实现的内核一次处理，数据连续存放、可利用 SIMD 与缓存，开销降低数十到数百倍（视操作而定）。

Polars 惰性模式带来哪些优化？

先构建完整查询计划再执行：谓词下推在读取时就过滤、投影裁剪只读所需列、合并相邻操作、并行执行，还能流式处理超出内存的数据。最终 collect 才真正计算。

数据量超过内存怎么办？

按列只读需要的字段、用更紧凑的类型；分块处理；使用 Polars 流式或 DuckDB 等可溢出到磁盘的引擎；数据转为 Parquet；仍不够则迁移到数据仓库或分布式计算。
