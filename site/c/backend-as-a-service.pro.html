后端即服务 (Supabase / Firebase)

Backend as a Service

📐 01 · 定义

后端即服务（Backend as a Service，BaaS）是把数据库、认证、文件存储、实时订阅和函数等常见后端能力打包成托管服务，前端通过 SDK 直接调用的模式，代表产品有 Supabase、Firebase。它能大幅缩短开发时间，但安全模型转移到数据库规则上：客户端密钥是公开的，权限全靠服务端规则保证。

⚙️ 02 · 原理
  1. 1

    在控制台创建项目，获得项目 URL 和可公开的客户端密钥（Supabase 的 anon/publishable key、Firebase 配置）。

  2. 2

    前端通过 SDK 直接读写数据、调用认证接口，SDK 自动附带当前用户的身份令牌。

  3. 3

    服务端依据访问规则判定请求：Supabase 使用 PostgreSQL 行级安全，Firebase 使用 Security Rules。

  4. 4

    需要保密逻辑或第三方密钥时，放在边缘函数或云函数中执行，使用服务端密钥。

  5. 5

    平台托管扩缩容、备份和监控，开发者通过迁移、规则文件管理变更。

🔤 03 · 术语
Supabase
以 PostgreSQL 为核心的开源 BaaS，提供认证、存储、实时和边缘函数。
Firebase
Google 的 BaaS，数据库有 Firestore 与 Realtime Database。
行级安全 (RLS)
按策略限制用户可访问的行，Supabase 的核心授权机制。
service_role key
Supabase 绕过 RLS 的服务端密钥，绝不能暴露到客户端。
Security Rules
Firebase 的声明式访问规则，控制客户端读写。
💻 04 · 代码
Supabase 表启用 RLSsql
-- 建表：每条待办属于一个用户
create table public.todos (
  id bigint generated always as identity primary key,
  user_id uuid not null references auth.users(id) default auth.uid(),
  title text not null,
  done boolean not null default false
);

-- 启用行级安全：未写策略前，客户端默认无任何访问权
alter table public.todos enable row level security;

-- 只能读、写自己的行
create policy "read own todos" on public.todos
  for select to authenticated using ((select auth.uid()) = user_id);

create policy "insert own todos" on public.todos
  for insert to authenticated with check ((select auth.uid()) = user_id);

-- 前端：await supabase.from('todos').select('*') 只会返回当前用户的行

RLS 是用公开密钥直连数据库时的安全边界；(select auth.uid()) 写法为官方性能建议。

🕳️ 07 · 常见坑

  • ✗表未启用 RLS，任何人用公开密钥可读写

    ✓所有暴露的表启用 RLS 并编写最小策略

  • ✗把 service_role key 写进前端或提交仓库

    ✓仅在服务端函数中使用，泄露立即轮换

  • ✗Firebase 规则保持测试模式全开放

    ✓上线前改为基于 request.auth 的规则并测试

  • ✗AI 生成的 Supabase 代码只写查询不写策略

    ✓要求同时生成 RLS 策略，并用不同账号验证

🎤 09 · 面试追问
BaaS 的公开密钥泄露了怎么办？

Supabase 的 anon/publishable key 和 Firebase 配置本就设计为公开，只标识项目，不代表权限。真正的安全来自 RLS 或 Security Rules。需要保密的是 service_role 等服务端密钥，泄露必须立即轮换。

什么时候不适合用 BaaS？

业务逻辑复杂、需要大量服务端事务编排，数据规模或查询模式超出平台能力，有严格的数据驻留或合规要求，或对成本的可预测性要求很高时。也可以组合：数据和认证用 BaaS，复杂逻辑放自有服务。

RLS 策略如何测试？

在测试环境创建多个用户，分别用其令牌通过客户端 SDK 执行读写，断言只能访问自己的数据、不能写入他人数据；同时测试匿名访问。Supabase 也支持在 SQL 中模拟角色和 JWT 声明执行查询，可以写成数据库测试纳入 CI。
