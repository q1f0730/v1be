熔断器 (Circuit Breaker)

Circuit Breaker

📐 01 · 定义

熔断器（Circuit Breaker）是一种容错模式：当对某个依赖的调用失败率或超时超过阈值时，暂时停止调用并快速失败，过一段时间再放少量请求探测恢复。它属于服务间通信的韧性层，防止下游故障耗尽调用方的线程、连接与重试预算，从而阻断连锁故障。Michael Nygard 在《Release It!》中推广了此模式。

⚙️ 02 · 原理
  1. 1

    闭合（Closed）：正常调用，同时在滑动窗口内统计失败率与慢调用比例。

  2. 2

    当失败率超过阈值（且窗口内调用数达到最小样本量）时，切换到断开（Open）。

  3. 3

    断开状态下调用直接失败或走降级逻辑，不再请求下游，给下游恢复时间。

  4. 4

    等待时间到期后进入半开（Half-Open），只放行有限个探测请求。

  5. 5

    探测成功率达标则回到闭合；仍失败则重新断开，并重新计时。

🔤 03 · 术语
滑动窗口 (Sliding Window)
按最近 N 次调用或最近 N 秒统计失败率。
最小调用数 (Minimum Calls)
窗口内样本不足时不触发熔断，避免偶发失败误判。
降级 (Fallback)
熔断时返回缓存、默认值或简化结果。
慢调用阈值 (Slow Call Threshold)
超过指定耗时即视为失败，计入熔断统计。
舱壁 (Bulkhead)
按依赖隔离线程池/连接池，常与熔断配合使用。
💻 04 · 代码
pybreaker 包装外部调用python
import pybreaker, requests

# 连续失败 5 次断开，30 秒后进入半开试探
breaker = pybreaker.CircuitBreaker(fail_max=5, reset_timeout=30)

@breaker
def get_rate(currency: str) -> float:
    resp = requests.get(f"https://api.example.com/rates/{currency}", timeout=2)
    resp.raise_for_status()
    return resp.json()["rate"]

def rate_with_fallback(currency: str) -> float:
    try:
        return get_rate(currency)
    except pybreaker.CircuitBreakerError:
        return cached_rate(currency)   # 熔断中：直接用缓存，不打下游
    except requests.RequestException:
        return cached_rate(currency)   # 单次失败也降级

def cached_rate(currency: str) -> float:
    return 7.0  # 示例：实际应读本地缓存

超时与熔断配合：先用 timeout 限制单次等待，再用熔断阻止持续打向故障依赖。

📊 05 · 参数对比

熔断关键参数

参数作用设置思路
失败率阈值触发断开的失败比例高于正常波动，留余量
最小调用数防止小样本误判按流量设置，低流量需更大窗口
断开等待时间给下游恢复的时间参考下游典型恢复时长
半开探测数恢复时放行的请求量少量即可，避免冲垮下游

🕳️ 07 · 常见坑

  • ✗熔断只看错误，不看慢调用

    ✓把超时与慢调用计入失败，避免线程被拖死

  • ✗所有下游共用一个熔断器

    ✓按依赖（必要时按接口）分别熔断

  • ✗熔断后没有降级，用户直接看到 500

    ✓设计降级：缓存、默认值、功能隐藏或明确提示

  • ✗把 4xx 业务错误也计为失败

    ✓只统计下游故障类错误（超时、5xx、连接失败）

🎤 09 · 面试追问
熔断器与重试如何配合？

重试放在熔断器内部或之前需谨慎：每次重试都计入统计；熔断打开后重试应立即停止。重试需有限次数+指数退避+抖动，避免在下游恢复瞬间造成冲击。

半开状态为什么只放少量请求？

下游可能刚恢复、容量有限；全量流量瞬间涌入会再次压垮它。少量探测成功后再闭合，失败则重新断开，相当于渐进恢复。

熔断器和限流有什么区别？

限流保护自己（或下游）不被过量请求压垮，按速率拒绝；熔断根据下游健康状况决定是否调用，保护调用方并给下游恢复时间。一个看流量，一个看错误。
