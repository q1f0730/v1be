四大黄金信号

Golden Signals

📐 01 · 定义

四大黄金信号（Four Golden Signals）是 Google《SRE》一书提出的面向用户服务的监控基线：延迟（Latency）、流量（Traffic）、错误（Errors）、饱和度（Saturation）。它属于可观测性与 SRE 实践层，回答「服务对用户是否健康」，为 SLO 与告警提供起点；同类方法还有面向请求的 RED 与面向资源的 USE。

⚙️ 02 · 原理
  1. 1

    延迟：处理请求所需时间，用分位数（P50/P95/P99）而非平均值，并区分成功与失败请求的延迟。

  2. 2

    流量：系统承受的需求量，如每秒 HTTP 请求数、并发会话数、每秒处理的消息数或 Token 数。

  3. 3

    错误：失败请求的比率，包括显式错误（5xx）、隐式错误（200 但内容错误）和超出 SLO 的慢响应。

  4. 4

    饱和度：服务有多「满」，关注最受限的资源，如 CPU、内存、连接池、队列长度、GPU 显存，常作为容量预警。

  5. 5

    基于四个信号建立看板与 SLO，告警优先针对影响用户的症状（错误率、延迟），而不是底层原因。

🔤 03 · 术语
分位数延迟 (Percentile Latency)
P99 表示 99% 请求不超过该耗时，能暴露长尾。
RED 方法
Rate、Errors、Duration，面向请求驱动服务的简化版本。
USE 方法
Utilization、Saturation、Errors，面向资源（CPU、磁盘）的分析方法。
症状告警 (Symptom-based Alerting)
按用户可感知的问题告警，而非按内部原因。
SLI / SLO
服务水平指标 / 目标，常由黄金信号推导而来。
💻 04 · 代码
Prometheus 中的四个信号yaml
# recording rules：把四个信号预计算为便于看板和告警使用的指标
groups:
  - name: golden-signals
    rules:
      - record: job:http_requests:rate5m          # 流量
        expr: sum by (job) (rate(http_requests_total[5m]))
      - record: job:http_errors:ratio5m           # 错误率
        expr: |
          sum by (job) (rate(http_requests_total{status=~"5.."}[5m]))
          / sum by (job) (rate(http_requests_total[5m]))
      - record: job:http_latency:p99_5m           # 延迟（P99）
        expr: |
          histogram_quantile(0.99,
            sum by (job, le) (rate(http_request_duration_seconds_bucket[5m])))
      - record: instance:cpu:saturation           # 饱和度（以 CPU 使用率示意）
        expr: 1 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m]))

指标名遵循常见约定（需应用与 node_exporter 暴露对应指标）；饱和度应选最先耗尽的资源。

📊 05 · 参数对比

三种监控方法对比

方法关注对象指标
四大黄金信号面向用户的服务延迟、流量、错误、饱和度
RED请求驱动的微服务速率、错误、耗时
USE硬件与系统资源利用率、饱和度、错误
⚖️ 06 · 方案取舍

症状告警（错误率、延迟）

优点直接对应用户影响，噪音少

代价定位根因需要再下钻

适用值班告警的主要来源

原因告警（CPU、磁盘）

优点能提前预警

代价易产生大量不影响用户的告警

适用容量预警，通常不叫醒人

基于 SLO 燃烧率告警

优点兼顾灵敏度与误报

代价需先定义 SLO 与错误预算

适用成熟团队的标准做法

🕳️ 07 · 常见坑

  • ✗用平均延迟衡量性能

    ✓使用 P95/P99 等分位数，并用直方图指标聚合

  • ✗错误只统计 5xx

    ✓把业务失败、超时与超过 SLO 的慢请求也计入

  • ✗把失败请求的快速响应混入延迟统计，使延迟看起来很好

    ✓成功与失败请求的延迟分开统计

  • ✗饱和度只看 CPU

    ✓找出真正的瓶颈资源：连接池、队列、线程池、显存

☑️ 08 · 检查清单
🎤 09 · 面试追问
为什么不用平均延迟？

延迟分布通常长尾，少量极慢请求被大量快请求平均掉；而长尾请求往往影响最重要的用户或在扇出调用中被放大。分位数能直接反映这部分体验。

饱和度和利用率有什么区别？

利用率是资源忙碌的时间比例；饱和度是超出处理能力、正在排队的工作量。利用率 100% 前就可能出现排队，延迟上升，饱和度更能预测性能劣化。

LLM 应用的黄金信号如何调整？

延迟可拆为首 Token 时间与每 Token 时间；流量用请求数与 Token 吞吐；错误包含限流、超时、内容拒绝和结构化输出解析失败；饱和度关注 GPU 显存、KV 缓存与排队长度。
