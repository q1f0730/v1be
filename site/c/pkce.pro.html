授权码证明密钥 (PKCE)

PKCE

📐 01 · 定义

PKCE（Proof Key for Code Exchange，RFC 7636）是 OAuth 2.0 授权码流程的扩展：客户端为每次授权生成随机 code_verifier，授权请求只发送其哈希 code_challenge，用授权码换令牌时再提交原文，授权服务器比对后才发放令牌。它属于身份认证协议层，防止授权码被截获后冒用；RFC 9700（OAuth 2.0 安全最佳实践）建议所有客户端使用。

⚙️ 02 · 原理
  1. 1

    客户端生成高熵随机字符串 code_verifier（43–128 个字符），保存在本地会话中。

  2. 2

    计算 code_challenge = BASE64URL(SHA256(code_verifier))，method 为 S256。

  3. 3

    授权请求携带 code_challenge 与 code_challenge_method，授权服务器将其与签发的授权码绑定。

  4. 4

    回调拿到授权码后，客户端在令牌请求中提交 code 与原始 code_verifier。

  5. 5

    授权服务器重新计算哈希并比对，一致才签发令牌；截获授权码者因没有 verifier 无法兑换。

🔤 03 · 术语
code_verifier
客户端每次授权生成的随机密钥原文，只在换令牌时发送。
code_challenge
verifier 的 SHA-256 哈希经 Base64URL 编码，在授权请求中发送。
S256 / plain
两种转换方法；plain 直接发原文，仅在无法计算 SHA-256 时使用。
公共客户端 (Public Client)
无法安全保存密钥的客户端，如 SPA、移动 App。
授权码拦截攻击
恶意应用或日志截获重定向中的授权码并抢先兑换令牌。
💻 04 · 代码
浏览器生成 PKCE 参数javascript
// 生成 code_verifier（32 字节随机数 → 43 个 Base64URL 字符）
function base64url(bytes) {
  return btoa(String.fromCharCode(...new Uint8Array(bytes)))
    .replace(/\+/g, "-").replace(/\//g, "_").replace(/=+$/, "");
}
const verifier = base64url(crypto.getRandomValues(new Uint8Array(32)));

// code_challenge = BASE64URL(SHA256(verifier))
const digest = await crypto.subtle.digest("SHA-256", new TextEncoder().encode(verifier));
const challenge = base64url(digest);
sessionStorage.setItem("pkce_verifier", verifier);

const url = new URL("https://auth.example.com/authorize");
url.search = new URLSearchParams({
  response_type: "code", client_id: "my-spa",
  redirect_uri: "https://app.example.com/callback",
  scope: "openid profile", state: crypto.randomUUID(),
  code_challenge: challenge, code_challenge_method: "S256",
}).toString();
location.assign(url);
// 回调后 POST /token 时附带 code 和 code_verifier=sessionStorage 中的值

演示原理；生产中建议使用 oauth4webapi 等成熟库，并校验 state 防 CSRF。

📊 05 · 参数对比

OAuth 客户端与 PKCE

客户端类型能否保存密钥建议
服务端 Web 应用能（机密客户端）client_secret + PKCE
单页应用 SPA不能授权码 + PKCE，禁止隐式流程
移动/桌面 App不能授权码 + PKCE，使用系统浏览器
CLI / 设备不能PKCE 或设备授权流程
⚖️ 06 · 方案取舍

授权码 + PKCE

优点防截获，无需前端存密钥

代价多一步实现，依赖授权服务器支持

适用所有新客户端的默认选择

隐式流程 (Implicit)

优点实现简单

代价令牌暴露在 URL，已不推荐

适用不应再用于新项目

BFF 代管令牌

优点令牌不进浏览器，降低 XSS 窃取风险

代价需要后端组件与会话

适用安全要求高的 SPA

🕳️ 07 · 常见坑

  • ✗使用 plain 方法或固定的 verifier

    ✓始终使用 S256，每次授权重新生成随机 verifier

  • ✗以为有了 PKCE 就不需要 state

    ✓PKCE 防授权码冒用，state（或 nonce）仍用于防 CSRF 与关联请求

  • ✗在 SPA 或 App 中内嵌 client_secret

    ✓公共客户端不使用密钥，依靠 PKCE 与精确的重定向 URI

  • ✗用不安全的随机数生成 verifier

    ✓使用 crypto.getRandomValues 等密码学安全随机源

🎤 09 · 面试追问
PKCE 为什么能防授权码拦截？

攻击者截获的只是授权码；换令牌需要原始 verifier，而授权请求中只出现了它的 SHA-256 哈希，哈希不可逆，攻击者无法构造 verifier，因此无法兑换令牌。

机密客户端还需要 PKCE 吗？

需要。RFC 9700 建议所有客户端使用 PKCE：它还能防授权码注入攻击，即攻击者把自己的授权码注入受害者会话。OAuth 2.1 草案也将其设为授权码流程的必选项。

PKCE 能防 XSS 窃取令牌吗？

不能。PKCE 保护的是授权码兑换环节；令牌一旦进入浏览器，XSS 仍可读取。应配合 CSP、短期令牌、刷新令牌轮换或 BFF 模式。
