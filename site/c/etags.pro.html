实体标签与协商缓存

ETags

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

ETag（实体标签）是服务器为资源某个具体版本生成的不透明标识，放在响应头中。客户端之后带 If-None-Match 发起条件请求，若版本未变服务器返回 304 Not Modified 而不传正文，从而节省带宽；带 If-Match 写入时可实现乐观并发控制。它是 HTTP 协商缓存的核心机制（RFC 9110）。

⚙️ 02 · 原理
  1. 1

    服务器返回资源时生成 ETag（内容哈希、版本号或修改时间与大小的组合）。

  2. 2

    客户端缓存响应及其 ETag；缓存过期或要求验证时，请求带 If-None-Match: 该 ETag。

  3. 3

    服务器比较当前 ETag：相同则返回 304 无正文，不同则返回 200 和新内容。

  4. 4

    写请求带 If-Match: 该 ETag，版本不符时服务器返回 412，防止覆盖他人修改。

  5. 5

    弱 ETag（W/ 前缀）表示语义等价即可，适合压缩等字节不同但内容相同的情况。

🔤 03 · 术语
强 ETag (Strong ETag)
字节级完全相同才匹配。
弱 ETag (Weak ETag)
以 W/ 开头，语义等价即视为相同。
If-None-Match
条件读：ETag 不匹配时才返回完整内容。
304 Not Modified
资源未变，客户端继续使用本地缓存。
If-Match / 412
条件写：版本不匹配时返回 412 Precondition Failed。
Last-Modified
基于修改时间的验证器，精度只到秒。
💻 04 · 代码
条件读与条件写http
# 1. 首次请求：服务器返回 ETag
GET /api/articles/7 HTTP/1.1

HTTP/1.1 200 OK
ETag: "a1b2c3"
Cache-Control: no-cache
Content-Type: application/json

{"id": 7, "title": "Hello", "version": 3}

# 2. 再次请求：带上 ETag 做验证，未变则无正文
GET /api/articles/7 HTTP/1.1
If-None-Match: "a1b2c3"

HTTP/1.1 304 Not Modified
ETag: "a1b2c3"

# 3. 更新时带 If-Match，被他人抢先修改则失败
PUT /api/articles/7 HTTP/1.1
If-Match: "a1b2c3"
Content-Type: application/json

{"title": "Hello, world"}

HTTP/1.1 412 Precondition Failed

If-None-Match 省带宽，If-Match 防覆盖；同一个 ETag 同时服务缓存与并发控制。

⚖️ 06 · 方案取舍

内容哈希 ETag

优点准确，与部署实例无关

代价需读取并计算整个内容

适用中小响应、静态文件

版本号 ETag

优点无需计算，天然支持并发控制

代价需维护版本字段

适用数据库资源的 API

修改时间+大小

优点计算便宜

代价多机时间或文件属性可能不一致

适用单机静态文件服务

🕳️ 07 · 常见坑

  • ✗多台服务器生成的 ETag 不一致，验证总是失败

    ✓基于内容或版本生成，不依赖 inode 等本机属性

  • ✗开启压缩后强 ETag 与原始内容不匹配

    ✓为不同编码使用不同 ETag，或使用弱 ETag

  • ✗框架对动态响应自动生成哈希 ETag，仍要完整计算响应

    ✓对大响应用版本号提前判断，跳过生成正文

  • ✗用弱 ETag 做 If-Match 并发控制

    ✓条件写使用强 ETag 或显式版本号

☑️ 08 · 检查清单
🎤 09 · 面试追问
ETag 和 Last-Modified 都有时用哪个？

按 RFC 9110，服务器收到 If-None-Match 时应优先使用它，忽略 If-Modified-Since。ETag 更精确，能区分一秒内的多次修改，也能表达内容回滚到旧版本的情况；Last-Modified 作为兼容补充。

强弱 ETag 的区别与用途？

强 ETag 要求字节完全相同，可用于条件写、分段请求；弱 ETag 以 W/ 开头，只要语义等价即可匹配，适合压缩、空白差异等场景，只能用于缓存验证，不能用于 If-Match 写入。

API 中如何用 ETag 防止并发覆盖？

GET 返回基于版本号的 ETag；客户端 PUT/PATCH 带 If-Match；服务端在同一条 UPDATE 中校验版本，不符返回 412；客户端重新获取最新资源后合并修改再提交。缺少 If-Match 时可返回 428 强制要求。
