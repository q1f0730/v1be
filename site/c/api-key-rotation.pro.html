API密钥定期轮换

API Key Rotation

📐 01 · 定义

API 密钥轮换（API Key Rotation）是按计划或在疑似泄露时生成新密钥、平滑切换使用方、再吊销旧密钥的运维实践。它属于密钥管理（Secrets Management）层，目的是缩短任一密钥的有效暴露窗口。轮换的关键在于支持新旧密钥短期并存，实现零停机切换。

⚙️ 02 · 原理
  1. 1

    盘点所有密钥及其使用方、存放位置、权限范围和负责人，建立密钥清单。

  2. 2

    生成新密钥，并写入密钥管理服务或部署平台的环境变量，而非代码仓库。

  3. 3

    在新旧密钥同时有效的过渡期内，逐个更新所有使用方的配置并重新部署。

  4. 4

    通过访问日志确认旧密钥已无调用后再吊销；疑似泄露时应立即吊销。

  5. 5

    记录轮换时间与操作人，并通过自动化（定时任务或密钥管理服务）降低人工成本。

🔤 03 · 术语
密钥管理服务 (Secrets Manager)
集中存储、访问控制和轮换密钥的服务。
双密钥过渡 (Dual-Key Overlap)
新旧密钥同时有效一段时间，确保无缝切换。
吊销 (Revocation)
使密钥立即失效，不能再用于认证。
密钥扫描 (Secret Scanning)
检测代码仓库与日志中意外提交的密钥。
短期凭证 (Short-lived Credential)
自动过期的临时凭证，如 OIDC 联合身份签发的令牌。
💻 04 · 代码
零停机轮换流程bash
# 0. 先在服务商控制台创建新密钥（此时新旧两把同时有效）

# 1. 写入部署平台的密钥存储（示例：GitHub Actions Secrets）
gh secret set PAYMENT_API_KEY --body "$NEW_KEY"

# 或写入 Cloudflare Workers 的密钥
printf '%s' "$NEW_KEY" | npx wrangler secret put PAYMENT_API_KEY

# 2. 重新部署所有使用方，使其读取新密钥
gh workflow run deploy.yml

# 3. 观察：确认旧密钥不再有调用（在服务商的用量/日志页面查看）

# 4. 在服务商控制台吊销旧密钥

# 5. 防止泄露：扫描仓库历史中残留的密钥
gitleaks detect --source . --log-opts="--all"

顺序是先加新、再切换、确认后吊销旧；命令均为对应工具的真实用法。

⚖️ 06 · 方案取舍

长期静态密钥 + 定期轮换

优点接入简单，服务商普遍支持

代价仍有暴露窗口

适用第三方 SaaS API

短期凭证（OIDC 联合等）

优点无需保存长期密钥

代价需平台支持与配置

适用CI 访问云平台

密钥管理服务自动轮换

优点自动化、可审计

代价依赖云服务与集成工作

适用数据库凭证等受支持场景

🕳️ 07 · 常见坑

  • ✗先吊销旧密钥再部署新密钥

    ✓先让新密钥上线，确认无旧密钥调用后再吊销

  • ✗泄露后只删除提交，没有吊销密钥

    ✓Git 历史和 fork 中仍可找到，必须立即吊销

  • ✗密钥写在前端代码或移动应用里

    ✓前端可见即公开，秘密密钥只放在服务端

  • ✗把 .env 内容贴给 AI 工具排查问题

    ✓脱敏后再分享，若已泄露立即轮换

🎤 09 · 面试追问
如何实现零停机的密钥轮换？

依赖新旧密钥并存：先生成新密钥并保持旧密钥有效，把新密钥分发到所有使用方并重新部署，通过日志确认旧密钥流量归零后再吊销。若服务商只允许一把有效密钥，就需要维护窗口或在应用层支持多密钥回退。

密钥误提交到 Git 后该怎么做？

首先立即吊销并更换该密钥，因为公开仓库可能在几分钟内被扫描利用，私有仓库也可能被克隆。然后排查是否有异常调用，再视需要清理历史。仅仅删除提交或改写历史并不能让已泄露的密钥变安全。

为什么短期凭证优于定期轮换？

定期轮换只是缩短暴露窗口，长期密钥仍需存储和分发。短期凭证由身份联合（如 CI 的 OIDC）按需签发、分钟到小时级自动过期，没有需要保管的长期秘密，泄露后可利用的时间也很短。
