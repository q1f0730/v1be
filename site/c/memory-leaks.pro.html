内存泄漏

Memory Leaks

🧸 回到小白版

📐 01 · 定义

内存泄漏（Memory Leak）指程序持续保留已不再需要的内存，使占用随运行时间单调增长，最终导致性能下降、频繁 GC 或被 OOM 终止。在 C/C++ 中常因忘记释放；在带垃圾回收的语言里，多因对象仍被意外引用，如无界缓存、未注销的监听器、全局集合和闭包。排查依赖堆快照对比和分配追踪。

⚙️ 02 · 原理
  1. 1

    程序分配对象，并在某处保留引用，例如放进全局字典、缓存或事件监听列表。

  2. 2

    业务上对象已不再使用，但引用仍在，垃圾回收器认为它可达，无法回收。

  3. 3

    随请求或时间累积，常驻内存持续上升，GC 频率和停顿时间增加。

  4. 4

    内存达到容器限制或系统上限，进程被 OOM Killer 杀掉或抛出内存溢出错误。

  5. 5

    排查：在不同时刻取堆快照对比增长最多的对象类型，追溯保留它们的引用链。

🔤 03 · 术语
常驻内存 (RSS)
进程实际占用的物理内存，是观察泄漏的常用指标。
堆快照 (Heap Snapshot)
某时刻堆上所有对象及引用关系的记录，用于对比分析。
保留路径 (Retainer Path)
从 GC 根到某对象的引用链，解释它为何不能被回收。
弱引用 (Weak Reference)
不阻止对象被回收的引用，可用于缓存和映射。
内存碎片 (Fragmentation)
空闲内存分散导致 RSS 偏高，不一定是泄漏。
💻 04 · 代码
tracemalloc 对比快照python
import tracemalloc

_cache = {}  # 无界缓存：典型泄漏源

def handle(request_id: int):
    _cache[request_id] = "x" * 10_000  # 每个请求都存，从不清理

tracemalloc.start()
before = tracemalloc.take_snapshot()

for i in range(5_000):
    handle(i)

after = tracemalloc.take_snapshot()
# 按代码行统计增长最多的分配位置
for stat in after.compare_to(before, "lineno")[:3]:
    print(stat)

# 修复思路：用有上限的缓存，如 functools.lru_cache(maxsize=1024)
# 或 cachetools.TTLCache，确保旧条目会被淘汰

对比前后快照，直接定位到持续分配却不释放的代码行。

🕳️ 07 · 常见坑

  • ✗看到内存升高就断定泄漏，实际是缓存预热或 GC 未触发。

    ✓观察长时间趋势和 GC 后的基线是否持续上升。

  • ✗用定时重启长期掩盖泄漏。

    ✓重启只作临时措施，同时安排定位和修复。

  • ✗把请求级数据挂在全局单例上。

    ✓请求数据随请求生命周期释放，全局对象只放共享只读数据。

🎤 09 · 面试追问
有 GC 的语言为什么还会内存泄漏？

GC 只回收不可达对象。如果对象业务上已无用但仍被引用，比如放在全局字典、未注销的监听器、闭包捕获或无界缓存里，它就始终可达，不会被回收，内存持续增长。

线上怀疑内存泄漏，如何排查？

先看监控确认 GC 后基线持续上升而非正常波动；找出与上升相关的版本或流量；在预发复现，间隔取两次以上堆快照对比增长对象；顺着保留路径找到持有引用的代码；修复后用浸泡测试验证。

内存上涨一定是泄漏吗？

不一定。缓存预热、负载增加、GC 策略延迟回收、内存碎片或分配器不把内存归还系统都会让 RSS 偏高。判断泄漏要看负载稳定时内存是否无上限地持续增长。
