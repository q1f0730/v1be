分布式 SQL 数据库 (NewSQL)

Distributed SQL

📐 01 · 定义

分布式 SQL（Distributed SQL，常称 NewSQL）数据库对外提供关系模型、SQL 与 ACID 事务，对内把数据按键范围自动分片到多台节点，并用 Raft/Paxos 共识复制，实现水平扩展和自动故障转移。代表有 Google Spanner、CockroachDB、TiDB、YugabyteDB。它试图同时获得单机关系库的易用性和 NoSQL 的扩展性。

⚙️ 02 · 原理
  1. 1

    表数据按主键排序后切成连续的范围（CockroachDB 称 range，TiDB 称 region），超过阈值自动分裂并在节点间迁移以均衡负载。

  2. 2

    每个范围有多个副本组成一个共识组，写入需多数派确认，少数节点故障不丢数据、不停服务。

  3. 3

    SQL 层把查询拆解为对多个范围的读写，并尽量把过滤和聚合下推到存储节点执行。

  4. 4

    跨范围事务借助全局时间戳与 MVCC：Spanner 用 TrueTime，CockroachDB 用混合逻辑时钟，TiDB 用中心化授时（TSO）。

  5. 5

    事务提交采用基于共识日志的两阶段提交变体；冲突时事务可能被中止，要求客户端重试。

🔤 03 · 术语
范围/Region (Range)
按主键连续切分的数据片段，是复制、迁移与负载均衡的基本单位。
多数派 (Quorum)
共识组中超过半数的副本，写入获得多数派确认即视为提交。
混合逻辑时钟 (HLC)
结合物理时间与逻辑计数的时钟，用于在无原子钟环境下为事务排序。
TrueTime
Spanner 提供带误差区间的全局时间 API，依靠 GPS 与原子钟。
热点 (Hotspot)
写入集中在单个范围，如单调递增主键导致的尾部写入热点。
事务重试错误 (40001)
序列化冲突的 SQLSTATE，应用需要捕获并重试整个事务。
💻 04 · 代码
避免热点的建表方式sql
-- CockroachDB：用随机 UUID 主键分散写入，避免自增主键尾部热点
CREATE TABLE orders (
  id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id    UUID NOT NULL,
  amount     DECIMAL(12, 2) NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  INDEX (user_id, created_at)
);

-- 查看数据被切成了哪些范围、分布在哪些节点
SHOW RANGES FROM TABLE orders;

-- 调整副本数（默认 3），提高容错
ALTER TABLE orders CONFIGURE ZONE USING num_replicas = 5;

-- TiDB 的对应做法：AUTO_RANDOM 打散主键
-- CREATE TABLE orders (id BIGINT PRIMARY KEY AUTO_RANDOM, ...);
-- SHOW TABLE orders REGIONS;

不同产品语法与默认值不同，以各自官方文档为准；应用端务必实现 40001 重试。

⚖️ 06 · 方案取舍

分布式 SQL

优点自动分片与故障转移，保留 SQL 与事务

代价单次写延迟更高，成本与运维复杂

适用单机库容量或可用性到顶，需多地域

单机库 + 读副本

优点简单成熟，延迟最低

代价写入受单机上限约束

适用绝大多数中小规模业务

应用层手动分库分表

优点可精确控制数据分布

代价跨分片查询与事务需自行处理

适用已有大量 MySQL 资产且团队有经验

🕳️ 07 · 常见坑

  • ✗沿用自增主键，写入全部打到最后一个范围

    ✓使用随机或打散的主键，或哈希分片索引

  • ✗应用不处理事务重试错误

    ✓捕获 40001 等可重试错误，整体重试事务并设置上限

  • ✗把单机库的大事务直接搬过来

    ✓拆小事务，避免跨大量范围的长事务

  • ✗多地域部署却忽略副本放置与就近读

    ✓按访问地域配置副本与 leader 位置，评估跨地域写延迟

🎤 09 · 面试追问
分布式 SQL 如何做到强一致又可扩展？

扩展靠按键范围自动分片，每片独立复制与迁移；一致性靠每个分片内的 Raft 多数派写入，加上全局时间戳与 MVCC 为跨分片事务排序，提交走基于共识的两阶段提交。代价是写入至少一次多数派往返，跨分片事务更慢。

为什么自增主键在分布式 SQL 中是反模式？

数据按主键范围切片，单调递增的键总是落在最后一个范围，所有写入集中到一个共识组的 leader，无法利用其他节点。使用随机 UUID、AUTO_RANDOM 或哈希前缀能把写入分散到多个范围。

Spanner 的 TrueTime 解决了什么问题？

它给出带误差上界的时间区间，事务提交时等待误差区间过去（commit wait），从而保证提交时间戳顺序与真实时间顺序一致，实现外部一致性。没有原子钟的系统用混合逻辑时钟加最大时钟偏移假设，偏移超限时需拒绝服务或重试。
