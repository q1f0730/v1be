外键约束

Foreign Keys

📐 01 · 定义

外键约束（Foreign Key Constraint）声明子表某列的值必须在父表的主键或唯一键中存在，由数据库在写入时强制检查。它属于数据完整性层的引用完整性（Referential Integrity）机制，防止出现孤儿记录，并可定义父行删除或更新时的级联行为。

⚙️ 02 · 原理
  1. 1

    建表或 ALTER TABLE 时声明 FOREIGN KEY (col) REFERENCES parent(key)，被引用列必须有唯一约束。

  2. 2

    向子表插入或更新时，数据库查找父表对应键，不存在则拒绝写入。

  3. 3

    删除或更新父行时，按 ON DELETE / ON UPDATE 规则处理：拒绝、级联、置空或置默认值。

  4. 4

    检查默认在每条语句结束时进行；声明 DEFERRABLE 后可推迟到事务提交时检查。

  5. 5

    检查需要查找子表引用列，若子表外键列无索引，删除父行时可能触发子表全表扫描。

🔤 03 · 术语
引用完整性 (Referential Integrity)
所有引用都指向真实存在的记录。
ON DELETE CASCADE
父行删除时自动删除引用它的子行。
ON DELETE SET NULL
父行删除时把子行外键列置为 NULL。
可延迟约束 (DEFERRABLE)
约束检查推迟到事务提交，便于循环引用或批量导入。
孤儿记录 (Orphan Row)
引用的父记录已不存在的子行。
💻 04 · 代码
外键与删除行为sql
CREATE TABLE orgs (
  id bigint PRIMARY KEY
);

CREATE TABLE projects (
  id     bigint PRIMARY KEY,
  org_id bigint NOT NULL
    REFERENCES orgs(id) ON DELETE CASCADE   -- 删组织连带删项目
);

CREATE TABLE tasks (
  id          bigint PRIMARY KEY,
  project_id  bigint NOT NULL REFERENCES projects(id) ON DELETE RESTRICT,
  assignee_id bigint REFERENCES users(id) ON DELETE SET NULL  -- 人走了任务保留
);

-- PostgreSQL 不会自动给外键列建索引，需手动补上
CREATE INDEX ON projects (org_id);
CREATE INDEX ON tasks (project_id);

-- 大表加外键：先 NOT VALID 再校验，减少锁时间
ALTER TABLE tasks ADD CONSTRAINT tasks_creator_fk
  FOREIGN KEY (creator_id) REFERENCES users(id) NOT VALID;
ALTER TABLE tasks VALIDATE CONSTRAINT tasks_creator_fk;

不同关系选择不同删除行为；外键列要自建索引，大表加约束分两步。

📊 05 · 参数对比

ON DELETE 行为对比

行为父行删除时适用关系
NO ACTION / RESTRICT有子行则拒绝子数据重要，需显式处理
CASCADE子行一并删除强从属，如订单与明细
SET NULL子行外键置空可选关联，如负责人
SET DEFAULT子行外键置默认值有兜底归属的场景
⚖️ 06 · 方案取舍

数据库外键

优点强一致，任何写入路径都受保护

代价写入多一次检查，分库分表难用

适用单库关系型业务，默认首选

应用层校验

优点灵活，可跨库跨服务

代价并发与多入口下容易漏，出现孤儿

适用跨服务、分片或特殊性能约束

外键 + 软删除

优点保留引用关系与历史

代价需处理已删父行仍被引用的语义

适用需审计、可恢复的数据

🕳️ 07 · 常见坑

  • ✗外键列不建索引，删父行时锁等待严重

    ✓为子表外键列建索引（PostgreSQL 不会自动创建）

  • ✗随手用 CASCADE，一次删除连带清空大量数据

    ✓仅对强从属关系用 CASCADE，其余用 RESTRICT 并显式处理

  • ✗迁移顺序错误，先建子表引用尚不存在的父表

    ✓按依赖顺序建表，或先建表后统一加约束

  • ✗批量导入时临时删外键忘记加回

    ✓用可延迟约束或 NOT VALID + VALIDATE，并在检查清单中核对

🎤 09 · 面试追问
为什么有些大厂规范禁止使用外键？

主要出于分库分表后无法跨库约束、高并发下级联与检查带来的锁争用、以及运维变更成本。代价是需在应用层保证一致性并定期巡检孤儿数据。对单库中小规模业务，外键的收益通常大于成本。

外键会带来哪些锁问题？

子表插入需对父行加共享级别锁以防并发删除，父行更新或删除需检查子表。外键列无索引时检查要扫子表，持锁更久，易引发阻塞甚至死锁。

什么时候用 DEFERRABLE INITIALLY DEFERRED？

存在循环引用（如两表互相引用）或批量导入顺序不可控时，把检查推迟到 COMMIT，事务内允许暂时不一致，提交时仍保证完整性。
