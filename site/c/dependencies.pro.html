📐 01 · 定义

依赖（Dependencies）是项目运行或构建所需的外部代码包，分为直接依赖（你声明的）和传递依赖（依赖的依赖）。一个现代项目的依赖树往往包含成百上千个包，它们共同决定了应用的功能、体积、安全面和许可证义务。依赖管理的目标是可复现、可审计、可持续更新。

⚙️ 02 · 原理
  1. 1

    声明：在 package.json 等清单文件中列出直接依赖及其可接受的版本范围。

  2. 2

    解析：包管理器递归展开传递依赖，求出满足所有版本约束的依赖图。

  3. 3

    锁定：把依赖图中每个包的精确版本、下载地址和校验和写入锁文件。

  4. 4

    审计：扫描依赖中的已知漏洞（CVE）与许可证，生成报告或阻断构建。

  5. 5

    更新：通过自动化工具定期提出升级，经测试验证后合并，避免依赖长期过时。

🔤 03 · 术语
传递依赖 (Transitive Dependency)
你未直接声明、由依赖引入的依赖。
依赖地狱 (Dependency Hell)
版本约束冲突导致无法安装或运行的局面。
CVE
公开漏洞的统一编号，安全扫描工具据此报告风险。
SBOM
软件物料清单，列出软件包含的全部组件与版本。
Dependabot
GitHub 提供的依赖更新与安全告警工具。
💻 04 · 代码
自动化依赖更新yaml
# .github/dependabot.yml —— 让 GitHub 每周自动提交依赖升级 PR
version: 2
updates:
  - package-ecosystem: "npm"      # Node 项目
    directory: "/"                # package.json 所在目录
    schedule:
      interval: "weekly"
    open-pull-requests-limit: 5
    groups:
      dev-tools:                  # 把开发依赖的小版本升级合并成一个 PR
        dependency-type: "development"
        update-types: ["minor", "patch"]

  - package-ecosystem: "pip"      # Python 项目
    directory: "/"
    schedule:
      interval: "weekly"

# 本地也可以手动查看依赖树与漏洞：
#   npm ls --depth=1      npm audit      pip-audit

配合 CI 测试，自动化工具能把依赖升级变成持续的小步操作，而不是一年一次的大工程。

⚖️ 06 · 方案取舍

频繁小步升级

优点每次变更小，问题易定位

代价持续占用评审精力

适用有完善测试的活跃项目

定期集中升级

优点节奏可控

代价积压后升级跨度大、风险高

适用维护资源有限的项目

供应商化（vendoring）

优点完全离线可控

代价仓库膨胀，更新麻烦

适用隔离网络或严格审计环境

🕳️ 07 · 常见坑

  • ✗只审查直接依赖，忽略传递依赖

    ✓扫描整个依赖树，关注被间接引入的高危包

  • ✗npm audit fix --force 一键升级到不兼容版本

    ✓逐个评估高危漏洞，在分支中升级并跑测试

  • ✗Agent 自动加了依赖没人注意

    ✓评审 diff 时重点检查清单与锁文件变化

  • ✗依赖多年不升级

    ✓设定升级节奏，至少及时处理安全更新

🎤 09 · 面试追问
如何应对一个深层传递依赖的漏洞？

先确认漏洞代码路径是否真的被调用；查看直接依赖是否已发布修复版本并升级；若尚未修复，可使用包管理器的覆盖机制（npm overrides、pnpm overrides）强制指定安全版本，并跑测试验证兼容性，同时关注上游修复进展。

什么是 SBOM，为什么越来越受重视？

SBOM 是软件物料清单，完整列出组件、版本、来源和许可证。重大供应链安全事件后，政府与企业采购越来越要求提供 SBOM，以便漏洞披露时快速判断受影响范围。常见格式有 SPDX 与 CycloneDX。

依赖越少越好吗？

不绝对。依赖少意味着攻击面和维护成本更低，但自行实现复杂功能（加密、解析、日期）往往更危险。原则是：核心复杂能力用成熟库，琐碎小功能避免引入依赖，并持续评估每个依赖的价值与风险。
