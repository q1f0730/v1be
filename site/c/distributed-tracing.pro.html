分布式链路追踪

Distributed Tracing

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

分布式链路追踪（Distributed Tracing）记录一个请求穿越多个服务、队列和数据库的路径与耗时。请求有唯一 Trace ID，每段操作是一个 Span，跨进程靠请求头传播上下文。它是可观测性三支柱之一，用于定位延迟瓶颈与错误源，主流标准为 OpenTelemetry 与 W3C Trace Context。

⚙️ 02 · 原理
  1. 1

    入口服务收到请求时创建根 Span，生成 Trace ID；若请求已带 traceparent 头则沿用。

  2. 2

    服务内部的关键操作创建子 Span，记录开始结束时间、属性和错误状态。

  3. 3

    调用下游时把追踪上下文注入请求头，下游提取后创建子 Span，形成父子关系。

  4. 4

    SDK 把 Span 批量导出到 Collector，再发送到后端存储，如 Jaeger、Tempo 或商业平台。

  5. 5

    后端按 Trace ID 拼接出瀑布图，配合采样策略控制数据量与成本。

🔤 03 · 术语
Span
一次操作的记录，含名称、起止时间、属性、状态和父 Span。
Trace ID
贯穿一次请求所有 Span 的唯一标识，W3C 中为 32 个十六进制字符。
traceparent 头
W3C 定义的传播头，含版本、Trace ID、父 Span ID 和标志位。
采样 (Sampling)
只保留部分链路，分头部采样和尾部采样。
OpenTelemetry Collector
接收、处理并转发遥测数据的独立组件。
💻 04 · 代码
OpenTelemetry 手动埋点python
from opentelemetry import trace
from opentelemetry.propagate import inject
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor, ConsoleSpanExporter
import requests

provider = TracerProvider()
provider.add_span_processor(BatchSpanProcessor(ConsoleSpanExporter()))
trace.set_tracer_provider(provider)
tracer = trace.get_tracer("checkout")

with tracer.start_as_current_span("checkout") as span:
    span.set_attribute("order.items", 3)
    with tracer.start_as_current_span("call-inventory"):
        headers = {}
        inject(headers)            # 写入 traceparent 头，传给下游
        requests.get("http://inventory:8080/stock", headers=headers, timeout=2)
# 生产中把 ConsoleSpanExporter 换成 OTLP 导出器发往 Collector

创建父子 Span 并把上下文注入请求头；也可用自动埋点库免改代码。

📊 05 · 参数对比

可观测性三支柱

信号擅长回答局限
指标 (Metrics)系统整体是否异常、趋势如何缺少单个请求细节
日志 (Logs)某个事件的具体上下文跨服务难以串联
链路 (Traces)请求慢在哪一段、错在哪个服务数据量大，需要采样
⚖️ 06 · 方案取舍

头部采样

优点实现简单、开销低

代价可能漏掉罕见错误和慢请求

适用流量大、成本敏感

尾部采样

优点可保留所有错误和慢链路

代价Collector 需缓存完整链路，资源消耗大

适用重视异常排查

自动埋点

优点接入快，覆盖常见框架

代价业务语义少，Span 可能过多

适用起步阶段

🕳️ 07 · 常见坑

  • ✗某个中间服务没传播上下文，链路在它那里断成两截。

    ✓所有服务和网关统一使用 W3C Trace Context 传播。

  • ✗异步消息没携带追踪上下文。

    ✓把上下文写入消息头，消费端提取后建立关联。

  • ✗把用户 ID 等高基数字段写进 Span 名称。

    ✓Span 名称保持低基数，变量放在属性中。

  • ✗日志里没有 Trace ID，无法从链路跳到日志。

    ✓在日志中输出 Trace ID 和 Span ID。

☑️ 08 · 检查清单
🎤 09 · 面试追问
链路追踪的上下文是怎么跨服务传递的？

调用方 SDK 把当前 Trace ID、Span ID 和采样标志按 W3C Trace Context 格式注入 traceparent 请求头；被调方提取后，以该 Span 为父创建新 Span。消息队列则写入消息头。任何一环不传播，链路就会断开。

头部采样和尾部采样怎么选？

头部采样在入口就决定是否记录，开销小，但无法预知请求会不会出错；尾部采样在链路完成后根据结果决定保留，能保留所有错误和慢请求，代价是 Collector 需缓存完整链路。常组合使用。

有了日志为什么还需要链路追踪？

日志分散在各服务，难以还原一次请求的完整路径和各段耗时；链路追踪直接给出调用树和瀑布图，快速定位慢段。两者通过 Trace ID 关联，从链路跳到对应日志看细节。
