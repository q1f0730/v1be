查询改写与 HyDE

Query Rewriting & HyDE

📐 01 · 定义

查询改写（Query Rewriting）是在检索前用规则或 LLM 把用户原始问题转换为更适合检索的形式，包括补全多轮对话中的指代、纠错与规范化、扩展同义词、拆分子问题、生成多个查询变体等。HyDE（Hypothetical Document Embeddings）是其中一种：先让模型生成假设答案，再用其嵌入去检索真实文档。它属于 RAG 的检索前处理层。

⚙️ 02 · 原理
  1. 1

    接收用户问题与对话历史，判断是否需要改写（如含代词、过短、包含多个子问题）。

  2. 2

    上下文改写：结合历史把问题改为独立完整的问题，如「它多少钱」→「X 产品的价格是多少」。

  3. 3

    多查询/分解：生成若干同义改写或子问题，分别检索后合并结果（可用 RRF 融合排名）。

  4. 4

    HyDE：让 LLM 写一段假设性答案文档，用它的向量检索，因为答案与文档在嵌入空间中更接近。

  5. 5

    检索结果进入重排与生成；原问题仍用于最终回答，避免改写偏离用户意图。

🔤 03 · 术语
独立问题改写 (Standalone Question)
把依赖上下文的追问改写成无需历史即可理解的问题。
HyDE
用 LLM 生成的假设文档的嵌入进行检索。
多查询检索 (Multi-Query)
生成多个查询变体并合并检索结果，提升召回。
Step-back Prompting
先提出更抽象的上位问题检索背景知识。
RRF (Reciprocal Rank Fusion)
按排名倒数融合多路检索结果的简单方法。
💻 04 · 代码
独立问题改写与 HyDEpython
from openai import OpenAI
client = OpenAI()
MODEL = "gpt-4o-mini"   # 示例，可换成任意聊天模型

def ask(prompt: str) -> str:
    r = client.chat.completions.create(model=MODEL, temperature=0,
        messages=[{"role": "user", "content": prompt}])
    return r.choices[0].message.content.strip()

def standalone(history: str, question: str) -> str:
    return ask(f"对话历史：\n{history}\n\n把最后的问题改写为不依赖历史、"
               f"可独立检索的完整问题，只输出问题。\n问题：{question}")

def hyde_vector(question: str) -> list[float]:
    fake_doc = ask(f"写一段可能出现在帮助文档中的段落来回答：{question}")
    emb = client.embeddings.create(model="text-embedding-3-small", input=fake_doc)
    return emb.data[0].embedding   # 用它去向量库检索真实文档

q = standalone("用户：你们的 Pro 套餐包含什么？\n助手：包含……", "它多少钱？")
vec = hyde_vector(q)
# hits = vector_db.search(vec, top_k=5)   # 检索后仍用原问题生成最终回答

改写解决指代与口语问题；HyDE 以答案风格文本检索，代价是多一次 LLM 调用与延迟。

📊 05 · 参数对比

常见改写策略

策略解决的问题代价
独立问题改写多轮对话中的指代一次 LLM 调用
多查询 + 融合措辞与文档不匹配，召回低多次检索，成本增加
子问题分解复合、多跳问题检索次数多，需合并
HyDE问题短、与文档表述差异大可能引入幻觉内容的偏差
关键词/同义词扩展专有名词、缩写可能引入噪音
⚖️ 06 · 方案取舍

规则改写（同义词表、纠错）

优点快、确定、无额外调用

代价覆盖有限，维护词表

适用领域术语固定

LLM 改写

优点灵活理解意图与上下文

代价增加延迟与成本，可能曲解

适用多轮对话、口语化输入

不改写，靠混合检索 + 重排

优点架构简单

代价指代与多跳问题仍难

适用单轮、问题规范的场景

🕳️ 07 · 常见坑

  • ✗改写后丢失用户的限定条件（时间、版本）

    ✓提示中要求保留实体与约束，并抽样检查改写结果

  • ✗用改写后的问题生成最终回答

    ✓改写只用于检索，生成时使用原问题与对话上下文

  • ✗HyDE 用于模型完全不了解的私有领域

    ✓假设答案可能方向错误，需评测，必要时与原查询检索结果融合

  • ✗所有问题都改写，徒增延迟

    ✓先判断是否需要改写，或并行检索原问题与改写版本

🎤 09 · 面试追问
HyDE 为什么能提升检索？

短问题与长文档在嵌入空间里分布不同；LLM 生成的假设答案在形式和用词上更像真实文档，用其向量检索更容易命中相关段落。即使内容有误，相关性信号往往仍有效。

多查询检索如何合并结果？

每个查询变体各自检索，再去重合并；常用 RRF 按各列表中的排名倒数求和排序，无需分数归一化。最后可交给重排模型精排。

查询改写会不会带来风险？

可能曲解意图、丢失约束或引入不存在的实体，导致检索偏离；也增加延迟与成本。需要日志记录改写结果、评测对比，并在不确定时回退到原问题检索。
