缓存预热

Cache Warming

🧸 回到小白版

📐 01 · 定义

缓存预热（Cache Warming）是在流量到来之前，主动把预计会被访问的热点数据加载进缓存，避免冷启动时大量未命中直接冲击数据库。典型时机包括新缓存集群上线、缓存节点重启、大促或发布会前、CDN 新内容发布。预热本身也要限速，否则会变成另一种压力源。

⚙️ 02 · 原理
  1. 1

    确定热点集合：来自访问日志排行、昨日统计、运营配置或线上流量采样。

  2. 2

    从数据库或源站批量读取数据，写入缓存并设置带抖动的 TTL。

  3. 3

    按批次与速率执行，监控数据库负载，避免预热本身造成过载。

  4. 4

    预热完成后再切入流量，或通过灰度逐步提高新节点的流量比例。

  5. 5

    也可用持久化（如 Redis RDB/AOF）或从旧集群复制，缩短重启后的冷启动。

🔤 03 · 术语
冷启动 (Cold Start)
缓存为空时命中率极低的阶段。
热点集合 (Hot Set)
预计会被高频访问、值得预热的数据。
流量回放 (Traffic Replay)
用录制的真实请求驱动预热。
灰度切流 (Gradual Shift)
逐步把流量从旧节点迁到新节点。
CDN 预取 (Prefetch)
主动让 CDN 节点提前拉取并缓存资源。
💻 04 · 代码
分批限速预热热点商品python
import json, random, time, redis

r = redis.Redis()
BATCH, PAUSE = 200, 0.2         # 每批 200 条，批间暂停 0.2 秒，控制数据库压力

def hot_product_ids(limit: int = 5000) -> list[int]:
    # 取昨日浏览量最高的商品；db_query 为业务自定义
    return db_query(
        "SELECT product_id FROM product_daily_views "
        "WHERE day = current_date - 1 ORDER BY views DESC LIMIT %s", (limit,))

def warm():
    ids = hot_product_ids()
    for i in range(0, len(ids), BATCH):
        rows = db_get_products(ids[i:i + BATCH])     # 一次批量查询
        pipe = r.pipeline(transaction=False)          # 管道减少网络往返
        for p in rows:
            ttl = 3600 + random.randint(0, 600)       # TTL 抖动，避免同时过期
            pipe.set(f"product:{p['id']}", json.dumps(p), ex=ttl, nx=True)
        pipe.execute()
        time.sleep(PAUSE)
    print(f"warmed {len(ids)} products")

if __name__ == "__main__":
    warm()

批量读、管道写、限速与 TTL 抖动；nx=True 不覆盖线上已写入的更新值。

📊 05 · 参数对比

预热数据来源

来源优点局限
历史访问日志排行反映真实热度对新内容无效
运营/活动配置可提前覆盖新品与活动依赖人工准确性
流量回放最接近真实访问模式需要录制与回放设施
旧集群数据复制完整保留工作集需版本与格式兼容
⚖️ 06 · 方案取舍

主动预热

优点切流瞬间即有高命中率

代价需维护热点识别与脚本

适用大促、新集群上线

被动自然填充

优点零额外工作

代价冷启动期数据库压力大

适用流量小、后端余量大

持久化缓存

优点重启后快速恢复

代价占用磁盘，恢复期加载慢

适用单节点重启频繁

🕳️ 07 · 常见坑

  • ✗预热脚本全速运行，先把数据库打满

    ✓分批限速，并监控数据库负载

  • ✗所有预热数据用同一 TTL，一小时后集体过期

    ✓TTL 加随机抖动或按热度分层

  • ✗预热覆盖了刚被业务更新的新值

    ✓写入使用 NX，或比较版本号后再写

  • ✗缓存刚清空就切入全部流量

    ✓预热完成或灰度逐步放量

🎤 09 · 面试追问
什么情况下必须做缓存预热？

后端在零命中情况下无法承受正常流量时：新缓存集群替换旧集群、全量清缓存后、大促与热点事件前、多数节点同时重启。若后端余量足够承受冷启动，自然填充也可以接受。

如何确定要预热哪些数据？

基于访问日志或埋点统计热度排行，覆盖贡献主要流量的头部数据；结合运营提供的新品和活动清单；用历史曲线估算覆盖率与目标命中率的关系，在成本与效果间选择数量。

如何避免预热本身造成故障？

限速分批并监控数据库；在低峰期执行；使用只读副本作为数据源；写入使用 NX 避免覆盖更新；预热可中断、可重入；失败时有降级方案，例如灰度切流而非一次切换。
