约定式提交

Conventional Commits

📐 01 · 定义

Conventional Commits（约定式提交）是一份关于提交信息结构的轻量规范：type(scope)!: description 加可选正文和脚注。它把提交信息变成机器可解析的数据，与语义化版本（SemVer）对应——fix 对应补丁号、feat 对应次版本号、BREAKING CHANGE 对应主版本号，从而支撑自动生成变更日志和自动发版。

⚙️ 02 · 原理
  1. 1

    首行格式为 type(可选 scope)(可选 !): 描述，type 常用 feat、fix，规范也允许 docs、refactor、test、chore 等。

  2. 2

    空一行后写可选正文，说明动机与细节；再空一行写脚注，格式类似 Git trailer，如 Refs: #123。

  3. 3

    破坏性变更用两种方式之一标记：type 后加 !，或脚注写 BREAKING CHANGE: 说明，二者都映射为主版本号升级。

  4. 4

    commitlint 等工具在 commit-msg 钩子里解析首行，不符合规则就拒绝提交，保证仓库历史一致。

  5. 5

    semantic-release、release-please 等工具读取自上次发布以来的提交，推算下一个版本号并生成 CHANGELOG。

🔤 03 · 术语
type
提交类别，规范强制的只有 feat 与 fix，其余由团队约定。
scope
括号中的影响范围，如 feat(auth):，可选。
BREAKING CHANGE
脚注标记的不兼容变更，触发主版本号升级。
Git Trailer
提交信息末尾的 键: 值 元数据行，如 Co-authored-by。
commitlint
校验提交信息是否符合约定格式的 Node 工具。
release-please
Google 维护的工具，依据约定式提交生成发布 PR 与变更日志。
💻 04 · 代码
约定式提交示例与校验配置text
# 新功能（次版本号 +1）
feat(auth): 支持通行密钥登录

# 修复（补丁号 +1），正文与脚注
fix(api): 分页游标为空时返回 400

空游标此前导致 500，改为参数校验。

Refs: #482

# 破坏性变更（主版本号 +1）两种写法
feat(api)!: 移除 v1 用户接口

refactor: 重命名配置项

BREAKING CHANGE: config.timeout 改为 config.timeoutMs

# commitlint.config.js（配合 commit-msg 钩子）
# export default { extends: ["@commitlint/config-conventional"] };

展示 feat/fix/破坏性变更的写法与对应版本号变化，以及 commitlint 的最简配置。

📊 05 · 参数对比

提交类型与版本号映射

提交内容示例首行SemVer 影响
fixfix: 修复空指针PATCH，如 1.4.2→1.4.3
featfeat: 新增导出 CSVMINOR，如 1.4.2→1.5.0
! 或 BREAKING CHANGEfeat!: 删除旧接口MAJOR，如 1.4.2→2.0.0
docs / chore / test 等docs: 更新 README默认不触发发版（取决于工具配置）
⚖️ 06 · 方案取舍

本地 commit-msg 钩子强制

优点问题在提交时即被发现

代价可被 --no-verify 绕过

适用个人或小团队项目

CI 校验 PR 标题

优点不依赖本地环境，强制力高

代价反馈较晚

适用开源项目、使用 squash merge 时

只约定不校验

优点零成本

代价很快走样，自动发版不可靠

适用原型期或无发版需求

🕳️ 07 · 常见坑

  • ✗squash merge 时只校验了单个提交，PR 标题却随意

    ✓squash 合并以 PR 标题为最终提交信息，应在 CI 中校验 PR 标题

  • ✗把破坏性变更写成普通 feat

    ✓任何不兼容改动都加 ! 或 BREAKING CHANGE 脚注，否则自动发版会漏升主版本

  • ✗type 种类无限扩张，每人自造

    ✓在 commitlint 配置中锁定 type-enum 白名单

  • ✗让 AI 生成提交信息却不提供规范

    ✓在规则文件中写明格式与可用 type，让 Agent 按约定生成

🎤 09 · 面试追问
约定式提交如何与 SemVer 联动？

发版工具从上个 tag 起扫描提交：出现 BREAKING CHANGE 或 ! 则升主版本；否则有 feat 升次版本；否则有 fix 升补丁版本。其余类型默认不发版。1.0.0 之前的项目，部分工具会把破坏性变更降级处理，需看配置。

为什么规范只强制 feat 和 fix？

因为只有它们和 SemVer 直接对应。其他类型如 docs、refactor 来自 Angular 约定，团队可自由增减。规范保持最小，便于不同生态采纳，扩展部分交给 commitlint 配置约束。

提交被 --no-verify 绕过怎么办？

本地钩子只是第一道防线。应在 CI 上对 PR 标题或提交范围再跑一次 commitlint，并通过分支保护让检查成为合并的必要条件，这样绕过本地钩子也无法合入主分支。
