数据库死锁

Deadlocks

📐 01 · 定义

死锁是两个或多个事务各自持有对方需要的锁并互相等待，形成等待环，任何一方都无法继续。数据库会通过等待图检测死锁，选择一个事务作为牺牲者回滚以打破环路。死锁无法完全消除，工程目标是降低频率并让应用能安全重试。

⚙️ 02 · 原理
  1. 1

    事务 A 锁住行 1，事务 B 锁住行 2，随后 A 请求行 2、B 请求行 1，形成环。

  2. 2

    锁等待超过一定时间（PostgreSQL 的 deadlock_timeout 默认 1 秒）后，数据库检查等待图。

  3. 3

    发现环路即选择牺牲者回滚，返回死锁错误（PG 为 40P01，MySQL 为错误 1213）。

  4. 4

    另一事务获得锁继续执行；被回滚的事务释放全部锁，需由应用从头重试。

  5. 5

    数据库在日志或状态命令中记录死锁详情，用于定位涉及的语句和锁。

🔤 03 · 术语
等待图 (Wait-for Graph)
节点为事务、边为等待关系的图，有环即死锁。
牺牲者 (Victim)
被数据库选中回滚以解除死锁的事务。
锁顺序 (Lock Ordering)
所有事务按同一顺序获取锁，从根本上避免环。
间隙锁 (Gap Lock)
InnoDB 锁住索引记录间的间隙，常引发意外死锁。
锁超时 (Lock Timeout)
等锁超过阈值直接报错，与死锁检测不同。
💻 04 · 代码
复现与按序加锁sql
-- 复现（两个会话交替执行）
-- 会话 A: BEGIN; UPDATE accounts SET balance = balance - 10 WHERE id = 1;
-- 会话 B: BEGIN; UPDATE accounts SET balance = balance - 10 WHERE id = 2;
-- 会话 A: UPDATE accounts SET balance = balance + 10 WHERE id = 2;  -- 等待 B
-- 会话 B: UPDATE accounts SET balance = balance + 10 WHERE id = 1;  -- 形成环
-- ERROR: deadlock detected (SQLSTATE 40P01)

-- 修复：无论转账方向，都按 id 升序一次性锁住相关行
BEGIN;
SELECT id FROM accounts
WHERE id IN (1, 2)
ORDER BY id
FOR UPDATE;
UPDATE accounts SET balance = balance - 10 WHERE id = 2;
UPDATE accounts SET balance = balance + 10 WHERE id = 1;
COMMIT;

-- PostgreSQL：记录长时间锁等待，便于排查
ALTER SYSTEM SET log_lock_waits = on;
SELECT pg_reload_conf();
-- MySQL：查看最近一次死锁详情
-- SHOW ENGINE INNODB STATUS;

按固定顺序加锁打破环路；开启锁等待日志帮助定位。

⚖️ 06 · 方案取舍

统一加锁顺序

优点从根源消除这类死锁

代价需约束所有代码路径

适用多行更新的核心业务

捕获死锁并重试

优点实现简单，兜底所有情况

代价重试增加延迟，需幂等

适用任何事务型系统都应具备

粗粒度锁（表锁/分布式锁）

优点不会出现行级环路

代价并发度大幅下降

适用低频的批处理任务

🕳️ 07 · 常见坑

  • ✗把死锁当作数据库 bug，只调大超时

    ✓分析死锁日志，修正加锁顺序或索引

  • ✗批量 UPDATE 不排序，与其他批次交叉

    ✓按主键排序或分批固定顺序处理

  • ✗重试时只重放失败那条语句

    ✓整个事务回滚后从头重试

  • ✗外键检查隐式加锁被忽略

    ✓分析时考虑外键、唯一约束带来的隐式锁

🎤 09 · 面试追问
死锁和锁等待超时有什么区别？

死锁是循环等待，没有外力永远无法解除，数据库主动检测并回滚一方；锁等待超时是单向等待太久，对方迟早会释放，只是超过了设置的阈值（如 lock_timeout、innodb_lock_wait_timeout）而报错。

为什么缺索引会导致死锁增多？

没有合适索引时，UPDATE 需要扫描更多行，InnoDB 会对扫描到的记录和间隙加锁，锁范围扩大，不同事务的锁区间更容易交叉形成环。补上索引后只锁命中行。

线上出现死锁如何排查？

先取死锁日志（MySQL 用 SHOW ENGINE INNODB STATUS，PG 看服务器日志），找出两个事务各持有和等待的锁及语句；回到代码确认执行顺序；再看执行计划判断锁范围是否过大，最后修顺序或索引。
