Webhook 回调

Webhook

📐 01 · 定义

Webhook 是一种由服务提供方在事件发生时主动向订阅方预先登记的 URL 发送 HTTP 请求（通常是 POST + JSON）的回调机制。它属于系统集成层的事件推送模式，替代客户端轮询，常见于支付结果、代码仓库事件、表单提交等场景，核心难点在验签、幂等和重试。

⚙️ 02 · 原理
  1. 1

    订阅方在提供方后台或 API 注册回调 URL，并选择关注的事件类型，获得签名密钥。

  2. 2

    事件发生后，提供方构造事件载荷，用密钥对原始请求体计算 HMAC 签名并放入请求头。

  3. 3

    订阅方收到请求，先用原始 body 重新计算签名并恒定时间比较，校验时间戳防重放。

  4. 4

    校验通过后快速返回 2xx，把实际处理放进后台队列，避免超时引发重投。

  5. 5

    提供方在非 2xx 或超时时按退避策略重试，因此订阅方需按事件 ID 去重。

🔤 03 · 术语
HMAC 签名
用共享密钥对消息计算的摘要，证明来源与完整性。
至少一次投递 (At-least-once)
保证送达但可能重复，接收方需幂等。
重放攻击 (Replay Attack)
截获合法请求后重复发送；用时间戳加去重防御。
恒定时间比较 (Constant-time Compare)
比较耗时与内容无关，防止计时侧信道。
死信 (Dead Letter)
多次重试仍失败、被单独保存待人工处理的消息。
💻 04 · 代码
Flask 接收并验签python
import hmac, hashlib, time, os
from flask import Flask, request, abort

app = Flask(__name__)
SECRET = os.environ["WEBHOOK_SECRET"].encode()
seen = set()  # 生产中改用数据库唯一约束或 Redis

@app.post("/webhooks/orders")
def orders_hook():
    body = request.get_data()                    # 必须用原始字节
    ts = request.headers.get("X-Timestamp", "0")
    sig = request.headers.get("X-Signature", "")
    if abs(time.time() - int(ts)) > 300:         # 5 分钟窗口防重放
        abort(400)
    mac = hmac.new(SECRET, ts.encode() + b"." + body, hashlib.sha256)
    if not hmac.compare_digest(mac.hexdigest(), sig):
        abort(401)
    event = request.get_json()
    if event["id"] in seen:                     # 按事件 ID 去重
        return "", 200
    seen.add(event["id"])
    # enqueue(event)  放入队列异步处理，尽快返回
    return "", 200

头名与签名拼接方式是示例，实际以提供方文档为准；核心是原始 body、恒定时间比较与去重。

🕳️ 07 · 常见坑

  • ✗对解析后再序列化的 JSON 验签，签名总对不上

    ✓用框架提供的原始请求体字节计算签名

  • ✗用 == 比较签名

    ✓使用 hmac.compare_digest 等恒定时间比较

  • ✗不去重，重试导致重复发货或重复入账

    ✓以事件 ID 建唯一约束，重复事件直接返回 2xx

  • ✗假设事件按顺序到达

    ✓以事件内时间或版本判断新旧，必要时回查最新状态

🎤 09 · 面试追问
Webhook 接收端如何保证幂等？

以提供方事件 ID 为键写入带唯一约束的处理表，与业务更新放在同一事务；重复到达时检测到冲突直接返回 2xx。业务操作本身也尽量设计成按状态判断的幂等更新。

为什么签名里要包含时间戳？

仅对 body 签名，攻击者截获后可无限重放。把时间戳纳入签名并限制有效窗口，配合事件 ID 去重，可防重放；同时要求双方时钟大致同步。

Webhook 丢了怎么办？

除依赖提供方重试外，应定期调用对方查询 API 对账补齐遗漏；关键业务在用户操作后也可主动查询最新状态，不把推送当作唯一来源。
