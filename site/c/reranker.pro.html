重排序模型 (Reranker)

Reranker

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

重排序模型（Reranker）是检索流程中的第二阶段精排组件：对第一阶段（向量检索、BM25 等）召回的候选文档，逐一与查询联合编码并计算相关性分数，再按分数重新排序，只保留前若干条交给大模型。它通常采用交叉编码器（Cross-Encoder），准确率明显高于双塔检索，但计算成本更高，因此只用于小规模候选集。

⚙️ 02 · 原理
  1. 1

    第一阶段用双编码器或 BM25 快速召回较多候选（如几十到上百条），优先保证召回率。

  2. 2

    重排模型把“查询 + 候选文档”拼成一个输入，经 Transformer 让两者的 token 充分交互，输出一个相关性分数。

  3. 3

    对所有候选打分后降序排列，可配合阈值过滤掉低相关文档。

  4. 4

    取前 K 条（常见 3–10 条）放入大模型上下文，减少噪声与 token 消耗。

  5. 5

    可选用开源模型本地部署（如 BGE、Jina 系列）或托管 API（如 Cohere Rerank），按延迟与成本选择。

🔤 03 · 术语
交叉编码器 (Cross-Encoder)
查询与文档拼接后共同编码，直接输出相关性分数。
双编码器 (Bi-Encoder)
查询与文档分别编码成向量再比相似度，可预先建索引。
两阶段检索 (Retrieve-then-Rerank)
先快速召回，再精排的检索架构。
召回率 (Recall@K)
相关文档出现在前 K 个结果中的比例。
nDCG
考虑排名位置的排序质量指标，越靠前的相关结果权重越高。
💻 04 · 代码
用 Cross-Encoder 重排候选python
from sentence_transformers import CrossEncoder

# 开源英文重排模型；中文可选 BAAI/bge-reranker 系列（以模型卡为准）
model = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")

query = "How do I get a refund for return shipping?"
candidates = [  # 第一阶段召回的候选（实际可能有几十条）
    "Orders ship within 2 business days.",
    "Return shipping is refunded if the item is defective.",
    "You can track your package in the app.",
    "Refunds are issued to the original payment method.",
]

scores = model.predict([(query, doc) for doc in candidates])
ranked = sorted(zip(candidates, scores), key=lambda x: x[1], reverse=True)

TOP_K = 2
for doc, s in ranked[:TOP_K]:          # 只把前 K 条交给大模型
    print(f"{s:.2f}  {doc}")

交叉编码器对每个“查询-文档”对打分；候选越多越慢，所以只在召回之后使用。

📊 05 · 参数对比

双编码器 vs 交叉编码器

维度双编码器（检索）交叉编码器（重排）
计算方式分别编码，向量相似度拼接联合编码
能否预建索引能不能，需实时计算
适用规模百万级文档几十到上百条候选
准确度较好通常更高
延迟毫秒级（有索引）随候选数线性增长
⚖️ 06 · 方案取舍

不加重排

优点架构简单、延迟最低

代价排序噪声大，易答非所问

适用原型或数据量很小

开源重排模型自部署

优点数据不出域，单次成本低

代价需要 GPU/CPU 资源与运维

适用有隐私要求、调用量大

托管重排 API

优点接入快、效果稳定

代价按调用付费，数据需外发

适用快速上线、调用量中等

🕳️ 07 · 常见坑

  • ✗召回数量太少（如只取 5 条）再重排

    ✓召回阶段多取一些（几十条），给重排留选择空间

  • ✗对全库文档跑交叉编码器

    ✓只对召回候选重排，全库检索用双编码器或 BM25

  • ✗中文场景用纯英文重排模型

    ✓选择支持中文或多语言的重排模型并做评测

  • ✗没有评测集就判断“加了重排更好”

    ✓用标注问答对比较 Recall@K、nDCG 和最终答案准确率

☑️ 08 · 检查清单
🎤 09 · 面试追问
为什么不直接用交叉编码器做检索？

交叉编码器必须把查询和每个文档一起计算，无法预先离线编码建索引；对百万文档逐一打分延迟和成本都不可接受。因此用双编码器或 BM25 先召回小候选集，再用交叉编码器精排，兼顾速度和精度。

重排模型如何影响 RAG 的整体效果？

它提升送入上下文的文档质量：相关内容排到前面，无关内容被过滤，减少大模型被干扰和“中段遗忘”的概率，同时降低 token 成本。但它无法补救召回阶段漏掉的文档，召回率仍是上限。

怎样选择召回数和重排后的 K？

召回数越大，越不易漏掉相关文档，但重排延迟线性增加；K 越大，上下文越完整，但噪声和成本上升。应在评测集上网格搜索，在可接受延迟内找最优组合。
