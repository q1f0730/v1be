批量赋值漏洞

Mass Assignment

🧸 回到小白版

📐 01 · 定义

批量赋值漏洞（Mass Assignment，CWE-915）指框架把请求字段自动绑定到数据模型时未限制可写字段，攻击者额外提交 role、is_admin 等敏感属性即可改写它们。OWASP API Security Top 10（2023）将其归入 API3「对象属性级授权失效」。根因是信任客户端提交的整个对象。

⚙️ 02 · 原理
  1. 1

    接口把请求 JSON 直接展开到模型，例如 User(**body) 或 user.update(body)。

  2. 2

    正常客户端只发送 name、avatar 等字段，界面上看不到敏感字段。

  3. 3

    攻击者通过抓包或阅读前端代码、文档猜测字段名，额外加入 is_admin: true。

  4. 4

    框架把所有名称匹配的字段写入数据库，权限、余额或资源归属因此被篡改。

  5. 5

    防御核心是为每个接口定义显式的可写字段白名单（DTO / Schema），其余拒绝或忽略。

🔤 03 · 术语
CWE-915
对动态确定的对象属性修改控制不当。
DTO (Data Transfer Object)
专为接口输入输出定义的数据结构。
强参数 (Strong Parameters)
Rails 中用 permit 声明允许字段的机制。
BOPLA
对象属性级授权失效，OWASP API3:2023。
过度数据暴露
响应返回了不该给客户端的字段，与批量赋值同属 BOPLA。
💻 04 · 代码
用 Pydantic 限定可写字段python
from fastapi import FastAPI, Depends
from pydantic import BaseModel, ConfigDict, Field

app = FastAPI()

class UserUpdate(BaseModel):
    model_config = ConfigDict(extra="forbid")   # 多余字段直接 422
    name: str | None = Field(default=None, max_length=50)
    avatar_url: str | None = None
    # 不包含 role、is_admin、balance 等字段

class AdminUserUpdate(UserUpdate):
    role: str | None = None                      # 仅管理员接口可改

def current_user():
    ...  # 从会话或 token 取当前用户（省略）

@app.patch("/me")
def update_me(body: UserUpdate, user=Depends(current_user)):
    changes = body.model_dump(exclude_unset=True)  # 只取客户端实际提交的字段
    for k, v in changes.items():
        setattr(user, k, v)
    # db.commit()
    return {"updated": list(changes)}

按接口定义输入模型，extra=forbid 拒绝多余字段；管理员可改字段放在独立模型。

⚖️ 06 · 方案取舍

白名单输入模型

优点明确、可审查，最安全

代价每个接口要写模型

适用默认推荐

黑名单排除敏感字段

优点写法少

代价新增敏感字段时容易漏

适用不推荐

多余字段静默忽略

优点兼容旧客户端

代价攻击尝试不可见

适用过渡期，并记录日志

🕳️ 07 · 常见坑

  • ✗直接用 ORM 模型作为请求体类型

    ✓接口输入使用独立的 DTO，与数据库模型分离

  • ✗前端隐藏了字段就以为用户改不了

    ✓服务端白名单才是边界，前端隐藏不构成防护

  • ✗嵌套对象未校验，通过关联字段修改 owner_id

    ✓嵌套结构也逐层定义可写字段

  • ✗AI 生成的 CRUD 代码直接 update(**body)

    ✓审查生成代码，要求按接口定义输入模型

🎤 09 · 面试追问
为什么白名单优于黑名单？

黑名单要求列出所有敏感字段，模型新增字段（如 credit_limit）时很容易忘记同步，默认就是可写的。白名单默认拒绝，只有明确允许的字段可写，新增字段不会自动暴露。

批量赋值和越权访问有什么区别？

越权访问（BOLA）是能操作不属于自己的对象，例如改别人的订单；批量赋值是在自己有权操作的对象上，修改了不应允许修改的属性，例如把自己的角色改成管理员。两者需要分别防护。

如何在代码审查中发现这类问题？

搜索直接把请求体展开到模型或 update 的写法，检查序列化器是否使用全部字段，确认输入模型不含权限、金额、归属、状态等敏感字段，并补充提交这些字段的负向测试。
