CI 工作负载身份联邦 (OIDC)

CI Workload Identity Federation

📐 01 · 定义

CI 工作负载身份联邦是让 CI/CD 任务用平台签发的短期 OIDC 身份令牌，向云厂商换取临时访问凭证的机制，从而不再在 CI 中保存长期云密钥。GitHub Actions、GitLab CI 等充当 OIDC 身份提供方，AWS IAM、Google Cloud Workload Identity Federation、Azure 联合凭证负责校验令牌声明并授予最小权限。

⚙️ 02 · 原理
  1. 1

    在云账号中登记 CI 平台为可信的 OIDC 身份提供方，如 GitHub 的签发者 https://token.actions.githubusercontent.com。

  2. 2

    创建角色或服务账号，信任策略中限定令牌的受众（aud）与主体（sub），如只允许某仓库的 main 分支或某个环境。

  3. 3

    任务运行时向 CI 平台请求 OIDC 令牌（GitHub 需要 id-token: write 权限），令牌包含仓库、分支、工作流等声明。

  4. 4

    任务用令牌调用云的安全令牌服务换取临时凭证，凭证有效期短，过期自动失效。

  5. 5

    云侧审计日志记录每次换取所对应的仓库与运行信息，便于溯源。

🔤 03 · 术语
OIDC 令牌 (ID Token)
由身份提供方签名的 JWT，声明了调用者身份与上下文。
sub 声明
令牌主体，GitHub 中形如 repo:org/repo:ref:refs/heads/main，是信任条件核心。
aud 声明
令牌受众，指明令牌给谁使用，如 sts.amazonaws.com。
AssumeRoleWithWebIdentity
AWS STS 用外部 OIDC 令牌换取临时凭证的接口。
工作负载身份池 (Workload Identity Pool)
Google Cloud 中管理外部身份映射的资源。
💻 04 · 代码
AWS 角色信任策略json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
          "token.actions.githubusercontent.com:sub": "repo:acme/web:ref:refs/heads/main"
        }
      }
    }
  ]
}

工作流需声明 permissions: id-token: write，并用 aws-actions/configure-aws-credentials 指定 role-to-assume；sub 条件务必精确到仓库与分支或环境。

CI 访问云的凭证方式

方式凭证寿命泄露影响轮换
长期访问密钥存为 CI Secret长期可被长期滥用需手动轮换

⚖️ 06 · 方案取舍

OIDC 联邦

优点无需存储密钥，按仓库/分支精细授权

代价初次配置信任策略较繁琐

适用云厂商与 CI 平台都支持时的首选

自托管 Runner 实例角色

优点配置简单

代价难以区分不同仓库与任务的权限

适用单一用途、隔离良好的 Runner

长期密钥

优点任何平台都可用

代价泄露风险高、审计困难

适用仅限无法联邦的遗留系统，并严格轮换

🕳️ 07 · 常见坑

  • ✗信任策略的 sub 用通配符 repo:acme/*

    ✓精确限定仓库与分支或环境，不同用途使用不同角色

  • ✗未校验 aud，令牌可被其他受众复用

    ✓在条件中同时校验 aud 与 sub

  • ✗拉取请求工作流也能换取生产部署凭证

    ✓生产角色只信任受保护分支或带审批的环境

  • ✗迁移到 OIDC 后忘记删除旧长期密钥

    ✓迁移完成后吊销并删除旧密钥，扫描仓库与 CI 变量

🎤 09 · 面试追问
OIDC 联邦为什么比在 CI 存密钥安全？

长期密钥一旦从日志、依赖或被入侵的工作流中泄露，攻击者可在任意地点长期使用。OIDC 令牌由 CI 平台为单次运行签发并绑定仓库、分支等声明，换得的云凭证很快过期；云侧还可按声明精确限权，并完整审计每次使用。

信任策略中 sub 条件为什么关键？

同一个 OIDC 提供方为平台上所有仓库签发令牌。若只校验签发者与受众，任何人的仓库都可能换取你的角色。sub 声明区分组织、仓库、分支、环境或拉取请求，必须精确匹配，才能确保只有受信的工作流获得权限。

拉取请求触发的工作流有什么额外风险？

外部贡献者的代码会在 CI 中运行，可能窃取令牌或凭证。应只让受保护分支或需审批的部署环境换取高权限角色，拉取请求工作流仅授予只读或无云权限，并谨慎使用会以目标仓库权限运行的触发器。
