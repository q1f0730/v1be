主节点选举机制

Leader Election

🧸 回到小白版

📐 01 · 定义

主节点选举（Leader Election）是让一组同质实例中在同一时刻只有一个成为领导者、负责执行特定工作（如调度任务、写入、协调）的机制，领导者故障后自动选出新的。通常借助共识存储（etcd、ZooKeeper）或 Kubernetes Lease 上的租约实现，关键难点是避免同时出现两个领导者。

⚙️ 02 · 原理
  1. 1

    竞选：实例尝试在共享存储中创建或更新一个租约/锁记录，写入自己的身份。

  2. 2

    当选：成功获得记录的实例成为领导者，开始执行只允许单实例做的工作。

  3. 3

    续约：领导者在租约到期前定期续约；其他实例则持续观察该记录。

  4. 4

    失效转移：领导者崩溃或失联导致租约过期，其他实例抢占记录成为新领导者。

  5. 5

    防护：旧领导者恢复后需检测已失去领导权，并配合递增的防护令牌拒绝其写入。

🔤 03 · 术语
租约 (Lease)
带有效期的所有权声明，需定期续约，过期自动失效。
防护令牌 (Fencing Token)
每次换主递增的编号，下游拒绝更旧编号的请求。
僵尸领导者 (Zombie Leader)
已失去领导权却不自知、仍在执行操作的旧实例。
Kubernetes Lease
coordination.k8s.io 中用于选主和心跳的轻量 API 对象。
临时节点 (Ephemeral Node)
ZooKeeper 中随会话结束自动删除的节点，常用于选主。
💻 04 · 代码
K8s Lease 选主记录yaml
# 控制器类组件（如 kube-controller-manager）用 Lease 选主
# 查看：kubectl get lease -n kube-system
apiVersion: coordination.k8s.io/v1
kind: Lease
metadata:
  name: my-operator-leader
  namespace: ops
spec:
  holderIdentity: my-operator-7d9f-abcde   # 当前领导者的身份
  leaseDurationSeconds: 15                 # 超过此时长未续约即可被抢占
  acquireTime: "2026-10-20T08:00:00.000000Z"
  renewTime: "2026-10-20T08:05:12.000000Z" # 领导者定期更新
  leaseTransitions: 3                      # 领导者变更次数

通常由 client-go 的 leaderelection 等库自动维护，示例展示其状态字段。

⚖️ 06 · 方案取舍

单领导者+热备

优点逻辑简单，避免重复执行

代价故障转移有租约时长的空窗

适用定时任务、控制器、调度器

按分片多领导者

优点负载分散，故障影响小

代价分片分配与再平衡更复杂

适用任务量大需要水平扩展

无领导者+幂等

优点无选举，扩展性好

代价需要任务可安全重复执行

适用任务天然幂等

🕳️ 07 · 常见坑

  • ✗GC 停顿后旧领导者继续写入，与新领导者冲突

    ✓每次操作前检查租约，并在下游使用防护令牌拒绝旧写入

  • ✗租约时长设得过短，网络抖动导致频繁换主

    ✓根据续约间隔和网络状况设定，续约周期显著短于租约

  • ✗用 Redis 单节点 SETNX 当可靠选主

    ✓关键场景使用基于共识的存储，并结合防护令牌

🎤 09 · 面试追问
选主机制如何避免同时有两个领导者？

仅靠租约无法完全避免：旧领导者可能因停顿而不知租约已过期。需要两层保障：选主依赖线性一致存储保证同一时刻只授予一个租约；下游资源校验单调递增的防护令牌，拒绝旧领导者的写入。

Kubernetes 控制器为什么需要选主？

控制器通常多副本部署以保证可用，但调和逻辑若多副本同时执行会重复操作或冲突。通过 Lease 选主，只有领导者执行调和，其他副本待命，领导者故障时在租约过期后接管。

租约时长怎么定？

租约越短，故障转移越快，但网络抖动或停顿更易误判导致换主；越长则故障空窗越久。一般续约间隔为租约的几分之一，并留出重试余量，再按业务可容忍的中断时间折中。
