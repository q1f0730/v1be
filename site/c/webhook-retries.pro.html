Webhook异步回调重试

Webhook Retries

📐 01 · 定义

Webhook 重试（Webhook Retries）是事件提供方在 HTTP 回调失败时自动重新发送的机制。它属于跨系统集成的可靠性层：接收方返回非 2xx、超时或连接失败时，提供方按退避策略在一段时间内多次重投。由此接收方面对的是至少一次投递，必须做签名校验、快速响应和按事件 ID 去重。

⚙️ 02 · 原理
  1. 1

    业务事件发生后，提供方向接收方登记的 URL 发起 HTTPS POST，带上事件体和签名头。

  2. 2

    接收方应在数秒内返回 2xx；超时、5xx 或连接错误会被提供方视为失败。

  3. 3

    提供方按指数退避加抖动安排下一次投递，持续数小时到数天，具体周期由各平台决定。

  4. 4

    多次失败后，部分平台会告警、禁用端点或标记失败，并提供手动重发入口。

  5. 5

    接收方验证签名，按事件 ID 去重，入队后立即返回 200，耗时处理放到后台。

🔤 03 · 术语
签名校验 (Signature Verification)
用共享密钥对请求体做 HMAC，确认请求来自真实提供方且未被篡改。
事件 ID (Event ID)
提供方给每个事件的唯一标识，重试时保持不变，是去重依据。
重放攻击 (Replay Attack)
攻击者重发截获的合法请求，常用时间戳容差加去重防御。
指数退避 (Exponential Backoff)
每次重试间隔按倍数增长，避免持续冲击故障端点。
Standard Webhooks
一份开放的 webhook 签名与投递规范，统一了头字段和签名格式。
💻 04 · 代码
Stripe Webhook 接收端python
import stripe
from flask import Flask, request

app = Flask(__name__)
ENDPOINT_SECRET = "whsec_..."  # 从 Stripe 控制台获取
seen = set()  # 示意；生产中用数据库唯一约束

@app.post("/webhooks/stripe")
def stripe_webhook():
    payload = request.get_data()
    sig = request.headers.get("Stripe-Signature")
    try:
        event = stripe.Webhook.construct_event(payload, sig, ENDPOINT_SECRET)
    except (ValueError, stripe.error.SignatureVerificationError):
        return "bad signature", 400   # 4xx：不要让对方重试伪造请求

    if event["id"] in seen:          # 重试带来的重复事件
        return "", 200
    seen.add(event["id"])
    enqueue_job(event)               # 耗时逻辑丢给后台队列
    return "", 200                    # 尽快返回 2xx

先验签、再按 event.id 去重、入队后立刻返回 200，适配提供方的重试。

📊 05 · 参数对比

主流平台的重试行为

平台失败判定重试方式（以官方文档为准）
Stripe非 2xx 或超时线上模式最长约 3 天指数退避
GitHub非 2xx 或超时不自动重试，可手动重发
自建发送端自定义指数退避加抖动，设总时限并记录日志

🕳️ 07 · 常见坑

  • ✗在 webhook 里同步调用多个外部服务，超时后被重复投递。

    ✓只做验签和入队，几秒内返回 2xx。

  • ✗用解析后的 JSON 重新序列化去验签，签名总对不上。

    ✓用原始请求体字节验签，框架里读 raw body。

  • ✗验签失败返回 500，伪造请求被提供方反复重试。

    ✓签名或格式错误返回 4xx，只有临时故障才返回 5xx。

  • ✗假设事件按发生顺序到达。

    ✓以事件内时间戳或重新查询资源最新状态为准。

🎤 09 · 面试追问
Webhook 接收端应该返回什么状态码？

成功入队就返回 2xx；签名错误、请求格式不对返回 4xx，表示重试无意义；依赖暂时不可用才返回 5xx，让提供方重试。注意部分平台对 4xx 也会重试，需看各自文档。

如何设计一个可靠的 webhook 发送端？

事件先持久化到 outbox；按指数退避加抖动重试并设总时限；每次带相同事件 ID 和签名；记录投递日志供用户查看；连续失败告警并可禁用端点；提供手动重发和事件查询 API 作补偿。

怎样防止 webhook 重放攻击？

签名中包含时间戳，接收端拒绝超过容差窗口（如几分钟）的请求；同时按事件 ID 去重，窗口内重复的直接忽略；全程 HTTPS，密钥定期轮换。
