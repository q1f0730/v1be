备份恢复演练

Testing Your Restores

🧸 回到小白版

📐 01 · 定义

恢复演练（Restore Testing）是定期把备份真正恢复到独立环境，并验证数据完整性、可用性与恢复耗时的实践。备份任务显示“成功”只证明写出了文件，不证明能恢复。只有演练才能确认实际可达的 RPO（最多丢多少数据）和 RTO（多久恢复服务）。

⚙️ 02 · 原理
  1. 1

    自动选取最新（或随机历史）备份，从异地存储下载到隔离环境。

  2. 2

    在临时实例上执行完整恢复流程，与真实事故时使用的步骤一致。

  3. 3

    校验数据：行数、关键表最近记录时间、校验和，以及应用的冒烟测试。

  4. 4

    记录恢复耗时与最新数据时间点，对比 RTO/RPO 目标。

  5. 5

    清理临时环境，任一步失败即告警；演练结果与发现的问题回写到运维手册。

🔤 03 · 术语
RPO (Recovery Point Objective)
可容忍丢失的最大数据时间窗口。
RTO (Recovery Time Objective)
从故障到恢复服务的最长可接受时间。
3-2-1 原则
至少 3 份数据、2 种介质、1 份异地。
不可变备份 (Immutable Backup)
写入后在保留期内不可修改或删除，防勒索。
逻辑备份 / 物理备份
导出 SQL 或数据，与拷贝数据文件的两种方式。
💻 04 · 代码
每日自动恢复演练bash
#!/usr/bin/env bash
set -euo pipefail
BUCKET=s3://my-backups/pg
HOST=restore-test.internal   # 隔离的临时实例
DB=restore_check

# 1. 取最新的备份文件（pg_dump -Fc 生成的自定义格式）
LATEST=$(aws s3 ls "$BUCKET/" | sort | tail -n 1 | awk '{print $4}')
aws s3 cp "$BUCKET/$LATEST" /tmp/latest.dump

# 2. 恢复并计时
dropdb -h "$HOST" --if-exists "$DB"
createdb -h "$HOST" "$DB"
START=$(date +%s)
pg_restore -h "$HOST" -d "$DB" --no-owner -j 4 /tmp/latest.dump
echo "restore took $(( $(date +%s) - START ))s"

# 3. 校验：最近一天应当有订单，否则视为备份异常
COUNT=$(psql -h "$HOST" -d "$DB" -Atc \
  "SELECT count(*) FROM orders WHERE created_at > now() - interval '1 day'")
[ "$COUNT" -gt 0 ] || { echo "FAIL: no recent orders in backup"; exit 1; }
echo "OK: $COUNT recent orders"

真实执行恢复并校验业务数据新鲜度；退出码非 0 即接入告警。

📊 05 · 参数对比

恢复演练分级

级别内容建议频率
自动校验备份可下载、可解析、校验和正确每次备份后
自动恢复恢复到临时实例并跑数据断言每日或每周
应用级演练应用连接恢复库跑冒烟测试每月
灾难演练按手册切换整套环境、计时每季度或半年
⚖️ 06 · 方案取舍

全自动定期恢复

优点持续验证，问题早发现

代价占用计算与存储成本

适用核心数据库默认要做

抽样手工演练

优点能验证人和流程

代价频率低，依赖个人

适用配合自动化做年度演练

只监控备份任务成功

优点几乎零成本

代价无法发现不可恢复的备份

适用不应作为唯一手段

🕳️ 07 · 常见坑

  • ✗备份脚本报成功，但文件是空的或被截断

    ✓每次备份后校验大小、校验和并抽样恢复

  • ✗演练只恢复了数据库，忘了密钥、配置和对象存储

    ✓列出完整恢复依赖清单并一并演练

  • ✗备份与生产在同一账号，被同一次误操作删除

    ✓异地、跨账号、不可变存储

  • ✗从未计时，RTO 只是纸面数字

    ✓每次演练记录实际耗时并更新目标

☑️ 08 · 检查清单
🎤 09 · 面试追问
为什么说没测过的备份等于没有备份？

备份可能因权限、磁盘满、版本不兼容、加密密钥丢失、脚本静默失败而不可用，这些只有恢复时才暴露。2017 年 GitLab 数据库事故中，多种备份机制被发现未正常工作，就是典型案例。

如何定义 RPO 和 RTO？

与业务一起定：RPO 看能接受丢多少数据，决定备份频率与是否需要 WAL 归档/PITR；RTO 看能停多久，决定恢复方式（快照、热备、多活）。目标必须经演练验证，而非估算。

演练中除了数据库还要验证什么？

加密密钥与 KMS 权限、配置与密钥管理、对象存储文件、DNS 与连接串切换、依赖服务、监控告警，以及人员是否熟悉手册。很多恢复失败是因为数据之外的依赖缺失。
