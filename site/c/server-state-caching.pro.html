服务端状态缓存 (TanStack Query / SWR)

Server State Caching

📐 01 · 定义

服务端状态缓存指在前端用专门的库管理「来自服务器的数据」：缓存响应、请求去重、后台重新获取、过期判断、变更后失效。它属于前端数据层，与 UI 本地状态不同——服务端状态由远端拥有、可能被他人修改、随时可能过期。TanStack Query 与 SWR 是代表实现，核心思想是 stale-while-revalidate。

⚙️ 02 · 原理
  1. 1

    每个查询由唯一的查询键（queryKey）标识，相同键的组件共享一份缓存与一次进行中的请求。

  2. 2

    数据在 staleTime 内视为新鲜，直接使用缓存；超过后变为过期，但仍先展示旧数据。

  3. 3

    过期数据在组件挂载、窗口重新聚焦、网络重连或定时轮询时触发后台重新获取。

  4. 4

    没有组件使用的查询在 gcTime（v4 前称 cacheTime）后被垃圾回收。

  5. 5

    变更（mutation）成功后通过 invalidateQueries 让相关查询失效并重新获取，或直接写入缓存。

🔤 03 · 术语
查询键 (Query Key)
唯一标识一份服务端数据的数组键，参数变化即为新缓存。
staleTime
数据保持新鲜的时长，期间不会自动重新获取。TanStack Query 默认 0。
gcTime
无订阅者的缓存保留时长，TanStack Query 默认 5 分钟。
请求去重 (Deduplication)
同一键的并发请求合并为一次网络请求。
失效 (Invalidation)
把缓存标记为过期并触发重新获取。
💻 04 · 代码
TanStack Query 查询与失效typescript
import { useQuery, useMutation, useQueryClient } from "@tanstack/react-query";

function useTodos() {
  return useQuery({
    queryKey: ["todos"],
    queryFn: () => fetch("/api/todos").then(r => r.json()),
    staleTime: 30_000,   // 30 秒内视为新鲜，多组件共享不重复请求
  });
}

function useAddTodo() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: (title: string) =>
      fetch("/api/todos", { method: "POST", body: JSON.stringify({ title }) }),
    // 写入成功后让列表失效，自动重新获取
    onSuccess: () => qc.invalidateQueries({ queryKey: ["todos"] }),
  });
}

// 组件中：const { data, isPending, error } = useTodos();

多个组件调用 useTodos 只发一次请求；新增后失效列表即可刷新，无需手动管理。

📊 05 · 参数对比

服务端状态 vs 客户端状态

维度服务端状态客户端状态
归属远端数据库/API当前浏览器
是否会过期会，可能被他人修改不会自行变化
典型数据用户资料、订单列表弹窗开关、表单输入
推荐工具TanStack Query、SWRuseState、Zustand
⚖️ 06 · 方案取舍

TanStack Query

优点功能全：变更、分页、无限加载、DevTools

代价概念较多，包体略大

适用数据交互复杂的应用

SWR

优点API 简洁、轻量

代价复杂变更与缓存操作需自行组织

适用以读取为主的应用

全局状态库手动管理

优点完全掌控

代价需自写去重、过期、重试，易出错

适用极简场景或特殊需求

框架内置数据获取（RSC/loader）

优点服务端获取，减少客户端 JS

代价客户端交互后的缓存同步需另行处理

适用Next.js/Remix 等全栈框架

🕳️ 07 · 常见坑

  • ✗把服务端数据复制进 Redux/Zustand 再手动同步

    ✓服务端数据交给查询缓存，全局状态只放 UI 状态

  • ✗查询键没包含所有参数，不同筛选条件共用缓存

    ✓把影响结果的参数都放进 queryKey

  • ✗staleTime 保持默认 0，挂载和聚焦时频繁重新获取

    ✓根据数据变化频率设置合理的 staleTime

  • ✗变更后忘记失效相关查询，列表显示旧数据

    ✓在 onSuccess/onSettled 中失效所有相关键

🎤 09 · 面试追问
staleTime 和 gcTime 的区别？

staleTime 决定数据多久后变为过期、需要后台刷新；gcTime 决定没有组件使用时缓存还保留多久才删除。数据可以过期但仍在缓存中，用于先展示再刷新。

为什么不建议把服务端数据放进 Redux？

服务端数据需要去重、过期、重试、后台刷新、失效等能力，手写易出错且代码冗长；专门的查询缓存库内置这些能力，Redux 更适合纯客户端状态。

SSR 场景下如何避免客户端重复请求？

在服务端预取数据填充 QueryClient，将缓存脱水（dehydrate）随 HTML 下发，客户端水合（HydrationBoundary）后直接使用，并设置大于 0 的 staleTime 防止挂载即重新获取。
