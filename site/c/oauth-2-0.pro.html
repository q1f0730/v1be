开放授权框架

OAuth 2.0

📐 01 · 定义

OAuth 2.0 是 RFC 6749 定义的授权框架，让用户在不交出密码的前提下，授权第三方应用以受限范围（scope）访问其在另一服务上的资源。它定义了资源所有者、客户端、授权服务器、资源服务器四种角色和多种授权流程。它本身不是认证协议，登录场景应使用其上的 OpenID Connect。

⚙️ 02 · 原理
  1. 1

    客户端把用户重定向到授权服务器，携带 client_id、redirect_uri、scope、state 和 PKCE 的 code_challenge。

  2. 2

    用户在授权服务器登录并同意授权，授权服务器带着一次性授权码重定向回 redirect_uri。

  3. 3

    客户端校验 state 后，用授权码和 code_verifier（机密客户端另加凭证）向令牌端点换取访问令牌。

  4. 4

    客户端携带访问令牌调用资源服务器，资源服务器校验令牌及其 scope 后返回数据。

  5. 5

    访问令牌过期后，客户端用刷新令牌换取新令牌，无需用户再次授权。

🔤 03 · 术语
授权码流程 (Authorization Code)
用一次性授权码换令牌的主流流程，应配合 PKCE。
PKCE
RFC 7636，用 verifier/challenge 对防止授权码被截获滥用。
Scope
访问令牌被授予的权限范围，如只读邮箱。
state 参数
随机值，用于防止授权回调的 CSRF 攻击。
客户端凭证流程 (Client Credentials)
无用户参与、服务间调用使用的流程。
💻 04 · 代码
授权码 + PKCE 流程http
# 1. 浏览器跳转到授权端点（code_challenge = BASE64URL(SHA256(code_verifier))）
GET /authorize?response_type=code&client_id=my-app
    &redirect_uri=https%3A%2F%2Fapp.example.com%2Fcallback
    &scope=openid%20profile%20email&state=Xy7k2Q
    &code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
    &code_challenge_method=S256 HTTP/1.1
Host: auth.example.com

# 2. 用户同意后，回调到 redirect_uri（客户端需校验 state）
# https://app.example.com/callback?code=SplxlOBeZQQYbYS6WxSbIA&state=Xy7k2Q

# 3. 后端用授权码 + code_verifier 换令牌
POST /token HTTP/1.1
Host: auth.example.com
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&code=SplxlOBeZQQYbYS6WxSbIA
&redirect_uri=https%3A%2F%2Fapp.example.com%2Fcallback
&client_id=my-app&code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk

示例取值来自 RFC 7636 与 RFC 6749 附录；URL 中换行仅为排版，实际为单行。

📊 05 · 参数对比

授权流程选择

流程适用客户端状态
授权码 + PKCEWeb、SPA、移动端推荐
客户端凭证服务对服务推荐（无用户场景）
设备授权电视、CLI 等输入受限设备推荐（RFC 8628）
隐式流程/密码流程历史方案安全最佳实践不再推荐
⚖️ 06 · 方案取舍

接入现成身份提供商

优点安全实现成熟，省时

代价依赖第三方与费用

适用绝大多数应用

自建授权服务器

优点完全可控

代价实现复杂、易出安全漏洞

适用平台型产品，需对外开放 API

BFF 模式处理令牌

优点浏览器不接触令牌

代价需要服务端组件

适用安全要求高的 SPA

🕳️ 07 · 常见坑

  • ✗用 OAuth 访问令牌判断“用户是谁”

    ✓登录使用 OpenID Connect，校验 ID Token 的 iss、aud

  • ✗redirect_uri 使用通配符或前缀匹配

    ✓授权服务器精确匹配预注册的回调地址

  • ✗不校验 state，或公共客户端不用 PKCE

    ✓始终使用 PKCE，并校验 state

  • ✗申请远超需要的 scope

    ✓按最小权限申请，按需增量授权

🎤 09 · 面试追问
OAuth 2.0 和 OpenID Connect 的区别？

OAuth 2.0 解决授权：客户端获得访问某资源的令牌，令牌不保证能说明用户身份。OIDC 在 OAuth 2.0 之上增加 ID Token（JWT）、标准声明和 UserInfo 端点，专门解决认证，告诉客户端是谁、何时、如何登录。

PKCE 解决了什么问题？

公共客户端（移动应用、SPA）无法安全保存 client_secret，授权码在回调时可能被恶意应用或日志截获。PKCE 让客户端先发送 verifier 的哈希，换令牌时提交原始 verifier，截获授权码的攻击者没有 verifier 就无法换取令牌。

为什么隐式流程被弃用？

隐式流程把访问令牌直接放在重定向 URL 的片段中返回，可能通过浏览器历史、Referer、恶意脚本泄露，且无法使用刷新令牌和发送者约束。随着浏览器普遍支持 CORS，授权码 + PKCE 可以安全替代它。
