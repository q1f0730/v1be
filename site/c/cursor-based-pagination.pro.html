基于游标的分页

Cursor-Based Pagination

📐 01 · 定义

基于游标的分页（Cursor / Keyset Pagination）用上一页最后一条记录的排序键作为下一页的起点，以 WHERE 键 > 游标 代替 OFFSET 跳过行。它位于 API 与查询设计层，解决深分页越翻越慢、数据插入删除导致的重复或漏项问题，是信息流与大列表接口的主流方案。

⚙️ 02 · 原理
  1. 1

    确定稳定且唯一的排序键，常用 (created_at, id) 组合，id 用于打破时间相同的并列。

  2. 2

    首页按排序键取 limit+1 条，多取的一条用于判断是否还有下一页。

  3. 3

    把最后一条的排序键编码（常见 base64 JSON）为不透明游标，随响应返回给客户端。

  4. 4

    下一页请求携带游标，服务端解码后执行 WHERE (created_at, id) < (?, ?) ORDER BY … LIMIT。

  5. 5

    配合与排序键一致的复合索引，每页只扫描所需行，耗时与页码深度无关。

🔤 03 · 术语
键集分页 (Keyset Pagination)
用排序键比较而非偏移量定位下一页。
不透明游标 (Opaque Cursor)
客户端不解析、只原样回传的分页令牌。
行值比较 (Row Value Comparison)
(a,b) < (x,y) 形式的多列字典序比较。
并列打破 (Tie-breaker)
在非唯一排序键后追加唯一列保证顺序确定。
深分页 (Deep Pagination)
OFFSET 很大时需扫描并丢弃大量行的性能问题。
💻 04 · 代码
游标编码与查询python
import base64, json

def encode_cursor(row):
    data = {"t": row["created_at"].isoformat(), "id": row["id"]}
    return base64.urlsafe_b64encode(json.dumps(data).encode()).decode()

def decode_cursor(cursor):
    return json.loads(base64.urlsafe_b64decode(cursor.encode()))

SQL_FIRST = """SELECT id, created_at, title FROM posts
  ORDER BY created_at DESC, id DESC LIMIT %(n)s"""
SQL_NEXT = """SELECT id, created_at, title FROM posts
  WHERE (created_at, id) < (%(t)s, %(id)s)   -- 行值比较
  ORDER BY created_at DESC, id DESC LIMIT %(n)s"""

def list_posts(cur, limit=20, cursor=None):
    params = {"n": limit + 1}               # 多取一条判断 has_more
    if cursor:
        params.update(decode_cursor(cursor))
    cur.execute(SQL_NEXT if cursor else SQL_FIRST, params)
    rows = cur.fetchall()                   # 假设使用 dict_row 行工厂
    has_more = len(rows) > limit
    rows = rows[:limit]
    nxt = encode_cursor(rows[-1]) if has_more else None
    return {"data": rows, "next_cursor": nxt}
# 需要索引：CREATE INDEX ON posts (created_at DESC, id DESC);

排序键加 id 保证唯一；limit+1 判断是否有下一页；索引顺序须与 ORDER BY 一致。

⚖️ 06 · 方案取舍

OFFSET 分页

优点实现简单，可直接跳到第 N 页

代价深页慢，并发写入导致错位

适用后台管理、数据量小

游标分页

优点性能稳定，无重复漏项

代价不能跳页，排序字段受限

适用信息流、无限滚动、公开 API

游标 + 近似总数

优点兼顾体验与性能

代价总数不精确，需额外说明

适用需显示大致结果量的列表

🕳️ 07 · 常见坑

  • ✗只按 created_at 排序，时间相同的行被跳过或重复

    ✓追加唯一列 id 作并列打破，游标同时包含两者

  • ✗游标直接暴露原始 SQL 字段且未校验

    ✓游标编码为不透明令牌，解码后校验类型，必要时签名

  • ✗ORDER BY 方向与索引不一致，退化为排序

    ✓按 ORDER BY 列与方向建复合索引并用 EXPLAIN 验证

  • ✗排序字段可被更新，导致记录在页间移动

    ✓选择不可变或很少变化的字段做排序键

☑️ 08 · 检查清单
🎤 09 · 面试追问
为什么 OFFSET 深分页很慢？

数据库必须按序生成并丢弃前 OFFSET 行才能返回结果，扫描量与偏移成正比。即便有索引也要遍历这些索引项。键集分页直接从索引中游标位置开始读取，代价只与页大小有关。

游标分页如何支持多种排序？

每种排序都需要唯一排序键组合和对应索引，游标中记录排序方式与键值，服务端校验游标与当前排序一致。排序维度过多时应限制可选项。

如何实现「上一页」？

反转比较方向与 ORDER BY 查询（如 > 游标 ORDER BY ASC），取到后再在应用层反转结果顺序；也可同时返回 prev_cursor 与 next_cursor。
