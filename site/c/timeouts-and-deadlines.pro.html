超时与截止时间传播

Timeouts & Deadlines

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

超时（Timeout）是单次操作允许等待的最长时间；截止时间（Deadline）是整个请求链路必须完成的绝对时间点，并随调用向下游传播。它们属于分布式系统可靠性层：没有超时的调用会在下游卡住时无限占用线程和连接，逐级堆积成连锁故障；截止时间传播则避免上游已放弃、下游仍在白做工。

⚙️ 02 · 原理
  1. 1

    每次网络调用至少区分连接超时（建立连接）和读取超时（等待响应），也可设置总超时。

  2. 2

    入口服务为请求确定总预算，例如用户可接受的等待时间，换算成绝对截止时间。

  3. 3

    调用下游时把剩余时间传递下去（如 gRPC deadline、自定义请求头），下游据此设置自己的超时。

  4. 4

    每一跳都扣除已用时间；剩余预算不足时直接放弃，不再发起注定超时的调用。

  5. 5

    超时触发后取消进行中的工作（关闭连接、取消上下文），并返回错误或降级结果。

🔤 03 · 术语
连接超时 (Connect Timeout)
建立 TCP/TLS 连接允许的最长时间。
读取超时 (Read Timeout)
两次收到数据之间允许的最长间隔，并非总耗时。
截止时间传播 (Deadline Propagation)
把请求的绝对截止时间沿调用链传给下游。
取消 (Cancellation)
超时后通知下游停止工作，释放资源。
超时预算 (Timeout Budget)
把总时限按调用链分配给各环节。
💻 04 · 代码
requests 超时与剩余预算python
import time, requests

TOTAL_BUDGET = 3.0  # 整个请求最多 3 秒

def handle(user_id: str):
    deadline = time.monotonic() + TOTAL_BUDGET
    profile = call(f"https://users.internal/{user_id}", deadline)
    orders = call(f"https://orders.internal/{user_id}", deadline)
    return profile, orders

def call(url: str, deadline: float):
    remaining = deadline - time.monotonic()
    if remaining <= 0.05:
        raise TimeoutError("budget exhausted")  # 不再发注定超时的请求
    # (连接超时, 读取超时)；读取超时不超过剩余预算
    resp = requests.get(url, timeout=(0.5, remaining),
                        headers={"X-Deadline-Ms": str(int(remaining * 1000))})
    resp.raise_for_status()
    return resp.json()

requests 默认不设超时会一直等；这里用剩余预算限制每一跳并告知下游。

🕳️ 07 · 常见坑

  • ✗只设连接超时，没设读取超时

    ✓两者都设，并对总耗时设上限

  • ✗下游超时比上游还长

    ✓下游超时应小于上游剩余预算

  • ✗超时后不取消下游工作，资源继续被占用

    ✓传递取消信号，数据库查询同样设语句超时

  • ✗超时与重试叠加，总耗时远超用户可接受范围

    ✓重试计入总预算，剩余时间不足即停止

🎤 09 · 面试追问
超时值应该怎么定？

参考依赖的 P99/P99.9 延迟留适当余量，同时不超过上游剩余预算与用户可接受时间。太短误杀正常请求，太长失去保护作用；需结合监控持续调整。

读取超时 5 秒，为什么请求可能跑 1 分钟？

多数库的读取超时是两次收到数据之间的间隔；服务端持续缓慢发送数据，每次间隔都没超时，总时长就会很长。需要另设总超时或截止时间。

gRPC 的 deadline 如何传播？

客户端设置 deadline 后，gRPC 把剩余时间通过 grpc-timeout 元数据传给服务端；服务端的上下文带该截止时间，继续调用下游时使用同一上下文即可自动传播并在到期时取消。
