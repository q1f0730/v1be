先规划后写码 (Plan 模式)

Plan Before Code

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

先规划后写码（Plan Before Code）是在 AI 编码中把“调研与方案”与“执行修改”分成两个阶段的工作方法：先让 Agent 在只读状态下阅读代码、提出实施计划，经人审阅批准后再允许写文件和执行命令。Claude Code 的 Plan 模式即其产品化形态，目的是在成本最低的阶段纠正方向。

⚙️ 02 · 原理
  1. 1

    进入只读规划状态：Agent 可以读文件、搜索代码，但不能编辑文件或执行有副作用的命令。

  2. 2

    Agent 梳理需求、定位相关模块、识别约束，输出包含改动文件、步骤、风险和验证方式的计划。

  3. 3

    人审阅计划，补充遗漏的约束或否决不合适的方案，必要时多轮修订。

  4. 4

    批准后切换到执行模式，Agent 按计划逐步修改，并运行测试或类型检查验证。

  5. 5

    复杂任务可把计划写入文件（如 PLAN.md），作为长任务的外部记忆和进度清单。

🔤 03 · 术语
Plan 模式 (Plan Mode)
Claude Code 的只读权限模式，Agent 只调研和出方案，不改文件。
权限模式 (Permission Mode)
控制 Agent 能否编辑文件、执行命令以及是否需逐次确认。
规格驱动开发 (Spec-Driven Development)
先写需求与设计文档，再让 AI 按规格实现。
验收标准 (Acceptance Criteria)
判断改动完成的可检验条件，如测试通过、接口行为。
爆炸半径 (Blast Radius)
一次改动可能影响的范围，计划中应明确。
💻 04 · 代码
Claude Code 规划再执行bash
# 以 Plan 模式启动：只读调研，不会改文件
claude --permission-mode plan

# 会话中也可按 Shift+Tab 在权限模式间切换

# 非交互方式先生成计划并落盘，便于评审
claude -p --permission-mode plan \
  "为 /api/orders 增加分页。列出要改的文件、步骤、风险和测试方案" \
  > PLAN.md

# 人工审阅、修改 PLAN.md 后，再按计划执行
claude "按 PLAN.md 实施，每完成一步运行 pnpm test"

以官方 CLI 参数演示两阶段流程；具体快捷键与模式名以当前版本文档为准。

📊 05 · 参数对比

好计划应包含

要素内容作用
范围要改和不改的文件控制爆炸半径
步骤有序、可独立验证的小步便于回滚和检查
风险兼容性、数据迁移、性能提前决策
验证具体测试命令与预期定义完成标准
⚖️ 06 · 方案取舍

每个任务都先规划

优点方向错误早发现

代价小改动也多一轮交互

适用跨文件、陌生代码、高风险改动

直接执行

优点快

代价方向错要整体返工

适用单文件小修、明确的机械改动

计划落盘为文档

优点可评审、可接续

代价需维护文档

适用多会话长任务、团队协作

🕳️ 07 · 常见坑

  • ✗计划只扫一眼就批准

    ✓重点审改动范围、数据变更和验证方式

  • ✗计划里没有验证步骤

    ✓要求写出具体测试命令和预期结果

  • ✗执行中偏离计划却不察觉

    ✓让 Agent 每步对照计划汇报，偏离时先停下说明

  • ✗一个计划包揽过大的需求

    ✓拆成多个可独立交付和验证的小计划

☑️ 08 · 检查清单
🎤 09 · 面试追问
为什么 AI 编码要先规划？

Agent 的错误往往源于对需求或代码结构的误解，而非语法。规划阶段只读、成本低，人在这里纠偏最便宜；直接执行则错误被写进多个文件，审查和回滚成本都更高。计划还给出了验收标准，便于判断是否完成。

规划阶段人应该重点审什么？

审范围是否过大、是否触及不该改的模块；审对现有架构和约定的理解是否正确；审数据迁移、接口兼容、安全等不可逆风险；审验证方式是否真实可执行。语法和细节可以交给后续测试和代码审查。

规划和 TDD 能结合吗？

可以。计划中先列出要新增的测试用例作为验收标准，执行阶段让 Agent 先写失败的测试，再实现到通过。这样计划可验证，Agent 也有明确的完成信号，不容易过早宣布完成。
