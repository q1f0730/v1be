开源与许可证

Open Source & License

📐 01 · 定义

开源（Open Source）指源代码公开，并以符合开源定义（OSI 审核）的许可证授权他人使用、修改和再分发。许可证（License）是具有法律效力的授权条款，决定你能否商用、修改后是否必须开源、是否需要保留版权声明和是否获得专利授权。没有许可证的公开代码，默认保留全部版权，并不能自由使用。

⚙️ 02 · 原理
  1. 1

    授权：作者在仓库中放置 LICENSE 文件，并在清单中用 SPDX 标识符声明许可证。

  2. 2

    宽松型许可：MIT、BSD、Apache-2.0 允许闭源商用，主要要求保留版权和许可声明。

  3. 3

    著佐权（Copyleft）：GPL 要求分发衍生作品时以相同许可证提供源代码。

  4. 4

    网络条款：AGPL 把「通过网络向用户提供服务」也视为触发开源义务的情形。

  5. 5

    合规执行：使用方通过许可证扫描识别依赖许可证，按条款保留声明或履行开源义务。

🔤 03 · 术语
OSI
开源促进会，审核许可证是否符合开源定义。
SPDX 标识符
许可证的标准简称，如 MIT、Apache-2.0、GPL-3.0-only。
Copyleft（著佐权）
要求衍生作品沿用相同许可证开放源码的条款。
专利授权 (Patent Grant)
Apache-2.0 等明确授予使用者相关专利许可。
源码可用 (Source-available)
代码公开但限制商用等，不属于 OSI 定义的开源。
💻 04 · 代码
扫描依赖许可证bash
# Node.js：汇总所有依赖的许可证（license-checker 为社区工具）
npx license-checker --summary

# 发现不允许的许可证时让命令失败，可放进 CI
npx license-checker --production --failOn "GPL-3.0;AGPL-3.0"

# Python：列出已安装包的许可证
pip install pip-licenses
pip-licenses --format=markdown --order=license

# 为自己的项目声明许可证（package.json 中使用 SPDX 标识符）
npm pkg set license="MIT"

# 查看仓库许可证（GitHub CLI）
gh repo view --json licenseInfo

上线或交付前扫描依赖许可证，可把强著佐权等风险许可证挡在 CI 阶段。

📊 05 · 参数对比

常见许可证义务对比

许可证闭源商用修改后须开源特别条款
MIT允许否保留版权与许可声明
Apache-2.0允许否明确专利授权，需声明修改
GPL-3.0分发时受限分发衍生作品须开源强著佐权
AGPL-3.0受限通过网络提供服务也须开源覆盖 SaaS 场景
无许可证不允许—默认保留全部版权
⚖️ 06 · 方案取舍

宽松许可（MIT/Apache）

优点利于广泛采用与商用

代价他人可闭源使用而不回馈

适用希望最大化使用的库与工具

强著佐权（GPL/AGPL）

优点保证改进回馈社区

代价企业采用意愿较低

适用希望衍生作品保持开源

源码可用许可

优点公开代码同时保护商业利益

代价不被视为开源，社区接受度低

适用商业公司防止云厂商托管

🕳️ 07 · 常见坑

  • ✗GitHub 上公开的代码就当作可以随便用

    ✓先看 LICENSE，无许可证即不能复制使用

  • ✗SaaS 产品引入 AGPL 组件而未评估义务

    ✓引入前做许可证审查，必要时选替代方案或咨询法务

  • ✗打包分发时删掉了第三方版权声明

    ✓保留依赖的版权与许可声明，可生成第三方声明文件

  • ✗开源自己的项目却不放许可证

    ✓明确选择并添加 LICENSE 文件

🎤 09 · 面试追问
MIT 和 Apache-2.0 怎么选？

两者都宽松、允许闭源商用。Apache-2.0 额外包含明确的专利授权与专利报复条款，并要求标注修改，对企业更有法律确定性；MIT 更短更简单。重视专利保护的项目多选 Apache-2.0。

开源模型的「开源」和软件开源一样吗？

不完全一样。很多模型只开放权重，训练数据和代码未公开，许可证可能限制商用规模或用途。使用前要单独阅读模型许可证（如各家社区许可），确认商用、再分发和衍生模型的条件。

AI 生成的代码有许可证风险吗？

可能有。模型可能复现训练数据中受许可证约束的代码片段。缓解：使用提供代码相似性过滤或知识产权保障的工具设置，对较长的、疑似照搬的代码做检索比对，并保留依赖许可证扫描流程。
