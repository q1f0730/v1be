合并请求 (PR)

Pull Request

📐 01 · 定义

合并请求（Pull Request，PR；GitLab 称 Merge Request）是代码托管平台上的协作流程：开发者请求把一个分支的改动合入目标分支，团队在其中查看 diff、逐行评论、运行自动检查并审批。PR 是代码质量、知识共享和变更审计的关口，也是 AI Agent 产出进入主干前最重要的人工审查环节。

⚙️ 02 · 原理
  1. 1

    推送分支：开发者在功能分支上完成改动、自测通过后，将分支推送到远程仓库。

  2. 2

    发起 PR：选择源分支与目标分支，填写标题、描述、关联的 Issue 与测试说明。

  3. 3

    自动检查：CI 运行测试、Lint、构建和安全扫描，结果显示在 PR 中。

  4. 4

    评审迭代：评审者逐行评论或要求修改，作者追加提交回应，直到获得批准。

  5. 5

    合并：满足保护规则后以 merge、squash 或 rebase 方式合入，并删除源分支。

🔤 03 · 术语
代码评审 (Code Review)
他人检查改动的正确性、设计与可维护性。
草稿 PR (Draft PR)
标记为未完成、暂不可合并的 PR，用于早期反馈。
CODEOWNERS
按路径指定必需评审人的配置文件。
必需状态检查 (Required Checks)
CI 检查通过才允许合并的保护规则。
Squash and merge
把 PR 所有提交压缩成一个提交合入目标分支。
💻 04 · 代码
用 gh 处理 PRbash
# 推送分支后创建 PR（--fill 用提交信息填充标题与描述）
git push -u origin feat/search
gh pr create --base main --fill --draft

# 或者明确写标题与描述
gh pr create --title "feat(search): add fuzzy search" \
  --body "Closes #42. Tested: unit tests + manual check on /search."

gh pr status                   # 我的 PR 与待我评审的 PR
gh pr checks                   # 查看 CI 检查结果
gh pr diff 128                 # 查看某个 PR 的改动
gh pr checkout 128             # 把别人的 PR 拉到本地测试
gh pr review 128 --approve     # 批准
gh pr merge 128 --squash --delete-branch

gh CLI 让 PR 的创建、检查、评审与合并都能在终端完成，也便于 Agent 调用。

📊 05 · 参数对比

PR 评审关注层次

层次关注点谁来查
自动化测试、类型、格式、安全扫描CI 必需检查
正确性逻辑、边界条件、错误处理评审者
设计职责划分、可维护性、一致性资深评审者
影响面数据库迁移、配置、依赖、权限相关负责人（CODEOWNERS）
⚖️ 06 · 方案取舍

小 PR（几百行内）

优点评审快、质量高、易回滚

代价需拆分任务

适用默认推荐

大 PR

优点功能一次完整交付

代价评审质量下降，冲突风险高

适用尽量避免，可拆成系列 PR

AI 辅助评审

优点快速发现常见问题

代价可能误报或遗漏设计问题

适用作为人工评审的补充

🕳️ 07 · 常见坑

  • ✗PR 描述为空，评审者不知道改了什么、为什么

    ✓写明动机、改动要点、测试方式与风险

  • ✗Agent 一次生成几千行的 PR

    ✓要求拆分为多个独立可评审的小 PR

  • ✗只看 diff 不拉下来运行

    ✓对关键改动本地运行或查看预览环境

  • ✗CI 失败仍强行合并

    ✓开启必需检查，修复后再合并

🎤 09 · 面试追问
好的代码评审看什么？

先看是否解决了正确的问题，再看正确性（边界、错误处理、并发）、安全（鉴权、输入、密钥）、设计与可维护性、测试是否覆盖关键路径。风格问题交给自动化工具，评论区分「必须改」与「建议」。

squash、merge、rebase 三种合并方式怎么选？

squash 让主干每个 PR 一个提交，历史干净，适合多数团队；merge commit 保留完整分支历史和合并点，便于追溯；rebase merge 线性且保留每个提交，要求提交本身整洁。团队应统一一种。

如何评审 AI 生成的 PR？

与人类 PR 同等标准，并额外关注：是否引入不必要或不存在的依赖、是否偏离项目约定、测试是否真正验证行为而非迎合实现、是否改动了无关文件、是否存在看似合理但错误的 API 用法。
