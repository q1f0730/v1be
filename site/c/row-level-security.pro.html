行级安全策略 (RLS)

Row-Level Security

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

行级安全（Row-Level Security, RLS）是数据库根据当前用户或会话上下文，自动为查询附加过滤条件、只允许访问或修改特定行的访问控制机制。PostgreSQL 用 CREATE POLICY 实现，Supabase 以它保护前端直连。它把多租户隔离下沉到数据层，避免漏写 WHERE 导致越权。

⚙️ 02 · 原理
  1. 1

    对表执行 ENABLE ROW LEVEL SECURITY；启用后若没有任何策略，普通角色默认看不到任何行。

  2. 2

    用 CREATE POLICY 定义规则：USING 过滤可见与可操作的行，WITH CHECK 校验写入的新行。

  3. 3

    策略可按命令（SELECT、INSERT、UPDATE、DELETE）和角色分别定义，多条宽松策略按 OR 组合。

  4. 4

    查询执行时数据库把策略条件自动加入查询，应用代码无需显式写过滤。

  5. 5

    当前用户身份来自数据库角色或会话变量（如 current_setting），由应用在连接上设置。

🔤 03 · 术语
USING 子句
决定哪些现有行对查询可见或可更新、删除。
WITH CHECK 子句
决定插入或更新后的新行是否允许写入。
BYPASSRLS
可绕过行级安全的角色属性，超级用户默认具备。
FORCE ROW LEVEL SECURITY
让表所有者也受策略约束。
会话变量 (current_setting)
在连接上设置的自定义参数，常存租户 ID。
💻 04 · 代码
PostgreSQL 多租户 RLSsql
CREATE TABLE documents (
  id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  tenant_id uuid NOT NULL,
  title     text NOT NULL
);
CREATE INDEX ON documents (tenant_id);          -- 策略条件需要索引

ALTER TABLE documents ENABLE ROW LEVEL SECURITY;
ALTER TABLE documents FORCE ROW LEVEL SECURITY; -- 表所有者也受约束

-- 只能看到、修改本租户的行；写入的行也必须属于本租户
CREATE POLICY tenant_isolation ON documents
  USING (tenant_id = current_setting('app.tenant_id')::uuid)
  WITH CHECK (tenant_id = current_setting('app.tenant_id')::uuid);

-- 应用在每个事务开始时设置租户（SET LOCAL 只在当前事务有效）
BEGIN;
SET LOCAL app.tenant_id = '6f1c2a3e-0000-4000-8000-000000000001';
SELECT * FROM documents;          -- 自动只返回该租户数据
COMMIT;

-- 应用连接使用的角色不能是超级用户，也不能有 BYPASSRLS

策略同时约束读和写；租户上下文用 SET LOCAL 绑定事务，配合连接池更安全。

⚖️ 06 · 方案取舍

仅应用层过滤

优点简单，无数据库依赖

代价任何遗漏都会越权

适用单租户或内部工具

应用过滤 + RLS 兜底

优点纵深防御，遗漏也不泄露

代价策略需维护与测试

适用多租户 SaaS 推荐

前端直连 + RLS（如 Supabase）

优点开发快，无需后端 API

代价策略即全部防线，必须严谨

适用小团队快速开发

🕳️ 07 · 常见坑

  • ✗建表后忘记启用 RLS，前端可读全表

    ✓所有暴露给客户端的表强制启用，并在 CI 中检查

  • ✗应用用超级用户或表所有者连接，RLS 被绕过

    ✓使用专用低权限角色，并对表 FORCE ROW LEVEL SECURITY

  • ✗只写 USING 不写 WITH CHECK，可插入他人租户数据

    ✓写操作策略同时定义 WITH CHECK

  • ✗连接池中会话变量残留到下一个请求

    ✓用 SET LOCAL 绑定在事务内，或每次请求重置

🎤 09 · 面试追问
RLS 对性能有什么影响？

策略条件会加入每个查询，相当于额外的 WHERE。条件列有索引时开销很小；若策略调用复杂函数或子查询，可能阻碍索引使用并逐行计算，需要用 EXPLAIN 检查，并把函数标记为合适的稳定性级别。

Supabase 为什么特别强调 RLS？

Supabase 允许前端用公开的 anon key 直接通过 API 访问数据库，此时 RLS 策略就是数据访问的主要边界。表未启用 RLS 或策略过宽，任何人都可能读写数据；service_role 密钥会绕过 RLS，只能在服务端使用。

如何测试 RLS 策略？

以不同用户或租户身份建立会话，分别执行增删改查，断言只能访问自己的行、无法写入他人数据；覆盖未设置上下文的情况，确认默认拒绝。把这些测试纳入 CI。
