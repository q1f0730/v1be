测试驱动开发 (TDD)

Test-Driven Development

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

测试驱动开发（Test-Driven Development，TDD）是先写一个会失败的测试、再写刚好让它通过的代码、最后重构的开发方法，由 Kent Beck 推广，属于工程实践层，用短小的“红-绿-重构”循环驱动设计，使需求先被表达为可执行的规格。在 AI 编码中，先写测试能给 Agent 明确、可验证的完成标准。

⚙️ 02 · 原理
  1. 1

    红：根据一个小需求写测试，运行确认它因功能缺失而失败，证明测试本身有效。

  2. 2

    绿：编写最少量的实现代码让测试通过，此时不追求优雅或通用，只求变绿。

  3. 3

    重构：在测试保护下改善代码结构、消除重复，保持所有测试通过。

  4. 4

    重复循环，每次只推进一个小行为，逐步扩展测试清单直到需求完成。

  5. 5

    用于 AI 编码时，可先让 Agent 只写测试并确认失败、提交，再要求它实现且不得修改测试。

🔤 03 · 术语
红-绿-重构 (Red-Green-Refactor)
TDD 的三步循环：失败、通过、改善结构。
测试清单 (Test List)
开始前列出待实现行为的清单，逐条转为测试。
三角测量 (Triangulation)
用多个具体例子逼出通用实现，避免硬编码。
BDD (行为驱动开发)
以业务语言描述行为的 TDD 变体，如 Given-When-Then。
回归测试 (Regression Test)
防止已修复问题或已有功能再次出错的测试。
💻 04 · 代码
一次红-绿-重构python
# 第 1 步（红）：先写测试，运行 pytest 会失败（函数尚不存在）
def test_slugify_basic():
    assert slugify("Hello World") == "hello-world"

def test_slugify_strips_symbols():
    assert slugify("  AI & You!  ") == "ai-you"

# 第 2 步（绿）：写最少的实现让测试通过
import re

def slugify(text: str) -> str:
    text = text.strip().lower()
    text = re.sub(r"[^a-z0-9]+", "-", text)   # 非字母数字统一成连字符
    return text.strip("-")

# 第 3 步（重构）：测试保持绿色的前提下改进命名、抽取函数等
# 新需求（如支持中文）先追加一个失败的测试，再进入下一轮

测试先于实现存在并先失败，第二个用例逼出了去除符号的通用实现。

⚖️ 06 · 方案取舍

严格 TDD

优点设计好、回归保护强

代价需要纪律，探索期显慢

适用业务规则明确的核心逻辑

先探索原型再补测试

优点快速验证可行性

代价原型容易变成生产代码

适用技术不确定性高的阶段

AI 写测试、人审、AI 实现

优点兼顾速度与验收

代价人需认真审测试

适用用 Agent 开发功能时

🕳️ 07 · 常见坑

  • ✗测试一写完就直接通过，没见过红

    ✓必须先运行看到预期的失败，确认测试有效

  • ✗一次写一大堆测试再实现

    ✓一次只推进一个测试，保持循环短小

  • ✗跳过重构步骤，代码越积越乱

    ✓每次变绿后检查重复和命名再继续

  • ✗Agent 用硬编码返回值让测试通过

    ✓增加多组用例三角测量，并审查实现

🎤 09 · 面试追问
为什么 TDD 要求先看到测试失败？

先失败证明测试确实在检测目标行为，且断言能够抓到错误。如果测试一开始就通过，可能是断言写错、测试没被执行，或者功能早已存在。没有见过红的测试，无法确定它将来能保护你。

TDD 如何影响代码设计？

先写测试会迫使你从调用方视角设计接口，难以测试的代码通常意味着依赖过多或职责混杂，于是自然倾向依赖注入、小函数和清晰边界。测试成为代码的第一个使用者，暴露出糟糕的 API。

怎么在 AI 编码中实践 TDD？

分两步：先让 Agent 根据需求写测试，明确说不要写实现，运行确认失败，人审测试后提交；再让 Agent 实现直到测试通过，并禁止修改测试。这样测试成为客观验收标准，防止 Agent 迁就自己的实现。
