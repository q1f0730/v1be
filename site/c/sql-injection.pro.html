SQL注入

SQL Injection

📐 01 · 定义

SQL 注入（SQL Injection）是攻击者通过把恶意 SQL 片段混入应用拼接的查询语句，使数据库执行非预期命令的漏洞，属于 OWASP Top 10 中的注入（Injection）类。它可导致数据泄露、篡改、绕过登录甚至控制服务器。根因是把不可信输入当作代码拼进查询，根本解法是参数化查询。

⚙️ 02 · 原理
  1. 1

    应用把用户输入直接拼接进 SQL 字符串，如 WHERE name = '用户输入'。

  2. 2

    攻击者输入含引号和 SQL 关键字的内容，闭合原有字符串并追加自己的条件或语句。

  3. 3

    数据库解析整个字符串时无法区分开发者写的代码和用户数据，于是执行被篡改的语义。

  4. 4

    常见利用手法有 UNION 查询拼接数据、布尔或时间盲注逐位推断、堆叠查询执行额外语句。

  5. 5

    参数化查询让 SQL 结构与数据分开发送，数据库始终把参数当作值而不是代码。

🔤 03 · 术语
参数化查询 (Parameterized Query)
用占位符表示值，值单独绑定，结构无法被改变。
预编译语句 (Prepared Statement)
先编译 SQL 结构再绑定参数执行，常用于参数化。
盲注 (Blind SQLi)
页面无直接回显，通过真假响应或延迟推断数据。
ORM
对象关系映射库，默认参数化，但原生 SQL 接口仍可能注入。
二阶注入 (Second-Order)
恶意数据先被存储，之后在其他查询中被拼接触发。
💻 04 · 代码
拼接 vs 参数化python
import sqlite3
conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE users(name TEXT, role TEXT)")
conn.executemany("INSERT INTO users VALUES (?, ?)",
                 [("alice", "admin"), ("bob", "user")])

name = "x' OR '1'='1"   # 攻击者输入

# 错误：字符串拼接，条件被篡改为恒真，返回全部用户
unsafe = f"SELECT * FROM users WHERE name = '{name}'"
print(conn.execute(unsafe).fetchall())   # [('alice','admin'), ('bob','user')]

# 正确：参数化，输入只被当作一个普通字符串值
safe = conn.execute("SELECT * FROM users WHERE name = ?", (name,))
print(safe.fetchall())                    # []

# 表名、排序字段不能参数化，应使用白名单
sort = "name"
assert sort in {"name", "role"}
print(conn.execute(f"SELECT * FROM users ORDER BY {sort}").fetchall())

可直接运行，对比同一输入在拼接与参数化下的结果；标识符需用白名单。

防御手段对比

手段效果说明
参数化查询根本防御值与 SQL 结构分离
标识符白名单必需补充表名、列名、排序方向无法参数化

🕳️ 07 · 常见坑

  • ✗以为用了 ORM 就绝对安全

    ✓审查 raw、literal 等原生接口，同样使用参数绑定

  • ✗把用户输入拼进 ORDER BY 或表名

    ✓使用固定白名单映射

  • ✗AI 生成的代码用 f-string 拼 SQL

    ✓在规则文件中禁止拼接，并用 lint 或扫描工具检测

  • ✗数据库报错信息直接返回给用户

    ✓对外返回通用错误，详细信息只写日志

☑️ 08 · 检查清单
🎤 09 · 面试追问
为什么参数化能根本防御 SQL 注入？

参数化把 SQL 语句结构和数据分开传给数据库：结构先被解析确定，参数只能作为值填入，无论内容包含什么引号或关键字，都无法改变语句的语法结构。转义则是试图让数据“看起来不像代码”，容易遗漏。

哪些地方不能参数化，怎么处理？

表名、列名、排序方向、LIMIT 在部分驱动中等 SQL 标识符和关键字通常不能用占位符。正确做法是用白名单把用户选择映射到固定的合法值，绝不直接拼接原始输入。

什么是二阶 SQL 注入？

恶意输入第一次写入时被安全地参数化保存，没有触发；但之后另一段代码从数据库读出这个值，信任它并拼接进新的 SQL，此时才触发注入。防御原则是任何来源的数据进入 SQL 时都参数化，包括来自自己数据库的数据。
