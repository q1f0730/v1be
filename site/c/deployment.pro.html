📐 01 · 定义

部署（Deployment）是把通过测试的构建产物发布到目标运行环境并对外提供服务的过程，属于交付与运维层。它涵盖构建、配置注入、发布、健康检查、流量切换和回滚，目标是可重复、可观测、可回退。现代部署通常由 CI/CD 流水线自动完成，并采用滚动、蓝绿或金丝雀等策略降低风险。

⚙️ 02 · 原理
  1. 1

    代码合并后 CI 执行安装、测试和构建，产出不可变制品，如镜像或静态文件包，并打上版本标识。

  2. 2

    按环境注入配置和密钥，同一制品通过不同配置部署到测试、预发和生产环境。

  3. 3

    按策略发布新版本：滚动替换实例、蓝绿整体切换，或金丝雀先放少量流量。

  4. 4

    通过健康检查和监控指标（错误率、延迟）判断新版本是否正常，异常时自动或手动回滚。

  5. 5

    数据库迁移需与代码发布协调，通常采用先兼容扩展、后清理的两阶段方式。

🔤 03 · 术语
CI/CD
持续集成与持续交付/部署，自动化构建、测试和发布。
不可变制品 (Immutable Artifact)
构建一次、各环境复用的产物，避免环境间差异。
蓝绿部署 (Blue-Green)
准备完整新环境，验证后一次性切换流量。
金丝雀发布 (Canary)
先把小比例流量导给新版本，观察后逐步扩大。
健康检查 (Health Check)
平台定期探测实例是否可用，决定是否接收流量。
💻 04 · 代码
GitHub Actions 测试后部署yaml
# .github/workflows/deploy.yml
name: deploy
on:
  push:
    branches: [main]
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production        # 可配置审批与环境级密钥
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm test             # 测试不过则不会部署
      - run: npm run build
      - name: Deploy
        run: ./scripts/deploy.sh  # 替换为平台 CLI，如 vercel/wrangler
        env:
          DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}

合并到 main 即测试、构建、部署；密钥来自仓库 Secrets，不写入代码。

🕳️ 07 · 常见坑

  • ✗在服务器上直接改代码热修

    ✓所有变更走代码仓库和流水线，保证可追溯

  • ✗代码与破坏性数据库迁移同时发布

    ✓拆为扩展-迁移-收缩多步，保证新旧代码都能运行

  • ✗没有回滚预案，出问题临时想办法

    ✓保留上一版本制品，演练一键回滚

  • ✗让 AI Agent 直接持有生产部署凭证

    ✓部署经流水线和人工审批，Agent 只提交代码

🎤 09 · 面试追问
蓝绿部署和金丝雀发布怎么选？

蓝绿切换简单、回滚快，但需要双份资源，且切换瞬间全部用户都用上新版本。金丝雀先让小部分流量试用，通过指标逐步放量，风险最小但需要流量控制和完善监控。核心服务、监控完善时更适合金丝雀。

为什么强调“构建一次，多处部署”？

如果每个环境重新构建，依赖版本、构建环境的差异可能导致测试通过的版本与生产版本不同。使用同一不可变制品，只通过配置区分环境，才能确保测试验证的正是要上线的东西，回滚也只需切换制品版本。

如何做零停机的数据库迁移？

采用扩展-收缩模式：先加新列或新表且保持兼容，发布同时读写新旧结构的代码；回填数据；再发布只用新结构的代码；最后删除旧结构。每一步都能单独回滚，任何时刻新旧代码都能正常运行。
