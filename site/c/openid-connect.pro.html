📐 01 · 定义

OpenID Connect（OIDC）是构建在 OAuth 2.0 之上的身份认证层。OAuth 只解决“授权访问资源”，OIDC 额外定义了 ID Token、UserInfo 端点和发现机制，让客户端以标准方式确认“登录的是谁”，是“用 Google/企业 SSO 登录”的底层协议。

⚙️ 02 · 原理
  1. 1

    客户端在授权请求中带上 scope=openid，并附 state、nonce，以及推荐的 PKCE 参数。

  2. 2

    用户在身份提供方（OP）完成认证与同意，OP 通过 redirect_uri 回传一次性授权码 code。

  3. 3

    客户端在后端用 code（加 code_verifier 或客户端密钥）向 token 端点换取 ID Token 与 Access Token。

  4. 4

    客户端校验 ID Token：签名（用 JWKS 公钥）、iss、aud、exp、nonce，全部通过才建立本地会话。

  5. 5

    需要更多资料时，用 Access Token 调用 UserInfo 端点；端点地址可从发现文档自动获取。

🔤 03 · 术语
身份提供方 (OpenID Provider, OP)
负责认证用户并签发 ID Token 的服务，如 Google、Okta、Keycloak。
依赖方 (Relying Party, RP)
接入 OIDC 登录、信任 OP 断言的应用。
ID Token
OP 签名的 JWT，包含 iss、sub、aud、exp、nonce 等身份声明。
nonce
客户端生成并在 ID Token 中回显的随机值，用于防重放。
发现文档 (Discovery)
/.well-known/openid-configuration，列出各端点与支持的算法。
JWKS
OP 公布的 JSON Web Key 集合，用于验证 ID Token 签名。

⚖️ 06 · 方案取舍

授权码 + PKCE

优点token 不经浏览器地址栏，安全性最高

代价需后端或 PKCE 支持，步骤较多

适用Web、SPA、移动端的默认选择

隐式流程 (Implicit)

优点纯前端、无需后端换 token

代价token 暴露在 URL，已不推荐

适用仅维护老系统

托管 IdP（Auth0/Cognito 等）

优点省去自建，MFA、社交登录开箱即用

代价按 MAU 计费，有锁定风险

适用团队小、要快速上线

🕳️ 07 · 常见坑

  • ✗拿 Access Token 当登录凭证，不校验 ID Token

    ✓登录只认校验通过的 ID Token，Access Token 只用于调 API

  • ✗只解码 JWT 不验签，或不检查 aud

    ✓用 JWKS 验签，并校验 iss、aud、exp、nonce

  • ✗用 email 作为用户主键

    ✓用 iss + sub 组合做唯一标识，email 可能变化或未验证

  • ✗缺少 state 校验，回调可被 CSRF

    ✓生成随机 state 存会话，回调时严格比对

🎤 09 · 面试追问
OIDC 比纯 OAuth“登录”多解决了什么？

纯 OAuth 的 Access Token 面向资源服务器，客户端无法可靠判断用户是谁、token 是否发给自己。OIDC 增加签名的 ID Token（aud 指向客户端、含 nonce 防重放）、标准 claims、UserInfo 与发现机制，使认证可互操作。

ID Token 需要校验哪些字段？

签名（按 kid 从 JWKS 取公钥，限制 alg）；iss 等于预期 OP；aud 包含本 client_id；exp 未过期、iat 合理；nonce 与发起时一致；如用到还要看 azp、auth_time、acr。

SPA 为什么推荐 BFF 而非前端存 token？

前端存 token 易被 XSS 窃取。BFF（Backend for Frontend）由后端完成授权码交换并持有 token，浏览器只拿 HttpOnly 会话 Cookie，攻击面更小，刷新令牌也不暴露给 JS。
