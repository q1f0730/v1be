单体仓库 (Monorepo)

Monorepo

📐 01 · 定义

单体仓库（Monorepo）指把多个相关项目（应用、库、服务）放在同一个版本控制仓库中统一管理，属于代码组织与工程效能层。它不等于单体架构：仓库里可以有多个独立部署的服务。核心价值是原子化跨项目改动、共享代码与统一工具链；代价是需要工作区、增量构建、缓存和代码归属等工具支撑规模。

⚙️ 02 · 原理
  1. 1

    仓库按约定划分目录，常见为 apps/（可部署应用）与 packages/（共享库）。

  2. 2

    包管理器工作区（pnpm/npm/Yarn workspaces）把内部包相互链接，无需发布即可引用。

  3. 3

    构建工具（Turborepo、Nx、Bazel）分析包依赖图，按拓扑顺序执行任务并并行化。

  4. 4

    对任务输入做哈希，命中本地或远程缓存则直接复用输出，避免重复构建和测试。

  5. 5

    CI 根据改动文件计算受影响的包（affected），只构建、测试、部署这些包。

🔤 03 · 术语
工作区 (Workspace)
包管理器在一个仓库内管理多个包并本地互相链接。
任务图 (Task Graph)
按包依赖关系推导出的任务执行顺序与并行度。
远程缓存 (Remote Cache)
团队和 CI 共享的构建产物缓存，以输入哈希为键。
受影响分析 (Affected)
根据改动推算哪些项目需要重新构建和测试。
CODEOWNERS
按路径指定代码负责人，PR 自动请求对应人评审。
💻 04 · 代码
Turborepo 任务配置json
// turbo.json（Turborepo 2.x 使用 tasks 字段）
{
  "$schema": "https://turborepo.com/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**", ".next/**", "!.next/cache/**"]
    },
    "test": {
      "dependsOn": ["^build"]
    },
    "lint": {},
    "dev": {
      "cache": false,
      "persistent": true
    }
  }
}

^build 表示先构建依赖的内部包；outputs 声明可缓存产物，命中缓存即跳过。

⚖️ 06 · 方案取舍

Monorepo

优点原子改动、共享代码、工具统一

代价需要缓存与增量 CI，权限粒度粗

适用多项目强耦合、同一团队维护

Polyrepo（多仓库）

优点边界清晰、权限独立、仓库小

代价共享代码要发版，跨仓改动协调难

适用团队/服务高度独立

混合模式

优点按领域分组成几个中型仓库

代价边界划分需要判断

适用组织规模中等、领域分明

🕳️ 07 · 常见坑

  • ✗把 Monorepo 当成单体架构，所有服务一起部署

    ✓仓库统一不等于部署统一，按应用独立构建发布

  • ✗CI 每次跑全量构建与测试，越来越慢

    ✓用 affected 分析与远程缓存只跑受影响部分

  • ✗内部包之间随意深层引用对方内部文件

    ✓通过 package.json exports 暴露公共入口，设边界规则

  • ✗缓存未声明全部输入（如环境变量），产物错误复用

    ✓在任务配置中声明影响输出的 env 与文件

☑️ 08 · 检查清单
🎤 09 · 面试追问
Monorepo 与单体架构有什么区别？

Monorepo 是代码存放方式，单体是部署架构。Google 等公司在一个仓库里维护大量独立服务；反之一个单体应用也可以拆在多个仓库。二者正交。

远程缓存如何保证不会用错产物？

对任务输入（源码、依赖锁、配置、声明的环境变量、上游产物）计算哈希作为键，输入变化即缓存失效。风险在于未声明的输入，必须在配置里显式列出。

AI 编码 Agent 在 Monorepo 中要注意什么？

上下文巨大，需通过规则文件说明目录结构与边界，限定 Agent 工作的包；跨包改动要跑受影响测试；可为每个子项目放置独立的说明文件。
