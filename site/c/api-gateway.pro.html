📐 01 · 定义

API 网关（API Gateway）是位于客户端与后端服务之间的统一入口层，负责请求路由，并集中处理横切关注点：认证鉴权、限流、TLS 终止、请求/响应转换、缓存、日志与指标。它常见于微服务架构，向外暴露统一的 API 面，屏蔽内部服务拆分细节。代表实现有 Kong、Apache APISIX、Envoy、AWS API Gateway 等。

⚙️ 02 · 原理
  1. 1

    客户端请求到达网关，网关终止 TLS，并根据主机名、路径、方法或请求头匹配路由规则。

  2. 2

    依次执行插件/过滤器链：认证（API Key、JWT、OAuth）、授权、限流、请求体大小与格式校验。

  3. 3

    通过服务发现或静态配置选择上游实例，结合负载均衡、超时、重试和熔断转发请求。

  4. 4

    可对响应做转换、聚合多个服务结果（BFF 模式）或缓存，并附加统一的错误格式与 CORS 头。

  5. 5

    全过程记录访问日志、指标与追踪信息，为可观测性和计费提供统一数据源。

🔤 03 · 术语
路由 (Route)
把匹配的请求映射到某个上游服务的规则。
上游 (Upstream)
网关后面实际处理请求的服务或实例组。
BFF (Backend for Frontend)
为特定前端定制聚合接口的网关层模式。
插件 / 过滤器 (Plugin / Filter)
在请求生命周期中执行的可组合处理单元。
南北向流量 (North-South Traffic)
外部客户端与内部系统之间的流量，网关主要处理此类。
服务网格 (Service Mesh)
处理服务间东西向流量的基础设施，与网关互补。
💻 04 · 代码
Kong 声明式配置：路由+鉴权+限流yaml
# kong.yml（DB-less 模式，字段以 Kong 官方文档为准）
_format_version: "3.0"
services:
  - name: order-service
    url: http://orders.internal:8080
    routes:
      - name: orders
        paths: ["/api/orders"]
    plugins:
      - name: key-auth            # 需要携带 API Key
      - name: rate-limiting
        config:
          minute: 60              # 每个消费者每分钟 60 次
          policy: local
  - name: user-service
    url: http://users.internal:8080
    routes:
      - name: users
        paths: ["/api/users"]
consumers:
  - username: mobile-app
    keyauth_credentials:
      - key: <从密钥管理注入，勿提交明文>

在网关层集中声明路由、认证和限流，后端服务无需各自实现这些横切逻辑。

📊 05 · 参数对比

网关、反向代理与服务网格

组件主要职责流量方向典型产品
反向代理转发、TLS、负载均衡南北向Nginx、HAProxy
API 网关反向代理 + 鉴权、限流、API 管理南北向Kong、APISIX、AWS API Gateway
服务网格服务间 mTLS、重试、观测东西向Istio、Linkerd
BFF按前端聚合与裁剪数据南北向自研 Node/GraphQL 层
⚖️ 06 · 方案取舍

集中式网关

优点横切逻辑统一，安全策略一致

代价可能成为瓶颈与单点，需高可用部署

适用多数微服务系统的入口

每个前端一个 BFF

优点接口贴合前端需求

代价服务数量增多，逻辑重复

适用Web、移动端需求差异大

无网关，服务直接暴露

优点架构简单

代价鉴权限流分散，暴露内部结构

适用单体或极少量服务

🕳️ 07 · 常见坑

  • ✗在网关里写大量业务逻辑

    ✓网关只做横切关注点，业务逻辑留在服务内

  • ✗后端服务完全信任网关，内部端口可被直接访问

    ✓网络隔离上游服务，服务内部仍做必要的授权校验

  • ✗网关单实例部署

    ✓多实例 + 负载均衡，配置健康检查与故障转移

  • ✗超时与重试未配置，慢服务拖垮网关

    ✓为每条路由设置超时、重试上限和熔断

☑️ 08 · 检查清单
🎤 09 · 面试追问
API 网关和反向代理有什么区别？

反向代理主要负责转发、TLS 终止和负载均衡；API 网关在此基础上增加 API 管理能力，如认证、按消费者限流、请求转换、聚合、开发者门户与计费。很多网关本身基于 Nginx 或 Envoy 构建。

网关会成为单点故障或性能瓶颈吗？

会有这种风险，所以要多实例水平扩展、前置负载均衡、保持网关无状态，并避免在网关中执行重计算或阻塞调用。限流计数等共享状态可放在 Redis 等外部存储，或接受本地近似计数。

有了网关，后端服务还需要鉴权吗？

需要做纵深防御。网关负责认证身份，但细粒度的资源级授权（这个用户能否访问这个订单）依赖业务数据，应在服务内完成。同时内部网络要隔离，防止绕过网关直接访问服务。
