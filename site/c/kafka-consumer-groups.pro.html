Kafka消费者组

Kafka Consumer Groups

📐 01 · 定义

Kafka 消费者组（Consumer Group）是一组共享同一 group.id 的消费者，共同消费一个或多个主题：每个分区在同一时刻只分配给组内一个消费者，从而实现并行处理与负载均衡；不同组相互独立，各自维护消费进度，实现同一数据被多个系统分别消费。

⚙️ 02 · 原理
  1. 1

    加入组：消费者以相同 group.id 订阅主题，由组协调器（Group Coordinator）管理成员。

  2. 2

    分区分配：按分配策略把分区分给各成员，同一分区只属于组内一个消费者。

  3. 3

    拉取处理：每个消费者只从分配给自己的分区批量拉取消息并在本地处理。

  4. 4

    提交位点：处理后把偏移量提交到内部主题 __consumer_offsets，记录组的进度。

  5. 5

    再平衡：成员加入、离开或超时时重新分配分区，新的所有者从已提交位点继续。

🔤 03 · 术语
消费位点 (Offset)
消费者组在每个分区已处理到的位置。
消费滞后 (Consumer Lag)
分区最新位点与组已提交位点的差值，表示积压。
再平衡 (Rebalance)
组成员变化时重新分配分区的过程。
协作式再平衡 (Cooperative Rebalancing)
增量迁移分区，避免全部成员同时停止消费。
静态成员 (Static Membership)
配置 group.instance.id，短暂重启不触发再平衡。
max.poll.interval.ms
两次 poll 最大间隔，超出则被视为失效并触发再平衡。
💻 04 · 代码
查看与重置消费进度bash
# 查看组内每个分区的当前位点、最新位点和滞后（LAG）
kafka-consumer-groups.sh --bootstrap-server kafka:9092 \
  --describe --group order-service

# 列出所有消费者组
kafka-consumer-groups.sh --bootstrap-server kafka:9092 --list

# 先预演：把位点重置到某个时间点（不加 --execute 只显示结果）
kafka-consumer-groups.sh --bootstrap-server kafka:9092 \
  --group order-service --topic orders \
  --reset-offsets --to-datetime 2026-10-20T00:00:00.000 --dry-run

# 确认后执行（需先停掉该组所有消费者）
kafka-consumer-groups.sh --bootstrap-server kafka:9092 \
  --group order-service --topic orders \
  --reset-offsets --to-datetime 2026-10-20T00:00:00.000 --execute

LAG 是最重要的健康指标；重置位点用于回放数据或跳过坏消息，务必先预演。

策略行为适用
Range按主题连续分段分配需同主题间分区对齐时

⚖️ 06 · 方案取舍

增加组内消费者

优点提高并行度

代价超过分区数的消费者会空闲

适用分区数大于当前消费者数

增加分区数

优点提高并行上限

代价改变 key 映射，影响顺序

适用消费者数已达分区数上限

单消费者内多线程

优点不增分区也能提速

代价位点提交与顺序管理更复杂

适用处理耗时长、无严格顺序要求

🕳️ 07 · 常见坑

  • ✗消费者数多于分区数，以为能继续提升吞吐

    ✓并行上限等于分区数，需要时先增加分区

  • ✗单条处理过慢超过 max.poll.interval.ms，反复再平衡

    ✓减小 max.poll.records、异步处理或调大间隔

  • ✗自动提交位点，处理未完成即提交，崩溃后丢消息

    ✓关闭自动提交，处理成功后手动提交

  • ✗滚动发布时频繁触发全组再平衡，消费停顿

    ✓使用协作式分配策略，并配置静态成员

☑️ 08 · 检查清单
🎤 09 · 面试追问
为什么组内消费者数超过分区数没有意义？

同一分区在同一时刻只能被组内一个消费者消费，以保证分区内有序和位点管理简单，所以多出的消费者分不到分区而空闲，只能作为热备。并行度上限由分区数决定。

再平衡为什么会造成消费停顿？

传统 eager 协议下所有成员先撤销全部分区再重新分配，期间整组停止消费。协作式再平衡只迁移需要变化的分区；静态成员避免短暂重启触发再平衡；新一代组协议（KIP-848）把分配移到 broker 端进一步改善。

消费滞后持续增长，怎么排查？

先看是否所有分区都滞后：全部滞后多为处理能力不足，可增加消费者/分区或优化处理逻辑；个别分区滞后多为热点 key 或某消费者卡住；再看是否频繁再平衡、下游依赖变慢。
