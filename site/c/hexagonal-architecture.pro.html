六边形架构 / 整洁架构

Hexagonal Architecture

📐 01 · 定义

六边形架构（Hexagonal Architecture，又称端口与适配器）由 Alistair Cockburn 于 2005 年提出，整洁架构（Clean Architecture）是 Robert C. Martin 2012 年总结的同类思想。核心是依赖只指向内部：业务核心定义端口（接口），数据库、Web 框架等外部技术以适配器实现端口，使业务可独立测试、技术可替换。

⚙️ 02 · 原理
  1. 1

    把应用分为内部（领域模型与用例）和外部（UI、数据库、第三方服务、消息系统）。

  2. 2

    内部定义端口：驱动端口是外界调用应用的入口（如用例接口），被驱动端口是应用需要的外部能力（如仓储接口）。

  3. 3

    外部实现适配器：HTTP 控制器、CLI 属于驱动适配器；数据库仓储、邮件网关属于被驱动适配器。

  4. 4

    依赖倒置：核心只依赖自己定义的抽象，适配器依赖核心，组装在应用启动的组合根中完成。

  5. 5

    测试时用内存适配器替换真实数据库，用例测试无需启动框架或外部服务。

🔤 03 · 术语
端口 (Port)
由应用核心定义的接口，描述它对外提供或需要的能力。
适配器 (Adapter)
把具体技术（SQL、HTTP、SDK）转换为端口接口的实现。
驱动/被驱动 (Driving/Driven)
主动调用应用的一侧与被应用调用的一侧，也称主/次适配器。
依赖规则 (Dependency Rule)
整洁架构的要求：源代码依赖只能指向更内层的策略。
组合根 (Composition Root)
应用入口处集中创建并装配具体适配器的位置。
💻 04 · 代码
端口与内存适配器python
from typing import Protocol

class UserRepo(Protocol):               # 被驱动端口：核心定义
    def get_email(self, uid: int) -> str | None: ...

class Mailer(Protocol):
    def send(self, to: str, body: str) -> None: ...

class SendWelcome:                      # 用例：只依赖端口
    def __init__(self, repo: UserRepo, mailer: Mailer):
        self.repo, self.mailer = repo, mailer
    def __call__(self, uid: int) -> bool:
        email = self.repo.get_email(uid)
        if not email:
            return False
        self.mailer.send(email, "欢迎加入")
        return True

# 测试用适配器：无需数据库与邮件服务
class InMemoryRepo:
    def __init__(self, data): self.data = data
    def get_email(self, uid): return self.data.get(uid)

class FakeMailer:
    def __init__(self): self.sent = []
    def send(self, to, body): self.sent.append(to)

m = FakeMailer()
assert SendWelcome(InMemoryRepo({1: "a@x.com"}), m)(1) and m.sent == ["a@x.com"]

生产环境换成 SQL 仓储和 SMTP 适配器即可，用例代码不改；Protocol 需要 Python 3.8+，X | None 写法需 3.10+。

📊 05 · 参数对比

几种分层架构对比

架构依赖方向关注点
传统三层UI → 业务 → 数据访问业务层直接依赖数据库实现
六边形适配器 → 端口 ← 核心内外对称，强调可替换适配器
洋葱架构外环依赖内环领域模型位于圆心
整洁架构框架 → 接口适配 → 用例 → 实体以依赖规则统一上述思想
⚖️ 06 · 方案取舍

严格端口与适配器

优点核心可单测，技术栈可替换

代价接口与映射代码增多，入门门槛高

适用业务复杂、生命周期长的系统

轻量分层（只抽仓储）

优点成本低，保留主要测试收益

代价框架依赖仍可能渗入业务

适用中小型项目、团队较小

直接用框架约定

优点开发最快，生态工具最全

代价业务与框架强耦合，难迁移难测

适用原型、短期项目或纯 CRUD

🕳️ 07 · 常见坑

  • ✗领域实体直接继承 ORM 基类

    ✓领域模型保持纯对象，在适配器中做 ORM 映射

  • ✗为每个类都建接口，抽象泛滥

    ✓只在外部依赖边界建端口，内部代码直接调用

  • ✗端口按数据库表设计，泄漏存储细节

    ✓端口以业务语言命名，如 find_active_orders，而非通用 SQL 操作

  • ✗依赖规则只靠约定，逐渐被破坏

    ✓用 import-linter、ArchUnit 等工具在 CI 中检查依赖方向

🎤 09 · 面试追问
六边形架构和三层架构的本质区别？

三层架构中业务层依赖数据访问层的具体实现，依赖方向自上而下直达数据库。六边形架构通过依赖倒置，让数据库适配器依赖业务核心定义的接口，核心不知道任何技术细节。结果是核心可脱离基础设施测试，替换存储只需新增适配器。

如何防止 AI 生成的代码破坏分层？

在规则文件中写明目录职责与禁止的 import，例如 domain 目录不得引入 ORM 和 Web 框架；在 CI 加架构测试自动拦截；评审时重点看新代码的依赖方向。把这些约束作为 Agent 的上下文，比事后重构便宜得多。

什么情况下这种架构是过度设计？

逻辑主要是表单与数据库的直接映射、生命周期短或团队很小时，额外的接口与映射层收益有限。可先只抽象最可能替换或最难测的外部依赖（如支付、邮件），随复杂度增长再逐步演进。
