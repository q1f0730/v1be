事件溯源

Event Sourcing

🧸 回到小白版

📐 01 · 定义

事件溯源（Event Sourcing）是一种持久化模式：不直接保存实体的当前状态，而是把每次状态变化作为不可变事件按顺序追加到事件存储中，当前状态通过按顺序重放事件得到。它天然提供完整审计历史和时间回溯能力，常与 CQRS 搭配，但带来事件版本演进和查询方面的复杂度。

⚙️ 02 · 原理
  1. 1

    命令处理：加载实体的历史事件并重放出当前状态，再校验命令是否允许执行。

  2. 2

    追加事件：校验通过后生成新事件，追加到该实体的事件流末尾，从不修改旧事件。

  3. 3

    并发控制：追加时附带期望版本号，若事件流已被他人追加则冲突重试。

  4. 4

    读取状态：按顺序折叠事件得到状态；事件过多时定期保存快照以加速加载。

  5. 5

    下游投影：事件被订阅后构建各种读模型，也可以重放全部事件来重建读模型。

🔤 03 · 术语
事件流 (Event Stream)
同一实体（聚合）按顺序排列的全部事件。
事件存储 (Event Store)
只追加、按流和版本组织事件的持久化存储。
快照 (Snapshot)
某一版本时的状态缓存，加载时从快照之后开始重放。
乐观并发 (Optimistic Concurrency)
按期望版本追加，版本不符即拒绝，避免覆盖。
事件升级 (Upcasting)
读取时把旧版本事件转换为新结构的兼容手段。
💻 04 · 代码
最小事件存储python
import json, sqlite3

db = sqlite3.connect(":memory:")
db.execute("""CREATE TABLE events (
  stream_id TEXT, version INTEGER, type TEXT, data TEXT,
  PRIMARY KEY (stream_id, version))""")   # 主键保证同版本只能写一次

def append(stream, expected_version, type_, data):
    # expected_version 不对会触发主键冲突 → 乐观并发失败
    db.execute("INSERT INTO events VALUES (?,?,?,?)",
               (stream, expected_version + 1, type_, json.dumps(data)))

def load(stream):
    balance, version = 0, 0
    for v, t, d in db.execute("SELECT version, type, data FROM events "
                              "WHERE stream_id=? ORDER BY version", (stream,)):
        amt = json.loads(d)["amount"]
        balance += amt if t == "Deposited" else -amt   # 折叠事件得到状态
        version = v
    return balance, version

append("acct-1", 0, "Deposited", {"amount": 100})
append("acct-1", 1, "Withdrawn", {"amount": 30})
print(load("acct-1"))          # (70, 2)

用 (stream_id, version) 唯一约束实现乐观并发；状态由事件重放计算得出。

📊 05 · 参数对比

状态存储 vs 事件溯源

维度状态存储事件溯源
存什么当前状态全部变化事件
历史审计需额外审计表天然完整
查询直接查询需投影成读模型
结构演进迁移表结构需兼容旧事件版本
⚖️ 06 · 方案取舍

事件溯源

优点完整审计、可回溯、易构建新视图

代价学习曲线陡，事件版本演进难

适用金融账务、审计要求高的核心域

状态存储+审计日志

优点查询简单，团队熟悉

代价审计日志可能与状态不一致

适用多数业务系统

状态存储+CDC 事件

优点低侵入地对外提供变化流

代价事件是表级变化而非业务语义

适用需要数据同步但不需完整溯源

🕳️ 07 · 常见坑

  • ✗直接修改或删除历史事件来纠错

    ✓追加补偿或更正事件，保持历史不可变

  • ✗事件字段随意变更，旧事件无法反序列化

    ✓事件带版本号，新增字段向后兼容，必要时 upcasting

  • ✗长生命周期实体每次加载重放上万事件

    ✓定期生成快照，从快照之后开始重放

  • ✗把个人敏感数据直接写入不可变事件

    ✓敏感字段加密存储，删除时销毁密钥（加密擦除）

☑️ 08 · 检查清单
🎤 09 · 面试追问
事件溯源中如何处理并发写？

每个事件流有单调版本号，写入时声明期望版本，存储层原子检查当前版本是否匹配，不匹配说明有人先写入，返回冲突；客户端重新加载最新状态、重新校验命令后再尝试追加。

事件结构变了怎么办？

事件不可变，不能批量改写历史。常用做法：只做向后兼容的新增字段；为事件加版本号，读取时用 upcaster 把旧版本转成新结构；变化很大时定义新事件类型，必要时通过流复制迁移。

GDPR 删除请求和不可变事件冲突吗？

有冲突。常见方案是加密擦除：每个用户的敏感字段用独立密钥加密，删除时销毁密钥使数据不可读；或把敏感数据放在事件之外的可删除存储，事件只保存引用。
