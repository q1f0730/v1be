子代理

Subagents

📐 01 · 定义

子代理（Subagent）是主智能体在运行中派生出的专用智能体实例，拥有独立的上下文窗口、系统提示词和受限工具集，完成指定子任务后只把结果返回给主智能体。它是多智能体模式在编码 Agent（如 Claude Code）中的具体落地，主要用于隔离上下文、并行探索与职责专精。

⚙️ 02 · 原理
  1. 1

    预先定义子代理：名称、何时使用的描述、系统提示词、允许的工具和可选模型。

  2. 2

    主智能体根据描述自动判断或由用户显式指定，把子任务连同必要上下文委派出去。

  3. 3

    子代理在全新上下文中工作，读文件、搜索、运行命令，不污染主对话。

  4. 4

    完成后返回精简结论（如相关文件路径与发现），中间过程留在子代理上下文中。

  5. 5

    主智能体基于结果继续推进，可同时派出多个子代理并行处理互不依赖的任务。

🔤 03 · 术语
上下文隔离 (Context Isolation)
子代理的探索过程不进入主对话上下文。
工具白名单 (Tool Allowlist)
限定子代理可用的工具，降低风险。
委派 (Delegation)
主智能体把子任务和所需上下文交给子代理。
上下文腐化 (Context Rot)
上下文越长，模型对早期信息利用越差的现象。
项目级/用户级定义
Claude Code 中子代理可放在项目或用户目录下共享或私用。
💻 04 · 代码
Claude Code 子代理定义text
# 文件：.claude/agents/code-reviewer.md（项目级，随仓库共享）
---
name: code-reviewer
description: 代码审查专家。在完成代码修改后主动使用，
  检查正确性、安全性与可维护性。
tools: Read, Grep, Glob, Bash
model: inherit
---
你是资深代码审查者。被调用时：
1. 运行 git diff 查看最近改动
2. 只关注被修改的文件
3. 按「必须修复 / 建议修改 / 可选优化」分级输出
4. 每个问题给出文件路径、行号和修复示例

不要修改任何文件，只输出审查意见。

YAML 头部声明名称、使用时机与工具，正文是系统提示词；只读工具降低误改风险。

📊 05 · 参数对比

子代理与主对话分工

维度主对话子代理
上下文累积整个会话每次任务全新开始
职责规划、决策、与用户沟通检索、审查、测试等专项
工具通常完整按任务最小化
产出最终修改与答复压缩后的结论
⚖️ 06 · 方案取舍

主对话直接处理

优点信息完整，无交接损失

代价大量探索内容挤占上下文

适用小任务、需要连续推理

委派子代理

优点保护主上下文，可并行

代价交接可能丢失细节，额外 token

适用大范围搜索、独立审查

专精子代理库

优点提示词可复用，行为稳定

代价定义需要维护

适用团队常见重复任务

🕳️ 07 · 常见坑

  • ✗description 写得含糊，主智能体从不调用或乱调用

    ✓写清触发场景与能力边界，必要时显式点名调用

  • ✗审查类子代理拥有写权限，直接改了代码

    ✓只读任务只给 Read/Grep/Glob 等工具

  • ✗委派时只给一句话，子代理缺少关键上下文

    ✓交代目标、相关文件、约束与期望输出格式

  • ✗让多个子代理并行修改同一批文件

    ✓写操作集中在一处，子代理负责调研与产出建议

☑️ 08 · 检查清单
🎤 09 · 面试追问
子代理解决的核心问题是什么？

上下文管理。大量文件读取、搜索结果和日志若都进入主对话，会挤占窗口并降低后续推理质量。子代理在独立上下文中消化这些信息，只返回结论，主对话保持干净聚焦。

子代理和 Skills 有什么区别？

子代理是独立运行的智能体实例，有自己的上下文与工具；Skills 是按需加载到当前智能体上下文中的指令与资源包，不另起上下文。前者解决隔离与并行，后者解决专业知识复用。

什么时候不该用子代理？

任务很小、需要与主对话频繁来回、或需要用到主对话中大量已有细节时，委派的交接成本和信息损失会超过收益；强依赖的连续编码改动也更适合在主对话完成。
