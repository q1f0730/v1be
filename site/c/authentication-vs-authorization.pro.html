认证 vs 授权

Authentication vs Authorization

📐 01 · 定义

认证（Authentication，AuthN）确认“你是谁”，即验证主体身份；授权（Authorization，AuthZ）决定“你能做什么”，即判断已识别的主体能否对某资源执行某操作。二者属于应用安全的访问控制层，按顺序发生：先认证得到身份，再基于身份、角色或属性做授权判断。混淆两者是越权漏洞的常见根源。

⚙️ 02 · 原理
  1. 1

    认证：用户提交凭证（密码、OTP、通行密钥或第三方登录），服务端验证后确立身份。

  2. 2

    建立会话：服务端签发会话 ID 或令牌，后续请求凭此证明已认证。

  3. 3

    授权：每个请求到达后，服务端根据身份、角色、资源归属等策略判断是否允许操作。

  4. 4

    执行策略：允许则继续处理，否则返回 403，或对隐藏资源返回 404。

  5. 5

    审计：记录认证事件和授权拒绝，用于发现撞库、越权尝试等异常。

🔤 03 · 术语
多因素认证 (MFA)
组合多种凭证类型，如密码加一次性验证码。
RBAC (基于角色的访问控制)
按角色分配权限，用户通过角色获得权限。
ABAC (基于属性的访问控制)
根据用户、资源、环境属性动态计算是否允许。
通行密钥 (Passkey)
基于 WebAuthn 公钥凭证的无密码认证方式。
主体 (Principal)
通过认证的身份实体，可以是用户或服务。
💻 04 · 代码
Express 中分离认证与授权typescript
import express from "express";
const app = express();

// 认证：确定是谁；verifySession 为项目自己的会话校验函数
function authenticate(req, res, next) {
  const user = verifySession(req.headers.cookie);
  if (!user) return res.status(401).json({ error: "unauthenticated" });
  req.user = user;
  next();
}

// 授权：判断能不能做
const requireRole = (role: string) => (req, res, next) =>
  req.user.roles.includes(role) ? next()
    : res.status(403).json({ error: "forbidden" });

app.delete("/admin/users/:id", authenticate, requireRole("admin"),
  (req, res) => res.sendStatus(204));

app.get("/orders/:id", authenticate, async (req, res) => {
  const order = await db.orders.findById(req.params.id);
  // 资源级授权：只能看自己的订单
  if (!order || order.userId !== req.user.id) return res.sendStatus(404);
  res.json(order);
});

401 对应认证失败、403 对应授权失败；资源归属检查需在处理函数中完成。

⚖️ 06 · 方案取舍

RBAC

优点简单直观，易审计

代价细粒度需求导致角色爆炸

适用权限模型较稳定的系统

ABAC/策略引擎

优点细粒度、可表达复杂规则

代价策略难调试和审计

适用多租户、复杂合规

托管认证服务

优点省去密码、MFA 实现

代价依赖第三方与费用

适用绝大多数中小产品

🕳️ 07 · 常见坑

  • ✗认证通过就认为可以访问任意资源

    ✓每个资源操作都做归属或权限检查

  • ✗前端隐藏按钮当作授权

    ✓授权必须在服务端执行

  • ✗用 OAuth 访问令牌直接当作登录凭证

    ✓登录使用 OpenID Connect 的 ID Token 并校验受众

  • ✗授权逻辑散落在各处、写法不一

    ✓集中封装授权函数或使用策略库，统一测试

☑️ 08 · 检查清单
🎤 09 · 面试追问
OAuth 2.0 是认证协议吗？

不是。OAuth 2.0 是授权框架，用于让第三方应用获得访问资源的有限权限，访问令牌不代表用户身份。OpenID Connect 在 OAuth 2.0 之上增加了 ID Token 和用户信息端点，专门解决认证问题，“用某某登录”通常基于 OIDC。

RBAC 和 ABAC 怎么选？

RBAC 适合权限与岗位对应清晰的场景，简单易审计；当权限需要依赖资源属性（所属部门、状态）、时间或地点等动态条件时，ABAC 更合适。实践中常以 RBAC 为主，在特定资源上叠加属性条件。

如何系统地防止越权？

默认拒绝；服务端统一的授权层，每个接口显式声明所需权限；数据查询带上租户或用户条件；对资源 ID 做归属校验；编写越权测试用例（用 A 的身份访问 B 的资源）；记录并监控授权拒绝。
