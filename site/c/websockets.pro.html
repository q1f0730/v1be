📐 01 · 定义

WebSocket（RFC 6455）是在单条 TCP 连接上提供全双工、低开销消息通道的协议。它以一次 HTTP/1.1 升级握手开始，之后客户端和服务端可随时互发文本或二进制帧，适合聊天、协同编辑、实时行情与游戏。长连接带来的连接管理、扩容与鉴权是工程重点。

⚙️ 02 · 原理
  1. 1

    客户端发送带 Upgrade: websocket、Sec-WebSocket-Key 的 HTTP GET 请求。

  2. 2

    服务端校验后返回 101 Switching Protocols，并用该 key 计算 Sec-WebSocket-Accept。

  3. 3

    之后双方以帧通信，客户端发往服务端的帧必须掩码，帧可分片承载大消息。

  4. 4

    用 Ping/Pong 控制帧做心跳，检测断线并维持中间设备的连接状态。

  5. 5

    任一方发 Close 帧并带状态码结束；多实例部署时需借助发布订阅在实例间广播。

🔤 03 · 术语
升级握手 (Upgrade Handshake)
用 HTTP 请求把连接切换为 WebSocket 协议。
帧 (Frame)
WebSocket 传输单位，分文本、二进制、控制帧。
掩码 (Masking)
客户端帧必须用随机键异或，防代理缓存投毒。
子协议 (Subprotocol)
经 Sec-WebSocket-Protocol 协商的上层消息格式。
CSWSH
跨站 WebSocket 劫持，因未校验 Origin 被他站建立连接。
背压 (Backpressure)
发送速度超过对端接收时的缓冲控制。
💻 04 · 代码
Node ws 服务端与心跳javascript
// npm i ws
import { WebSocketServer } from 'ws';

const ALLOWED_ORIGINS = new Set(['https://app.example.com']);
const wss = new WebSocketServer({ port: 8080 });

wss.on('connection', (ws, req) => {
  // 防跨站 WebSocket 劫持：校验 Origin（鉴权另需 Cookie 或 token）
  if (!ALLOWED_ORIGINS.has(req.headers.origin)) return ws.close(1008, 'origin');

  ws.isAlive = true;
  ws.on('pong', () => { ws.isAlive = true; });
  ws.on('message', (data) => ws.send(`echo: ${data}`));
});

// 每 30 秒心跳：上一轮没回 pong 的连接视为断开
const timer = setInterval(() => {
  for (const ws of wss.clients) {
    if (!ws.isAlive) { ws.terminate(); continue; }
    ws.isAlive = false;
    ws.ping();
  }
}, 30_000);
wss.on('close', () => clearInterval(timer));

// 浏览器端：const s = new WebSocket('wss://api.example.com/ws');
//          s.onmessage = (e) => console.log(e.data);

Origin 校验防 CSWSH；Ping/Pong 心跳清理半开连接，参考 ws 官方示例。

原生 WebSocket

优点协议标准、开销小

适用团队有能力自管连接层

Socket.IO 等封装库

优点自带重连、房间、降级

适用快速做实时功能

优点免运维，弹性扩容

代价按连接/消息计费

适用连接数波动大

🕳️ 07 · 常见坑

  • ✗不校验 Origin，导致跨站 WebSocket 劫持

    ✓握手时校验 Origin 白名单并做鉴权

  • ✗把 token 放在 URL 查询参数，被访问日志记录

    ✓用 Cookie，或连接后首条消息发送短期 token

  • ✗多实例部署后，消息只发给同实例的连接

    ✓用 Redis Pub/Sub 等在实例间广播

  • ✗空闲连接被负载均衡超时断开

    ✓心跳间隔小于各层空闲超时，客户端指数退避重连

🎤 09 · 面试追问
WebSocket 握手是怎样完成的？

客户端发 GET，带 Upgrade: websocket、Sec-WebSocket-Key 与版本 13。服务端把 key 拼接固定 GUID 后做 SHA-1 再 Base64，作为 Sec-WebSocket-Accept 随 101 返回，此后不再走 HTTP。

WebSocket 如何横向扩展？

连接是有状态的，扩容要解决两点：均衡器支持升级和长连接（会话保持可选）；消息需能送达任意实例上的连接，常用 Redis Pub/Sub、NATS 或 Kafka 做广播，并维护用户到实例的映射。

AI 流式输出该用 WebSocket 还是 SSE？

多数场景用 SSE：只需服务端单向推送 token，基于普通 HTTP，易过代理与鉴权，主流大模型 API 也以 SSE 返回。需要双向实时交互（语音对话、打断、协同）时才选 WebSocket。
