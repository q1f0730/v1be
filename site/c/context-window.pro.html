上下文窗口

Context Window

📐 01 · 定义

上下文窗口（Context Window）是模型单次请求能处理的最大 Token 数，输入（系统提示、历史、工具定义、附件）与输出共同占用这一额度。它是模型的「工作记忆」上限，超出部分要么报错要么被截断。窗口大小由模型架构和训练决定，应用层只能管理放进去的内容。

⚙️ 02 · 原理
  1. 1

    拼装：应用把系统提示、工具定义、历史消息、检索资料、当前问题按顺序拼成一次请求。

  2. 2

    计数：服务端把全部内容分词计数，加上 max_tokens 预留，超过窗口则拒绝或报错。

  3. 3

    注意力计算：模型对窗口内所有 Token 做注意力，长度越长计算和显存开销越大。

  4. 4

    生成输出：输出 Token 也写入同一窗口，生成到上限或停止符为止。

  5. 5

    管理策略：应用层通过截断、摘要、检索、子任务隔离，把最相关的信息留在窗口内。

🔤 03 · 术语
上下文长度 (Context Length)
窗口能容纳的 Token 总数，输入与输出共享。
Lost in the Middle
研究发现模型对长上下文中间位置的信息利用较差的现象。
上下文压缩 (Compaction)
把旧对话总结成摘要以腾出空间，Claude Code 等工具内置此功能。
提示缓存 (Prompt Caching)
缓存重复的提示前缀，降低重复发送长上下文的成本与延迟。
检索增强 (RAG)
只把与问题相关的文档片段检索出来放入窗口，而非全文塞入。
💻 04 · 代码
按预算裁剪历史python
# 保留系统提示 + 最近的若干轮对话，使总 Token 不超预算
import tiktoken

enc = tiktoken.get_encoding("o200k_base")  # 估算用，精确值以模型官方计数为准

def n_tokens(msg):
    return len(enc.encode(msg["content"]))

def trim_history(messages, budget):
    """messages: [{'role':..., 'content':...}]，从最新往回保留"""
    kept, used = [], 0
    for msg in reversed(messages):
        cost = n_tokens(msg)
        if used + cost > budget:
            break
        kept.append(msg)
        used += cost
    return list(reversed(kept))

# 窗口 = 输入 + 输出：预算要扣掉给输出留的 max_tokens
history = [{"role": "user", "content": "..."}]
print(trim_history(history, budget=8000))

最朴素的滑动窗口策略；生产中常配合摘要旧轮次，避免丢失早期关键信息。

📊 05 · 参数对比

上下文管理策略对比

策略原理适用风险
滑动窗口只保留最近 N 轮闲聊、短任务丢失早期约定
摘要压缩旧内容总结成短摘要长对话、长 Agent 会话细节在摘要中丢失
检索增强按需检索相关片段大文档库问答检索不准则答错
子任务隔离子 Agent 独立窗口，只回传结论复杂编码、调研协调成本增加
⚖️ 06 · 方案取舍

直接塞满长上下文

优点实现简单，信息不丢

代价贵、慢，中段信息利用可能变差

适用一次性分析中等长度文档

RAG 检索

优点成本低，可扩展到海量资料

代价需要建索引，检索质量决定上限

适用资料远超窗口或频繁更新

定期摘要压缩

优点会话可无限延续

代价摘要有损，可能遗漏细节

适用长时间运行的 Agent 会话

🕳️ 07 · 常见坑

  • ✗窗口标称很大就把整个代码库塞进去

    ✓只放与任务相关的文件，让 Agent 用搜索工具按需读取

  • ✗忘记输出也占窗口，输入顶满后回复被截断

    ✓输入预算 = 窗口 − max_tokens − 安全余量

  • ✗关键约束只在很早的对话里说过一次

    ✓写进系统提示或项目说明文件（如 CLAUDE.md），每次都在

  • ✗长会话质量下降仍硬撑

    ✓开新会话并带上精炼的任务摘要，比拖着脏上下文更稳

☑️ 08 · 检查清单
🎤 09 · 面试追问
窗口 200K 是否意味着能稳定用满 200K？

不一定。标称值是上限；实际效果受位置偏差影响，长文检索类任务在中段可能变差，且成本和延迟随长度增加。应以自身任务做「大海捞针」类测试，并通过检索和精选内容控制实际长度。

Claude Code 这类 Agent 怎么管理上下文？

按需读取文件而非全量加载；工具输出过长时截断；会话接近上限时自动压缩历史；用子 Agent 处理独立子任务以隔离上下文；用项目说明文件持久化关键约定。核心思路是让窗口里只有当下最相关的信息。

为什么长上下文推理更贵更慢？

标准自注意力计算量随序列长度平方增长，KV 缓存显存随长度线性增长；每生成一个 Token 都要关注全部前文。所以供应商对长输入计价更高或限制更多，提示缓存能显著降低重复前缀成本。
