📐 01 · 定义

gRPC 是 Google 开源的高性能远程过程调用框架，以 HTTP/2 为传输层、默认用 Protocol Buffers 定义接口和序列化消息。通过代码生成，调用远程服务就像调用本地函数。它支持一元调用与三种流式调用、超时传播和拦截器，广泛用于微服务内部通信。

⚙️ 02 · 原理
  1. 1

    在 .proto 文件中定义 service 与方法、请求和响应消息。

  2. 2

    protoc 及语言插件生成客户端存根（stub）和服务端接口代码。

  3. 3

    客户端调用存根，请求被序列化为 Protobuf，作为 HTTP/2 流发送，元数据放在头部。

  4. 4

    服务端反序列化、执行业务逻辑，返回响应与状态码（放在 HTTP/2 trailers 中）。

  5. 5

    截止时间（deadline）随调用传播，超时自动取消；长连接复用承载大量并发调用。

🔤 03 · 术语
存根 (Stub)
生成的客户端代理，封装序列化与网络调用。
一元调用 (Unary RPC)
一个请求对应一个响应。
流式 RPC (Streaming RPC)
服务端流、客户端流、双向流三种模式。
截止时间 (Deadline)
调用必须完成的绝对时间点，超时返回 DEADLINE_EXCEEDED。
元数据 (Metadata)
随调用传递的键值对，类似 HTTP 头。
gRPC-Web
让浏览器经代理调用 gRPC 服务的协议变体。
💻 04 · 代码
Python 客户端调用与超时python
# greeter.proto:
#   service Greeter { rpc SayHello (HelloRequest) returns (HelloReply); }
#   message HelloRequest { string name = 1; }
#   message HelloReply   { string message = 1; }
# 生成代码：pip install grpcio grpcio-tools
#   python -m grpc_tools.protoc -I. --python_out=. --grpc_python_out=. greeter.proto
import grpc
import greeter_pb2, greeter_pb2_grpc

with grpc.insecure_channel("localhost:50051") as channel:   # 内网示例，生产用 TLS
    stub = greeter_pb2_grpc.GreeterStub(channel)
    try:
        reply = stub.SayHello(
            greeter_pb2.HelloRequest(name="Q1f730"),
            timeout=2.0,                                  # 必须设截止时间
            metadata=[("x-request-id", "req-123")],
        )
        print(reply.message)
    except grpc.RpcError as e:
        if e.code() == grpc.StatusCode.DEADLINE_EXCEEDED:
            print("超时")
        elif e.code() == grpc.StatusCode.UNAVAILABLE:
            print("服务不可用，可按策略重试")
        else:
            raise

接口由 .proto 生成；每次调用都设 timeout，并按状态码区分可重试错误。

⚖️ 06 · 方案取舍

gRPC

优点强契约、性能好、原生流式

代价调试不直观，浏览器需代理

适用微服务内部、多语言调用

REST/JSON

优点通用、易调试、生态成熟

代价契约松散，载荷较大

适用对外公开 API

Connect / gRPC-Web

优点复用 proto 契约到浏览器

代价多一层协议与工具链

适用前后端共享 proto

🕳️ 07 · 常见坑

  • ✗调用不设 deadline，下游卡住时请求无限挂起

    ✓每个调用设置截止时间并向下游传播

  • ✗用四层负载均衡，长连接导致流量集中在少数实例

    ✓用七层（如 Envoy）或客户端负载均衡

  • ✗所有错误都返回 UNKNOWN

    ✓按语义映射标准状态码，附带错误详情

  • ✗随意修改 proto 字段编号或类型

    ✓遵循 Protobuf 兼容规则，在 CI 中做破坏性变更检查

🎤 09 · 面试追问
为什么 gRPC 在 Kubernetes 默认 Service 下负载不均？

kube-proxy 做的是四层连接级均衡，而 gRPC 客户端复用一条 HTTP/2 长连接发送所有请求，连接建立后请求全落在同一 Pod。需改用 headless Service 加客户端负载均衡，或经 Envoy/服务网格做请求级均衡。

deadline 和 timeout 有何不同？为什么要传播？

timeout 是相对时长，deadline 是绝对时间点。gRPC 把 deadline 随调用传给下游，下游可得知剩余时间，在上游已放弃时及时取消，避免为已超时的请求继续消耗资源。

gRPC 的四种调用模式分别适合什么？

一元：普通请求响应。服务端流：订阅、大结果分批下发。客户端流：批量上传、遥测上报。双向流：实时对话、协同。流式调用需注意背压与连接寿命管理。
