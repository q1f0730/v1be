健康检查机制

Health Checks

📐 01 · 定义

健康检查（Health Check）是由负载均衡器、容器编排器或监控系统周期性探测服务实例状态的机制，根据结果决定是否转发流量、重启实例或发出告警。它位于运维与流量调度层，通常分为存活检查（是否需要重启）和就绪检查（能否接流量），是自动故障转移与滚动发布的前提。

⚙️ 02 · 原理
  1. 1

    服务暴露健康端点（如 /healthz、/readyz）或可被探测的 TCP 端口、命令。

  2. 2

    探测方按固定周期请求端点，在超时时间内收到成功响应（如 2xx）即记为一次成功。

  3. 3

    连续失败次数达到阈值后判定不健康：就绪失败则摘除流量，存活失败则重启容器。

  4. 4

    启动较慢的服务用启动探针（startup probe）延后其他探针，避免启动中被误杀。

  5. 5

    实例恢复后连续成功达到阈值再重新加入负载均衡，避免状态频繁抖动。

🔤 03 · 术语
存活探针 (Liveness Probe)
判断进程是否卡死，失败则重启容器。
就绪探针 (Readiness Probe)
判断实例能否接流量，失败则从服务端点摘除。
启动探针 (Startup Probe)
启动完成前屏蔽其他探针，保护慢启动应用。
失败阈值 (failureThreshold)
连续失败多少次才判定不健康。
级联故障 (Cascading Failure)
一个依赖故障通过检查连锁导致全体下线。
💻 04 · 代码
Kubernetes 三类探针yaml
apiVersion: v1
kind: Pod
metadata:
  name: api
spec:
  containers:
    - name: api
      image: example/api:1.4.2
      ports: [{ containerPort: 8080 }]
      startupProbe:            # 最多给 30×5=150 秒启动
        httpGet: { path: /healthz, port: 8080 }
        periodSeconds: 5
        failureThreshold: 30
      livenessProbe:           # 只检查进程自身，不查数据库
        httpGet: { path: /healthz, port: 8080 }
        periodSeconds: 10
        timeoutSeconds: 2
        failureThreshold: 3
      readinessProbe:          # 关键依赖不可用时暂停接流量
        httpGet: { path: /readyz, port: 8080 }
        periodSeconds: 5
        failureThreshold: 2

存活只看自身，就绪可看关键依赖，慢启动用 startupProbe 兜住。

📊 05 · 参数对比

三类探针对比

探针失败后动作应检查什么
Liveness重启容器进程是否响应、是否死锁
Readiness摘除流量，不重启初始化完成、关键依赖可用
Startup超限后重启应用是否已完成启动
⚖️ 06 · 方案取舍

浅检查（只返回 200）

优点快速稳定，不受依赖影响

代价发现不了依赖或内部异常

适用Liveness 探针

深检查（含依赖）

优点能反映真实服务能力

代价依赖抖动可能导致全体摘除

适用Readiness 或外部监控

外部合成监控

优点从用户视角验证端到端

代价定位粒度粗，有成本

适用关键用户路径与 SLA 监控

🕳️ 07 · 常见坑

  • ✗存活探针检查数据库，库一抖所有 Pod 被重启

    ✓Liveness 只检查进程自身，依赖检查放到 Readiness

  • ✗超时与阈值过小，GC 停顿就被误判

    ✓按 P99 响应时间设置超时，失败阈值至少数次

  • ✗健康端点需要鉴权或经过限流

    ✓健康端点轻量、免鉴权，仅暴露在内网或不含敏感信息

  • ✗进程收到终止信号仍报告就绪

    ✓优雅停机时先让 Readiness 失败，等流量摘除再退出

🎤 09 · 面试追问
Readiness 检查依赖数据库有什么风险？

数据库短暂抖动会让所有实例同时不就绪，负载均衡无可用后端，局部问题放大为全站不可用。可只检查关键且实例独有的依赖，加缓存结果与容忍阈值，或在全部失败时保留流量。

滚动发布中健康检查起什么作用？

新实例通过 Readiness 才接流量，编排器据此决定是否继续替换旧实例；若新版本始终不就绪，发布会停滞而不是把坏版本推满，为回滚争取时间。

如何实现优雅停机？

收到 SIGTERM 后先让就绪检查失败或从注册中心注销，等待负载均衡摘除并处理完在途请求，再关闭连接和进程；配合 preStop 钩子与足够的终止宽限期。
