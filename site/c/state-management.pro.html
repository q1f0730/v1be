状态管理

State Management

📐 01 · 定义

状态管理是前端应用中组织、共享与更新随时间变化的数据（状态）的方法与工具，涵盖组件局部状态、跨组件共享的客户端状态、来自服务器的数据缓存、URL 状态与表单状态。它属于前端架构层，核心原则是单一数据源、派生而非复制、按作用域就近放置；选错层级是界面不同步类 Bug 的主要来源。

⚙️ 02 · 原理
  1. 1

    组件局部状态（如 useState）保存只与该组件相关的 UI 细节，如弹窗开关、输入框内容。

  2. 2

    多个组件共享的状态上提到共同父级，或放入 Context、Zustand、Redux 等全局 store。

  3. 3

    服务器数据属于服务端状态：用 TanStack Query、SWR 等缓存库管理请求、缓存、失效与重新获取。

  4. 4

    筛选条件、分页等可分享的状态放在 URL 查询参数中，刷新和分享链接都能还原。

  5. 5

    状态更新遵循不可变原则：生成新对象触发重新渲染，派生值在渲染或选择器中计算而不另存。

🔤 03 · 术语
单一数据源 (Single Source of Truth)
同一份数据只在一个地方存储，其余处读取或派生。
派生状态 (Derived State)
可由已有状态计算得出的值，不应另外存储。
服务端状态 (Server State)
来源于服务器、可能过期的数据，需缓存与同步策略。
选择器 (Selector)
从 store 中选取或计算所需片段，减少无关重渲染。
不可变更新 (Immutable Update)
不直接修改原对象，而是返回新对象表示新状态。
💻 04 · 代码
Zustand 购物车 storetypescript
import { create } from "zustand";

type Item = { id: string; qty: number };
type CartState = {
  items: Item[];
  add: (id: string) => void;
  remove: (id: string) => void;
};

export const useCart = create<CartState>()((set) => ({
  items: [],
  add: (id) =>
    set((s) => ({
      items: s.items.some((i) => i.id === id)
        ? s.items.map((i) => (i.id === id ? { ...i, qty: i.qty + 1 } : i))
        : [...s.items, { id, qty: 1 }],   // 不可变更新：返回新数组
    })),
  remove: (id) => set((s) => ({ items: s.items.filter((i) => i.id !== id) })),
}));

// 派生值用选择器计算，不另存 count，避免两份数据不同步
export const useCartCount = () =>
  useCart((s) => s.items.reduce((n, i) => n + i.qty, 0));

export function CartBadge() {
  const count = useCartCount();   // 只在数量变化时重渲染
  return <span>{count}</span>;
}

购物车只存 items，角标数量由选择器派生；商品详情等服务器数据交给请求缓存库。

📊 05 · 参数对比

状态分类与归属

状态类型例子推荐方案
局部 UI 状态弹窗开关、Tab 选中组件内 useState
共享客户端状态登录用户、主题、购物车Context / Zustand / Redux
服务端状态列表、详情数据TanStack Query / SWR
URL 状态搜索词、分页、筛选路由查询参数
表单状态字段值、校验错误表单库或受控组件
⚖️ 06 · 方案取舍

React 内置（state + Context）

优点无依赖，概念少

代价Context 值变化会使所有消费者重渲染

适用中小应用、低频变化的数据

轻量 store（Zustand 等）

优点API 简单，选择器订阅精细

代价缺少强约束，规模大时需自定规范

适用多数中型应用

Redux Toolkit

优点规范严格、调试工具强

代价样板与概念较多

适用大型团队、复杂状态流

🕳️ 07 · 常见坑

  • ✗把服务器数据复制进全局 store 手动同步

    ✓用请求缓存库管理服务端状态与失效

  • ✗同一数据在多个组件各存一份

    ✓上提到共同来源，其余处读取或派生

  • ✗直接修改状态对象（push、赋值属性）

    ✓使用不可变更新，或借助 Immer

  • ✗所有状态都放全局，任何变化都引发大范围重渲染

    ✓就近放置状态，全局 store 用选择器订阅

☑️ 08 · 检查清单
🎤 09 · 面试追问
为什么要区分客户端状态和服务端状态？

服务端状态由服务器拥有，可能被他人修改而过期，需要缓存、去重、后台刷新、失效与重试；客户端状态由前端独占、同步可控。把二者混在同一 store 会导致大量手写同步逻辑与陈旧数据 Bug。

Context 为什么可能造成性能问题？

Provider 的 value 变化时，所有使用该 Context 的组件都会重新渲染，即使只用到其中一个字段。可拆分多个 Context、memo 化 value，或改用支持选择器订阅的 store。

如何决定一个状态放在哪里？

先问能否由已有数据派生；再看谁在用：单组件用局部状态，几个相邻组件上提到父级，跨远距离共享放全局 store；来自服务器的交给缓存库；需要刷新后保留或可分享的放 URL。
