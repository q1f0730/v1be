单体 vs 微服务

Monolith vs Microservices

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

单体与微服务（Monolith vs Microservices）是两种系统架构风格。单体把全部功能构建、部署为一个进程；微服务按业务能力拆成多个独立部署、通过网络通信、各自拥有数据的小服务。这是架构层的取舍：微服务换来独立发布和按需扩展，代价是分布式系统的复杂度和运维成本。

⚙️ 02 · 原理
  1. 1

    单体中模块之间是进程内函数调用，共享一个数据库和事务，一次构建一次部署。

  2. 2

    模块化单体（Modular Monolith）在单体内按领域划清边界，限制跨模块直接访问数据。

  3. 3

    微服务按限界上下文（Bounded Context）拆分，每个服务独立代码库或目录、独立部署、独占数据存储。

  4. 4

    服务间通过 HTTP/gRPC 同步调用或消息异步通信，引入超时、重试、版本兼容等问题。

  5. 5

    拆分常用绞杀者模式（Strangler Fig）：逐步把功能从单体迁到新服务，路由层分流。

🔤 03 · 术语
限界上下文 (Bounded Context)
领域驱动设计中模型含义一致的边界，常作为服务拆分单位。
模块化单体 (Modular Monolith)
单一部署单元，但内部按领域严格分模块、控制依赖。
绞杀者模式 (Strangler Fig)
在旧系统外围逐步用新服务替换功能，直至旧系统可下线。
分布式单体 (Distributed Monolith)
拆成多个服务却高度耦合、必须一起发布，兼具两者缺点。
康威定律 (Conway's Law)
系统结构倾向于复制组织的沟通结构。
💻 04 · 代码
微服务各自拥有数据yaml
# docker-compose.yml：两个服务、两个独立数据库
services:
  orders:
    build: ./orders
    environment:
      DATABASE_URL: postgres://app:pw@orders-db:5432/orders
      INVENTORY_URL: http://inventory:8080   # 通过 API 访问，不直连对方库
    depends_on: [orders-db]
  inventory:
    build: ./inventory
    environment:
      DATABASE_URL: postgres://app:pw@inventory-db:5432/inventory
    depends_on: [inventory-db]
  orders-db:
    image: postgres:16
    environment: { POSTGRES_USER: app, POSTGRES_PASSWORD: pw, POSTGRES_DB: orders }
  inventory-db:
    image: postgres:16
    environment: { POSTGRES_USER: app, POSTGRES_PASSWORD: pw, POSTGRES_DB: inventory }

每个服务独占数据库，跨服务只能走接口，这是微服务与分布式单体的分界。

📊 05 · 参数对比

架构选型对照

维度单体模块化单体微服务
部署一个单元一个单元每服务独立
数据一致性本地事务本地事务最终一致，需 Saga 等
团队规模适配小团队小到中型多个自治团队
运维复杂度低低高：服务发现、追踪、网关
⚖️ 06 · 方案取舍

单体优先

优点开发调试快，事务简单

代价规模变大后耦合重、发布互相牵制

适用新产品、需求快速变化、团队小

模块化单体

优点边界清晰，日后易拆

代价需持续约束依赖纪律

适用预期会增长但还没到多团队

微服务

优点独立发布与扩展，故障隔离

代价网络、一致性、可观测性成本高

适用多团队并行、各部分负载差异大

🕳️ 07 · 常见坑

  • ✗多个服务共用一个数据库表，改字段要所有服务一起发布。

    ✓每个服务独占数据，跨域数据通过 API 或事件同步。

  • ✗按技术层拆服务（前端服务、DB 服务），每个需求都改多个服务。

    ✓按业务能力或限界上下文拆分。

  • ✗服务链路同步调用过深，一个慢全链路慢。

    ✓控制调用深度，非关键路径改为异步事件。

  • ✗没有追踪和集中日志就拆了几十个服务。

    ✓先建好 CI/CD、分布式追踪、集中日志再拆。

🎤 09 · 面试追问
什么时候不应该上微服务？

团队小、领域边界还不稳定、缺乏自动化部署和可观测性时。此时拆分会把需求变更变成跨服务协调，并引入网络故障和一致性问题。Fowler 提出的单体优先就是先做好模块边界再拆。

微服务下如何处理跨服务事务？

避免分布式两阶段提交，常用 Saga：把大事务拆为一系列本地事务，每步发布事件触发下一步，失败时执行补偿操作。配合 outbox 保证事件可靠发出，消费端幂等。

怎么识别分布式单体？

信号包括：多个服务必须同时发布；共享数据库表；一个请求同步串联很多服务；改一个功能要改多个仓库。解决方向是重新划边界、拆数据、改异步。
