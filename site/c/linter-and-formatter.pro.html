代码检查与格式化

Linter & Formatter

📐 01 · 定义

代码检查器（Linter）通过静态分析发现潜在错误、可疑写法和规范违背，如未使用变量、可能的空引用；格式化器（Formatter）只负责统一代码排版，如缩进、换行、引号。二者属于开发工具链的质量层，在编辑器、提交钩子和 CI 中自动运行，是 AI 编码 Agent 获取快速反馈的重要信号。

⚙️ 02 · 原理
  1. 1

    工具把源码解析为抽象语法树（AST），在此基础上分析结构而非简单文本匹配。

  2. 2

    Linter 按规则集遍历 AST，报告问题并标注严重级别，部分规则支持自动修复。

  3. 3

    Formatter 依据 AST 重新输出代码，结果只由代码内容和少量配置决定，与原始排版无关。

  4. 4

    编辑器在保存时运行格式化与检查；提交钩子（如 lint-staged）只处理暂存文件。

  5. 5

    CI 以检查模式运行，发现未格式化或 lint 错误即失败，保证主分支一致。

🔤 03 · 术语
抽象语法树 (AST)
源码的树状结构表示，静态分析工具的基础。
ESLint
JavaScript/TypeScript 主流 Linter，支持插件和自定义规则。
Prettier
约定优于配置的代码格式化器，可选项刻意很少。
Ruff
Rust 编写的 Python Linter 与格式化器，速度很快。
lint-staged
在 Git 提交前只对暂存文件运行检查的工具。
💻 04 · 代码
Python 用 Ruff 检查与格式化bash
# 安装
pip install ruff

# 检查问题（未使用导入、未定义变量等）
ruff check .

# 自动修复可安全修复的问题
ruff check . --fix

# 格式化代码（风格兼容 Black）
ruff format .

# CI 中只检查不修改：有未格式化文件则返回非零退出码
ruff format --check .
ruff check . --output-format=github

同一工具覆盖检查与格式化；CI 使用 --check 模式，本地使用自动修复。

🕳️ 07 · 常见坑

  • ✗Linter 的风格规则与 Formatter 冲突

    ✓关闭 Linter 中的格式类规则，排版交给 Formatter

  • ✗大量 eslint-disable 压掉警告

    ✓修复根因，确需禁用时写明原因并限定范围

  • ✗格式化与功能改动混在同一提交

    ✓单独提交全量格式化，便于审查和 blame

  • ✗只在本地运行，CI 不检查

    ✓CI 中以 check 模式运行并阻止合并

🎤 09 · 面试追问
为什么 Linter 和 Formatter 要分开？

两者目标不同：Formatter 解决排版一致，确定性强、无需讨论；Linter 解决代码质量和潜在错误，需要按项目取舍规则。混用会导致规则冲突和重复报错，社区普遍做法是关闭 Linter 中的格式规则，交给 Formatter 统一处理。

静态分析和类型检查有何区别？

类型检查基于类型系统证明类型层面的一致性，如参数类型匹配；Linter 基于规则模式发现可疑写法，如未处理的 Promise、可能的逻辑错误。两者互补，TypeScript 项目常同时使用 tsc 与 typescript-eslint。

Linter 对 AI 编码有什么价值？

它提供秒级、确定性、机器可读的反馈，Agent 能直接根据错误位置和规则名自我修正；统一的格式化也让 AI 生成的 diff 更干净、易审查。把检查命令写进规则文件，让 Agent 每次改动后运行，可显著减少低级错误。
