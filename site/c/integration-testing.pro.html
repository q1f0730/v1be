集成测试

Integration Testing

📐 01 · 定义

集成测试（Integration Testing）验证多个模块或系统组件组合在一起时能否正确协作，重点是接口与边界：代码与数据库、消息队列、外部 API、文件系统之间的交互。它位于测试金字塔中间层，比单元测试更接近真实环境、能发现映射、配置和协议不一致的问题，又比端到端测试更快、更易定位故障。

⚙️ 02 · 原理
  1. 1

    确定测试边界：选择一组需要真实协作的组件（如服务层 + 仓储层 + 数据库），其余外部依赖用替身或沙箱。

  2. 2

    准备真实或近似真实的依赖，例如用 Docker / Testcontainers 启动临时 PostgreSQL、Redis。

  3. 3

    执行数据库迁移并写入种子数据，让每次测试都从同一个已知的初始状态开始。

  4. 4

    通过公开接口（函数调用或 HTTP 请求）驱动被测流程，断言返回值以及数据库、消息等副作用。

  5. 5

    每个测试结束后回滚事务或清理数据，保证测试彼此独立、可重复、可并行执行。

🔤 03 · 术语
测试金字塔 (Test Pyramid)
大量单元测试、适量集成测试、少量端到端测试的分层结构。
测试替身 (Test Double)
Mock、Stub、Fake 等替代真实依赖的对象。
Testcontainers
在测试代码中启动一次性 Docker 依赖的开源库。
夹具 (Fixture)
测试前后准备与清理环境的可复用代码。
契约测试 (Contract Testing)
验证服务间接口约定，常用于替代部分跨服务集成测试。
💻 04 · 代码
用真实数据库做集成测试python
import pytest
import sqlalchemy as sa
from testcontainers.postgres import PostgresContainer

@pytest.fixture(scope="module")
def engine():
    # 启动临时 PostgreSQL 容器，测试结束自动销毁
    with PostgresContainer("postgres:16") as pg:
        eng = sa.create_engine(pg.get_connection_url())
        with eng.begin() as c:
            c.execute(sa.text("CREATE TABLE users (id serial PRIMARY KEY, email text UNIQUE NOT NULL)"))
        yield eng

def register(conn, email):
    conn.execute(sa.text("INSERT INTO users(email) VALUES (:e)"), {"e": email})

def test_register_writes_row(engine):
    with engine.begin() as c:
        register(c, "a@example.com")
        n = c.execute(sa.text("SELECT count(*) FROM users")).scalar_one()
    assert n == 1

def test_duplicate_email_rejected(engine):
    with pytest.raises(sa.exc.IntegrityError), engine.begin() as c:
        register(c, "a@example.com")   # 唯一约束生效

用真实 PostgreSQL 验证 SQL 与约束行为，这是 Mock 无法覆盖的部分；需要本机 Docker。

📊 05 · 参数对比

三层测试对比

维度单元测试集成测试端到端测试
范围单个函数/类多个组件+真实依赖完整用户流程
速度毫秒级秒级秒到分钟级
定位故障精确较精确困难
发现的问题逻辑错误映射、配置、SQL、协议流程与环境问题
⚖️ 06 · 方案取舍

真实依赖（容器化数据库）

优点行为与生产一致，能测约束和 SQL 方言

代价需要 Docker，速度较慢

适用数据访问层、迁移验证

内存替代（如 SQLite 代替 PostgreSQL）

优点快，无外部依赖

代价方言与约束差异导致假阳性

适用早期原型，不推荐长期使用

Mock 外部服务

优点稳定、可模拟异常

代价可能与真实接口漂移

适用第三方 API，配合契约测试

🕳️ 07 · 常见坑

  • ✗用 SQLite 测试，生产是 PostgreSQL

    ✓使用与生产相同的数据库引擎和主版本

  • ✗测试共享数据、顺序依赖，单独跑就失败

    ✓每个测试独立准备数据，结束后回滚或清理

  • ✗集成测试 Mock 掉所有依赖，名不副实

    ✓明确边界：被测协作链路使用真实依赖

  • ✗连接共享开发库或生产库跑测试

    ✓只使用一次性测试环境，凭据与生产隔离

🎤 09 · 面试追问
集成测试和端到端测试的边界在哪？

集成测试关注一部分组件的协作，通常绕过 UI，直接调用服务或 API，并可替换部分外部依赖；端到端测试从用户界面出发，贯穿整个部署好的系统。前者定位快、稳定性高，后者最接近真实但慢且易不稳定。

为什么不用 SQLite 代替 PostgreSQL 做测试？

两者在类型系统、约束检查、SQL 语法、事务隔离和函数支持上都有差异，测试通过不代表生产可行。容器化真实数据库启动只需数秒，能验证迁移、索引和约束等真实行为，性价比更高。

让 AI 写集成测试时要注意什么？

明确告诉它使用临时测试数据库、禁止连接生产凭据；要求每个测试自行准备与清理数据；检查它是否为了让测试通过而 Mock 掉被测部分或放宽断言。测试应先在改动前失败、改动后通过，才说明有效。
