Redis内存淘汰策略

Redis Eviction Policies

🧸 回到小白版

📐 01 · 定义

Redis 内存淘汰策略决定当内存使用达到 maxmemory 上限时，如何为新写入腾出空间：拒绝写入，还是按近似 LRU、LFU、随机或剩余 TTL 删除部分键。它与过期（TTL 到期删除）是两种不同机制。策略选择直接影响缓存命中率，以及 Redis 被当作存储使用时的数据安全。

⚙️ 02 · 原理
  1. 1

    配置 maxmemory 设定内存上限；写入命令执行前检查是否超限。

  2. 2

    超限时按 maxmemory-policy 选择淘汰对象：allkeys-* 在所有键中选，volatile-* 只在设置了 TTL 的键中选。

  3. 3

    LRU 与 LFU 均为近似算法：每次随机采样若干键（maxmemory-samples，默认 5）选出最该淘汰的。

  4. 4

    LFU 使用对数计数器记录访问频率，并随时间衰减，由 lfu-log-factor 与 lfu-decay-time 调节。

  5. 5

    noeviction（默认）不淘汰，超限后写命令返回 OOM 错误，读命令仍可执行。

🔤 03 · 术语
maxmemory
Redis 可使用的最大内存，达到后触发淘汰策略。
LRU
最近最少使用，淘汰最久未被访问的键。
LFU
最不经常使用，淘汰访问频率最低的键。
volatile-ttl
在有 TTL 的键中优先淘汰剩余时间最短的。
过期 (Expiration)
键到达 TTL 后被删除，与内存是否满无关。
evicted_keys
INFO stats 中累计被淘汰的键数量。
💻 04 · 代码
配置与观察淘汰行为bash
#!/usr/bin/env bash
# 纯缓存场景：设上限并在所有键中按访问频率淘汰
redis-cli CONFIG SET maxmemory 2gb
redis-cli CONFIG SET maxmemory-policy allkeys-lfu
redis-cli CONFIG REWRITE            # 写回 redis.conf，重启后仍生效

# 查看当前配置与内存
redis-cli CONFIG GET 'maxmemory*'
redis-cli INFO memory | grep -E '^(used_memory_human|maxmemory_human|maxmemory_policy):'

# 淘汰与过期是两个计数
redis-cli INFO stats | grep -E '^(evicted_keys|expired_keys):'

# LFU 策略下可查看单个键的访问频率计数
redis-cli OBJECT FREQ product:42

# 估算某个键占用的内存（字节）
redis-cli MEMORY USAGE product:42

# 若 Redis 同时存放会话等不可丢数据，考虑拆实例或改用 volatile-*
# noeviction 下写满会报：OOM command not allowed when used memory > 'maxmemory'

evicted_keys 是被挤掉，expired_keys 是到期删除；OBJECT FREQ 需 LFU 策略。

📊 05 · 参数对比

淘汰策略速查

策略候选范围规则适用
noeviction（默认）—不淘汰，写入报错Redis 作为存储，不能丢数据
allkeys-lru全部键最近最少使用通用缓存
allkeys-lfu全部键访问频率最低热点稳定、长尾明显的缓存
volatile-lru / volatile-lfu有 TTL 的键LRU / LFU缓存与持久数据混存
volatile-ttl有 TTL 的键剩余 TTL 最短TTL 能反映重要性时
⚖️ 06 · 方案取舍

allkeys-lfu

优点抗偶发扫描，保留稳定热点

代价新热点需时间积累频率

适用访问分布稳定的缓存

allkeys-lru

优点对访问模式变化反应快

代价一次全量扫描会冲掉热点

适用热点快速变化

noeviction

优点绝不静默丢数据

代价写满即写入失败

适用队列、会话、锁等关键数据

🕳️ 07 · 常见坑

  • ✗未设置 maxmemory，Redis 用尽系统内存被 OOM Killer 杀掉

    ✓设置 maxmemory，并为持久化 fork 留出余量

  • ✗用 volatile-* 但大部分键没有 TTL，等同不淘汰

    ✓缓存键统一设置 TTL，或改用 allkeys-*

  • ✗缓存与会话、队列共用实例并开 allkeys 淘汰

    ✓按用途拆分实例，关键数据用 noeviction

  • ✗把 evicted_keys 增长当正常现象长期忽略

    ✓持续淘汰说明容量不足，评估扩容或缩短 TTL

☑️ 08 · 检查清单
🎤 09 · 面试追问
Redis 的 LRU 为什么是近似的？

精确 LRU 需要维护全局访问链表，每次访问都调整，内存与 CPU 开销大。Redis 为每个键记录最近访问时间，淘汰时随机采样 maxmemory-samples 个键，淘汰其中最久未访问的，并维护候选池。增大采样数更接近精确 LRU，但更耗 CPU。

LRU 和 LFU 怎么选？

热点稳定、偶有批量扫描时选 LFU，扫描访问一次的键不会挤掉高频热点；热点变化快（如新闻、短期活动）时 LRU 对新热点反应更快。不确定时可在影子环境用真实流量对比命中率。

淘汰和过期有什么区别？

过期是键达到 TTL 后被删除，与内存是否充足无关，Redis 通过访问时惰性检查和后台定期抽样清理。淘汰只在内存超过 maxmemory 时发生，按策略删除可能尚未过期的键。两者分别计入 expired_keys 与 evicted_keys。
