AI 幻觉

Hallucination

🧸 回到小白版

📐 01 · 定义

幻觉（Hallucination）指模型生成流畅、自信但与事实或给定资料不符的内容，如编造论文、API、函数参数或引用。根源在于 LLM 以「生成合理续写」为目标而非检索事实，且缺乏可靠的不确定性表达。它是 LLM 应用最核心的可靠性风险，需在系统设计层面缓解。

⚙️ 02 · 原理
  1. 1

    知识缺口：训练数据未覆盖或已过时，模型仍按语言模式补全出看似合理的答案。

  2. 2

    参数化记忆有损：知识被压缩在权重里，相近概念容易混淆，如把两个库的 API 混用。

  3. 3

    对齐偏差：训练中「给出答案」常被奖励，「不知道」较少被奖励，导致倾向作答。

  4. 4

    解码放大：较高 temperature 增加选中低概率错误 Token 的机会，一步错后续自洽地错。

  5. 5

    上下文不忠实：即使提供了资料，模型也可能忽略或曲解，称为忠实度（Faithfulness）问题。

🔤 03 · 术语
事实性 (Factuality)
输出是否与真实世界知识一致。
忠实度 (Faithfulness)
输出是否忠于提供的资料，而非自行添加内容。
接地 (Grounding)
让回答以检索资料或工具结果为依据，并可追溯来源。
包幻觉 (Package Hallucination)
模型推荐不存在的软件包名，可被攻击者抢注投毒。
校准 (Calibration)
模型表达的置信度与实际正确率是否匹配。
💻 04 · 代码
核实 AI 给的依赖bash
# AI 建议安装某个包时，先核实它真实存在、来源可信

# 1. 查 PyPI 上是否存在及其元信息（不存在会返回 404）
curl -s https://pypi.org/pypi/requests/json | python3 -c \
  "import sys,json; i=json.load(sys.stdin)['info']; print(i['name'], i['version'], i['home_page'] or i['project_urls'])"

# 2. 查 npm 包信息与维护者
npm view express name version repository.url maintainers

# 3. 验证 AI 声称的函数/参数真的存在：直接查看帮助
python3 -c "import json; help(json.dumps)" | head -20

# 4. 安装后跑一遍再信，而不是只看 AI 的解释
python3 -c "import requests; print(requests.__version__)"

防代码幻觉的底线：包名、API、参数都以官方注册表和实际运行结果为准。

手段作用层效果成本

⚖️ 06 · 方案取舍

允许模型回答「不知道」

优点减少编造

代价回答率下降，用户可能不满

适用医疗、法律、金融等高风险场景

强制基于检索资料作答

优点可溯源，忠实度高

代价资料缺失时无法回答

适用企业知识库、客服

多次采样一致性检查

优点能发现不稳定答案

代价成本成倍增加

适用关键判断、离线批处理

🕳️ 07 · 常见坑

  • ✗直接 pip/npm install AI 推荐的陌生包名

    ✓先在官方注册表核实存在、下载量和维护者

  • ✗AI 给了引用链接就当已核实

    ✓实际打开链接，确认内容支持该说法

  • ✗以为接入 RAG 就不会幻觉

    ✓仍需评估忠实度，并要求引用原文片段

  • ✗让 AI 自己检查自己并全盘相信

    ✓用外部信号校验：测试、编译器、检索、人工

🎤 09 · 面试追问
幻觉能被彻底消除吗？

目前不能。生成式模型的概率本质决定了始终有出错概率。工程目标是降低频率并让错误可被发现：接地到检索或工具、结构化输出加校验、关键路径人工复核、对用户展示来源与置信提示。

编码场景如何系统性对抗幻觉？

让 Agent 在真实环境中闭环：读实际源码和文档而非凭记忆、运行类型检查和测试、执行代码看结果；依赖版本以锁文件为准；为 Agent 提供文档检索工具（如 MCP 文档服务）；评审时重点核对新增依赖和外部 API 调用。

如何度量幻觉？

按任务定义：问答类用标注集算事实错误率；RAG 类测忠实度，检查每句话能否在检索内容中找到支撑；代码类看编译通过率和测试通过率。可用 LLM 评审辅助，但需抽样人工校准。
