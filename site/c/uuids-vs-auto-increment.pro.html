UUID与自增主键

UUIDs vs Auto-Increment

🧸 回到小白版

📐 01 · 定义

主键生成策略决定每行记录的唯一标识如何产生：自增整数（Auto-Increment / IDENTITY / SEQUENCE）由数据库按序分配；UUID（RFC 9562）是 128 位标识，可在任意节点独立生成。选择影响索引局部性、存储大小、分布式写入、URL 暴露与数据合并，属于数据建模层的基础决策。

⚙️ 02 · 原理
  1. 1

    自增主键由数据库序列维护计数器，插入时取下一个值，新行总落在 B-tree 索引最右侧。

  2. 2

    序列为性能不参与事务回滚，失败插入会留下空洞，因此自增 ID 不保证连续。

  3. 3

    UUIDv4 为 122 位随机数，可在客户端生成，但随机插入导致索引页分裂与缓存命中下降。

  4. 4

    UUIDv7 高位是 Unix 毫秒时间戳、低位随机，按时间大致有序，兼顾分布式生成与索引局部性。

  5. 5

    存储上 bigint 占 8 字节，UUID 用原生类型占 16 字节，存成字符串则约 36 字节且比较更慢。

🔤 03 · 术语
RFC 9562
2024 年发布的 UUID 规范，取代 RFC 4122，定义了 v6、v7、v8。
UUIDv7
以 Unix 毫秒时间戳开头的 UUID，生成顺序与时间大致一致。
序列 (Sequence)
数据库中生成递增数值的对象，支撑 SERIAL/IDENTITY。
页分裂 (Page Split)
B-tree 页满时拆分为两页，随机键插入会频繁触发。
枚举攻击 (Enumeration)
通过遍历连续 ID 探测或抓取他人资源。
💻 04 · 代码
两种主键的建表写法sql
-- 自增：PostgreSQL 推荐 IDENTITY（SQL 标准），比 SERIAL 更规范
CREATE TABLE orders (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  created_at timestamptz NOT NULL DEFAULT now()
);

-- UUID：用原生 uuid 类型（16 字节），不要存成 varchar
-- gen_random_uuid() 生成 v4，PostgreSQL 13 起内置
CREATE TABLE files (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  name text NOT NULL
);

-- 混合方案：内部 bigint 主键做关联，对外暴露 UUID
CREATE TABLE users (
  id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  public_id uuid NOT NULL UNIQUE DEFAULT gen_random_uuid(),
  email     text NOT NULL
);
-- 需要 UUIDv7 时，可在应用层生成（各语言有成熟库），
-- 或确认所用数据库版本是否已内置 v7 函数

对内用紧凑有序的整数，对外暴露不可猜的 UUID，是常见折中。

📊 05 · 参数对比

主键方案对比

方案大小索引局部性分布式生成
bigint 自增8 字节好（顺序追加）需中心化分配
UUIDv416 字节差（随机）可任意节点生成
UUIDv716 字节较好（时间有序）可任意节点生成
Snowflake 类 ID8 字节好（时间有序）需分配机器号
⚖️ 06 · 方案取舍

bigint 自增

优点最小最快，易读易调试

代价可被枚举，泄露业务量，合库冲突

适用单库、内部表、无需对外暴露

UUIDv4

优点不可猜，客户端可离线生成

代价随机写入，索引膨胀、缓存不友好

适用数据量不大或需离线生成

UUIDv7

优点可分布式生成且大致有序

代价16 字节，泄露创建时间

适用分布式系统、新项目主键

🕳️ 07 · 常见坑

  • ✗把 UUID 存成 varchar(36)

    ✓使用原生 uuid 或 binary(16) 类型，节省空间并加快比较

  • ✗以为自增 ID 连续，用 MAX(id) 统计数量

    ✓回滚和缓存都会产生空洞，计数请用 COUNT 或业务字段

  • ✗对外 URL 直接暴露自增 ID 且无权限校验

    ✓先做对象级权限检查；需要时对外换用 UUID

  • ✗以为 UUID 不可猜就能替代鉴权

    ✓ID 只是标识，访问控制必须独立校验

☑️ 08 · 检查清单
🎤 09 · 面试追问
为什么随机 UUID 做主键会影响写入性能？

B-tree 主键按键序存储，随机键使插入分散到所有页，导致频繁页分裂、写放大和缓冲池命中率下降；InnoDB 聚簇索引下影响更明显。时间有序的 UUIDv7 或自增键能让插入集中在索引尾部。

UUIDv7 有什么需要注意的？

前 48 位是毫秒时间戳，会暴露记录创建时间；依赖生成端时钟，时钟回拨可能破坏有序；同一毫秒内的单调性取决于实现。对外暴露时需评估时间信息是否敏感。

分库分表时自增主键有什么问题？

各分片独立自增会产生重复 ID。可用步长错开、号段服务、Snowflake 类方案或 UUID。迁移、合并数据时也要考虑冲突，因此分布式系统通常优先选去中心化生成。
