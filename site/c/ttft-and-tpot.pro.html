首字延迟与出字速度 (TTFT / TPOT)

TTFT & TPOT

📐 01 · 定义

TTFT（Time To First Token，首 token 延迟）指从发出请求到收到第一个输出 token 的时间；TPOT（Time Per Output Token，每输出 token 时间）指首 token 之后平均每个 token 的生成间隔。二者分别对应推理的预填充（prefill）与解码（decode）阶段，是衡量 LLM 体感速度的核心指标。

⚙️ 02 · 原理
  1. 1

    请求到达后先排队，再进入预填充：模型一次性处理全部输入 token 并建立 KV 缓存，输入越长耗时越久。

  2. 2

    预填充结束产出第一个 token，TTFT = 网络 + 排队 + 预填充时间；流式输出下这正是用户看到首字的时刻。

  3. 3

    随后进入解码：每步生成一个 token，受显存带宽限制，单步耗时相对稳定，平均值即 TPOT。

  4. 4

    总延迟约为 TTFT + TPOT ×（输出 token 数 − 1）；输出越长，TPOT 对总时长的影响越大。

  5. 5

    服务端批量越大，吞吐越高，但单请求 TPOT 往往变慢；需在吞吐与延迟间按 SLO 权衡并看 P50/P99 分布。

🔤 03 · 术语
预填充 (Prefill)
并行处理整段输入并写入 KV 缓存的阶段，决定 TTFT。
解码 (Decode)
逐 token 自回归生成的阶段，决定 TPOT。
ITL (Inter-Token Latency)
相邻两个 token 的到达间隔，TPOT 可视为其平均值。
吞吐 (Throughput)
单位时间内系统生成的 token 总数，常用 tokens/s。
连续批处理 (Continuous Batching)
按 token 步动态加入/移出请求，提高 GPU 利用率。
Prompt Caching
复用相同前缀的 KV 缓存，可明显降低长前缀请求的 TTFT。
💻 04 · 代码
流式调用测 TTFT 与 TPOTpython
import time
from openai import OpenAI

client = OpenAI()  # 读取 OPENAI_API_KEY；兼容接口可传 base_url
start = time.perf_counter()
first, stamps = None, []
stream = client.chat.completions.create(
    model="gpt-4o-mini",  # 示例模型名，以官方文档为准
    messages=[{"role": "user", "content": "用三句话介绍 Redis"}],
    stream=True,
)
for chunk in stream:
    if chunk.choices and chunk.choices[0].delta.content:
        now = time.perf_counter()
        first = first or now
        stamps.append(now)

ttft = first - start
# 注意：一个 chunk 可能含多个 token，这里是按 chunk 的近似值
tpot = (stamps[-1] - first) / max(len(stamps) - 1, 1)
print(f"TTFT={ttft*1000:.0f}ms  TPOT≈{tpot*1000:.1f}ms/chunk")

客户端视角测量：TTFT 含网络与排队；按 chunk 计时只是近似，精确值需按 token 数换算。

⚖️ 06 · 方案取舍

大批量高吞吐

优点单位 token 成本低

代价单请求 TPOT 变慢

适用离线批处理、后台任务

小批量低延迟

优点TTFT、TPOT 都更好

代价GPU 利用率低、成本高

适用实时对话、编程助手

预填充与解码分离部署

优点两阶段互不干扰，延迟更稳

代价架构复杂，需传输 KV 缓存

适用大规模在线推理服务

🕳️ 07 · 常见坑

  • ✗只看平均值，忽视长尾

    ✓报告 P50/P90/P99，并按输入长度分桶分析

  • ✗把每个流式 chunk 当成一个 token

    ✓用 usage 中的输出 token 数换算，或按服务端指标统计

  • ✗压测只用短提示，线上全是长文档

    ✓压测数据的输入/输出长度分布应与线上一致

  • ✗推理模型的“思考”时间未计入体验

    ✓对思考型模型单独衡量首个可见输出时间，必要时展示进度

🎤 09 · 面试追问
为什么长提示主要拖慢 TTFT 而不是 TPOT？

预填充必须处理全部输入 token 才能产出首字，耗时随输入长度增长。解码阶段每步只算一个新 token，虽然要读更长的 KV 缓存会略慢，但主要瓶颈是读取权重的显存带宽，因此对 TPOT 的影响相对较小。

如何在吞吐和延迟之间做取舍？

先按产品定义 SLO，例如交互式聊天要求较低的 TTFT 与 TPOT。然后在满足 P99 SLO 的前提下尽量增大批大小以提高吞吐、降低成本。离线任务没有延迟要求，可以用 Batch API 或大批量换最低单价。

人眼阅读速度对 TPOT 有什么意义？

流式输出时，只要出字速度快于用户阅读速度，体感就是流畅的，继续压低 TPOT 的边际收益有限。此时优化重点应转向 TTFT 和总成本；但对代码生成等需要完整结果的任务，总时长更重要。
