基于角色的访问控制

RBAC

🧸 回到小白版

📐 01 · 定义

基于角色的访问控制（Role-Based Access Control, RBAC）把权限授予角色，再把角色分配给用户，用户通过所属角色获得权限。NIST 将其标准化为核心、层级和约束（职责分离）模型。它属于授权层，用于在组织规模增长时简化权限管理与审计，是企业系统、云平台和 Kubernetes 的主流授权方式。

⚙️ 02 · 原理
  1. 1

    定义权限为对资源的操作，如 invoice:read、invoice:approve。

  2. 2

    按岗位职责定义角色，把一组权限绑定到角色，例如财务、审批人、管理员。

  3. 3

    把角色分配给用户或用户组，用户的有效权限是其所有角色权限的并集。

  4. 4

    请求到达时，授权层检查当前用户的有效权限是否包含所需权限，并结合资源归属判断。

  5. 5

    通过角色层级继承减少重复配置，用职责分离约束防止同一人兼任冲突角色。

🔤 03 · 术语
权限 (Permission)
对某类资源执行某个操作的许可。
角色层级 (Role Hierarchy)
高级角色继承低级角色的权限。
职责分离 (SoD)
禁止同一用户同时拥有相互冲突的角色。
ABAC
基于属性的访问控制，按用户、资源、环境属性动态判断。
角色爆炸 (Role Explosion)
为细分场景不断新增角色导致难以管理。
💻 04 · 代码
权限检查装饰器python
from functools import wraps

ROLE_PERMS = {
    "viewer":   {"invoice:read"},
    "accountant": {"invoice:read", "invoice:create"},
    "approver": {"invoice:read", "invoice:approve"},
}
SOD_CONFLICTS = [{"accountant", "approver"}]   # 职责分离：不能既创建又审批

def perms_of(user) -> set[str]:
    return set().union(*(ROLE_PERMS[r] for r in user["roles"]))

def assign_role(user, role):
    new = set(user["roles"]) | {role}
    if any(c <= new for c in SOD_CONFLICTS):
        raise PermissionError("违反职责分离")
    user["roles"] = sorted(new)

def require(perm):
    def deco(fn):
        @wraps(fn)
        def wrapper(user, *args, **kwargs):
            if perm not in perms_of(user):   # 检查权限，而不是检查角色名
                raise PermissionError(f"缺少权限 {perm}")
            return fn(user, *args, **kwargs)
        return wrapper
    return deco

@require("invoice:approve")
def approve_invoice(user, invoice_id): pass

代码检查权限而非角色名，角色调整无需改代码；职责分离在分配角色时校验。

📊 05 · 参数对比

授权模型对比

模型判断依据优点不足
ACL资源上的用户列表直观、粒度细规模大时难管理
RBAC用户的角色易管理、易审计难表达动态条件
ABAC用户/资源/环境属性灵活，可表达复杂规则策略复杂难审计
ReBAC用户与资源的关系图适合共享与协作场景需要专门的关系存储
⚖️ 06 · 方案取舍

纯 RBAC

优点简单清晰，审计方便

代价无法表达「只能改自己的」

适用内部系统、后台管理

RBAC + 资源归属检查

优点兼顾管理性与对象级控制

代价需在业务层实现归属判断

适用大多数 SaaS 应用

策略引擎（如 OPA）

优点统一、可测试的授权策略

代价引入新组件与学习成本

适用多服务、规则复杂

🕳️ 07 · 常见坑

  • ✗代码里写 if role == "admin"

    ✓检查具体权限，角色与权限映射放在配置或数据库中

  • ✗为每个特殊需求新建角色，角色数量失控

    ✓定期合并角色，动态条件交给属性或归属检查

  • ✗只做功能级 RBAC，未检查资源归属

    ✓在权限检查之外校验用户是否有权访问该具体对象

  • ✗只在前端隐藏按钮

    ✓每个后端接口都执行授权检查

🎤 09 · 面试追问
RBAC 和 ABAC 如何结合？

用 RBAC 决定用户能做哪类操作，用属性条件进一步限制范围，例如审批人只能审批本部门且金额低于阈值的发票。实现上可由策略引擎统一评估角色与属性。

什么是最小权限原则在 RBAC 中的体现？

角色只包含完成职责所需的权限；用户只分配当前需要的角色；临时提权有时限并留审计记录；定期复核并回收不再需要的角色，避免权限随时间累积。

Kubernetes 的 RBAC 有哪些核心对象？

Role 与 ClusterRole 定义对资源的动词权限（命名空间级与集群级），RoleBinding 与 ClusterRoleBinding 把角色绑定到用户、组或 ServiceAccount。授权是纯允许式的，没有拒绝规则。
