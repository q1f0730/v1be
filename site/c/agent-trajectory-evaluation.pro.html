智能体轨迹评测

Agent Trajectory Evaluation

📐 01 · 定义

轨迹评测（Trajectory Evaluation）是 Agent 评测的一种，除了检查最终结果，还检查 Agent 执行过程中的工具调用序列、参数、中间推理与副作用。它能发现「结果对但过程错」的问题，如走捷径、越权操作、冗余调用和成本失控，是 Agent 上线前评审与回归测试的关键环节。

⚙️ 02 · 原理
  1. 1

    通过日志或追踪（如 OpenTelemetry span）完整记录每一步：工具名、参数、返回值、耗时与 Token 消耗。

  2. 2

    为评测用例定义参考轨迹或约束：必须调用的工具、禁止的动作、允许的顺序关系。

  3. 3

    用确定性规则比对：精确匹配、按序包含、无序包含、子集/超集，或计算工具调用的精确率与召回率。

  4. 4

    对难以规则化的部分，用 LLM 评审（LLM-as-a-judge）按评分细则判断每步是否合理。

  5. 5

    汇总过程指标与结果指标，并多次重复运行，评估非确定性带来的稳定性差异。

🔤 03 · 术语
轨迹 (Trajectory)
Agent 从接收任务到结束的完整动作序列，含思考、工具调用与观察。
按序匹配 (In-order Match)
参考轨迹的步骤按相同顺序出现在实际轨迹中，允许中间有额外步骤。
工具调用精确率/召回率
实际调用中正确调用的占比，与参考调用被覆盖的占比。
pass^k
同一任务连续 k 次都成功的概率，衡量 Agent 的稳定性，见 τ-bench。
副作用检查 (Side-effect Check)
核验环境最终状态，如数据库是否被误改，而不只看文本输出。
💻 04 · 代码
规则化轨迹打分python
# 每一步记录为 (工具名, 参数) ；示例为纯 Python，无第三方依赖
FORBIDDEN = {"delete_file", "git_push_force"}

def in_order_match(actual, reference):
    """reference 中的工具按顺序出现在 actual 中即可"""
    it = iter(name for name, _ in actual)
    return all(ref in it for ref in reference)

def score(actual, reference):
    names = [n for n, _ in actual]
    hits = sum(1 for r in reference if r in names)
    return {
        "in_order": in_order_match(actual, reference),
        "recall": hits / len(reference),
        "forbidden": sorted(FORBIDDEN & set(names)),
        "steps": len(actual),          # 冗余步骤也要关注
    }

actual = [("read_file", {"path": "app.py"}), ("edit_file", {}),
          ("delete_file", {"path": "test_app.py"}), ("run_tests", {})]
print(score(actual, ["read_file", "edit_file", "run_tests"]))
# in_order=True，但 forbidden=['delete_file']，应判定失败

结果与顺序都对，但删除了测试文件；轨迹规则能抓到仅看结果会漏掉的违规。

📊 05 · 参数对比

轨迹匹配模式对比

模式判定条件适用场景
精确匹配工具序列完全一致流程固定的业务操作
按序匹配参考步骤按顺序出现关键步骤有先后依赖
无序匹配参考步骤都出现即可步骤可并行或顺序无关
约束检查无禁止动作、步数与成本在上限内安全与成本兜底
LLM 评审按评分细则判断合理性开放式任务、路径多样
⚖️ 06 · 方案取舍

确定性规则匹配

优点可复现、便宜、易进 CI

代价合理的替代路径会被误判

适用流程明确、工具集小的 Agent

LLM 评审轨迹

优点能评价开放路径的合理性

代价有偏差和成本，需校准

适用编码、研究等路径多样的任务

只评最终状态

优点实现最简单

代价漏掉作弊、越权与浪费

适用仅作为结果指标的一部分

🕳️ 07 · 常见坑

  • ✗参考轨迹写得过死，Agent 更优的路径被判失败

    ✓关键步骤用按序或无序匹配，其余用约束和结果检查兜底

  • ✗只跑一次就下结论

    ✓每个用例多次运行，统计成功率与 pass^k

  • ✗评测只看文本输出，没核对环境状态

    ✓在沙箱中检查文件、数据库等最终状态与副作用

  • ✗日志缺失工具参数，事后无法复盘

    ✓结构化记录每步参数、返回与耗时，敏感字段脱敏

🎤 09 · 面试追问
为什么 Agent 评测不能只看最终答案？

Agent 有副作用：结果正确时也可能删了测试、越权读文件、调用付费接口几十次。只看结果会把这些作弊和风险当成功。轨迹评测补上过程维度，同时能定位失败发生在哪一步，便于改提示或工具。

参考轨迹不唯一时怎么评？

把轨迹拆成硬约束和软评价：硬约束如必须先读后写、禁止危险动作、步数上限用规则检查；路径选择是否合理交给 LLM 评审按细则打分，并用人工标注样本校准评审一致性。

τ-bench 的 pass^k 想说明什么？

它要求同一任务 k 次都成功，衡量可靠性而非偶尔成功。Agent 输出非确定，单次通过率高不代表稳定；面向真实用户的客服、运维 Agent 更关心一致性，pass^k 随 k 增大下降越快说明越不稳。
