法定人数机制

Quorums

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

法定人数机制（Quorum）是复制系统中规定一次读或写必须得到多少个副本确认才算成功的规则。设副本数 N、写需确认数 W、读需确认数 R，当 W + R > N 时读写集合必然相交，读能看到最新写入。它让系统在部分副本故障时仍可工作，并在一致性、延迟与可用性之间调节。

⚙️ 02 · 原理
  1. 1

    数据复制到 N 个副本节点，通常分布在不同机架或可用区以隔离故障。

  2. 2

    写入：请求发往全部副本，收到至少 W 个确认即向客户端返回成功。

  3. 3

    读取向副本发请求，收到至少 R 个响应后按版本号或时间戳选出最新值。

  4. 4

    W + R > N 保证读集合与最近写集合至少重叠一个副本，从而读到最新值。

  5. 5

    读修复与后台反熵把落后的副本补齐，确认数不足时请求以失败返回。

🔤 03 · 术语
N / W / R
副本数、写入确认数、读取响应数三个可调参数。
严格法定人数 (Strict Quorum)
读写只计入数据真正归属的 N 个副本。
宽松法定人数 (Sloppy Quorum)
归属副本不可达时临时写入其他节点，提高可用性。
提示移交 (Hinted Handoff)
临时节点暂存写入，归属副本恢复后再转交给它。
LOCAL_QUORUM
Cassandra 中只在本数据中心内取多数，避免跨地域延迟。
💻 04 · 代码
Cassandra 一致性级别sql
-- cqlsh：keyspace 每个数据中心 3 副本
CREATE KEYSPACE shop WITH replication =
  {'class': 'NetworkTopologyStrategy', 'dc1': 3};

-- QUORUM = floor(3/2)+1 = 2
-- 写 QUORUM + 读 QUORUM：2 + 2 > 3，读能看到已确认的写
CONSISTENCY QUORUM;
INSERT INTO shop.carts (user_id, item, qty) VALUES (42, 'book', 1);
SELECT * FROM shop.carts WHERE user_id = 42;

-- 读 ONE：延迟最低、可用性最高，但可能读到旧值（1 + 2 = 3，不大于 3）
CONSISTENCY ONE;
SELECT * FROM shop.carts WHERE user_id = 42;

-- 多数据中心时常用 LOCAL_QUORUM，避免跨地域往返
CONSISTENCY LOCAL_QUORUM;

CONSISTENCY 是 cqlsh 命令，驱动中按语句设置；W+R>N 才保证读到最新确认写入。

📊 05 · 参数对比

N=3 时的组合

W / R是否重叠特点
W=2, R=2是读写均衡，常见默认
W=3, R=1是读快，任一副本故障即不可写
W=1, R=3是写快，读需全部副本在线
W=1, R=1否延迟最低，可能读到旧值
⚖️ 06 · 方案取舍

多数派读写

优点容忍少数副本故障且读到最新

代价每次操作等待多个副本

适用大多数需要较强一致的数据

低 W/R

优点延迟低、可用性高

代价可能读到旧值

适用计数、日志、可容忍陈旧

宽松法定人数

优点分区时仍可写

代价W+R>N 不再保证读到最新

适用购物车等写可用性优先

🕳️ 07 · 常见坑

  • ✗以为 W+R>N 就等于线性一致

    ✓并发写、失败写的部分残留仍可能导致异常，需版本与读修复配合

  • ✗写失败后客户端以为没写入，但部分副本已写

    ✓写失败结果视为不确定，重试需幂等

  • ✗多数据中心使用 QUORUM，每次跨地域等待

    ✓按需使用 LOCAL_QUORUM，并明确跨地域一致性需求

☑️ 08 · 检查清单
🎤 09 · 面试追问
为什么 W+R>N 能读到最新写？

成功的写入至少落在 W 个副本上，读取会询问 R 个副本；W+R>N 时两个集合必然至少有一个副本相同，读到的响应中至少一个包含该写入，再按版本号选出最新值返回。

宽松法定人数有什么代价？

分区时写入可落到非归属节点并靠提示移交补回，提高了写可用性；但此时 W 个确认并不在 N 个归属副本中，读的 R 个副本可能都不含新值，W+R>N 的保证失效，只能保证最终一致。

Raft 的多数派和 Dynamo 式 Quorum 有何不同？

Raft 由领导者对日志排序，多数派复制后提交，提供线性一致；Dynamo 式无领导者，客户端或协调者并行写多个副本，没有全局顺序，需要版本向量或 LWW 处理冲突，通常只提供可调的最终一致。
