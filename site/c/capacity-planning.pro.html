容量规划工程

Capacity Planning

🧸 回到小白版

📐 01 · 定义

容量规划（Capacity Planning）是根据业务增长预测和系统性能模型，提前确定需要多少计算、存储、网络与数据库资源，以在满足 SLO 的前提下控制成本的工程活动。它结合历史数据、压测结果、排队论估算和冗余要求（如 N+1），回答「何时、加多少、加在哪」。

⚙️ 02 · 原理
  1. 1

    测基线：采集当前流量、资源利用率与延迟，找出对容量最敏感的瓶颈资源。

  2. 2

    建模型：通过压测得到单实例在满足延迟 SLO 时能承受的最大吞吐。

  3. 3

    预测需求：结合历史增长趋势、季节性峰值和业务活动计划估算未来峰值流量。

  4. 4

    加冗余：考虑 N+1 或可用区故障、发布期间实例减少，并预留突发余量。

  5. 5

    执行复盘：提前采购或配置扩容策略，定期对比预测与实际值并修正模型。

🔤 03 · 术语
利特尔法则 (Little's Law)
L = λW：系统内平均请求数等于到达率乘以平均停留时间。
余量 (Headroom)
峰值负载之外为突发和故障预留的容量。
N+1 冗余
在满足需求的 N 份资源外再多备一份以容忍单点故障。
拐点 (Knee Point)
利用率超过某值后延迟急剧上升的位置。
负载测试 (Load Testing)
按预期或更高流量施压，测量吞吐与延迟关系。
💻 04 · 代码
估算实例数python
import math

peak_rps = 1200          # 预测峰值每秒请求数（含活动增长）
latency_s = 0.15         # 平均处理耗时
per_inst_max_rps = 180   # 压测得出：单实例 p99 仍达标时的最大吞吐
target_util = 0.6        # 只用到 60%，远离延迟拐点
zones = 3                # 跨 3 个可用区，需容忍丢失 1 个

# 利特尔法则：系统中同时在处理的请求数
concurrency = peak_rps * latency_s
needed = peak_rps / (per_inst_max_rps * target_util)
# 丢失一个可用区后剩余实例仍需扛住峰值
total = math.ceil(needed * zones / (zones - 1))

print(f"并发约 {concurrency:.0f}，正常需 {math.ceil(needed)} 台，"
      f"考虑可用区故障共需 {total} 台")

所有输入都应来自压测与监控；N+1 和目标利用率决定了最终余量。

🕳️ 07 · 常见坑

  • ✗按 CPU 利用率规划，忽视数据库连接、带宽等真实瓶颈

    ✓压测找出首个饱和资源，以其为规划依据

  • ✗把利用率目标定到 90% 以上

    ✓考虑排队效应和故障冗余，常见目标显著低于满载

  • ✗只扩应用层，下游数据库和第三方配额跟不上

    ✓沿调用链评估所有依赖的容量与限额

  • ✗依赖自动扩缩应对秒级突发

    ✓提前预热，并设置最小实例数和扩容余量

🎤 09 · 面试追问
为什么不能把服务器用到 100%？

排队论表明利用率接近 100% 时排队等待时间急剧增长，延迟远超 SLO；突发流量和实例故障也需要余量。此外 N+1 冗余要求故障后剩余资源能承担全部负载，因此正常利用率必须留出空间。

如何确定单实例容量？

在接近生产的环境做阶梯压测，逐步增加负载，记录吞吐与 p99 延迟、错误率，找到延迟或错误率超出 SLO 前的最大吞吐作为容量上限，同时记录首先饱和的资源。

大促容量规划你会怎么做？

根据历史大促与业务目标估算峰值倍数；全链路压测找瓶颈；为数据库、缓存、消息队列和第三方接口确认容量；提前扩容和预热；准备限流、降级与熔断预案；活动中实时监控并复盘。
