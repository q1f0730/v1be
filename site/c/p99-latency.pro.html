99分位长尾延迟

p99 Latency

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

p99 延迟（99th Percentile Latency）是把一段时间内的请求耗时排序后第 99 百分位的值，即 99% 的请求不超过它、最慢的 1% 超过它。它是衡量长尾延迟的核心指标，比平均值更能反映真实用户体验。在扇出调用中，一个用户请求依赖多个后端，任一后端的长尾都会放大为用户侧的高延迟。

⚙️ 02 · 原理
  1. 1

    服务记录每个请求的耗时，通常用直方图（Histogram）按桶计数而非保存每个值。

  2. 2

    查询时按时间窗口聚合各实例的直方图，估算目标分位数，如 p50、p95、p99。

  3. 3

    平均值会被大量快请求稀释，而 p99 揭示最慢一批用户的真实等待。

  4. 4

    扇出放大：若一个请求并行调用 100 个后端，每个后端 p99 慢，用户请求变慢的概率就很高。

  5. 5

    长尾成因包括 GC 停顿、排队、锁竞争、冷缓存、慢磁盘和网络重传。

🔤 03 · 术语
百分位数 (Percentile)
排序后位于某百分比位置的值，p99 表示第 99 百分位。
长尾延迟 (Tail Latency)
分布中最慢那部分请求的延迟。
直方图 (Histogram)
把观测值落入预设桶计数，可在服务端聚合后估算分位数。
对冲请求 (Hedged Request)
请求超过一定时间未返回时向另一副本再发一次，取先到者。
分位数不可平均
多个实例的 p99 不能直接求平均，需合并原始分布再计算。
💻 04 · 代码
平均值掩盖长尾python
import numpy as np

rng = np.random.default_rng(0)
# 98% 请求约 50ms，2% 请求遇到 GC/排队约 2s
fast = rng.normal(50, 10, 9_800)
slow = rng.normal(2_000, 200, 200)
latency_ms = np.concatenate([fast, slow])

print(f"mean = {latency_ms.mean():.0f} ms")            # 约 90ms，看着还行
print(f"p50  = {np.percentile(latency_ms, 50):.0f} ms")
print(f"p99  = {np.percentile(latency_ms, 99):.0f} ms")  # 约 2s，真实长尾

# Prometheus 中按直方图计算 p99（先按 le 聚合所有实例再求分位）：
# histogram_quantile(0.99,
#   sum by (le) (rate(http_request_duration_seconds_bucket[5m])))

平均值只有约 90ms，p99 却接近 2 秒；Prometheus 用直方图在聚合后求分位。

🕳️ 07 · 常见坑

  • ✗把各实例的 p99 取平均当作全局 p99。

    ✓合并直方图桶后再计算分位数。

  • ✗直方图桶边界与 SLO 阈值不匹配，估算误差大。

    ✓在 SLO 阈值附近设置桶边界。

  • ✗只在低流量时段看 p99，样本太少波动大。

    ✓确保窗口内样本量足够，或看更长窗口。

  • ✗压测工具存在协调遗漏，p99 被低估。

    ✓使用固定到达率模型或做校正。

☑️ 08 · 检查清单
🎤 09 · 面试追问
为什么用 p99 而不是平均延迟？

延迟分布通常右偏，少量很慢的请求对平均值影响有限，却严重影响这部分用户。高频用户在一次会话中会发出很多请求，几乎必然碰到长尾。p99 能直接暴露这部分体验，更适合作为 SLO。

扇出为什么会放大长尾？

若一个用户请求要等 N 个后端全部返回，用户请求的延迟取决于最慢的那个。即使每个后端只有 1% 的请求慢，N 很大时至少一个慢的概率接近 1 减 0.99 的 N 次方，比如 N 为 100 时约 63%。

有哪些降低长尾延迟的手段？

减少 GC 停顿与锁竞争；限制队列长度避免排队；预热缓存；对冲请求或绑定请求在多个副本间竞速；把慢操作移出关键路径；对扇出调用设置截止时间并允许部分结果。
