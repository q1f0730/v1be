精确一次语义 (EOS)

Exactly-Once Semantics

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

精确一次语义（Exactly-Once Semantics，EOS）指每条消息对最终结果的影响恰好发生一次，既不丢也不重复。网络与故障下「投递」本身难以只发生一次，因此实践中靠至少一次投递加幂等或事务实现「效果上的精确一次」。Kafka 通过幂等生产者与事务在其内部读-处理-写链路上提供该保证。

⚙️ 02 · 原理
  1. 1

    幂等生产者：broker 按生产者 ID 与序列号去重，生产者重试不会产生重复写入。

  2. 2

    事务写入：生产者以 transactional.id 开启事务，把多分区写入原子提交或中止。

  3. 3

    偏移量入事务：消费位点通过 sendOffsetsToTransaction 与输出消息一起提交。

  4. 4

    隔离读取：下游消费者设置 isolation.level=read_committed，只读已提交事务的消息。

  5. 5

    外部系统：写数据库等外部系统时，需用幂等写入或把位点与结果存入同一事务。

🔤 03 · 术语
至少一次 (At-least-once)
失败会重试，保证不丢但可能重复。
至多一次 (At-most-once)
不重试，保证不重复但可能丢失。
幂等生产者 (Idempotent Producer)
通过 PID 与序列号让 broker 丢弃重复的重试写入。
transactional.id
跨重启稳定的事务标识，用于隔离旧实例（僵尸实例）。
read_committed
消费者隔离级别，跳过未提交或已中止事务的消息。
💻 04 · 代码
Kafka 事务性读-处理-写python
from confluent_kafka import Consumer, Producer

consumer = Consumer({"bootstrap.servers": "kafka:9092", "group.id": "enricher",
                     "enable.auto.commit": False,
                     "isolation.level": "read_committed"})
producer = Producer({"bootstrap.servers": "kafka:9092",
                     "transactional.id": "enricher-1"})  # 隐含开启幂等
consumer.subscribe(["orders"])
producer.init_transactions()

while True:
    msg = consumer.poll(1.0)
    if msg is None or msg.error():
        continue
    producer.begin_transaction()
    producer.produce("orders-enriched", key=msg.key(), value=msg.value().upper())
    # 把消费位点与输出放进同一事务，原子提交
    producer.send_offsets_to_transaction(
        consumer.position(consumer.assignment()),
        consumer.consumer_group_metadata())
    producer.commit_transaction()      # 异常时应 abort_transaction() 并重处理

输出消息与消费位点同事务提交，崩溃重启后不会出现输出了却未记位点的重复。

📊 05 · 参数对比

三种投递语义

语义实现方式风险
至多一次先提交位点再处理处理失败即丢消息
至少一次处理完再提交位点崩溃后重复处理
精确一次（效果）至少一次 + 幂等/事务实现复杂，有性能开销
⚖️ 06 · 方案取舍

Kafka 事务

优点Kafka 内部链路端到端精确一次

代价吞吐下降、延迟增加，不覆盖外部系统

适用Kafka 到 Kafka 的流处理

至少一次 + 幂等消费

优点通用、简单，适用任何下游

代价需要设计幂等键与去重存储

适用写数据库、调第三方 API

位点与结果同库事务

优点对数据库下游实现精确一次

代价消费者需自管位点

适用结果写入关系型数据库

🕳️ 07 · 常见坑

  • ✗以为开启 Kafka 事务后，写数据库和调外部 API 也只会一次

    ✓事务仅覆盖 Kafka 内部，外部副作用需幂等或同库事务

  • ✗下游消费者仍用默认 read_uncommitted，读到中止事务数据

    ✓消费事务性主题时设置 isolation.level=read_committed

  • ✗transactional.id 随机生成，重启后无法隔离僵尸实例

    ✓按实例或分区使用稳定的 transactional.id

🎤 09 · 面试追问
真正的「精确一次投递」可能吗？

在不可靠网络中，发送方无法区分消息丢失还是确认丢失，只能重试，因此投递层面最多做到至少一次。所谓精确一次是处理效果层面：通过去重、幂等或原子事务，使重复投递不产生重复影响。

Kafka 幂等生产者怎么去重？

每个生产者获得 PID，发往每个分区的消息带递增序列号；broker 记录各 PID 在该分区最近的序列号，收到重复或乱序序列号即拒绝或丢弃，从而消除重试带来的重复写入。

消费 Kafka 写 MySQL 如何做到效果上一次？

方式一：业务写入幂等，如用消息唯一 ID 做唯一键或 upsert；方式二：把消费位点存进 MySQL，与业务数据同一事务提交，启动时从库中读取位点继续消费。
