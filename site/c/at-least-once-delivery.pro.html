至少一次投递语义

At-Least-Once Delivery

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

至少一次投递（At-Least-Once Delivery）是消息传递语义的一种：系统保证每条消息最终至少被处理一次，但在超时、重试或消费者崩溃时可能重复投递。它位于消息系统与消费者的契约层，用重复换取不丢失，要求消费端实现幂等（Idempotency）来消化重复。

⚙️ 02 · 原理
  1. 1

    生产者发送消息后等待中间件确认，超时未收到确认就重发，此时可能产生重复写入。

  2. 2

    消费者取到消息先执行业务逻辑，成功后再确认（ack）或提交位移。

  3. 3

    若处理完成但确认前崩溃，中间件认为未处理，会把同一条消息重新投递。

  4. 4

    消费者用消息 ID 或业务唯一键去重，已处理过的直接确认跳过，从而得到有效一次的结果。

  5. 5

    与之对比，先确认后处理是至多一次（At-Most-Once），崩溃会丢消息但不会重复。

🔤 03 · 术语
至多一次 (At-Most-Once)
消息最多处理一次，可能丢失但不会重复。
恰好一次 (Exactly-Once)
每条消息效果只生效一次，通常靠幂等加事务在特定范围内实现。
幂等消费者 (Idempotent Consumer)
重复处理同一消息结果不变的消费者，常用去重表实现。
确认 (Acknowledgement)
消费者告诉中间件消息已处理完成、可以删除的信号。
事务性发件箱 (Transactional Outbox)
业务数据与待发消息同库同事务写入，再异步投递，避免双写不一致。
💻 04 · 代码
去重表实现幂等消费sql
-- 记录已处理过的消息 ID（PostgreSQL）
CREATE TABLE processed_messages (
  message_id   TEXT PRIMARY KEY,
  processed_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 在同一事务里：先占位去重，再执行业务
BEGIN;
INSERT INTO processed_messages (message_id)
VALUES ('msg-7f3a')
ON CONFLICT (message_id) DO NOTHING;
-- 应用代码检查受影响行数：
--   0 行 = 重复消息，ROLLBACK 后直接 ack
--   1 行 = 首次处理，继续执行下面的业务 SQL
UPDATE accounts SET balance = balance - 100 WHERE id = 42;
COMMIT;

去重记录与业务更新同事务提交，重复投递时插入失败即可安全跳过。

📊 05 · 参数对比

三种投递语义对比

语义确认时机风险典型场景
至多一次处理前确认崩溃时丢消息指标采样、日志
至少一次处理后确认重复处理订单、支付通知等主流业务

⚖️ 06 · 方案取舍

至少一次 + 幂等

优点不丢数据，实现成熟

代价每个消费者都要做去重

适用大多数业务消息的默认选择

至多一次

优点无重复，吞吐高

代价故障时会丢消息

适用丢一些也无所谓的数据

中间件事务（如 Kafka EOS）

优点读-处理-写闭环内效果一次

代价仅限同一系统内，外部副作用仍需幂等

适用Kafka 到 Kafka 的流处理

🕳️ 07 · 常见坑

  • ✗以为用了 SQS 标准队列就不会重复，没做去重。

    ✓按官方说明，标准队列可能重复投递，消费端必须幂等。

  • ✗用时间戳加随机数当去重键，重发时生成了新键。

    ✓去重键由生产者在首次创建消息时生成并随消息传递。

  • ✗去重记录和业务写入不在一个事务里。

    ✓放进同一数据库事务，或使用带条件的原子更新。

  • ✗去重表无限增长，拖慢查询。

    ✓按重投窗口设置过期清理，例如保留数天到数周。

🎤 09 · 面试追问
为什么分布式系统很难做到真正的恰好一次？

网络无法区分对方没收到和确认丢了，发送方只能重试或放弃。所以端到端只能在至少一次基础上，用幂等或事务让效果只生效一次；一旦涉及发邮件、调第三方等外部副作用，就必须靠幂等键。

Kafka 的幂等生产者解决了什么？

它为生产者分配 ID 并给每条消息编序号，broker 丢弃重复序号，从而消除生产者重试导致的分区内重复。Kafka 3.0 起 enable.idempotence 默认开启。它不解决消费端重复处理的问题。

Outbox 模式和至少一次有什么关系？

业务数据和待发消息写进同一事务的 outbox 表，再由中继进程投递。中继可能重复发送，所以下游仍是至少一次，但它保证了不会出现数据已提交而消息没发出去的不一致。
