HTTP状态码语义

HTTP Status Codes

📐 01 · 定义

HTTP 状态码（Status Code）是服务器在响应行里返回的三位整数，属于应用层协议语义，由 RFC 9110 统一定义。首位数字划分五个类别（1xx 信息、2xx 成功、3xx 重定向、4xx 客户端错误、5xx 服务端错误），让客户端、代理、缓存和监控系统无需解析响应体就能判断结果并决定下一步动作。

⚙️ 02 · 原理
  1. 1

    客户端发出请求，服务器处理后在响应首行写入状态码和原因短语，如 HTTP/1.1 404 Not Found；HTTP/2 起不再传原因短语。

  2. 2

    首位数字决定通用处理逻辑：客户端遇到未知的 4xx 码时，必须按该类的 x00（即 400）处理。

  3. 3

    3xx 配合 Location 头驱动跳转；301/308 表示永久，302/307 表示临时，307/308 要求保持原请求方法和请求体。

  4. 4

    缓存层依据状态码判断能否缓存：200、301、404 等默认可启发式缓存，多数 5xx 不缓存。

  5. 5

    网关、重试库和监控按类别做决策：5xx 和 429 常被视为可重试，4xx 通常不应自动重试。

🔤 03 · 术语
原因短语 (Reason Phrase)
状态码后的人类可读文本，客户端不应依赖它做逻辑判断。
幂等 (Idempotent)
重复执行多次与执行一次效果相同，GET/PUT/DELETE 属于此类，决定能否安全重试。
Retry-After
随 429 或 503 返回的头，告诉客户端多少秒后或哪个时间点再试。
问题详情 (Problem Details)
RFC 9457 定义的 application/problem+json 错误体格式。
条件请求 (Conditional Request)
携带 If-None-Match 等头，资源未变时服务器返回 304 省去响应体。
💻 04 · 代码
FastAPI 返回语义化状态码python
from fastapi import FastAPI, HTTPException, status

app = FastAPI()
users = {1: {"id": 1, "name": "Ada"}}

@app.get("/users/{uid}")
def get_user(uid: int):
    if uid not in users:
        # 资源不存在：404，而不是 200 + success:false
        raise HTTPException(status_code=404, detail="user not found")
    return users[uid]          # 默认 200

@app.post("/users", status_code=status.HTTP_201_CREATED)
def create_user(name: str):
    uid = max(users) + 1
    users[uid] = {"id": uid, "name": name}
    return users[uid]          # 新建资源：201

用框架内置异常和 status 常量表达结果，参数校验失败时 FastAPI 自动返回 422。

📊 05 · 参数对比

易混状态码对照

状态码语义典型场景
401 vs 403未认证 vs 已认证但无权限没带 token 回 401；普通用户访问管理接口回 403
400 vs 422请求格式错 vs 格式对但语义校验不过JSON 解析失败回 400；字段值不合法常回 422
302 vs 307临时跳转；307 严格保持方法POST 后跳转若要保留 POST 用 307
502 vs 504上游返回无效响应 vs 上游超时Nginx 后端崩溃多为 502，处理太慢为 504
409 vs 412状态冲突 vs 前置条件失败重复创建回 409；If-Match 版本不符回 412
⚖️ 06 · 方案取舍

严格使用标准状态码

优点缓存、网关、监控开箱即用

代价需要团队统一约定细分语义

适用对外 REST API、需要可观测性时

一律 200，错误放响应体

优点前端只需一条解析路径

代价监控失明，缓存和重试会误判

适用基本不推荐；仅限遗留协议兼容

状态码 + Problem Details

优点机器可判类别，人可读细节

代价需定义错误 type 目录

适用多团队协作的中大型 API

🕳️ 07 · 常见坑

  • ✗未登录和无权限都返回 403

    ✓缺失或无效凭证回 401 并带 WWW-Authenticate；身份明确但无权回 403

  • ✗对 POST 的 5xx 自动重试，导致重复下单

    ✓只重试幂等请求，或为 POST 加 Idempotency-Key 去重

  • ✗资源不存在时为防探测回 403，又在别处回 404

    ✓统一策略：对无权资源一律 404，避免泄露存在性

  • ✗把业务失败（余额不足）当 500

    ✓500 只留给未预期异常；可预期的业务失败用 4xx 并给错误码

🎤 09 · 面试追问
401 和 403 的本质区别是什么？

401 表示请求缺少或携带了无效的认证凭证，规范要求带 WWW-Authenticate 头提示如何认证，重新登录可能解决。403 表示服务器已知道你是谁但拒绝执行，换凭证也没用。若想隐藏资源是否存在，可对无权访问统一返回 404。

为什么不建议所有错误都返回 200？

状态码是基础设施唯一能读懂的信号：CDN 会缓存“成功”的错误页，重试库和熔断器无法识别失败，APM 的错误率永远是 0，浏览器和爬虫也会误判。业务细节可以放响应体，但类别必须体现在状态码上。

301、302、307、308 应如何选择？

看两点：永久还是临时、是否必须保持请求方法。301/302 历史上允许客户端把 POST 改成 GET；307（临时）和 308（永久）明确禁止改方法。网站换域名用 301 或 308，表单提交后跳转结果页常用 303。
