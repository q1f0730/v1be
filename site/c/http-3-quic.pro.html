HTTP/3 与 QUIC

HTTP/3 & QUIC

📐 01 · 定义

HTTP/3（RFC 9114，2022 年）是运行在 QUIC 之上的 HTTP 版本。QUIC（RFC 9000）是基于 UDP 的加密传输协议，把 TLS 1.3 内置于握手中，提供多路复用的独立流、更快的连接建立和连接迁移。它解决了 HTTP/2 在 TCP 上的传输层队头阻塞问题，在丢包率高的移动网络与弱网环境中优势明显。

⚙️ 02 · 原理
  1. 1

    客户端首次通常用 HTTP/1.1 或 HTTP/2 访问，服务器通过 Alt-Svc 响应头或 DNS HTTPS 记录告知支持 h3。

  2. 2

    QUIC 握手把传输与 TLS 1.3 合并，新连接通常 1-RTT 即可发送请求，会话恢复时可用 0-RTT 立即发送数据。

  3. 3

    每个 HTTP 请求映射到独立的 QUIC 流，丢包只阻塞所属流，其他流继续交付，消除 TCP 层队头阻塞。

  4. 4

    连接由连接 ID 而非四元组标识，手机从 Wi-Fi 切到蜂窝网络时 IP 变化，连接可以迁移而不必重建。

  5. 5

    头部压缩改用 QPACK（RFC 9204），以适应流之间乱序到达；拥塞控制在用户态实现，可更快迭代。

🔤 03 · 术语
队头阻塞 (Head-of-Line Blocking)
前面的数据丢失导致后续已到达数据无法交付的现象。
0-RTT
利用之前会话的密钥在首个报文中携带应用数据，存在重放风险。
连接 ID (Connection ID)
QUIC 用来标识连接的字段，使连接在地址变化后得以保持。
Alt-Svc
HTTP 响应头，告知客户端同一资源可通过其他协议或端点访问，如 h3。
QPACK
HTTP/3 的头部压缩格式，避免 HPACK 在乱序流下的阻塞。
💻 04 · 代码
检测与开启 HTTP/3bash
# 1) 查看站点是否通过 Alt-Svc 宣告 h3
curl -sI https://www.cloudflare.com | grep -i alt-svc

# 2) 直接用 HTTP/3 请求（需要 curl 编译时启用 HTTP/3 支持）
curl --http3-only -sI https://www.cloudflare.com -o /dev/null -w '%{http_version}\n'

# 3) Nginx（1.25 及以上内置 QUIC 支持）的典型配置片段
cat <<'EOF'
server {
    listen 443 quic reuseport;   # UDP 443，用于 HTTP/3
    listen 443 ssl;              # TCP 443，用于 HTTP/1.1 与 HTTP/2
    http2 on;
    ssl_certificate     /etc/ssl/site.crt;
    ssl_certificate_key /etc/ssl/site.key;
    ssl_protocols TLSv1.3;       # QUIC 要求 TLS 1.3
    add_header Alt-Svc 'h3=":443"; ma=86400';
}
EOF
# 别忘了在防火墙/安全组放行 UDP 443

多数场景直接在 CDN 控制台开启 HTTP/3 更简单；自建时须同时保留 TCP 回退。

⚖️ 06 · 方案取舍

CDN 开启 HTTP/3

优点一键开启，自动回退，覆盖终端用户

代价仅优化用户到边缘这一段

适用面向公网用户的网站与 API

源站自建 HTTP/3

优点端到端可控

代价UDP 运维、负载均衡与监控更复杂

适用无 CDN 且移动端流量大

保持 HTTP/2

优点成熟稳定，工具链完善

代价弱网下受 TCP 队头阻塞影响

适用内网服务或网络质量稳定

🕳️ 07 · 常见坑

  • ✗只开 UDP 443 监听却未放行防火墙

    ✓在安全组与防火墙同时放行 UDP 443，并保留 TCP 回退

  • ✗对非幂等请求启用 0-RTT

    ✓0-RTT 数据可被重放，仅允许幂等请求或在服务端拒绝

  • ✗四层负载均衡按源 IP 哈希，连接迁移后打到别的节点

    ✓使用支持 QUIC 连接 ID 路由的负载均衡

  • ✗期望内网低丢包环境也明显提速

    ✓以真实移动网络与弱网数据评估收益

☑️ 08 · 检查清单
🎤 09 · 面试追问
HTTP/2 已经多路复用了，为什么还需要 HTTP/3？

HTTP/2 在一个 TCP 连接上复用多个流，但 TCP 是有序字节流，任一报文丢失时其后的所有数据都要等重传，所有流一起被阻塞。QUIC 在传输层就区分流，丢包只影响对应的流，在弱网下尾延迟显著降低。

0-RTT 有什么安全风险？

0-RTT 数据使用之前会话派生的密钥，在握手完成前发送，缺乏新鲜性保证，攻击者可截获后重放。因此只应承载幂等请求，服务端可拒绝或对 0-RTT 请求做重放检测，如单次使用票据。

为什么 QUIC 选择基于 UDP 而不是改造 TCP？

TCP 实现在操作系统内核和大量中间设备中，修改需要漫长的部署周期，中间设备还会干扰新选项。UDP 几乎处处可通过，QUIC 在用户态实现、整体加密，协议可以快速迭代，也避免了中间设备僵化。
