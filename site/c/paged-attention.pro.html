分页注意力 (PagedAttention)

PagedAttention

🧸 回到小白版

📐 01 · 定义

PagedAttention 是 vLLM 团队在 SOSP 2023 论文中提出的注意力计算与 KV 缓存管理方法，借鉴操作系统虚拟内存分页：把每个序列的 KV 缓存切分为固定大小的块，按需分配到不连续的物理显存中，并用块表维护映射。它消除了按最大长度预留带来的碎片与浪费，大幅提升可并发的序列数和推理吞吐。

⚙️ 02 · 原理
  1. 1

    传统实现为每个请求按最大可能长度预留一段连续 KV 显存，实际生成较短时大部分空间被浪费，且存在外部碎片。

  2. 2

    PagedAttention 把 KV 缓存划分为固定 Token 数的块，每个序列拥有逻辑块序列，块表把逻辑块映射到任意物理块。

  3. 3

    生成新 Token 时只在最后一个块写满后才分配新物理块，浪费最多不超过一个块。

  4. 4

    注意力内核按块表逐块读取 K 和 V 计算注意力，无需物理连续。

  5. 5

    多个序列可共享相同前缀的物理块并用写时复制处理分叉，支撑并行采样、束搜索与前缀缓存。

🔤 03 · 术语
KV 块 (KV Block)
存放固定数量 Token 的 Key 与 Value 张量的显存单元。
块表 (Block Table)
记录序列逻辑块到物理块映射的数据结构，类似页表。
写时复制 (Copy-on-Write)
共享块在某个序列需要修改时才复制，节省并行采样显存。
前缀缓存 (Prefix Caching)
复用相同提示前缀已计算好的 KV 块，减少重复预填充。
gpu-memory-utilization
vLLM 参数，指定引擎可使用的显存比例，剩余空间用于 KV 缓存。
💻 04 · 代码
估算 KV 缓存与可容纳块数python
# 每个 Token 的 KV 字节数 = 2(K和V) × 层数 × KV头数 × 头维度 × 每元素字节
def kv_bytes_per_token(layers, kv_heads, head_dim, dtype_bytes=2):
    return 2 * layers * kv_heads * head_dim * dtype_bytes

# 以 Llama-3-8B 公开配置为例：32 层，8 个 KV 头（GQA），头维度 128，FP16
per_tok = kv_bytes_per_token(32, 8, 128)
print(per_tok / 1024, "KiB/token")              # 128.0 KiB/token

block_tokens = 16                                # vLLM 常见默认块大小
per_block = per_tok * block_tokens
free_for_kv = 20 * 1024**3                       # 假设留给 KV 缓存 20 GiB
blocks = free_for_kv // per_block
print(blocks, "blocks ≈", blocks * block_tokens, "tokens")  # 10240 blocks ≈ 163840 tokens

# 预留式分配：每个请求按 8192 上限预留，只能并发 20 个
print(free_for_kv // (per_tok * 8192), "requests if reserved")
# 分页式分配：若平均只用 1500 Token，约可并发 100 个以上
print(free_for_kv // (per_tok * 1500), "requests if paged")

数字由公开模型配置推算，仅用于说明量级；实际可用显存还取决于权重、激活与引擎开销。

📊 05 · 参数对比

KV 缓存管理方式

方式分配粒度浪费共享前缀
连续预留按最大长度整段内部与外部碎片严重困难
PagedAttention固定大小块每序列最多浪费一个块块级共享与写时复制
前缀缓存（基于分页）按块哈希复用低跨请求复用系统提示
KV 量化（可叠加）降低每元素字节以精度换容量与分页正交
⚖️ 06 · 方案取舍

提高显存利用比例

优点KV 块更多，并发与吞吐更高

代价与其他进程共卡时易 OOM

适用GPU 专用于推理服务

开启前缀缓存

优点相同系统提示或多轮对话减少重复计算

代价缓存命中依赖前缀完全一致

适用固定长系统提示、Agent 多轮调用

限制最大上下文长度

优点降低单请求最坏情况占用

代价无法处理超长输入

适用业务输入长度可控

🕳️ 07 · 常见坑

  • ✗max-model-len 设得远大于业务需要

    ✓按实际最长输入加输出设置，避免启动时 KV 容量不足

  • ✗多个推理进程共享一张卡却都用默认显存比例

    ✓为每个进程显式分配显存比例，总和留出余量

  • ✗提示前缀中包含时间戳等可变内容，前缀缓存失效

    ✓把稳定内容放前面，可变内容放后面

  • ✗只看显存占用高就判断有问题

    ✓引擎会预先占用 KV 池，应看 KV 使用率与抢占指标

🎤 09 · 面试追问
PagedAttention 借鉴了操作系统的哪些思想？

虚拟内存分页：序列看到连续的逻辑块，物理块可以分散，由块表做地址映射；按需分配，用到才分配新块；共享页与写时复制，多个序列共享相同前缀块，修改时才复制。由此消除了外部碎片，内部碎片限制在一个块以内。

为什么 KV 缓存是 LLM 服务的显存瓶颈？

每个 Token 都要为每一层保存 K 与 V，占用随层数、KV 头数、头维度和序列长度线性增长，并发请求再相乘。长上下文和高并发时 KV 缓存可超过模型权重本身，决定能同时服务多少请求。

前缀缓存对 Agent 应用有什么价值？

Agent 每轮调用都携带相同的系统提示、工具定义和不断增长的对话历史。前缀缓存让这些已计算过的 KV 块被直接复用，只需预填充新增内容，显著降低首 Token 延迟与算力开销。前提是前缀逐 Token 完全一致。
