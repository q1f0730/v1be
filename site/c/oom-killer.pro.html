内存溢出强制终结

OOM Killer

🧸 回到小白版

📐 01 · 定义

OOM Killer 是 Linux 内核在系统或 cgroup 内存耗尽且无法回收时，选择并强杀进程以释放内存的机制。容器超出 cgroup 内存上限即被终止，Kubernetes 显示为 OOMKilled、退出码 137。它属于操作系统资源管理层，是设置内存限制、排查神秘重启的关键。

⚙️ 02 · 原理
  1. 1

    进程申请内存，内核尝试回收页缓存、换出等方式满足；容器受 cgroup 上限约束。

  2. 2

    回收失败且达到系统或 cgroup 内存上限时，触发 OOM 处理。

  3. 3

    内核按 oom_score 选择进程，分值主要取决于内存占用，并受 oom_score_adj 调整。

  4. 4

    被选中的进程收到 SIGKILL 立即终止，无法捕获，也没有机会做清理。

  5. 5

    内核日志记录 Killed process 信息；Kubernetes 按重启策略重启容器并记录原因。

🔤 03 · 术语
oom_score_adj
取值 -1000 到 1000 的调整值，-1000 表示不会被 OOM 杀死。
cgroup 内存上限 (memory.max)
cgroup v2 中限制一组进程可用内存的接口文件。
退出码 137
128 加 9，表示进程被 SIGKILL 终止，常见于 OOM。
QoS 类 (QoS Class)
按 requests 与 limits 划分的服务质量等级，共三类。
节点压力驱逐 (Node-pressure Eviction)
kubelet 在节点内存紧张时主动驱逐 Pod，先于内核 OOM。
💻 04 · 代码
排查 OOM 的常用命令bash
# 1. 内核日志里找被杀进程
dmesg -T | grep -iE "out of memory|killed process"

# 2. Kubernetes：确认容器上次终止原因
kubectl get pod api-7d9f -o jsonpath='{.status.containerStatuses[0].lastState.terminated.reason}'
# 输出 OOMKilled 即为超出内存 limit

# 3. cgroup v2：查看上限与 OOM 次数（在容器内或对应 cgroup 目录）
cat /sys/fs/cgroup/memory.max
grep oom_kill /sys/fs/cgroup/memory.events

# 4. 查看某进程的 OOM 评分与调整值
cat /proc/$(pgrep -o myapp)/oom_score
cat /proc/$(pgrep -o myapp)/oom_score_adj

从内核日志、Pod 状态、cgroup 计数和进程评分四个角度确认是否发生 OOM。

⚖️ 06 · 方案取舍

requests 等于 limits

优点Guaranteed QoS，最不易被驱逐

代价无法借用空闲内存，成本高

适用关键有状态服务

limits 高于 requests

优点可突发使用内存

代价节点超卖时更易被驱逐或 OOM

适用负载波动的无状态服务

不设内存 limit

优点不会因 limit 被杀

代价可能拖垮整个节点

适用一般不推荐

🕳️ 07 · 常见坑

  • ✗JVM 堆上限接近容器 limit，堆外内存一加就 OOM。

    ✓按容器内存比例设堆，例如用 MaxRAMPercentage 留出堆外空间。

  • ✗只看应用日志，找不到崩溃原因。

    ✓SIGKILL 无法记录日志，应查 Pod 终止原因和内核日志。

  • ✗把关键进程 oom_score_adj 设为 -1000，结果其他重要进程被杀。

    ✓谨慎使用，优先通过合理 limit 和容量规划解决。

  • ✗limit 设得刚好等于平均用量。

    ✓按峰值用量加余量设置，并监控接近上限的告警。

🎤 09 · 面试追问
OOMKilled 和 Evicted 有什么区别？

OOMKilled 是容器内存超过自己的 limit，被内核 OOM Killer 用 SIGKILL 杀掉，容器原地重启；Evicted 是节点内存压力达到 kubelet 驱逐阈值，kubelet 主动驱逐 Pod，Pod 需要重新调度到其他节点。

内核如何选择要杀的进程？

为每个进程计算 oom_score，主要依据其内存占用占可用内存的比例，再加上 oom_score_adj 调整，选分数最高的杀掉。Kubernetes 根据 QoS 类为容器设置不同的 oom_score_adj，BestEffort 最先被杀。

Java 应用在容器里频繁 OOM 怎么办？

确认 JVM 识别容器限制，用 MaxRAMPercentage 等参数让堆只占容器内存一部分，给元空间、线程栈、直接内存留余量；用 NMT 等工具查看堆外占用；同时排查真实泄漏。
