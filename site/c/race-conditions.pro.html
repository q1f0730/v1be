竞态条件

Race Conditions

🧸 回到小白版

📐 01 · 定义

竞态条件（Race Condition）指程序结果依赖于多个并发执行单元的时序，当它们无同步地访问共享状态且至少一方在写时，会出现不确定的错误结果。它存在于线程、进程、分布式服务乃至数据库事务各层，典型形态是读-改-写和先检查后执行（TOCTOU），解决手段是原子操作、锁、事务隔离或乐观并发控制。

⚙️ 02 · 原理
  1. 1

    两个执行单元几乎同时读取同一个共享值，例如两个请求读到的库存都是 1。

  2. 2

    各自基于旧值计算新结果并写回，后写的覆盖先写的，出现丢失更新（Lost Update）。

  3. 3

    先检查后执行时，检查与执行之间状态被别人改变，导致检查结论失效。

  4. 4

    问题只在特定交错时序下出现，本地测试难复现，高并发或线上负载下才暴露。

  5. 5

    修复思路是让读-改-写成为原子操作：加锁、数据库条件更新、版本号比较（CAS）或唯一约束。

🔤 03 · 术语
临界区 (Critical Section)
访问共享资源、同一时刻只允许一个执行单元进入的代码段。
丢失更新 (Lost Update)
并发读-改-写中一方的修改被另一方覆盖。
TOCTOU
检查时刻与使用时刻之间状态被改变导致的竞态。
比较并交换 (CAS)
仅当当前值等于预期值时才写入的原子操作，乐观并发的基础。
数据竞争 (Data Race)
多线程无同步地访问同一内存且至少一个是写，是竞态的一种。
💻 04 · 代码
读改写竞态与加锁python
import threading, time

stock = 100
lock = threading.Lock()

def buy_unsafe():
    global stock
    current = stock          # 读
    time.sleep(0)            # 让出 CPU，放大交错概率
    stock = current - 1      # 写：可能覆盖别人的结果

def buy_safe():
    global stock
    with lock:               # 临界区：读改写整体原子化
        stock -= 1

for fn in (buy_unsafe, buy_safe):
    stock = 100
    ts = [threading.Thread(target=fn) for _ in range(100)]
    [t.start() for t in ts]; [t.join() for t in ts]
    print(fn.__name__, stock)  # unsafe 往往 > 0，safe 稳定为 0

演示读-改-写在多线程下丢失更新，以及用锁保护临界区后结果确定。

📊 05 · 参数对比

不同层级的防护手段

层级典型竞态常用手段
进程内多线程共享变量读改写Mutex、原子类型、不可变数据
数据库超卖、重复创建条件 UPDATE、唯一约束、SELECT FOR UPDATE
分布式服务多实例同时处理同一任务乐观锁版本号、带租约的分布式锁
文件系统TOCTOU 检查后写原子 rename、O_EXCL 创建
⚖️ 06 · 方案取舍

悲观锁

优点语义直观，冲突时不需重试

代价吞吐低，易死锁

适用冲突频繁、临界区短

乐观并发（版本号/CAS）

优点无锁等待，读多写少时高效

代价冲突时要重试，热点下浪费

适用冲突少的更新

数据库原子语句

优点简单可靠，无需额外组件

代价只适合能用单条语句表达的逻辑

适用扣库存、计数器等

🕳️ 07 · 常见坑

  • ✗先 SELECT 查库存够不够，再 UPDATE 扣减，两步之间被并发穿透。

    ✓用 UPDATE … SET stock=stock-1 WHERE id=? AND stock>0 并检查影响行数。

  • ✗用 Redis SETNX 做分布式锁但不设过期，持有者崩溃后永久死锁。

    ✓用 SET key val NX PX 设租约，释放时校验持有者标识。

  • ✗认为有 GIL 的 Python 不会有竞态。

    ✓GIL 只保证字节码级别，复合操作仍需加锁。

  • ✗只在单机测试并发，没覆盖多实例部署。

    ✓在多副本和压测场景下验证，借助竞态检测工具。

🎤 09 · 面试追问
如何防止秒杀超卖？

核心是把检查和扣减合成一个原子操作：数据库条件更新并检查影响行数，或 Redis Lua 脚本原子扣减；订单表加唯一约束防重复下单；高峰时前置队列削峰。不要在应用层先查后改。

乐观锁和悲观锁怎么选？

看冲突概率和临界区长度。冲突少、读多写少用乐观锁，用版本号比较更新，失败重试；冲突多或重试代价高用悲观锁如 SELECT FOR UPDATE，但要控制持锁时间和加锁顺序。

怎样发现代码中的竞态？

代码审查关注共享状态和先查后改模式；使用工具，如 Go 的 -race、C/C++ 的 ThreadSanitizer；在压测中构造高并发；对 AI 生成的并发代码要求写出并发测试用例。
