语义化版本控制

Semantic Versioning

📐 01 · 定义

语义化版本（Semantic Versioning，SemVer）是一套版本号命名规范，格式为 MAJOR.MINOR.PATCH，属于软件发布与依赖管理层。它把版本号变成对兼容性的承诺：不兼容的 API 变更升主版本，向后兼容的新功能升次版本，向后兼容的修复升补丁版本，让包管理器可以用范围表达式安全地自动升级依赖。

⚙️ 02 · 原理
  1. 1

    先定义公开 API（Public API）；SemVer 的所有承诺都只针对这份公开接口，内部实现改动不受约束。

  2. 2

    破坏兼容就升 MAJOR 并把 MINOR、PATCH 归零；新增兼容功能升 MINOR、PATCH 归零；只修 bug 升 PATCH。

  3. 3

    0.y.z 表示初始开发期，规范说明此阶段任何变更都可能不兼容，公开 API 不应视为稳定。

  4. 4

    预发布版本用连字符后缀，如 1.0.0-rc.1，优先级低于对应正式版；+ 后的构建元数据不参与排序。

  5. 5

    包管理器用范围解析依赖：npm 的 ^1.2.3 允许 <2.0.0，~1.2.3 允许 <1.3.0，锁文件再固定实际安装版本。

🔤 03 · 术语
破坏性变更 (Breaking Change)
让现有调用方无法不改代码继续工作的变更，如删参数、改返回结构。
插入符范围 (Caret Range)
^ 允许不改变最左非零位的升级；^0.2.3 只允许 <0.3.0。
锁文件 (Lockfile)
package-lock.json 等，记录精确解析结果，保证可复现安装。
预发布标识 (Pre-release)
如 -alpha.1、-rc.2，按点分段比较，数字段按数值排序。
约定式提交 (Conventional Commits)
feat/fix/BREAKING CHANGE 前缀规范，可自动推导下一个版本号。
💻 04 · 代码
npm 版本范围与升版bash
# 查看某包所有已发布版本
npm view react versions --json

# 安装时写入 ^ 范围（默认），允许兼容升级
npm install lodash@^4.17.0

# 改为精确版本，不自动升级
npm install lodash@4.17.21 --save-exact

# 查看哪些依赖有新版本（Current/Wanted/Latest）
npm outdated

# 发布自己的包前升版：patch / minor / major / prerelease
npm version patch        # 1.4.2 -> 1.4.3，并打 git tag
npm version premajor --preid=rc   # 1.4.3 -> 2.0.0-rc.0

npm version 会改 package.json 并创建提交和标签；Wanted 列即范围内可升到的最高版本。

📊 05 · 参数对比

npm 范围写法对照

写法允许范围适用
1.2.3仅 1.2.3关键依赖、需完全可控
~1.2.3>=1.2.3 <1.3.0只接受补丁修复
^1.2.3>=1.2.3 <2.0.0npm 默认，接受兼容新功能
^0.2.3>=0.2.3 <0.3.00.x 阶段，次版本视为可破坏
>=1.2.3无上限不推荐，可能跨主版本
⚖️ 06 · 方案取舍

依赖用 ^ 范围 + 锁文件

优点易获取修复，安装可复现

代价更新锁文件时可能引入回归

适用大多数应用项目

依赖全部精确版本

优点完全确定，无意外升级

代价安全补丁需手动跟进

适用强合规或极少维护的项目

日历版本 CalVer

优点一眼看出发布时间

代价不表达兼容性

适用按时间节奏发布的应用或发行版

🕳️ 07 · 常见坑

  • ✗在补丁版本里悄悄改了函数返回结构

    ✓任何公开 API 不兼容变更都升 MAJOR，并写迁移说明

  • ✗以为 ^0.3.0 会自动升到 0.4.0

    ✓0.x 下 ^ 只允许补丁级升级，跨次版本需手动改范围

  • ✗库项目提交锁文件就以为用户也被锁定

    ✓锁文件只对当前项目生效，库的使用者按自己的范围解析

  • ✗已发布版本发现问题就覆盖重发

    ✓已发布内容不可修改，发布新的补丁版本并弃用旧版

🎤 09 · 面试追问
为什么 0.x 版本需要特殊对待？

SemVer 规定 0.y.z 是初始开发阶段，公开 API 不稳定，任何变更都可能破坏兼容。因此 npm 对 ^0.y.z 收紧为只允许补丁升级。发布 1.0.0 意味着正式承诺公开 API，之后的破坏性变更必须升主版本。

锁文件和版本范围是什么关系？

范围声明“可接受哪些版本”，锁文件记录“这次实际装了哪个”。范围给升级留空间，锁文件保证团队、CI 和生产安装一致。更新依赖本质是在范围内重新解析并改写锁文件，应当作为可审查的变更。

如何判断一个改动是不是破坏性的？

站在调用方看：不改代码还能否编译、运行并得到符合文档的结果。删除或重命名导出、改变参数顺序或类型、收窄返回值、改变默认行为、提高运行时最低版本，通常都算破坏性变更。
