Git 钩子 (pre-commit)

Git Hooks

📐 01 · 定义

Git Hooks（Git 钩子）是 Git 在特定事件（提交、推送等）前后自动执行的脚本，位于 .git/hooks 或 core.hooksPath 指定目录。客户端钩子用于在代码进入仓库前做格式化、静态检查和密钥扫描；pre-* 类钩子以非零退出码即可中止操作。因为 .git 目录不随仓库分发，团队通常借助 pre-commit、husky 等框架共享配置。

⚙️ 02 · 原理
  1. 1

    Git 在执行 commit、push 等命令的固定节点查找同名可执行文件，如 pre-commit、commit-msg、pre-push。

  2. 2

    pre-commit 在生成提交对象前运行，常只针对暂存区（staged）文件做 lint、格式化与密钥扫描。

  3. 3

    commit-msg 收到提交信息临时文件路径作为参数，可读取并校验格式，例如约定式提交。

  4. 4

    脚本退出码非 0 时 Git 中止当前操作；用户可用 --no-verify 跳过 pre-commit 与 commit-msg 钩子。

  5. 5

    pre-commit 框架读取仓库内的 .pre-commit-config.yaml，执行 pre-commit install 写入钩子，按配置下载并缓存各工具环境。

🔤 03 · 术语
core.hooksPath
Git 配置项，指定钩子目录，可指向仓库内受版本控制的文件夹。
客户端钩子 (Client-side Hook)
在开发者本机运行，可被绕过，不能作为唯一安全措施。
服务端钩子 (Server-side Hook)
pre-receive 等，在远端仓库接收推送时运行，托管平台常以规则替代。
--no-verify
跳过 pre-commit 和 commit-msg 钩子的命令行参数。
gitleaks
开源密钥扫描工具，可作为 pre-commit 钩子检测提交中的凭证。
lint-staged
JS 生态工具，只对暂存文件运行指定命令，常与 husky 搭配。
💻 04 · 代码
pre-commit 框架配置yaml
# 安装：pip install pre-commit && pre-commit install
# rev 请改为各仓库当前发布的版本号
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v4.6.0
    hooks:
      - id: trailing-whitespace
      - id: end-of-file-fixer
      - id: check-yaml
      - id: check-added-large-files
      - id: detect-private-key     # 拦截私钥文件
  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.18.0
    hooks:
      - id: gitleaks               # 扫描 API Key 等密钥
# 手动对全部文件跑一遍：pre-commit run --all-files
# 升级 rev：pre-commit autoupdate

共享到仓库的钩子配置：基础卫生检查加私钥与密钥扫描，rev 以官方最新为准。

📊 05 · 参数对比

常用客户端钩子

钩子触发时机可否中止典型用途
pre-commit生成提交前是格式化、lint、密钥扫描
prepare-commit-msg打开编辑器前是预填模板或分支号
commit-msg提交信息写完后是校验提交信息格式
post-commit提交完成后否通知、统计
pre-push推送前是跑单元测试、阻止推 main
⚖️ 06 · 方案取舍

pre-commit 框架（Python）

优点多语言、环境隔离、生态丰富

代价需要 Python 环境

适用多语言或非 JS 项目

husky + lint-staged

优点与 npm 生态无缝，安装自动化

代价主要服务 JS 项目

适用前端 / Node 项目

手写脚本 + core.hooksPath

优点零依赖，完全可控

代价维护成本高，跨平台麻烦

适用极简项目或特殊需求

🕳️ 07 · 常见坑

  • ✗把钩子当作唯一的安全防线

    ✓钩子可被 --no-verify 绕过，CI 中必须重复执行同样的检查

  • ✗pre-commit 里跑完整测试，每次提交等几分钟

    ✓提交钩子只做秒级检查，耗时测试放 pre-push 或 CI

  • ✗密钥已经提交后才加扫描钩子

    ✓历史中的密钥仍可被取到，应立刻轮换密钥并清理历史

  • ✗钩子只检查全部文件，改一行也很慢

    ✓只处理暂存文件（pre-commit 框架默认如此），用 run --all-files 做定期全量

🎤 09 · 面试追问
为什么钩子不能直接提交到仓库生效？

.git 目录不受版本控制，克隆时不会带上 hooks。共享方式是把配置或脚本放在仓库内，再由 pre-commit install、husky 安装脚本或 core.hooksPath 让每个开发者本地启用。这也意味着必须有人执行安装，所以要在 CI 兜底。

客户端钩子与 CI 检查如何分工？

钩子负责快速反馈，在提交前拦住格式错误和明显的密钥泄露，降低 CI 噪音；CI 负责强制执行，因为钩子可被跳过或未安装。两者运行同一套配置，保证本地通过即 CI 通过。

AI Agent 改代码时钩子有什么价值？

Agent 执行 git commit 同样会触发钩子，格式与密钥问题会被当场拒绝，Agent 读到错误后可自行修复。注意要在规则中禁止 Agent 使用 --no-verify，否则它可能为了完成任务直接绕过。
