后台异步任务队列

Background Jobs

📐 01 · 定义

后台任务（Background Jobs）是把耗时或可延后的工作（发邮件、生成报表、调用外部 API、处理图片）从请求路径中拆出，写入任务队列，由独立的 worker 进程异步消费执行。它位于应用架构的异步处理层，缩短接口响应时间、削峰填谷，并通过重试提升可靠性。

⚙️ 02 · 原理
  1. 1

    Web 进程把任务名与参数序列化后推入 broker（如 Redis、RabbitMQ、SQS），立即返回。

  2. 2

    一个或多个 worker 进程从队列拉取任务并执行，可按队列划分优先级与资源。

  3. 3

    执行失败时按退避策略重试，超过最大次数后进入死信队列或标记失败。

  4. 4

    确认机制决定消息何时删除：执行后确认可防丢，但 worker 崩溃时任务可能被重复执行。

  5. 5

    调度器（如 Celery beat、cron）按时间周期投递定时任务，结果可写回数据库或结果后端。

🔤 03 · 术语
Broker
存储与分发任务消息的中间件，如 Redis、RabbitMQ。
Worker
消费队列并执行任务的独立进程。
确认 (Ack)
worker 告知 broker 任务已处理，可删除消息。
指数退避 (Exponential Backoff)
每次重试间隔成倍增长，避免压垮下游。
Outbox 模式
业务数据与待发消息同库同事务写入，再异步投递。
💻 04 · 代码
Celery 任务与重试python
from celery import Celery
import requests

app = Celery("tasks", broker="redis://localhost:6379/0")
app.conf.task_acks_late = True              # 执行完再确认，崩溃可重投
app.conf.worker_prefetch_multiplier = 1     # 长任务避免预取堆积

@app.task(
    autoretry_for=(requests.RequestException,),
    retry_backoff=True,      # 指数退避
    retry_jitter=True,       # 随机抖动
    max_retries=5,
)
def send_receipt(order_id: int):
    # 幂等：已发送则跳过（acks_late 下可能重复执行）
    # if already_sent(order_id): return
    resp = requests.post("https://mail.example.com/send",
                         json={"order_id": order_id}, timeout=10)
    resp.raise_for_status()

# Web 端：只入队，不等待结果
# send_receipt.delay(981)
# 启动 worker：celery -A tasks worker --loglevel=INFO

入队后立即返回；失败自动退避重试；acks_late 换来不丢任务，代价是任务必须幂等。

⚖️ 06 · 方案取舍

同步在请求内处理

优点简单，结果立即可见

代价接口慢，失败影响用户请求

适用耗时很短且必须立即完成

Redis 队列

优点部署简单、延迟低

代价持久化与投递保证弱于专业 MQ

适用中小规模、已有 Redis

专业 MQ / 托管队列

优点持久化、确认、死信完善

代价运维或费用成本更高

适用关键业务、高吞吐

🕳️ 07 · 常见坑

  • ✗在数据库事务提交前就入队，worker 读不到新数据

    ✓事务提交后再入队（如 on_commit 钩子），或使用 outbox

  • ✗任务参数传整个 ORM 对象

    ✓只传 ID 等小参数，worker 执行时重新读取最新数据

  • ✗任务不幂等，重试导致重复扣款或重复邮件

    ✓以业务键去重，或检查状态后再执行

  • ✗没有监控，队列积压数小时无人察觉

    ✓监控队列长度、任务耗时与失败率并设置告警

🎤 09 · 面试追问
如何保证任务不丢也不重复？

严格「恰好一次」很难。常规做法是至少一次投递：持久化 broker、执行后确认、失败重试，再在任务层实现幂等（业务唯一键、状态机检查），把重复执行的影响消除。

数据库写入和发消息怎么保证一致？

用 outbox 模式：业务数据和待发送事件在同一本地事务写入，独立进程轮询或基于 CDC 把 outbox 记录投递到队列，投递成功后标记，避免「写库成功但消息丢失」。

长任务如何避免被重复执行？

让可见性超时或确认超时大于任务最长耗时；降低或关闭预取；把长任务拆成可续跑的小步并记录进度；同时保证幂等，即使重复执行也无副作用。
