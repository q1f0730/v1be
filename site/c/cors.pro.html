跨源资源共享

CORS

📐 01 · 定义

跨源资源共享（Cross-Origin Resource Sharing，CORS）是浏览器在同源策略基础上、允许服务器通过 HTTP 响应头声明哪些其他源可以读取其资源的机制，由 WHATWG Fetch 标准定义。它是浏览器端的放行协议而非服务端访问控制，只约束浏览器脚本能否读取响应，对 curl 无效。

⚙️ 02 · 原理
  1. 1

    浏览器判断请求是否跨源：协议、域名、端口任一不同即为跨源，并在请求中附带 Origin 头。

  2. 2

    简单请求（特定方法与头）直接发送，浏览器检查响应中的 Access-Control-Allow-Origin 决定是否交给脚本。

  3. 3

    非简单请求（如 PUT、带自定义头或 JSON 类型）先发 OPTIONS 预检，询问允许的方法和头。

  4. 4

    服务器返回 Allow-Methods、Allow-Headers、Max-Age 等，预检通过后浏览器才发送真实请求。

  5. 5

    携带 Cookie 需前端设置 credentials，服务器返回 Allow-Credentials: true 且 Allow-Origin 不能为 *。

🔤 03 · 术语
同源策略 (Same-Origin Policy)
浏览器限制脚本读取其他源资源的基础安全模型。
源 (Origin)
协议 + 主机 + 端口的组合，三者相同才算同源。
预检请求 (Preflight)
浏览器自动发送的 OPTIONS 请求，确认是否允许实际请求。
带凭证请求 (Credentialed Request)
携带 Cookie 或 HTTP 认证信息的跨源请求。
Vary: Origin
提示缓存按 Origin 区分响应，动态返回 Allow-Origin 时需要。
💻 04 · 代码
Express 白名单式 CORSjavascript
import express from "express";
import cors from "cors";

const app = express();
const allowlist = new Set([
  "https://app.example.com",
  "http://localhost:5173",     // 本地开发
]);

app.use(cors({
  origin(origin, cb) {
    // 无 Origin（如服务器间调用）放行；CORS 本就不约束它们
    if (!origin || allowlist.has(origin)) return cb(null, true);
    cb(null, false);            // 不返回 CORS 头，浏览器将拦截读取
  },
  credentials: true,            // 允许携带 Cookie，此时不能用 *
  methods: ["GET", "POST", "PUT", "DELETE"],
  maxAge: 600,                  // 预检结果缓存秒数
}));

app.get("/api/me", (req, res) => res.json({ ok: true }));
app.listen(3000);

使用 cors 中间件按白名单回显 Origin；cors 会自动处理预检与 Vary 头。

📊 05 · 参数对比

关键 CORS 响应头

响应头作用注意
Access-Control-Allow-Origin允许读取的源带凭证时不能为 *
Access-Control-Allow-Credentials允许携带凭证仅能为 true
Access-Control-Allow-Methods/Headers预检允许的方法与头只在预检响应中需要
Access-Control-Max-Age预检缓存时长浏览器有各自上限
⚖️ 06 · 方案取舍

精确白名单

优点最安全

代价新增前端域名需改配置

适用带登录态的 API

Allow-Origin: *

优点简单

代价不能带凭证

适用完全公开、无需鉴权的数据

同源反向代理

优点彻底避免跨源

代价多一层代理配置

适用前后端可部署在同一域名

🕳️ 07 · 常见坑

  • ✗把请求的 Origin 原样回显并允许凭证

    ✓只回显白名单中的源

  • ✗用正则匹配域名，被 example.com.evil.com 绕过

    ✓完整精确比对源字符串

  • ✗以为配置了 CORS 接口就安全了

    ✓CORS 不是鉴权，接口仍需认证与授权

  • ✗白名单包含 null 源

    ✓不要信任 null，沙箱 iframe 等可伪造该来源

🎤 09 · 面试追问
CORS 错误时请求到底发出去了吗？

要看情况。简单请求已经发到服务器并被处理，只是浏览器拒绝把响应交给脚本；非简单请求在预检失败时，真实请求不会发送。这也是为什么 CORS 不能防御 CSRF：简单请求的副作用已经发生。

为什么带凭证时 Allow-Origin 不能为 *？

如果允许任意源带着用户 Cookie 读取响应，任何恶意网站都能以用户身份读取私有数据，相当于取消同源策略。因此规范要求带凭证的响应必须明确指定单一源，迫使服务器做出有意识的信任决定。

CORS 是防谁的？

CORS 保护的是用户：防止用户浏览器中的恶意网站脚本，借用户的登录状态读取其他站点的数据。它并不保护服务器免受非浏览器客户端访问，攻击者用 curl 可以忽略 CORS，因此服务端必须自行鉴权。
