提示词 (Prompt)

Prompt

📐 01 · 定义

提示词（Prompt）是发送给 LLM 的全部输入文本，包括指令、上下文资料、示例和输出格式要求。由于模型行为完全由输入条件化，提示词就是「用自然语言编写的程序接口」。提示工程（Prompt Engineering）研究如何组织这些内容，让输出更准确、稳定、可解析。

⚙️ 02 · 原理
  1. 1

    明确任务：说清目标、受众和成功标准，减少模型自行猜测的空间。

  2. 2

    提供上下文：给出必要的背景资料、代码片段或数据，模型只能基于看到的内容作答。

  3. 3

    给出示例：少样本（Few-shot）示例比抽象描述更能锁定格式与风格。

  4. 4

    约束输出：指定结构（JSON、表格、标签包裹），便于程序解析和校验。

  5. 5

    迭代评测：用一组固定样本对比不同版本提示词的效果，像改代码一样做回归。

🔤 03 · 术语
零样本 (Zero-shot)
不给示例，仅靠指令让模型完成任务。
少样本 (Few-shot)
在提示中放几个输入—输出示例，引导格式和判断标准。
思维链 (Chain-of-Thought)
让模型先写出推理步骤再给结论，常提升多步问题准确率。
结构化输出 (Structured Output)
要求或强制模型按 JSON Schema 等格式输出。
提示注入 (Prompt Injection)
外部内容中夹带指令，劫持模型行为的攻击方式。

审查下面的 React 组件，找出 bug 和可访问性问题。
只报告确定的问题，不确定的标注「待确认」。
</task>

<context>
项目使用 React 18 + TypeScript，样式用 Tailwind。
</context>

<code>
{{在这里粘贴组件代码}}
</code>

<output_format>
按 JSON 数组输出，每项包含：
- line: 行号
- severity: high | medium | low
- issue: 问题描述
- fix: 修改建议
</output_format>

用 XML 标签分隔角色、任务、资料和格式，是 Anthropic 文档推荐的写法，便于模型区分指令与数据。

📊 05 · 参数对比

提示技巧与适用场景

技巧作用适用场景
明确角色与受众统一语气和专业深度写作、解释、审查
少样本示例锁定格式与判断标准分类、抽取、改写
分步推理提升复杂推理准确率数学、调试、规划
标签分隔资料防止资料被当成指令长文档、用户输入
指定输出结构便于程序解析接入代码的任何场景
⚖️ 06 · 方案取舍

简短指令

优点省 Token、快

代价模型自由发挥多，结果不稳定

适用简单、容错高的任务

详细指令 + 示例

优点稳定、可控

代价Token 成本高，示例可能过拟合

适用生产环境、格式严格

拆成多步提示链

优点每步简单可测，易定位问题

代价调用次数和延迟增加

适用复杂流程、需中间校验

🕳️ 07 · 常见坑

  • ✗把用户输入直接拼进指令区

    ✓用标签包裹外部内容，并声明其中的指令不应执行

  • ✗只说「不要做 X」

    ✓同时说明应该怎么做，正向描述比禁令更有效

  • ✗凭感觉改提示词，没有对比

    ✓建立固定样本集，每次改动跑一遍对比结果

  • ✗示例全是同一类，模型照抄

    ✓示例覆盖不同情况，包括边界与反例

🎤 09 · 面试追问
提示工程会被更强的模型淘汰吗？

技巧类花招会弱化，但核心不会：清楚表达需求、提供正确上下文、定义输出契约、做评测。模型越强，瓶颈越转向「给什么上下文」，即上下文工程（Context Engineering），本质仍是提示设计。

怎样让模型稳定输出合法 JSON？

优先用供应商的结构化输出或工具调用能力（按 Schema 约束）；其次在提示中给 Schema 和示例、低 temperature；最后在代码侧用 JSON 解析加 Schema 校验，失败时带错误信息重试。

如何防御提示注入？

无法单靠提示完全防住。分层做：外部内容用标签隔离并声明为数据；最小化工具权限；敏感操作需人工确认；对输出做过滤；把系统指令与用户数据分在不同角色。Agent 读网页、读邮件时风险最高。
