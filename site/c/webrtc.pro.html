WebRTC 实时音视频

WebRTC

📐 01 · 定义

WebRTC 是由 W3C（浏览器 API）与 IETF（协议）共同制定的实时通信标准，让浏览器和移动端无需插件即可进行低延迟的音视频与任意数据传输。它包含媒体采集、编解码、NAT 穿透、强制加密传输和拥塞控制等能力，是视频会议、云游戏、实时语音 AI 等场景的基础。

⚙️ 02 · 原理
  1. 1

    通过 getUserMedia 获取麦克风与摄像头，创建 RTCPeerConnection 并添加媒体轨道或数据通道。

  2. 2

    信令不在标准范围内：双方需借助应用自己的通道（如 WebSocket、HTTP）交换 SDP Offer/Answer，描述编解码器与媒体参数。

  3. 3

    ICE 收集候选地址：本机地址、经 STUN 发现的公网映射地址、TURN 中继地址，双方逐对连通性检测选出可用路径。

  4. 4

    连接建立后用 DTLS 协商密钥，媒体经 SRTP 加密传输，数据通道基于 SCTP over DTLS，加密是强制的。

  5. 5

    传输过程中根据带宽估计动态调整码率与分辨率；多人场景常经 SFU 服务器转发，而非全网状互连。

🔤 03 · 术语
SDP (Session Description Protocol)
描述媒体格式、编解码器和传输参数的文本格式，用于 Offer/Answer 协商。
ICE
交互式连接建立框架，收集并测试候选地址以穿越 NAT 建立连接。
STUN / TURN
STUN 帮助发现公网地址；TURN 在直连失败时中继全部流量。
SFU (Selective Forwarding Unit)
只转发不混流的媒体服务器，是多人会议的主流架构。
DTLS-SRTP
用 DTLS 握手交换密钥、用 SRTP 加密媒体的 WebRTC 安全机制。
💻 04 · 代码
浏览器端建立 WebRTC 连接javascript
// 信令通道由应用自行实现，这里假设 signaling 是一个已连接的 WebSocket
const pc = new RTCPeerConnection({
  iceServers: [
    { urls: 'stun:stun.example.com:3478' },
    { urls: 'turn:turn.example.com:3478', username: 'u', credential: 'p' }, // 受限网络兜底
  ],
})

const mic = await navigator.mediaDevices.getUserMedia({ audio: true })
mic.getTracks().forEach((t) => pc.addTrack(t, mic))

pc.ontrack = (e) => { document.querySelector('audio').srcObject = e.streams[0] }
pc.onicecandidate = (e) => e.candidate && signaling.send(JSON.stringify({ ice: e.candidate }))

const offer = await pc.createOffer()
await pc.setLocalDescription(offer)
signaling.send(JSON.stringify({ sdp: pc.localDescription }))

signaling.onmessage = async ({ data }) => {
  const msg = JSON.parse(data)
  if (msg.sdp) await pc.setRemoteDescription(msg.sdp)        // 对端的 Answer
  if (msg.ice) await pc.addIceCandidate(msg.ice)
}

STUN/TURN 地址为占位；TURN 凭证应由服务端短期签发，不要写死在前端。

📊 05 · 参数对比

多人音视频架构对比

架构原理优势代价
Mesh（全网状）每人与每人直连无需媒体服务器人数一多上行带宽爆炸
SFU服务器选择性转发各路流可扩展，延迟低需要部署媒体服务器
MCU服务器解码混流再编码客户端只收一路服务器算力成本高，延迟增加
SFU + 联播 (Simulcast)发送多档码率按需转发适配不同网络发送端编码开销增加
⚖️ 06 · 方案取舍

WebRTC

优点端到端延迟低，浏览器原生，内置抗丢包

代价信令、NAT 穿透与媒体服务器运维复杂

适用实时对话、会议、语音 AI

WebSocket 传音频

优点实现简单，复用现有后端

代价基于 TCP，弱网下抖动与延迟大

适用服务器间或网络稳定的场景

HLS/DASH 直播

优点可大规模分发，CDN 友好

代价延迟通常为数秒

适用一对多直播，不需要交互

🕳️ 07 · 常见坑

  • ✗只配 STUN，企业或移动网络下连接失败

    ✓部署 TURN 中继并监控中继使用比例

  • ✗TURN 凭证长期有效且写在前端

    ✓由服务端签发带过期时间的临时凭证

  • ✗多人会议用 Mesh 架构

    ✓超过少数参与者时改用 SFU

  • ✗未处理回声与音频处理约束

    ✓启用 echoCancellation、noiseSuppression 等约束并实测耳机与外放

🎤 09 · 面试追问
为什么 WebRTC 还需要信令服务器？

两端建立连接前互不知道对方地址和能力，需要交换 SDP 与 ICE 候选。标准刻意不规定信令协议，让应用自由选择 WebSocket、HTTP 等方式，并结合自身的认证与房间逻辑。连接建立后媒体可以点对点传输。

ICE 如何穿越 NAT？

双方收集多类候选：本机地址、STUN 返回的 NAT 外部映射地址、TURN 中继地址，交换后按优先级配对做连通性检测，优先直连，失败则走 TURN。对称型 NAT 和严格防火墙下往往只能依赖 TURN。

实时语音 AI 为什么偏好 WebRTC？

语音对话对端到端延迟和抖动敏感。WebRTC 基于 UDP，内置抖动缓冲、丢包隐藏、回声消除和带宽自适应，浏览器原生支持麦克风采集与播放。部分模型服务商的实时接口也提供 WebRTC 接入方式。
