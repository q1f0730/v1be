连接排空

Connection Draining

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

连接排空（Connection Draining）是负载均衡器在后端实例下线时，停止向其分配新连接或请求，同时让已建立连接在时限内自然结束的机制。AWS ALB/NLB 中称为注销延迟（Deregistration Delay），Google Cloud 称连接排空。它位于流量接入层，与优雅停机配合实现发布缩容不断连。

⚙️ 02 · 原理
  1. 1

    实例被标记下线，原因可能是发布替换旧版本、自动缩容、手动注销或健康检查连续失败。

  2. 2

    负载均衡器将其状态置为 draining，不再路由新的请求或连接给它。

  3. 3

    已有连接和在途请求继续在该实例上完成，长连接需要应用主动收尾。

  4. 4

    排空超时到达或在途连接数归零后，负载均衡器才把该实例从目标组中彻底移除。

  5. 5

    应用端同步执行优雅停机，在排空窗口内关闭空闲 keep-alive 连接后退出。

🔤 03 · 术语
注销延迟 (Deregistration Delay)
AWS 目标组中目标从 draining 到移除的最长等待，默认 300 秒。
Keep-Alive 连接
HTTP 复用的长连接，排空时需要服务端关闭或发 Connection: close。
GOAWAY 帧
HTTP/2 中通知对端不再接受新流、让其换连接的控制帧。
长连接 (WebSocket / gRPC Stream)
可能持续数小时，排空窗口内往往结束不了，需应用层迁移。
粘性会话 (Sticky Session)
把同一用户固定到同一实例，排空时会话需迁移或失效。
💻 04 · 代码
AWS 目标组排空操作bash
TG_ARN="arn:aws:elasticloadbalancing:...:targetgroup/api/abc123"

# 1. 把注销延迟从默认 300 秒调到 60 秒（请求都很短时）
aws elbv2 modify-target-group-attributes \
  --target-group-arn "$TG_ARN" \
  --attributes Key=deregistration_delay.timeout_seconds,Value=60

# 2. 注销实例：进入 draining，不再接新请求
aws elbv2 deregister-targets \
  --target-group-arn "$TG_ARN" \
  --targets Id=i-0123456789abcdef0

# 3. 等待排空完成后再停机
aws elbv2 wait target-deregistered \
  --target-group-arn "$TG_ARN" \
  --targets Id=i-0123456789abcdef0

用 AWS CLI 调整排空时长、注销目标并等待排空完成，再安全停机。

📊 05 · 参数对比

排空时长怎么定

流量类型建议思路风险
短 HTTP 请求略大于 p99.9 请求耗时过长会拖慢发布
文件上传/下载按最大传输时间估算过短会中断传输
WebSocket/长流应用层通知客户端重连仅靠排空无法覆盖
⚖️ 06 · 方案取舍

较长排空时间

优点慢请求也能完成

代价发布和缩容变慢，成本增加

适用存在长请求或大文件传输

较短排空时间

优点发布快

代价慢请求可能被中断

适用请求普遍很短且可重试

应用层主动迁移

优点可处理长连接

代价需客户端支持重连

适用WebSocket、gRPC 流

🕳️ 07 · 常见坑

  • ✗负载均衡排空 300 秒，但 Pod 宽限期只有 30 秒，进程先被杀。

    ✓让应用停机时长与排空窗口匹配，必要时调大宽限期。

  • ✗服务端不关闭空闲 keep-alive，客户端继续复用到已摘除实例。

    ✓停机时关闭空闲连接，HTTP/2 发送 GOAWAY。

  • ✗以为排空能保住 WebSocket 会话。

    ✓服务端主动通知并让客户端带退避重连。

🎤 09 · 面试追问
连接排空和优雅停机是什么关系？

排空是负载均衡侧动作：不给实例发新流量、给旧连接时间结束；优雅停机是应用侧动作：停止接新工作、完成在途工作再退出。两者时间窗口要对齐，排空先开始，应用在窗口内完成退出。

HTTP/2 和 gRPC 长连接如何排空？

一个连接承载很多请求，单纯等待连接结束可能很久。服务端应发送 GOAWAY，告知客户端不要在该连接上开新流，客户端会建立新连接到其他实例，已在途的流继续完成。

注销延迟设得越长越好吗？

不是。过长会让每次发布和缩容都等待很久，滚动发布总时长成倍增加。应按 p99.9 请求时长加余量设定，长连接场景交给应用层迁移。
