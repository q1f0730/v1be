账户枚举漏洞

Account Enumeration

📐 01 · 定义

账户枚举（Account Enumeration）是指攻击者通过登录、注册、找回密码等接口的响应差异，判断某个用户名或邮箱是否已注册。差异可能来自提示文案、HTTP 状态码、响应时长或后续行为。它常是撞库、定向钓鱼和暴力破解的前置侦察。

⚙️ 02 · 原理
  1. 1

    攻击者准备候选用户名或邮箱列表，批量调用登录、注册等认证相关接口。

  2. 2

    比较响应正文、状态码、重定向目标、Set-Cookie 等可观测差异。

  3. 3

    测量响应时间：用户存在时执行慢哈希，不存在时立即返回，形成时间侧信道。

  4. 4

    把确认存在的账户用于撞库、口令喷洒或社会工程，提高攻击命中率。

  5. 5

    防御方统一对外响应与耗时，并用限流、验证码和监控提高批量探测成本。

🔤 03 · 术语
时间侧信道 (Timing Side Channel)
通过响应耗时差异推断内部分支走向。
口令喷洒 (Password Spraying)
用少量常见口令轮流尝试大量账户，规避单账户锁定。
撞库 (Credential Stuffing)
用其他站点泄露的账号密码组合批量登录。
统一响应 (Generic Response)
无论账户是否存在都返回相同文案、状态码与结构。
虚拟哈希 (Dummy Hash)
账户不存在时也做一次哈希校验，使耗时一致。
💻 04 · 代码
统一文案与耗时的登录python
from argon2 import PasswordHasher
from argon2.exceptions import VerifyMismatchError

ph = PasswordHasher()
# 启动时预先算好一个虚拟哈希，参数与真实用户一致
DUMMY_HASH = ph.hash("dummy-password-for-timing")
GENERIC = "用户名或密码错误"

def login(username: str, password: str):
    user = find_user(username)          # 业务查询，可能返回 None
    stored = user.password_hash if user else DUMMY_HASH
    try:
        ph.verify(stored, password)     # 两条分支都执行慢哈希
        ok = user is not None
    except VerifyMismatchError:
        ok = False
    if not ok:
        return 401, GENERIC             # 文案、状态码完全一致
    return 200, "ok"

账户不存在时也跑一次哈希，消除时间差；find_user 为业务自定义。

各接口的泄露点与改法

接口常见泄露推荐响应

⚖️ 06 · 方案取舍

完全统一响应

优点从根上消除枚举

代价注册体验变差，用户困惑

适用金融、医疗等高敏场景

保留友好提示 + 强限流

优点体验好，攻击成本可控

代价仍可慢速枚举

适用社交、内容类公开账户

验证码/风控挑战

优点有效抑制自动化

代价增加摩擦，可被打码平台绕过

适用检测到异常频率时触发

🕳️ 07 · 常见坑

  • ✗文案统一了，但状态码或重定向仍不同

    ✓对比两种情况的完整 HTTP 响应，包括头和跳转

  • ✗用户不存在时直接返回，耗时明显更短

    ✓执行虚拟哈希，或把发邮件等操作放入异步队列

  • ✗锁定策略本身暴露存在性（只有真账户会被锁）

    ✓对不存在账户也计数，或改用渐进延迟

  • ✗只修了 Web 页面，App/API 端仍有差异

    ✓所有客户端共用同一认证服务与响应规范

🎤 09 · 面试追问
怎样实际测试是否存在时间侧信道？

选一个确定存在和一个确定不存在的账户，各请求数百次，统计响应时间分布（中位数、P95），看分布是否可区分。需在相近网络条件下测，排除缓存与冷启动影响。

注册必须告诉用户“邮箱已占用”怎么办？

可把结论移到邮件里：页面统一显示“请查收邮件”，已注册者收到“你已有账户，可直接登录或重置密码”。若产品坚持页面提示，就配合严格限流、验证码和异常监控。

枚举漏洞风险等级该怎么评？

单独看多为低到中危，但要结合场景：用户名是否公开、是否有限流和 MFA、账户本身是否敏感（如成人、医疗类网站，存在性本身就是隐私）。与撞库结合时影响会放大。
