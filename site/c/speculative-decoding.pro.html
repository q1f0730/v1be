投机解码 (Speculative Decoding)

Speculative Decoding

📐 01 · 定义

投机解码（Speculative Decoding）是一种无损的 LLM 推理加速方法：用一个更小更快的草稿模型（或其他机制）一次性猜测接下来的若干个 Token，再由目标大模型在一次前向传播中并行验证，按特定的接受-拒绝规则保留正确前缀。在标准算法下输出分布与目标模型单独生成完全一致，因而不损失质量。

⚙️ 02 · 原理
  1. 1

    草稿器连续自回归生成 k 个候选 Token，草稿器可以是小模型、目标模型的附加预测头（如 Medusa、EAGLE），或从提示中匹配 n-gram。

  2. 2

    目标模型对「上下文 + k 个候选」做一次前向，得到每个位置自己的概率分布；由于解码受显存带宽限制，这次前向的耗时接近生成单个 Token。

  3. 3

    从第一个候选开始依次验证：以 min(1, p/q) 的概率接受（p 为目标概率，q 为草稿概率）。

  4. 4

    遇到第一个被拒绝的位置时，从调整后的分布 max(0, p−q) 归一化中重新采样一个 Token，丢弃其后的候选。

  5. 5

    若全部接受，额外获得目标模型在下一位置采样的 Token。每轮至少产出 1 个 Token，接受率越高加速越明显。

🔤 03 · 术语
草稿模型 (Draft Model)
生成候选 Token 的小模型，需与目标模型使用相同的分词器。
接受率 (Acceptance Rate)
草稿 Token 被目标模型接受的比例，决定实际加速比。
推测长度 k
每轮草稿生成的 Token 数，过大会增加被拒绝的浪费。
提示查找解码 (Prompt Lookup)
从输入文本中匹配 n-gram 作为草稿，无需额外模型，适合摘要与代码编辑。
EAGLE / Medusa
在目标模型上附加轻量预测头生成草稿的变体方法。
💻 04 · 代码
transformers 辅助生成python
# pip install transformers accelerate torch
from transformers import AutoModelForCausalLM, AutoTokenizer

# 目标模型与草稿模型必须共享分词器；模型名以官方文档为准
target_id = "Qwen/Qwen2.5-7B-Instruct"
draft_id = "Qwen/Qwen2.5-0.5B-Instruct"

tok = AutoTokenizer.from_pretrained(target_id)
target = AutoModelForCausalLM.from_pretrained(target_id, torch_dtype="auto", device_map="auto")
draft = AutoModelForCausalLM.from_pretrained(draft_id, torch_dtype="auto", device_map="auto")

inputs = tok("用三句话解释什么是投机解码。", return_tensors="pt").to(target.device)

# 1) 草稿模型投机解码
out = target.generate(**inputs, assistant_model=draft, max_new_tokens=128)
print(tok.decode(out[0], skip_special_tokens=True))

# 2) 无需草稿模型：从输入中查找 n-gram 作为候选
out2 = target.generate(**inputs, prompt_lookup_num_tokens=10, max_new_tokens=128)

贪心解码下结果应与不加速时一致；生产部署通常在 vLLM、SGLang 等推理引擎中开启对应配置。

📊 05 · 参数对比

投机解码的草稿来源

方案草稿来源额外成本适用
独立草稿模型同系列小模型额外显存与一次小模型推理有合适小模型的开源系列
Medusa / EAGLE目标模型上的附加预测头需训练预测头追求更高接受率
提示查找 (n-gram)输入文本中的片段几乎为零摘要、改写、代码编辑等复制较多的任务
自投机目标模型跳层或早退无需第二个模型显存紧张时
⚖️ 06 · 方案取舍

开启投机解码

优点单请求延迟显著降低，输出质量不变

代价额外显存与算力，接受率低时可能变慢

适用低并发、延迟敏感的交互场景

只用连续批处理

优点高并发下吞吐最好，配置简单

代价单请求生成速度不变

适用高并发、吞吐优先的批量服务

换更小或量化模型

优点速度与成本同时下降

代价可能损失质量

适用质量要求可以放宽的任务

🕳️ 07 · 常见坑

  • ✗草稿模型与目标模型分词器不同

    ✓选用同系列共享词表的模型，或使用支持通用辅助解码的实现

  • ✗在 GPU 已打满的高并发下仍开启，吞吐反而下降

    ✓按负载压测，必要时只在低负载时启用或调小 k

  • ✗只看论文加速比，不测自己任务的接受率

    ✓在真实提示分布上记录接受率与端到端延迟

  • ✗以为采样设置下结果逐字相同

    ✓保证的是分布一致；随机采样时具体文本仍会随机变化

🎤 09 · 面试追问
为什么投机解码能在不损失质量下加速？

自回归解码受显存带宽限制，目标模型前向处理 1 个或 k 个 Token 耗时相近。让小模型先猜 k 个，大模型一次验证，多个 Token 共享一次大模型前向。接受-拒绝采样规则经过证明，最终分布与目标模型直接采样完全相同。

什么情况下投机解码收益很小甚至为负？

草稿与目标分布差距大导致接受率低；高并发时 GPU 已处于计算瓶颈，验证多余 Token 占用了本可服务其他请求的算力；草稿模型本身不够快。因此需要在真实负载下测量，而不是默认开启。

提示查找解码为什么对代码编辑特别有效？

代码编辑与摘要等任务的输出大量复制输入中的片段。提示查找直接在输入里匹配当前末尾的 n-gram，把其后续作为草稿，不需要额外模型，命中时一次可接受很多 Token，对 Agent 改写文件这类场景加速明显。
