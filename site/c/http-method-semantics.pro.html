HTTP方法安全性与幂等性

HTTP Method Semantics

📐 01 · 定义

HTTP 方法语义由 RFC 9110 定义，核心是两个属性：安全（Safe，不改变服务器状态，如 GET、HEAD）和幂等（Idempotent，执行一次与多次的预期效果相同，如 PUT、DELETE）。它属于协议语义层，决定缓存、预取、代理与客户端是否可以自动重试，是设计可靠 API 的基础契约。

⚙️ 02 · 原理
  1. 1

    安全方法只读：GET、HEAD、OPTIONS、TRACE；浏览器、爬虫、预取可随意发起。

  2. 2

    幂等方法包含全部安全方法，再加 PUT 和 DELETE，网络失败时可安全重试。

  3. 3

    POST 和 PATCH 不保证幂等，重复发送可能创建多条记录或重复应用修改。

  4. 4

    缓存层通常只缓存 GET/HEAD 响应；非安全方法成功后会使相关缓存失效。

  5. 5

    非幂等操作可借助 Idempotency-Key 请求头，由服务端记录结果实现重复请求去重。

🔤 03 · 术语
安全方法 (Safe Method)
语义上只读，客户端不请求状态变更。
幂等 (Idempotent)
多次相同请求对服务器的预期效果与一次相同。
可缓存 (Cacheable)
响应允许被存储并复用，GET、HEAD 默认可缓存。
幂等键 (Idempotency-Key)
客户端生成的唯一键，让服务端对重复 POST 去重。
预检请求 (Preflight)
跨域非简单请求前浏览器自动发出的 OPTIONS 请求。
💻 04 · 代码
用幂等键让 POST 可重试python
import json
import redis
from flask import Flask, request

app = Flask(__name__)
r = redis.Redis()

@app.post("/v1/payments")
def create_payment():
    key = request.headers.get("Idempotency-Key")
    if not key:
        return {"error": "Idempotency-Key required"}, 400
    cache_key = f"idem:{key}"
    # 占位：只有第一个请求能 SET 成功，24 小时过期
    if not r.set(cache_key, "processing", nx=True, ex=86400):
        saved = r.get(cache_key)
        if saved == b"processing":
            return {"error": "in progress"}, 409
        return json.loads(saved), 200        # 重放首次结果
    result = {"id": "pay_1", "amount": request.json["amount"]}
    # charge(...)  真实扣款逻辑
    r.set(cache_key, json.dumps(result), ex=86400)
    return result, 201

同一幂等键重复提交返回首次结果；生产中还应校验请求体与首次一致。

📊 05 · 参数对比

方法属性一览

方法安全幂等常见用途
GET / HEAD是是读取资源 / 只取头
PUT否是整体替换或按 ID 创建
DELETE否是删除资源
POST否否创建、触发动作
PATCH否不保证部分更新
⚖️ 06 · 方案取舍

PUT 按客户端 ID 创建

优点天然幂等，重试安全

代价客户端需生成 ID

适用离线优先、客户端可生成 UUID

POST + 幂等键

优点保留 POST 语义，可安全重试

代价服务端需存储键与结果

适用支付、下单等关键写操作

POST 不做处理

优点实现最简单

代价超时重试导致重复数据

适用重复无害的操作，如日志上报

🕳️ 07 · 常见坑

  • ✗用 GET 执行删除或状态变更，如 /delete?id=1

    ✓改为 DELETE/POST，并加 CSRF 防护

  • ✗以为幂等等于每次响应相同

    ✓幂等指服务器状态效果相同，响应码可以不同（如第二次 DELETE 返回 404）

  • ✗PATCH 用增量语义 {"count": "+1"} 却允许自动重试

    ✓非幂等 PATCH 不自动重试，或改为设定绝对值

  • ✗GET 请求带 body 传参

    ✓GET body 无定义语义，参数放 query；复杂查询用 POST

🎤 09 · 面试追问
DELETE 第二次返回 404，还算幂等吗？

算。幂等关注的是对服务器状态的效果：第一次删除后资源已不存在，第二次请求不会产生新的副作用。响应状态码不同不影响幂等性。

为什么客户端和代理只自动重试幂等请求？

网络超时时无法判断请求是否已在服务端执行。幂等请求重发不会造成额外效果，可安全重试；非幂等请求重发可能导致重复创建或扣款，因此需要幂等键等机制。

幂等键服务端怎么实现才可靠？

用原子操作（唯一约束或 SET NX）占位，处理中再次请求返回冲突；完成后存储响应并设置过期；校验同一键的请求参数一致，不一致返回错误。
