领域驱动设计 (DDD)

Domain-Driven Design

📐 01 · 定义

领域驱动设计（DDD）是 Eric Evans 于 2003 年系统提出的软件建模方法，主张以业务领域为中心组织代码与团队。战略设计用限界上下文和通用语言划清模型边界；战术设计用实体、值对象、聚合、领域事件等模式在边界内表达业务规则。它主要解决复杂业务中模型混乱、概念歧义和改动牵一发动全身的问题。

⚙️ 02 · 原理
  1. 1

    与领域专家协作（如事件风暴工作坊），梳理业务流程、关键事件与名词，形成团队共享的通用语言。

  2. 2

    按语义一致性划分限界上下文：同一个词（如「用户」）在不同上下文可以有不同模型，各自独立演进。

  3. 3

    用上下文映射描述上下文之间的关系，如客户-供应方、遵奉者、防腐层（ACL）、开放主机服务。

  4. 4

    在上下文内识别聚合：一组必须保持一致的对象，由聚合根对外暴露行为，并在一个事务内守护不变量。

  5. 5

    聚合之间通过 ID 引用和领域事件协作，跨聚合的一致性通常接受最终一致。

  6. 6

    代码目录、模块和服务边界与限界上下文对齐，让业务改动集中在少数模块内。

🔤 03 · 术语
限界上下文 (Bounded Context)
一个模型及其通用语言保持一致含义的边界，常对应模块、服务或团队。
通用语言 (Ubiquitous Language)
领域专家与开发者共用、并直接体现在代码命名中的业务词汇。
聚合 (Aggregate)
作为一致性边界的一组实体与值对象，外部只能通过聚合根修改。
值对象 (Value Object)
无身份、按属性判等且通常不可变的对象，如金额、地址。
防腐层 (Anti-Corruption Layer)
在两个上下文之间做模型翻译，防止外部模型污染本地模型。
领域事件 (Domain Event)
领域中已发生、业务关心的事实，如「订单已支付」，用于解耦协作。
💻 04 · 代码
聚合根守护不变量python
from dataclasses import dataclass, field
from decimal import Decimal

@dataclass(frozen=True)
class Money:                      # 值对象：不可变、按值相等
    amount: Decimal
    currency: str = "CNY"

@dataclass
class Order:                      # 聚合根：外部只能通过它改订单
    order_id: str
    lines: list = field(default_factory=list)
    status: str = "DRAFT"
    events: list = field(default_factory=list)

    def add_line(self, sku: str, qty: int, price: Money):
        if self.status != "DRAFT":
            raise ValueError("已提交的订单不能再加商品")   # 不变量
        if qty <= 0:
            raise ValueError("数量必须为正")
        self.lines.append((sku, qty, price))

    def submit(self):
        if not self.lines:
            raise ValueError("空订单不能提交")
        self.status = "SUBMITTED"
        self.events.append(("OrderSubmitted", self.order_id))  # 领域事件

业务规则写在聚合方法里而不是散在控制器中；事件由应用层发布给其他上下文。

📊 05 · 参数对比

DDD 战术模式速查

模式身份职责持久化
实体 (Entity)有唯一 ID随时间变化的业务对象随所属聚合保存
值对象无 ID描述属性，不可变嵌入实体中
聚合根有 ID一致性边界入口仓储以聚合为单位读写
领域服务无状态不属于单个实体的业务逻辑无
仓储 (Repository)—像集合一样存取聚合封装具体数据库
⚖️ 06 · 方案取舍

完整 DDD（战略+战术）

优点复杂规则清晰，边界稳定可演进

代价学习与建模成本高，代码量增加

适用核心业务复杂且长期演进

只用战略设计

优点以较低成本获得清晰的模块边界

代价上下文内部仍可能是贫血模型

适用中等复杂度、需要拆模块或服务

简单 CRUD

优点开发快，框架脚手架即可

代价规则增多后逻辑散落难维护

适用支撑域或以数据录入为主的系统

🕳️ 07 · 常见坑

  • ✗聚合设计过大，一次加载整棵对象树导致锁冲突

    ✓聚合尽量小，只包含必须同事务一致的数据，其余用 ID 引用

  • ✗一个事务里修改多个聚合

    ✓一次事务只改一个聚合，跨聚合用领域事件与最终一致

  • ✗照搬战术模式却不和业务方建立通用语言

    ✓先做领域建模与命名对齐，模式是手段而非目标

  • ✗按技术层拆微服务，再叫它 DDD

    ✓服务边界应对齐限界上下文，而非 controller/service/dao 分层

☑️ 08 · 检查清单
🎤 09 · 面试追问
如何确定聚合边界？

从不变量出发：哪些数据必须在同一时刻强一致，才放进同一聚合。其余通过 ID 引用与事件最终一致。经验上聚合要小，否则会带来并发冲突与加载成本。也要看业务能否接受短暂不一致，例如库存与订单常分属不同聚合。

限界上下文和微服务是什么关系？

限界上下文是模型与语言的边界，微服务是部署单元。一个上下文可以是一个服务，也可以是模块化单体中的一个模块；一个服务不应横跨多个上下文的模型。先在单体中把上下文划清，再按需要拆服务，风险更低。

什么时候不该用 DDD？

业务规则简单、以增删改查为主，或属于可外购的通用域（如认证、支付网关集成）时，DDD 的建模成本大于收益。DDD 应集中投入在决定竞争力的核心域，其余用简单方案或现成服务。
