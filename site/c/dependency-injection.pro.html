依赖注入 (DI)

Dependency Injection

📐 01 · 定义

依赖注入（Dependency Injection，DI）是一种设计技术：对象不在内部自行创建其依赖（数据库连接、HTTP 客户端、配置等），而是由外部通过构造函数、参数或属性传入。它是控制反转（IoC）的一种实现，使代码依赖抽象而非具体实现，从而易于测试、替换和组合，是分层架构与六边形架构落地的基础手段。

⚙️ 02 · 原理
  1. 1

    识别依赖：类或函数完成工作所需的外部协作者，如仓储、邮件服务、时钟。

  2. 2

    用接口或协议定义依赖的抽象（Python 的 Protocol、TypeScript 的 interface），业务代码只依赖抽象。

  3. 3

    通过构造函数注入（最常用）、方法参数注入或框架提供的注入机制，把具体实现传入。

  4. 4

    在应用入口的组合根（Composition Root）集中创建并装配所有具体实现，生产与测试使用不同装配。

  5. 5

    可选使用 DI 容器或框架（如 FastAPI Depends、Spring、NestJS）自动解析依赖图并管理生命周期。

🔤 03 · 术语
控制反转 (IoC)
对象不再主动获取依赖，由外部控制创建与装配。
构造函数注入 (Constructor Injection)
通过构造参数传入依赖，依赖关系显式且不可变。
组合根 (Composition Root)
应用中集中装配依赖的唯一位置，通常在入口处。
DI 容器 (DI Container)
根据注册信息自动创建和注入依赖的框架组件。
服务定位器 (Service Locator)
对象主动向全局注册表索取依赖，常被视为反模式。
生命周期 (Lifetime / Scope)
依赖实例的存活范围，如单例、每请求、每次新建。
💻 04 · 代码
构造函数注入 + 测试替身python
from typing import Protocol

class Mailer(Protocol):
    def send(self, to: str, body: str) -> None: ...

class UserRepo(Protocol):
    def add(self, email: str) -> int: ...

class SignupService:
    def __init__(self, repo: UserRepo, mailer: Mailer):   # 依赖从外部传入
        self.repo, self.mailer = repo, mailer

    def signup(self, email: str) -> int:
        uid = self.repo.add(email)
        self.mailer.send(email, "欢迎注册")
        return uid

# 测试：注入假实现，不连数据库、不真发邮件
class FakeRepo:
    def __init__(self): self.rows = []
    def add(self, email): self.rows.append(email); return len(self.rows)
class FakeMailer:
    def __init__(self): self.sent = []
    def send(self, to, body): self.sent.append(to)

def test_signup_sends_mail():
    repo, mailer = FakeRepo(), FakeMailer()
    assert SignupService(repo, mailer).signup("a@x.com") == 1
    assert mailer.sent == ["a@x.com"]

业务类只依赖协议；生产在组合根注入真实实现，测试注入内存假对象。

📊 05 · 参数对比

依赖获取方式对比

方式可测试性依赖是否显式评价
内部直接 new / 全局单例差否紧耦合，难以替换
服务定位器中否，藏在实现里常被视为反模式
构造函数注入好是首选
框架 DI 容器好是（通过声明）规模大时减少装配代码
⚖️ 06 · 方案取舍

手动注入（纯构造函数）

优点简单透明，无框架依赖

代价依赖多时装配代码冗长

适用中小型项目、库代码

框架内置 DI（如 FastAPI Depends）

优点与框架集成，按请求管理生命周期

代价绑定框架

适用Web 应用

通用 DI 容器

优点自动解析复杂依赖图

代价引入魔法，排错困难

适用大型企业应用

🕳️ 07 · 常见坑

  • ✗在业务代码各处调用容器取依赖

    ✓只在组合根使用容器，业务类通过构造参数接收依赖

  • ✗构造函数参数越来越多仍不拆分

    ✓依赖过多提示职责过多，应拆分类

  • ✗为每个类都定义接口，过度抽象

    ✓只为确实需要替换或隔离的外部依赖定义抽象

  • ✗单例依赖持有请求级状态，导致数据串号

    ✓明确生命周期，请求相关数据使用请求作用域

🎤 09 · 面试追问
依赖注入和控制反转是什么关系？

控制反转是更宽泛的原则：把流程或对象创建的控制权从业务代码交给框架或外部。依赖注入是实现 IoC 的一种具体方式，专指依赖由外部提供。模板方法、事件回调也是 IoC 的其他形式。

为什么说服务定位器是反模式？

对象内部调用全局定位器获取依赖，依赖关系不出现在构造签名中，阅读代码看不出它需要什么，测试时必须配置全局状态，且缺少依赖要到运行时才报错。构造函数注入让依赖显式、可在编译或启动期检查。

依赖注入如何帮助 AI 编程？

依赖显式且可替换的代码更容易让 AI 生成单元测试：可以直接注入假对象，而不必启动数据库或调用外部服务。在规则文件中要求“外部依赖通过构造函数注入”，能让 Agent 生成的代码更易测、更易审查。
