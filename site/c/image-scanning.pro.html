容器镜像漏洞扫描

Image Scanning

📐 01 · 定义

容器镜像扫描（Image Scanning）是软件供应链安全的一环：解析镜像各层里的操作系统包与语言依赖，生成软件物料清单（SBOM），再与 CVE 等漏洞库比对，输出漏洞、严重级别和可修复版本，通常作为 CI 门禁和镜像仓库准入策略执行。

⚙️ 02 · 原理
  1. 1

    解包镜像：按层读取文件系统，识别发行版（如 Debian、Alpine）及其包管理数据库。

  2. 2

    盘点组件：解析 dpkg/apk/rpm 数据库和 package-lock、go.sum、jar 等语言清单，得到组件与版本列表（SBOM）。

  3. 3

    匹配漏洞：用组件名+版本对照 NVD、发行版安全公告、GitHub Advisory 等数据源，得到 CVE 列表。

  4. 4

    评级与过滤：按 CVSS/厂商严重级别分级，标记是否已有修复版本，并应用忽略清单（如 .trivyignore）。

  5. 5

    策略执行：CI 中超过阈值即以非零退出码失败；仓库或准入控制器可拒绝未扫描或高危镜像。

🔤 03 · 术语
软件物料清单 (SBOM)
镜像内所有组件及版本的结构化清单，常见格式为 SPDX 与 CycloneDX。
CVE (Common Vulnerabilities and Exposures)
公开漏洞的统一编号体系，如 CVE-2021-44228。
CVSS
通用漏洞评分系统，0–10 分量化漏洞严重程度。
可修复 (Fixed Version)
上游已发布修复版本的漏洞，可通过升级包消除。
VEX
漏洞可利用性声明，说明某 CVE 在本产品中是否真正受影响。
准入控制 (Admission Control)
K8s 在创建资源前执行的策略校验，可拦截不合规镜像。
💻 04 · 代码
Trivy 扫描并设门禁bash
# 1) 只关心高危/严重，且仅统计已有修复版本的漏洞
trivy image \
  --severity HIGH,CRITICAL \
  --ignore-unfixed \
  --exit-code 1 \
  myapp:1.4.2          # 有命中则退出码为 1，CI 失败

# 2) 生成 SBOM（CycloneDX 格式）留档
trivy image --format cyclonedx --output sbom.cdx.json myapp:1.4.2

# 3) 之后数据库更新了，可直接对 SBOM 复扫，无需重新拉镜像
trivy sbom sbom.cdx.json

# 4) 用 Grype 交叉验证，达到 high 级别即失败
grype myapp:1.4.2 --fail-on high

把扫描变成可失败的 CI 步骤，并保存 SBOM 以便漏洞库更新后复扫。

CI 构建时扫描

优点问题在合并前暴露，修复成本低

代价只反映构建当天的漏洞库

适用所有项目的默认基线

优点新 CVE 公布后能发现存量镜像风险

准入时强制拦截

🕳️ 07 · 常见坑

  • ✗阈值设为任何漏洞都失败，团队很快学会跳过扫描

    ✓先只拦 CRITICAL/HIGH 且可修复，配合有到期时间的忽略清单

  • ✗只在构建时扫一次，上线后不再关注

    ✓对仓库中在用镜像定期复扫或对 SBOM 复扫，新 CVE 触发工单

  • ✗用 latest 标签扫描，扫的和部署的不是同一个镜像

    ✓按镜像 digest（sha256）扫描和部署，结果与制品一一对应

  • ✗基础镜像臃肿，大量与业务无关的包贡献漏洞

    ✓换用 slim、distroless 等精简基础镜像，从源头减少攻击面

🎤 09 · 面试追问
扫描报 200 个漏洞，你怎么排优先级？

先按严重级别和是否有修复版本过滤；再看组件是否在运行路径上被加载（可达性）、是否暴露在网络面；结合 EPSS/KEV 判断是否已被在野利用。升级基础镜像通常一次消掉大半。

镜像扫描和 SAST、依赖扫描有何区别？

SAST 分析自研源码的缺陷；依赖扫描（SCA）看清单文件中的三方库；镜像扫描看最终制品，覆盖系统包和真正打进去的依赖，更贴近运行时，但看不到自研代码逻辑漏洞。

为什么有了 SBOM 还要 VEX？

SBOM 只说明包含什么组件，匹配出的 CVE 未必可利用，比如漏洞函数没被调用或配置未开启。VEX 由供应方声明不受影响/已修复/调查中，用来降噪，让下游只处理真实风险。
