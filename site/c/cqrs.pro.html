命令查询职责分离

CQRS

📐 01 · 定义

命令查询职责分离（CQRS）是一种架构模式：把修改状态的命令（Command）和读取数据的查询（Query）拆成两套模型，必要时使用不同的存储。写模型专注业务规则和一致性，读模型按页面或查询需求反规范化，从而分别优化和扩展。读模型通常通过事件异步更新，因此存在同步延迟。

⚙️ 02 · 原理
  1. 1

    命令端：接收意图明确的命令，校验业务规则后修改写模型，不返回查询数据。

  2. 2

    发布变化：写入成功后发出领域事件，可通过 Outbox 或 CDC 可靠投递。

  3. 3

    投影：订阅事件的投影程序把变化写入一个或多个反规范化的读模型。

  4. 4

    查询端：直接读取为查询定制的读模型，例如搜索索引、缓存或宽表。

  5. 5

    一致性：读模型相对写模型有延迟，界面需按最终一致设计或做读己之写处理。

🔤 03 · 术语
命令 (Command)
表达改变状态意图的请求，如 PlaceOrder，可被拒绝。
查询 (Query)
只读请求，不产生副作用。
读模型 / 投影 (Projection)
由事件推导出的、为特定查询优化的数据视图。
反规范化 (Denormalization)
冗余存储数据以减少查询时的关联计算。
投影重建 (Replay)
从头重放事件以重新生成或修复读模型。
💻 04 · 代码
命令与投影分离typescript
type OrderPlaced = { type: "OrderPlaced"; orderId: string; userId: string; total: number };

// 写模型：只关心业务规则
const orders = new Map<string, { status: string; total: number }>();
const bus: Array<(e: OrderPlaced) => void> = [];

function placeOrder(cmd: { orderId: string; userId: string; total: number }) {
  if (cmd.total <= 0) throw new Error("金额必须为正");      // 业务校验
  if (orders.has(cmd.orderId)) throw new Error("订单已存在");
  orders.set(cmd.orderId, { status: "PLACED", total: cmd.total });
  bus.forEach((h) => h({ type: "OrderPlaced", ...cmd }));  // 发布事件
}

// 读模型：按「用户订单汇总」页面定制
const userSummary = new Map<string, { count: number; spent: number }>();
bus.push((e) => {
  const s = userSummary.get(e.userId) ?? { count: 0, spent: 0 };
  userSummary.set(e.userId, { count: s.count + 1, spent: s.spent + e.total });
});

placeOrder({ orderId: "o1", userId: "u1", total: 99 });
console.log(userSummary.get("u1"));   // { count: 1, spent: 99 }

进程内演示；生产中事件经消息系统异步传递，读模型存于独立存储。

⚖️ 06 · 方案取舍

完整 CQRS（分离存储）

优点读写独立优化与扩展

代价同步延迟、组件多、调试难

适用读写负载差异大、查询复杂

同库读写模型分离

优点代码清晰，无同步延迟

代价扩展受限于单库

适用想理清复杂领域逻辑

传统 CRUD

优点简单直接，团队熟悉

代价复杂查询与业务规则混杂

适用大多数普通业务系统

🕳️ 07 · 常见坑

  • ✗简单 CRUD 系统也上 CQRS，复杂度远超收益

    ✓只在复杂领域或读写差异显著的子系统中使用

  • ✗用户提交后马上查询，读模型还没更新

    ✓返回命令结果给前端乐观展示，或关键页面读写模型

  • ✗投影非幂等，事件重放后数据翻倍

    ✓投影按事件 ID 或版本幂等处理，支持安全重建

☑️ 08 · 检查清单
🎤 09 · 面试追问
CQRS 一定要配合事件溯源吗？

不需要。CQRS 只要求读写模型分离，写端可以是普通关系表，通过 Outbox 或 CDC 更新读模型。事件溯源与 CQRS 常一起使用，因为事件流天然适合投影，但两者可以独立采用。

CQRS 带来的最大挑战是什么？

读写之间的最终一致：用户可能看不到刚做的修改；还要处理投影失败、重放、事件版本演进和多个读模型的运维。调试时需要跨组件追踪一次变更的完整路径。

什么场景适合 CQRS？

读写比例悬殊、查询形态多样（列表、搜索、报表）、业务规则复杂需要清晰写模型、或读写需独立扩展的子系统。不应作为整个系统的默认架构，而是局部使用。
