软件供应链攻击

Supply Chain Attacks

📐 01 · 定义

软件供应链攻击指攻击者不直接攻击目标系统，而是污染其依赖的源代码、第三方包、构建工具、CI 流水线或分发渠道，让恶意代码随正常更新进入下游。与“已知漏洞”不同，这里的组件本身是被故意植入恶意行为，扫描已知 CVE 往往发现不了。

⚙️ 02 · 原理
  1. 1

    入口一：注册与流行包相似的名字（typosquatting），或 AI 幻觉出的包名，等待误装。

  2. 2

    入口二：依赖混淆，把内部包名发布到公共仓库并给出更高版本号，诱使解析器优先拉取。

  3. 3

    入口三：接管维护者账号或长期潜伏取得信任，在正常版本中植入后门（如 2024 年 xz-utils 事件）。

  4. 4

    恶意代码常借安装脚本（npm postinstall、setup.py）在安装时立即执行，窃取凭据或植入持久化。

  5. 5

    入口四：攻破构建系统或 CI，篡改产物而源码看起来干净；防御依赖来源证明与可复现构建。

🔤 03 · 术语
Typosquatting
注册与知名包拼写相近的名字诱导误装。
依赖混淆 (Dependency Confusion)
利用公私仓库解析顺序，让公共同名包替换内部包。
Slopsquatting
抢注大模型常幻觉出的不存在包名，等 AI 生成代码去安装。
SLSA
供应链制品完整性分级框架，要求可追溯的构建来源。
来源证明 (Provenance)
签名声明制品由哪个仓库、哪次构建产出。
Sigstore
开源签名基础设施，用短期证书和透明日志签名制品。
💻 04 · 代码
安装与构建加固bash
#!/usr/bin/env bash
set -euo pipefail

# Node：严格按锁文件安装，并禁止依赖的安装脚本自动执行
npm ci --ignore-scripts

# 校验已安装包的 registry 签名与来源证明（provenance）
npm audit signatures

# 发布自己的包时附带来源证明（需在受支持的 CI 中运行）
# npm publish --provenance --access public

# Python：用 pip-tools 生成带哈希的锁定文件
pip-compile --generate-hashes -o requirements.txt requirements.in
# 安装时任何包哈希不匹配都会失败
pip install --require-hashes -r requirements.txt

# 安装 AI 建议的新依赖前，先确认包确实存在且来源可信
npm view some-package name repository.url time.created

锁版本+校验哈希+禁安装脚本+来源证明，并核实 AI 推荐的包名。

⚖️ 06 · 方案取舍

私有代理仓库 + 白名单

优点集中管控可安装的包

代价引入新包流程变慢

适用企业内网与高合规团队

新版本冷却期

优点多数恶意版本几天内被发现下架

代价安全补丁也会延迟采纳

适用非紧急的常规升级

禁用安装脚本

优点阻断最常见的安装即执行

代价部分原生模块需手动构建

适用CI 与开发机默认开启

🕳️ 07 · 常见坑

  • ✗直接运行 AI 生成的 pip/npm install 命令

    ✓安装前核实包名、维护者、下载量和仓库链接

  • ✗CI 中的 Action/镜像只用可变标签如 @v3、latest

    ✓固定到完整 commit SHA 或镜像 digest

  • ✗CI 令牌拥有全仓库写权限

    ✓按任务最小权限，发布用 OIDC 短期凭据

  • ✗内部包名未加 scope，公共仓库可被抢注

    ✓用组织 scope，并在公共仓库占位

🎤 09 · 面试追问
供应链攻击和依赖漏洞有什么区别？

依赖漏洞是无意的缺陷，通常有 CVE，可被扫描器匹配；供应链攻击是故意投毒，恶意版本刚发布时没有 CVE，需靠来源验证、行为检测、锁定版本和审核新依赖来防御。

依赖混淆是怎么发生的？如何防？

构建同时配置了私有与公共仓库，解析器按版本号取最高者，攻击者在公共仓库发布同名高版本即可被拉取。防法：使用 scope/命名空间，配置包到仓库的显式映射，只允许私有代理转发白名单包。

用 AI 写代码会带来哪些供应链新风险？

模型可能推荐不存在的包名，攻击者抢注后被自动安装（slopsquatting）；Agent 在终端自动执行安装命令时缺少人工把关。应限制 Agent 安装权限、核实新依赖，并在 CI 中统一校验。
