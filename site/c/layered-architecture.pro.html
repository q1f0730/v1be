分层架构

Layered Architecture

🧸 回到小白版

📐 01 · 定义

分层架构（Layered Architecture）按职责把系统划分为若干水平层，典型为表现层、业务（领域）层、数据访问层，每层只依赖其下方的层并通过明确接口交互。它是最常见的应用架构风格，通过关注点分离降低修改影响面、方便测试与替换实现；六边形、整洁架构等可视为其依赖方向更严格的演进。

⚙️ 02 · 原理
  1. 1

    表现层处理 HTTP/UI 交互：解析请求、校验格式、调用业务层并把结果转成响应。

  2. 2

    业务层承载规则与用例编排，不关心数据来自哪个数据库，也不关心结果如何展示。

  3. 3

    数据访问层（Repository/DAO）封装 SQL、ORM 或外部 API 调用，向上提供领域对象。

  4. 4

    依赖自上而下单向流动；严格分层禁止跨层调用，宽松分层允许跳过中间层。

  5. 5

    层间传递 DTO 或领域对象，避免把数据库实体或框架对象泄漏到上层。

🔤 03 · 术语
关注点分离 (Separation of Concerns)
不同职责放在不同模块，降低相互影响。
仓储模式 (Repository)
以集合式接口封装数据持久化细节。
服务层 (Service Layer)
定义应用用例边界、编排业务逻辑的层。
DTO (Data Transfer Object)
层间或跨进程传递数据的简单对象。
污水池反模式 (Sinkhole)
请求穿过各层却几乎不做处理，分层只增加样板代码。
💻 04 · 代码
三层结构的最小示例python
import sqlite3

# 数据访问层：只管怎么存取
class UserRepo:
    def __init__(self, conn: sqlite3.Connection):
        self.conn = conn
    def find_by_email(self, email: str):
        return self.conn.execute(
            "SELECT id, email FROM users WHERE email = ?", (email,)).fetchone()
    def insert(self, email: str) -> int:
        cur = self.conn.execute("INSERT INTO users(email) VALUES (?)", (email,))
        return cur.lastrowid

# 业务层：只管规则，不写 SQL、不碰 HTTP
class UserService:
    def __init__(self, repo: UserRepo):
        self.repo = repo
    def register(self, email: str) -> int:
        email = email.strip().lower()
        if self.repo.find_by_email(email):
            raise ValueError("邮箱已注册")
        return self.repo.insert(email)

# 表现层：只管输入输出格式
def register_handler(body: dict, service: UserService) -> dict:
    try:
        return {"status": 201, "id": service.register(body["email"])}
    except ValueError as e:
        return {"status": 409, "error": str(e)}

换数据库只改 UserRepo；业务规则可脱离 HTTP 和真实数据库进行单元测试。

⚖️ 06 · 方案取舍

经典分层

优点易理解、团队上手快

代价业务层常依赖数据层实现细节

适用中小型 CRUD 应用

六边形/整洁架构

优点业务核心不依赖基础设施，易测易换

代价接口与样板代码更多

适用业务复杂、生命周期长

不分层脚本式

优点最快写出原型

代价规模变大后难维护

适用一次性工具、原型验证

🕳️ 07 · 常见坑

  • ✗在控制器或页面组件里直接写 SQL

    ✓数据访问集中到仓储层，上层只调接口

  • ✗ORM 实体一路传到前端响应

    ✓在边界转换为 DTO，避免泄漏字段与懒加载问题

  • ✗业务逻辑散落在仓储层的查询里

    ✓仓储只做数据存取，规则判断放业务层

  • ✗为简单功能强行堆五六层空壳

    ✓层数匹配复杂度，无逻辑的层可合并

🎤 09 · 面试追问
分层架构和六边形架构的核心区别？

经典分层中业务层依赖数据访问层，依赖方向指向基础设施；六边形架构让业务核心定义端口接口，数据库、HTTP 等适配器实现这些接口，依赖指向核心，因此替换基础设施和单测更容易。

如何防止分层在演进中被破坏？

用目录与包可见性约束；引入依赖规则检查工具在 CI 中拦截违规导入；Code Review 关注跨层调用；在规则文件中向 AI Agent 写明分层约定和禁止事项。

事务边界应放在哪一层？

通常放在业务（服务）层的用例方法上：一个用例对应一个事务，保证多次仓储操作的原子性。放在数据访问层粒度太细，放在控制器层又把业务语义泄露到表现层。
