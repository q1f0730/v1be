联合索引与最左前缀

Composite Indexes

🧸 回到小白版

📐 01 · 定义

联合索引（Composite Index / 复合索引）是在多列上按指定顺序建立的单个索引，属于数据库索引与查询优化层。B-tree 联合索引按 (a, b, c) 字典序排序，因此遵循最左前缀原则：查询必须从最左列开始连续使用才能高效定位。列顺序设计决定它能服务哪些查询、能否同时满足过滤、排序与覆盖。

⚙️ 02 · 原理
  1. 1

    索引条目按第一列排序，第一列相同时按第二列排序，依此类推，形成字典序。

  2. 2

    等值条件依次匹配最左的连续列，可把搜索范围收窄到很小的区间。

  3. 3

    遇到范围条件（>、<、BETWEEN）后，后续列通常无法再用于定位，只能在区间内过滤。

  4. 4

    若 ORDER BY 与索引列顺序一致，数据库可直接按索引顺序输出，省去额外排序。

  5. 5

    索引包含查询所需全部列时成为覆盖索引，无需回表读取数据行。

🔤 03 · 术语
最左前缀 (Leftmost Prefix)
联合索引只能从第一列开始、连续使用若干列来定位。
等值优先，范围在后 (ESR)
常见设计经验：等值列在前，排序列其次，范围列最后。
回表 (Table Lookup)
通过索引找到行位置后，再去表中读取其他列。
索引下推 (Index Condition Pushdown)
MySQL 在存储引擎层用索引列先过滤，减少回表。
选择性 (Selectivity)
列不同值越多、过滤后剩余行越少，选择性越高。
💻 04 · 代码
列顺序与最左前缀验证sql
-- 常见查询：某租户下某状态的订单，按时间倒序
CREATE INDEX idx_orders_tenant_status_created
  ON orders (tenant_id, status, created_at DESC);

-- ✅ 用到全部三列：两列等值 + 按第三列有序输出
EXPLAIN SELECT id FROM orders
 WHERE tenant_id = 7 AND status = 'paid'
 ORDER BY created_at DESC LIMIT 20;

-- ✅ 只用最左列也能走索引
EXPLAIN SELECT id FROM orders WHERE tenant_id = 7;

-- ❌ 跳过最左列，通常无法用该索引定位
EXPLAIN SELECT id FROM orders WHERE status = 'paid';

-- 覆盖索引：INCLUDE 附带列（PostgreSQL 11+）
CREATE INDEX idx_cover ON orders (tenant_id, status) INCLUDE (amount);

等值列在前、排序列在后，可同时满足过滤与 ORDER BY；跳过首列则失效。

📊 05 · 参数对比

索引 (a,b,c) 能否命中

查询条件可用列说明
a = ? AND b = ?a, b最左连续等值
a = ? AND c = ?a（c 仅过滤）跳过 b，c 无法定位
a > ? AND b = ?a（b 仅过滤）范围后列无法定位
b = ? AND c = ?通常不可用缺最左列
⚖️ 06 · 方案取舍

一个宽联合索引

优点一份索引服务多种前缀查询，可覆盖

代价写放大、体积大，列序难兼顾

适用查询模式集中且稳定

多个单列索引

优点灵活，各自简单

代价多条件时依赖索引合并，常不如联合索引

适用查询条件组合多变

覆盖索引（含 INCLUDE）

优点避免回表，读最快

代价索引更大、写入更慢

适用热点只读查询

🕳️ 07 · 常见坑

  • ✗按列的「重要性」排序，而不是按查询模式

    ✓按 ESR：等值过滤列→排序列→范围列，再结合选择性

  • ✗建了 (a,b) 又建 (a)，形成冗余索引

    ✓(a,b) 已覆盖只按 a 的查询，删除冗余索引减少写开销

  • ✗认为 WHERE 条件书写顺序影响命中

    ✓优化器会重排 AND 条件，关键是索引列顺序

  • ✗依赖 skip scan 让跳过首列的查询变快

    ✓部分数据库支持但取决于首列基数，不可作为设计前提

🎤 09 · 面试追问
为什么范围条件之后的列无法用于定位？

B-tree 按字典序排列，a 取某个范围时，b 在这个区间内并不有序，无法二分定位，只能逐条过滤。等值条件则保证后续列在区间内有序。

WHERE a=? ORDER BY b 与 WHERE a>? ORDER BY b，索引(a,b) 表现有何不同？

前者 a 固定，b 在区间内有序，可直接按索引输出无需排序；后者跨越多个 a 值，b 整体无序，通常需要额外排序（filesort/Sort 节点）。

如何在索引数量和写性能之间权衡？

每个索引都要在写入时维护，增加 I/O 与锁争用。用 pg_stat_user_indexes 或 sys schema 找未使用和冗余索引；优先一个联合索引服务多个前缀查询。
