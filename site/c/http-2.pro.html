HTTP/2

📐 01 · 定义

HTTP/2 是 HTTP 的第二个主要版本（现行规范 RFC 9113），保持方法、状态码、头部等语义不变，改变的是传输方式：二进制分帧、单连接多路复用、HPACK 头部压缩与流级流量控制。它解决了 HTTP/1.1 的应用层队头阻塞和多连接开销，但仍受 TCP 层队头阻塞影响。

⚙️ 02 · 原理
  1. 1

    浏览器通过 TLS 的 ALPN 扩展协商 h2；明文 h2c 浏览器不支持，多用于内部服务。

  2. 2

    消息被拆成二进制帧（HEADERS、DATA 等），每帧带流 ID。

  3. 3

    多个请求作为独立的流在同一连接上交错传输，响应可乱序返回。

  4. 4

    HPACK 用静态表、动态表与哈夫曼编码压缩重复的头部字段。

  5. 5

    流量控制按流和连接两级窗口限速；单个 TCP 丢包仍会阻塞所有流。

🔤 03 · 术语
帧 (Frame)
HTTP/2 最小传输单位，有类型、长度与流 ID。
流 (Stream)
连接内一个双向帧序列，对应一次请求/响应。
多路复用 (Multiplexing)
多个流在同一连接上并发交错传输。
HPACK
HTTP/2 头部压缩格式，RFC 7541。
ALPN
TLS 扩展，握手时协商应用层协议（h2、http/1.1）。
服务器推送 (Server Push)
服务端主动推送资源，已被主流浏览器移除。
💻 04 · 代码
验证站点是否启用 HTTP/2bash
# 1. 看 curl 实际协商到的协议版本（输出 2 表示 HTTP/2）
curl -sI --http2 https://www.example.com -o /dev/null -w '%{http_version}\n'

# 2. 看 TLS 握手中 ALPN 协商结果
echo | openssl s_client -alpn h2 -connect www.example.com:443 2>/dev/null \
  | grep -i 'ALPN'
# 期望输出：ALPN protocol: h2

# 3. 详细过程：可看到 "using HTTP/2" 及流 ID
curl -sv --http2 https://www.example.com -o /dev/null 2>&1 | grep -iE 'ALPN|HTTP/2'

# Nginx 启用方式（1.25.1 起推荐写法）：
#   listen 443 ssl;
#   http2 on;
# 更早版本写作：listen 443 ssl http2;

以 ALPN 协商结果为准；浏览器 DevTools 网络面板的 Protocol 列显示 h2。

⚖️ 06 · 方案取舍

启用 HTTP/2

优点少连接、多并发、头部压缩

代价高丢包网络下可能不如多连接

适用绝大多数 HTTPS 站点

再加 HTTP/3

优点消除 TCP 队头阻塞，连接迁移

代价UDP 可能被拦截，运维新

适用移动端、弱网用户多

内部服务 h2c

优点gRPC 等可用，无 TLS 开销

代价流量明文

适用可信内网的服务间调用

🕳️ 07 · 常见坑

  • ✗仍保留域名分片和大量资源合并

    ✓HTTP/2 下改为合理拆分，利用多路复用与缓存

  • ✗以为启用 HTTP/2 后就没有队头阻塞

    ✓TCP 层仍会阻塞，弱网可考虑 HTTP/3

  • ✗只在 CDN 开启，以为全链路都是 h2

    ✓分别确认边缘与回源各段使用的协议

  • ✗继续依赖已废弃的服务器推送

    ✓改用 103 Early Hints 或 preload

🎤 09 · 面试追问
HTTP/2 多路复用解决了什么、没解决什么？

解决了 HTTP/1.1 同一连接只能串行、需开多连接的问题，多个流可交错传输。没解决 TCP 层队头阻塞：任意一个包丢失，TCP 必须按序交付，所有流都要等重传。HTTP/3 通过 QUIC 按流独立交付来解决。

为什么服务器推送被淘汰？

服务端很难知道客户端缓存里已有什么，经常推送重复资源浪费带宽，实际收益有限且实现复杂。Chrome 已移除支持，替代方案是 103 Early Hints 和 preload，让浏览器自己决定是否请求。

HPACK 为什么不直接用 gzip 压缩头部？

对头部用通用压缩曾导致 CRIME 攻击，可通过压缩后长度推测密文中的 Cookie。HPACK 用静态表、动态表索引和哈夫曼编码，设计上降低此类风险，同时适合头部高度重复的场景。
