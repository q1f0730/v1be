输入验证

Input Validation

📐 01 · 定义

输入验证（Input Validation）是在数据进入系统时检查其类型、格式、长度、范围和业务规则，拒绝不合规数据的安全与质量控制手段。它必须在服务端执行，前端校验只用于改善体验。验证是防御注入、越权、数据污染的第一道防线，但需要与参数化查询、输出编码等措施配合，不能单独依赖。

⚙️ 02 · 原理
  1. 1

    确定信任边界：凡来自客户端、第三方、文件、LLM 输出的数据都视为不可信输入。

  2. 2

    语法校验：检查类型、格式、长度、字符集，如邮箱格式、整数范围、枚举取值。

  3. 3

    语义校验：检查业务规则，如结束日期晚于开始日期、资源属于当前用户。

  4. 4

    规范化：校验前统一编码、去除首尾空格、规范化路径，避免绕过检查。

  5. 5

    拒绝并反馈：不合规时返回明确的 4xx 错误，不尝试「修正」可疑输入后继续处理。

🔤 03 · 术语
白名单校验 (Allowlist)
只接受明确允许的格式与取值，优于黑名单过滤。
信任边界 (Trust Boundary)
数据从不可信区域进入可信区域的分界点。
Schema 校验
用 Zod、Pydantic、JSON Schema 声明式描述并校验数据结构。
批量赋值 (Mass Assignment)
直接把请求体全部字段写入模型，导致越权修改。
输出编码 (Output Encoding)
按输出上下文转义数据，防 XSS，与输入验证互补。
💻 04 · 代码
用 Zod 做服务端校验typescript
// npm install zod
import { z } from "zod";

const SignupSchema = z.object({
  email: z.string().trim().toLowerCase().email().max(254),
  name: z.string().trim().min(1).max(50),
  age: z.number().int().min(13).max(120),
  plan: z.enum(["free", "pro"]),          // 白名单取值
}).strict();                              // 拒绝多余字段，防批量赋值

export function handleSignup(body: unknown) {
  const result = SignupSchema.safeParse(body);
  if (!result.success) {
    // 返回 400 与字段级错误，不回显原始可疑输入
    return { status: 400, errors: result.error.flatten().fieldErrors };
  }
  const data = result.data;               // 类型安全、已规范化的数据
  // 后续数据库操作仍需参数化查询
  return { status: 201, data };
}

声明式 Schema 同时得到校验与类型；strict 拒绝未声明字段，防止客户端偷塞 role 等字段。

📊 05 · 参数对比

校验在各层的职责

层做什么能否作为安全防线
前端表单即时提示格式错误不能，可被绕过
API 入口Schema 校验类型、格式、范围能，必须有
业务层权限、归属、状态等业务规则能，必须有
数据库约束、唯一索引、外键最后防线，保证数据完整
⚖️ 06 · 方案取舍

白名单校验

优点安全性高，规则明确

代价需穷举合法格式

适用枚举、ID、格式固定的字段

黑名单过滤

优点实现简单

代价容易被变形绕过

适用仅作补充，不单独依赖

富文本消毒（Sanitize）

优点允许用户提交受限 HTML

代价需维护成熟库与规则

适用评论、编辑器内容

🕳️ 07 · 常见坑

  • ✗只在前端校验，后端直接入库

    ✓服务端对所有入口重新校验

  • ✗把请求体整体传给 ORM 更新

    ✓只挑选允许修改的字段，或用 strict Schema

  • ✗把 LLM 输出当可信数据直接执行或入库

    ✓对模型输出同样做 Schema 与业务校验

  • ✗用正则过滤 SQL 关键字防注入

    ✓使用参数化查询，校验只是辅助

☑️ 08 · 检查清单
🎤 09 · 面试追问
有了输入验证，还需要参数化查询吗？

需要。输入验证检查数据是否符合预期，但很多合法输入本身就包含引号等特殊字符（如人名 O'Brien）；参数化查询从机制上把数据与代码分开，无论内容如何都不会被当作 SQL 执行。两者是纵深防御的不同层。

如何防止批量赋值漏洞？

不要把请求体整体传给数据模型。使用显式字段白名单或拒绝多余字段的严格 Schema；把 role、is_admin、owner_id 等敏感字段只在服务端设置；为创建和更新分别定义输入 DTO。

Agent 场景中输入验证有何新挑战？

模型输出和工具参数也是不可信输入：可能被提示注入操纵、格式漂移或越权。对工具调用参数做 Schema 校验与权限检查，对文件路径、命令、URL 做白名单限制，敏感操作要求人工确认。
