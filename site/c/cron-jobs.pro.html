定时任务 (Cron)

Cron Jobs

📐 01 · 定义

Cron 是类 Unix 系统中按时间表周期执行命令的守护进程，Cron 表达式用分、时、日、月、周五个字段描述触发时间。它属于运维调度层，常用于备份、清理、报表与同步。云平台、Kubernetes CronJob、GitHub Actions schedule 等都沿用这套表达式，但时区与可靠性语义各不相同。

⚙️ 02 · 原理
  1. 1

    每个用户有一份 crontab，cron 守护进程每分钟检查一次，匹配当前时间的条目就派生进程执行。

  2. 2

    五个字段依次为分钟、小时、日、月、星期，支持 *、逗号列表、- 范围与 / 步长。

  3. 3

    日与星期字段同时受限时，标准 cron 按「或」处理，只要其一匹配就执行。

  4. 4

    任务在极简环境中运行：PATH 很短、无交互 shell 配置，输出默认发邮件或被丢弃。

  5. 5

    cron 不处理重叠、补跑与失败重试；这些要靠 flock、幂等脚本或更上层的调度器解决。

🔤 03 · 术语
crontab
存放定时任务条目的表，crontab -e 编辑，crontab -l 查看。
Cron 表达式
五字段时间规则；部分系统扩展出秒或年字段。
flock
Linux 文件锁命令，常用于防止同一任务重叠执行。
systemd timer
systemd 的定时单元，支持日志、依赖与 Persistent 补跑。
Kubernetes CronJob
按 Cron 表达式创建 Job，可设并发策略与时区字段。
💻 04 · 代码
健壮的 crontab 条目bash
# crontab -e 编辑当前用户的任务
# 环境变量：cron 下 PATH 很短，显式设置
PATH=/usr/local/bin:/usr/bin:/bin
MAILTO=""

# 每天 03:00 备份；flock -n 防止上一次没跑完又启动
0 3 * * * cd /srv/app && flock -n /tmp/backup.lock ./backup.sh >> /var/log/backup.log 2>&1

# 每 5 分钟健康检查（curl -f 遇 HTTP 错误返回非零）
*/5 * * * * curl -fsS -m 10 https://example.com/health > /dev/null || logger "health check failed"

# 注意：crontab 中 % 是特殊字符，需写成 \%
0 0 * * * tar czf /backup/db-$(date +\%F).tgz /srv/data

# 时间按服务器时区计算，先用 timedatectl 确认

绝对路径、日志重定向、防重叠锁与时区确认，是 cron 任务最常缺的四件事。

⚖️ 06 · 方案取舍

系统 cron

优点随处可用、零依赖

代价无监控、无补跑、单点

适用单机、低重要性任务

托管/集群调度

优点有日志、重试与并发控制

代价引入平台依赖与配置复杂度

适用生产业务任务

工作流编排器

优点依赖关系、回填、可视化

代价组件重、学习成本高

适用多步骤数据管道

🕳️ 07 · 常见坑

  • ✗脚本手动跑正常，cron 下找不到命令

    ✓使用绝对路径或在 crontab 顶部设置 PATH

  • ✗没有日志，任务失败数周无人发现

    ✓重定向输出，并接入心跳监控（如任务结束时 ping 一个地址）

  • ✗多台实例都配了同一个 cron，任务重复执行

    ✓只在一处调度，或使用分布式锁与幂等设计

  • ✗忽视时区与夏令时导致执行时间漂移

    ✓服务器统一 UTC，必要时用支持时区的调度器

🎤 09 · 面试追问
0 0 1 * 1 会在什么时候执行？

标准 cron 中日与星期都受限时取「或」：每月 1 号零点，以及每个周一零点都会执行，而不是「既是 1 号又是周一」。这是常见误解，需要交集时应在脚本内判断。

如何保证定时任务在多副本服务中只执行一次？

把调度从应用副本中剥离，交给单一调度器（K8s CronJob、云调度服务）；或用分布式锁（如 Redis SET NX 带过期）抢占执行权；任务本身做幂等，重复执行也无副作用。

服务器宕机错过了执行时间怎么办？

标准 cron 不补跑。可用 systemd timer 的 Persistent=true，在启动后补跑错过的一次；K8s CronJob 有 startingDeadlineSeconds 控制错过后多久内仍可启动；关键任务用工作流编排器支持回填。
