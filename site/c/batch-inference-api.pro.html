批量推理接口 (Batch API)

Batch Inference API

🧸 回到小白版

📐 01 · 定义

批量推理接口（Batch API）让调用方把大量独立请求打包成一个任务异步提交，由服务商在完成窗口内（OpenAI 与 Anthropic 文档均为 24 小时内）利用闲置算力处理，价格通常比同步调用低约一半（以官方定价为准），且限额独立于实时接口。适合分类、抽取、翻译、评测等不需要即时结果的离线任务。

⚙️ 02 · 原理
  1. 1

    把每个请求写成一行 JSON（JSONL），包含自定义 ID 与完整请求体，ID 用于结果回填。

  2. 2

    上传文件（OpenAI 需先上传 purpose=batch 的文件；Anthropic 可直接在请求中提交请求数组）并创建批任务。

  3. 3

    服务端排队并分批调度执行，任务状态经历 validating、in_progress、completed 等阶段，可轮询查询。

  4. 4

    完成后下载结果文件，每行含对应的自定义 ID 与响应或错误；结果顺序不保证与输入一致。

  5. 5

    失败或过期的单条请求单独列出，调用方按 ID 重试，而不必重跑整批。

🔤 03 · 术语
JSONL
每行一个 JSON 对象的文本格式，批任务的输入输出格式。
custom_id
每条请求的自定义标识，用于把结果映射回原始数据。
完成窗口 (Completion Window)
服务商承诺处理完成的最长时间，如 24h。
批处理限额 (Batch Quota)
批任务的排队 token 上限，与实时速率限制分开计算。
幂等重试
按 custom_id 只重提失败条目，避免重复计费。
💻 04 · 代码
OpenAI Batch API 提交与取回python
import json
from openai import OpenAI

client = OpenAI()
reviews = ["物流很快", "质量太差了", "一般般"]

with open("in.jsonl", "w", encoding="utf-8") as f:
    for i, text in enumerate(reviews):
        f.write(json.dumps({
            "custom_id": f"r-{i}", "method": "POST",
            "url": "/v1/chat/completions",
            "body": {"model": "gpt-4o-mini",  # 以官方文档为准
                     "messages": [{"role": "user",
                                   "content": f"情感分类(正/负/中)：{text}"}]},
        }, ensure_ascii=False) + "\n")

file = client.files.create(file=open("in.jsonl", "rb"), purpose="batch")
batch = client.batches.create(input_file_id=file.id,
    endpoint="/v1/chat/completions", completion_window="24h")

# 之后轮询：status == "completed" 时下载
b = client.batches.retrieve(batch.id)
if b.status == "completed":
    print(client.files.content(b.output_file_id).text)

构造 JSONL、上传、创建批任务、轮询并下载结果；结果按 custom_id 对齐。

📊 05 · 参数对比

同步调用 vs 批量接口

维度同步调用批量接口
延迟秒级分钟到 24 小时
单价标准价通常约为一半（以官方为准）
速率限制RPM/TPM 限制独立的批处理队列额度
失败处理即时重试按 custom_id 事后补跑
适用交互式产品离线标注、评测、数据处理
⚖️ 06 · 方案取舍

Batch API

优点成本低、不占实时限额

代价结果延迟不可控

适用离线、量大、可等待

同步并发调用

优点结果快、实现直观

代价触发限流，按标准价计费

适用量小或需要当天交付

自建推理批处理

优点极大批量时单价可更低

代价需 GPU 与运维能力

适用长期、超大规模任务

🕳️ 07 · 常见坑

  • ✗custom_id 用行号，数据重排后无法对齐

    ✓使用稳定的业务主键作为 custom_id

  • ✗默认结果按输入顺序返回

    ✓按 custom_id 建立映射，不依赖顺序

  • ✗一个请求格式错导致整批校验失败才发现

    ✓提交前本地校验 JSONL，小批量先试跑

  • ✗忽略单条失败与过期请求

    ✓解析错误文件，只重提失败条目

🎤 09 · 面试追问
Batch API 为什么能更便宜？

服务商可以把批任务安排在负载低谷，用更大的批大小和更灵活的调度提高 GPU 利用率，不必为其预留实时容量。用户用延迟换价格，服务商用灵活性换利用率，双方都受益。

如何设计批任务的容错？

以稳定业务 ID 作为 custom_id；结果入库前做 schema 校验；把 errored、expired 条目收集起来重新组批；整个流程做成幂等的工作流，重复执行不会产生重复写入或重复计费。

什么场景不适合用 Batch API？

需要即时反馈的交互式功能、后一步依赖前一步结果的多轮 Agent 流程，以及有严格时限（如几分钟内必须完成）的任务。这些场景应使用同步接口，配合并发控制和缓存降低成本。
