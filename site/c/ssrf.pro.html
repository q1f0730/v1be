服务端请求伪造

SSRF

📐 01 · 定义

服务端请求伪造（Server-Side Request Forgery, SSRF）是攻击者诱使服务器向其指定的地址发起请求的漏洞，常见于 URL 预览、Webhook 配置、图片抓取等功能。由于请求来自服务器内部，攻击者可借此访问内网服务、云元数据接口获取凭证。它被列入 OWASP Top 10（2021 A10）。

⚙️ 02 · 原理
  1. 1

    应用接收用户提供的 URL，由服务端代为请求，例如抓取网页生成预览。

  2. 2

    攻击者提交指向内部地址的 URL，如 127.0.0.1、10.0.0.0/8 或云元数据地址 169.254.169.254。

  3. 3

    服务器位于内网可信区，请求能到达外部无法访问的管理接口或数据库 HTTP 端口。

  4. 4

    绕过手段包括重定向到内网、DNS 重绑定、十进制或 IPv6 等 IP 表示法。

  5. 5

    响应若被回显给攻击者，就可直接读取内部数据，即使不回显也可用于探测端口。

🔤 03 · 术语
云元数据服务 (IMDS)
169.254.169.254 上提供实例信息与临时凭证的接口。
IMDSv2
AWS 要求先 PUT 获取会话令牌的元数据版本，可缓解 SSRF。
DNS 重绑定 (DNS Rebinding)
校验时解析为公网 IP，请求时解析为内网 IP。
盲 SSRF (Blind SSRF)
看不到响应内容，但可通过时间或副作用探测。
出口过滤 (Egress Filtering)
在网络层限制服务器可访问的目标地址。
💻 04 · 代码
解析后校验并固定 IPpython
import ipaddress, socket
from urllib.parse import urlparse

def resolve_public_ip(url: str) -> tuple[str, str]:
    u = urlparse(url)
    if u.scheme not in ("http", "https") or not u.hostname:
        raise ValueError("只允许 http/https")
    port = u.port or (443 if u.scheme == "https" else 80)
    infos = socket.getaddrinfo(u.hostname, port, proto=socket.IPPROTO_TCP)
    for info in infos:
        ip = ipaddress.ip_address(info[4][0])
        if not ip.is_global:   # 排除私有、回环、链路本地(含 169.254.x.x)、保留等
            raise ValueError(f"禁止访问内部地址 {ip}")
    return u.hostname, infos[0][4][0]

# 用法要点：
# 1. 用返回的 IP 发起连接（并设置 Host 头/SNI），避免 DNS 重绑定
# 2. 禁止自动跟随重定向；如需跟随，每一跳重新校验
# 3. 设置超时与响应大小上限
host, ip = resolve_public_ip("https://example.com/a.png")
print(host, ip)

按解析结果判断而非字符串匹配；连接时使用已校验的 IP，并对重定向逐跳校验。

域名白名单

优点最安全，规则简单

代价灵活性差

适用只需访问少数已知服务

解析后拒绝内网地址

优点支持任意公网 URL

适用URL 预览、通用抓取

隔离的出站代理

优点网络层兜底，集中管控

适用抓取量大或多服务共用

🕳️ 07 · 常见坑

  • ✗用字符串判断是否包含 localhost 或 127.

    ✓解析为 IP 后用 ipaddress 判断地址类别

  • ✗校验了第一个 URL，却让 HTTP 库自动跟随重定向

    ✓关闭自动重定向，或每一跳重新校验

  • ✗云实例仍允许 IMDSv1

    ✓强制使用 IMDSv2 并限制跳数

  • ✗AI Agent 的 fetch 工具可访问任意地址

    ✓Agent 抓取工具同样经过出站代理与内网拦截

🎤 09 · 面试追问
为什么 SSRF 在云环境中危害更大？

云实例可通过链路本地地址访问元数据服务，获取实例角色的临时凭证。攻击者借 SSRF 读取这些凭证后，可直接调用云 API 访问存储、数据库等资源，从一个 Web 漏洞扩大为整个云账号的入侵。

如何防御 DNS 重绑定？

只解析一次域名，对所有解析结果做校验，然后直接用校验通过的 IP 建立连接，并通过 Host 头与 SNI 传递原域名；避免「先校验域名、再让 HTTP 库重新解析」的两段式流程。

只靠应用层校验够吗？

不够，应纵深防御：应用层校验 URL 与 IP，网络层把抓取服务放在隔离子网并限制出口，云上启用 IMDSv2，服务以最小权限运行，这样单点疏漏不会直接导致凭证泄露。
