蓝绿部署

Blue-Green Deployments

📐 01 · 定义

蓝绿部署（Blue-Green Deployment）是同时维护两套完整的生产环境：蓝色运行当前版本，绿色部署新版本并完成验证，然后在路由层把全部流量一次性切到绿色；出问题时再切回蓝色即可回滚。它属于发布策略层，以双倍资源换取近乎瞬时的切换和回滚，难点在于数据库变更和有状态组件的兼容。

⚙️ 02 · 原理
  1. 1

    蓝色环境承载全部生产流量，绿色环境部署新版本，配置与规模和蓝色一致。

  2. 2

    在绿色环境运行冒烟测试与关键路径验证，可通过内部入口或测试流量访问。

  3. 3

    切换路由：修改负载均衡目标组、Kubernetes Service 选择器或 DNS 记录，指向绿色。

  4. 4

    观察指标，异常时把路由切回蓝色完成回滚；稳定后蓝色保留一段时间再回收或作为下次发布的目标。

  5. 5

    数据库通常两套环境共享，需要采用扩展-收缩（Expand-Contract）方式做向后兼容的迁移。

🔤 03 · 术语
扩展-收缩迁移 (Expand-Contract)
先加兼容新旧版本的结构，切换后再删除旧结构的数据库迁移方式。
流量切换 (Cutover)
把生产流量从旧环境转到新环境的动作。
冒烟测试 (Smoke Test)
上线前对关键功能的快速验证。
选择器 (Selector)
Kubernetes Service 用标签选择后端 Pod，改标签即可切换。
DNS TTL
DNS 记录缓存时间，影响基于 DNS 切换的生效速度。
💻 04 · 代码
切换 Service 选择器bash
# 前提：已有 api-blue 和 api-green 两个 Deployment，
# Pod 标签分别为 app=api,version=blue 与 app=api,version=green

# 1. 确认绿色环境全部就绪
kubectl rollout status deployment/api-green

# 2. 一次性把流量切到绿色
kubectl patch service api \
  -p '{"spec":{"selector":{"app":"api","version":"green"}}}'

# 3. 观察错误率与延迟；如有问题，立刻切回蓝色
# kubectl patch service api \
#   -p '{"spec":{"selector":{"app":"api","version":"blue"}}}'

# 4. 稳定后缩容蓝色，保留以便快速回滚
kubectl scale deployment/api-blue --replicas=0

修改 Service 选择器实现原子切换；回滚只是把选择器改回 blue。

🕳️ 07 · 常见坑

  • ✗新版本数据库迁移删除了旧版本依赖的字段，回滚后蓝色报错。

    ✓采用扩展-收缩迁移，确保新旧版本都能读写。

  • ✗绿色环境没预热就切全量流量，冷缓存导致延迟飙升。

    ✓切换前预热缓存与连接池。

  • ✗切换后立即销毁蓝色，出问题无法快速回滚。

    ✓保留蓝色一段观察期再回收。

  • ✗后台任务在蓝绿两边同时运行，重复执行。

    ✓确保定时任务和消费者只在一侧激活。

🎤 09 · 面试追问
蓝绿部署中数据库如何处理？

通常共享一个数据库，所以迁移必须对新旧版本都兼容。采用扩展-收缩：先新增字段或表并双写，切换并稳定后再删除旧结构。这样任何时刻回滚到蓝色都不会因结构变化报错。

蓝绿和金丝雀如何选择？

蓝绿一次切全量，回滚快但新版本一上来就面对全部用户；金丝雀先给小比例流量，按指标逐步放大，影响面更小但耗时更长、需要流量拆分能力。高风险变更倾向金丝雀，也可组合使用。

蓝绿部署切换后长连接怎么办？

修改路由只影响新连接，已有的 keep-alive、WebSocket 连接仍连在蓝色。需要在蓝色实施连接排空、关闭空闲连接或让客户端重连，确保流量真正迁移。
