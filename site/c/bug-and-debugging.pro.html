Bug & Debugging

📐 01 · 定义

Bug 是程序行为与预期不符的缺陷；调试（Debugging）是定位并消除缺陷根因的系统化过程。专业调试遵循科学方法：稳定复现、收集证据、提出假设、设计实验验证、修复并加回归测试。它与 AI 编程密切相关：Agent 修 bug 的成败，很大程度取决于能否复现问题并拿到客观的验证信号。

⚙️ 02 · 原理
  1. 1

    复现：找到能稳定触发问题的输入、环境与步骤，最好缩减为最小复现用例。

  2. 2

    观察：收集报错、堆栈、日志、监控数据，确定故障在什么条件下出现、什么条件下不出现。

  3. 3

    定位：用断点、日志、二分（git bisect）等手段缩小问题出现的代码范围。

  4. 4

    假设与验证：针对根因提出假设，设计实验证伪或证实，而不是盲目改代码。

  5. 5

    修复与防回归：修复根因后补充测试用例，确保同类问题不会再次出现。

🔤 03 · 术语
断点 (Breakpoint)
让程序在指定位置暂停，以检查变量和调用栈。
git bisect
用二分查找定位引入 bug 的那次提交。
回归 (Regression)
原本正常的功能因新改动而出错。
海森堡 Bug (Heisenbug)
一观察（加日志、调试）就消失的 bug，常与并发或时序有关。
根因分析 (Root Cause Analysis)
追查问题的根本原因，而非只处理表面症状。
💻 04 · 代码
用 git bisect 定位回归bash
# 场景：现在的版本有 bug，两周前的 v1.2.0 是好的
git bisect start
git bisect bad                 # 当前提交有问题
git bisect good v1.2.0         # 这个版本没问题

# Git 会自动切到中间的提交，测试后告诉它结果：
#   git bisect good   或   git bisect bad
# 重复几次即可找到第一个出问题的提交

# 更省事：给一个测试命令，退出码 0 表示 good，自动二分
git bisect run npm test -- --run tests/checkout.test.ts

git bisect reset               # 结束，回到原来的分支

# Python 中设置断点：在代码里写 breakpoint() 进入 pdb
# 常用命令：n 下一行  s 进入函数  p 变量  c 继续  q 退出

二分查找让定位回归的次数随提交数对数增长，配合自动化测试几乎无需人工。

📊 05 · 参数对比

调试手段选择

手段适用问题成本
打印/日志流程与数据流向低，但需清理
断点调试器复杂状态、逻辑分支中，需要可本地运行
git bisect「以前好的现在坏了」低，需有可判定的测试
最小复现复杂系统中的疑难问题中高，但最可靠
线上可观测性只在生产出现的问题需提前埋点
⚖️ 06 · 方案取舍

直接让 AI 看报错修复

优点快，常见错误效果好

代价可能只修表面症状

适用报错清晰的简单问题

先写失败测试再修复

优点有客观验证，防回归

代价需要额外时间

适用逻辑 bug、重要功能

系统性根因分析

优点彻底解决问题

代价耗时

适用线上事故、反复出现的问题

🕳️ 07 · 常见坑

  • ✗没复现就开始改代码，靠猜

    ✓先建立稳定复现，修复后用同一方法验证

  • ✗一次改多处，不知道哪处起了作用

    ✓每次只改一个变量，观察结果

  • ✗用 try/except 吞掉异常让报错「消失」

    ✓找到并修复根因，必要时记录日志后再抛出

  • ✗修完不加测试，同一 bug 几个月后再现

    ✓为每个修复的 bug 补一个回归测试

🎤 09 · 面试追问
讲一个你的调试方法论。

复现 → 缩小范围 → 假设 → 验证 → 修复 → 防回归。先构造最小复现，用日志、断点或 bisect 定位范围，针对根因提出可证伪的假设并逐一实验，修复后补测试，最后复盘为何测试没提前发现。

如何调试只在生产环境出现的问题？

依靠可观测性：结构化日志、错误追踪、链路追踪与指标；对比生产与预发的配置、数据与流量差异；在安全前提下增加针对性日志或特性开关；尝试用生产数据快照在隔离环境复现。避免直接在生产上试验性修改。

怎样让 AI Agent 更有效地修 bug？

提供可执行的复现方式（命令或失败测试）、完整报错与相关代码位置；要求它先说明根因假设再修改；以测试通过作为完成标准；限制改动范围；若多次失败，回滚并换新会话重新描述问题。
