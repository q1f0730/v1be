长上下文中段遗忘

Lost in the Middle

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

长上下文中段遗忘（Lost in the Middle）指大模型在长输入中对位于中间位置的信息利用明显变差的现象：相关信息放在开头或结尾时准确率最高，放在中间时显著下降，呈“U 形曲线”。该现象由 2023 年 Liu 等人的论文系统描述。新一代模型已有改善，但长上下文中的信息利用仍不均匀，这直接影响 RAG 拼接与长文档问答的设计。

⚙️ 02 · 原理
  1. 1

    实验把一个包含答案的文档与多个干扰文档拼接，改变答案文档的位置，测量模型回答准确率。

  2. 2

    结果显示首位效应与近因效应：开头和结尾的信息被利用得最好，中间位置的准确率最低。

  3. 3

    增加上下文中的文档数量会整体拉低表现，即使答案文档没有被移除。

  4. 4

    可能原因包括训练数据中关键信息分布偏向首尾、注意力分配随距离与位置变化，以及位置编码外推的局限。

  5. 5

    “大海捞针”类简单检索测试表现好，不代表模型能在长上下文中做多跳推理和信息综合。

🔤 03 · 术语
U 形曲线 (U-shaped Curve)
准确率随信息位置变化，两端高、中间低。
首位/近因效应 (Primacy / Recency)
对开头和结尾信息利用更好的倾向。
大海捞针 (Needle in a Haystack)
在长文本中插入一句事实并测试能否找回的评测。
有效上下文长度 (Effective Context)
模型能可靠利用信息的长度，常小于标称窗口。
上下文重排 (Context Reordering)
把最相关的文档放在首尾、较弱的放中间。
💻 04 · 代码
把最相关文档放到首尾python
def reorder_for_long_context(docs_by_relevance: list[str]) -> list[str]:
    """输入按相关性降序的文档，输出首尾最相关、中间最弱的顺序。
    思路同 LangChain 的 LongContextReorder。"""
    front, back = [], []
    for i, doc in enumerate(docs_by_relevance):
        (front if i % 2 == 0 else back).append(doc)
    return front + back[::-1]

ranked = ["D1 最相关", "D2", "D3", "D4", "D5 最弱"]
print(reorder_for_long_context(ranked))
# ['D1 最相关', 'D3', 'D5 最弱', 'D4', 'D2']

def build_prompt(question: str, docs: list[str]) -> str:
    ctx = "\n\n".join(f"<doc id={i}>{d}</doc>" for i, d in enumerate(docs))
    # 问题和关键要求在资料后再重复一次，利用近因效应
    return f"问题：{question}\n\n{ctx}\n\n请只依据以上资料回答：{question}，并注明 doc id。"

把强相关文档放首尾、问题在末尾重复；更根本的做法仍是减少无关文档。

📊 05 · 参数对比

缓解手段对比

手段做法效果与代价
精简上下文检索 + 重排后只放 Top-K最有效，依赖检索质量
上下文重排最相关的放首尾零成本，改善有限
问题置后/重复资料后再写一遍问题简单有效，略增 token
分而治之分段提取再汇总（map-reduce）更准，调用次数增加
结构化标记用 XML 标签分隔并编号便于引用与定位
⚖️ 06 · 方案取舍

整篇塞入长上下文

优点实现简单，不会漏检索

代价中段信息易被忽略，成本高

适用文档短于有效上下文、需全局理解

检索 + 精简

优点准确、便宜、可引用

代价依赖检索与切块质量

适用大多数知识问答

Map-Reduce 分段处理

优点覆盖完整、每段关注度高

代价调用次数多、延迟高

适用长报告摘要、多文档比较

🕳️ 07 · 常见坑

  • ✗认为窗口越大就能放心塞入全部资料

    ✓以评测为准，优先检索精简，监控长度与准确率关系

  • ✗只用“大海捞针”测试就认定长上下文可靠

    ✓用贴近业务的多跳问答和综合任务做评测

  • ✗把核心指令写在长资料中间

    ✓系统指令放开头，问题与关键约束放在资料之后

  • ✗长对话持续累积不做压缩

    ✓定期总结压缩历史，或开新会话携带摘要

☑️ 08 · 检查清单
🎤 09 · 面试追问
Lost in the Middle 的实验结论是什么？

在多文档问答和键值检索任务中，答案位于输入开头或结尾时模型表现最好，位于中间时显著下降，即使模型的上下文窗口足以容纳全部输入。增加文档数也会降低整体表现，说明“能放下”不等于“能用好”。

这对 RAG 系统设计有什么启示？

不要靠增加检索条数来提高召回后直接拼接，而应召回后重排、只保留最相关的少量片段；把最相关内容放在首尾；在资料之后重复问题；需要综合大量材料时采用分段提取再汇总。

新模型还存在这个问题吗？

不少新模型在大海捞针测试上接近满分，但在需要多跳推理、信息综合或长度接近上限的任务上，性能仍会随上下文增长与位置变化而下降。因此应在自己的任务上实测，而不是依赖标称窗口。
