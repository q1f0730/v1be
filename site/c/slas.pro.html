服务等级协议

SLAs

📐 01 · 定义

服务等级协议（Service Level Agreement, SLA）是服务提供方与客户之间关于可用性、性能等指标的书面承诺，通常附带未达标时的赔偿条款（如服务抵扣）。它建立在内部的 SLI（指标）与 SLO（目标）之上，属于可靠性工程与商务契约的交界层，决定了系统需要投入多少冗余与运维成本。

⚙️ 02 · 原理
  1. 1

    定义 SLI：可量化的服务指标，如成功请求比例、P99 延迟，并明确统计口径。

  2. 2

    设定 SLO：内部目标值，如 30 天内 99.9% 请求成功，通常比 SLA 更严格。

  3. 3

    对外签订 SLA：承诺值、统计周期、排除项（计划维护、客户原因）与赔偿梯度。

  4. 4

    用 SLO 推出错误预算（Error Budget），预算消耗过快时冻结发布、优先修可靠性。

  5. 5

    持续监控并出具报表，违约时按条款计算服务抵扣，通常需客户主动申请。

🔤 03 · 术语
SLI (Service Level Indicator)
衡量服务水平的具体指标，如可用率、延迟。
SLO (Service Level Objective)
团队为 SLI 设定的内部目标值。
错误预算 (Error Budget)
1 减 SLO，即周期内允许的不可靠额度。
服务抵扣 (Service Credit)
未达 SLA 时按比例返还的费用额度。
复合可用性 (Composite Availability)
串联依赖的可用性相乘，整体低于任一组件。
💻 04 · 代码
可用性与错误预算计算python
def downtime_budget(slo: float, days: int = 30) -> float:
    """返回周期内允许的停机分钟数"""
    return (1 - slo) * days * 24 * 60

for slo in (0.99, 0.999, 0.9995, 0.9999):
    print(f"{slo:.2%}  ->  {downtime_budget(slo):7.1f} 分钟/30天")
# 99.00% ->   432.0
# 99.90% ->    43.2
# 99.95% ->    21.6
# 99.99% ->     4.3

# 串联依赖：整体可用性 = 各组件相乘
deps = {"负载均衡": 0.9999, "应用": 0.999, "数据库": 0.9995}
total = 1.0
for a in deps.values():
    total *= a
print(f"整体约 {total:.4%}")  # 约 99.84%，低于任一组件

# 错误预算消耗：30 天内已失败请求占比 / 允许占比
failed, total_req, slo = 12_000, 20_000_000, 0.999
print(f"预算已用 {failed / total_req / (1 - slo):.0%}")  # 60%

每多一个 9，停机预算缩小十倍；串联依赖会拉低整体可用性。

📊 05 · 参数对比

SLI、SLO、SLA 区别

概念面向示例未达成后果
SLI工程团队成功请求比例无，仅是度量
SLO内部30 天 99.9% 成功冻结发布、复盘
SLA客户与法务月可用性 99.9%服务抵扣或违约
⚖️ 06 · 方案取舍

提高 SLA 承诺

优点商务竞争力强

代价冗余、值班、跨区成本陡增

适用企业客户、核心业务

SLA 低于 SLO 留余量

优点内部问题不直接触发赔偿

代价对外承诺显得保守

适用绝大多数服务的推荐做法

不提供 SLA

优点无违约风险

代价难以进入企业采购

适用Beta、免费或早期产品

🕳️ 07 · 常见坑

  • ✗SLA 和 SLO 设成同一个值

    ✓SLO 比 SLA 更严格，留出缓冲

  • ✗用服务器存活时间衡量可用性

    ✓以用户可感知的成功请求比例或合成探测为 SLI

  • ✗承诺 99.99% 却依赖单一可用区的数据库

    ✓按依赖链计算复合可用性，补足冗余后再承诺

  • ✗SLA 未写清统计口径与排除项

    ✓明确周期、计算方式、维护窗口与申请赔偿流程

🎤 09 · 面试追问
为什么不追求 100% 可用？

成本随 9 的个数指数增长，且用户侧网络、终端本身也不是 100% 可靠，超过某点用户无感知。留出错误预算可用于发布新功能与实验，在速度与稳定间取得平衡。

错误预算耗尽后怎么办？

按事先约定的策略执行：暂停非紧急发布、把工程资源转向可靠性修复与复盘，直到预算恢复；关键在于策略由产品和工程提前共同认可，而不是事后争论。

如何为一个 API 选择 SLI？

从用户体验出发：可用性用非 5xx 且未超时的请求占比；延迟用 P95/P99 低于阈值的比例；在负载均衡或网关处统一采集，排除健康检查与客户端错误，口径保持稳定。
