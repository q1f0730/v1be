数据模式演进 (Schema Registry)

Schema Evolution

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

模式演进（Schema Evolution）指数据结构随业务变化而修改时，保证新旧生产者与消费者仍能正确读写的规则与机制。在事件流和数据湖中，数据被长期保存并被多方读取，必须用 Avro、Protobuf、JSON Schema 等带模式的格式，并借助模式注册中心（Schema Registry）在发布前做兼容性校验。

⚙️ 02 · 原理
  1. 1

    生产者序列化时把模式注册到注册中心，消息只携带模式 ID，消费者按 ID 取回写入模式进行反序列化。

  2. 2

    每个主题（subject）配置兼容级别；新版本模式提交时，注册中心将其与上一版或全部历史版本比对。

  3. 3

    向后兼容（BACKWARD）：用新模式的消费者能读旧数据，因此先升级消费者；允许删除字段、新增带默认值的字段。

  4. 4

    向前兼容（FORWARD）：用旧模式的消费者能读新数据，因此先升级生产者；FULL 同时满足两者。

  5. 5

    读取时由写入模式与读取模式做解析：缺失字段用默认值，多余字段被忽略，类型不兼容则拒绝注册。

🔤 03 · 术语
写入/读取模式 (Writer/Reader Schema)
数据写入时使用的模式与消费者期望的模式，Avro 在读取时对两者做解析。
BACKWARD
Confluent Schema Registry 默认兼容级别：新模式能读取上一版本模式写入的数据。
传递兼容 (Transitive)
要求新模式与所有历史版本兼容，而不仅是上一版本。
主题 (Subject)
注册中心中模式版本的命名空间，常按 topic 名加 -key 或 -value 命名。
保留字段号 (reserved)
Protobuf 中声明已删除的字段编号和名称，防止被复用。
💻 04 · 代码
注册前校验模式兼容性bash
SR=http://localhost:8081
CT="Content-Type: application/vnd.schemaregistry.v1+json"

# 1) 为 orders-value 设置兼容级别
curl -s -X PUT -H "$CT" --data '{"compatibility": "BACKWARD"}' \
  $SR/config/orders-value

# 2) 新模式：新增带默认值的 coupon 字段
NEW='{"schema": "{\"type\":\"record\",\"name\":\"Order\",\"fields\":[{\"name\":\"id\",\"type\":\"string\"},{\"name\":\"amount\",\"type\":\"double\"},{\"name\":\"coupon\",\"type\":[\"null\",\"string\"],\"default\":null}]}"}'

# 3) 先测兼容性，返回 {"is_compatible": true} 再注册
curl -s -X POST -H "$CT" --data "$NEW" \
  $SR/compatibility/subjects/orders-value/versions/latest

curl -s -X POST -H "$CT" --data "$NEW" \
  $SR/subjects/orders-value/versions

把第 3 步放进 CI，模式不兼容时构建失败，避免坏模式进入生产。

📊 05 · 参数对比

兼容级别与升级顺序

级别允许的改动先升级谁
BACKWARD删字段、加带默认值字段消费者
FORWARD加字段、删带默认值字段生产者
FULL只能增删带默认值字段任意顺序
*_TRANSITIVE同上，但与全部历史版本比对同对应级别
NONE不校验需人工协调，生产慎用
⚖️ 06 · 方案取舍

Avro + 注册中心

优点读写模式解析成熟，消息体紧凑

代价需要运维注册中心，调试需工具

适用Kafka 事件流、数据管道

Protobuf

优点跨语言代码生成，字段号机制清晰

代价proto3 字段默认值语义需注意

适用gRPC 与事件共用模型

无模式 JSON

优点上手零成本，人可直接读

代价无编译期与发布期校验，易悄悄破坏下游

适用原型或单一消费者

🕳️ 07 · 常见坑

  • ✗Protobuf 删字段后复用原字段号

    ✓删除时用 reserved 保留字段号和名称

  • ✗直接改字段类型（如 int 改 string）

    ✓新增字段并双写，下游迁移完成后废弃旧字段

  • ✗BACKWARD 级别下先升级了生产者

    ✓按兼容级别规定的顺序发布，或改用 FULL

  • ✗只与上一版本比对，长期保存的旧数据读不了

    ✓数据会被回放时使用 *_TRANSITIVE 级别

🎤 09 · 面试追问
BACKWARD 和 FORWARD 兼容分别保护谁？

BACKWARD 保证用新模式的读者能读旧数据，保护的是先升级的消费者以及历史数据回放；FORWARD 保证旧读者能读新数据，保护的是尚未升级的消费者。选择取决于谁先发布：消费者先升级用 BACKWARD，生产者先升级用 FORWARD。

如何安全地重命名一个字段？

重命名对多数格式等同于删除加新增。安全做法：新增新名字段并带默认值，生产者双写；消费者逐步切换到新字段；确认没有读取方后再删除旧字段。Avro 可用 aliases 辅助读取，但仍需评估各语言实现的支持程度。

为什么数据湖也需要模式演进管理？

湖中数据会被多年后的作业重读，表格式要能用当前模式读取旧文件。Iceberg 按列 ID 而非列名跟踪字段，支持安全地加列、删列、重命名和部分类型提升；若绕过表格式直接写文件，模式漂移会让查询出错或静默产生空值。
