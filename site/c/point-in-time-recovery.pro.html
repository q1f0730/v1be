时间点恢复 (PITR)

Point-in-Time Recovery

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

时间点恢复（PITR）是把数据库恢复到过去任意指定时刻状态的能力。它以一个基础备份为起点，再按顺序重放之后连续归档的事务日志（PostgreSQL 的 WAL、MySQL 的 binlog），在目标时间点停止。常用于撤销误删表、错误批量更新等逻辑错误。

⚙️ 02 · 原理
  1. 1

    定期做物理基础备份（如 pg_basebackup），并记录备份开始时的日志位置。

  2. 2

    持续归档事务日志到独立存储，形成从基础备份开始不间断的日志链。

  3. 3

    恢复时先还原基础备份到新实例，再配置日志来源与恢复目标时间。

  4. 4

    数据库按顺序重放日志，到达目标时间或事务点后暂停或结束恢复。

  5. 5

    核对数据无误后提升为可写实例，或导出所需数据回灌到生产库。

🔤 03 · 术语
基础备份 (Base Backup)
某一时刻数据目录的完整物理拷贝。
WAL 归档 (WAL Archiving)
把写满的 WAL 段持续复制到归档存储。
recovery_target_time
PostgreSQL 恢复的目标时间参数。
时间线 (Timeline)
每次 PITR 后产生新时间线，避免与原历史混淆。
binlog
MySQL 二进制日志，用于复制和时间点恢复。
保留期 (Retention Window)
可恢复到的最早时间，取决于备份与日志保留时长。
💻 04 · 代码
PostgreSQL 恢复到误删前bash
# 前提：主库已开启 archive_mode=on，并配置 archive_command 持续归档 WAL
# 场景：14:30 误删表，恢复到 14:29

# 1. 在新目录还原基础备份（不要覆盖仍在运行的生产数据目录）
tar -xzf /backups/base_20261020.tar.gz -C /var/lib/postgresql/pitr

# 2. 配置恢复参数（PostgreSQL 12+ 写在 postgresql.conf 中）
cat >> /var/lib/postgresql/pitr/postgresql.conf <<'EOF'
restore_command = 'cp /mnt/wal_archive/%f %p'
recovery_target_time = '2026-10-20 14:29:00+08'
recovery_target_action = 'pause'
EOF

# 3. 创建 recovery.signal，进入目标恢复模式并启动
touch /var/lib/postgresql/pitr/recovery.signal
pg_ctl -D /var/lib/postgresql/pitr -o "-p 5433" start

# 4. 到达目标后暂停，检查数据是否正确
psql -p 5433 -c "SELECT count(*) FROM orders;"

# 5. 确认无误后结束恢复，实例变为可写
psql -p 5433 -c "SELECT pg_wal_replay_resume();"

在独立实例恢复并先暂停核对；生产中常用 pgBackRest、WAL-G 等工具封装。

📊 05 · 参数对比

PITR 实现方式

平台机制说明
PostgreSQL 自建基础备份 + WAL 归档可用 pgBackRest/WAL-G/Barman
MySQL 自建全量备份 + binlogmysqlbinlog 按时间截止重放
Amazon RDS自动备份 + 事务日志恢复为新实例，保留期最长 35 天
多数托管数据库控制台选择时间点通常恢复到新实例而非原地
⚖️ 06 · 方案取舍

PITR

优点可精确到秒，丢失极少

代价需持续归档，恢复耗时较长

适用误操作与逻辑错误

定时快照/逻辑备份

优点简单，恢复步骤少

代价最多丢一个备份周期的数据

适用RPO 宽松的系统

延迟副本

优点可快速取回误删前数据

代价多一个实例成本

适用频繁需要快速撤销误操作

🕳️ 07 · 常见坑

  • ✗WAL 归档链中断而无人发现

    ✓监控归档失败与延迟，定期验证可恢复

  • ✗在生产实例上原地恢复，覆盖了误删之后的正常写入

    ✓恢复到新实例，只把需要的数据回灌

  • ✗目标时间未写时区，恢复到了错误时刻

    ✓目标时间带明确时区偏移

  • ✗保留期太短，发现问题时已无法回到那个时间

    ✓按问题发现周期设定保留期

🎤 09 · 面试追问
PITR 的原理是什么？

数据库所有修改先写日志。拿到某时刻的物理基础备份后，按顺序重放其后的日志，就能重建之后任意时刻的状态；设定目标时间，到达后停止重放即可。前提是日志链完整连续。

误删一张表，怎样尽量不影响其他数据？

不在生产原地回退。把备份 PITR 到误删前一刻的新实例，导出这张表（或缺失的数据），再导入生产库；这样误删之后其他表的正常写入不受影响。

PITR 和主从复制能互相替代吗？

不能。复制会把误删同步到副本，无法撤销逻辑错误；PITR 能回到过去但恢复耗时较长，不适合快速故障切换。高可用靠复制，防误操作和灾难恢复靠备份加 PITR。
