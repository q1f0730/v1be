负载均衡

Load Balancer

📐 01 · 定义

负载均衡器（Load Balancer）位于客户端与一组后端实例之间，按算法把请求或连接分配到健康的实例上。它提供水平扩展、故障隔离与无停机发布能力。按工作层次分为四层（基于 TCP/UDP 连接）和七层（理解 HTTP，可按路径、头部路由）。

⚙️ 02 · 原理
  1. 1

    客户端连接负载均衡器的地址（VIP 或域名），而不是某台后端。

  2. 2

    均衡器按算法在健康实例中选择后端：轮询、加权、最少连接、哈希等。

  3. 3

    健康检查持续探测后端：主动定时请求探活接口，或被动统计失败自动摘除。

  4. 4

    七层均衡器可终止 TLS、解析 HTTP，按 Host/路径路由，并注入 X-Forwarded-For 等头。

  5. 5

    实例下线时先进入连接排空，等存量请求处理完再移除，实现无损发布。

🔤 03 · 术语
L4 / L7 负载均衡
按传输层连接转发，与按 HTTP 内容转发。
健康检查 (Health Check)
判定后端可用性的探测，失败即停止转发。
会话保持 (Sticky Session)
同一客户端固定转发到同一后端。
连接排空 (Connection Draining)
摘除实例前等待现有请求完成。
一致性哈希 (Consistent Hashing)
增减节点时只迁移少量键的哈希分配方式。
最少连接 (Least Connections)
把新请求发给当前活跃连接最少的后端。
💻 04 · 代码
Nginx 七层负载均衡text
# /etc/nginx/conf.d/api.conf
upstream api_backend {
    least_conn;                               # 最少连接算法
    server 10.0.1.11:8080 weight=2 max_fails=3 fail_timeout=10s;
    server 10.0.1.12:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.13:8080 backup;             # 其他都不可用时才启用
    keepalive 32;                             # 与后端保持的空闲长连接数
}

server {
    listen 80;
    location / {
        proxy_pass http://api_backend;
        proxy_http_version 1.1;               # 后端长连接需要 HTTP/1.1
        proxy_set_header Connection "";
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        # 连接失败、超时或 502/503 时换下一台重试（注意非幂等请求）
        proxy_next_upstream error timeout http_502 http_503;
    }
}
# 开源版只有被动健康检查（max_fails）；主动 health_check 属于 NGINX Plus

max_fails 实现被动摘除；keepalive 复用与后端的连接，降低握手开销。

📊 05 · 参数对比

常见分配算法

算法原理适用场景
轮询/加权轮询依次分配，按权重比例实例同构、请求耗时相近
最少连接选活跃连接最少者请求耗时差异大、长连接
IP/键哈希按客户端或键哈希固定后端需要会话保持或本地缓存
随机二选一随机挑两台取较空闲者大规模集群，实现简单
⚖️ 06 · 方案取舍

四层（如 NLB）

优点性能高、延迟低，协议无关

代价无法按 URL/头部路由

适用TCP/UDP、gRPC 直通、超高吞吐

七层（如 ALB、Nginx）

优点内容路由、TLS 终止、重写

代价开销更大，需解析协议

适用HTTP 服务与微服务网关

客户端负载均衡

优点少一跳，服务间调用延迟低

代价每种语言都要实现与维护

适用服务网格或 gRPC 内部调用

🕳️ 07 · 常见坑

  • ✗健康检查只探活端口，应用已不可用仍接流量

    ✓探测能反映依赖状态的就绪接口

  • ✗依赖粘性会话保存用户状态，实例下线即丢会话

    ✓会话外置到 Redis 或改用无状态 token

  • ✗对 POST 等非幂等请求自动重试导致重复下单

    ✓仅对幂等请求重试，或使用幂等键

  • ✗后端看到的客户端 IP 全是均衡器地址

    ✓读取 X-Forwarded-For 并只信任已知代理

🎤 09 · 面试追问
四层和七层负载均衡如何选？

需要按路径、Host、头部路由，做 TLS 终止、重写或 WAF，选七层；追求极致吞吐、低延迟或非 HTTP 协议（数据库、游戏 UDP），选四层。很多架构是四层在前保证扩展，七层在后做路由。

为什么最少连接比轮询更适合长连接？

轮询只保证请求数平均，不考虑每个请求持续多久。WebSocket、gRPC 流等长连接会在某些实例上堆积，轮询仍持续往上分配；最少连接按当前活跃连接选择，更接近真实负载。

如何做到发布时零错误？

实例先从均衡器摘除（或就绪检查失败），进入连接排空；应用收到终止信号后停止接新请求、处理完存量再退出；新实例就绪检查通过后才接流量；配合滚动或蓝绿发布。
