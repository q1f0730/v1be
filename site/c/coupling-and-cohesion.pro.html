耦合与内聚

Coupling & Cohesion

🧸 回到小白版

📐 01 · 定义

耦合（Coupling）衡量模块之间相互依赖的程度，内聚（Cohesion）衡量一个模块内部元素服务于同一目的的程度。这对概念源自 20 世纪 70 年代的结构化设计，是评价模块划分质量的核心标准：追求低耦合、高内聚，使变更局部化、模块可独立理解、测试与替换。

⚙️ 02 · 原理
  1. 1

    耦合有强弱之分：从共享全局状态、依赖内部实现，到仅通过稳定接口与数据传递，依赖越隐式越强。

  2. 2

    内聚也有高低：按功能单一目的组织最高，按时间、偶然拼凑组织最低。

  3. 3

    变更影响面是直观度量：改一个需求需要触及的模块越多，说明耦合越高或内聚越低。

  4. 4

    可用传入/传出依赖数量等指标量化包的耦合与稳定性，辅助发现「被所有人依赖又频繁变化」的热点。

  5. 5

    降低耦合的常用手段：依赖接口而非实现、依赖注入、事件解耦、明确的模块边界与公开 API。

🔤 03 · 术语
传入耦合 (Afferent Coupling, Ca)
依赖该模块的外部模块数量。
传出耦合 (Efferent Coupling, Ce)
该模块依赖的外部模块数量。
不稳定度 (Instability)
I = Ce/(Ca+Ce)，越接近 1 越容易受外部变化影响。
共生性 (Connascence)
描述两段代码需一起修改的耦合类型与强度的框架。
单一职责原则 (SRP)
一个模块只应有一个引起它变化的原因，与高内聚相通。
💻 04 · 代码
从紧耦合到依赖接口python
from typing import Protocol

# 紧耦合：订单服务直接 new 具体的邮件实现，还读全局配置
class SmtpMailer:
    def send(self, to: str, body: str) -> None: ...

class OrderServiceBad:
    def place(self, user_email: str) -> None:
        SmtpMailer().send(user_email, "下单成功")  # 换短信/测试都得改这里

# 低耦合：依赖抽象接口，由外部注入实现
class Notifier(Protocol):
    def send(self, to: str, body: str) -> None: ...

class OrderService:
    def __init__(self, notifier: Notifier):
        self.notifier = notifier
    def place(self, user_email: str) -> None:
        # 高内聚：只做下单相关的事
        self.notifier.send(user_email, "下单成功")

class FakeNotifier:            # 测试替身
    def __init__(self): self.sent = []
    def send(self, to, body): self.sent.append((to, body))

svc = OrderService(FakeNotifier())
svc.place("a@example.com")

依赖接口 + 注入实现后，换通知渠道或写单元测试都无需改动 OrderService。

📊 05 · 参数对比

耦合类型由强到弱

类型表现改进方向
内容耦合直接改另一模块的内部数据通过公开方法访问
公共耦合共享全局变量显式传参或封装状态
控制耦合传标志位控制对方逻辑分支拆分为多个专门方法
数据耦合只传递必要的数据理想状态之一
⚖️ 06 · 方案取舍

抽象接口解耦

优点可替换、易测试

代价间接层增多，阅读跳转多

适用实现可能变化或需测试替身

直接调用具体实现

优点简单直白

代价变更与测试成本高

适用稳定且只有一种实现

事件/消息解耦

优点发布方不知道订阅方，扩展容易

代价调用链不直观，调试与一致性更难

适用跨模块副作用多

🕳️ 07 · 常见坑

  • ✗为解耦给每个类都加接口

    ✓只在有多种实现、需测试替身或边界处抽象

  • ✗utils/common 模块无限膨胀

    ✓按领域拆分，杜绝「什么都放」的低内聚模块

  • ✗表面拆成多个微服务，却共享同一数据库表

    ✓按数据所有权划分边界，通过 API 或事件交互

  • ✗让 AI 跨十几个文件做小改动而不审视结构

    ✓把改动面过大视为耦合信号，先重构边界

🎤 09 · 面试追问
如何在代码评审中识别高耦合？

看一个需求是否改动大量文件；是否有循环依赖、共享全局状态；是否访问其他模块的内部字段；是否频繁传布尔标志控制对方行为；测试是否必须启动大量真实依赖。

微服务一定比单体耦合低吗？

不一定。服务若同步链式调用、共享数据库或必须同时发布，就是「分布式单体」，耦合不降反增还多了网络故障。耦合取决于边界划分，而非部署单元数量；模块化单体同样能做到低耦合。

高内聚和单一职责原则是什么关系？

二者相通：单一职责强调一个模块只有一个变化原因，高内聚强调模块内元素服务于同一目的。职责混杂的模块会因多个原因频繁变化，也意味着内聚低。
