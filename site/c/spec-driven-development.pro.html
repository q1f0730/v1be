规格驱动开发

Spec-Driven Development

🧸 回到小白版

📐 01 · 定义

规格驱动开发（Spec-Driven Development）是 AI 编码时代流行的工作方式：先把需求、验收标准、技术设计和任务拆分写成结构化文档（spec），经人审阅后再交给 Agent 按任务逐步实现与验证。spec 成为人与 AI 之间的契约和长期上下文，减少「凭感觉写码」的返工。

⚙️ 02 · 原理
  1. 1

    写需求：用用户故事与可验证的验收标准描述要做什么，不涉及实现细节。

  2. 2

    写设计：明确架构、数据模型、接口、依赖与约束，记录关键取舍。

  3. 3

    拆任务：把设计拆成小而可独立验证的任务清单，并标明任务间的依赖顺序。

  4. 4

    逐项实现：Agent 每次只做一项任务，按验收标准补测试并运行通过。

  5. 5

    回写同步：需求或设计变更时先改 spec，再改代码，保持文档与实现一致。

🔤 03 · 术语
验收标准 (Acceptance Criteria)
可客观判定需求是否完成的条件，最好能转成测试。
EARS 语法
用 WHEN/IF…THE SYSTEM SHALL… 模板书写无歧义需求的方法。
Spec Kit
GitHub 开源的规格驱动开发工具包，提供规格、计划、任务等流程命令。
凭感觉编程 (Vibe Coding)
不写规格、靠对话即兴让 AI 写代码的方式。
活文档 (Living Documentation)
随代码持续更新、始终反映现状的文档。
💻 04 · 代码
一份精简 spec 示例text
# Feature: 导出订单为 CSV

## 需求（EARS 写法）
- WHEN 用户在订单页点击「导出」 THE SYSTEM SHALL 下载当前筛选结果的 CSV
- IF 结果超过 10000 行 THE SYSTEM SHALL 改为异步生成并邮件通知
- THE SYSTEM SHALL 对金额列保留两位小数

## 设计
- 接口：GET /api/orders/export?status=&from=&to=
- 复用 OrderQuery 的筛选逻辑；流式写出，避免整表进内存

## 任务
- [ ] 1. 抽取 OrderQuery 筛选为公共函数（含单测）
- [ ] 2. 实现 export 接口，流式输出 CSV（含单测）
- [ ] 3. 超过阈值走异步任务 + 邮件（含集成测试）
- [ ] 4. 前端导出按钮与加载状态

需求可测、设计有约束、任务可单独验证，Agent 可按条目逐个完成。

📊 05 · 参数对比

spec 三层文档

文档回答什么谁主导
需求做什么、怎样算完成产品/人
设计怎么做、为什么这么做工程师与 AI 共同
任务按什么顺序做、每步怎么验证AI 起草、人审阅
⚖️ 06 · 方案取舍

完整 spec 流程

优点返工少，可审阅，团队可协作

代价前期投入大，小改动显得繁琐

适用新功能、多人协作、跨多文件

轻量计划后编码

优点兼顾速度与方向感

代价边界情况易遗漏

适用中等规模改动

直接对话编码

优点最快，适合探索

代价难以复现决策，易偏离

适用原型、一次性脚本

🕳️ 07 · 常见坑

  • ✗spec 写成泛泛的愿景，没有可验证标准

    ✓每条需求附可测试的验收标准，能转成测试用例

  • ✗实现中改了方案，spec 不更新，后续 Agent 被误导

    ✓变更先改 spec 再改代码，把 spec 纳入代码审查

  • ✗让 AI 写完 spec 不审就开工

    ✓人重点审需求边界和设计取舍，确认后再进入实现

☑️ 08 · 检查清单
🎤 09 · 面试追问
规格驱动开发和传统瀑布有什么不同？

它不是一次写完全部文档再长期开发，而是以功能为单位、小步循环；spec 由 AI 辅助快速起草和更新，且直接作为 Agent 的执行上下文和验收依据，迭代周期以小时或天计。

spec 写到多细合适？

细到 Agent 不需要猜关键决策即可：需求边界、错误处理、数据结构、接口约定要明确；具体代码实现留给 Agent。判断标准是两个不同 Agent 按 spec 做出的结果在行为上一致。

怎么防止 spec 与代码脱节？

spec 与代码放同一仓库并在 PR 中一起审查；任务清单与提交对应；验收标准尽量落成自动化测试，让测试成为可执行的规格，文档过时会在测试中暴露。
