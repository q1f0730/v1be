派生仓库 (Fork)

Fork

📐 01 · 定义

Fork（派生）是代码托管平台（GitHub、GitLab 等）提供的服务端仓库复制功能：在你的账号下创建一个与上游仓库共享历史的独立副本。它属于协作流程层，是开源贡献的标准模型——贡献者无需上游写权限，在自己的 Fork 中开发，再通过 Pull Request 提议合并。

⚙️ 02 · 原理
  1. 1

    在平台上点击 Fork，服务端创建一个属于你的新仓库，包含上游的提交历史与分支（可选仅默认分支）。

  2. 2

    把 Fork 克隆到本地，origin 指向你的 Fork，再添加 upstream 远程指向原仓库。

  3. 3

    在功能分支上开发并推送到 origin，然后从 Fork 的分支向上游发起 Pull Request。

  4. 4

    上游持续前进，需定期 fetch upstream 并合并或变基到本地，保持 Fork 同步、减少冲突。

  5. 5

    PR 合并后可删除功能分支；Fork 的权限、Actions 与密钥设置与上游相互独立。

🔤 03 · 术语
上游 (Upstream)
被 Fork 的原仓库，约定用名为 upstream 的远程指向它。
origin
克隆时默认的远程名，在 Fork 工作流中指向你自己的副本。
跨仓库 PR (Cross-repo PR)
从 Fork 的分支向上游分支发起的拉取请求。
同步 Fork (Sync fork)
把上游新提交合入你的 Fork，GitHub 网页与 gh CLI 都支持。
维护者可编辑 (Allow edits by maintainers)
允许上游维护者直接向你的 PR 分支推送修改。
💻 04 · 代码
标准 Fork 贡献流程bash
# 用 GitHub CLI 一步完成 Fork + 克隆 + 配置 upstream
gh repo fork owner/project --clone
cd project
git remote -v            # origin=你的 Fork，upstream=原仓库

# 每次开工前先同步上游
git fetch upstream
git switch main
git merge --ff-only upstream/main
git push origin main

# 在功能分支上开发
git switch -c fix-typo
git commit -am "docs: fix typo in README"
git push -u origin fix-typo

# 向上游发起 PR
gh pr create --repo owner/project --fill

不在 Fork 的 main 上直接开发；main 只用于跟随上游，改动都放功能分支。

📊 05 · 参数对比

协作模型对比

模型是否需写权限适合
Fork + PR否开源项目、外部贡献者
共享仓库 + 分支是公司内部团队
长期硬分叉否项目方向分歧、独立维护
⚖️ 06 · 方案取舍

Fork 工作流

优点上游无需授权，安全隔离

代价需维护同步，CI 密钥对 Fork PR 受限

适用开源与外部协作

同仓库分支工作流

优点流程简单，CI 与权限统一

代价需给成员写权限

适用信任边界内的团队

硬分叉独立发展

优点完全自主决定方向

代价难以合入上游修复

适用上游停止维护或方向不合

🕳️ 07 · 常见坑

  • ✗长期不同步，PR 时冲突巨大

    ✓开工前 fetch upstream，PR 前变基到最新上游

  • ✗在 Fork 的 main 分支上直接提交

    ✓main 只跟随上游，每个改动独立功能分支

  • ✗为 Fork PR 的 CI 随意开放仓库密钥

    ✓谨慎使用 pull_request_target，不在其中检出并运行不可信代码

  • ✗Fork 后忽略原项目许可证义务

    ✓保留版权声明与许可证，按条款处理再分发

🎤 09 · 面试追问
Fork 和 Clone 的本质区别？

Clone 是 Git 操作，把仓库复制到本地；Fork 是托管平台功能，在服务端为你创建一个保留上游关联的仓库副本，使你无写权限也能推送并发起跨仓库 PR。典型流程是先 Fork 再 Clone 自己的 Fork。

为什么 Fork 发来的 PR 默认拿不到仓库密钥？

PR 代码不可信，若 CI 运行时能读取密钥，攻击者可在 PR 中改脚本窃取。GitHub 对来自 Fork 的 pull_request 事件默认不提供密钥且令牌只读；pull_request_target 有密钥但运行在基础分支上下文，误用会造成严重漏洞。

同步 Fork 用 merge 还是 rebase？

Fork 的 main 应与上游保持一致，用 fast-forward 合并即可；个人功能分支在提 PR 前可 rebase 到最新上游得到线性历史，但已被他人基于其工作的分支不宜改写历史。
