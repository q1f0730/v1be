Terraform State

📐 01 · 定义

Terraform 状态文件（state）记录了配置中的每个资源地址与云上真实资源 ID 及其属性之间的映射。Terraform 依靠它计算计划（plan）中的增删改、追踪依赖和提升性能。状态必须妥善存放、加锁与保护：它可能包含明文敏感信息，损坏或并发写入会导致资源被误建或误删。

⚙️ 02 · 原理
  1. 1

    记录映射：apply 后把资源地址（如 aws_s3_bucket.logs）与真实 ID、属性写入状态。

  2. 2

    计算差异：plan 时对比配置、状态与刷新得到的真实资源，生成需要执行的变更。

  3. 3

    远程存储：团队使用 S3、Terraform Cloud 等远程后端共享状态，而非放在本地。

  4. 4

    加锁：执行时获取状态锁，防止多人或多条流水线同时修改同一份状态。

  5. 5

    重构：通过 moved 块、import 块或 state 子命令调整映射而不重建资源。

🔤 03 · 术语
后端 (Backend)
决定状态存放位置与加锁方式的配置，如 s3、gcs。
状态锁 (State Locking)
防止并发操作同时写同一状态的互斥机制。
漂移 (Drift)
真实资源被手动修改，与状态和配置不一致。
moved 块
在配置中声明资源地址变更，避免重命名时销毁重建。
import 块
把已存在的云资源纳入 Terraform 管理并写入状态。
💻 04 · 代码
常用状态操作bash
# 初始化远程后端（S3 后端的锁参数见官方文档，较新版本支持 use_lockfile）
terraform init -backend-config="bucket=my-tf-state" \
               -backend-config="key=prod/network.tfstate"

terraform state list                         # 列出状态中所有资源地址
terraform state show aws_s3_bucket.logs      # 查看某资源记录的属性

# 只检测漂移：刷新状态与真实资源的差异，不改基础设施
terraform plan -refresh-only

# 重命名资源地址而不重建（也可在配置中写 moved 块）
terraform state mv aws_s3_bucket.logs aws_s3_bucket.access_logs

# 放弃管理但保留真实资源
terraform state rm aws_instance.legacy

# 进程异常退出后锁未释放时，确认无人操作再强制解锁
terraform force-unlock <LOCK_ID>

state 子命令直接改映射，执行前应备份并确认；可审查的 moved/import 块更推荐。

🕳️ 07 · 常见坑

  • ✗把 tfstate 提交到 Git 仓库

    ✓使用远程后端，并把 *.tfstate 加入 .gitignore

  • ✗状态桶未加密、权限过宽，泄露其中的密码和密钥

    ✓启用加密与版本控制，严格限制读取权限

  • ✗重命名资源后直接 apply，资源被销毁重建

    ✓使用 moved 块或 state mv，先看 plan 确认无销毁

  • ✗手工在控制台改资源，导致长期漂移

    ✓定期执行 refresh-only 检测漂移，变更一律走代码

🎤 09 · 面试追问
Terraform 为什么需要状态文件？

云 API 无法可靠地根据配置反查对应哪个真实资源，状态保存了地址到真实 ID 的映射；它还记录依赖关系以便正确删除顺序，并缓存属性提升大规模基础设施的 plan 性能。

两个人同时 apply 会怎样？

若后端支持并启用了锁，后到者会因拿不到锁而失败；若没有锁，双方可能基于同一旧状态计算并写回，后写覆盖先写，造成状态与真实资源不一致，甚至重复创建资源。

状态文件中的敏感信息怎么保护？

状态会以明文保存资源属性，可能含数据库密码等。应使用加密的远程后端、开启版本控制、严格限制访问权限；尽量让密钥由密钥管理服务生成和引用。OpenTofu 还提供状态加密功能。
