可观测性三支柱 (指标 / 日志 / 链路)

Observability

📐 01 · 定义

可观测性（Observability）指仅凭系统对外输出的遥测数据，就能推断其内部状态、回答事先没预料到的问题的能力。业界常用三类信号：指标（Metrics）、日志（Logs）和链路追踪（Traces），并通过 trace ID 等上下文相互关联。OpenTelemetry 是采集与传输这三类信号的开放标准。

⚙️ 02 · 原理
  1. 1

    应用通过 SDK 或自动插桩产生遥测：计数器、直方图等指标，结构化日志，以及描述每个操作耗时的 span。

  2. 2

    链路上下文（trace ID、span ID）通过 HTTP 头（W3C traceparent）在服务间传播，把分散的 span 串成一条 trace。

  3. 3

    日志中写入当前 trace ID，使得从指标告警跳转到相关 trace，再定位到具体日志行成为可能。

  4. 4

    遥测经 Collector 等代理处理（采样、脱敏、批量），发送到 Prometheus、Loki、Jaeger 或商业平台存储。

  5. 5

    基于指标设置 SLO 告警，基于 trace 与日志做根因分析，形成“发现—定位—修复”闭环。

🔤 03 · 术语
Span
链路中的单个操作单元，含名称、起止时间、属性和父子关系。
上下文传播 (Context Propagation)
在进程与服务间传递 trace 信息，常用 W3C Trace Context。
采样 (Sampling)
只保留部分 trace 以控制成本，分头部采样和尾部采样。
基数 (Cardinality)
指标标签取值组合数，过高会导致存储和查询成本爆炸。
OTLP
OpenTelemetry 协议，用于传输指标、日志和 trace。
Collector
OpenTelemetry 的独立代理，负责接收、处理和导出遥测数据。
💻 04 · 代码
OpenTelemetry 手动埋点python
import logging
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor, ConsoleSpanExporter

# 生产环境把 ConsoleSpanExporter 换成 OTLP 导出器
provider = TracerProvider()
provider.add_span_processor(BatchSpanProcessor(ConsoleSpanExporter()))
trace.set_tracer_provider(provider)
tracer = trace.get_tracer("checkout-service")
logging.basicConfig(level=logging.INFO)

def checkout(order_id: str):
    with tracer.start_as_current_span("checkout") as span:
        span.set_attribute("order.id", order_id)
        trace_id = format(span.get_span_context().trace_id, "032x")
        logging.info("checkout start trace_id=%s", trace_id)  # 日志关联 trace
        with tracer.start_as_current_span("charge_card"):
            pass  # 调用支付服务
        with tracer.start_as_current_span("write_db"):
            pass  # 写订单

checkout("o-123")

父 span 下嵌套子 span 记录每一步耗时，并把 trace ID 写进日志，实现信号关联。

📊 05 · 参数对比

三类信号对比

信号数据形态擅长回答成本特点
指标聚合数值时序是否异常、趋势如何低，但受标签基数影响
日志离散事件文本/JSON具体发生了什么随流量线性增长
链路追踪带因果关系的 span 树慢在哪、错在哪个服务高，通常需要采样
⚖️ 06 · 方案取舍

全量 trace

优点不漏任何异常请求

代价存储成本高

适用流量小或关键交易链路

头部采样（固定比例）

优点实现简单、成本可控

代价可能漏掉罕见错误

适用大流量常规服务

尾部采样（Collector 端）

优点优先保留错误与慢请求

代价需缓冲完整 trace，资源消耗高

适用需要精准排障的生产系统

🕳️ 07 · 常见坑

  • ✗指标标签使用用户 ID、URL 全路径

    ✓只用低基数标签，高基数信息放日志或 trace 属性

  • ✗日志无结构、不带 trace ID

    ✓使用结构化日志并自动注入 trace 上下文

  • ✗各服务传播头不一致，trace 断裂

    ✓统一采用 W3C Trace Context，网关与消息队列也传播

  • ✗遥测中包含密码、Token 等敏感数据

    ✓在 SDK 或 Collector 层做脱敏与字段过滤

☑️ 08 · 检查清单
🎤 09 · 面试追问
监控和可观测性有什么区别？

监控针对已知问题，预先定义指标和阈值来判断“是否出问题”；可观测性强调能通过丰富、可关联的遥测数据回答事先没想到的问题，即“为什么出问题”。监控是可观测性的子集。

为什么指标标签基数需要控制？

时序数据库为每个标签组合存一条时间序列。若把用户 ID 等高基数字段作为标签，序列数会呈乘积增长，导致内存、存储和查询成本暴涨甚至服务崩溃。高基数维度应放在日志或 trace 中。

如何在 Agent 或 LLM 应用中做可观测性？

为每次模型调用、工具调用和检索步骤创建 span，记录模型名、token 用量、延迟和错误；用 trace 串起一次完整 Agent 运行。注意对提示和输出中的个人信息做脱敏，并控制大文本存储成本。
