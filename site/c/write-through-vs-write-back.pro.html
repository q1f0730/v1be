直写与异步回写

Write-Through vs Write-Back

📐 01 · 定义

直写（Write-Through）与回写（Write-Back，也称 Write-Behind）是缓存的两种写策略。直写在写缓存的同时同步写入后端存储，完成后才返回；回写只写缓存并标记为脏数据，稍后异步批量写回。前者一致性好但写延迟高，后者写入快、能合并写，但缓存故障时可能丢数据。

⚙️ 02 · 原理
  1. 1

    直写：写请求同时更新缓存与持久存储，两者都成功才返回，缓存与存储保持一致。

  2. 2

    回写：写请求只更新缓存并记录脏标记，不等待持久存储，立即返回。

  3. 3

    回写的后台任务按时间或数量阈值，把脏数据批量刷入存储；同一键多次写只刷最后一次。

  4. 4

    回写在刷盘前若缓存节点崩溃，未持久化的写入会丢失，需要复制或日志保护。

  5. 5

    另有绕写（Write-Around）：写只进存储不进缓存，避免一次性数据污染缓存。

🔤 03 · 术语
脏数据 (Dirty Data)
已在缓存修改、尚未写回存储的数据。
写合并 (Write Coalescing)
同一键多次写入只持久化最后一次。
绕写 (Write-Around)
写操作绕过缓存，只写存储。
刷新 (Flush)
把脏数据写回持久存储的动作。
掉电保护 (Battery-backed Cache)
存储控制器用电池或电容保护回写缓存。
💻 04 · 代码
两种写策略的最小实现python
import threading

class WriteThrough:
    def __init__(self, cache: dict, db: dict):
        self.cache, self.db = cache, db
    def put(self, k, v):
        self.db[k] = v          # 先写持久层，失败则抛错、不更新缓存
        self.cache[k] = v       # 两者都成功才返回

class WriteBack:
    def __init__(self, cache: dict, db: dict):
        self.cache, self.db = cache, db
        self.dirty, self.lock = {}, threading.Lock()
    def put(self, k, v):
        self.cache[k] = v       # 只写缓存，立即返回
        with self.lock:
            self.dirty[k] = v   # 同一键多次写会被合并
    def flush(self):            # 由定时器或阈值触发
        with self.lock:
            batch, self.dirty = self.dirty, {}
        self.db.update(batch)   # 批量落库；flush 前进程崩溃，这批数据就丢了

wb = WriteBack({}, {})
for i in range(1000):
    wb.put("view:42", i)        # 1000 次写
wb.flush()
print(wb.db)                    # {'view:42': 999}，只落库 1 次

回写把 1000 次写合并为 1 次落库，代价是 flush 前崩溃会丢数据。

📊 05 · 参数对比

写策略对比

策略写延迟数据丢失风险适用
直写高（含存储写）低订单、账户等关键数据
回写低（仅缓存）有（未刷盘部分）计数、浏览量、指标
绕写存储写延迟低写多读少、一次性数据
⚖️ 06 · 方案取舍

直写

优点缓存与存储一致，故障不丢写

代价写延迟叠加，写放大

适用写入必须可靠且立即可读

回写

优点写快、合并写、削峰

代价可能丢数据，一致性弱

适用可容忍少量丢失的高频写

绕写 + 读时填充

优点避免缓存被写污染

代价刚写入的数据首读未命中

适用写后很少立即读取

🕳️ 07 · 常见坑

  • ✗用回写缓存存支付状态等关键数据

    ✓关键数据直写持久层，回写只用于可丢数据

  • ✗直写时先写缓存再写库，库失败后缓存是脏的

    ✓先写持久层，成功后再更新缓存或删除缓存

  • ✗回写队列无上限，存储故障时内存被撑爆

    ✓设置脏数据上限与背压，超限时降级为直写

  • ✗忽略操作系统页缓存也是回写

    ✓需要持久性时显式 fsync 或使用数据库事务

🎤 09 · 面试追问
回写缓存如何降低数据丢失风险？

缩短刷新间隔、限制脏数据量；缓存节点做主从复制；先写追加日志（类似 WAL）再更新内存；硬件层面用电池或电容保护的控制器缓存。本质是在写性能与可丢失窗口之间选择。

浏览量计数适合哪种策略？

适合回写：写入极高频且同一键反复更新，合并后批量落库能大幅降低数据库写压力；偶尔丢失几秒计数业务上可接受。可用 Redis INCR 累加，定时把增量批量写回数据库。

数据库本身用的是哪种策略？

多数数据库的缓冲池对数据页是回写：修改先在内存中，后台刷脏页。持久性靠预写日志保证：提交时日志先落盘，崩溃后重放日志恢复。这样兼得回写的性能与直写般的可靠性。
