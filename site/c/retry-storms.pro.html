重试风暴

Retry Storms

📐 01 · 定义

重试风暴（Retry Storm）是指下游出现故障或变慢时，各层客户端同时、反复重试，使请求量成倍放大，把原本可恢复的局部问题变成持续过载的现象。它属于分布式系统的过载与级联故障范畴，多层调用链中每层都重试 N 次时，最底层可能承受 N 的层数次方倍流量。

⚙️ 02 · 原理
  1. 1

    下游因发布变更、容量不足或自身依赖问题，出现部分请求失败或延迟明显升高。

  2. 2

    上游客户端超时后重试，请求量增加，下游负载进一步升高、失败率上升。

  3. 3

    多层链路中每层独立重试，放大效应相乘，例如三层各重试 3 次最多 27 倍。

  4. 4

    即使原始故障消除，积压的重试流量仍让服务无法恢复，形成亚稳态故障。

  5. 5

    防护依赖重试预算、只在单层重试、退避抖动、熔断和服务端卸载共同作用。

🔤 03 · 术语
重试放大 (Retry Amplification)
多层重试叠加使底层请求量成倍增长。
重试预算 (Retry Budget)
限制重试请求占总请求的比例，例如不超过 10%。
亚稳态故障 (Metastable Failure)
触发因素消失后，系统仍被自身反馈环困在故障态。
熔断器 (Circuit Breaker)
失败率超阈值时暂停调用下游，一段时间后试探恢复。
重试节流 (Retry Throttling)
gRPC 中基于令牌桶，失败多时自动停止重试的机制。
💻 04 · 代码
gRPC 重试与节流配置json
{
  "methodConfig": [{
    "name": [{ "service": "orders.OrderService" }],
    "retryPolicy": {
      "maxAttempts": 3,
      "initialBackoff": "0.2s",
      "maxBackoff": "2s",
      "backoffMultiplier": 2,
      "retryableStatusCodes": ["UNAVAILABLE"]
    }
  }],
  "retryThrottling": {
    "maxTokens": 10,
    "tokenRatio": 0.1
  }
}

gRPC 服务配置：限定重试次数和可重试状态码，retryThrottling 在失败率高时自动停止重试。

🕳️ 07 · 常见坑

  • ✗SDK、网关、业务代码各自默认重试，叠加后远超预期。

    ✓梳理全链路重试点，只保留一处。

  • ✗对超时也无脑重试，而下游其实已在处理原请求。

    ✓确认操作幂等，超时重试配合幂等键与预算。

  • ✗故障恢复时所有客户端同时重连。

    ✓重连加退避抖动，服务端配合负载卸载。

  • ✗服务返回过载错误仍被当作可重试。

    ✓约定过载信号不重试，或尊重 Retry-After。

🎤 09 · 面试追问
如何量化并控制重试放大？

放大倍数约为各层尝试次数的乘积。控制方法：只在一层重试；设置重试预算，例如 Google SRE 书中建议重试占比低于 10%；下游返回过载信号时上游不再重试；监控重试与原始请求的比例。

什么是亚稳态故障，和重试有何关系？

系统被触发进入故障后，即使触发原因消失，也因正反馈环无法自愈。重试就是典型反馈环：失败引发重试，重试加剧过载。打破它要减载，例如关闭重试、卸载流量或临时扩容。

重试和熔断应怎么配合？

重试处理偶发瞬时错误，熔断处理持续故障。熔断打开后请求直接失败、不再重试；半开状态放少量请求试探。顺序上一般是先过熔断器再决定是否重试。
