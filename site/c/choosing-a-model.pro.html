怎么选模型

Choosing a Model

📐 01 · 定义

模型选型（Choosing a Model）是在能力、成本、延迟、上下文长度、部署与合规约束之间做权衡，为具体任务挑选合适 LLM 的工程决策。成熟做法不是选一个「最强」模型，而是基于业务评测集比较候选模型，并按任务难度做路由：简单任务用小模型，复杂任务用旗舰模型。

⚙️ 02 · 原理
  1. 1

    定义任务：明确输入类型、输出格式、质量标准和可接受的延迟与单价。

  2. 2

    列出约束：数据能否出境、是否需私有部署、需要多长上下文、是否要工具调用。

  3. 3

    建评测集：从真实业务中抽取几十到几百条样本，带参考答案或评分标准。

  4. 4

    对比测试：多个候选模型跑同一评测集，记录质量、延迟、Token 成本。

  5. 5

    路由上线：按任务复杂度分流到不同模型，并持续监控、随新模型发布复评。

🔤 03 · 术语
评测集 (Eval Set)
代表真实任务的固定样本集，用于客观比较模型与提示。
模型路由 (Model Routing)
按任务类型或难度把请求分发给不同模型。
首 Token 延迟 (TTFT)
从发出请求到收到第一个输出 Token 的时间。
LLM-as-a-Judge
用另一个模型按标准给输出打分，需抽样人工校准。
开源权重 (Open Weights)
公开模型参数，可自行部署与微调。
💻 04 · 代码
按难度路由模型python
# 简单的规则路由：便宜模型兜底，复杂任务升级
# 模型名以供应商当前文档为准，建议放在配置文件而非写死
MODELS = {
    "fast":  "claude-haiku-4-5",    # 分类、抽取、短回复
    "smart": "claude-sonnet-4-5",   # 编码、分析、多步任务
}

def pick_model(task_type: str, input_tokens: int) -> str:
    if task_type in {"classify", "extract", "summarize_short"}:
        return MODELS["fast"]
    if task_type in {"code", "agent", "analysis"} or input_tokens > 20_000:
        return MODELS["smart"]
    return MODELS["fast"]

print(pick_model("classify", 300))   # -> fast 模型
print(pick_model("code", 5000))      # -> smart 模型

路由规则应以评测数据为依据，并保留按配置切换模型的能力。

选型评估矩阵

维度如何度量常见取舍

⚖️ 06 · 方案取舍

单一旗舰模型

优点简单，效果上限高

代价成本高，简单任务浪费

适用早期验证、调用量小

多模型路由

优点成本与质量兼顾

代价需维护路由逻辑和多套评测

适用调用量大、任务类型多样

开源模型自部署

优点数据可控、可微调

代价硬件与运维投入，能力可能不足

适用合规要求高或规模极大

🕳️ 07 · 常见坑

  • ✗只看公开排行榜就定模型

    ✓用自己业务的样本评测，榜单只作初筛

  • ✗代码里写死模型名，升级要改多处

    ✓模型名放配置，统一管理和灰度切换

  • ✗评测只看质量，不算成本和延迟

    ✓评测报告同时给出质量、单次成本、P95 延迟

  • ✗选定后不再复评

    ✓新模型发布或价格调整时重跑评测

🎤 09 · 面试追问
如何在没有标准答案时评测模型？

制定评分细则（rubric），用成对比较让人或 LLM 评审判断哪个更好；LLM 评审要抽样人工校准一致性，并注意位置偏差、长度偏好；对可客观检验的部分（格式、代码测试）用自动化指标。

什么时候该考虑微调而不是换模型？

提示工程和检索已经做足，仍需稳定的特定格式、风格或领域行为，且有足量高质量标注数据时考虑微调。若问题是缺知识，优先 RAG；若是推理能力不足，换更强模型通常更划算。

编码 Agent 的模型怎么选？

看长上下文下的代码理解、工具调用稳定性、多步任务成功率和指令遵循，而不只是单题代码分数。可用 SWE-bench 类基准初筛，再用自家仓库的真实任务试跑，比较完成率与成本。
