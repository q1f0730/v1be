恢复时间与恢复点目标

RTO & RPO

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

RTO（Recovery Time Objective，恢复时间目标）是故障后到服务恢复的最长可接受时间；RPO（Recovery Point Objective，恢复点目标）是以时间衡量的最大可接受数据丢失，即可回退到多久之前的状态。二者是业务连续性与灾难恢复规划的核心指标，决定备份频率、复制方式和 DR 成本。

⚙️ 02 · 原理
  1. 1

    业务方评估停机与丢数据的代价，为每个系统给出可接受的 RTO 与 RPO。

  2. 2

    RPO 决定数据保护方式：每日备份对应约一天，日志归档或持续复制可缩到分钟或秒级。

  3. 3

    RTO 决定恢复方式：从备份重建需小时级，温备或自动故障转移可到分钟级。

  4. 4

    架构与手册按目标设计，例如 WAL 归档间隔、跨区复制、IaC 重建时间。

  5. 5

    通过演练测出实际恢复时间（RTA）与实际数据损失（RPA），与目标比较并改进。

🔤 03 · 术语
恢复时间实际值 (RTA)
演练或真实事件中测得的实际恢复耗时。
最大可容忍停机 (MTPD)
业务能承受的最长中断，RTO 必须小于它。
WAL 归档 (WAL Archiving)
PostgreSQL 持续保存预写日志，用于时间点恢复。
业务影响分析 (BIA)
评估各业务中断造成损失的过程，是设定 RTO/RPO 的依据。
MTTR (Mean Time To Recovery)
平均恢复时间，是对历史表现的统计，不同于目标值 RTO。
💻 04 · 代码
用 WAL 归档压缩 RPOtext
# postgresql.conf：持续归档 WAL，配合基础备份做时间点恢复
wal_level = replica
archive_mode = on

# 每个写满的 WAL 段都复制到归档位置（示例：本地挂载的备份盘）
archive_command = 'test ! -f /mnt/wal_archive/%f && cp %p /mnt/wal_archive/%f'

# 即使写入很少，也最多每 60 秒切换一次 WAL 段
# 这让最坏情况下的数据丢失大致限制在约 1 分钟量级
archive_timeout = 60

# 恢复时在新实例中设置：
# restore_command = 'cp /mnt/wal_archive/%f %p'
# recovery_target_time = '2026-10-20 10:00:00+08'

archive_timeout 限定 WAL 段切换间隔，从配置层面约束 RPO；示例取自官方文档写法。

⚖️ 06 · 方案取舍

宽松目标（小时级）

优点成本低，架构简单

代价故障时业务中断长、丢数据多

适用内部工具、可补录的数据

严格目标（分钟级）

优点业务影响小

代价需复制、温备、自动化，成本高

适用在线交易、核心用户功能

RPO 接近零

优点几乎不丢数据

代价同步复制增加写延迟

适用资金、账务类数据

🕳️ 07 · 常见坑

  • ✗所有系统统一定一个 RTO/RPO，核心系统不够，边缘系统浪费。

    ✓按业务影响分级设定。

  • ✗RPO 只看备份频率，忽略备份本身上传失败。

    ✓监控备份成功与归档延迟，失败即告警。

  • ✗RTO 只算数据恢复时间，没算发现、决策和 DNS 切换。

    ✓RTO 从故障发生算到用户可用，端到端演练测量。

🎤 09 · 面试追问
RTO 和 MTTR 有什么区别？

RTO 是事先设定的目标，即最长可接受的恢复时间；MTTR 是事后统计的历史平均恢复时间。评审时用 MTTR 及演练数据验证能否满足 RTO，并关注最坏情况而不只是平均值。

RPO 为零可以只靠备份实现吗？

不行。备份总有间隔，备份点之后的写入会丢失。接近零的 RPO 需要同步复制，让写入在确认前已到达另一副本；但复制会同步误删除，所以仍需时间点恢复来应对逻辑错误。

如何说服业务方接受合理的 RTO/RPO？

把目标和成本放在一起：给出不同档位所需架构、月成本和演练要求，对应停机每小时与丢数据的损失估算，让业务方在代价与风险间做选择，而不是一律要求零。
