Saga 分布式事务模式

Saga Pattern

🧸 回到小白版

📐 01 · 定义

Saga 是处理跨服务长事务的模式，最早由 Garcia-Molina 与 Salem 于 1987 年提出：把一个全局事务拆成一串本地事务，每步提交后发布事件或由协调者推进下一步；任一步失败时，按相反顺序执行已完成步骤的补偿事务，使系统回到业务上一致的状态。它以最终一致取代分布式锁和两阶段提交。

⚙️ 02 · 原理
  1. 1

    把业务流程拆成有序的本地事务 T1…Tn，每个只修改自己服务的数据并立即提交。

  2. 2

    为每个可回滚步骤设计补偿事务 C1…Cn，在语义上撤销其效果，如退款、释放库存，而非数据库层面的回滚。

  3. 3

    编排式由中央协调者驱动步骤与补偿；协同式由各服务监听事件自行决定下一步。

  4. 4

    关键转折步骤（pivot）之后的步骤应设计为可重试直至成功，之前的步骤可补偿。

  5. 5

    协调状态需持久化，步骤与补偿都必须幂等，并配合发件箱模式可靠发布事件。

🔤 03 · 术语
补偿事务 (Compensating Transaction)
在业务语义上撤销已提交步骤效果的操作，如取消订单、退款。
编排 (Orchestration)
由一个协调者集中决定调用哪个服务以及何时补偿。
协同 (Choreography)
无中心协调者，各服务订阅事件并发布新事件推进流程。
转折事务 (Pivot Transaction)
Saga 中的不可逆分界点，之后的步骤只能重试不能补偿。
语义锁 (Semantic Lock)
用 PENDING 等状态标记处理中的数据，应对 Saga 缺乏隔离性的问题。
💻 04 · 代码
最小编排式 Sagapython
class SagaFailed(Exception):
    pass

def run_saga(steps, ctx):
    """steps: [(动作, 补偿)]，动作与补偿都必须幂等"""
    done = []
    for action, compensate in steps:
        try:
            action(ctx)
            done.append(compensate or (lambda c: None))  # 无补偿的步骤占位
        except Exception as e:
            for comp in reversed(done):      # 逆序补偿已完成的步骤
                comp(ctx)
            raise SagaFailed(f"失败于 {action.__name__}: {e}") from e

def reserve(ctx): ctx["log"].append("预留库存")
def release(ctx): ctx["log"].append("释放库存")
def charge(ctx):  ctx["log"].append("扣款")
def refund(ctx):  ctx["log"].append("退款")
def ship(ctx):    raise RuntimeError("物流不可用")

ctx = {"log": []}
try:
    run_saga([(reserve, release), (charge, refund), (ship, None)], ctx)
except SagaFailed as e:
    print(e, ctx["log"])
# 失败于 ship: 物流不可用 ['预留库存', '扣款', '退款', '释放库存']

演示补偿顺序；生产中协调状态需持久化，可用 Temporal 等持久化执行框架承载。

📊 05 · 参数对比

Saga 与两阶段提交

维度Saga两阶段提交 (2PC)
一致性最终一致，中间态可见强一致，原子提交
锁持有每步本地提交即释放准备阶段到提交期间一直持有
失败处理执行补偿事务协调者决定回滚或提交
可用性参与方故障不阻塞其他服务协调者故障可能阻塞参与方
适用跨服务、长时间业务流程同一信任域内短事务
⚖️ 06 · 方案取舍

编排式

优点流程集中可见，易于监控与修改

代价协调者成为关键组件，有耦合

适用步骤多、分支复杂的流程

协同式

优点服务松耦合，无中心依赖

代价流程分散在事件中，难追踪与排查

适用步骤少、团队自治度高

避免拆分（同库事务）

优点直接用 ACID，最简单

代价限制服务独立演进

适用强一致需求且数据可放在同一服务

🕳️ 07 · 常见坑

  • ✗补偿不幂等，重试时重复退款

    ✓补偿使用幂等键，并记录已执行状态

  • ✗忽略中间态被其他请求读到

    ✓使用 PENDING 等语义锁状态，读取方据此处理

  • ✗把不可撤销操作（如发短信）放在早期步骤

    ✓不可逆步骤尽量后置，放在转折点之后

  • ✗本地事务提交成功但事件发布丢失

    ✓使用发件箱模式，事件与业务数据同事务写入

🎤 09 · 面试追问
Saga 缺少隔离性会导致什么问题？

各步骤独立提交，其他事务可能读到中间结果（脏读类问题）、两个 Saga 交错导致更新丢失。常用对策：语义锁标记处理中状态、交换式更新、重读校验、调整步骤顺序把风险高的放后，或按业务键串行化同一实体的 Saga。

补偿事务本身失败怎么办？

补偿应设计为可重试且幂等，失败后按退避持续重试；超过阈值进入死信或人工处理队列并告警。设计上应确保补偿最终能够成功，例如退款失败可转为挂账待处理，而不是让流程停在不一致状态。

为什么微服务通常不用 2PC 而用 Saga？

2PC 要求所有参与者支持 XA 并在准备阶段持锁，协调者故障会阻塞，跨服务和跨技术栈时可用性与性能代价高。Saga 每步本地提交、释放资源，用补偿换取可用性，契合服务自治与异步通信。
