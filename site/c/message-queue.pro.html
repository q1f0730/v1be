消息队列

Message Queue

📐 01 · 定义

消息队列是生产者与消费者之间的异步中间件：生产者把消息写入队列后即可返回，消费者按自己的节奏取出处理并确认。它实现服务解耦、削峰填谷和失败重试，常见实现有 RabbitMQ、Amazon SQS、Kafka（日志型）、Redis Streams。代价是引入最终一致性与重复消费等问题。

⚙️ 02 · 原理
  1. 1

    生产者把消息发送给 Broker，Broker 持久化后返回确认。

  2. 2

    消费者拉取（或被推送）消息；处理期间消息对其他消费者不可见或标记为未确认。

  3. 3

    处理成功后消费者确认（ack/删除），Broker 才真正移除消息。

  4. 4

    超时未确认的消息重新投递，因此语义通常是“至少一次”，消费者需幂等。

  5. 5

    多次失败的消息转入死信队列（DLQ）供排查；队列积压量是扩容消费者的信号。

🔤 03 · 术语
Broker
负责接收、存储和投递消息的服务端。
确认 (Ack)
消费者告知已成功处理，消息可被移除。
至少一次 (At-least-once)
消息不丢但可能重复投递的语义。
可见性超时 (Visibility Timeout)
SQS 中消息被取走后对他人隐藏的时长。
死信队列 (DLQ)
存放多次处理失败消息的队列。
Outbox 模式
业务写入与待发消息同事务落库，再异步投递。
💻 04 · 代码
SQS 幂等消费者python
import json, boto3

sqs = boto3.client("sqs")
QUEUE_URL = "https://sqs.us-east-1.amazonaws.com/123456789012/orders"

def consume_forever():
    while True:
        resp = sqs.receive_message(
            QueueUrl=QUEUE_URL,
            MaxNumberOfMessages=10,
            WaitTimeSeconds=20,       # 长轮询，减少空请求
            VisibilityTimeout=60,     # 需大于单条消息的最长处理时间
        )
        for msg in resp.get("Messages", []):
            body = json.loads(msg["Body"])
            # 幂等：同一 order_id 只处理一次（mark_processed 用唯一约束实现）
            if mark_processed(body["order_id"]):
                send_confirmation_email(body)
            # 处理成功才删除；抛异常则不删，超时后重新投递
            sqs.delete_message(QueueUrl=QUEUE_URL, ReceiptHandle=msg["ReceiptHandle"])

# 队列上配置 RedrivePolicy：maxReceiveCount=5 后转入死信队列

先处理后删除；重复投递靠业务幂等吸收；失败次数过多进入 DLQ。

⚖️ 06 · 方案取舍

任务队列（RabbitMQ/SQS）

优点每条消息一个消费者处理，简单

代价消费后即删，不能回放

适用后台任务、邮件、转码

日志型（Kafka）

优点高吞吐，多订阅方可回放

代价运维复杂，有序性按分区

适用事件驱动、数据集成

数据库表当队列

优点无新组件，可与业务同事务

代价高吞吐下扩展性差

适用规模小、强一致需求

🕳️ 07 · 常见坑

  • ✗假设消息只会投递一次

    ✓按至少一次设计，消费者用唯一键实现幂等

  • ✗先写数据库再发消息，进程崩溃导致消息丢失

    ✓使用 Outbox 模式或事务消息

  • ✗可见性超时小于处理时间，消息被重复处理

    ✓超时大于最长处理时间，或处理中延长超时

  • ✗没有死信队列，毒消息无限重试

    ✓设置最大重试次数与 DLQ，并对 DLQ 告警

☑️ 08 · 检查清单
🎤 09 · 面试追问
如何实现“恰好一次”处理？

端到端的恰好一次很难靠队列单独保证。实践是“至少一次投递 + 幂等消费”：用业务唯一键、去重表或条件写入，使重复消息不产生副作用。Kafka 事务能在其内部读-处理-写链路中提供恰好一次语义。

消息顺序怎么保证？

全局有序代价很高。通常只需按业务键有序：Kafka 用相同键进入同一分区，SQS FIFO 用 MessageGroupId。同一分组内只能串行消费，并行度受分组数限制；重试时还需避免乱序。

队列积压时怎么办？

先看消息年龄与积压量是否持续增长；扩容消费者（受分区数等限制）；排查下游瓶颈或毒消息；必要时降级非关键处理、批量消费。长期则做容量规划，按积压指标自动扩缩容。
