服务网格

Service Mesh

📐 01 · 定义

服务网格（Service Mesh）是微服务通信的基础设施层：在每个服务旁部署代理（sidecar，或节点级代理），由控制平面统一下发配置，透明地提供 mTLS 加密与身份认证、重试与超时、流量切分、熔断和可观测性，使这些能力不必写进每个服务的业务代码。

⚙️ 02 · 原理
  1. 1

    数据平面：每个 Pod 注入代理（如 Envoy），透明拦截该服务的全部进出流量。

  2. 2

    控制平面：如 istiod 汇总服务发现、路由规则和证书，推送给所有代理。

  3. 3

    安全：代理之间自动建立 mTLS，基于工作负载身份做认证与授权。

  4. 4

    流量治理：按规则执行重试、超时、按权重分流（金丝雀）、故障注入。

  5. 5

    可观测：所有代理以统一格式产出请求指标、访问日志和链路追踪数据。

🔤 03 · 术语
Sidecar 代理
与业务容器同 Pod 运行、拦截其网络流量的代理容器。
数据平面 / 控制平面
前者转发实际流量，后者管理配置、证书与策略。
mTLS (Mutual TLS)
通信双方互相验证证书的 TLS，用于服务间身份认证。
Ambient 模式
Istio 的无 sidecar 模式，用节点级 ztunnel 与可选 waypoint 代理。
金丝雀发布 (Canary)
按比例把少量流量导到新版本观察后再扩大。
💻 04 · 代码
Istio 分流+重试+mTLSyaml
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: reviews
spec:
  hosts: ["reviews"]
  http:
  - route:
    - destination: {host: reviews, subset: v1}
      weight: 90                      # 90% 流量到稳定版
    - destination: {host: reviews, subset: v2}
      weight: 10                      # 10% 金丝雀
    retries: {attempts: 3, perTryTimeout: 2s}
    timeout: 6s
---
apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata:
  name: default
  namespace: prod
spec:
  mtls: {mode: STRICT}                # 命名空间内只接受 mTLS 流量

subset v1/v2 需在 DestinationRule 中定义；业务代码无需改动。

⚖️ 06 · 方案取舍

引入服务网格

优点统一安全与流量治理，语言无关

代价额外延迟、资源占用和运维复杂度

适用服务多、多语言、合规要求 mTLS

SDK/框架内实现

优点无额外组件，开销小

代价每种语言重复实现，升级困难

适用服务少、技术栈统一

仅网关+NetworkPolicy

优点简单，覆盖南北向流量

代价服务间缺少加密与精细治理

适用规模较小的集群

🕳️ 07 · 常见坑

  • ✗服务很少就上网格，运维成本远超收益

    ✓先评估是否真的需要 mTLS 与精细流量治理

  • ✗应用层与网格都配重试，重试次数相乘放大故障

    ✓统一在一层配置重试，并设置总超时与重试预算

  • ✗直接切 STRICT mTLS，未注入代理的服务调用全断

    ✓先用 PERMISSIVE 模式过渡，确认全部注入后再切换

🎤 09 · 面试追问
服务网格解决了哪些问题？

把服务间通信的横切关注点从业务代码剥离：mTLS 加密与身份、授权策略、重试超时熔断、流量切分、统一的指标与追踪。多语言团队不必各自实现，策略可集中管理和审计。

sidecar 模式的代价是什么？

每个 Pod 多一个代理容器，占用 CPU 内存，请求多两跳增加延迟；代理升级需要重启 Pod；注入与启动顺序问题会导致偶发失败。Ambient 等无 sidecar 模式正是为降低这些成本。

API 网关和服务网格的区别？

API 网关处理南北向流量：外部请求入口、认证、限流、API 管理；服务网格处理东西向流量：集群内服务间通信的安全与治理。两者可以并存，部分产品同时覆盖两种场景。
