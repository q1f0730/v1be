水平与垂直扩展

Horizontal vs Vertical Scaling

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

水平扩展（Horizontal Scaling）靠增加实例数量分担负载；垂直扩展（Vertical Scaling）靠给单实例更多 CPU、内存或更快磁盘提升能力。二者是容量规划的两条基本路径：水平扩展上限高、可容错，但要求无状态或分片；垂直扩展改造成本低，却受单机上限约束且常需重启。

⚙️ 02 · 原理
  1. 1

    垂直扩展：更换更大规格的实例或调大容器资源限制，单节点处理能力提升。

  2. 2

    垂直扩展通常需要重启或迁移实例，存在短暂中断，且最终受最大规格限制。

  3. 3

    水平扩展：增加副本，由负载均衡分发请求，应用需无状态或会话外置。

  4. 4

    有状态组件水平扩展需要分片或复制，例如数据库读副本分担读、分片分担写。

  5. 5

    实践中常组合使用：先确定合适的单实例规格，再按负载水平扩展副本。

🔤 03 · 术语
扩展 (Scale Out / Scale Up)
前者加机器数量，后者加单机能力。
分片 (Sharding)
把数据按键拆分到多个节点，实现写入的水平扩展。
读副本 (Read Replica)
复制主库数据只处理读请求，用于水平扩展读。
VPA (Vertical Pod Autoscaler)
Kubernetes 中自动推荐或调整 Pod 资源请求的组件。
阿姆达尔定律 (Amdahl's Law)
程序中不可并行部分决定了加速比的上限。
💻 04 · 代码
两种扩展的 kubectl 操作bash
# 水平扩展：副本从 3 增加到 6，由 Service 自动分发流量
kubectl scale deployment/api --replicas=6

# 垂直扩展：调大单个 Pod 的资源（会触发滚动重建 Pod）
kubectl set resources deployment/api \
  --requests=cpu=1,memory=2Gi \
  --limits=cpu=2,memory=4Gi

# 观察效果：资源使用（需要集群安装 metrics-server）
kubectl top pods -l app=api

# 数据库层的水平扩展通常是加读副本或分片，
# 不能像无状态服务一样直接 scale 副本数

无状态服务直接调副本数；调资源会重建 Pod，属于垂直扩展。

📊 05 · 参数对比

两种扩展方式对比

维度水平扩展垂直扩展
上限理论上很高，受协调开销限制受单机最大规格限制
容错多副本，单点故障影响小单实例故障即全停
改造成本需无状态或分片几乎不需改代码
变更中断增减副本通常无中断常需重启或迁移
⚖️ 06 · 方案取舍

优先垂直扩展

优点简单快速，无需改架构

代价成本随规格非线性上升，有天花板

适用数据库主库、早期产品

优先水平扩展

优点弹性好，可容错

代价需处理状态、一致性与负载均衡

适用无状态 Web/API 服务

组合使用

优点兼顾单机效率与弹性

代价需要容量规划经验

适用多数生产系统

🕳️ 07 · 常见坑

  • ✗应用在内存保存会话，水平扩展后用户频繁掉登录。

    ✓会话外置到共享存储或使用签名令牌。

  • ✗服务水平扩到几十个副本，数据库连接数被打满。

    ✓使用连接池或数据库代理，按下游容量限制副本。

  • ✗单线程程序换更多核的机器，性能毫无提升。

    ✓先确认瓶颈与并行度，再选扩展方式。

🎤 09 · 面试追问
数据库扩展为什么比应用服务难？

数据库有状态，水平扩展需要处理数据分布和一致性。读可以用读副本扩展但有复制延迟；写需要分片，带来跨分片事务和重新分片的复杂度。所以数据库常先垂直扩展，再按需引入读副本、缓存和分片。

水平扩展是否能无限提升性能？

不能。阿姆达尔定律指出不可并行部分限制加速比；协调开销、共享依赖如数据库和锁、网络带宽都会成为瓶颈。扩展前应找出真正瓶颈。

什么时候选择垂直扩展更合理？

负载稳定、单机规格尚有余量、应用难以无状态化或改造成本高时，例如单主数据库和早期产品。它能快速见效，但要同时规划达到上限后的水平扩展路径。
