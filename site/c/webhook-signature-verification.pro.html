Webhook签名校验

Webhook Signature Verification

📐 01 · 定义

Webhook 签名校验是接收方确认回调请求确实来自声明的发送方、且内容未被篡改的机制。主流做法是发送方用共享密钥对原始请求体（常加时间戳）计算 HMAC-SHA256 并放入请求头，接收方重新计算并常量时间比对，再配合时间窗口和事件去重防重放。

⚙️ 02 · 原理
  1. 1

    双方预先共享一个签名密钥（signing secret），由发送方平台生成并在控制台展示。

  2. 2

    发送方对原始字节请求体（或“时间戳.请求体”）计算 HMAC，放入如 X-Hub-Signature-256 的请求头。

  3. 3

    接收方读取未经解析的原始请求体，用同一密钥和算法重新计算签名。

  4. 4

    使用常量时间比较函数对比两个签名，不一致直接返回 401 并记录日志。

  5. 5

    校验时间戳在允许窗口内，并按事件 ID 去重，保证重放和重复投递不会被重复处理。

🔤 03 · 术语
HMAC
基于哈希的消息认证码（RFC 2104），需要密钥才能生成有效值。
原始请求体 (Raw Body)
未经 JSON 解析与重新序列化的字节流，签名针对它计算。
常量时间比较 (Constant-time Compare)
比较耗时与内容无关，防止逐字节猜测签名。
重放攻击 (Replay Attack)
截获合法请求后原样重发，以触发重复操作。
幂等键 (Idempotency Key)
用事件 ID 记录已处理事件，重复到达时跳过。
密钥轮换 (Secret Rotation)
新旧密钥并存一段时间，接收方任一校验通过即接受。
💻 04 · 代码
校验 GitHub Webhookpython
import hmac, hashlib, os
from flask import Flask, request, abort

app = Flask(__name__)
SECRET = os.environ["GITHUB_WEBHOOK_SECRET"].encode()

@app.post("/webhooks/github")
def github_webhook():
    body = request.get_data()  # 原始字节，不要先解析再序列化
    received = request.headers.get("X-Hub-Signature-256", "")
    expected = "sha256=" + hmac.new(SECRET, body, hashlib.sha256).hexdigest()
    if not hmac.compare_digest(expected, received):
        abort(401)

    delivery_id = request.headers.get("X-GitHub-Delivery")
    # 用 delivery_id 做去重后再处理，处理耗时的任务放进队列
    event = request.get_json()
    return "", 204

签名基于原始请求体；compare_digest 做常量时间比较，投递 ID 用于去重。

⚖️ 06 · 方案取舍

共享密钥 HMAC

优点实现简单、性能好，生态最普遍

代价双方都持密钥，泄露需轮换

适用绝大多数 SaaS 回调

非对称签名（如 Ed25519）

优点接收方只持公钥，泄露风险低

代价实现与密钥分发更复杂

适用多租户、大量接收方

mTLS 或 IP 白名单

优点网络层拦截，免改业务

代价IP 会变，不能防内容篡改

适用作为签名之外的补充

🕳️ 07 · 常见坑

  • ✗框架先把 JSON 解析了，再序列化后计算签名

    ✓在中间件中保留原始字节，如 express.raw()

  • ✗用 == 比较签名

    ✓用 hmac.compare_digest 或 crypto.timingSafeEqual

  • ✗签名通过就同步执行耗时业务，超时触发重试

    ✓先返回 2xx，任务入队异步处理并按事件 ID 去重

  • ✗测试环境与生产共用一个签名密钥

    ✓按环境分配密钥，存入密钥管理服务

🎤 09 · 面试追问
为什么签名要包含时间戳？

只签请求体时，截获的合法请求可无限期重放。把时间戳纳入签名内容，攻击者改时间戳就会破坏签名；接收方只接受窗口内的请求，再配合事件 ID 去重，即可在窗口内也防重复处理。

为什么不能用普通字符串比较？

普通比较遇到第一个不同字节就返回，耗时随匹配前缀长度变化。攻击者可通过大量请求测时逐字节猜出正确签名。常量时间比较消除这种时间侧信道。

密钥轮换时如何不中断回调？

发送方在过渡期同时用新旧密钥签名（或多个签名值），接收方配置两把密钥，任一校验通过即接受；确认全部切换后移除旧密钥。Stripe、Standard Webhooks 都支持多签名并存。
