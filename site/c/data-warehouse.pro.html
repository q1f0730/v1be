数据仓库 (BigQuery / Snowflake)

📐 01 · 定义

数据仓库（Data Warehouse）是面向分析的集中式数据存储，属于数据平台的存储与计算层。它把来自业务数据库、日志、SaaS 等多个来源的数据按统一模型整合，用列式存储和大规模并行计算支撑报表、BI 与即席查询，把分析负载与在线业务库隔离。BigQuery、Snowflake、Redshift 是常见的云数仓。

⚙️ 02 · 原理
  1. 1

    数据通过 ETL/ELT 管道从业务库、事件流、第三方 API 抽取，批量或增量加载进仓库的原始层（staging/raw）。

  2. 2

    在仓库内用 SQL 转换（常配合 dbt）清洗、去重、关联，产出按主题组织的事实表与维度表。

  3. 3

    存储多为列式格式并做压缩与分区，查询只读涉及的列和分区，以减少扫描量。

  4. 4

    云数仓普遍存算分离：存储按量计费，计算以虚拟仓库/slot 等形式按需扩缩，并行执行查询。

  5. 5

    BI 工具、Notebook 或应用通过 SQL 读取汇总层（mart），按扫描量或计算时长计费。

🔤 03 · 术语
星型模型 (Star Schema)
中心事实表连接多张维度表的建模方式，便于聚合分析。
事实表 (Fact Table)
记录业务事件与度量（如订单金额），通常行数最多。
维度表 (Dimension Table)
描述事实的上下文属性，如用户、商品、日期。
缓慢变化维 (SCD)
处理维度属性随时间变化的建模方法，如 Type 2 保留历史版本。
存算分离 (Separation of Storage and Compute)
存储与计算独立扩缩、分别计费的架构。
💻 04 · 代码
按分区查询控制扫描量sql
-- BigQuery：建按日分区、按用户聚簇的事实表
CREATE TABLE analytics.fct_orders (
  order_id STRING,
  user_id STRING,
  amount NUMERIC,
  created_at TIMESTAMP
)
PARTITION BY DATE(created_at)
CLUSTER BY user_id;

-- 只扫最近 7 天的分区，而不是全表
SELECT user_id, SUM(amount) AS gmv
FROM analytics.fct_orders
WHERE created_at >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 7 DAY)
GROUP BY user_id
ORDER BY gmv DESC
LIMIT 100;

按时间分区过滤可显著减少扫描字节数，在按量计费的数仓里直接等于省钱。

⚖️ 06 · 方案取舍

云托管数仓

优点免运维、弹性扩缩、生态成熟

代价按量费用易失控，存在厂商锁定

适用团队小、数据量增长快

自建开源 OLAP

优点成本可控、可深度调优

代价需要专人运维与容量规划

适用数据量大且有运维能力

直接查业务库只读副本

优点零额外系统，最快上手

代价复杂分析仍慢，模型混乱

适用早期、报表需求少

🕳️ 07 · 常见坑

  • ✗SELECT * 扫全表，按量计费的数仓一次查询扣掉大笔费用

    ✓只选需要的列，按分区过滤，并开启查询字节上限

  • ✗原始数据直接给 BI 用，各报表口径不一致

    ✓建分层模型（raw→staging→mart），统一指标定义

  • ✗把数仓当 OLTP 用，频繁单行更新

    ✓数仓适合批量追加；高频点更新留在业务库

  • ✗没有数据新鲜度监控，上游断了几天才发现

    ✓对关键表设置新鲜度与行数检查并告警

🎤 09 · 面试追问
数据仓库和数据湖、湖仓有什么区别？

数仓存清洗后的结构化数据，Schema-on-write，查询快；数据湖用对象存储放原始多格式数据，便宜但治理难；湖仓在对象存储上加表格式（如 Iceberg、Delta）提供事务与 Schema，试图兼得二者。

如何控制 BigQuery 之类按量计费数仓的成本？

分区+聚簇减少扫描；禁止 SELECT *；设置 maximum bytes billed；常用聚合做物化视图；稳定负载考虑预留容量；按项目/标签拆账单监控 Top 查询。

为什么分析查询不应直接跑在生产主库？

分析查询扫大量行，占用 CPU、I/O 与缓冲池，会挤压在线事务延迟；行存不适合大聚合；长查询还可能阻塞清理或复制。应隔离到副本或数仓。
