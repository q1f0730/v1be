服务发现

Service Discovery

📐 01 · 定义

服务发现（Service Discovery）是在动态环境中把逻辑服务名解析为当前可用实例地址的机制，属于分布式系统的网络与控制面层。容器和自动扩缩让实例 IP 随时变化，服务发现通过注册表、健康检查和解析（DNS、API 或代理）让调用方无需写死地址。Kubernetes Service、Consul、etcd 是常见实现。

⚙️ 02 · 原理
  1. 1

    实例启动后注册到注册表（自注册或由平台/第三方代为注册），记录服务名、地址、端口与元数据。

  2. 2

    注册表通过心跳、TTL 或主动健康检查维护实例状态，不健康实例被剔除。

  3. 3

    客户端发现：调用方查询注册表获得实例列表，自行做负载均衡选择目标。

  4. 4

    服务端发现：调用方请求一个稳定入口（负载均衡器、K8s Service 虚拟 IP、Sidecar 代理），由它转发。

  5. 5

    Kubernetes 中 CoreDNS 把 Service 名解析为 ClusterIP，EndpointSlice 记录后端 Pod，kube-proxy 或 eBPF 负责转发。

🔤 03 · 术语
注册表 (Service Registry)
保存服务名到实例地址映射的数据库，需高可用。
客户端发现 (Client-side Discovery)
调用方直接查询注册表并自行负载均衡。
服务端发现 (Server-side Discovery)
调用方访问固定入口，由路由层选择实例。
EndpointSlice
Kubernetes 中记录 Service 后端 Pod 地址的资源。
Headless Service
不分配 ClusterIP 的 Service，DNS 直接返回各 Pod 地址。
💻 04 · 代码
Kubernetes Service 与 DNS 访问yaml
# 为带 app=orders 标签的 Pod 提供稳定的服务名
apiVersion: v1
kind: Service
metadata:
  name: orders
  namespace: shop
spec:
  selector:
    app: orders        # 只把就绪（Ready）的匹配 Pod 加入后端
  ports:
    - port: 80
      targetPort: 8080
# 同命名空间内访问：http://orders
# 跨命名空间访问：http://orders.shop.svc.cluster.local
# Pod 扩缩或重建后 IP 变化，调用方地址不变

Service 以标签选择后端 Pod，结合 readiness 探针剔除未就绪实例，DNS 名保持不变。

⚖️ 06 · 方案取舍

DNS 解析

优点通用、语言无关

代价TTL 与客户端缓存导致更新滞后

适用平台内服务调用

客户端发现 + SDK

优点可做智能负载均衡

代价每种语言需 SDK，耦合注册表

适用单语言、需精细路由

服务网格

优点统一流量治理与可观测

代价增加延迟与运维复杂度

适用大量微服务、多语言

🕳️ 07 · 常见坑

  • ✗代码或配置中写死 Pod/虚拟机 IP

    ✓通过服务名访问，地址交给平台解析

  • ✗客户端长期缓存 DNS 结果，不随实例变化更新

    ✓遵守 TTL，长连接定期重建或使用支持重解析的客户端

  • ✗只注册不做健康检查，故障实例仍接收流量

    ✓配置 readiness/健康检查，失败即摘除

  • ✗注册表单点部署

    ✓注册表多副本、跨可用区部署，客户端有缓存兜底

☑️ 08 · 检查清单
🎤 09 · 面试追问
客户端发现与服务端发现的优缺点？

客户端发现少一跳、可定制负载均衡，但每个语言要实现并与注册表耦合；服务端发现对调用方透明、语言无关，但多一个转发组件，需保证其高可用与性能。

Kubernetes 中访问一个 Service 发生了什么？

Pod 通过 CoreDNS 把服务名解析为 ClusterIP；发往该 IP 的流量被 kube-proxy 规则（iptables/IPVS）或 eBPF 转换到 EndpointSlice 中某个就绪 Pod 的地址。

为什么基于 DNS 的发现会出现流量不均？

客户端或运行时缓存 DNS 结果，长连接（HTTP/2、gRPC）建立后长期复用同一后端；新扩容实例收不到流量。需要客户端负载均衡、连接定期轮换或 L7 代理。
