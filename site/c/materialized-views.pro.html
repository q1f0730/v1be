物化视图

Materialized Views

🧸 回到小白版

📐 01 · 定义

物化视图（Materialized View）是把查询结果实际存储下来的数据库对象。与每次访问都重新执行查询的普通视图不同，它在刷新时计算并保存结果，读取时像读表一样快，可建索引。代价是数据只反映上次刷新时的状态，需要设计刷新策略。

⚙️ 02 · 原理
  1. 1

    定义：CREATE MATERIALIZED VIEW … AS SELECT …，创建时执行一次并存储结果。

  2. 2

    读取：查询物化视图就是读一张普通表，可在其上建立索引加速。

  3. 3

    刷新：PostgreSQL 需显式执行 REFRESH，重新计算整个查询结果。

  4. 4

    CONCURRENTLY 刷新不阻塞读，但要求视图有唯一索引，且通常比普通刷新更慢。

  5. 5

    调度：用 cron、pg_cron 或业务事件触发刷新，刷新间隔决定数据新鲜度。

🔤 03 · 术语
普通视图 (View)
保存的查询定义，每次访问实时执行。
全量刷新 (Complete Refresh)
丢弃旧结果，重新执行完整查询。
增量维护 (Incremental View Maintenance)
只根据变更更新受影响的结果行。
REFRESH CONCURRENTLY
PostgreSQL 中不阻塞读的刷新方式，需唯一索引。
数据新鲜度 (Staleness)
物化结果落后源数据的时间。
💻 04 · 代码
日销售汇总物化视图sql
-- 预先汇总，看板查询从秒级变为毫秒级
CREATE MATERIALIZED VIEW daily_sales AS
SELECT date_trunc('day', o.created_at)::date AS day,
       p.category,
       count(*)          AS orders,
       sum(oi.qty * oi.unit_price) AS revenue
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
JOIN products p     ON p.sku = oi.sku
GROUP BY 1, 2
WITH DATA;

-- CONCURRENTLY 刷新要求有唯一索引
CREATE UNIQUE INDEX daily_sales_pk ON daily_sales (day, category);

-- 看板直接查询
SELECT * FROM daily_sales WHERE day >= current_date - 30 ORDER BY day;

-- 定时刷新（如每 15 分钟），刷新期间读请求不被阻塞
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_sales;

-- 使用 pg_cron 扩展调度（需已安装）
-- SELECT cron.schedule('*/15 * * * *', 'REFRESH MATERIALIZED VIEW CONCURRENTLY daily_sales');

唯一索引是并发刷新的前提；刷新频率就是数据可接受的滞后上限。

⚖️ 06 · 方案取舍

物化视图

优点声明式，SQL 即定义，可建索引

代价刷新是全量重算，有滞后

适用报表、看板等可容忍延迟

触发器维护汇总表

优点实时更新

代价增加写入开销，逻辑分散

适用汇总简单且需实时

应用缓存

优点灵活，可放在内存

代价需自行处理失效

适用结果小、访问极热

🕳️ 07 · 常见坑

  • ✗普通 REFRESH 锁住视图，刷新期间看板卡住

    ✓建唯一索引后使用 CONCURRENTLY

  • ✗刷新间隔短于刷新耗时，任务堆积

    ✓监控刷新耗时，调度避免重叠执行

  • ✗以为 PostgreSQL 物化视图会自动更新

    ✓必须显式刷新，并在页面标注数据更新时间

  • ✗实时性要求强的数据也放物化视图

    ✓实时数据查源表或用增量维护方案

☑️ 08 · 检查清单
🎤 09 · 面试追问
物化视图和普通视图的本质区别？

普通视图只是保存的查询，访问时展开执行，数据实时但性能取决于底层查询；物化视图存储结果，读快但有滞后，需要刷新。前者是抽象封装，后者是用存储换计算的缓存。

REFRESH CONCURRENTLY 的原理和代价？

它在临时空间计算新结果，再与旧结果按唯一索引比对，只对差异行执行增删改，因此刷新期间读不被阻塞。代价是比较过程更耗时、更占资源，且必须有覆盖所有行的唯一索引。

什么时候不该用物化视图？

数据需要实时准确（如余额、库存）；源数据变化极快而查询很少；结果集与源表差不多大，物化不节省计算。此时更适合优化原查询、加索引或用触发器维护汇总。
