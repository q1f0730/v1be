指标基数控制

Metrics Cardinality

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

指标基数（Metrics Cardinality）指一个指标名下由不同标签取值组合产生的独立时间序列数量。每个唯一组合都要单独存储和索引，总序列数约等于各标签取值数的乘积。把用户 ID、请求 URL、trace ID 等无界值放进标签会导致基数爆炸，使监控系统内存、查询和费用急剧上升。

⚙️ 02 · 原理
  1. 1

    序列生成：指标名加上一组标签键值唯一确定一条时间序列，例如按 method 和 status 区分。

  2. 2

    乘积效应：各标签取值数相乘，10 个路由×5 种方法×6 个状态码即为 300 条序列。

  3. 3

    存储压力：时序数据库为每条活跃序列维护内存索引，序列越多内存占用越高。

  4. 4

    爆炸来源：无界标签（用户 ID、原始 URL、错误消息）导致序列数随流量持续增长。

  5. 5

    治理：埋点时限制标签取值，采集端丢弃或聚合高基数标签，并监控序列总数。

🔤 03 · 术语
时间序列 (Time Series)
指标名加唯一标签组合对应的一串带时间戳的样本。
标签 (Label / Attribute)
附加在指标上的维度键值对，用于筛选与聚合。
活跃序列 (Active Series)
近期仍在产生样本的序列，决定内存占用。
序列流失 (Churn)
序列频繁新建与消失，如 Pod 名随每次发布变化。
Exemplar
附在指标样本上的示例 trace ID，避免把 trace ID 当标签。
💻 04 · 代码
采集端丢弃高基数标签yaml
# prometheus.yml
scrape_configs:
  - job_name: api
    static_configs:
      - targets: ["api:9100"]
    metric_relabel_configs:
      # 删除不该存在的高基数标签
      - action: labeldrop
        regex: "user_id|session_id|request_id"
      # 整个丢弃某个调试用的高基数指标
      - source_labels: [__name__]
        regex: "http_request_duration_by_path_seconds.*"
        action: drop

# 排查：哪些指标序列最多（在 Prometheus 中执行）
#   topk(10, count by (__name__) ({__name__=~".+"}))
# 某指标的某标签有多少种取值
#   count(count by (path) (http_requests_total))

采集端兜底只是止血，根本办法是在埋点处把路径归一为路由模板等有界值。

📊 05 · 参数对比

标签取值是否合适

标签取值范围建议
method / status_code有界、很小适合
route（路由模板）有界适合，如 /users/{id}
原始 URL path无界不适合，需归一化
user_id / trace_id无界不适合，放日志或 exemplar
⚖️ 06 · 方案取舍

埋点时控制标签

优点从源头解决，成本最低

代价需开发规范与代码审查

适用所有新指标

采集端 relabel 丢弃

优点无需改应用，快速止血

代价信息丢失，规则需维护

适用线上已出现基数爆炸

高维分析交给日志/链路

优点保留细粒度上下文

代价查询成本高，不适合告警

适用需要按用户排查问题

🕳️ 07 · 常见坑

  • ✗把原始 URL 作为标签，带 ID 的路径产生海量序列

    ✓使用框架的路由模板作为标签值

  • ✗把错误消息全文放进标签

    ✓用有限的错误类别或错误码作为标签

  • ✗在 Kubernetes 中以 Pod 名为维度长期聚合，发布后序列大量流失

    ✓告警与看板按服务或 Deployment 聚合

  • ✗直方图桶数过多且叠加多个标签

    ✓精简桶数量，减少直方图上的标签维度

☑️ 08 · 检查清单
🎤 09 · 面试追问
为什么不能把 user_id 当指标标签？

每个用户一个序列，序列数随用户量无界增长，时序库为每条活跃序列维护索引和内存，很快耗尽资源，查询也变慢，按序列计费的服务费用飙升。按用户分析应使用日志或链路数据。

如何估算一个指标的基数？

各标签可能取值数相乘，再乘以产生该指标的实例数。例如 20 个路由、4 种方法、5 类状态码、50 个 Pod 约为 2 万条序列；直方图还需乘以桶数加上 sum 与 count 序列。

指标、日志、链路在高维数据上怎么分工？

指标适合低基数、可聚合、用于告警和趋势的数据；日志和链路保留高维细节，如用户、请求 ID、参数，用于排查。通过 exemplar 或 trace ID 关联，从异常指标跳转到具体请求。
