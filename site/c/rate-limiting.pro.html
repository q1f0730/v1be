限流

Rate Limiting

📐 01 · 定义

限流（Rate Limiting）是在单位时间内限制某个主体（用户、IP、API Key、租户）可发起请求数的流量控制机制，超限请求被拒绝、排队或降级。它位于网关或应用中间件层，用于保护后端容量、防滥用与暴力破解、保证多租户公平，并支撑按套餐计量的商业模式。

⚙️ 02 · 原理
  1. 1

    请求到达时提取限流键，如 user_id、API Key 或客户端 IP，还可与接口路径组合成更细的维度。

  2. 2

    在共享存储（常用 Redis）中按算法更新计数或令牌，多实例共享同一状态。

  3. 3

    令牌桶按固定速率补充令牌，请求消耗令牌，允许一定突发；滑动窗口统计近期请求数。

  4. 4

    未超限则放行；超限返回 429 Too Many Requests，并附 Retry-After 提示等待时间。

  5. 5

    响应中可附带剩余额度等头部，客户端据此主动退避，减少无效请求。

🔤 03 · 术语
令牌桶 (Token Bucket)
按速率补令牌、按请求扣令牌，允许受控突发。
漏桶 (Leaky Bucket)
以恒定速率处理请求，平滑输出流量。
滑动窗口 (Sliding Window)
统计最近 N 秒请求数，避免固定窗口边界突刺。
429 Too Many Requests
RFC 6585 定义的限流状态码。
Retry-After
告诉客户端多久后可重试的响应头。
💻 04 · 代码
Redis 固定窗口限流python
import time
import redis

r = redis.Redis()

def allow(key: str, limit: int = 100, window: int = 60) -> tuple[bool, int]:
    """每 window 秒最多 limit 次；返回 (是否放行, 剩余次数)"""
    bucket = int(time.time()) // window
    rkey = f"rl:{key}:{bucket}"
    pipe = r.pipeline()
    pipe.incr(rkey)               # 原子自增
    pipe.expire(rkey, window)     # 窗口过期自动清理
    count, _ = pipe.execute()
    return count <= limit, max(0, limit - count)

# 在中间件中使用
ok, remaining = allow(f"user:{42}:POST:/v1/messages")
if not ok:
    # 返回 429，并告诉客户端何时重试
    status, headers = 429, {"Retry-After": "60"}

固定窗口实现最简单但边界处可能放过约两倍流量；要求更平滑时改用令牌桶或滑动窗口。

🕳️ 07 · 常见坑

  • ✗在代理之后直接取 remote_addr，所有人共用一个 IP

    ✓仅信任已知代理设置的 X-Forwarded-For 并正确解析

  • ✗INCR 与 EXPIRE 分开执行，进程崩溃留下永不过期的键

    ✓用 pipeline/MULTI 或 Lua 脚本保证原子性

  • ✗客户端收到 429 立即重试，形成重试风暴

    ✓客户端遵循 Retry-After，使用指数退避加随机抖动

  • ✗登录、验证码等敏感接口与普通接口共用宽松额度

    ✓对敏感接口单独设置更严格的限流键与阈值

🎤 09 · 面试追问
令牌桶和漏桶的区别？

令牌桶以固定速率积累令牌，桶满前可攒下额度，允许短时突发；漏桶以恒定速率流出请求，输出平滑但不允许突发。API 限流多用令牌桶，流量整形多用漏桶。

分布式限流如何保证准确？

把计数放在 Redis 等共享存储，用 Lua 脚本把读-判断-写合成原子操作；对精度要求不高时可本地预分配额度定期同步，以降低延迟与存储压力。

限流和熔断有什么区别？

限流是服务端控制进入系统的请求速率，保护自身容量；熔断是调用方在下游持续失败时暂停调用并快速失败，防止故障级联扩散。二者常配合使用。
