数据库索引

Indexes

📐 01 · 定义

数据库索引（Index）是为加速按特定列查找而额外维护的数据结构，最常见的是 B-tree（B 树），此外还有哈希、GIN、GiST 等类型。它属于数据库存储与查询优化层，以额外的存储空间和写入开销，换取查询从全表扫描变为对数级查找，是解决慢查询最常用的手段。

⚙️ 02 · 原理
  1. 1

    创建索引时，数据库按索引列的值排序构建 B-tree，叶子节点保存键值与行位置。

  2. 2

    查询时优化器根据统计信息评估成本，选择索引扫描、仅索引扫描或全表扫描。

  3. 3

    复合索引按列顺序排序，遵循最左前缀原则：(a, b) 可服务 a 或 a+b 条件，难以单独服务 b。

  4. 4

    每次 INSERT、UPDATE、DELETE 都需同步维护所有相关索引，索引越多写入越慢。

  5. 5

    通过 EXPLAIN ANALYZE 查看实际执行计划和耗时，验证索引是否被使用。

🔤 03 · 术语
B-tree
平衡多路搜索树，支持等值、范围查询和排序，默认索引类型。
复合索引 (Composite Index)
包含多列的索引，列顺序决定能服务的查询。
覆盖索引 (Covering Index)
索引包含查询所需全部列，无需回表读取。
选择性 (Selectivity)
列中不同值的比例，选择性越高索引越有效。
全表扫描 (Seq Scan)
逐行读取整张表，数据大时很慢。
💻 04 · 代码
用 EXPLAIN 验证索引sql
-- 慢查询：按用户查最近订单
EXPLAIN ANALYZE
SELECT id, amount, created_at FROM orders
WHERE user_id = 42
ORDER BY created_at DESC
LIMIT 20;
-- 无索引时计划通常为 Seq Scan + Sort

-- 复合索引：等值列在前，排序列在后
CREATE INDEX CONCURRENTLY idx_orders_user_created
  ON orders (user_id, created_at DESC);

-- 再次 EXPLAIN ANALYZE，计划应变为 Index Scan，且无需单独排序

-- 部分索引：只索引未完成订单，体积更小
CREATE INDEX idx_orders_pending ON orders (created_at)
  WHERE status = 'pending';

-- 查看未被使用的索引（PostgreSQL 统计视图）
SELECT indexrelname, idx_scan FROM pg_stat_user_indexes ORDER BY idx_scan;

PostgreSQL 语法；CONCURRENTLY 建索引不阻塞写入，但不能在事务块内执行。

⚖️ 06 · 方案取舍

为高频查询建精准复合索引

优点查询快，可覆盖排序

代价写入变慢、占空间

适用读多写少的热点查询

少建索引

优点写入快

代价查询可能全表扫描

适用写入密集的日志类表

部分索引/表达式索引

优点体积小、针对性强

代价查询条件必须匹配

适用只查询特定子集

🕳️ 07 · 常见坑

  • ✗给每一列都建单列索引

    ✓按实际查询模式建复合索引，删除无用索引

  • ✗在索引列上套函数，如 WHERE lower(email)=...

    ✓建立表达式索引或存储规范化后的值

  • ✗复合索引列顺序随意

    ✓等值条件列在前，范围和排序列在后

  • ✗生产大表直接 CREATE INDEX 锁表

    ✓PostgreSQL 使用 CREATE INDEX CONCURRENTLY

🎤 09 · 面试追问
为什么建了索引查询还是不走？

可能原因：条件选择性低，优化器认为全表扫描更便宜；在索引列上用了函数或隐式类型转换；复合索引没有满足最左前缀；使用前导通配符 LIKE '%x'；统计信息过时。应通过 EXPLAIN 和更新统计信息逐一排查。

复合索引的最左前缀原则是什么？

复合索引按第一列排序，第一列相同再按第二列排序。因此 (a, b, c) 能高效服务 a、a+b、a+b+c 的条件，而单独查 b 或 c 时，B-tree 无法利用顺序定位。设计时通常把等值过滤列放前面，范围或排序列放后面。

索引是不是越多越好？

不是。每个索引都占用存储，并在每次写入时需要维护，降低 INSERT、UPDATE 性能；过多索引也会增加优化器的选择负担。应根据真实查询模式建立少量精准的索引，并定期清理从未被使用的索引。
