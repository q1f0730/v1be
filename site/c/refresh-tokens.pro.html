刷新令牌

Refresh Tokens

📐 01 · 定义

刷新令牌（Refresh Token）是授权服务器签发的长期凭证，仅用于向令牌端点换取新的短期访问令牌（Access Token），而不直接访问资源。它由 OAuth 2.0（RFC 6749）定义，用来兼顾安全与体验：访问令牌短命以缩小泄露窗口，刷新令牌让用户免于频繁重新登录，因此需要更严格的存储与保护。

⚙️ 02 · 原理
  1. 1

    用户登录或授权成功后，授权服务器同时返回短期访问令牌和长期刷新令牌。

  2. 2

    客户端用访问令牌调用 API；访问令牌过期后，向令牌端点提交刷新令牌。

  3. 3

    服务器校验刷新令牌（是否存在、未过期、未吊销、属于该客户端），签发新的访问令牌。

  4. 4

    启用轮换（Rotation）时同时签发新刷新令牌并作废旧的；旧令牌被再次使用即视为泄露。

  5. 5

    检测到重用时吊销该令牌族下的全部刷新令牌，强制合法用户与攻击者都重新登录。

🔤 03 · 术语
刷新令牌轮换 (Rotation)
每次刷新都签发新刷新令牌并使旧令牌失效。
重用检测 (Reuse Detection)
已作废的刷新令牌再次出现时判定泄露并吊销整个令牌族。
令牌族 (Token Family)
由同一次登录衍生出的一串刷新令牌。
发送者约束 (Sender-Constrained)
令牌绑定客户端密钥，如 DPoP、mTLS，被盗也难使用。
滑动过期 (Sliding Expiration)
每次使用延长有效期，但通常仍设绝对上限。
💻 04 · 代码
刷新令牌轮换与重用检测python
import secrets, hashlib, datetime as dt

def _h(t): return hashlib.sha256(t.encode()).hexdigest()   # 只存哈希

def issue_refresh(db, user_id, family_id=None):
    token = secrets.token_urlsafe(32)
    db.insert("refresh_tokens", token_hash=_h(token), user_id=user_id,
              family_id=family_id or secrets.token_hex(8), used=False,
              expires_at=dt.datetime.utcnow() + dt.timedelta(days=30))
    return token

def refresh(db, token):
    row = db.find_one("refresh_tokens", token_hash=_h(token))
    if row is None or row.expires_at < dt.datetime.utcnow():
        raise PermissionError("invalid")
    if row.used:                                  # 旧令牌被重放：判定泄露
        db.revoke_family(row.family_id)
        raise PermissionError("reuse detected")
    db.mark_used(row.id)                          # 作废旧令牌
    new_rt = issue_refresh(db, row.user_id, row.family_id)
    access = make_access_token(row.user_id)       # 签发短期访问令牌
    return access, new_rt

db 与 make_access_token 为示意接口；要点是哈希存储、一次性使用与令牌族吊销。

📊 05 · 参数对比

访问令牌 vs 刷新令牌

维度访问令牌刷新令牌
用途调用资源 API换取新访问令牌
有效期短（分钟到小时）长（天到周，需上限）
发送对象资源服务器仅授权服务器令牌端点
撤销方式通常等待过期服务端可随时吊销
⚖️ 06 · 方案取舍

刷新令牌轮换 + 重用检测

优点能发现令牌被盗

代价并发刷新需处理竞态

适用浏览器与移动端公共客户端

不轮换的长期刷新令牌

优点实现简单

代价被盗后长期可用

适用安全存储的机密客户端

发送者约束令牌

优点令牌被盗也难以使用

代价实现复杂，支持有限

适用金融等高安全场景

🕳️ 07 · 常见坑

  • ✗刷新令牌明文存于数据库

    ✓只存哈希值，比对时哈希后查询

  • ✗浏览器中把刷新令牌放 localStorage

    ✓用 HttpOnly、Secure Cookie 或 BFF 模式在服务端保管

  • ✗多个标签页并发刷新触发误判重用

    ✓客户端串行刷新，或服务端设置短暂宽限期

  • ✗用户改密、登出后刷新令牌仍有效

    ✓这些事件触发时吊销该用户全部刷新令牌

🎤 09 · 面试追问
为什么需要刷新令牌，而不是直接用长期访问令牌？

访问令牌频繁发送给各资源服务器，暴露面大，且通常无状态难以撤销，所以应短命。刷新令牌只发往授权服务器、可在服务端吊销，保护更集中。两者组合既缩小了泄露窗口，又避免用户频繁重新登录。

刷新令牌轮换如何发现令牌被盗？

每个刷新令牌只能使用一次。若攻击者和合法用户先后使用同一个令牌，第二次使用的必定是已作废的令牌，服务器据此判定泄露，吊销整个令牌族，双方都需重新登录，攻击者因此失去访问权。

SPA 应该如何保存刷新令牌？

浏览器环境中任何 JS 可读的存储都可能被 XSS 窃取。推荐 BFF（Backend for Frontend）模式，由同域后端保管令牌，前端只持有 HttpOnly 会话 Cookie；若必须在前端处理，则启用轮换并设置较短的绝对有效期。
