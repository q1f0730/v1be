B+ 树与 LSM 树

B+Tree vs LSM-Tree

📐 01 · 定义

B+ 树与 LSM 树（Log-Structured Merge-Tree）是两类主流存储引擎索引结构。B+ 树原地更新有序页，读取路径短而稳定，代表为 InnoDB、PostgreSQL 索引；LSM 树先把写入缓冲在内存，再顺序刷成不可变有序文件并后台合并，写吞吐高，代表为 RocksDB、Cassandra。选型本质是在读放大、写放大和空间放大之间取舍。

⚙️ 02 · 原理
  1. 1

    B+ 树：数据按键有序存放在固定大小的页中，内部节点只存键与指针，叶子节点相互链接，便于范围扫描。

  2. 2

    B+ 树写入需定位叶子页原地修改，页满则分裂；配合 WAL 保证崩溃一致，随机写较多。

  3. 3

    LSM 树：写入先追加 WAL，再写入内存表（memtable）；内存表满后整体刷成磁盘上的有序文件（SSTable）。

  4. 4

    LSM 读取需依次查内存表和多层 SSTable，通常借助每个文件的布隆过滤器跳过不含该键的文件。

  5. 5

    LSM 后台合并（compaction）把多层文件归并，丢弃被覆盖的旧值与删除标记（tombstone），回收空间并控制读放大。

🔤 03 · 术语
写放大 (Write Amplification)
实际写入存储的数据量与用户写入数据量之比。
读放大 (Read Amplification)
完成一次查询需要读取的页或文件数量。
SSTable
按键排序且写入后不可变的磁盘文件，是 LSM 树的基本存储单元。
分层/分级合并 (Leveled/Tiered)
两种 compaction 策略，前者读与空间更优，后者写放大更低。
墓碑 (Tombstone)
LSM 中表示删除的标记，合并到最底层前不能丢弃。
填充因子 (Fill Factor)
B 树页预留空间比例，影响页分裂频率与空间利用率。
💻 04 · 代码
极简 LSM 写读路径python
import bisect
class TinyLSM:
    """教学示例：内存表 + 不可变有序段，省略 WAL 与布隆过滤器"""
    def __init__(self, limit=3):
        self.mem, self.segments, self.limit = {}, [], limit
    def put(self, k, v):            # 删除可用 v=None 作为墓碑
        self.mem[k] = v
        if len(self.mem) >= self.limit:
            self.segments.append(sorted(self.mem.items()))  # 刷成有序段
            self.mem = {}
    def get(self, k):
        if k in self.mem:
            return self.mem[k]
        for seg in reversed(self.segments):        # 新段优先
            i = bisect.bisect_left(seg, (k,))
            if i < len(seg) and seg[i][0] == k:
                return seg[i][1]
        return None
    def compact(self):              # 合并所有段，新值覆盖旧值，丢弃墓碑
        merged = {}
        for seg in self.segments:
            merged.update(seg)
        self.segments = [sorted((k, v) for k, v in merged.items() if v is not None)]
db = TinyLSM()
for i in range(7):
    db.put(f"k{i}", i)
db.put("k1", None)
db.put("k2", 20)
print(db.get("k2"), len(db.segments))   # 20 3

可见读要查多个段（读放大），合并会重写数据（写放大），这正是 LSM 的核心取舍。

📊 05 · 参数对比

B+ 树与 LSM 树对比

维度B+ 树LSM 树
写入模式原地更新，随机写多追加与顺序刷盘
点查路径固定、延迟稳定可能查多层，依赖布隆过滤器
范围扫描叶子链表，效率高需多路归并
空间页内有碎片合并前存在冗余旧值
性能抖动页分裂后台合并占用 IO 与 CPU
⚖️ 06 · 方案取舍

B+ 树引擎

优点读延迟稳定，事务与范围查询成熟

代价高写入下随机 IO 与页分裂开销大

适用读多写少、OLTP 通用业务

LSM 分层合并

优点写吞吐高，空间与读放大较可控

代价合并写放大较高

适用写多且仍有大量点查

LSM 分级合并

优点写放大最低

代价空间放大和读放大较高

适用写入极多、读取较少，如时序与日志

🕳️ 07 · 常见坑

  • ✗LSM 引擎合并跟不上写入，触发写入降速

    ✓监控待合并量，预留 IO 余量，调整合并线程与策略

  • ✗大量删除后空间不回收、范围扫描变慢

    ✓理解墓碑需合并到底层才清除，必要时手动触发范围合并

  • ✗B+ 树主键用随机 UUID 导致频繁页分裂

    ✓使用有序 ID（如 UUIDv7、自增）减少随机插入

  • ✗只看基准写吞吐就选 LSM

    ✓按真实读写比例、点查与范围查询分布压测

🎤 09 · 面试追问
为什么 LSM 树写入快？

写入只做 WAL 追加和内存表插入，内存表满后整体顺序写成有序文件，避免了 B+ 树定位叶子页后的随机写。代价是后台合并会多次重写数据（写放大），读取可能查多个文件（读放大）。

布隆过滤器在 LSM 中起什么作用？

每个 SSTable 附带布隆过滤器，点查时先判断键是否可能在该文件中。结果为「不存在」时一定不在，可直接跳过读盘，显著降低读放大。它对范围查询帮助不大，前缀布隆过滤器可部分缓解。

什么是 RUM 猜想，它如何指导选型？

RUM 猜想认为读开销（Read）、更新开销（Update）和内存或空间开销（Memory）三者不能同时最优，优化其二必然牺牲第三。B+ 树偏读，LSM 偏写，不同合并策略在写放大与空间放大间移动，选型要先明确主要瓶颈。
