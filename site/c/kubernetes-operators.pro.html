K8s Operator 模式

Kubernetes Operators

📐 01 · 定义

Operator 是 Kubernetes 的扩展模式：用自定义资源（CRD）描述某类应用的期望状态，再用自定义控制器持续调和（reconcile），把部署、扩容、备份、升级、故障恢复等运维知识编码为程序。它让数据库、消息队列等有状态复杂软件也能像 Deployment 一样被声明式管理。

⚙️ 02 · 原理
  1. 1

    定义 CRD，向 API Server 注册新的资源类型，如 PostgreSQL 集群，包含 spec（期望）与 status（现状）。

  2. 2

    控制器通过 informer 监听自定义资源及其关联对象的变化，把对象键放入工作队列。

  3. 3

    Reconcile 函数读取当前状态并与 spec 比较，创建或修改 StatefulSet、Service、Secret 等子资源，使现实趋近期望。

  4. 4

    调和是电平触发且必须幂等：无论触发几次、从何种中间状态开始，结果都应一致；失败则带退避重新入队。

  5. 5

    通过 ownerReferences 让子资源随父资源被垃圾回收，用 finalizer 在删除前执行清理（如删除外部备份）。

🔤 03 · 术语
自定义资源定义 (CRD)
向 Kubernetes API 注册新资源类型的方式，可带 OpenAPI 校验。
调和循环 (Reconcile Loop)
不断比较期望与实际状态并采取动作消除差异的控制逻辑。
电平触发 (Level-triggered)
根据当前完整状态决策，而不是依赖单个事件，丢事件也能自愈。
Finalizer
对象删除前必须被移除的标记，控制器借此完成外部资源清理。
Kubebuilder / Operator SDK
构建 Operator 的主流 Go 框架，基于 controller-runtime。
💻 04 · 代码
用 CloudNativePG 声明集群yaml
# 前提：已安装 CloudNativePG Operator
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: app-db
  namespace: prod
spec:
  instances: 3               # 1 主 2 备，Operator 负责复制与故障切换
  storage:
    size: 20Gi
  resources:
    requests:
      cpu: "1"
      memory: 2Gi
    limits:
      memory: 2Gi
  bootstrap:
    initdb:
      database: app
      owner: app
# kubectl apply -f app-db.yaml
# kubectl get cluster -n prod app-db   # 查看 Operator 汇报的状态

用户只写期望状态；创建 Pod、配置复制、主库故障后提升备库都由 Operator 调和完成。字段以官方文档为准。

📊 05 · 参数对比

扩展 Kubernetes 的方式

方式能做什么复杂度
Helm Chart模板化安装一组资源低，无运行期逻辑
Operator持续管理生命周期与故障恢复高，需要开发与维护控制器
准入 Webhook创建/修改资源时校验或改写中
聚合 API Server提供全新 API 后端很高，少数场景使用
⚖️ 06 · 方案取舍

使用成熟社区 Operator

优点沉淀了大量运维经验，开箱即用

代价升级与行为受上游约束

适用数据库、消息队列等通用中间件

自研 Operator

优点精确编码自家运维流程

代价开发与长期维护成本高，Bug 影响面大

适用内部平台有重复且复杂的运维模式

托管云服务

优点无需运维控制器与存储

代价成本较高，可定制性低

适用团队小、追求稳定

🕳️ 07 · 常见坑

  • ✗Reconcile 依赖事件类型做增量处理

    ✓每次都读取完整当前状态做决策，保证幂等与自愈

  • ✗在 Reconcile 中频繁更新 status 触发自身无限循环

    ✓仅在状态真正变化时更新，并使用 status 子资源与 generation 判断

  • ✗删除时未处理外部资源，留下孤儿云盘或备份

    ✓使用 finalizer 清理外部资源后再放行删除

  • ✗Operator 拥有集群级管理员权限

    ✓按需授予最小 RBAC，限定命名空间与资源类型

🎤 09 · 面试追问
为什么 Operator 必须是电平触发而非边沿触发？

事件可能丢失、重复或乱序，控制器也可能重启。若只按单个事件增量处理，状态会漂移。电平触发每次比较完整的期望与实际状态再行动，任何时刻重新运行都能收敛，这也要求操作幂等。

什么时候不该写 Operator？

若只是安装一组静态资源，Helm 或 Kustomize 就够；若运维动作很少、靠人偶尔执行即可，控制器的开发与维护成本不划算；有成熟社区 Operator 或托管服务时优先复用。Operator 适合需要持续自动化、复杂且重复的生命周期管理。

finalizer 的作用和风险？

它让对象删除被挂起，直到控制器完成清理并移除标记，用于删除云资源、备份等外部依赖。风险是控制器故障时 finalizer 永远不被移除，对象卡在 Terminating，命名空间也删不掉，需要监控并有人工处理流程。
