真实执行计划剖析

EXPLAIN ANALYZE

🧸 回到小白版
📐定义⚙️原理🔤术语💻代码📊参数对比⚖️方案取舍🕳️常见坑☑️检查清单🎤面试追问🔗延伸阅读
📐 01 · 定义

EXPLAIN ANALYZE 是关系型数据库的执行计划剖析命令：它真正执行 SQL，并在计划树的每个节点上报告实际行数、循环次数和耗时（PostgreSQL 还可附带缓冲区命中）。与只给估算的 EXPLAIN 不同，它能暴露估算偏差、全表扫描和低效连接，是查询调优的第一手证据。

⚙️ 02 · 原理
  1. 1

    优化器根据统计信息生成多个候选计划，选总代价（cost）最低的一个执行。

  2. 2

    ANALYZE 选项让数据库真实执行该计划，并对每个节点计时、计数。

  3. 3

    输出为树形结构，自底向上读：叶子是扫描节点，上层是连接、排序、聚合。

  4. 4

    每个节点对比估算 rows 与实际 rows，偏差数量级大说明统计信息过期或谓词相关性未被建模。

  5. 5

    加 BUFFERS 可看到 shared hit（内存命中）与 read（磁盘读），判断瓶颈在 IO 还是 CPU。

🔤 03 · 术语
执行计划 (Query Plan)
优化器决定的扫描方式、连接顺序与算法组成的树。
代价估算 (Cost)
优化器内部的相对代价单位，不等于毫秒。
Seq Scan / Index Scan
顺序全表扫描与按索引访问两种扫描节点。
Nested Loop / Hash Join
嵌套循环连接与哈希连接，适用于不同数据规模。
loops
节点被执行的次数，实际总行数 ≈ rows × loops。
统计信息 (Statistics)
ANALYZE 采集的列分布数据，决定估算准确度。
💻 04 · 代码
PostgreSQL 剖析慢查询sql
-- EXPLAIN ANALYZE 会真正执行语句；写操作务必包在事务里回滚
BEGIN;

EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id, o.total
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE c.country = 'CN'
  AND o.created_at >= now() - interval '7 days'
ORDER BY o.created_at DESC
LIMIT 50;

ROLLBACK;

-- 读输出时重点看：
--  1. rows=估算 vs actual rows=实际，差距是否达到数量级
--  2. 哪个节点 actual time 最大（时间是包含子节点的累计值）
--  3. Seq Scan 是否出现在大表上，Rows Removed by Filter 是否很多
--  4. Buffers: shared read 多说明大量走磁盘

-- 估算偏差大时，先刷新统计信息再看
ANALYZE orders;

先找耗时最大、估算偏差最大的节点；BUFFERS 区分内存命中与磁盘读取。

⚖️ 06 · 方案取舍

EXPLAIN（仅估算）

优点不执行，安全、瞬间返回

代价看不到真实行数与耗时

适用生产上查看长查询的计划

EXPLAIN ANALYZE

优点真实耗时与行数，证据充分

代价会执行语句，有计时开销

适用副本或预发环境调优

auto_explain / 慢日志

优点自动捕获线上真实慢查询

代价有性能开销，需控制阈值

适用排查偶发慢查询

🕳️ 07 · 常见坑

  • ✗对 UPDATE/DELETE 直接 EXPLAIN ANALYZE

    ✓包在 BEGIN … ROLLBACK 中，或只在副本执行

  • ✗把 cost 数值当成毫秒比较

    ✓cost 是相对单位，看 actual time 判断耗时

  • ✗只看总时间，不看 loops

    ✓节点时间按每次循环给出，需乘 loops

  • ✗在空测试库上调优，结论不适用生产

    ✓用接近生产的数据量和分布验证

☑️ 08 · 检查清单
🎤 09 · 面试追问
估算行数严重偏差会导致什么？

优化器基于错误基数选择计划，例如以为只有几行而选 Nested Loop，实际上万行导致内层循环爆炸；或以为很多行放弃索引。修复从 ANALYZE 刷新统计、提高统计目标、建立多列扩展统计入手。

为什么建了索引却仍是 Seq Scan？

可能是谓词选择性低，全表扫更便宜；对列用了函数或隐式类型转换导致索引不可用；统计信息过期；或表本身很小。用 EXPLAIN ANALYZE 比较实际耗时，确认是否真的更慢。

MySQL 有 EXPLAIN ANALYZE 吗？

有。MySQL 8.0.18 起支持 EXPLAIN ANALYZE，以树形格式输出每个迭代器的实际耗时与行数，同样会真正执行查询。更早版本只能用 EXPLAIN 与 optimizer trace 等手段。
