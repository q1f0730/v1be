可用区 (AZ)

Availability Zones

📐 01 · 定义

可用区（Availability Zone, AZ）是云厂商在同一地理区域（Region）内划分的、拥有独立供电、制冷和网络的一个或多个数据中心集合。可用区之间通过低延迟专线互联，但故障相互隔离。它是云基础设施的故障域单位：把实例和数据分布到多个可用区，可以在单个机房级故障时保持服务可用。

⚙️ 02 · 原理
  1. 1

    一个区域包含多个可用区，各可用区物理隔离，降低火灾、断电等同时影响多个可用区的概率。

  2. 2

    可用区之间有高带宽、低延迟网络，适合同步复制和跨区负载均衡。

  3. 3

    应用把副本分布在多个可用区，负载均衡器跨区分发流量并剔除故障区的后端。

  4. 4

    托管数据库的多可用区部署在另一可用区维护备库，主库故障时自动切换。

  5. 5

    容量规划按失去任意一个可用区后，剩余可用区仍能承载峰值流量来确定副本数。

🔤 03 · 术语
区域 (Region)
云厂商的独立地理区域，包含多个可用区。
多可用区部署 (Multi-AZ)
把同一服务的副本放到多个可用区以容忍单区故障。
拓扑分布约束 (Topology Spread Constraints)
Kubernetes 中让 Pod 按区域等拓扑均匀分布的调度规则。
跨区流量费 (Inter-AZ Data Transfer)
部分云厂商对可用区之间的数据传输计费。
静态稳定性 (Static Stability)
某个可用区故障时，无需临时扩容或变更也能继续工作。
💻 04 · 代码
Pod 跨可用区均匀分布yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: api }
spec:
  replicas: 6
  selector: { matchLabels: { app: api } }
  template:
    metadata: { labels: { app: api } }
    spec:
      topologySpreadConstraints:
        - maxSkew: 1                               # 各区副本数最多差 1
          topologyKey: topology.kubernetes.io/zone # 按可用区分布
          whenUnsatisfiable: DoNotSchedule
          labelSelector: { matchLabels: { app: api } }
      containers:
        - name: api
          image: example/api:1.0

用拓扑分布约束把 6 个副本均匀放到各可用区，单区故障时仍有其余副本。

⚖️ 06 · 方案取舍

单可用区

优点延迟最低，无跨区费用

代价机房级故障即全停

适用开发测试、可中断的批处理

多可用区

优点容忍单区故障，成本适中

代价跨区流量费、部署更复杂

适用生产服务的基本要求

多区域

优点容忍区域级故障

代价成本高，数据一致性难

适用关键业务或合规要求

🕳️ 07 · 常见坑

  • ✗副本数为 3 但调度后全在一个可用区。

    ✓配置拓扑分布约束或反亲和，并在部署后核查。

  • ✗应用多可用区，但数据库或 NAT 网关只在一个可用区。

    ✓逐个检查依赖组件的可用区分布。

  • ✗两个区各承载 50% 峰值，一个区故障后另一个被压垮。

    ✓按 N-1 可用区仍能承载峰值来规划容量。

🎤 09 · 面试追问
为什么多可用区不等于高可用？

还要看所有依赖是否同样跨区、容量是否足以承载失去一个区后的流量、故障检测与切换是否自动可靠，以及是否存在共享的控制面依赖。任何一环单区部署都会成为单点。

什么是静态稳定性？

系统在某个可用区故障时，不需要依赖控制面去临时启动新资源或修改配置就能继续服务，例如提前在每个区预置足够容量。因为故障期间控制面本身也可能不可用。

跨可用区同步复制有什么代价？

每次写入都要等待另一个区确认，增加写延迟；还会产生跨区数据传输费用；备区故障时可能影响主库写入，需要设计降级为异步的策略。
