HTTP长轮询

Long Polling

📐 01 · 定义

长轮询（Long Polling）是用普通 HTTP 模拟服务端推送的技术：客户端发出请求后，服务端在有新数据或超时之前不返回响应；客户端收到响应后立刻发起下一次请求。它无需特殊协议，兼容性最好，但每条消息都要一次完整请求往返，连接与资源开销较大。

⚙️ 02 · 原理
  1. 1

    客户端带上游标（上次收到的最后一条消息 ID）发起普通 HTTP 请求。

  2. 2

    服务端若已有游标之后的新数据，立即返回；否则把请求挂起等待。

  3. 3

    有新消息时唤醒挂起的请求并返回；等待超过时限则返回空响应（如 204）。

  4. 4

    客户端处理结果、更新游标后立刻发起下一轮请求，出错时退避重试。

  5. 5

    游标保证两次请求之间的空档期内产生的消息，在下一轮请求时被补发而不丢失。

🔤 03 · 术语
短轮询 (Short Polling)
固定间隔请求，无论有无数据立即返回。
挂起请求 (Hanging Request)
服务端暂不响应、保持打开的请求。
游标 (Cursor)
标记客户端已接收位置的 ID 或时间戳。
轮询超时 (Poll Timeout)
服务端最长挂起时间，需小于各层代理超时。
惊群 (Thundering Herd)
大量挂起请求同时被唤醒、同时重连。
💻 04 · 代码
带游标的长轮询javascript
// 服务端（Express）：有新消息立即返回，否则最多挂起 25 秒
const messages = [];           // 示例用内存，生产用数据库或 Redis
const waiters = new Set();

app.get('/poll', (req, res) => {
  const since = Number(req.query.since ?? 0);
  const fresh = messages.filter((m) => m.id > since);
  if (fresh.length) return res.json(fresh);

  const done = (msg) => { clearTimeout(timer); waiters.delete(done); res.json([msg]); };
  const timer = setTimeout(() => { waiters.delete(done); res.status(204).end(); }, 25_000);
  waiters.add(done);
  req.on('close', () => { clearTimeout(timer); waiters.delete(done); });
});

function publish(text) {
  const msg = { id: messages.length + 1, text };
  messages.push(msg);
  for (const w of [...waiters]) w(msg);
}

// 客户端：收到响应立刻发下一轮，出错时等待后重试
async function poll(since = 0) {
  for (;;) {
    try {
      const r = await fetch(`/poll?since=${since}`);
      if (r.status === 200) { const msgs = await r.json(); since = msgs.at(-1).id; render(msgs); }
    } catch { await new Promise((ok) => setTimeout(ok, 2000)); }
  }
}

游标防止请求间隙丢消息；挂起时限要短于代理与负载均衡的超时。

⚖️ 06 · 方案取舍

长轮询

优点纯 HTTP，穿透企业代理最稳

代价请求头开销大，挂起占资源

适用兼容兜底或低频推送

SSE

优点单连接持续推送，自动重连

代价单向，部分代理需配置

适用服务端单向推送

短轮询

优点实现最简单，易缓存

代价延迟与空请求浪费

适用数据分钟级变化

🕳️ 07 · 常见坑

  • ✗挂起 60 秒，被负载均衡 60 秒空闲超时切断

    ✓挂起时长设为明显小于各层超时，如 20–30 秒

  • ✗不带游标，两次请求之间的消息丢失

    ✓请求带上最后收到的 ID，服务端补发

  • ✗同步阻塞式服务器每个挂起请求占一个线程

    ✓使用异步 IO 框架承载挂起连接

  • ✗服务端故障时客户端立即疯狂重试

    ✓错误时指数退避并加随机抖动

🎤 09 · 面试追问
长轮询和短轮询的本质区别？

短轮询无论是否有数据都立即返回，客户端按固定间隔重复请求，延迟取决于间隔且大量请求为空。长轮询在没有数据时挂起请求，数据一到即返回，延迟接近实时，空请求只在超时时出现。

长轮询如何在多实例部署下工作？

请求可能落在任意实例，因此消息不能只存在某实例内存中。需把消息写入共享存储（数据库、Redis），并通过 Pub/Sub 通知各实例唤醒挂起的请求；游标基于全局递增 ID。

现在还有理由用长轮询吗？

有。某些企业代理或老旧网络环境会阻断 WebSocket 或缓冲流式响应，长轮询最可靠；Telegram Bot API 的 getUpdates 就采用长轮询。Socket.IO 等库也把它作为降级传输。
