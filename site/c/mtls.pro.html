双向 TLS (mTLS)

mTLS

📐 01 · 定义

双向 TLS（mTLS）是在标准 TLS 基础上要求客户端也出示证书、双方相互验证身份的连接方式。普通 HTTPS 只验证服务器，mTLS 让服务端在握手阶段即可确认调用方是哪个服务或设备。它是服务间零信任通信、服务网格、物联网设备接入和高安全 API 的常用机制，通常配合私有 CA 与短期证书自动轮换。

⚙️ 02 · 原理
  1. 1

    组织建立私有 CA，为每个服务或设备签发证书，证书中的主体或 SAN 字段承载其身份（如 SPIFFE ID）。

  2. 2

    握手时服务端发送证书并请求客户端证书（TLS 1.3 中为 CertificateRequest 消息）。

  3. 3

    客户端校验服务端证书链与主机名，再发送自己的证书并用私钥签名握手内容证明持有私钥。

  4. 4

    服务端校验客户端证书链、有效期与吊销状态，提取身份后交给授权层判断该身份能否访问目标资源。

  5. 5

    服务网格或 SPIRE 等系统自动签发短期证书并轮换，应用通常无需改代码即可获得 mTLS。

🔤 03 · 术语
私有 CA (Private CA)
组织内部的证书颁发机构，用于签发服务与设备证书。
SPIFFE ID
形如 spiffe://域/路径 的工作负载身份标识，常写入证书的 URI SAN。
SVID
SPIFFE 可验证身份文档，常见形式为 X.509 证书。
证书轮换 (Rotation)
在证书过期前自动更换新证书，短期证书可减少吊销需求。
PeerAuthentication
Istio 中配置服务间 mTLS 模式（如 STRICT）的资源。
💻 04 · 代码
本地搭建 mTLS 并验证bash
# 1) 私有 CA
openssl req -x509 -newkey rsa:2048 -nodes -keyout ca.key -out ca.crt \
  -days 365 -subj "/CN=demo-ca"

# 2) 用 CA 签发服务端（localhost）与客户端（orders-service）证书
for n in server client; do
  cn=$([ $n = server ] && echo localhost || echo orders-service)
  openssl req -newkey rsa:2048 -nodes -keyout $n.key -out $n.csr -subj "/CN=$cn"
  openssl x509 -req -in $n.csr -CA ca.crt -CAkey ca.key -CAcreateserial \
    -out $n.crt -days 30 -extfile <(printf "subjectAltName=DNS:$cn")
done

# 3) 要求客户端证书的测试服务（-Verify 表示必须提供客户端证书）
openssl s_server -accept 8443 -cert server.crt -key server.key \
  -CAfile ca.crt -Verify 1 -www &
sleep 1

# 4) 带证书访问成功；不带证书握手失败
curl --cacert ca.crt --cert client.crt --key client.key https://localhost:8443/ -o /dev/null -w '%{http_code}\n'
curl --cacert ca.crt https://localhost:8443/ || echo "无客户端证书：被拒绝"
kill %1

仅用于学习；生产中应由服务网格或 SPIRE、cert-manager 自动签发短期证书并轮换。

📊 05 · 参数对比

服务间身份认证方式对比

方式身份载体优点缺点
mTLSX.509 证书传输层强认证并加密证书生命周期管理复杂
API Key共享密钥字符串简单易泄露、难轮换、无法证明调用方
JWT / OAuth 客户端凭证签名令牌可携带权限声明仍需 TLS 保护传输
服务网格自动 mTLS网格签发的工作负载证书对应用透明、自动轮换需要运维服务网格
⚖️ 06 · 方案取舍

服务网格自动 mTLS

优点零代码改动，统一策略与轮换

代价增加 sidecar 或节点代理开销

适用Kubernetes 上的大量微服务

应用内直接配置 mTLS

优点不依赖额外基础设施

代价每种语言都要处理证书加载与轮换

适用服务少或跨环境的点对点集成

网关终止 mTLS

优点集中管理外部客户端证书

代价网关到后端需另行保护

适用对外 B2B 或设备接入 API

🕳️ 07 · 常见坑

  • ✗证书有效期很长且没有自动轮换

    ✓使用短期证书与自动化签发，监控到期时间

  • ✗认为通过 mTLS 就等于有访问权限

    ✓认证之后仍需基于身份的授权策略

  • ✗迁移时直接开启严格模式，未改造的服务全部中断

    ✓先用宽松模式兼容明文，确认全部就绪再切严格

  • ✗客户端关闭证书校验以绕过报错

    ✓正确配置 CA 信任链，禁止跳过校验

🎤 09 · 面试追问
mTLS 握手比普通 TLS 多了什么？

服务端在握手中发送证书请求，客户端除校验服务端证书外，还要发送自己的证书链，并用私钥对握手记录签名以证明持有私钥；服务端校验链、有效期与吊销状态后才完成握手。这让身份认证在任何应用数据传输前完成。

为什么服务网格普遍采用短期证书？

证书吊销检查在分布式环境中难以可靠实施。把证书有效期缩短到小时或天级并自动轮换，即使私钥泄露，可被利用的窗口也很短，基本无需依赖吊销列表，同时避免人工续期导致的过期事故。

mTLS 和零信任的关系？

零信任要求每次访问都验证身份而不信任网络位置。mTLS 为服务间通信提供基于加密证明的工作负载身份与加密通道，是零信任在服务层的关键构件；但还需要授权策略、设备与用户身份、持续监控共同组成完整体系。
