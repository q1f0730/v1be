预写日志 (WAL)

Write-Ahead Log

📐 01 · 定义

预写日志（WAL）是数据库保证持久性与原子性的核心机制：任何数据页修改在写入数据文件之前，先把描述该修改的日志记录顺序写入并刷到持久存储。崩溃后通过重放日志恢复到一致状态。WAL 同时是物理复制、逻辑解码（CDC）和时间点恢复（PITR）的基础。

⚙️ 02 · 原理
  1. 1

    事务修改内存中的数据页，同时生成 WAL 记录并分配单调递增的日志序列号（LSN）。

  2. 2

    提交时只需把 WAL 刷盘（fsync），脏数据页可稍后由后台进程写回，顺序写日志比随机写数据页更快。

  3. 3

    检查点定期把脏页写回数据文件并记录位置，崩溃恢复只需从最近检查点开始重放。

  4. 4

    崩溃后数据库从检查点读取 WAL 依次重做（redo），确保已提交事务不丢、未完成事务不生效。

  5. 5

    备库持续接收并重放主库 WAL 实现物理复制；归档 WAL 加基础备份可恢复到任意时间点。

🔤 03 · 术语
LSN (Log Sequence Number)
WAL 中的字节位置，用来比较日志进度与复制延迟。
检查点 (Checkpoint)
保证此前所有修改已写入数据文件的点，限定恢复需要重放的范围。
整页写 (Full Page Writes)
检查点后页面首次修改时写入整页镜像，防止部分写导致页损坏。
复制槽 (Replication Slot)
PostgreSQL 为消费者保留其尚未读取的 WAL，避免被提前回收。
synchronous_commit
PostgreSQL 参数，控制提交返回前是否等待本地或备库 WAL 落盘。
💻 04 · 代码
检查 WAL 与复制槽占用sql
-- 当前 WAL 写入位置与 WAL 级别
SELECT pg_current_wal_lsn();
SHOW wal_level;           -- replica / logical
SHOW synchronous_commit;

-- 复制槽为消费者保留了多少 WAL：不活跃的槽会让磁盘持续增长
SELECT slot_name, slot_type, active,
       pg_size_pretty(
         pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)
       ) AS retained_wal
FROM pg_replication_slots;

-- 备库延迟（在主库执行）
SELECT client_addr, state,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)) AS replay_lag
FROM pg_stat_replication;

-- PostgreSQL 13+ 可用 max_slot_wal_keep_size 限制单个槽保留的 WAL
-- 不再需要的槽：SELECT pg_drop_replication_slot('slot_name');

废弃的 CDC 或备库复制槽是 WAL 撑满磁盘的常见原因，应纳入监控告警。

📊 05 · 参数对比

WAL 相关的持久性取舍

设置效果风险
fsync=on（默认）提交时 WAL 真正落盘无，生产必须开启
synchronous_commit=off提交不等 WAL 刷盘，延迟更低崩溃可能丢最近少量已提交事务
同步复制提交等待备库确认备库故障会阻塞写入
full_page_writes=on防止页部分写损坏检查点后 WAL 量增加
⚖️ 06 · 方案取舍

严格持久（同步刷盘）

优点已确认提交绝不丢失

代价每次提交受磁盘刷新延迟限制

适用交易、账务等核心数据

异步提交

优点写延迟显著降低，吞吐更高

代价崩溃窗口内可能丢少量事务，但不会损坏数据

适用日志、埋点等可容忍少量丢失

同步复制到备库

优点主库宕机也不丢已提交事务

代价写延迟增加网络往返

适用要求 RPO 为零的系统

🕳️ 07 · 常见坑

  • ✗用 fsync=off 换取性能

    ✓保持 fsync 开启；需要低延迟时评估 synchronous_commit=off

  • ✗复制槽的消费者下线后无人清理

    ✓监控 retained_wal 与 active 状态，设置 max_slot_wal_keep_size

  • ✗只做数据目录快照，不归档 WAL

    ✓基础备份加持续 WAL 归档，才能做时间点恢复

  • ✗检查点过于频繁导致 WAL 与 IO 激增

    ✓按写入量调整 max_wal_size 与 checkpoint_timeout

☑️ 08 · 检查清单
🎤 09 · 面试追问
为什么先写日志再写数据页能提升性能？

WAL 是顺序追加写，数据页修改是分散的随机写。提交时只需把较小的日志顺序刷盘，数据页可以批量、延迟写回，多次修改同一页还能合并。崩溃时用日志重做即可恢复，因此兼顾持久性与性能。

PostgreSQL 磁盘被 WAL 撑满，如何排查？

先看 pg_replication_slots：不活跃或落后的复制槽会阻止 WAL 回收；再看归档是否失败（archive_command 报错会导致 WAL 堆积）；最后检查 max_wal_size 与检查点设置。处理后补上监控与槽保留上限。

WAL 与 CDC 是什么关系？

WAL 记录了所有已提交的修改。PostgreSQL 在 wal_level=logical 时可通过逻辑解码把 WAL 转成行级变更事件，Debezium 等工具基于复制槽读取，实现不侵入业务代码的变更数据捕获。复制槽也意味着消费者停摆时 WAL 会堆积。
