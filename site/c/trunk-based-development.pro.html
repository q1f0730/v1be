主干开发 (Trunk-Based)

Trunk-Based Development

📐 01 · 定义

主干开发（Trunk-Based Development）是一种版本控制分支策略：开发者把小批量改动频繁合入单一主干（main/trunk），功能分支寿命通常不超过一两天，未完成功能通过功能开关隐藏，主干始终保持可发布。它属于工程流程与持续集成层，是持续交付的前提，DORA 研究将其列为与高交付效能相关的能力之一。

⚙️ 02 · 原理
  1. 1

    开发者从主干拉出短命分支（或直接在主干提交），只包含一个小的、可独立集成的改动。

  2. 2

    提交前在本地和 CI 中运行快速测试；PR 小、评审快，当天合并。

  3. 3

    未完成功能用功能开关（feature flag）或抽象分支（branch by abstraction）隐藏，代码合入但不对用户生效。

  4. 4

    每次合并触发 CI 构建与测试，主干一旦失败优先修复或回滚。

  5. 5

    发布从主干直接部署，或按需切出短期发布分支，只做必要的修复挑拣（cherry-pick）。

🔤 03 · 术语
主干 (Trunk)
团队共享的唯一长期分支，如 main。
短命分支 (Short-lived Branch)
存在时间通常不超过一两天的功能分支。
功能开关 (Feature Flag)
运行时开关，使未完成代码合入但不生效。
抽象分支 (Branch by Abstraction)
先引入抽象层，在主干上逐步替换实现的大改方法。
GitFlow
使用 develop、feature、release、hotfix 等长期分支的模型，与主干开发相对。
💻 04 · 代码
功能开关隐藏未完成功能typescript
// 新结算流程还没做完，但代码每天合入 main
import { isEnabled } from "./flags";

export function CheckoutPage({ user }: { user: { id: string } }) {
  // 开关默认关闭；内部员工可先打开测试
  if (isEnabled("new-checkout", user)) {
    return <NewCheckout />;      // 半成品，只对白名单可见
  }
  return <LegacyCheckout />;     // 线上用户仍走旧流程
}

// flags.ts：最简单的实现，可替换为 LaunchDarkly、Unleash 等
const internal = new Set(["u_001", "u_002"]);
export function isEnabled(flag: string, user: { id: string }) {
  if (flag === "new-checkout") return internal.has(user.id);
  return false;
}

代码先合入主干但默认不生效；功能完成并验证后移除开关与旧代码。

⚖️ 06 · 方案取舍

主干开发

优点冲突少、反馈快、随时可发布

代价依赖完善测试与功能开关纪律

适用CI 成熟、部署频繁的团队

长期功能分支

优点隔离开发，主干不受未完成代码影响

代价合并地狱、集成风险后置

适用实验性、可能被放弃的大改动

GitFlow

优点版本边界清晰

代价流程重，分支多，交付慢

适用需维护多个已发布版本

🕳️ 07 · 常见坑

  • ✗名义上主干开发，分支却活一两周

    ✓设置分支寿命目标，把功能拆成可独立合并的小步

  • ✗功能开关用完不删，代码里堆满死分支

    ✓开关设负责人与到期日，发布稳定后清理

  • ✗测试慢且不稳定，主干经常红

    ✓保证快速可靠的 CI，主干失败时停止合并优先修复

  • ✗把大重构一次性合进主干

    ✓用抽象分支或并行实现逐步替换

🎤 09 · 面试追问
主干开发如何保证主干稳定？

依靠小批量改动、合并前自动化测试、快速代码评审、功能开关隐藏未完成功能，以及主干失败时的停线修复文化。必要时用合并队列（merge queue）确保合入的组合也通过测试。

功能开关会带来哪些问题？

开关组合导致测试路径增加；长期不清理形成技术债；开关配置错误可能误放功能。需给开关分类（发布、实验、运维），设置负责人与到期日并定期清理。

AI 编码 Agent 和主干开发如何配合？

Agent 适合产出小而独立的改动；每个任务一个短命分支与小 PR，让 CI 和人工评审快速通过。避免让 Agent 长时间在大分支上累积大量改动，否则合并冲突与评审成本陡增。
