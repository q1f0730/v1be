事件驱动架构 (EDA)

Event-Driven Architecture

📐 01 · 定义

事件驱动架构（Event-Driven Architecture，EDA）是以“事件”——系统中已发生的、不可变的事实（如订单已创建）——作为服务间通信核心的架构风格。生产者发布事件而不关心谁消费，消费者通过消息代理订阅并异步处理。它降低服务间的时间与依赖耦合，便于扩展新功能，但带来最终一致性、调试难度和消息语义等挑战。

⚙️ 02 · 原理
  1. 1

    识别领域事件：以过去式命名的业务事实，如 OrderPlaced、PaymentFailed，定义其 schema 与版本。

  2. 2

    生产者在完成本地状态变更后发布事件；为保证状态与事件一致，常用事务性发件箱（Outbox）模式。

  3. 3

    消息代理（Kafka、RabbitMQ、云事件总线等）持久化并路由事件，支持多个消费者独立订阅。

  4. 4

    消费者异步处理事件并更新自身状态；由于通常是至少一次投递，消费者必须幂等。

  5. 5

    复杂业务流程可采用编舞（服务互相响应事件）或编排（中心协调者驱动步骤，如 Saga 编排器）。

🔤 03 · 术语
领域事件 (Domain Event)
业务中已发生的事实，不可变，以过去式命名。
事件通知 (Event Notification)
事件只携带标识，消费者需回查详情。
事件携带状态转移 (Event-Carried State Transfer)
事件包含足够数据，消费者无需回查生产者。
编舞 vs 编排 (Choreography vs Orchestration)
去中心化响应事件 vs 由协调者统一驱动流程。
幂等消费者 (Idempotent Consumer)
重复处理同一事件不会产生额外副作用。
CloudEvents
CNCF 的事件元数据格式规范，统一事件描述。
💻 04 · 代码
Redis Streams 发布与幂等消费python
import json, redis

r = redis.Redis(decode_responses=True)
STREAM, GROUP = "orders.events", "sms-service"

# 生产者：订单写库成功后发布事件（生产中用 Outbox 保证一致）
r.xadd(STREAM, {"type": "OrderPlaced", "id": "evt-1001",
                "data": json.dumps({"order_id": 42, "phone": "138****0000"})})

# 消费者组：每个服务一个组，组内多个实例分摊消息
try:
    r.xgroup_create(STREAM, GROUP, id="0", mkstream=True)
except redis.ResponseError:
    pass  # 组已存在

resp = r.xreadgroup(GROUP, "worker-1", {STREAM: ">"}, count=10, block=5000)
for _, messages in resp or []:
    for msg_id, fields in messages:
        # 幂等：用事件 ID 去重，SET NX 成功才处理
        if r.set(f"done:{GROUP}:{fields['id']}", 1, nx=True, ex=86400):
            print("发送短信", json.loads(fields["data"]))
        r.xack(STREAM, GROUP, msg_id)   # 处理完确认

每个服务独立消费组订阅同一事件流；事件 ID 去重保证至少一次投递下的幂等。

📊 05 · 参数对比

同步调用 vs 事件驱动

维度同步请求/响应事件驱动
耦合调用方需知道被调方及其可用性生产者不知道消费者
一致性易实现强一致通常为最终一致
故障影响下游故障直接传导代理缓冲，下游可稍后处理
可观测性调用链直观需追踪 ID 串联事件流
扩展新功能修改调用方新增订阅者
⚖️ 06 · 方案取舍

编舞（纯事件响应）

优点高度解耦，易扩展

代价全局流程不可见，难排查

适用步骤少、团队自治

编排（中心协调者）

优点流程清晰，便于补偿与监控

代价协调者成为耦合点

适用多步骤事务，如 Saga

同步 API 调用

优点简单直观，强一致

代价耦合高，级联故障风险

适用需要立即结果的查询

🕳️ 07 · 常见坑

  • ✗先发事件再写数据库，或反之，二者不在同一事务

    ✓使用 Outbox 模式或 CDC，保证状态与事件一致

  • ✗消费者不幂等，重复投递导致重复扣款

    ✓以事件 ID 去重，或让操作天然幂等

  • ✗事件 schema 随意修改，下游解析失败

    ✓为事件定义版本与兼容规则，使用 schema 注册中心

  • ✗把命令伪装成事件，如“SendEmail”

    ✓事件描述已发生事实，命令定向请求应使用队列或 API

☑️ 08 · 检查清单
🎤 09 · 面试追问
事件和命令有什么区别？

事件是已发生的事实，用过去式命名，发布者不关心谁处理、处理与否，可以有零到多个消费者；命令是请求某个特定接收者执行动作，期望被处理，通常只有一个处理者。混淆二者会导致隐性耦合。

如何保证数据库写入和事件发布的一致性？

直接“写库后发消息”存在双写问题：写库成功而发消息失败会丢事件。常用事务性 Outbox：在同一数据库事务中写业务数据和待发事件表，再由中继进程或 CDC 把事件可靠投递到消息代理。

事件驱动系统如何调试和观测？

为每个事件附带关联 ID 与追踪上下文，在生产、代理、消费各环节记录；使用分布式追踪串联异步链路；监控消费延迟、积压和死信数量；保留事件日志以便重放和排查。
