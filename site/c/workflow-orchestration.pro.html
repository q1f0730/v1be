数据任务编排 (Airflow / Dagster)

Workflow Orchestration

📐 01 · 定义

工作流编排（Workflow Orchestration）指用调度系统按依赖关系、时间表和重试策略自动执行一组任务，属于数据平台的控制层。它把「先抽数、再转换、再出报表」这类流程建模为 DAG（有向无环图），提供调度、依赖管理、重试、回填、告警与可观测性。代表工具有 Apache Airflow、Dagster、Prefect。

⚙️ 02 · 原理
  1. 1

    开发者用代码定义 DAG：节点是任务或数据资产，边是依赖关系，同时声明调度周期。

  2. 2

    调度器（Scheduler）按时间表或上游事件创建一次运行（run），判断哪些任务的依赖已满足。

  3. 3

    就绪任务被交给执行器（Executor）分发到 worker、容器或 K8s Pod 中运行。

  4. 4

    任务失败按配置重试，超过次数则标记失败、阻塞下游并触发告警。

  5. 5

    元数据库记录每次运行的状态与日志，支持重跑失败节点和对历史区间回填（backfill）。

🔤 03 · 术语
DAG (Directed Acyclic Graph)
有向无环图，表示任务间依赖且不允许循环。
回填 (Backfill)
对过去一段时间区间补跑任务，常用于修复或新上线。
幂等任务 (Idempotent Task)
同一输入重复执行结果一致，是安全重试的前提。
软件定义资产 (Software-defined Asset)
Dagster 的建模方式，以产出的数据表为中心而非任务。
传感器 (Sensor)
轮询外部条件（文件到达、表更新）满足后触发运行。
💻 04 · 代码
Airflow TaskFlow 定义 DAGpython
from datetime import datetime, timedelta
from airflow.sdk import dag, task  # Airflow 3；2.x 用 airflow.decorators

@dag(schedule="@daily", start_date=datetime(2026, 1, 1),
     catchup=False,
     default_args={"retries": 2, "retry_delay": timedelta(minutes=5)})
def daily_report():
    @task
    def extract() -> list[dict]:
        return [{"sku": "A100", "amount": 99}]  # 实际中从 API/数据库读取

    @task
    def transform(rows: list[dict]) -> float:
        return sum(r["amount"] for r in rows)

    @task
    def load(total: float):
        print(f"GMV = {total}")  # 实际中写入数仓

    load(transform(extract()))  # 函数调用关系即依赖

daily_report()

函数间传参自动形成 extract→transform→load 依赖；失败重试 2 次，间隔 5 分钟。

主流编排工具对比

工具建模核心特点
Apache Airflow任务 (Task) DAG历史最久、插件与社区最多

⚖️ 06 · 方案取舍

cron + 脚本

优点零依赖、最简单

代价无依赖管理、失败无感知

适用单个独立小任务

Airflow

优点生态成熟、托管服务多

代价调度器较重，本地开发体验一般

适用任务多、团队已有经验

Dagster

优点以资产为中心，血缘清晰

代价概念较多，需要学习

适用新建数据平台、重视数据质量

持久化执行框架（如 Temporal）

优点长流程状态可靠恢复

代价偏应用工作流，不专为数据设计

适用业务流程编排

🕳️ 07 · 常见坑

  • ✗任务非幂等，重试导致数据重复写入

    ✓按分区覆盖写或 MERGE，用运行日期作为参数

  • ✗在 DAG 顶层代码里查数据库或调 API

    ✓调度器会反复解析 DAG 文件；重操作放进任务内部

  • ✗任务内部用 now() 取时间，回填结果错乱

    ✓使用调度传入的逻辑日期/数据区间

  • ✗通过 XCom 等机制传大数据集

    ✓只传引用（路径、表名），数据放对象存储或数仓

🎤 09 · 面试追问
为什么编排任务必须设计为幂等？

重试、回填、手动重跑都会让同一任务对同一区间执行多次；非幂等写入会重复或丢失数据。常用按分区 overwrite、MERGE upsert，以逻辑日期为键。

Airflow 的 logical date 和实际运行时间有何不同？

logical date 表示这次运行负责的数据区间起点；按日调度通常在区间结束后才运行，所以实际执行时间晚于它。任务应据数据区间取数，回填才正确。

任务编排和持久化执行（durable execution）的区别？

前者以定时批处理 DAG 为主，关注调度、回填与数据依赖；后者把任意长时业务流程的状态持久化，崩溃后从断点继续，适合订单、审批等应用工作流。
