📐 01 · 定义

Token（词元）是 LLM 处理文本的基本单位，由分词器（Tokenizer）把文本切成子词片段并映射为整数 ID。它同时决定三件事：模型实际「看到」的输入、上下文窗口的占用量、API 计费数量。不同模型的分词器不同，同一段文字的 Token 数也不同。

⚙️ 02 · 原理
  1. 1

    训练分词器：用 BPE 等算法在语料上统计高频字节/字符组合，生成固定大小的词表。

  2. 2

    切分：推理时把输入文本按词表贪心合并成子词序列，常见英文单词可能是 1 个 Token。

  3. 3

    映射：每个 Token 对应一个整数 ID，再查表得到向量送入模型。

  4. 4

    生成：模型每一步输出一个 Token ID，解码器把 ID 拼回文本流式返回。

  5. 5

    计量：服务端分别统计输入 Token 与输出 Token，作为上下文占用和计费依据。

🔤 03 · 术语
分词器 (Tokenizer)
把文本与 Token ID 互相转换的组件，与模型绑定，不能混用。
BPE (Byte Pair Encoding)
反复合并最高频相邻符号对来构建子词词表的算法。
词表 (Vocabulary)
分词器能产生的全部 Token 集合，规模常见为数万到二十多万。
输入/输出 Token
提示词与模型回复分开计数，输出单价通常高于输入。
特殊 Token (Special Token)
标记消息边界、角色或结束的保留符号，不对应普通文字。
💻 04 · 代码
本地数 Tokenpython
# pip install tiktoken  （OpenAI 开源的分词库）
import tiktoken

# o200k_base 是 GPT-4o 系列使用的编码；cl100k_base 用于 GPT-4/3.5
enc = tiktoken.get_encoding("o200k_base")

for text in ["Hello, world!", "你好，世界！", "def add(a, b): return a + b"]:
    ids = enc.encode(text)                  # 文本 -> Token ID 列表
    pieces = [enc.decode([i]) for i in ids] # 每个 ID 还原成的片段
    print(len(ids), pieces)

# 注意：Claude 等其他模型分词器不同，
# 精确计数请用各家官方的计数接口，例如
# anthropic: client.messages.count_tokens(model=..., messages=[...])

同一段话换模型 Token 数就变；本地估算用于预算，精确值以供应商接口为准。

⚖️ 06 · 方案取舍

本地分词库估算

优点零成本、离线、快

代价与目标模型分词器可能不一致

适用粗略预算、批量预检

官方计数接口

优点与计费口径一致

代价多一次网络请求

适用需要精确控制上下文或成本时

读取响应 usage 字段

优点真实发生值，无额外开销

代价只能事后得知

适用成本监控与对账

🕳️ 07 · 常见坑

  • ✗用「1 个汉字 = 1 个 Token」之类固定比例算预算

    ✓比例随模型和文本变化，用目标模型的分词器或计数接口实测

  • ✗只算用户输入，忘了系统提示、工具定义和历史

    ✓以 usage.input_tokens 为准，把所有隐藏输入都计入

  • ✗用 A 模型的分词器给 B 模型截断文本

    ✓截断与计数使用同一模型的分词方案，并预留余量

🎤 09 · 面试追问
为什么用子词而不是按字或按词切分？

按词切词表会巨大且无法处理新词；按字符切序列太长、效率低。子词（BPE 等）在两者间折中：高频词整体保留、罕见词拆成片段，词表可控，又基本不会出现未登录词。字节级 BPE 还能覆盖任意 Unicode。

Agent 场景 Token 消耗为何远超聊天？

Agent 多轮调用工具，每轮都把系统提示、工具定义、完整历史和工具返回（如文件内容、命令输出）重新发送，输入随轮数累积增长。优化：提示缓存、裁剪工具输出、子任务隔离上下文、定期压缩历史。

如何控制一个功能的 Token 成本？

先测基线：记录每请求输入/输出 Token；再优化：精简提示、检索只取相关片段、缓存可复用前缀、限制输出长度、简单任务路由到小模型；最后加预算告警和单用户限额。
