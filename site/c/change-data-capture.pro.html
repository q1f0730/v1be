变更数据捕获 (CDC)

Change Data Capture

📐 01 · 定义

变更数据捕获（CDC）是从源数据库持续捕获行级插入、更新、删除事件，并以有序事件流的形式发送给下游系统的技术。主流方式是读取数据库的事务日志（如 PostgreSQL WAL、MySQL binlog），用于数据同步到搜索引擎、数仓、缓存失效和微服务间事件传递。

⚙️ 02 · 原理
  1. 1

    开启日志：数据库配置为输出足够信息，如 PostgreSQL wal_level=logical，MySQL binlog 行格式。

  2. 2

    初始快照：连接器首次启动时对现有数据做一致性快照，记录对应的日志位点。

  3. 3

    流式读取：之后从该位点持续读取事务日志，解析成包含前后镜像的变更事件。

  4. 4

    发布事件：按表或主键把事件写入 Kafka 等消息系统，保持同一主键的顺序。

  5. 5

    位点管理：定期提交已处理的日志位点（如复制槽 LSN），故障重启后从位点续传。

🔤 03 · 术语
WAL / binlog
数据库的事务日志，记录所有已提交的数据变更。
逻辑解码 (Logical Decoding)
PostgreSQL 把 WAL 解析成行级逻辑变更的机制。
复制槽 (Replication Slot)
记录消费位点的服务端对象，保证所需 WAL 不被删除。
LSN (Log Sequence Number)
WAL 中的位置编号，用于标识消费进度。
Debezium
基于 Kafka Connect 的开源 CDC 平台，支持多种数据库。

  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",

    "database.hostname": "pg.internal",
    "database.port": "5432",

    "database.dbname": "shop",
    "topic.prefix": "shop",
    "table.include.list": "public.orders,public.order_items",
    "slot.name": "debezium_orders"
  }
}

提交到 Kafka Connect 后，变更写入 shop.public.orders 等主题；密码用配置提供器引用。

📊 05 · 参数对比

CDC 实现方式对比

方式原理局限
基于日志读取 WAL/binlog需数据库权限与配置，运维复杂
基于查询轮询按 updated_at 定期查询捕获不到删除，有延迟和负载
基于触发器触发器写变更表增加写入开销，侵入业务库
应用双写代码同时写库和发消息无法保证原子性，易不一致
⚖️ 06 · 方案取舍

日志 CDC（Debezium）

优点捕获全部变更含删除，低侵入

代价需维护连接器和复制槽

适用数据同步、事件驱动集成

轮询 updated_at

优点实现简单，无需特殊权限

代价漏删除，难做到实时

适用小规模、可容忍延迟

Outbox + CDC

优点发布领域事件而非表结构变更

代价需要业务写 outbox 表

适用微服务对外发布事件

🕳️ 07 · 常见坑

  • ✗连接器停了很久，复制槽滞留导致 WAL 堆积撑满磁盘

    ✓监控复制槽延迟和 WAL 大小，设置 max_slot_wal_keep_size 等上限

  • ✗下游直接依赖源表结构，源库改表即下游崩

    ✓对外发布稳定的事件契约，或使用 Outbox 模式与 Schema Registry

  • ✗假设事件只投递一次，下游非幂等

    ✓按主键和 LSN 做幂等写入，容忍重复事件

🎤 09 · 面试追问
为什么基于日志的 CDC 优于轮询？

日志包含所有已提交变更（含删除和中间状态），按提交顺序排列，延迟低，且不对业务表发额外查询；轮询依赖 updated_at，捕获不到物理删除，可能漏掉同一周期内的多次变更。

CDC 能保证 exactly-once 吗？

通常是至少一次：连接器在提交位点前崩溃会重放部分事件。端到端精确一次需下游幂等或事务性写入配合。设计上应假设会收到重复事件，用主键加版本或 LSN 去重。

PostgreSQL 复制槽有什么风险？

复制槽会阻止服务端删除消费者尚未确认的 WAL，消费者停止后 WAL 持续累积可能撑满磁盘，还会拖住 VACUUM 清理边界。需监控槽延迟、及时删除废弃槽并设置 WAL 保留上限。
