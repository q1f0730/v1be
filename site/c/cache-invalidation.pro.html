缓存失效与更新策略

Cache Invalidation

📐 01 · 定义

缓存失效（Cache Invalidation）指在源数据变化后，让缓存中的旧副本被删除、更新或过期，使读者不会长期看到过时数据。它涉及失效时机、并发竞态和雪崩防护，被戏称为计算机科学两大难题之一。常见策略包括 TTL 过期、写后删除、版本化键和事件驱动失效。

⚙️ 02 · 原理
  1. 1

    旁路缓存（cache-aside）读：先查缓存，未命中则读数据库并回填缓存，设置 TTL。

  2. 2

    写路径：先提交数据库更新，再删除对应缓存键，让下次读取回填新值。

  3. 3

    TTL 作为兜底：即使删除失败或漏删，旧值也会在有限时间后自动过期。

  4. 4

    版本化键：把版本号或内容哈希放进键名，数据变更即换新键，旧键自然淘汰。

  5. 5

    事件驱动：通过 CDC 或消息监听数据变更，统一触发多处缓存与 CDN 失效。

🔤 03 · 术语
旁路缓存 (Cache-aside)
应用自行读写缓存，未命中时回源并回填。
TTL
缓存条目的存活时间，到期自动失效。
缓存击穿 (Cache Stampede)
热点键失效瞬间大量请求同时回源。
单飞 (Single-flight)
同一键并发未命中时只让一个请求回源。
延迟双删 (Delayed Double Delete)
写后删除，延迟片刻再删一次，缓解竞态。
租约 (Lease)
Facebook memcache 方案，防止旧值回填覆盖。
💻 04 · 代码
旁路缓存与写后删除python
import json, random, time, redis

r = redis.Redis()
BASE_TTL = 300

def get_user(uid: int) -> dict:
    key = f"user:{uid}"
    if (cached := r.get(key)) is not None:
        return json.loads(cached)
    # 单飞：只有拿到锁的请求回源，其余短暂等待后重读缓存
    if r.set(f"lock:{key}", 1, nx=True, ex=5):
        user = db_get_user(uid)
        # TTL 加随机抖动，避免大量键同一时刻过期
        r.set(key, json.dumps(user), ex=BASE_TTL + random.randint(0, 60))
        r.delete(f"lock:{key}")
        return user
    time.sleep(0.05)
    return get_user(uid)

def update_user(uid: int, fields: dict) -> None:
    db_update_user(uid, fields)     # 1. 先提交数据库事务
    r.delete(f"user:{uid}")         # 2. 再删除缓存（删除而非写入新值）

写后删除加 TTL 兜底；锁实现单飞防击穿。db_* 为业务自定义的数据库函数。

📊 05 · 参数对比

失效策略对比

策略一致性复杂度适用
仅 TTL最多旧 TTL 时长低可容忍旧数据的内容
写后删除 + TTL短暂不一致中大多数业务数据
版本化键强（换键即新）中静态资源、配置
CDC 事件失效秒级最终一致高多服务、多级缓存
⚖️ 06 · 方案取舍

写后删除缓存

优点简单，避免并发写入旧值

代价删除后首次读要回源

适用通用默认做法

写后更新缓存

优点读始终命中

代价并发写可能乱序覆盖成旧值

适用单写者、更新有序时

短 TTL 不主动失效

优点无失效逻辑

代价命中率与新鲜度只能折中

适用数据源不可监听

🕳️ 07 · 常见坑

  • ✗先删缓存再写库，并发读把旧值回填

    ✓先写库再删缓存，必要时延迟双删

  • ✗热点键过期瞬间数据库被打爆

    ✓单飞锁、提前刷新或逻辑过期

  • ✗只删了详情缓存，列表与聚合缓存仍是旧的

    ✓梳理数据到缓存键的依赖映射，统一失效

  • ✗缓存删除失败被静默忽略

    ✓删除失败重试或入队补偿，并保留 TTL 兜底

☑️ 08 · 检查清单
🎤 09 · 面试追问
为什么推荐删除缓存而不是更新缓存？

两个并发写可能以不同顺序更新数据库与缓存，导致缓存停留在旧值；删除操作是幂等的，下次读取从数据库回填最新值。更新缓存还会为可能无人读取的数据付出序列化成本。

先写库后删缓存还会不一致吗？

会，但窗口很小：读请求未命中、读到旧值，此时写请求更新库并删缓存，随后读请求才把旧值写入缓存。可用 TTL 兜底、延迟双删，或 Facebook memcache 论文中的租约机制避免旧值回填。

缓存击穿、穿透、雪崩如何区分与应对？

击穿：单个热点键失效，用单飞锁或提前刷新。穿透：查询不存在的数据每次都回源，缓存空值或用布隆过滤器。雪崩：大量键同时过期或缓存宕机，用 TTL 抖动、多级缓存和限流降级。
