eBPF 内核可编程

eBPF

📐 01 · 定义

eBPF（extended Berkeley Packet Filter）是 Linux 内核中的沙箱化虚拟机，可在不改内核源码、不加载内核模块的前提下，把经过验证的小程序挂到内核或用户态事件上运行。它位于内核层，广泛用于可观测性、网络数据面和运行时安全，是 Cilium、Falco、bpftrace 等工具的基石。

⚙️ 02 · 原理
  1. 1

    用受限 C 或 bpftrace 等高级语言编写程序，由 Clang/LLVM 编译为 eBPF 字节码。

  2. 2

    用户态加载器通过 bpf() 系统调用提交字节码，并声明程序类型（kprobe、tracepoint、XDP、tc、LSM 等）。

  3. 3

    验证器（Verifier）静态分析所有路径：确保会终止、内存访问有界、只调用允许的辅助函数，否则拒绝加载。

  4. 4

    通过验证的字节码由 JIT 编译为本机指令，挂载到对应钩子，事件发生时在内核上下文执行。

  5. 5

    程序通过 Map（哈希表、数组、环形缓冲区等）存取状态，并与用户态程序交换数据。

  6. 6

    借助 BTF 与 CO-RE（一次编译，到处运行），同一份程序可适配不同内核版本的结构体布局。

🔤 03 · 术语
验证器 (Verifier)
加载前对 eBPF 程序做静态检查的内核组件，保证安全与终止。
BPF Map
内核中的键值存储，供 eBPF 程序保存状态并与用户态共享数据。
kprobe / uprobe
动态挂载到内核函数或用户态函数入口/返回处的探针，接口不稳定。
跟踪点 (Tracepoint)
内核预定义的静态探测点，接口比 kprobe 更稳定。
XDP (eXpress Data Path)
在网卡驱动收包最早阶段运行 eBPF，用于高性能过滤与转发。
CO-RE / BTF
借助内核类型信息 BTF 在加载时重定位字段，实现跨内核版本运行。
💻 04 · 代码
bpftrace 排查常用命令bash
# 需要 root；内核需开启 BPF，建议带 BTF（存在 /sys/kernel/btf/vmlinux）
ls /sys/kernel/btf/vmlinux

# 列出可用的系统调用跟踪点
sudo bpftrace -l 'tracepoint:syscalls:sys_enter_open*'

# 统计哪些进程在发起 TCP 主动连接（Ctrl-C 结束后打印）
sudo bpftrace -e 'kprobe:tcp_connect { @[comm] = count(); }'

# 实时打印进程打开的文件
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat {
  printf("%-16s %s\n", comm, str(args.filename));
}'

# 查看当前已加载的 eBPF 程序
sudo bpftool prog list

无需改应用即可观测；较老 bpftrace 版本中 args.filename 需写成 args->filename。

⚖️ 06 · 方案取舍

现成工具 (bpftrace/BCC/Cilium)

优点上手快，覆盖常见场景，社区维护

代价定制能力有限，部分工具依赖内核头或编译器

适用排障、监控和标准网络策略

自研 libbpf + CO-RE 程序

优点开销低、可深度定制、可分发单一二进制

代价受验证器限制，开发调试门槛高

适用产品化的观测或安全 Agent

应用内埋点 (OpenTelemetry)

优点有业务语义，跨平台，不需特权

代价要改代码和重新发布

适用需要业务级链路追踪与指标

🕳️ 07 · 常见坑

  • ✗依赖 kprobe 挂载的内核函数，升级内核后失效

    ✓优先使用 tracepoint 或稳定钩子，并在目标内核版本矩阵上测试

  • ✗在高频事件上做大量 printf 输出

    ✓在内核侧用 Map 聚合，只向用户态输出汇总或采样结果

  • ✗在容器里随意授予 privileged 运行 eBPF 工具

    ✓按需授予 CAP_BPF、CAP_PERFMON 等最小能力，并审计加载的程序

  • ✗以为 eBPF 能看到 TLS 明文流量

    ✓内核网络层只见密文，需 uprobe 挂到 TLS 库函数上才能取明文

🎤 09 · 面试追问
eBPF 如何保证不把内核搞崩？

核心是验证器：加载前遍历所有执行路径，检查有界循环与终止、寄存器与指针类型、内存访问边界、栈大小和可调用的辅助函数，任何不安全路径都拒绝加载。程序只能通过辅助函数和 Map 与内核交互，再加上加载需要特权能力。

kprobe 和 tracepoint 怎么选？

tracepoint 是内核维护者定义的静态探测点，参数格式相对稳定，开销较低，适合长期运行的工具；kprobe 可挂到几乎任意内核函数，灵活但依赖内部实现，函数被内联或改名就失效，适合临时排障。生产工具优先 tracepoint，缺口再用 kprobe。

eBPF 可观测性与 Service Mesh Sidecar 比优势在哪？

eBPF 在内核层采集，对应用透明，无需每个 Pod 注入 Sidecar 代理，减少额外的网络跳数与资源开销。代价是缺乏应用层语义（如 TLS 内的 HTTP 细节需额外 uprobe），且依赖内核版本和特权部署。Cilium 等项目正是用它替代部分 Sidecar 功能。
