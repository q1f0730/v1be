事务四大基石特性

ACID

📐 01 · 定义

ACID 是数据库事务的四项保证：原子性（Atomicity）、一致性（Consistency）、隔离性（Isolation）、持久性（Durability）。它定义了一组读写操作作为整体执行时数据库应提供的行为，是关系型数据库区别于很多早期 NoSQL 的核心能力，也是业务正确性的基础。

⚙️ 02 · 原理
  1. 1

    原子性：事务内的修改要么全部生效要么全部撤销，引擎借助日志在失败时回滚。

  2. 2

    一致性：事务前后数据满足约束（主键、外键、CHECK）与业务不变式，后者需应用配合保证。

  3. 3

    隔离性：并发事务互不干扰的程度，由锁或 MVCC 实现，强弱由隔离级别决定。

  4. 4

    持久性：提交成功后即使崩溃也不丢失，通常靠预写日志（WAL）在提交时刷盘。

  5. 5

    崩溃恢复时，引擎重放已提交事务的日志、撤销未提交的修改，恢复到一致状态。

🔤 03 · 术语
预写日志 (WAL)
先把变更写入日志并落盘，再修改数据页。
MVCC
多版本并发控制，读不阻塞写，各事务看到自己的快照。
保存点 (Savepoint)
事务内的回滚点，可只撤销部分操作。
不变式 (Invariant)
任何时刻都必须成立的业务规则，如余额不为负。
fsync
要求操作系统把数据真正写到持久存储的系统调用。
BASE
基本可用、软状态、最终一致，常与 ACID 对照的设计取向。
💻 04 · 代码
转账事务与约束sql
-- 一致性的一部分交给约束：余额不能为负
CREATE TABLE accounts (
  id      int PRIMARY KEY,
  balance numeric(12,2) NOT NULL CHECK (balance >= 0)
);
INSERT INTO accounts VALUES (1, 100), (2, 0);

-- 原子性：两条更新作为整体
BEGIN;
UPDATE accounts SET balance = balance - 150 WHERE id = 1;  -- 违反 CHECK，报错
UPDATE accounts SET balance = balance + 150 WHERE id = 2;
COMMIT;  -- PostgreSQL 中事务已处于失败状态，COMMIT 实际执行回滚

-- 保存点：只撤销事务中的一部分
BEGIN;
UPDATE accounts SET balance = balance - 30 WHERE id = 1;
SAVEPOINT before_bonus;
UPDATE accounts SET balance = balance + 999 WHERE id = 2;
ROLLBACK TO SAVEPOINT before_bonus;  -- 撤销加 999
UPDATE accounts SET balance = balance + 30 WHERE id = 2;
COMMIT;

SELECT * FROM accounts;  -- 1: 70, 2: 30

约束保证不变式，事务保证整体生效；保存点可局部回滚。以 PostgreSQL 为例。

📊 05 · 参数对比

四项特性的实现机制

特性典型机制可调项/注意
原子性WAL / undo 日志长事务回滚代价高
一致性约束 + 应用逻辑约束外的规则靠代码保证
隔离性MVCC、锁由隔离级别决定强弱
持久性提交时 WAL 刷盘如 synchronous_commit 可换性能
⚖️ 06 · 方案取舍

严格 ACID 单库事务

优点正确性推理简单

代价扩展受单机或单分片限制

适用订单、支付、库存等核心数据

放宽持久性（异步提交）

优点写入延迟显著下降

代价崩溃可能丢最近少量已确认事务

适用日志、埋点等可丢数据

跨服务 Saga

优点支持微服务各自独立存储

代价无全局隔离，需补偿逻辑

适用无法放进同一数据库时

🕳️ 07 · 常见坑

  • ✗以为 ACID 的一致性会自动保证所有业务规则

    ✓把关键规则落到约束，其余在事务内显式校验

  • ✗ORM 默认自动提交，多步操作没包事务

    ✓显式开启事务，确认框架的事务边界

  • ✗事务中调用外部 HTTP，长时间持锁

    ✓外部调用移出事务，或使用 outbox 模式

  • ✗以为默认隔离级别就能防所有并发异常

    ✓了解所用库默认级别，必要时加锁或升级

🎤 09 · 面试追问
ACID 中的 C 和 CAP 中的 C 一样吗？

不一样。ACID 的一致性指事务把数据从一个满足约束的状态带到另一个；CAP 的一致性指分布式系统中读到最新写入（线性一致）。很多人认为 ACID 的 C 更多由应用保证，引擎只提供约束工具。

数据库如何在崩溃后保证持久性和原子性？

提交时先确保 WAL 刷盘再返回成功。重启时从检查点开始重放日志，把已提交但未写入数据页的修改补上；未提交事务的修改被撤销或因 MVCC 不可见。

微服务里怎样获得类似事务的效果？

常用 Saga：把大事务拆成本地事务序列，每步有补偿操作；配合 outbox 模式保证本地写与消息发送原子；全程幂等。代价是中间状态对外可见，没有跨服务的隔离性。
