消息分区路由键

Partition Keys

📐 01 · 定义

消息分区路由键（Partition Key）是生产者为每条消息指定的键，消息系统据此计算哈希并决定写入哪个分区（或分片）。它同时决定了三件事：同一键内的消息顺序、各分区间的负载均衡程度，以及消费并行度的上限分布，是 Kafka、Kinesis 等流系统设计中最关键的选择之一。

⚙️ 02 · 原理
  1. 1

    生产者为消息设置键，通常是业务实体 ID，如订单号或用户 ID。

  2. 2

    分区器对键做哈希再对分区数取模；Kafka Java 客户端默认使用 murmur2。

  3. 3

    键为空时，Kafka 新版客户端用粘性分区器批量写入某分区，再轮换以均衡负载。

  4. 4

    保序：同一键总落在同一分区，因而同一实体的消息保持写入顺序。

  5. 5

    分区数变化会改变取模结果，同一键可能映射到新分区，破坏原有顺序与局部性。

🔤 03 · 术语
分区器 (Partitioner)
根据键计算目标分区的生产者组件，可自定义。
murmur2
Kafka Java 客户端默认用于键哈希的非加密哈希算法。
粘性分区器 (Sticky Partitioner)
无键消息先填满一个批次再换分区，提升批量效率。
键倾斜 (Key Skew)
少数键消息量极大，导致对应分区成为热点。
复合键 (Composite Key)
由多个字段拼接的键，用于提高基数或控制共置。
💻 04 · 代码
按订单号设置分区键python
from confluent_kafka import Producer

p = Producer({
    "bootstrap.servers": "kafka:9092",
    "enable.idempotence": True,
    # librdkafka 默认分区器是 consistent_random（CRC32）；
    # 若需与 Java 生产者对同一键落到相同分区，显式改用 murmur2_random
    "partitioner": "murmur2_random",
})

def send(order_id: str, event: bytes):
    # 同一 order_id → 同一分区 → 该订单事件保持顺序
    p.produce("order-events", key=order_id.encode(), value=event)

send("order-1001", b'{"type":"Created"}')
send("order-1001", b'{"type":"Paid"}')
p.flush()

跨语言生产者混用时，分区器不一致会让同一键落到不同分区，导致乱序。

📊 05 · 参数对比

分区键选择对比

键顺序保证负载风险
无键 (null)无分布均匀
用户/订单 ID同一实体内有序头部用户可能成热点
租户 ID同一租户内有序大租户倾斜明显
租户+实体复合键同一实体内有序分布较均匀
⚖️ 06 · 方案取舍

按实体 ID 作键

优点实体内有序，便于状态处理

代价热点实体导致分区倾斜

适用需要按实体有序的事件流

不设键

优点负载最均匀，吞吐最高

代价不保证任何顺序

适用日志、指标等无序数据

自定义分区器

优点可隔离大客户、控制共置

代价增加维护成本，易出错

适用有明确倾斜且需特殊路由

🕳️ 07 · 常见坑

  • ✗Python 与 Java 生产者混写同一主题，同键落不同分区

    ✓统一分区器，librdkafka 设置 partitioner=murmur2_random

  • ✗上线后随意增加分区数，同键映射改变导致短期乱序

    ✓初始预留足够分区，扩容前评估对顺序与状态的影响

  • ✗用国家、状态等低基数字段作键，少数分区过载

    ✓选高基数键或使用复合键打散

  • ✗大量消息带空字符串键，全部落入同一分区

    ✓区分空串与 null，无业务键时显式不设键

🎤 09 · 面试追问
分区键如何影响消费并行度？

并行度上限是分区数，但实际负载取决于键的分布：若流量集中在少数键，对应分区的消费者忙而其他空闲，加消费者也无效。因此键需高基数且分布均匀，热点键需单独处理。

为什么扩分区会破坏顺序？

默认分区算法是哈希对分区数取模，分区数改变后同一键可能映射到新分区；新分区的新消息可能先于旧分区里尚未消费的旧消息被处理，造成同一实体的事件乱序。

大客户占了一半流量，怎么设计键？

可把大客户键拆为复合键（客户 ID+子实体 ID）分散到多个分区，只保证子实体内有序；或为大客户设独立主题；也可自定义分区器给其分配专用分区。前提是业务能接受更细粒度的顺序。
