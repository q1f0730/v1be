列式存储 (Parquet)

Columnar Storage

📐 01 · 定义

列式存储（Columnar Storage）是一种数据物理布局：同一列的值连续存放，而不是同一行的所有列连续存放。它属于存储引擎与文件格式层，代表有 Apache Parquet、ORC 以及 ClickHouse 等数据库的存储引擎。分析查询只读涉及的列、同类型数据压缩率高，因此能大幅降低 I/O，是数仓与湖仓的基础。

⚙️ 02 · 原理
  1. 1

    表被切成行组（row group），每个行组内每列单独存为一个列块（column chunk）。

  2. 2

    列块内再分页，并按列类型使用字典编码、RLE、位压缩等编码，再叠加 Snappy/ZSTD 等压缩。

  3. 3

    文件尾部元数据记录每列块的 min/max 等统计信息，查询可据此跳过不满足条件的行组（谓词下推）。

  4. 4

    查询引擎只读取 SELECT 与 WHERE 用到的列（列裁剪），未用到的列完全不读。

  5. 5

    读出的列以批为单位进入向量化执行，最终在需要时再拼回行（延迟物化）。

🔤 03 · 术语
列裁剪 (Projection Pushdown)
只读取查询涉及的列，跳过其余列的数据。
谓词下推 (Predicate Pushdown)
利用统计信息在读取前过滤掉不可能命中的数据块。
行组 (Row Group)
Parquet 中按行水平切分的数据块，内部按列存放。
字典编码 (Dictionary Encoding)
把重复值替换成小整数编号，低基数列压缩效果好。
延迟物化 (Late Materialization)
先在列上过滤，最后才拼装需要输出的整行。
💻 04 · 代码
Parquet 列裁剪与过滤读取python
import pandas as pd
import pyarrow.parquet as pq

# CSV 转 Parquet（需安装 pyarrow），默认 snappy 压缩
df = pd.read_csv("events.csv")
df.to_parquet("events.parquet", index=False)

# 只读两列，并把过滤条件下推到文件层
table = pq.read_table(
    "events.parquet",
    columns=["user_id", "amount"],
    filters=[("amount", ">", 100)],
)
print(table.num_rows)

# 查看行组与每列的统计信息
meta = pq.ParquetFile("events.parquet").metadata
print(meta.num_row_groups, meta.row_group(0).column(0).statistics)

columns 实现列裁剪，filters 借助行组统计跳过数据块，两者共同减少 I/O。

⚖️ 06 · 方案取舍

Parquet 等列式文件

优点压缩率高、分析读取快、生态广

代价单行更新难，小文件多时性能差

适用批量分析、数据湖

行式数据库

优点单行读写快、事务完整

代价大聚合要读全行，I/O 浪费

适用在线业务

列式数据库（如 ClickHouse）

优点实时写入+快速聚合

代价更新删除代价较高，需额外运维

适用实时分析看板

🕳️ 07 · 常见坑

  • ✗把大量 KB 级小 Parquet 文件写入数据湖

    ✓合并为较大文件（常见做法是数百 MB 级），减少元数据与打开开销

  • ✗查询仍 SELECT *，列存优势全无

    ✓只选需要的列，让引擎做列裁剪

  • ✗排序/分区键选得与过滤条件无关

    ✓按常用过滤列排序或分区，统计信息才能有效跳过数据

  • ✗用列式格式承载高频单行更新

    ✓高频更新留在 OLTP；湖仓用 Iceberg/Delta 管理批量 upsert

🎤 09 · 面试追问
Parquet 如何实现谓词下推？

每个行组/页记录列的 min/max、空值数等统计；读取前引擎用 WHERE 条件与统计比较，区间不可能命中的行组直接跳过。数据按过滤列有序时效果最好。

为什么列存压缩率高于行存？

同列数据类型相同、取值相近，适合字典、RLE、增量等编码；行存把不同类型交错存放，通用压缩算法能找到的重复模式少得多，因此列存往往能省下数倍存储与 I/O。

列存写入为何偏向批量？

一行要拆写到多个列块，且编码与压缩以块为单位；逐行写会产生大量小块和小文件，所以通常先在内存缓冲再批量落盘；ClickHouse 等引擎还会在后台合并小数据块。
