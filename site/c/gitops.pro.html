基于Git的持续交付

GitOps

📐 01 · 定义

GitOps 是一种以 Git 仓库作为系统期望状态唯一可信来源的持续交付与运维方式：基础设施和应用以声明式配置存放在 Git 中，集群内的代理（如 Argo CD、Flux）持续拉取并把实际状态调和到与 Git 一致。变更通过 PR 完成，天然具备审计、评审和回滚能力。

⚙️ 02 · 原理
  1. 1

    声明期望状态：用 Kubernetes 清单、Helm 或 Kustomize 描述应用与环境的目标状态。

  2. 2

    版本化：所有配置存于 Git，通过 PR 评审合并，每次变更都有提交记录可追溯。

  3. 3

    拉取同步：集群内的 GitOps 控制器监听仓库，发现新提交后自动拉取。

  4. 4

    持续调和：控制器对比实际状态与期望状态，自动修正差异，包括手工改动产生的漂移。

  5. 5

    回滚：回滚即 git revert 到旧提交，控制器自动把集群同步回该版本。

🔤 03 · 术语
期望状态 (Desired State)
Git 中声明的系统应有状态。
调和 (Reconciliation)
持续对比并消除实际状态与期望状态差异的循环。
拉取模式 (Pull-based)
集群内代理主动拉取配置，无需对外暴露集群凭证。
自愈 (Self-heal)
自动撤销绕过 Git 的手工修改。
配置仓库 (Config Repo)
与应用代码分离、专门存放部署清单的仓库。
💻 04 · 代码
Argo CD Applicationyaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: shop-api
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/example/shop-deploy.git
    targetRevision: main
    path: apps/shop-api/overlays/prod     # Kustomize 目录
  destination:
    server: https://kubernetes.default.svc
    namespace: shop
  syncPolicy:
    automated:
      prune: true        # Git 中删除的资源也从集群删除
      selfHeal: true     # 集群被手工修改时自动改回
    syncOptions:
      - CreateNamespace=true

CI 只负责构建镜像并更新配置仓库中的镜像标签，部署由 Argo CD 拉取完成。

🕳️ 07 · 常见坑

  • ✗把明文 Secret 提交到配置仓库

    ✓使用 Sealed Secrets、SOPS 或外部密钥管理器同步

  • ✗仍有人直接 kubectl 改生产，被自愈覆盖后引发困惑

    ✓收紧集群写权限，所有变更走 PR

  • ✗镜像标签用 latest，Git 中看不出实际部署版本

    ✓使用不可变标签或摘要，由 CI 提交更新

  • ✗一个仓库目录结构混乱，多环境配置大量复制

    ✓用 Kustomize overlays 或 Helm values 分层管理环境

🎤 09 · 面试追问
GitOps 和普通 CI/CD 的核心区别？

核心是拉取与持续调和：普通 CD 由流水线一次性推送变更，之后不再关心集群状态；GitOps 控制器持续把集群对齐到 Git，能发现并修正漂移，且部署凭证不必交给外部 CI 系统。

GitOps 中如何管理密钥？

不在 Git 中存明文：可存加密后的 Secret（Sealed Secrets、SOPS），由集群内私钥解密；或在 Git 中只声明引用，由 External Secrets 等从云密钥管理服务同步。重点是密钥轮换和访问控制。

紧急故障时还要走 PR 吗？

原则上要，可设快速通道：精简评审、预先批准的回滚 PR。若必须手工干预，可临时暂停自动同步，修复后立即把改动补回 Git 并恢复同步，否则自愈会覆盖手工修改或留下漂移。
