向后兼容性

Backward Compatibility

🧸 回到小白版

📐 01 · 定义

向后兼容（Backward Compatibility）指系统的新版本仍能正确服务旧版本的客户端、数据或调用方式。它覆盖 API、数据库结构、消息格式、SDK 与配置等层面。在无法同时升级所有调用方的现实中（尤其是移动端与第三方集成），它是平滑演进与安全发布的前提。

⚙️ 02 · 原理
  1. 1

    明确契约：接口、字段、语义、错误码与默认行为都属于对外承诺。

  2. 2

    优先做增量变更：新增可选字段、新增端点，不删除、不改名、不改语义。

  3. 3

    调用方遵循宽容读取：忽略不认识的字段，对新增枚举值有默认处理。

  4. 4

    必须破坏时走版本化：新版本并行运行，旧版本标记弃用并公告下线时间。

  5. 5

    用契约测试与 schema 差异检查在 CI 中自动拦截破坏性变更。

🔤 03 · 术语
破坏性变更 (Breaking Change)
会让现有调用方出错或行为改变的修改。
向前兼容 (Forward Compatibility)
旧版本能处理新版本产生的数据。
宽容读取 (Tolerant Reader)
只读取需要的字段，忽略其余。
语义化版本 (SemVer)
主版本.次版本.修订号，主版本递增表示不兼容。
Sunset 头
RFC 8594 定义，告知资源预计停止服务的时间。
契约测试 (Contract Testing)
验证提供方是否满足消费方期望的测试。
💻 04 · 代码
OpenAPI 中的安全演进yaml
# openapi.yaml 片段：v1 接口的兼容性演进
paths:
  /v1/users/{id}:
    get:
      responses:
        "200":
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/User"
components:
  schemas:
    User:
      type: object
      required: [id, name]          # 不新增必填项，避免旧请求失败
      properties:
        id:   { type: string }
        name: { type: string }
        display_name:               # 新增可选字段：兼容
          type: string
        nickname:
          type: string
          deprecated: true          # 标记弃用，保留一段时间再移除
          description: 请改用 display_name
# 在 CI 中检查破坏性变更（oasdiff 工具）：
#   oasdiff breaking openapi-main.yaml openapi.yaml

只增不删、新字段可选、旧字段先弃用；用 schema 差异工具在合并前拦截。

📊 05 · 参数对比

常见变更的兼容性

变更对旧客户端建议做法
新增可选响应字段通常安全客户端需忽略未知字段
新增必填请求参数破坏改为可选并给默认值
删除或重命名字段破坏先新增、双写、弃用，再删除
新增枚举值可能破坏客户端对未知值有兜底分支
⚖️ 06 · 方案取舍

URL 版本（/v1、/v2）

优点直观，易路由和缓存

代价版本粒度粗，维护多套

适用公开 API 大版本演进

日期/头部版本（如 Stripe）

优点细粒度，按账户固定版本

代价实现复杂，需版本转换层

适用大型平台型 API

只做增量不分版本

优点最简单，无版本碎片

代价历史包袱累积

适用内部 API 或调用方可控

🕳️ 07 · 常见坑

  • ✗字段没删，但语义或单位悄悄变了

    ✓语义变化视同破坏性变更，用新字段表达

  • ✗后端先上线新必填字段，旧 App 全部报错

    ✓先发兼容后端，旧版本占比降下来后再收紧

  • ✗客户端遇到未知枚举值直接崩溃

    ✓所有枚举处理都有默认分支

  • ✗AI 重构时顺手改了接口字段名

    ✓提示中明确接口契约不可变，CI 做 schema 对比

🎤 09 · 面试追问
向后兼容和向前兼容的区别？

向后兼容：新系统能处理旧客户端/旧数据，例如新 API 接受旧请求。向前兼容：旧系统能处理新数据，例如旧客户端收到含新字段的响应不出错。滚动发布期间新旧版本共存，两者通常都需要。

如何安全地重命名一个 API 字段？

新增新字段并同时返回新旧两个；文档与响应中标记旧字段弃用（可配 Deprecation/Sunset 头）；监控仍读取旧字段的调用方并通知迁移；调用量归零或到期后再删除旧字段。

移动端为什么让兼容更难？

用户不一定升级，旧版本可能存活很久，服务端无法强制同步更新。需要长期支持多个客户端版本，按版本统计流量，必要时用最低版本强制升级机制，并让客户端对未知字段宽容。
